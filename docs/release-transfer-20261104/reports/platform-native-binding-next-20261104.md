## Выбранное решение

**Request-only diff не выполнять; отдельный4file ordinary bridge API slice тоже пока не выполнять.** Технически он жизнеспособен, но лишь подготовителен: может убрать whole-course SHA admission из нового bridge ordinary context, однако сам **не разблокирует** Native JSON updates через существующий publish/sync/Moodle/AGS путь. У sync/stage и сохранённого Gateway остаются самостоятельные SHA consumers. Вместо промежуточного API нужен один end-to-end contract с известным actual Gateway и сохранением persisted scopes; ниже установлен его обязательный Source минимум. Это решение по объёму, а не предложение начать новую схему.

Стабильная identity нового ordinary запроса — настроенный Native CI ID + assessment TID + проверенный UID. Нужный semantic sidecar — текущая небольшая **work/slot/completion policy**, не весь file inventory и не hash этой policy. Native aggregate не заменяет required-slot completion; legacy SHA requests/readers/rows/events сохраняются. Новые proof/receipt/policyhash/registry, DB schema migration и recreate course не нужны.

Startup distinction существенен: native ordinary entry **не должна** прогоняться через whole verified legacy loader. Существующие legacy entries по-прежнему проверяются прежним способом. Если mixed config указывает legacy entry на **тот же редактируемый каталог**, legacy eager startup опять блокирует процесс: новый query это не лечит. Будущему end-to-end пакету нужна явная конфигурация native ordinary entry и сохранённых legacy snapshot paths, либо отдельный ordinary-only process config. Автоматическое подавление ошибки legacy verifier/ленивое ослабление legacy admission здесь не предлагается.

## Два варианта и минимальный bridge scope внутри будущего end-to-end пакета

**Вариант1 — request-only alias (`deliveryHash` → CI ID), 1–2files. Отклонить.** Он оставляет full loader, startup snapshot, FS UUID read и sync gate, а user-visible обновления не становятся возможны. Даже как подготовку это легко ошибочно объявить снятием SHA admission.

**Вариант2 — ordinary bridge vertical slice. Четыре production modules, но самостоятельно не брать в реализацию:**

1. `bridge/delivery.mjs`: reusable existing work/slot/completion parse definitions + relation logic отделить от full legacy grading/files/hash root. Широкие чужие Native fields не закрывать этим schema. Legacy delivery3/4 parse и accepted fields не менять.
2. `bridge/bindings.mjs`: сохранить `loadVerifiedBindings` для legacy callers, включая `tools/recognized-assignment-native.mjs`. Добавить native ordinary resolution внутри этого же owner module: configured CI → Native course path → только текущий operational work view. Нет whole inventory/hash и нет бессрочного startup policy snapshot для ordinary. Достаточно одного read/parse view на context; новый cache/proof layer не нужен.
3. `bridge/policy.mjs`: существующий uniqueness check различает legacy delivery/instance и configured native CI; existing `validateNativeGroups`/`assignedSlots`/`completion` сохраняют семантику. Не менять transition/recognized/request digest policy. Извлечение reusable existing relation logic не должно ослабить legacy checks.
4. `bridge/server.mjs`: settings получает явную **opt-in native ordinary** ветку существующего bindings массива; requests — строгий union legacy `{userUid,instance,deliveryHash,workId}` и native `{userUid,courseInstanceId,workId}` (enrollment без workId). Native branch выбирает CI только из trusted settings; Native `course.path` берётся через существующий model `selectCourseById(ci.course_id)`. Existing instance alias для выбора operational works задан в native settings. **Startup сначала разделяет entries**, и только legacy entries идут в `loadVerifiedBindings`; дальнейший native context не вызывает legacy loader. Ошибка legacy snapshot в mixed startup всё ещё fatal, как отмечено выше. Native ordinary не подменяет `context` managed/recognized flow. Modern enrollment/access/group/attempt checks сохраняются. Legacy work-launch, который допускает назначенную managed работу, остаётся legacy; новый ordinary branch не получает этот обход.

Зависимые existing contracts: `schemas/gateway-work-launch.schema.json`, `gateway-work-results.schema.json`, `gateway-enrollment.schema.json` получают явные union alternatives для нового identity, без optional/fake64 в старой форме; `config/pl.gateway.example.json` и точечная документация объясняют opt-in и сохранение legacy snapshot. Результаты нового API сохраняют currentAttempt/slots/completion/Native points и state semantics; Native CI identity заменяет hash identity только в новой wire alternative. Перечень — **4production+3wire schema+config/docs**, не «один handler». Новый module/framework не нужен. Exact response union ещё должен быть согласован как public contract перед кодом; old closed response clients продолжают получать старую форму на старом запросе.

Полезный будущий typed negative — legacy identity с `courseInstanceId` вперемешку с SHA-полями не принимается как ordinary DTO. Managed refusal остаётся runtime authorization contract; compiler не может определить managed работу по произвольной строке workId. Внешний JSON получает `unknown` аннотацию до existing `.parse`, затем `z.infer`/JSDoc конкретного union/projection. Нельзя объявить все native imports типизированными из-за этого небольшого DTO, ставить `as any`, дублировать declaration facade или новый validator ради покрытия. Проверки в этом аудите не выполнялись.

## Обязательный end-to-end минимум; почему нет самостоятельно полезного малого binding diff

- **Platform sync:** минимум existing `tools/sync-native-course.mjs` + `course-sync-policy.mjs`. Нужен explicit native-bound branch, который авторизует реальный настроенный Native course/CI и source path, вызывает тот же `syncDiskToSql` того же course record и не требует basename/hash/files/previous whole manifest. Legacy branch остаётся. Один `authorizeCourseSync` edit недостаточен: полный loader находится и в caller. Это ещё2productionfiles сверх bridge4, а не часть «бесплатного» request diff.
- **Publish/storage:** current stage/compose route использует pinned immutable release artifacts. Stable runtime identity можно отделить от deployment artifact pin, не снимая container read-only protection и не давая студенту писать trusted source. Но нельзя обещать редактируемый existing source/update, пока конкретный configured publish path не выбран. Ни course recreation, ни создание новой DB вместо такого решения не допустимы.
- **Gateway actual composition и legacy история:** сначала установить точный Source deployed конфигурации обычным existing integration evidence при разрешённой следующей работе; сейчас UNKNOWN, сеть для этого не открывалась. Saved f9 потребует как минимум companion work в `config.py`, `pl.py`, `app.py`, `assignments.py`, `grades.py` — не только нового query. Разделение live ordinary binding и old SHA event scopes должно сохранять чтение прежних observations/native_attempts/outbox, не помечать pending evidence obsolete лишь из-за metadata update. Это не решается `deliveryHash=null`, policyhash, synthetic current hash или переписыванием SQL rows.

Existing `delivery TEXT NOT NULL` columns сами не дают права молча переименовать старые scopes: новый write/read interpretation и old SHA→configured Native parent correspondence должны быть определены из actual config, а не угаданы. Schema3 может оставаться, если это действительно compatible read/write; новый schema/migration для удобства не предлагается |

Таким образом, **известный нижний предел** —6Platform production modules +5Gateway modules +contracts/config; с текущим stage workflow ещё минимум1Platform module и его реальный dependency consumer. Это не готовый exact11/12file план: actual publish route и deployed Gateway неизвестны. Исторические Native IDs и FK/results нельзя получить из одного textual UUID/hash; actual configured mapping должен продолжать ссылаться на прежний parent record. При отсутствии этого входа объявлять scope закрытым нельзя.

Отдельный содержательный binding diff без нового protocol/registry сейчас **не выделен**. Request-only и4file API slice оставляют тот же startup/sync/Gateway barrier и не дают текущему пользователю обещанного обновления. Ослабление только legacy file verifier означало бы новый accepted legacy integrity contract при старой persisted SHA identity, но всё равно не решило бы stage/Gateway consumers; такой обход не выбран. Полезный следующий шаг — подтвердить уже существующий actual Gateway/config/publish Source и выбрать единый compatibility diff указанной вертикали, а не реализовывать ещё один временный API. В рамках запрета сети/production и semantic migration это честный конечный остаток, не просьба пользователя придумать архитектуру.

**Scoring не выбран заново.** Actual `server.mjs:336–337` возвращает native attempt points/max_points вместе с completion. Saved Gateway `grades.py:110–140` ordinary `observe_lab` проверяет per-slot completion, но отправляет в AGS **native attempt points/max_points**; managed `observe:80–105` отправляет completedRequired/requiredCount. Native aggregate здесь не объявлен математически эквивалентным required-slot порогу. Первый пакет сохраняет оба поля/их смыслы, managed/recognition/AGS остаются прежними. Native-first scoring — отдельное неразрешённое изменение, не технический побочный эффект удаления SHA.

Решение: **не выполнять оба отдельные API варианта сейчас**. Bridge4 сохранён как точная составная часть будущего end-to-end scope, а не independently useful release patch. Ни полная новая схема, ни Native-first scoring, ни восстановление unused SHA гарантий для старых tests не предлагаются.
