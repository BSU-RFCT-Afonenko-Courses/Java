# Библиотеки, YAML и Native Quarto: варианты упрощения

Рекомендую сначала удалить собственное восстановление YAML origins в Core, затем привести оставшиеся зависимости к согласованной поставке кода и типов. Замена парсера ради уменьшения числа `any` оставит ненужный алгоритм на месте. Это записка для обсуждения, без продуктовых изменений и новых исполнений; допуск high и его origin прежние.

Сейчас здесь три разные проблемы. Core получает `parseDocument`/`isAlias` из minified `body-export/vendor/libraries.js`: exact YAML version и соответствующие declarations не установлены. Это недостаток поставки зависимости, а не доказанная неспособность YAML-библиотеки иметь типы. Поверх неё `project-context.ts` самостоятельно обходит AST, заменяет scalar values маркерами и восстанавливает origins. Это уже наш архитектурный слой. В том же Core `ProjectContract` выводится из схем Zod v4: полезная типизация фактически потребляемых полей уже существует. QRC принимает конфигурацию как `unknown` и разбирает её своими предметными функциями; отдельный YAML parser в этом входе не нужен.

QRC и Navigation импортируют vendored parse5 и затем приводят результат через `as unknown as Document` к собственным параллельным HTML-интерфейсам. У parse5 есть типизированный `parse`, возвращающий документ выбранного tree adapter. Сохранённая попытка подключить declarations vendored 7.3.0 в Navigation упёрлась в разрешение транзитивных `.js` imports в Deno, а не доказала несовместимость настоящих типов. Это задача упаковки/loader graph. Собственные операции поиска ссылок и правки HTML по offsets могут оставаться нужными; вручную описанный второй DOM вместо библиотечных типов — отдельный долг. Даже с типами проверка отсутствующих source locations нужна: parse5 прямо допускает её для неявно созданных узлов. [API parse5](https://parse5.js.org/functions/parse5.parse.html), [позиции узлов](https://parse5.js.org/interfaces/parse5.ParserOptions.html).

1. **Убрать origin-парсинг, оставить Native effective metadata.** Это предпочтительный первый шаг по уже подготовленному physical-path proposal: Quarto владеет merge/rebase, Core разбирает потребляемый contract и сохраняет реальные physical paths, выбранные файлы и роли. Inherited project-local paths при необходимости переносятся в leaf `_metadata.yml`. Это содержательная смена authoring contract, а не косметическая типизация. Эквивалентность всех missing/decoy paths не доказана: Native rebasing зависит от существования пути. Сразу удалить весь YAML parser/copy нельзя обещать — технический `probeConfiguration` для synthetic/excluded inputs пока остаётся отдельным остатком.

2. **Для оставшегося YAML выбрать явную типизированную зависимость по настоящей задаче.** Если нужны редактирование документа, комментарии и AST, `yaml@2` предоставляет Document API и собственные node guards. Если нужен только самостоятельный value-config, `@std/yaml` возвращает честный `unknown`, после которого работает предметный decoder. Это реальные варианты замены неизвестного bundle, но ни один не заменяет Native merge/rebase и не превращает произвольный YAML в доказанный `ProjectContract`. Новый формат авторских данных допустим, если он убирает реальную обязанность парсить/редактировать документ; просто переход на JSON этого не гарантирует. [yaml@2](https://eemeli.org/yaml/), [@std/yaml](https://jsr.io/@std/yaml/doc).

3. **Для HTML сначала исправить поставку parse5 и убрать теневые типы.** Нужно согласованно поставлять runtime, matching declarations и их транзитивные imports для реального loader, после чего QRC/Navigation используют настоящий tree adapter. Альтернатива `htmlparser2` имеет TypeScript source и event/stream API, но авторы прямо отмечают отличия от строгой HTML-spec обработки. Она оправдана при осознанной смене tree/offset semantics или переходе на потоковую обработку, а не ради `any`. Ускорение от смены библиотеки здесь не измерено. [htmlparser2](https://github.com/fb55/htmlparser2), [типизированный Parser](https://github.com/fb55/htmlparser2/blob/master/src/Parser.ts).

Схемы самого Quarto находятся в `src/resources/schema/*.yml`: определения полей `name/schema/description`, ссылки, `arrayOf`, `maybeArrayOf` и другие конструкции его schema DSL. `src/core/lib/yaml-schema/from-yaml.ts` преобразует их во внутренние `Schema/ConcreteSchema`. Это источник Native validation/completion, **не готовый полный TypeScript interface** для inspect JSON и произвольных metadata наших расширений. Не следует строить ещё один полный Quarto schema framework у нас. [Схемы Quarto](https://github.com/quarto-dev/quarto-cli/tree/main/src/resources/schema), [преобразователь](https://github.com/quarto-dev/quarto-cli/blob/main/src/core/lib/yaml-schema/from-yaml.ts).

Cache/freeze стоит оставить штатными: `freeze: true/auto` управляет повторным исполнением при global project render, incremental render исполняет код; engine cache управляется отдельно через `cache` и `--cache-refresh`. Native не обещает автоматически заметить любые внешние данные. Существующее evidence также показывает reuse произвольного вычисленного текста между профилями; один output-dir не доказывает изоляцию. Это авторская cache/privacy policy для обсуждения, а не основание добавить freshness registry, новый proof или скрытый blanket gate. Проверки ролей приватных материалов сохраняются. [Managing Execution](https://quarto.org/docs/projects/code-execution.html).
