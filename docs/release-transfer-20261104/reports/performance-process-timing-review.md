## Корректность и совместимость

- `src/report/types.ts:72–89`, `src/launchers/tool.ts:78–95`: настоящий typed receipt, optional additive `native_command`, literal clock/scope, nullable duration. Тип используется у сериализуемого объекта; сужение `kind` в `tool.ts:5` честное, без cast. Старые receipts без timing по-прежнему допустимы. Тип сам по себе не является runtime decoder, и diff этого не обещает.
- `tool.ts:98–104,124–144`: initial receipt сохраняет null до запуска. Первый monotonic read расположен после подготовки аргументов/data-dir и непосредственно перед созданием/spawn команды, второй — сразу после await status. Это локальный launcher envelope, включающий synchronous spawn, listener bookkeeping и ожидание/диспетчеризацию status, а не точный timestamp OS exit. CPU/startup/global critical path он не измеряет. Начальный read немного предшествует constructor/spawn; scope и документация этому соответствуют.
- `tool.ts:124,144`: в off/отсутствующем mode оба clock reads отключены. Новых файлов, процессов, flush или обходов нет. Несколько полей/объект timing создаются и в off, поэтому нулевой общий overhead off не доказан; это малая дополнительная аллокация, не дефект заявленного требования «без дополнительных clock reads». Численного overhead/ускорения это review не устанавливает.
- `tool.ts:132,143–175`: spawn throw не достигает timing update, initial null остаётся честным unknown. Pending и отсутствие final write также не превращаются в ноль. Нормальный nonzero status проходит тот же измерительный путь, что code 0. Если status с signal действительно получен, значение присваивается до final write и self re-signal. Само наличие этого кода не доказывает работоспособность signal delivery.
- `docs/general-use-formats.md:177+` точно ограничивает значение, unknown и пересечение parent/child intervals. `src/report/run.ts` переносит исходные process JSON в causal, `src/report/perfetto.ts` сохраняет receipts в metadata целиком: новое поле не требует нового decoder/новой схемы и не удаляет старые поля. Агентская activation/expectations логика не меняется.

`tests/runner/launchers.test.ts:14–71` существенно проверяет lifecycle timing: child читает initial null, сохраняются import.meta.main/argv/stdout/exit 23, final finite/nonnegative duration ограничена внешним wall envelope. По сохранённому плану этот fixture и affected typecheck PASS. Поэтому новые signal timing assertions пока не являются пройденным свидетельством. Signal forwarding/listener/self-signal исходники `tool.ts:134–146,178–180` в diff не менялись; дополнительное присваивание duration не стоит на пути доставки TERM до child status.

Exact clean-ad9 short baseline показывает только: через 2 s после host TERM launcher status pending, native alive, summary отсутствует; затем выполнен контролируемый cleanup. Он **не воспроизводит до конца 30 s** исход исходного fixture и **не доказывает** root cause. Discriminator на отдельной диагностической копии ad9 подтверждает установленные native handlers и достигнутый launcher await-status, но не наблюдает launcher forward callback или native handler после host TERM. Это сужает границу неизвестности до доставки/dispatch перед callback; не доказывает конкретную причину в OS/Deno/harness и не оправдывает изменение signal guards вслепую.

Поскольку эта граница наблюдается на исходном ad9 без timing diff, её честно вести как отдельное существующее unresolved ограничение. Нельзя утверждать blanket «сигналы сохранены PASS» или что candidate совершенно невиновен во всех signal сценариях. Узкое принятие timing для полученного status остаётся обоснованным по коду и пройденному адресному fixture. Для последующего успешного SP delta следует оценивать фактически записанные finite durations и успех native commands; отменённые/неполные записи оставлять unknown. Новый цикл full53/signal/course suites ради этой рецензии не требуется.
