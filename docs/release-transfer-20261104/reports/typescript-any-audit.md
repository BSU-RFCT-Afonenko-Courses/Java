Это и объясняет большое число пропусков при зелёном локальном typecheck. Режим `run` сам по себе их не диагностирует.

## Что не следует механически заменять

- `Core:observability/bridge.ts:15–19` и те же ABI-фасады: `Fn=(...args:any[])=>any`, `wrapSync<T extends Fn>(...,fn:T):T` — generic constraint для сохранения произвольной функции. Замена на `(...args:unknown[])=>unknown` из-за contravariance исключит обычные функции `(x:string)=>string` и может сломать ABI. Проверять сохранность `T` и существующие type tests; при необходимости Parameters/ReturnType generics, без ложного улучшения счётчика.
- `Core:infrastructure/project-context.ts:1375–1377` `as unknown as NativeOperationProjectContextBatch<C>['groups']` коррелирует generic strategy и выбранный C. Это непроверенное утверждение компилятора, **не успешная типизация**. Его следует отдельно заменить корректной generic factory/overload после доказательства correlation, а не слепым unknown.
- `core/_extensions/course-navigation/html/document.ts:86` parse5→локальный Document double cast — FFI/model compatibility, не JSON decoder. Сверить существующие parse5 declarations и локальную DOM модель; замена сигнатур без этого ломает навигацию.
- `@ts-expect-error` найден у instrumentation rebinding (`Core:infrastructure/process.ts:118,123,129`, body-export/references.ts:203,208, answer.ts:53,55; navigation/html/document.ts:89,94). Это suppression, не типовое покрытие. Их можно убрать отдельным сохранением типизированной wrapper binding; runtime поведение/ABI сохраняются. Добавление `ts-ignore`, двойного cast или подавления ошибок не закрывает долг.

## Первые три ограниченных исправления

1. **PL native-entry ↔ Core prepared API, high.** Ограничить начало `native-entry.ts` и существующий `native-adapter.PublicCore`: восстановить конкретные parse outputs, reservation/preparation/scope/lease/operation DTO из **существующих** публичных Core types; handoff object проверять по настоящему типу, не через `as`. Сначала выбрать переносимое type-only разрешение точного Core dependency в действующей composition (Source repos раздельны, installed public путь вычисляется runtime); абсолютный локальный import или голый `as typeof import(...)` не являются решением. Не менять runtime authority/lifetime/path selection. Приёмка: existing targeted typecheck и негативные type cases на typo API/неверный descriptor/preparation; ложный DTO не проходит compile. Это первый рекомендуемый fix.
2. **PL checked selection → materialization/feedback descriptor, high.** Ограничить `native-selection`, `native-check-projection`, `native-materialize` и `runtime-descriptor`: использовать вывод `NativeProjectCheckSchema`, существующие Core plan/condition/inventory/bindings types, конкретный return descriptor; raw `'what-check'` и runtime `whatCheck` должны быть разными статическими DTO. Сохранить existing decode/hash/role guards и validateAdditionalJavaSources; не дублировать runtime schemas. Приёмка: адресные существующие raw-origin/reference/materialization/type controls и type-negative неверной feedback стороны/плана. Export-course оставляется следующей партией, чтобы fix не разросся.
3. **Core inspect/PL candidate JSON boundary, high для общего owner DTO; medium для изолированного candidate reader.** `inspectNativeOwner/json` возвращают unknown; существующие проверки формируют узкий тип owner, необходимый bindOwner/assignment/PL callback. Аналогично уже имеющиеся parsed identity/prepared/request формы сохраняются после чтения candidate. Metadata extension bags — unknown до их текущего parse. Без нового общего validator/registry, permissive casts или ослабления refusal. Приёмка: existing malformed input/owner/profile/projection controls и адресный typecheck; literal helper call-order tests не нужны.

### Дополнение очереди до максимального собственного покрытия

Прежние первые три fix сохраняют порядок и уже распределённые owners. Затем включить **в том же общем плане**, а не отдельной state странице:

1. **Site typed provider facade + Download operation/plan/inventory chain (high, раздельные owner-партии).** Восстановить существующие public types после imports и validated DTO outputs до composition/publication; каждый exact Site ref получает свой допустимый Project/record contract. Это приоритет API уровня, равный PL дыре, а не косметическая уборка any.
2. **Ordinary state/wire boundaries (medium отдельными небольшими diff).** Site collection/state/NavigationContext, QRC search/config и Download receipt/request/AST envelope: unknown до существующего разбора, затем конкретный DTO. QRC Catalog/Import/Target и Download request/config уже служат примерами корректного подхода; не переписывать их ради метрики.
3. **Platform service/DB DTO и schema result chain (high для native services; medium для локальной payload функции).** Сначала typed/JSDoc signatures потребляемых native methods, query row guards и сохранение existing parse output, затем typed request/result flow всего bridge/tools. Проверка JS выбирается адресно на собственные файлы с existing tooling; это не новый coverage framework и не автоматическая миграция языка.
4. **Browser JS/DOM и UI FFI (medium/high по реальному API).** JSDoc/declarations для Reveal/bootstrap/собственных globals/events/DTO, узкие DOM node guards; проверить parse5 boundary без suppression/casts как «результата». Existing generic Metrics Fn исключение остаётся отдельным обоснованным constraint, а не любым public data payload.
5. **Закрытие remaining own tools/tests и exact Source runner gaps.** Прочитать недоступные здесь Site/QRC source compiler configs при появлении Source, проверить complete list статически достижимых собственных TS/JS entrypoints; добавить адресные negative type cases на реальные protocol mismatches. Tests/upstream fixtures/vendor не должны искусственно увеличивать покрытие своего runtime. Никакой общий процент не заявлен.

Итог дополнения: Site/QRC/Download/UI/Platform теперь имеют конкретную карту собственных границ, и очередь максимальной типизации охватывает их наряду с Core/PL. Неизвестность compiler gate у недоступных Site/QRC Source runners сохранена явно; runtime guards не обесценены, а отсутствие static checking не скрыто.
