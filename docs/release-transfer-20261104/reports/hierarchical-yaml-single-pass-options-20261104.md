# Иерархическая YAML metadata за одну операцию

**Рекомендую сохранить нынешние `_quarto*.yml` / `_metadata.yml` и общий `course-project`, а получать только этот namespace небольшим собственным загрузчиком за один проход.** Общие объявления остаются в родителях, leaf хранит лишь отличия. Один процесс читает каждый участвующий YAML один раз, объединяет значения в памяти и возвращает контексты сразу всех объявленных code directories. Для этого не нужны QMD в каждом каталоге, копия дерева, CST, markers или доказательство неподвижности исходников. Это прикладной договор Core, а не обещание полной эквивалентности всей metadata Quarto.

Второй жизнеспособный путь — небольшой сопровождаемый upstream batch command поверх внутренних функций Quarto. Он лучше сохраняет именно Native merge/rebase, но требует отдельного upstream source adapter и всё равно предметного решения о путях. Публичного готового вызова для списка произвольных code directories в прочитанном установленном Quarto нет. Это отсутствие готового интерфейса, а не необходимость создавать фиктивные документы.

Разбор Source-only. Текущий Core — `core-native-bridge`; product/mainstate/старые отчёты не менялись. Основа: [необходимость origin](core-origin-contract-necessity-20261104.md), [предыдущий physical-path proposal](core-native-path-contract-proposal-20261104.md), [замыкание удаления SHA](sha-removal-closure-20261104.md). Предложение переносить inherited paths в YAML каждого leaf здесь **не рекомендуется**: можно сохранить компактное наследование и разрешать поля при чтении их обычного файла.

Один обычный render с capture hook действительно убирает отдельный inspect **для metadata реальных rendered documents**. Он не создаёт metadata-контекст leaf, в котором нет документа. Bank page `bank/numbers.qmd` наследует metadata своего каталога; ссылка на `projects/numbers/console-greeting` не заставляет Quarto применить metadata этого code directory к bank page. Исключённый из render каталог также не получает filter callback. Поэтому один render полезен как Native источник actual document metadata/активных профилей, но самостоятельно всю задачу не закрывает.

## Вариант 1: узкий загрузчик `course-project` — рекомендуемый

Вход уже есть: owner, фактически выбранные profiles/format и список объявленных code-project directories. Нынешний `operation.ts:2670–2679` превращает их в адреса `native-input.qmd`; новый вход может передавать сами directories. Реальные документы курса продолжают обычный Native render; загрузчик не назначает им вторую metadata модель.

Одна операция строит дерево только участвующих ancestor directories, читает общий project YAML, нужные profile YAML / local config, directory YAML и их явно применяемые includes с memo по filename. Она берёт `course-project` и при необходимости `format.<selected>.course-project`, оставляя все другие Quarto ключи Quarto. Родительское состояние наследуется в памяти, дочернее добавляет только overrides. Общий YAML, на который ссылаются несколько leaves, разбирается один раз; операция не читает байты starter/tests ради metadata. Разбор обычным существующим YAML parser даёт значения; alias/tag/warnings не получают новых запретов ради origin qualification. Допустимость предметного результата определяет существующий decoder.

**Смешанные базы путей можно сохранить без origin DTO.** Текущее правило явно находится в `project-context.ts:438–448`:

- `components.*.path`, `build.files.*`, `instructions.gradle.path` при чтении известного YAML сразу нормализуются относительно каталога этого файла. В наследуемое состояние идёт готовый physical path (либо owner-relative path), без filename/range/raw/evidence.
- `starter.path`, `testsets.*.path`, `solutions.*.path`, `instructions.local.path` остаются относительными значениями до выбранного leaf, где разрешаются относительно code-project directory.

Например, родитель один раз задаёт `testsets.demo.path: demo`; листья `a` и `b` выбирают свои `a/demo` и `b/demo`. Общий `components.process.path` нормализуется один раз в родителе и остаётся общим. Наличие одноимённого shared/decoy каталога не меняет выбранную базу. Winning declaration не восстанавливается после Native merge: нужное значение преобразовано в тот момент, когда файл уже читается. Кратковременное знание filename для relative path/диагностики не требует сохранять provenance каждого scalar.

Это сохраняет существующее Core intent, а от прежнего Native-effective proposal отличается сознательно. Для физических путей Native использует другую функцию: `toInputRelativePaths:76858–76915` перебазирует **любую подходящую строку только при существовании `baseDir/value`**, иначе оставляет её. Потому `resolve(inputDir, nativeValue)` может выбрать другой decoy. Новый узкий loader должен применять определённые предметом базы независимо от existence, а затем проверять выбранный target. Его результат нельзя подписывать `Native effective metadata`.

Иерархия/overrides/profiles сохраняются; все leaf paths переписывать не требуется. Нынешний пример `java/tasks/projects/numbers/console-greeting/_metadata.yml:1–32` уже содержит нужные функциональные поля, новый обязательный descriptor не нужен. Internal schema допускается согласованно упростить: нормализованный path и выбранная роль вместо обязательного `NativeOrigin`, без восстановления relative string для старого reader. Actual files/private roles/target collisions и предметный decode остаются обязанностью consumers; SHA/membership/freshness registry отсюда не возникают.

### Precedence и includes: небольшой явный компромисс

Это не универсальный reimplementation Quarto. Сохранить нужно compact ancestor merge, именованные maps, boolean overrides, выбранные profiles и нужные includes. Maps сливаются по ключам, scalar заменяет прежний scalar. Если предметная схема допускает arrays, следует использовать объединение с удалением дубликатов, а не молча заменить обычным array overwrite (`mergeArrayCustomizer:18897–18924`). Нынешняя `ProjectContractSchema:64–92` в основном maps/scalars; parser не обязан запрещать arrays во всём YAML ради происхождения.

Профили лучше брать из actual Native operation/hook: Quarto уже выбрал defaults/groups/env. Namespace loader применяет соответствующие `_quarto-{profile}` в том же порядке: первый перечисленный профиль выигрывает scalar conflict, затем `.local`; это видно в `mergeProfiles:26439–26470`. Так ему не нужен собственный выбор dotenv/default/group. Если loader нужен до render, выбранный список профилей надо явно передать из composition, либо один раз получить Native owner config; это максимум один owner acquisition, не per-project inspect. Пустой request profiles нельзя автоматически объявить отсутствием активного default profile.

`metadata-files` требуют порядка и базы, а не CST. Root `_quarto` включает файлы до profiles (`92495–92508`, `92189–92209`); document/format includes проходят другую стадию (`91236–91256`). Нельзя обещать единое «включаем всё рекурсивно, последний файл побеждает» как Native. Для узкого loader разумный минимальный договор: явные namespace includes в порядке списка, file-relative definition paths по файлу, который действительно прочитан; различия document/format includes Quarto относятся к реальным документам. Если course-project используется в format overlay, применить этот выбранный overlay в loader явно. Profile includes нельзя автоматически обещать: [официальные profiles](https://quarto.org/docs/projects/profiles.html#profile-configuration) отдельно предупреждают, что `metadata-files` там не разрешаются. Это место для осознанного согласования authoring поведения, не новый запрет на YAML.

## Вариант 2: upstream batch command с внутренними Native helpers

В upstream source можно добавить одну directory-oriented команду: один раз инициализировать YAML state/schema и `projectContext(owner, notebookContext)`, получить resolved project config/profiles, затем обработать весь список directories и вернуть metadata одним JSON. Для этого не нужны временные QMD и снятие authored `project.render` в копии.

Минимальный reusable graph: `projectContext`/`withProjectCleanup` (root config, profiles, extensions, lifecycle), `directoryMetadataForInputFile` (directory layers), `toInputRelativePaths` / `projectMetadataForInputFile` (project contribution), `mergeConfigs` / `mergeFormatMetadata`. Для format-specific effective metadata нужны также stages из `resolveFormatsFromMetadata:91236` и `resolveFormats:91442–91620`. Последняя цепочка добавляет format extensions/brand/project filters/engine transformations. Её нельзя честно заменить одним `mergeConfigs` и назвать full Native document metadata; directory context имеет смысл определить как **project+directory metadata без document front matter/engine**. Для полного формата потребуется выделить directory-aware stage из upstream, а не подставить фиктивный engine/document.

Root bootstrap действительно выполняет обычный project discovery один раз (`projectContext:92130–92400`); создаёт `.quarto` cache/temp и file-information cache (`92340–92395`). `directoryMetadataForInputFile` само не memoizes YAML: вызов на каждый leaf снова проходит ancestors. Значит один процесс сам по себе не равен одному чтению YAML. Для настоящего одного прохода upstream adapter должен memoize parsed layer каждого ancestor и применять Native rebasing к его clone отдельно для каждого inputDir: rebase зависит от target directory. Один общий уже rebased объект всем leaves отдавать нельзя.

Installed bundle экспортирует только CLI dispatcher `quarto` (`190406–190425`), не эти helpers. Повторный вызов dispatcher в одном Deno процессе всё ещё делает отдельные inspect и не даёт нужный directory API. Практическая поставка — маленький patch/batch command в обычном upstream source/build либо сопровождаемый source adapter с его runtime/resources/import environment. Строковое вырезание функций из bundle не предлагается. Размер command может быть небольшим; сопровождение охватывает совместимость с upstream init/schema/format/extension stages. Это заметно шире собственного merge только одного namespace, зато Native владеет общими merge/rebase правилами.

У этого варианта остаётся предметный tradeoff: Native rebase не сохраняет нынешние input-local inherited paths во всех existence/decoy cases. Потребуется принять Native semantics или всё равно отдельно нормализовать наш namespace до merge. Переиспользование private функции не делает наши правила public supported API.

## Стоимость и выбор

Пусть `P` — число code directories, `Y` — число различных участвующих YAML, `D` — различных ancestor directories. Current acquisition делает один owner inspect, копию owner и по одному document inspect каждого synthetic input (`project-context.ts:579,594,653–671`). Snapshot SHA/fences — отдельная удаляемая область, не часть необходимой metadata работы.

Вариант 1: один metadata process, `Y` чтений/разборов YAML, один проход по `D`, in-memory merge/leaf path resolution. Namespace output всё равно имеет размер числа выбранных проектов/полей. Один real render курса остаётся штатной работой и сам может состоять из многих native document/Pandoc processes: обещание «один процесс на весь render» здесь отсутствует. Если используется owner inspect ради bootstrap, это одна дополнительная Native операция на owner; такой гибрид не надо называть строго одним общим процессом.

Вариант 2: один batch command, один обычный root discovery; `Y` reads достижимы после memoization directory layers. Native path fixup добавляет existence checks, зависящие от числа строк/target dirs; shared ancestors при наивном helper-loop перечитываются порядка `P × depth`. Повторного копирования owner и `P` inspect не требуется. Времен/ускорений из Source вывести нельзя; измерений здесь нет.

Рекомендация — вариант 1 с actual profiles из существующей Native операции. Он сохраняет компактную иерархию и нынешние выбранные physical paths без больших leaf YAML. Если пользователь считает точное следование всем Quarto metadata contributors важнее небольшого собственного loader, вариант 2 остаётся реальным путём с явной ценой сопровождения upstream adapter.

## Один будущий различающий spike — не выполнен

После выбора обсуждением: один throwaway namespace loader, один offline invocation с внешним wall cap30s, без Native/render/install/product edits. Вход — **существующие описания fixture** `core-native-bridge/tests/native-context-a1.ts` (два leaf a/b, inherited local testsets и definition-relative component), явно заданные YAML слои из этого fixture в памяти, плюс небольшой in-memory profile/format/include overlay. Не создавать QMD или copy tree. Для existence/decoy развилки передать loader таблицу заданных logical paths, не менять реальную файловую систему. Не более двух leaves, двух профилей, восьми contributing YAML значений; каждый input парсится один раз.

Единственный вопрос: можно ли получить прежние **выбранные physical paths и namespace overrides** для обоих leaves, включая shared decoy/missing definition, простым layer merge + early normalization, не сохраняя origin/markers и не вызывая Native? Выход — четыре маленьких результата (2 leaf × 2 profiles) и явная таблица отличий от выбранного прикладного договора. Успех оправдывает узкий loader; если для нужного authoring результата приходится воспроизводить существенные format/extension stages, выбрать upstream batch adapter. Это не full-course acceptance и не квалификация всей YAML поверхности. Cap — предел будущего опыта, не оценка его длительности. Других spikes в этом предложении нет.
