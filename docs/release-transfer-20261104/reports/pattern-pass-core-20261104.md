## Вывод

**Пересматривать нужно саму whole-owner same-S/byte-equality гарантию Core, а не считать её сохранение обязательным условием любого ускорения.** Native Quarto/Pandoc не требуют заморозить все соседние projects, vendor и невыбранные QMD ради одного корректно выбранного результата. Требования пользователя к student privacy, фактическим учебным определениям, выбранным inputs/profile/format, владению файлами и сохранности результатов не равны требованию заметить любое изменение любого файла до seal. Нынешние hashes/fences/provenance доказывают более сильное собственное свойство и имеют собственных consumers; одно только их наличие в spec не оправдывает это свойство.

В данной области не найден аналог PL delivery SHA как native DB identity. Но Core source SHA уже является public provenance/Artifact DTO, и его нельзя просто заменить фиктивной строкой или удалить только producer, оставив consumers неизменными. Ниже разделены техническая совместимость нынешнего API и действительная необходимость гарантии.

QRC не делает content SHA/inventory дерева в прочитанном production path. Его избыточная гарантия другого рода: детерминированный порядок служебных HTML-атрибутов и закрытый набор даже непотребляемых полей внешнего catalog JSON. У UI/Navigation нет общего hash/proof runtime; основные расходы — повторная HTML/DOM обработка поверх уже готового native результата.

## Типизация сохраняется независимо от runtime qualification

Пользовательское требование максимальной собственной TypeScript типизации остаётся в силе. Удаление hash/proof механизма не означает возврат к `any`, cast фасадам, скопированным DTO или доверие внешнему JSON только из-за аннотации. Нужны реальные public producer types, inferred constructor/schema output types, точные `student | full` / `student | author` / path-origin варианты, настоящие bytes payload types и `unknown` до существующего предметного parser там, где вход действительно внешний. Runtime engine сам не обеспечивает учебную audience policy или owner namespace; их honest contracts и проверки по назначению сохраняются.

Type-only contracts и адресные compiler negatives допустимы как следующий bounded diff: они не запускают new export validator, recursive freeze или validation matrix. Новые runtime guards ради TypeScript green не нужны. Если удаляется public digest поле, контракт producer/consumer должен меняться согласованно; нельзя оставить ложный тип с fake SHA либо ввести другой `policyHash` только для заполнения schema. Если допускаются дополнительные JSON поля, точный consumer projection остаётся типизированным; ненужная закрытость входа и точность потребляемых полей — разные свойства.

Мои прежние Coread80 и Site type-only APPROVE проверяли корректность конкретных изменений внутри действовавших callpaths. Они не утверждали необходимость бессрочно сохранять same-S/immutable/proof архитектуру. Новый source-only пересмотр не отменяет эти типовые findings и не использует старые собственные specs как обоснование дорогой qualification.
