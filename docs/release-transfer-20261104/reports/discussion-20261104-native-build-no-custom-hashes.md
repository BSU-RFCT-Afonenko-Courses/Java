# Docker, Quarto и Gradle без собственного хеширования

**Предложение: удалить нашу систему доказательства неизменности, пользоваться штатными инструментами и проверять реальную работу программы.** Последний candidate лишь пропускает часть SHA, сохраняя manifests/pins/receipts; этого недостаточно. Это записка для обсуждения: Source/DB/образы не менялись, запусков не было. Origin correction остаётся PENDING.

**Зачем проверки появились.** Они ловили изменение runner, библиотек, JDK/Gradle и копий исходников. Но совпадение байтов не доказывает работоспособность и не заменяет изоляцию процесса. В контролируемом image повторять эту проверку для каждого задания избыточно. Полезная проверка сборки — настоящие compilation, небольшой запуск и JUnit outcome при подготовке/изменении инструмента.

**Docker уже решает выбор image.** Наш Dockerfile начинает с `FROM …@sha256:…`: digest выбирает точное содержимое образа. Не нужно поверх этого придумывать ещё один реестр SHA каждого image-файла. Сам Docker вправе использовать hashes внутри своего протокола — запрет относится к нашей дублирующей обвязке. Digest не замораживает writable layer/mounted student files: их разделяют права и mounts. [Официальное описание digest](https://docs.docker.com/dhi/explore/security-concepts/digests/).

**Для студента достаточно пары команд:** `./gradlew run` и `./gradlew test` (Windows — `gradlew.bat`), с аргументами задачи при необходимости. Сейчас курс использует установленный `gradle`, Wrapper ещё не внедрён. `run` уже является JavaExec; его можно оставить либо получить из штатного Application plugin. В `test` сейчас дополнительно встроены наш `apiCheck` и запись SHA JAR — эту обвязку надо снять. Требования к API остаются обычными учебными compile/JUnit проверками, без отдельного обязательного допуска/сертификата. [Штатный run](https://docs.gradle.org/current/userguide/application_plugin.html#sec:application_usage).

Конфигурация Gradle — `build.gradle`/`build.gradle.kts`, **XML-конфиг не требуется**. JUnit XML — автоматически создаваемый **отчёт результата**, обычно `build/test-results/test`; Gradle также даёт HTML. Нельзя путать его с нашей конфигурацией или требовать вручную писать XML. Текущий серверный grader пока читает собственные JSON events из PlatformJUnitAdapter; переход сервера на штатный отчёт — отдельная согласованная замена reader, не уже готовая возможность. [Официальные test reports](https://docs.gradle.org/current/userguide/java_testing.html#sec:test_reporting).

**Фиксировать зависимости можно без собственного package manager.** Wrapper задаёт Gradle distribution; стандартные dependency lockfiles записывают разрешённые версии. Не наш `toolchain-lock.json` со списком файлов. Wrapper умеет сам проверять скачанный distribution checksum при первоначальном получении: это штатный механизм, не наш per-job обход. Нового npm/Nix-подобного слоя не нужно. Обычная фиксация и запись версий полезны для опыта; запрет запуска из-за любого отличия patch-версии — другая, избыточная гарантия. Наш Core уже требует Quarto>=1.11.5, а не ровно1.11.5; это надо сохранить в описании фактов. [Wrapper](https://docs.gradle.org/current/userguide/gradle_wrapper.html#sec:verification), [dependency locking](https://docs.gradle.org/current/userguide/dependency_locking.html).

**Сохранить результаты важнее сохранения hash-протокола.** Existing UUID/native numeric IDs/assignment identities сохраняются как данные. Новые UUID создаются стандартным API один раз и сохраняются в metadata; content hash или повторная генерация при export не нужны. Persisted Gateway/Platform hash coupling требует согласованного перехода readers/истории; удаление SHA не разрешает fresh DB, пересоздание parents или пересчёт баллов.
