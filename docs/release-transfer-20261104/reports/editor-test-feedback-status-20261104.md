# Редактор и понятный результат тестов: фактическое состояние 4 ноября

**Главный исходник уже можно открывать в редакторе прямо с текстом стартера. Массовое включение ещё не сделано. Полноценное, читаемое отображение результатов тестов пока не принято:** часть потерь исправлена, но есть оставшиеся потери контекста и предметных подробностей; установленный интерфейс PrairieLearn не проверен. Успех XML reader не подтверждает то, что студент увидит в браузере.

Разбор только по текущему Source и сохранённым свидетельствам. Platform остаётся чужим замороженным dirty candidate: код, тесты и состояние не изменены. Новых compiler/tests/build/render/inspect/hash/browser/VM/install/network запусков нет. Изменён только этот отчёт; R0–R6 переиспользованы.

## Что получит студент в редакторе

PL выбирает исходники из настоящего student-плана и source-profile, сохраняя имя относительно его корня. Для каждого `b.files` он создаёт `pl-file-editor file-name="…"` и вставляет текст одноимённого выбранного стартера. Следовательно, для обычного `Main.java` студент сразу получает его незавершённый код, а отправка редактора должна сдавать именно `Main.java`. Это существующий механизм, отдельный новый «главный Main» не нужен. Имена `Study.java`, `Circle.java` и относительные пути так же являются именами конкретных контролов; hardcode `Main.java` не требуется. Reference и закрытые tests в starter редактора не выбираются.

Существующий editor **поддерживает несколько фиксированных файлов**: ограничение «один файл» не зашито в генератор. Для каждого нужен одноимённый UTF-8 starter без NUL, до 1 MiB. Скачиваемые starter ZIP и README сохраняются. Наличие вспомогательных исходников само по себе тоже не запрещает editor: рядом с ним уже умеет появляться необязательный `additional-sources.zip`.

В курсе editor/Java задан default, но 127 явных upload overrides его подавляют. Из 76 проверяемых проектов с одним фиксированным primary лишь один переведён на editor; 75 остаются upload. Есть ещё 13 проектов с несколькими фиксированными primary и 10 manual. Это сохранённая адресная инвентаризация из предыдущего разбора, не новый прогон курса. Для 13 нельзя объявлять upload технически обязательным: их следует адресно сопоставить с уже существующим multi-editor и договором задачи.

**Свобода исходников требует настоящей доработки договора.** В текущем YAML 42 объявления `additional-java-sources`; из них 29 имеют `primary-required:false`, включая 26 с физически одним starter. Поэтому 29 — число free-primary договоров, а не общее число всех договоров дополнительных исходников. Сейчас PL прямо запрещает для free-primary любой режим, кроме upload. Сам grader уже позволяет primary отсутствовать и принимать исходники из ZIP с относительными путями; совпадающие primary/ZIP пути отвергаются.

Минимальный путь — редактор для выбранного primary со стартовым текстом, дополнительные исходники как необязательное приложение. Обычное решение в одном редакторе не должно требовать upload всего ответа. Там, где учебный договор разрешает иной primary filename/class/package, UI и `_files` приём должны позволять изменить имя/путь или исключить прежний primary из отправки и использовать допустимые дополнительные исходники. Нельзя просто снять validation: нетронутый стартер тогда может попасть в сборку вместе с заменяющей реализацией и конфликтовать с ней. Для fixed-primary простого снятия overrides достаточно; для free-primary нужны согласованные editor controls → submitted files → grader selection и инструкция README. Точное поле нового UI здесь не навязывается.

Свобода определяется задачей. «Сумма и произведение аргументов» требует `Main` без пакета, но оставляет вспомогательные классы/пакеты свободными. «Циклический сдвиг матрицы» задаёт API в `Study.java`, разрешая собственную демонстрацию и дополнительные классы. Ни `primary-required:false`, ни один физический starter не дают права механически переименовать весь курс в `Main.java` или запретить разрешённые решения.

## Что сейчас известно о результате тестов

В текущем Source цепочка такая: настоящие JUnit leaves и `getDisplayName()` → adapter с unique-id, signed execution metadata и разрешёнными observations → штатный JUnit XML и `junit_result.py` → проверка полноты/классификация/доля в Java grader → `student_feedback.py` → `results/results.json` → штатный элемент `pl-external-grader-results` в `question.html`. Владелец предметных названий/сравнений — Java tests; владелец достоверности и безопасной проекции — Platform; PL exporter подключает элемент. Формирование карточек и HTML/CSS отображение — разные границы.

| Что студент должен различать | Текущее Source-поведение и предел |
| --- | --- |
| Имена и группы | Полная карточка берёт leaf `getDisplayName()`, включая parameterized/dynamic имена. Без авторского имени останется имя метода. JUnit class/контейнер не выводится отдельной визуальной группой; private `owner` нужен расчёту upstream class maximum. `AutograderInfo.name/description`, points tags и maxpoints сохраняются в private grading metadata/XML reader, но implementation UI строится заново из `counts.cases` и их имён. Поэтому само наличие annotation/group в JUnit не гарантирует его показ студенту. |
| Баллы | Для Java implementation `weighted` остаётся принятой равной долей `passed/executed`; каждая карточка leaf имеет 0/1 либо 1/1. Containers, API и `assertAll` не добавляют баллов. Сохранение upstream points metadata не означает изменение учебных весов. 80/20 задаётся assessment auto/manual, а не умножением runner score на 0.8. |
| Предметный провал | Есть «Проверка не пройдена», разрешённые expected/actual, допуск и, для поддержанных string comparisons, позиция/строка/столбец и ограниченные фрагменты различия. Формулировка свойства часто остаётся общей: «равенство», «значение предиката», «равенство с допуском». Авторское assertion message не становится предметным объяснением автоматически. |
| Неисполненное / неизвестное | Пропущенный или aborted trusted case, container failure, неполный/повреждённый отчёт дают infrastructure/no-score, а не выдуманные failed rows. Отсутствие optional observation у завершённого leaf не означает неисполнение. Для единственного совпавшего `MethodSource` эта прежняя ошибка уже исправлена. При неоднозначном selector, например нескольких parameterized leaves одного метода, статус public scenario не угадывается; остаётся `not-run`, хотя этот текст не объясняет неоднозначность. |
| Compilation/API | Достоверная собственная некомпиляция/API mismatch даёт ноль попытки, без придуманных провалов зависимых тестов. Компиляция показывает до пяти собственных file:line и русскую категорию причины; API — объявленную ожидаемую и обнаруженную сигнатуру. Полный javac log/caret/context студенту не копируется. |
| Runtime/timeout/output limit | Есть различимые русские общие сообщения и подтверждённые исходы завершённых leaves. Для declared public test adapter может дать фиксированное наблюдение класса сбоя. Подробный student exception/stacktrace или stderr в карточке пока не гарантированы. |
| Сбой инструмента | `grading_error`, `gradable:false`, score отсутствует. Это принципиально иной исход, чем ошибка программы. Сохранение прежнего best/manual в живом PL относится к отдельной интеграционной границе. |

**Публичность требует явного объяснения.** Код/стартовые данные/teacher tests, полные Throwable messages, stacktrace, stdout/stderr и служебные пути не передаются студенту через сырой `rawResult`. При этом безопасная проекция публикует названия всех завершённых оценочных leaves и предметные значения, специально полученные доверенным assertion observer/TestReporter, в том числе leaves из закрытого testset. Закрытый исходник теста не означает скрытые имя и expected в отчёте: эти строки должны быть предназначены студенту. Учителю доступны сохранённые private runtime artifacts в операторском процессе; наличие отдельного удобного teacher UI для всех XML/log/stack здесь не подтверждено.

В новом XML candidate reader создаёт raw rows с пустыми `message` и `output`; нельзя приписывать ему прежние rich throwable messages из старого Circle `rawResult`. Сам XML и приватные журналы — отдельные артефакты. Расширять публичные детали следует из доверенного наблюдения в месте проверки, а не копированием произвольного Throwable/stdout: origin/private-data границы уже проверялись и остаются необходимыми.

`tests` в Java RESULTS — список карточек внешнего grader. `partial_scores` — отдельное поле Native submission; сохранённый upstream model принимает и сохраняет его отдельно от `feedback` и `score`, а для ungradable обнуляет score/partial_scores. Текущий Java `student_feedback.py` вообще не формирует `partial_scores` и не переносит в него JUnit groups. Собственный Native-answer route exporter заполняет partial_scores для numeric/choice/multipart/matching — это другой путь. Верхний/покарточный `output` также отдельное поле: Java безопасная проекция его из stderr/stdout не заполняет. Поэтому «добавим partial_scores/output» само по себе ни названия, ни подробности ошибок не исправляет. Точная установленная upstream external-results loader→feedback привязка в этом разборе не прочитана и end-to-end не подтверждена.

## Что исправлено, что ещё открыто

Переиспользуемые факты, без повторных запусков:

- Ordinary JUnit перестал отвергаться из-за неподдержанного observation overload; `assertAll` исполняется настоящим JUnit. Для failed unsupported overload безопасного expected/actual extraction всё ещё нет. `Допуск` теперь доходит до native description; отсутствие необязательных checks у успешного leaf больше не даёт ложную неполноту.
- Circle содержательно исправлена и отдельно проверена source-runtime: reference 6/6, starter 0/6, wrong 2/6, namespace 6/6. Есть русские имена, шесть самостоятельных leaves, typed площадь/delta. Это не приёмка всей совокупности тестов и не нынешнего XML image/UI. Точный старый Circle отчёт ещё воспроизводил ложный `not-run`; последующий принятый `b37febb6` исправил эту отдельную ошибку через MethodSource и один actual fixture. Сегодняшний Source сохраняет fix; объявлять старый дефект всё ещё неисправленным было бы неверно.
- **Подтверждённая оставшаяся потеря в текущем consumer:** сначала строятся русские public-карточки с input/state/action/expected, затем `native.tests` заменяется полным списком leaves. Public context остаётся в дополнительном `feedback.publicCases`, но не объединяется с карточкой полного набора. Обычный прочитанный шаблон не рисует это дополнительное поле. Одного DisplayName недостаточно, чтобы вернуть вход/действие.
- **Подтверждённый предметный пробел:** unsupported assertion может честно fail без понятных expected/actual; поддержанные properties всё ещё общие. Массовое наличие русских имён всем задачам не доказано: Tuesday R1 обнаружил 81/118 проектов без DisplayName, но этот исторический census не пересчитывался и после адресных правок не выдаётся за текущий точный счёт.
- **Подтверждённые Tuesday transpose defects остаются открыты:** свободные допустимые подписи файла отвергает reader точных `# Исходная`/`# Транспонированная`; student failure дочерней JVM переводится через stderr marker в новый trusted IOException. R1 воспроизвёл infrastructure в обоих случаях, а текущие TaskBinding/ProcessPort/FileInvocation сохраняют эти механизмы. Перенос на JUnit XML не меняет эти course helpers. Нельзя лечить это студентским нулём или молча сузить свободный формат условия.
- **Показ строк в UI — подтверждённый кандидат с неизвестной установленной реализацией.** В сохранённом upstream PrairieLearn `97894ad…` description выводится в обычном `li`, message/output — в `pre`. Структурированные expected/actual/diff у нас собраны в description с LF; без подходящего CSS переводы строк схлопнутся. R1 сохранил исходные LF/таб и HTML probe, но browser был заблокирован: нет screenshot/DOM результата и нет установленного template/CSS. Нельзя объявить, что нынешний сервер выглядит плохо или уже исправлен, только по этому Source.

Новый Platform XML пакет исправил настоящие функциональные ошибки reader — class maxpoints и успешные пустые factories/containers. Есть сохранённые targeted JDK/XML результаты, но full independent APPROVE прерван; candidate dirty/uncommitted, Docker image не квалифицирован. Эти успехи не закрывают перечисленные потери и внешний показ.

## Исходные требования вторника и ограниченный следующий пакет

Tuesday agenda, направления 1–3, и R1 handoff требуют проследить **условие → API → JUnit → observations → Native results → фактический показ**. Нужны русское понятное имя, конкретное свойство, существенные input/expected/actual/delta, место различия; отдельно проверяются формат Java-файла, сохранность LF и отображение браузером в обычном/узком окне. Различаются «успешно», «с ошибкой», «не выполнялось», «результат не установлен». Несколько различий допустимы внутри одного случая без фиктивных исходов и изменения знаменателя. Действующий `prairielearn-labs.md` дополнительно требует file/line/reason для компиляции, понятную API диагностику, краткое основное сообщение с отдельными техническими подробностями, отличие полного автоматического успеха от ожидающей ручной части и повторное открытие feedback в настоящем PL. Эти требования существовали до нынешнего обсуждения; новых критериев этим отчётом не вводится.

Готовый ограниченный Source scope на следующее разрешённое окно:

1. Включить существующий editor для 75 подтверждённых fixed-single вопросов; адресно выбрать допустимый existing multi-editor для 13 fixed-multiple. Для 29 free-primary согласовать один договор редактируемого/отключаемого primary с необязательными supplementary sources, сохранив обязательные API и разрешённые имена/пакеты. Выбранный starter остаётся initial content. Не требовать ZIP от каждого ответа и не заводить второй manifest/runner.
2. В существующем `student_feedback` собрать полную leaf-карточку вместе с совпавшим публичным контекстом; не считать public scenario новым баллом и не дублировать leaf. Для unmatched/ambiguous/missing observations показывать честное неизвестное с причиной. Expected/actual/delta/diff выводить в структурно читаемой поддержанной границе. Не возвращать raw Throwable/stdout и ручные YAML-копии исполняемых ожиданий.
3. В frozen Platform сначала вернуть владение одному исполнителю и завершить independent review; после этого исправлять только выбранную consumer/renderer границу и нужные безопасные details. Сохранить имеющиеся execution/score/privacy гарантии. Не открывать массовую переработку всех pedagogical cases, не менять число leaves/веса ради вида.
4. Использовать уже имеющиеся Circle/string/compile/runtime/error примеры для узкой приёмки изменённой границы. Реальный UI должен отдельно подтвердить имя, input/expected/actual, допуск, строки/длинный текст, compile/runtime/infrastructure, обычное и узкое окно, повторное открытие. До доступного разрешённого установленного UI этот пункт остаётся UNKNOWN. Ночью без сети можно готовить Source/локальные артефакты в разрешённом бюджете; новые VM/config/deploy/network и повтор R0–R6 не планируются. В нынешнем read-only поручении даже эти будущие проверки не запускались.

Transpose — отдельная уже доказанная course/helper задача с существующим свободным форматом, а не повод расширить ночной consumer scope на весь банк. Читаемые имена остальных тестов берутся из уже существующих требований задач; новое педагогическое разбиение и новые критерии не входят в этот пакет. Единица выпуска остаётся весь курс.
