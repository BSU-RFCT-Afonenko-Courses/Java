# Producer-аудит хеш-механизма PL

4 ноября 2026. Приоритет переопределён прямым запросом пользователя: пересмотреть необходимость гарантии неизменности, а не ускорять прежнюю гарантию любой ценой. Это Source-only producer review, не реализация и не приёмка production. Pandoc consumer остановлен. Source/Core/installed/courses/UUID/results/student files не менялись; новых guards/proofs, compiler/tests/probes/hash/inspect/build/render/network/commit не было. Прочитаны только адресные существующие цепочки PL, связанные Core producers и непосредственные Platform readers; повтор17направлений не выполнялся.

## Вывод

**Хеши целого native каталога и canonical `delivery.json` нужны нашей собственной immutable-поставке, а не native PrairieLearn. Их обязательность нельзя обосновывать тем, что собственный reader уже требует эти хеши.** Sidecar надо отделить от native JSON и оставить в нём только сведения, необходимые нашей интеграции. Допустимое изменение native JSON не должно автоматически превращаться в «подмену поставки» или требовать новой delivery identity.

При этом сейчас существуют действующие consumers: Gateway использует `deliveryHash` как контекст assignment/migration, Platform связывает им verification receipts и path, а source/inventory hashes проходят в grading jobs. Просто прекратить писать поля в PL без изменения этих readers сломает собственную интеграцию. Это размер требуемого удаления старого механизма, а не объективная причина его сохранять. SHA не удостоверяет владельца: изменивший unsigned JSON может пересчитать его SHA. Он обнаруживает отличие от сохранённого значения и служит content identity, но не заменяет user/course/attempt ownership и реальные native UUID.

## Что реально потребляет native PL

Exporter пишет `infoCourse.json`, `courseInstances/.../infoCourseInstance.json`, `.../infoAssessment.json`, `questions/.../info.json`, question HTML/resources/server files и при external grading `tests/grading-job.json`. Последний — собственный Platform grader descriptor; его читает наш grader, а не upstream схема course metadata. Native identifiers/UUID, zones/question references, grading method/options, workspace options и файлы имеют предметный смысл.

`delivery.json` с `sourceSnapshotHash/inventoryHash/verificationInventoryHash/files/deliveryHash` — отдельный наш manifest. В прочитанных pinned upstream `infoCourse/infoCourseInstance/infoAssessment/infoQuestion` schemas такого manifest нет. Core эти имена не производит и не читает. Найденные обязательные readers — **наши** Platform/Gateway (`bridge/delivery.mjs`, `bridge/bindings.mjs`, `tools/native-course-payload.mjs`, `tools/delivery_verification.py`, `tools/grading_job.py`), не native loader. Полный upstream loader этим аудитом не перечитывался; утверждение ограничено известной native file layout/schema и найденным фактическим своим callpath.

«Широкий JSON» означает все допустимые upstream поля и варианты, а не произвольные неизвестные keys: pinned upstream schemas сами содержат `additionalProperties:false`, но их набор разрешённых свойств существенно шире собственного method-specific binding. Ширина upstream и наши UUID/policy требования не требуют фиксации всех байтов каждого JSON/HTML/ресурса.

## Где возникает несовместимость с обычным Source/native JSON

1. **Даже изменение whitespace/порядка keys** в native `info.json`, не меняющее parsed object и accepted upstream schema, меняет `files[path]`. Platform/bridge отказывают до предметной native проверки. Изменение допустимого title/другого supported property имеет тот же эффект. Это прямое следствие чтения raw bytes, не запущенный эксперимент.
2. Дополнительный разрешённый файл вопроса не входит в exact `question_files`; verifier требует равенство set всех файлов. Это собственный closed package inventory, а не доказанное native ограничение.
3. `deliveryHash` включает `files` и source/check/scenario hashes, поэтому обычный content update меняет path и Gateway context. `bridge/policy.mjs:71` требует migration при смене hash. Это связывает обновление оформления/resources с assignment migration, хотя UUID/slots/results могли остаться прежними. Реальных production DB изменений/потерь в этой задаче не наблюдалось; риск нельзя выдавать за уже случившийся инцидент.
4. Core all-tree memberships/signatures запрещают добавление/изменение неиспользуемого source во время operation; PL `checkedJSON` запрещает даже эквивалентную перезапись dependency. Свежая операция получает новое состояние, но длительный export становится чувствителен к обычной работе с checkout. Это гарантия согласованности, выбранная шире конкретной зависимости.
5. Canonical JSON **сам по себе не вырезает произвольные valid JSON fields**: он сортирует keys и опускает `undefined`, то есть нормализует представление. Закрытые schemas/bindings и export reconstruction ограничивают поля отдельно. Нельзя обещать, что простое удаление canonical автоматически добавит author passthrough всех upstream fields.
6. Встречающиеся canonical comparisons repeated question/settings/slots предотвращают конфликт одного stable question ID из разных works. Этот предметный конфликт не следует терять при удалении delivery hashing; использовать прямую equality выбранных DTO, а не требовать canonical string/hash как API.

## Предложенный минимальный следующий diff

**Первый полезный пакет — убрать обязательную byte-freeze native output, сохранив sidecar только для реально используемых integration данных.** Это coordinated PL+Platform change, а не PL-only удаление поля с заведомо сломанным reader.

- PL `export-course.ts`: перестать добавлять full `files` SHA inventory в delivery и перестать выводить идентичность курса/назначения из SHA всего output. Сохранить UUID algorithms, question IDs, works/slots/completion/grading bindings. Workspace seed hashes не должны зависеть от общего inventory: взять уже готовые seed bytes/metadata из собственного producer, отдельно решить нужность его archive integrity на transport boundary. Per-question повторные inventories для duplicate output заменить сравнением уже подготовленных selected values/bytes — без повторного чтения готового каталога. Не заменять всю гарантию новым proof или policy-hash.
- Platform readers `bridge/delivery.mjs`, `bridge/bindings.mjs`, `tools/native-course-payload.mjs`, `tools/delivery_verification.py`, `tools/grading_job.py`: удалить обязательность `files` digest map и соответствующие полные reads/hash loops. Native JSON проверять существующими upstream schemas и только теми native UUID/method/slot/runtime связями, которые reader действительно использует. Допустимые upstream поля/дополнительные файлы не превращать в причину integrity-refusal. Список вопросов получать из semantic selected catalog/native layout, а не из digest inventory.
- Действующий `deliveryHash` нельзя тихо переименовать в произвольный fake64 и считать migration закрытой. В том же согласованном consumer изменении отвязать route/path/assignment context от SHA файлов: использовать уже существующие course/instance/assessment/question UUID и existing assignment version/attempt ownership. `course-sync-policy.mjs`, Gateway policy/server и recognition mapping — адресные consumers, которые владелец consumer половины должен включить в точный diff. **Результаты/прикреплённые файлы/начатые attempts не переносить и не пересоздавать.** Existing courseUuid equality в sync policy сохраняет реальное ограничение «не подменить другой курс».

Это минимальная **смысловая** замена для запроса пользователя; число файлов определяется действующим сквозным API, не искусственным локальным лимитом. Старые v3/v4 receipts при удалении полей нельзя выдавать за проверку новой поставки. Нужен явный отказ от их роли обязательного publication/runtime proof, а не ещё один receipt version ради сохранения той же цепи.

Небольшое независимое удаление с низким риском — убрать неиспользуемые `nativeProjectWitnessHash` и `nativeVerification.inventoryHash` и построение private verification records, нужных только последнему hash. Оно сокращает обвязку, но **само не решает** проблему native-wide JSON и не должно подменить основной пакет.

Затем producer follow-up: `native-check-inventory.ts`/`native-check-projection.ts`/`native-materialize.ts` и согласованные Platform Job readers перестают реконструировать legacy physical/hash projection на native bytes path; удаляются sourceSnapshotHash/inventoryHash и scenarios digest binding, остаются actual selected files/role/names и scenarios. Core отдельно сокращает all-source freeze до operation input consumption без нового registry/proof/discovery. Пользовательский запрос уже разрешает технический пересмотр; AGENTS/spec с историческим «immutable required» описывают старый контракт, не являются самостоятельным основанием сохранить его.

## Стоимость: известное и неизвестное

Переиспользованы R0–R6 и сохранённые PL/SP readings. R0–R6 прямо рекомендуют удалять обслуживающие обходы, не кешировать каждый guard. В `pl-canonical-performance-reading.md` прежние38181 spans соответствовали20 outer canonical operations и около0.159838s TS wall; рекурсивная телеметрия уже исправлена. Это **не доказательство**, что canonical/hash обвязка является главным временем курса. Сохранённый SP capture дал PASS/VALID, но его process envelopes не изолируют SHA IO/CPU; нового speedup утверждения нет.

По Source видны неизбежные дополнительные IO: per-question partial inventory, повтор stage inventory при duplicate и общий final stage inventory; затем те же exported files повторно читают разные собственные consumers. В native path одни A1 bytes хешируют Core producer, PL selection, origin projection, verification inventory и final-starter parity. Точное число вызовов на реальном Java/course, байты и exclusive seconds здесь **UNKNOWN**. Whole-source Core fence обычно перечитывает metadata/directory membership, не следует ошибочно считать каждый fence full byte hashing. Measurement не нужен для вывода, что native JSON не обязан оставаться byte-immutable; измерять только конкретное удаление после согласованного diff, без повторной общей матрицы.
