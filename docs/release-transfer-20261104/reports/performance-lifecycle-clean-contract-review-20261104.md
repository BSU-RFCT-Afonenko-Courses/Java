# Независимая рецензия чистого Performance lifecycle

**Вердикт: необходимы исправления дизайна; APPROVE пока не выдан.** Направление с одним `RunRecord`, обязательным discriminant и отдельными requested/observed signal согласовано. Отказ от EOF/status/normalize как предварительного условия interruption snapshot устраняет доказанную архитектурную преграду frozen candidate. Однако заявленный scope и две границы финализации пока не обеспечивают описанные гарантии.

Проверен [design](performance-lifecycle-clean-contract-20261104.md), accepted `c2dcf002a7396aa3b507e49b99e0ecf00ed9f438:src/runner/execute.ts`, соответствующий frozen Source, actual imports callers и цепочка `render → process/storage`. Это Source-only review. Frozen six-file candidate остаётся NOT QUALIFIED; причина сохранённого hang не установлена. Сохранённый caller137/SIGKILL и EXDEV не интерпретируются как Native outcome или product acceptance. Compiler/tests/signals/runner/network/DB/production не запускались, Source не менялся. Прежний runtime-budget15s считается исчерпанным по поручению root; не пересчитывался и не восстанавливался.

## Пять необходимых исправлений

1. **[P1] Включить `analysis/report.ts` в обязательный scope и запретить aggregate refresh повышать incomplete.** Design: строки30 и57. Actual Source: `src/analysis/report.ts:5–7` напрямую импортирует общий `RunRecord`, writer и historical; строки130–146 кладут `summarizeRun(run)` в aggregate **до** per-run writer, который отдельно ограничивает incomplete. Строка276 возвращает `summary.every(data_valid)`. Поэтому даже сохранённый INVALID per-run record не препятствует aggregate VALID после normalization доступных executor summaries. Строки202–206 читают удаляемые зеркала `buildExitCode/wallSeconds`: после чистого удаления обычные complete runs будут показаны как INCOMPLETE. Требование: разобрать completion до normalization/aggregation; aggregate quality, coverage, строки builds, итоговый exit и per-run refresh выводить из одного authoritative record. Incomplete можно показать как incomplete либо явно отклонить, но нельзя создавать для него complete/VALID aggregate или сканировать растущие raw ради повышения качества. Обновить эту actual цепочку вместе с указанными пятью contract files и шестью callers.

2. **[P1] Определить единственную точку выбора terminal snapshot при гонке cancel с normal finalization.** Design: строки42–49 запрещают повторную finalization и позднее повышение partial, но не определяют TERM во время resource read, normalize либо уже начатого complete writer. В current `execute.ts:298–315` и последующем writer есть async окна; простое добавление `Promise.race` позволит старой complete ветке продолжить запись после partial. Требование: выбор terminal snapshot одноразовый, данные snapshot неизменяемы; поздняя нормализация/complete writer не имеет права переименовать свой temp поверх выбранного incomplete. Явно определить, когда complete уже выбран и последующий OS signal относится только к завершению entrypoint. Listener живёт до окончания или отказа публикации; повторная отмена не создаёт новый writer. Здесь же закрепить владельца `AbortSignal → child.kill` ровно один раз и поведение уже отменённого входа/отмены до spawn: caller передаёт cancellation, execute владеет child и forwarding; неизвестный Native остаётся null. Normalization и optional derived artifacts не должны удерживать interruption snapshot за прежним ожиданием. Это локальный договор existing finalizer, без нового supervisor.

3. **[P1] Сделать первый observation failure отдельным событием incomplete, а не фактом для чтения после EOF.** Design: строки45–47 требуют немедленно сохранять факты, но только cancellation явно выбирает отдельную ветку; normal branch сначала ждёт status и обе EOF. В actual `execute.ts:35–75` ошибка открытия/записи лога сообщается callback, после неё pump продолжает drain; `215–234` читает ошибку только после общего `allSettled`. Если диск уже отказал, а другой pipe удерживается, обещанный `incomplete/observation-error` никогда не будет опубликован. Требование: status rejection/первый pump IO failure сразу разрешает выбор observation-error snapshot, сохраняя уже известный outcome и original cause, без ожидания второго EOF/status. Teardown остаётся отдельным. В normal complete условии должны быть не только settled promises, но успешное наблюдение требуемых EOF/facts. Будущий адресный control: ошибка одной pump при намеренно удержанном втором stream; snapshot появляется до освобождения второго stream. Сейчас control не запускать.

4. **[P1] Закрыть договор возврата и отказа writer: один record должен быть тем, который действительно опубликован.** Design: строки13 и51. Actual writer `report/run.ts:203–215,349–355` создаёт изменённые record/metadata и возвращает `void`; `execute.ts:306–315` возвращает отдельный result. Удаление имени `RunResult` само по себе эту рассогласованность не уберёт. Также фраза «ошибка summary/report добавляется к ошибке выполнения» не задаёт наблюдаемое caller поведение. Требование: передаваемый/возвращаемый authoritative snapshot совпадает с опубликованным `run.json`, включая paths, completion и quality; writer не скрыто меняет его в другую версию. Успешная публикация `run.json` подтверждается до derived writes. При отказе pre-spawn checkpoint child не запускается. При отказе final `run.json` нельзя вернуть intended complete как успешно сохранённый: caller получает failure с runId/path и исходной причиной; прежний checkpoint остаётся authoritative. При отказе только summary/report сохранить опубликованный record и передать caller отказ публикации вместе с исходным interruption/child result, не затирая их и не превращая его в success. Для interruption определить re-raise/exit также в ветке отказа сохранения, иначе listener может оставить driver живым. Это можно выразить existing return/typed error, отдельный mirrored success-result не нужен.

5. **[P1] Адаптация `render` требует проверки доказанного Native provenance и полноты, а не безусловного `complete`.** Design: строка57. Actual imports: `render.ts:8–10` использует `runOwnedProcess` и `finalizeRun`; `145–167` сохраняет доступный outcome после `OwnedProcessError` или normalization failure. В импортируемом `process.ts:459–498` `nativeStatus` начинается со статуса непосредственного wrapper, при escalation без native receipt подставляется137/SIGKILL, а `knownNativeOutcome` допускает escalation как альтернативу native receipt. Успешный return также может содержать wrapper fallback. Эти значения нельзя автоматически переименовать в `ObservedNativeOutcome` нового общего контракта. Требование: на существующей границе expose/preserve факт источника статуса и факт наблюдательных ошибок; при отсутствии native receipt использовать `native:null`, при observation failure — incomplete с доступными настоящими фактами. Если render завершился nonzero с доказанным outcome и полным наблюдением — это complete failure. Сохранить явный measurement scope для `/usr/bin/time`, охватывающего helper, и не выдавать его CPU/RSS за изолированные ресурсы Native; direct wall фиксировать на получении actual status, отдельно от EOF/driver elapsed. Допустим минимальный перенос provenance через existing outcome boundary; перенос/перестройка group/PTTY machinery не требуется. Если root оставляет этот producer вне изменения, общий новый контракт пока нельзя честно объявить единым для render и execute.

**Остаток [P1] к исходным пунктам2/4: initial checkpoint должен иметь определённый порядок относительно terminal writer.** Строка44 требует async pre-spawn публикацию `not-finalized` run/summary/report. Строки42/47 допускают cancellation до spawn, а53 ограничивает только число **terminal** writers. В тексте пока нет правила, запрещающего следующую последовательность: начат initial checkpoint write → cancellation выбирает interrupted → terminal writer публикует interrupted → поздний initial checkpoint rename/write затирает run.json либо summary/report значениями not-finalized. Тогда returned publication и authoritative files расходятся, хотя terminal writer действительно был один.

Нужно явно закрепить: initial checkpoint и terminal publication никогда не пишут эти файлы параллельно; начатая initial публикация завершается или отказывает **до** начала terminal публикации, а после terminal никакая initial запись уже невозможна. Cancellation при pending checkpoint может немедленно выбрать отделённый snapshot, запрещает spawn и сохраняется до публикации; её не нужно связывать с EOF/status/teardown. Если initial публикация отказывает, применить заявленный pre-spawn failure/typed-error/signal-policy договор, без child. Это последовательность existing двух публикаций, без нового writer framework. Достаточно уточнения текста; запуск или изменение frozen candidate не требуется.
