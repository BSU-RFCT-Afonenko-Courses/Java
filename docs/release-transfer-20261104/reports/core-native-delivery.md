## Решение для root

Предлагаю **один путь: existing native operation с owner-issued prepared lease и реальным Core child**, без внешнего `assignment-authority-location.json`, prior P и capsule в штатной assignment ветви. Сохраняются существующие публичные capture/lease/delivery/provenance API, native AST, Body v2, A1 plans, resource/role checks и publication после закрывающего fence. Нового framework, registry, DSL, универсального validator или параллельной operation не требуется.

Это осознанное изменение договора доверия: Core подтверждает текущий native результат принадлежащего автору проекта и установленного Quarto toolchain. Core больше не обещает независимую довызовную аттестацию полного launcher/module graph. Исполняемые авторские filters/hooks/engines — доверенный код владельца, как в ordinary Quarto; процесс с правом произвольно менять тот же private каталог не становится недоверенным sandbox guest. Проверки чужой/stale generation, публичных ресурсов и запрета закрытых student bytes сохраняются как самостоятельные свойства. Их нельзя заменить фразой «проект доверенный».

Прямое задание требует одного implementation-ready предложения до кода. Поэтому варианты нового installer/capsule и восстановления legacy не развиваются. Прочитанный brainstorming workflow применён только к анализу и проектному решению; предпочтение задания — данный report, без дополнительной серии вопросов, subagent review или отдельного design commit.

## Остаточные риски и граница готовности

1. Удаляется прежняя заявленная внешняя аттестация полного executable/module graph; same-user malicious code/временная подмена с восстановлением между static fences не покрываются ordinary operation договором. Это явно меняемый технический контракт, который root должен принять, а не скрыть под новым profile.
2. Actual installed Quarto filters/dependency JSONL могут выявить конкретный непереносимый AST, внешний resource или layout. Тогда исправляется точный owning boundary; unknown resources/private bytes остаются отказом. Observed declarations не дают общего доказательства loader closure.
3. Реальная SP/Java assignment pipeline после отсутствующей authority ещё не достигалась. Помимо найденного `sourceHashBytes` могут открыться дальнейшие интеграционные дефекты (в том числе hooks/download/QRC и full input coverage). Report не заявляет producer PASS, ускорение, release readiness или зелёную приёмку.
4. Core removal касается public/private фаз и потому требует независимого Sol/high review точного diff до установки. Его не заменяет собственный report. Авторские engines не запрещаются навсегда; static optimisation и поддержка их actual captured metadata остаются разными вопросами.

Запрашиваемое внутреннее решение root: принять описанный existing-operation путь и изменение trust contract, разрешив только этот Core diff и минимальный PL profiles handoff; до этого продуктовый Source остаётся чистым.

## Реализованный результат

Связный diff выполнен в Core Source. Удалены external authority reader/profile schema и пять protocol/duplicate-helper tests (`assignment-authority-{data,graph-size,inert}`, `assignment-bootstrap-inert`, `assignment-child-native`); actual native capture теперь проверяет `assignment-admission`. `assignment-child-execution`/`assignment-contract-probe` проверяют новый внутренний execution контекст, без fake qualification.
