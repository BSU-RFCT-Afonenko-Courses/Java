## Минимальное исправление и явная граница

Для существующих решений минимально достаточна адаптация **доверенного TaskBinding.read к фактическому формату конкретного решения**, без изменения студенческих исходников: сохранить процессный запуск и чтение созданного файла; заменить литеральное узнавание подписей на извлечение двух обозначенных матриц в принятом этим решением формате. Для уже известной альтернативы достаточно читателя двух подписанных блоков без проверки буквального текста заголовков; он сохраняет обе подписи, границы строк и все записанные числа. Нельзя вычислять транспонированную матрицу внутри reader, подставлять вход вместо исходной части отчёта, отбрасывать неправильные/лишние элементы либо искать в файле ожидаемые числа и объявлять успех.

Такой читатель принимает известные законные альтернативы, но не является универсальным автоматическим читателем произвольного отчёта. Таблицы с рамками, нумерацией строк, подписями сбоку или иной последовательностью блоков также могут быть законными. Поэтому ограниченный reader обязан отличать «данные извлечены и неверны» от «формат не распознан». Второе не даёт студенту ноль, не даёт автоматический PASS и не считается неисполненным тестом без объяснения; сохраняются файл и причина невозможности наблюдения для адаптации привязки.

Отдельный непринятый вариант для будущего обсуждения по [решению 81](../java/docs/refactoring-plan.md#decision-81) — **явно согласуемое дополнение стартера**, а не молчаливое требование текущего grader. Кандидат, минимальность и необходимость которого пока не установлены: `Study.readReport(Path output)`, возвращающий запись с двумя именованными матрицами и фактическими подписями: `sourceLabel`, `source`, `transposedLabel`, `transposed`. Точный Java-тип оформляет технический исполнитель после рецензии. Метод только читает указанный уже созданный файл в собственном свободном формате; не получает вход, не запускает process повторно и не вычисляет матрицы заново. Матрицы возвращаются с фактическими размерами/элементами; подписи — из файла. Реальная запись, File и CLI сохраняются. Достоверность извлечения и смысл подписей остаются проверяемыми по исходнику и файлу, а не доказываются одним совпадением возвращённого массива.

Возвращённые студентом массивы и подписи сами по себе не доказывают соответствие фактическим байтам файла; отсутствие параметра input и запрет вычислять результат заново этого не исправляют. Метод добавляет студенту обязанность разбирать собственный отчёт. До отдельного обоснования этой обязанности и независимой связи значений с файлом кандидат не является готовым к реализации API текущего пакета и не заменяет trusted-reader. Это новый наблюдательный API, которого сегодня нет: требуется согласованная дельта условия/стартера/API-допуска/эталона и независимая содержательная рецензия; предложение не объявляет её принятой. Если старое законное решение нельзя наблюдать без изменения его кода и адаптация trusted-reader объективно не решает задачу, решение 81 допускает редкое отдельно учтённое полное ручное исключение. Неготовность grader или инфраструктурный сбой сами по себе такого исключения не дают. Прежние законные решения не обязаны задним числом реализовывать новый метод.

## Самостоятельные случаи существующих свойств

Предлагаются **10 равновесных оценочных leaves: 2 открытых и 8 скрытых**, только после готовой корректной привязки и квалификации поддержки файловых ссылок средой. Автоматическая наблюдаемость всего набора пока не установлена. Один leaf — одно файловое действие на своём входе/состоянии; несколько assertions о его результате не увеличивают вес. Повтор demo и API-допуск в число не входят. Основание разбиения — [решение 65](../java/docs/refactoring-plan.md#decision-65), текущие [ContractTest](../java/tasks/projects/files/transpose-file-matrix/checks/src/test/java/ContractTest.java) и [PublicChecks](../java/tasks/projects/files/transpose-file-matrix/observations/src/test/java/PublicChecks.java).

| Случай / вид | Вход или состояние | Ожидаемое свойство | Отрицательный дефект |
| --- | --- | --- | --- |
| «Строки становятся столбцами: 3×3» / открытый | 1 2 3 / 4 5 6 / 7 8 9; новый каталог | Записаны исходная матрица и 1 4 7 / 2 5 8 / 3 6 9; различимые подписи; вход сохранён | Копирование вместо транспонирования; потеря исходной части |
| «Один элемент: −7» / открытый | −7 без завершающего LF | Обе записанные матрицы [[−7]] | Требование лишней строки/размера больше 1 |
| «Граница int в матрице 1×1» / скрытый | −2147483648 с LF | Обе матрицы [[Integer.MIN_VALUE]] | Неверное чтение допустимого int |
| «Независимая матрица 2×2» / скрытый | 2 −3 / 7 11 | Исходная сохранена, транспонированная 2 7 / −3 11 | Подгонка под пример 3×3, неверный обмен индексов |
| «Нет входа: прежний результат сохраняется» / скрытый | Отсутствующий вход, выход содержит KEEP | Отказ с причиной; выход побайтно прежний | Преждевременное открытие/очистка выхода |
| «Нет входа: прежнего результата нет» / скрытый | Отсутствующий вход, выхода первоначально нет | Обоснованный отказ из-за отсутствующего входа; создание нового пустого файла само по себе допустимо | Ложное сообщение об успешной обработке; необоснованный отказ |
| «Вход и выход — один путь» / скрытый | Одинаковый существующий путь | Отказ до открытия выхода; вход побайтно прежний | Самокопирование уничтожает данные |
| «Один файл через путь с ..» / скрытый | Вход и нормализованный алиас padding/../имя | То же | Сравнение только строк путей |
| «Один файл через жёсткую ссылку» / скрытый | Два имени одного файла | То же | Проверка лишь нормализованных имён |
| «Один файл через символическую ссылку» / скрытый | Ссылка на вход | То же | Неучёт файловой идентичности |

Старый assertion об отсутствии нового выхода исключается: условие явно сохраняет прежний результат, но не запрещает предварительное создание нового пустого файла. Если прежний результат существует, его сохранность обязательна и проверяется отдельным случаем KEEP.

Создание каталога/обычного файла наблюдается в каждом успешном случае; использование именно File, двумерного массива, CLI и объяснение чтения/записи проверяются по исходнику/демонстрации. Точный текст подписей и диагностики, сортировка чисел, проверка неквадратных входов и атомарность не становятся новыми оценочными свойствами.

Для ссылок нынешний `continue` внутри успешного leaf скрывает отсутствие проверки. До применения десяти случаев среда должна подтвердить поддержку обеих ссылок; недоступность операции — проблема квалификации среды, а не pass или fail студента. Нельзя молча менять знаменатель на 8/9 либо считать неполный отчёт полным. Условие «тот же файл» обосновывает эти варианты идентичности; специальных требований создавать ссылки к студенту нет.

## Assertions, отказы и риск исполнения

Boolean `Arrays.deepEquals` и ручные expected-строки заменить обычными JUnit сравнениями размеров и строк массивов с контекстом матрицы/строки; сравнивать все элементы, не только общий префикс. Например, сообщение «Транспонированная матрица, строка 2» дополняет реальные expected/actual. Проверки двух матриц одного файла допустимо объединить assertAll в пределах одного leaf. Исходная матрица ожидается из заданного входа, транспонированная — из явно заданных ожидаемых рядов соответствующего случая; YAML/DSL/дублирующий реестр не нужен. Короткое имя leaf и конкретное нарушение заменяют перечень успешных observations.

[ProcessPort](../java/tasks/projects/files/transpose-file-matrix/observations/src/test/java/ProcessPort.java) ловит Throwable и пишет COURSE_PORT_FAILURE; [FileInvocation](../java/tasks/projects/files/transpose-file-matrix/observations/src/test/java/FileInvocation.java) превращает это в trusted IOException. R1 отдельно подтвердил потерю происхождения TODO-исключения. Исправление Platform должно сохранить различие: исключение решения на допустимом входе — ошибка исполнения студента; невозможность запуска/чтения инструментом — tool error; несовпадение доказанно извлечённых значений — предметный fail. Не ловить все эти исходы одной AssertionError.

Особенно важно исправить смысл `refused`: сейчас любое IOException принимается за ожидаемый отказ, а любой непустой stdout/stderr тоже может зачесть отказ. Нужен наблюдаемый отказ, относящийся к заданной причине, плюс сохранность файлов; диагностический текст свободен. Произвольный TODO/runtime-crash, служебный сбой или посторонняя печать не доказывают обработку отсутствующего входа/самокопирования. Если из свободной диагностики нельзя надёжно установить причину, это граница наблюдения для привязки/ручной проверки, не повод назначить обязательный текст или новый код выхода без договора. Технический протокол передачи исключений не определяет учебную семантику отказа сам по себе.

Предлагаемое изменение будущего знаменателя после готовой корректной привязки — **5 → 10**, без групповых весов и без изменения 80/20. Прежние признанные результаты не пересчитываются. До готовой корректной привязки нельзя объявлять весь набор автоматически наблюдаемым. Безопасный следующий технический фрагмент — trusted-reader известных законных форматов с сохранением файла/данных и честным исходом unrecognized, без студентского нуля или PASS. Сохранение данных должно переживать cleanup временного каталога. Классификация origin/refusal требует отдельного точного договора; этот документ фиксирует её необходимость, но не утверждает технический протокол. Нужны независимая учебная рецензия предложения и техническое подтверждение reader/происхождения ошибок; этот отчёт их не подменяет.

По [независимой рецензии](transpose-file-contract-review.md) устранены два замечания: новый пустой выход при отсутствии входа не запрещён; readReport оставлен непринятым вариантом вне текущей реализации. Перед передачей проверен весь прежний исходный модельный интервал: 3 записи, назначения Astra/medium согласованы, начало не сдвигалось.
