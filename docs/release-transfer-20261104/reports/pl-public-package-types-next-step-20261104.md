Следующий ограниченный шаг возможен: провести существующий `PublicBodyPackage` от настоящего Core delivery до PL writer. Полная типизация Pandoc AST для этого не нужна. Сейчас Core действительно создаёт и проверяет `BodyPackage`, удаляет приватные поля вопросов и возвращает типизированный `NativeAssignmentDelivery`. PL теряет этот тип на параметре `operation:any` в composition/adapter; аннотация одного `exportPrairieLearn(p)` оставила бы эту дыру.

Конкретная задача — четыре production файла PL: `application/native-course.ts`, `native-adapter.ts`, `export-course.ts`, `export.ts`. Провести существующий `NativeOperation` через composition к настоящему вызову `assignmentDelivery`; сохранить выведенный delivery в callback, картах `bodies`/`menuBodies`, `input.body` и `exportPrairieLearn`; вывести `resourceBindings` из `BodyResource`. Источник типа — уже типизированный callback Core в `native-entry.ts`, дополнительный parse внутреннего пакета не нужен. Core менять не требуется. При необходимости согласовать существующий compiler fixture `tests/native-course-export-types.ts` и реальные body fixtures; в этой работе проверки не запускались.

Это закрывает оболочку пакета и ресурсы. `condition`, `publicAnswer`, `introduction` остаются текущими Core `any[]`, `Node.c` остаётся `any`; объявлять весь AST строго типизированным нельзя. В production trace публичный body не читается из JSON. Ручные проверки PL не являются полным decoder для произвольного внешнего `unknown`; такую отдельную задачу нельзя заменить cast.

Фактическая публичная модель (`core-native-bridge/.../body-export/model.ts:4`, `package-contracts.ts:11–96`):

- Пакет: `schema:"course-body-package-v2"`, `owner:string`, `release:string`, `apiVersion:number[]`, `questions`, `works`, `resources`.
- Вопрос: `owner,id,key,source:string`; `title?:string`, `difficulty?:"introductory"|"intermediate"|"advanced"`, `time?:number`, `visibility:"public"`, `statementVisibility:"open"|"restricted"`, `purpose?:"demonstration"|"discussion"|"independent-study"|"control"`, `hasPublicSolution:boolean`, `condition:any[]`, `publicAnswer:any[]`, `answerType:"manual"|"single-choice"|"numeric"|"multipart"|"matching"`. Приватных полей в публичном типе нет.
- Работа: `owner,id,key,source,title:string`, `kind:"lab"|"seminar"|"practical"|"test"`, `introduction?:any[]`, `slots:{id:string;selection:"fixed"|"random"|"choice";candidates:string[];assignment:{stage?:"demonstration"|"classroom"|"homework";requirement:"required"|"optional";workMode:"individual"|"pair"|"group"}}[]`, `relatedExercise?:string`, `theoryTime?:number`.
- Ресурс: обязательные `owner,source,effectiveBase,target,data:string`, `visibility:"public"`. Схема также проверяет ограничения строк/чисел, ключи и связи; TypeScript не заменяет runtime refinements.

Текущие guards и граница задачи:

`export.ts` проверяет exact allowed fields пакета/работы/вопроса, owner/key, выбранную работу, slots/candidates и правила видимости/демонстрации; `fields`/`record` принимают `any` и возвращают boolean. Они не сужают `unknown` до `PublicBodyPackage`. Верхняя проверка не доказывает тип `release`, содержимое числового `apiVersion`, все поля каждого ресурса; renderer проверяет owner/visibility/target/data только у используемых ресурсов. Core допускает необязательный `title`, PL требует непустой title — это существующий более строгий consumer guard, его надо сохранить. Core `BodyPackageSchema` описывает полный пакет с приватными полями и не подходит для простого `.parse(publicPackage)`.

Поэтому минимальный шаг использует настоящий внутренний producer и его публичный delivery contract; guards PL сохраняются как предметные проверки. Если будет предъявлен внешний JSON body, сначала нужен его конкретный вход и полный существующий/обоснованный public decode: текущий `fields` не даёт такого доказательства. Произвольный cast, отдельная копия DTO/schema или runtime import `course-core/...` этого не решают.

В `native-course.ts` сужение `operation` требуется в `prepareNativeCourse`, `withNativeAssignments` и operation-параметре `withNativeProjectPlans`, чтобы последний не возвращал operation к `any`; тип callback deliveries лучше вывести из `ReturnType<typeof createNativeAdapter>`/метода. Параметры `assignmentDelivery` следует брать из существующих `NativeAssignmentRequest`/`NativeAssignmentDeliveryOptions`, чтобы `projectPlans/references` не подменялись `unknown`-контрактом. Это потребует адресного согласования их уже существующих типов в той же composition; новый provider API/authority не нужен. Посторонние `Core:any`, policy/materialization DTO и общий writer schema dispatch не входят в закрытие body-пакета и должны быть явно оставлены за границей.
