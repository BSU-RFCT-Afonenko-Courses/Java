# PL, Download, Site: необходимость собственных механизмов

4 ноября 2026. Source-only проход по актуальным PL/Download и обеим закреплённым версиям Site. Поведение не менялось. Цель — найти не только повторные SHA, но и ненужные гарантии/преобразования; старый собственный spec не принят за доказательство необходимости. Предыдущий [producer hash audit](hash-mechanism-producer-review.md) не переписывался. Platform/Gateway — отдельная область root, здесь их код заново не аудировался.

## Результат

Наиболее убедительные локальные кандидаты — **повторная hash/clone-квалификация готового Core inventory перед ZIP** и **непотребляемые PL witness/verification hashes**. Для них уже видны конкретные consumers и ограниченный diff. У Site no-Download есть дополнительный Core validation pass, но его замена ordinary `inspectPublication` **не доказана эквивалентной**: эти маршруты проверяют разный объём. Существующие path/ownership/public-private проверки защищают другие, реальные границы: удалять их вместе с hash-обвязкой было бы ошибкой.

Более широкие несоответствия native возможностям тоже есть: PL описывает только собственное подмножество native JSON/Workspace; SP Site заново выбирает форматы документов и порой разбивает native render на отдельные вызовы; Download в author не умеет получить настоящий starter и вместо этого отказывает; HTML passes и обязательные локальные ZIP — собственные presentation решения. Это не доказательство, что все ограничения следует снять одним patch. Где нет доказанного native эквивалента с сохранением privacy/UUID/results, ниже прямо оставлено **UNKNOWN/отдельное решение**.

## Три ограниченных следующих diff

Это варианты реализации для root, **не начатые изменения**. Они удаляют механизмы, а не создают ещё один cache/proof/qualification framework.

1. **Site SP: удалить собственный per-document format resolver, опираясь на уже существующий J design.** Два production файла S `application/compose.ts` и `infrastructure/config.ts`: заменить `inspectDocuments`/renderTo selection и per-document capture на native project selection + один child `quarto render . --to <selected>`; actual output/owner coverage сохранить. Risk medium/high: mixed/custom formats/native defaults. Не обещает поведение всех S fixtures без адресной проверки, не запускается сейчас. Whole grading validation S6 в эту партию не включать.
2. **Download: packaging использует готовые bytes, не подтверждает self-described SHA второй раз.** Один production `application/package-artifact.ts`: сохранить единственный early snapshot unknown input, existing Core parse, safe target/audience/collision и ZIP writer; удалить per-file SHA/size comparison и вторую копию уже private bytes. CRC остаётся внутри ZIP. Публичное назначение helper — упаковка, не authority/currentness certification. Future acceptance — ZIP ровно переданных cloned bytes/paths, borrowed-input mutation не меняет архив; malformed path/audience всё ещё отказывает. Ошибка «переданные bytes не совпадают с caller.sha256» намеренно перестаёт быть subject API, а не скрывается тестовым suppression. Risk medium: external callers могли использовать helper именно как digest checker, публичный контракт/documentation надо обновить в том же bounded change.
3. **PL: удалить непотребляемый proof output.** `native-provenance.ts` — убрать `nativeProjectWitnessHash` и его hash/canonical; `verification-inventory.ts` — не строить/structuredClone полный private questions inventory и его inventoryHash, когда единственный production consumer `export-course` использует scenarios/scenariosHash. Нет нового JSON/receipt version только ради замены proof. Future acceptance сравнивает реальный producer project/scenario output и privacy, не прежний orphan hash. Risk low/medium: private module imports tests/external tools могут ожидать старые fields; публичный export graph/readers проверить адресно. Это полезное удаление, но **не подмена** большого удаления delivery/files immutable API из предыдущего аудита.

Отдельная гипотеза S6 **не готова к реализации как one-line swap**. Варианты: (а) убрать первый Core pass, сохранив выбор full PL composition только при реально выбранном adapter, или (б) явно определить ordinary Site как partial-publication маршрут и использовать inspectPublication.
