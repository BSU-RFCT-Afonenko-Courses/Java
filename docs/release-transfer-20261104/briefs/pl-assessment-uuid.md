# PL: сохранить UUID при переименовании assessment

Исполнитель Sol6.1/high, Standard; собственный допуск в report, не в нормативном model-admission.md. Repo `/home/tolya/JavaCodex/java-release-20261110/prairielearn`, branch `codex/java-release-20261110`, текущий HEAD `7a41b7cc73859f69bf45c304590d711d85bcae66` поверх base `1c41f03f83b26adfe58415b4d89958a3663fabf2`. Только ты writer PL после завершения Workspace пакета. Root меняет пять Java QMD после готовности этого контракта. Не создавать субагентов.

Обязательные требования: убрать j25 из учебных IDs/ссылок и сохранить опубликованную идентичность/результаты. Обзор `/home/tolya/JavaCodex/java-release-20261110/reports/java-identifiers-review.md` нашёл blocker: переименование work.id меняет UUID, который export-course.ts:679 безусловно вычисляет identity('assessment/'+work.id,courseUuid). Core native-course.ts:301–306 передаёт PL policy отдельно; PL application/native-business.ts AssessmentPolicySchema строгая, explicit UUID сейчас не поддержан. Пять работ Java меняют assessment.id, UUID литералы в QMD ранее отсутствовали. Нельзя оставлять j25 в учебном ID как обход, вводить course-specific таблицу внутри generic exporter или новую вечную систему published keys.

Выбранное узкое решение: необязательный стандартный `assessment.prairielearn.uuid` для сохранения существующей native UUID. Только локальная policy конкретной работы, не общий assessment-defaults. При наличии экспортёр пишет этот валидный UUID в infoAssessment.json; без него сохраняет прежнюю deterministic identity('assessment/'+work.id,courseUuid). Это используется для текущих пяти переименований; новые работы не обязываются заводить дополнительный key. Course/instance UUID, question UUID, work.id/пути и остальные правила не меняются. Invalid/duplicate explicit UUID должны быть понятной ошибкой существующей валидации; не добавлять общий validator/proof framework. Read AGENTS.md/spec/index.md и нужные действующие договоры.

Перед реализацией кратко запиши точные файлы/цепочку validation→export в `/home/tolya/JavaCodex/java-release-20261110/reports/pl-assessment-uuid.md`. Учитывай closed/strict policy checks как native, так и standalone path: field должен пройти штатный TS business contract и быть использован экспортёром; установка в общем defaults не должна тиражировать один UUID на все работы. Политика по-прежнему у PL, Core schema переопределять не нужно.

Проверка meaningful behavior: тот же явный UUID сохраняется при смене work.id; отсутствие field сохраняет старую генерацию; неверный UUID/конфликт не создают поставку. Используй адресные существующие test harness/fixtures и минимум нужных новых cases для этой реальной регрессии, без полной33suite/CI/course/render/Docker матрицы. Не строить новый тестовый runner.
