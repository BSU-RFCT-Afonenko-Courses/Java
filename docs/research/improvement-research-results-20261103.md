## Что доказано и что из этого следует

### 1. В Java grading повторяется работа, которая не является решением задачи

В Source Platform `865d017` штатный успешный native-путь **семь раз** вызывает полную проверку установок Gradle и JDK. Source lock содержит1035файлов общим объёмом516164993байта. Это номинально7245чтений файлов и3,613ГБ хешируемых bytes за успешный `grade()`, без учёта остальных проходов. Два полных прохода попадают в таймер `gradleBuild`; другие остаются вне его и вне JUnit `execution`.

Это **статическая трассировка Source и состава lock**, не измерение физического disk I/O и не подтверждение текущего server image. Время этих проходов отдельно неизвестно. Однако сам повтор установлен без нового полного хеширования. Прежние55,878с `gradleBuild` нельзя целиком приписать Gradle. [Порядок вызовов, первичные строки и расчёт](</home/tolya/JavaCodex/java-research-20261103/run-ultra-01a1a144-b034/R4/native-build-cost-note.md>).

Есть и **двойная компиляция production sources**. Сначала создаются `student` classes и выполняется API precheck; затем Gradle снова компилирует исходники для JAR. В прочитанном Source JUnit использует прежний каталог `student`, а JAR служит отдельным build evidence. Оценивание именно bytes этого JAR не установлено. Это дополнительная стадия, необходимость которой следует пересмотреть, а не сохранять по инерции. [Фактический порядок](</home/tolya/JavaCodex/java-research-20261103/run-ultra-01a1a144-b034/R4/cross-check-r2-r3.md>).

**Кандидат удаления:** повторные полные inventories из обработки ответа; проверка неизменной поставки относится к её подготовке/установке. Затем — второй путь компиляции: выбрать один результат для API, JUnit и нужного артефакта. Gradle самостоятельного IDE-проекта имеет отдельное полезное назначение; его наличие у студента не требует повторять весь build при каждом grading.

### 2. Обвязка JUnit теряет смысл и ограничивает обычный JUnit

Активный канон содержит128проектов, из них118автоматических. Статически найдено687 `@Test`; в81автоматическом проекте нет `@DisplayName`. У56 checks-файлов есть строка длиннее500символов; максимум2472. Длинные строки уже находятся в исходниках, массовое уничтожение LF генератором не подтверждено.

Circle сворачивает несколько свойств в boolean, использует отдельно написанные строки ожиданий и технические имена. Пять радиусов в закрытом методе остаются одним JUnit leaf; **фактический знаменатель —3**, а не число радиусов или assertions. Затем `student_feedback.py` заменяет подготовленные публичные карточки полным списком cases. В typed-пробе delta сохранена в промежуточных данных, но потеряна в native description.

Обычные `@DisplayName`, parameterized cases и содержательные assertions достаточны для авторского канона. Но исследованный Transform отверг стандартные `assertAll(String, Executable[])` и `assertEquals(double,double,String)`, которые прошли plain JUnit. Его blob совпадает между course pin и исследованным Source; фактически установленный серверный runtime неизвестен. Поэтому сохранение/расширение собственного assertions-фасада не следует считать исходным обязательным решением.

**Кандидат удаления:** ручной дубль expected, составные boolean вместо обычных сравнений, подмена списков результатов, повторные служебные допуски внутри предметных тестов. Упростить путь до обычного JUnit и короткого преобразования реальных результатов. Изменение числа оценочных случаев влияет на баллы; его нельзя спрятать внутри форматирования тестов. [R1 с точными источниками и воспроизводителями](</home/tolya/JavaCodex/java-research-20261103/run-ultra-01a1a144-b034/R1/report.md>).

### 4. Сборка повторяет metadata-разрешение и разбор общего текста

Quarto1.11.5 document inspect вызывает project inspect, проходящий все входы. Поэтому N document-вызовов могут давать N² project metadata work. Однако текущий Core уже имеет bounded profile и batch fast path; старую квадратичную ветвь нельзя автоматически приписывать всей нынешней сборке.

Конкретный повтор нынешнего пути — разбор общей Gradle-инструкции в разных `ProjectPlan`. Один и тот же фактический Markdown8раз разбирался Pandoc; operation-local reuse одного AST сохранил одинаковые результаты. Это кандидат убрать повтор без нового общего resolver. Другие profile/format-контексты не объявляются одинаковыми только из-за совпадения файлов. [R2: цепочки и замеры](</home/tolya/JavaCodex/java-research-20261103/run-ultra-01a1a144-b034/R2/report.md>).

### 5. Исполняемый Quarto работает; постоянная переиндексация для этого не нужна

R/knitr и Python/Jupyter исполнили штатные ячейки и inline; R include и сгенерированный `exr` дошли до `pre-ast` consumer. Но `freeze:auto` оставил старое значение после изменения внешних данных в обоих движках. В R не обновился include; смена student/full переиспользовала вычисленный текст другого профиля. Отдельный targeted render обновлял результат. Cell cache тоже требует явного обновления внешних зависимостей.

Рекомендуемый договор для обсуждения: известные QMD исполняются штатно, после исполнения закрывается итоговая AST-модель и её результат переиспользуют README/ZIP/Native. Новые source QMD генерируются **до** фиксации плана; производные ресурсы имеют выделенное место. Зависимости от данных и профиля задаются явно либо обновляются явной командой. Нельзя обещать обнаружение любого внешнего изменения; нельзя заменять это обещание discovery на каждом чтении. ### 7. Учебная проблема требует работы с последовательностью, а не новых рубрик

Полностью прочитаны лекции3,4,6,7,8 и соответствующие главы теории/статьи справочника. Всеобщая несвязность не подтверждена: в теории объекты/классы есть законченные объяснения, в лекции4 сильна цепь Document→Sender→CountingSender→DispatchStats. В лекции8 связны parseScore/catch/unwinding.

Адресные разрывы находятся на уровне общего хода: в лекции6 практическая задача каталога появляется после длинных ветвей механизмов; в лекции7 отбор отчёта прерывается самостоятельными Supplier/effects/reduce; в лекции8 итоговый loader приходится собирать мысленно из разных семейств примеров. Избыточный набор локальных опытов может вытеснять основную мысль, даже когда каждый опыт хорош.

Есть конкретные локальные недостатки: вход Ada/90,Ann/80 в лекции7 уже упорядочен, поэтому не показывает действия сортировки; теория interfaces вводит Self/parent slots без достаточной модели. В12прочитанных статьях справочника фундаментального объяснения, оставшегося только там, не обнаружено. Эти находки точнее общего требования переписать весь текст одинаковым способом.

Предложение — раньше задавать общий предмет и развивать один продолжающийся пример, а самостоятельные механические опыты подчинять возникающему вопросу. Справочные подробности распределять по назначению трёх форм. Это гипотеза, а не новая обязательная формула «один сюжет на всё». Полезные местные контрпримеры сохраняются. Новая лекция9 не написана; подготовлены варианты её композиции. [R5: адресные последовательности, прочитанные источники и варианты](</home/tolya/JavaCodex/java-research-20261103/run-ultra-01a1a144-b034/R5/report.md>).
