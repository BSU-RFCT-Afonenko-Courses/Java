## Обычный JUnit и результат в PrairieLearn

### Установленные факты

1. Штатный Java autograder PrairieLearn использует JUnit 5 и поддерживает библиотеки вопроса и общие библиотеки курса. Это готовое средство, но не доказательство равенства его образа нашей закреплённой Platform. [Официальный Java grader](https://docs.prairielearn.com/java-grader/#libraries-and-instructor-provided-classes).
2. Наш `PlatformJUnitAdapter` подключён к существующему `JUnitAutograder` как `TestExecutionListener`, учитывает обнаруженные, выполненные, пропущенные и динамические тесты. Он также различает инфраструктурную ошибку, ошибочный ответ и исключение студенческой программы. [Подключение и счётчики](https://github.com/Afonenko-Course-Tools/prairielearn-platform/blob/1cab18c5e693210b2b52930cacb00ceb5acd9797/runtime/java25-junit-v1/PlatformJUnitAdapter.java#L72), [подключение listener](https://github.com/Afonenko-Course-Tools/prairielearn-platform/blob/1cab18c5e693210b2b52930cacb00ceb5acd9797/runtime/java25-junit-v1/PlatformJUnitAdapter.java#L126).
3. Публичное наблюдение сейчас привязано к `Class#method` и паре `TestReporter` ключей `public-case`/`actual`. Его отсутствие не доказывает, что обычный JUnit-тест не выполнялся. Привязка только к методу также недостаточна для различения нескольких параметризованных вызовов, если они публикуют одинаковый ID: student-проекция принимает ровно одно совпадение. [Adapter](https://github.com/Afonenko-Course-Tools/prairielearn-platform/blob/1cab18c5e693210b2b52930cacb00ceb5acd9797/runtime/java25-junit-v1/PlatformJUnitAdapter.java#L112), [выбор наблюдения](https://github.com/Afonenko-Course-Tools/prairielearn-platform/blob/1cab18c5e693210b2b52930cacb00ceb5acd9797/runtime/student_feedback.py#L43).

Общая предметная подсказка может подменить совет при ошибке компиляции; данные javac, API и assertion не проходят через этот путь автоматически. Это конкретный участок переработки, не основание переписывать весь grader. ### Последующее решение о баллах, 29 октября

[Решение 52](../../refactoring-plan.md#decision-52) выбирает для всех задач с автопроверкой равный вес каждого оценочного теста и долю `passed / total` полного набора вместо нынешнего `all-pass`. В смешанной задаче 8 из 10 тестов дают 0.8 от автоматических 80%, то есть 64% общего максимума; ручные 20% отдельно. Чисто ручные задачи не получают фиктивной автодоли; demo не подменяет полный оценочный набор. Количество тестов влияет на относительный вес проверяемых областей по принятому правилу, отдельные веса учебных групп не выбраны.

Поддержка проверена по источникам, не запуском: PL-экспортёр 8.3 [включает `partialCredit` для не-all-pass](../../../tasks/_extensions/Afonenko-Course-Tools/course-prairielearn/application/export-course.ts#L386); закреплённый Platform `1cab18c5…` [передаёт JUnit score в режиме weighted](https://github.com/Afonenko-Course-Tools/prairielearn-platform/blob/1cab18c5e693210b2b52930cacb00ceb5acd9797/images/java25-grader/grade.py#L364). Его [JUnit-исполнитель считает earned/max](https://github.com/Afonenko-Course-Tools/prairielearn-platform/blob/1cab18c5e693210b2b52930cacb00ceb5acd9797/runtime/java25-junit-v1/upstream/JUnitAutograder.java#L261) при [стандартном весе 1](https://github.com/Afonenko-Course-Tools/prairielearn-platform/blob/1cab18c5e693210b2b52930cacb00ceb5acd9797/runtime/java25-junit-v1/upstream/JUnitAutograder.java#L288); неравные авторские веса целевому правилу не соответствуют. В закреплённом PL `92584fe4…` [контракт внешней оценки принимает score 0..1](https://github.com/PrairieLearn/PrairieLearn/blob/92584fe426ececb84bc2d09de9975c7056c0c5f6/docs/externalGrading.md#L144), а [partialCredit разрешает дробные баллы](https://github.com/PrairieLearn/PrairieLearn/blob/92584fe426ececb84bc2d09de9975c7056c0c5f6/apps/prairielearn/src/schemas/infoQuestion.ts#L283). Это готовая поддержка механизма, не утверждение, что нынешние Java-настройки уже переключены.

Нынешний исполнитель учитывает тестовые события JUnit (`isTest`), а не число assertions; стандартный вес может быть изменён `points=`, `maxpoints=` или `AutograderInfo`, поэтому равенство весов нужно обеспечить при переносе. Кроме того, [нынешние timeout/output-limit ветви](https://github.com/Afonenko-Course-Tools/prairielearn-platform/blob/1cab18c5e693210b2b52930cacb00ceb5acd9797/images/java25-grader/grade.py#L594) обнуляют весь результат, а неполное доверенное исполнение отвергается. Следовательно, наличие weighted не доказывает готовый `passed / total` при любом исходе.

По последующему [решению 53](../../refactoring-plan.md#decision-53) принимается завершённый достоверный набор исходов; обычные непройденные тесты входят в него и сохраняют частичный балл `passed / total`. Полная ошибка исполнителя и невалидный/неполный отчёт не дают оценки по обрывкам и не означают нуля студенту: результат не установлен, прежний лучший результат сохраняется. Отдельного пользовательского выбора «как начислить из прерванного запуска» нет. Надёжность проверяется при разработке и отрицательной квалификации по пунктам 49/41; единица параметризованного/динамического теста, discovery и обработка пропусков/прерываний, компиляции/API и таймаутов — технические границы, а не автоматически выбранные политики баллов. В частности, самостоятельная политика таймаута одного теста не принята. Это требование, не доказательство отсутствия сбоев; живой UI/сервер не проверены, новое исполнение не запускалось. Исторические факты выше и сравнение ниже сохраняют свои границы.

### Принятый принцип результата

29 октября [пунктом 37](../../refactoring-plan.md#decision-37) принято для **всех оценочных тестов**: при компиляции — файл/строка/диагностика; при нарушении базового starter API — метод/конструктор; для теста — русское понятное имя, свойство, expected/actual и локализация различия по применимости; при исключении/таймауте — причина и проверка. Данные должны соответствовать stdout/API/состоянию/байтам, без лишнего технического шума. Обычные JUnit names/assertions не требуют второго ручного описания каждого теста в YAML/карточках.

Инфраструктурный сбой не является ошибкой решения: результат пока не установлен. Полный автоматический зачёт показывается отдельно от ожидающей ручной части 20%. Demo — малый необязательный selfcheck; его успех не равен всему набору. Фактический UI, точный payload и исполнение на портале ещё не проверены. Ниже открыты способы доставки этого принятого результата, а не повторный выбор принципа.

### Выбор и варианты

Пользователь уже выбрал обычные Java/JUnit, необязательную самопроверку и раздельную форму сдачи. Открытый технический выбор — как сохранить один канон тестов при разных исполнителях и понятный результат, не сохраняя обязательный второй ручной протокол каждого теста.

| Вариант | Что переиспользуем | Цена сопровождения и предел |
| --- | --- | --- |
| Узкий адаптер стандартных событий JUnit и диагностики компилятора | Имеющийся listener, классификацию стадий, обычные имена/assertions, нынешний формат внешнего результата PL | Нужен явный отбор публичных сообщений и идентичность каждого вызова; сохраняются отдельные допуски API/полного набора. Наименьший объём изменения текущего пути |
| Единый результат стандартного запуска Gradle/JUnit, преобразуемый в результат PL | Обычный Gradle/JUnit и отчёт исполнителя | Нужно доказать соответствие пропущенных/динамических тестов, оценивания, таймаутов и стадий; одного XML недостаточно для нынешних гарантий API/полноты. Выбор формата не устраняет адаптер |
| Запуск всей локальной Gradle-сборки и в PL | Тот же сборочный сценарий | Сильнее сближает окружения, но расширяет состав исполнения, зависимости и стоимость. Нынешний закреплённый путь этого не обещает; для простых задач не требуется как первый шаг |

**Кандидат-рекомендация:** начать с первого варианта. Оставить тесты обычным JUnit, общие утилиты — обычными библиотеками, а классификацию исполнения и преобразование результата — тонким адаптером Platform. Не требовать `public-case` от каждого нового обычного теста. Использовать нынешние наблюдения как совместимый переход там, где они ещё нужны; не удалять его до проверки нового пути.
Сопоставление стандартного Gradle-отчёта можно исследовать отдельно для проектных задач; запуск Gradle в PL не становится обязательным следствием локального `gradle test`.

### Конкретный сценарий

Студент меняет `Main.java` и получает ошибку компиляции. Полезный результат называет стадию, присланный файл, строку и сообщение компилятора. Он не предлагает «сопоставить результат массива», поскольку программа ещё не запустилась.
После исправления обычный тест с русским `@DisplayName` сообщает нарушенное требование и локальное различие, например индекс и ожидаемое/полученное значение. Полный результат отдельно поясняет, что успех demo не означает успех всего набора. Для API-задачи показывается операция или состояние объекта, а не искусственный stdin.
Принцип такого результата принят пунктом 37; конкретное оформление остаётся эскизом, не снимком работающего интерфейса.

### Позднейшая точечная проверка

Одна ошибка javac; одно понятное assertion; API mismatch; runtime/timeout; успешный обычный тест без `TestReporter`; параметризованный метод с двумя разными исходами; сбой контейнера и пропущенный тест. Проверить локальный и PL-пути, полный балл, русские подписи и фактический студенческий экран. Не принимать потерю события за ошибку решения.

## Допустимый API и проверяемый учебный результат

**Историческая формулировка решения 36 от 29 октября; носитель контракта уточнён пунктом 51 ниже:** будущие условия Book/Car и аналогичных задач прямо ссылаются на обязательные базовые сигнатуры канонического стартера. Сигнатуры не копируются вручную в QMD; их состав выверяется по учебной цели, все нынешние детали Book.java не утверждены. Стартер/доверенная проверка используют один контракт; за его пределами свобода сохраняется. Обычное смешанное оценивание — 80/20, полный перенос прежнего результата без ручной части остаётся исключением. [Точное решение](../../refactoring-plan.md#decision-36).

**Уточнение последующим решением 51:** носитель контракта выбирается по учебной цели и компактности: краткая текстовая сигнатура создаваемого класса/метода в QMD допустима без обязательной заглушки; комплексный состав описывает стартовый проект по ссылке. Обязательный тонкий стартер для Book/Car не выбран; конкретные API и объём готового кода открыты. [Решение 51](../../refactoring-plan.md#decision-51) уточняет прежнее предпочтение пункта 36, не меняя 80/20.

В [Book PublicChecks](../../../tasks/projects/objects/book-selection/student/src/test/java/PublicChecks.java#L25) проверяются состояние, порядок, кратность и сохранность входа через `TaskBinding`, а не stdout. Стартер [Book.java](../../../tasks/projects/objects/book-selection/student/src/main/java/Book.java#L3) при этом задаёт конкретные конструкторы/методы. Несоответствие свободного условия фиксированному клиенту уже разобрано в [аудите контракта](../extension-architecture-20261027/assessment-contract-audit.md); это историческая причина требования согласовать обязательный контракт и проверку; после решения 51 носитель может быть кратким текстом QMD либо стартовым проектом по ссылке.

| Подход | Когда оправдан | Цена |
| --- | --- | --- |
| Условие явно задаёт учебный API | Сигнатура сама является учебной целью | Простой проверяющий клиент, но требование нужно принять по смыслу задачи; нельзя добавлять ради удобства тестов |
| Проверяющая привязка переводит допустимую реализацию в предметные операции | Требуется свобода организации с проверяемым поведением | Адаптер принадлежит проверке, требует явного поддержанного случая; неподготовленная привязка не становится ошибкой студента |
| Поведение/свойства оцениваются по сданному коду вручную | Конструирование собственного API составляет результат | Меньше хрупких предположений, больше работы проверяющего; нельзя выдавать ручной маршрут за успешную автоматическую проверку |

**Последующее прямое решение от 29 октября:** [пункт 49](../../refactoring-plan.md#decision-49) делает приёмку активных кодовых задач обязательной перед выпуском: все объявленные корректные эталоны/альтернативы компилируются и проходят полный предметный автонабор; стартер проверяется по объявленному ожиданию; отрицательные контроли — по нужной проверке и причине, без подмены случайным compile/инфраструктурным сбоем. Развиваются существующие `references`/`verification-expectations`; JUnit, PL и ручная часть имеют отдельные результаты. Точные ключи и механизм ещё не утверждены, запуск не выполнен.

**Кандидат-рекомендация:** выбирать минимальный подход по смыслу каждой группы, а не единый механизм отражения для всех задач. Существующие `references`, разные ожидаемые исходы стартера и отдельные контексты решений следует обобщать, а не изобретать проверку решений заново. Исследование само политику не меняло; позднее прямое решение пункта 36 заменило 70/30 на 80/20, формы сдачи сохраняются.
Обсуждение автора нужно там, где учебный API действительно открыт. Имена технического адаптера и правила загрузки классов выбирает технический владелец.

## Читаемые ID и опубликованная идентичность

**Принято 29 октября, [пункт 38](../../refactoring-plan.md#decision-38):** ограниченная карта нынешнего перехода старое→новое, сохранение нужной опубликованной идентичности и контекстов, новые объекты штатно. Массовые повторные переходы не предполагаются; постоянный отдельный обязательный published key для новых задач не вводится. Пользователь указал уже предусмотренный необязательный UUID задачи: его требуется переиспользовать для связки, а не вводить дублирующий механизм. Точное поле и прохождение через декларацию/модель/export ещё нужно адресно сверить перед реализацией. Карта охватывает question/work/slots/completion и отдельно старые URL/anchors/QRC/Moodle; точный формат/хранение не выбраны.

### Что реально связано сейчас

| Объект | Нынешний источник идентичности | Следствие переименования |
| --- | --- | --- |
| Вопрос PL, просмотренный путь PL 8.3 | `uuid(courseId + '/' + exerciseId)` | В этой формуле изменение `exr` меняет UUID; связку с предусмотренным optional UUID необходимо адресно проследить |
| Курс и экземпляр | `identity('course/'+courseId)`; `identity('instance/'+instance, courseUuid)` | Новая строка не означает перенос истории существующего экземпляра |
| Работа | `identity('assessment/'+work.id, courseUuid)` | Изменение `sec`/work ID меняет оценочную работу |
| Слот | `courseId/workId/localSlotId`; fixed использует exercise ID | Одного сохранённого question UUID недостаточно для результатов слота |
| Назначение/метка | Метка зависит от имени и экземпляра; bridge связывает delivery, work и время выдачи | Новое назначение может отсечь прежнюю попытку, даже когда вопрос тот же |

Источники: [вопрос](../../../tasks/_extensions/Afonenko-Course-Tools/course-prairielearn/application/export-course.ts#L361), [курс/экземпляр/метка](../../../tasks/_extensions/Afonenko-Course-Tools/course-prairielearn/application/export-course.ts#L163), [работа](../../../tasks/_extensions/Afonenko-Course-Tools/course-prairielearn/application/export-course.ts#L440), [слоты](../../../tasks/_extensions/Afonenko-Course-Tools/course-prairielearn/application/slots.ts#L4), [completion](../../../tasks/_extensions/Afonenko-Course-Tools/course-prairielearn/application/completion.ts#L15).

Штатный PL сохраняет UUID при переименовании каталога, но UUID уникален лишь внутри своего контекста. Скопированный UUID в другом курсе не переносит студенческую историю. [Официальный договор UUID](https://docs.prairielearn.com/uuid/).
В просмотренных entry paths PL 8.3 UUID вычисляется приведённой формулой. Это ограниченное наблюдение не устанавливает отсутствие указанного пользователем optional UUID: точное поле и его прохождение через декларацию/модель/экспорт нужно сверить адресно и переиспользовать, не создавать новый UUID-механизм. При этом [валидатор Platform](https://github.com/Afonenko-Course-Tools/prairielearn-platform/blob/v2.4.1/tools/delivery_verification.py#L44) сверяет UUID вопроса с binding, не требует пересчитать его из нового читаемого имени. Это граница технической проверки существующего пути, не доказательство готового маршрута миграции.

### Принятый предел и сохранённое сравнение вариантов

1. **Ограниченная карта совместимости в выпуске:** сохраняемые опубликованные UUID/контексты и перевод старых ключей на новые читаемые ID. Новые объекты используют штатную формулу. Нужны полнота, отсутствие коллизий и согласованный перевод слотов/ссылок. Наиболее явный кандидат для принятого удаления `j25`.
2. **Устойчивый published key рядом с авторским именем:** последующие переименования не требуют заново описывать всю карту. Это удобнее при частых изменениях, но добавляет авторскую сущность и постоянный договор; не стоит вводить без показанной необходимости.
3. **Полностью новые native identities с административным переносом:** честно разделяет существенно изменённые вопросы, но увеличивает объём сверки и подготовки целевых записей. Не нужен только ради чистки названий.

**Первый вариант принят пунктом 38** для нынешнего ограниченного перехода. Второй — постоянный обязательный published key — не выбран. Новые объекты создаются штатно; третий путь при существенном изменении смысла остаётся предметом адресного обоснования, а не автоматического пересоздания всех вопросов. Карта должна связывать старый и новый объект по сохранённой идентичности и источнику, а не только по новому label. Не создавать универсальный движок миграций.
Для сайта отдельно проверяются URL/якоря/QRC и внешние входы Moodle; они не равны UUID. `j25` в техническом требовании JDK не переименовывается механически.

### Сохранить на месте или переносить

Текущее [сопоставление вопросов](https://github.com/PrairieLearn/PrairieLearn/blob/eeca6f48c27e8a5cf4c285479b8dce7d2f579163/apps/prairielearn/src/sprocs/sync_questions.sql#L43) предпочитает UUID в том же course; [работ](https://github.com/PrairieLearn/PrairieLearn/blob/eeca6f48c27e8a5cf4c285479b8dce7d2f579163/apps/prairielearn/src/sprocs/sync_assessments.sql#L65) — в том же course instance. Совпавшая запись получает новое имя, а не новый DB ID. Связь вопроса с работой обновляется по паре `(question_id, assessment_id)`; её перенос в другую работу не переносит автоматически прежний `instance_question`. [Membership](https://github.com/PrairieLearn/PrairieLearn/blob/eeca6f48c27e8a5cf4c285479b8dce7d2f579163/apps/prairielearn/src/sprocs/sync_assessments.sql#L535).

| Изменение | Кандидат с наименьшим переносом | Что не следует обещать |
| --- | --- | --- |
| Только source path или читаемое `exr/sec`, прежний контракт | Сохранить вопрос, работу и membership; отделить новый ID от опубликованного UUID, старую выдачу сохранить; при необходимости административно поднять зачёт прежнего auto pass | Нынешний derive-экспортёр сделает это сам; одной сохранности question UUID хватит для slots/bridge |
| Редактура пояснения без изменения входов и результата | Тот же native объект, если старые варианты/ответы всё ещё читаются; сохранить старую выдачу как свидетельство | Любая правка текста семантически совместима; прежний variant обязательно соответствует новым файлам вопроса |
| Существенно новый API/условие/формат ответа | Сопоставить сохранение объекта с новым объектом и признанным прежним зачётом; новый объект предпочтительнее, если чтение старой сдачи становится двусмысленным | Требуется новая студенческая пересдача; старый код прошёл новые тесты |
| Перегруппировка вопросов, split/merge работы или задачи | Сохранить native identities там, где сохраняются реальные объекты; для новых отношений явно сопоставить зачёт и evidence | История одной работы автоматически стала историей другой; одному старому UUID можно придать два разных новых объекта без решения о преемственности |

Итак, создание всех записей заново не является обязательным первым шагом. Для простого переименования сохранение на месте уменьшает перенос данных; для split/merge и несовместимого контракта исходная карта должна сначала описать реальные связи. Во всех случаях ещё нужны проверки старого variant, доступности файлов/условия, замены delivery и последующих повторов; soft-delete DB-строки не гарантирует прежний студенческий доступ.
Если одна прежняя задача распадается на несколько новых или несколько объединяются, остаётся настоящий авторский вопрос преемственности: какие новые позиции покрывает признанный прежний результат. Это не повод пересматривать уже принятое освобождение от пересдачи; требуется показать конкретную пару старого и нового состава, а не выбирать универсальное правило заранее.

**Сценарий:** `exr-j25-reverse-array` становится читаемым активным ID; условие и контракт ответа не меняются. Новый ID виден на сайте, прежний вход ведёт к нужному материалу, PL узнаёт существующий question/assessment context. Перевод slot lookup сохраняет completion. Это ожидаемая совместимость, а не результат нынешнего экспортёра.
**Позднейшая проверка:** предварительный diff create/rename/retire; одна старая ссылка; одна fixed и одна choice позиция; прежний question UUID и assessment membership; отсутствие двойного веса; действительный студенческий список 10 лабораторных, тренировки и резерва вместо 87 технических обёрток.

## Перенос принятого полного зачёта

### Что позволяет штатный механизм

Принятый пользователем смысл: полностью успешная прежняя автоматическая проверка даёт полный зачёт новой задачи без ручной части; переносятся именно успешное решение и старая выдача, даже при новом несовместимом контракте. Эти принципы не являются открытым выбором.

Текущая [документация CSV](https://docs.prairielearn.com/manualGrading/#uploading-the-scores-and-feedback) разрешает полную оценку, компоненты и feedback, но игнорирует `submitted_answer`. Импорт балла не является импортом кода. Документированный [API](https://docs.prairielearn.com/api/) даёт чтение результатов и синхронизацию курса, не общий публичный endpoint записи решения/зачёта.

Новые перепроверенные детали источника:

- [score-upload.sql](https://github.com/PrairieLearn/PrairieLearn/blob/eeca6f48c27e8a5cf4c285479b8dce7d2f579163/apps/prairielearn/src/lib/score-upload.sql#L30) требует существующую целевую `instance_question`; submission может отсутствовать. Поэтому «сформировать CSV для нового вопроса» ещё не создаёт весь целевой контекст.
- [manualGrading.ts](https://github.com/PrairieLearn/PrairieLearn/blob/eeca6f48c27e8a5cf4c285479b8dce7d2f579163/apps/prairielearn/src/lib/manualGrading.ts#L682) создаёт job `Manual` только при существующей submission. Оценка самой instance_question может измениться и без неё. Это разные уровни аудита.
- [manualGrading.sql](https://github.com/PrairieLearn/PrairieLearn/blob/eeca6f48c27e8a5cf4c285479b8dce7d2f579163/apps/prairielearn/src/lib/manualGrading.sql#L553) снимает `requires_manual_grading`, но оставляет `unanswered`, если вопрос был таким. Пользователь разрешил освобождение от ручной части; проблема здесь — точный статус completion, а не требование сохранить pending.
- [Обновление оценки](https://github.com/PrairieLearn/PrairieLearn/blob/eeca6f48c27e8a5cf4c285479b8dce7d2f579163/apps/prairielearn/src/lib/manualGrading.ts#L724) пересчитывает assessment и вызывает LTI outcome update. Это не доказывает автоматическое согласование с отдельным Gateway/Moodle AGS.
- [Bridge](https://github.com/Afonenko-Course-Tools/prairielearn-platform/blob/v2.4.1/bridge/native.sql#L54) выбирает попытку после текущей выдачи назначения; читает текущие `score_perc`, `status`, manual flag. [Договор bridge](https://github.com/Afonenko-Course-Tools/prairielearn-platform/blob/v2.4.1/docs/community-gateway-bridge.md#L34) явно отличает последнюю попытку от лучшей оценки журнала. Значит успешный импорт в старую попытку нельзя считать завершением нового назначения.

Важна и арифметика представления зачёта. В прочитанном [manualGrading.ts:636–666](https://github.com/PrairieLearn/PrairieLearn/blob/eeca6f48c27e8a5cf4c285479b8dce7d2f579163/apps/prairielearn/src/lib/manualGrading.ts#L636) полный `score_perc` вычисляет ручные баллы как полный результат минус имеющиеся автоматические. Исторический вычислительный пример по прежнему соотношению (пункт 36 уже задаёт 80/20): при максимумах 70/30 и текущих auto=0 импорт одного total=100 даст manual=100, а не обычные компоненты 70+30. Это статическая подстановка в прочитанный код, не выполненный импорт. Штатные раздельные компоненты позволяют иной способ отражения признанного прежнего результата, но его подписи, аудит и последующее обновление нужно проверить. Нельзя слепо считать любой CSV с числом 100 эквивалентным по показу и устойчивости. Административно признанный auto-компонент также не следует подписывать как успех новых тестов.

### Куда прикрепить старый код

Штатные [личные вложения](https://docs.prairielearn.com/assessment/configuration/#student-attached-personal-notes) — готовый кандидат хранения старых 1–2 файлов/выдачи рядом с задачей, а не сдача новым тестам. Но нынешний [путь добавления](https://github.com/PrairieLearn/PrairieLearn/blob/eeca6f48c27e8a5cf4c285479b8dce7d2f579163/apps/prairielearn/src/pages/studentInstanceQuestion/studentInstanceQuestion.ts#L57) требует открытый/доступный контекст и variant; пользователь может удалять свои `student_upload`. [Чтение](https://github.com/PrairieLearn/PrairieLearn/blob/eeca6f48c27e8a5cf4c285479b8dce7d2f579163/apps/prairielearn/src/pages/studentAssessmentInstanceFile/studentAssessmentInstanceFile.ts#L19) связано с assessment и `allowPersonalNotes`.
Таким образом, штатный UI подтверждает частный доступ, но не готовый массовый административный импорт и не неизменяемость свидетельства. Нельзя обещать привязку вложений одним CSV или ссылкой в публичный `clientFilesQuestion`.

### Реальные маршруты

| Маршрут | Цена | Остающийся технический разрыв |
| --- | --- | --- |
| Штатный административный полный зачёт + частные вложения/пояснение происхождения | Минимальный дополнительный механизм; использует native журнал оценки | Подготовка target context, честная запись переноса, доступный файл и устойчивость после sync/новой попытки/назначения |
| Сохранение существующего native question при совместимом переименовании + штатное начисление | История остаётся у того же объекта; меньше переносимых связей | Новый UI/контракт обязан читать прежние сохранённые данные; смена работы/слота всё равно требует сверки |
| Узкое расширение административной операции поверх native возможностей | Можно атомарно связать основание, файл и нужный completion | Дополнительный код и сопровождение; оправдан только конкретным доказанным недостатком штатного маршрута, не новый сервис/журнал по умолчанию |

**Кандидат-рекомендация:** начать с первого маршрута, сохранить второй для совместимых идентичностей, третий рассматривать лишь после адресной проверки provisioning/status и устойчивости начисления. Полный зачёт — административное признание прежнего результата, не утверждение о прохождении нового теста и не фиктивная педагогическая рецензия.
Нельзя автоматически заменить это постоянным реестром Gateway: итог должен быть согласован в PL, completion и Moodle.

**Конкретный сценарий:** студент ранее полностью прошёл автоматическую проверку reverse-array. Сверка выбирает именно ту submission и её исходник. В текущей задаче видны полный зачёт и пояснение «перенесён по прежнему успешному результату»; старые файлы и выдача доступны рядом. Новые тесты над этим кодом не запускаются ради основания переноса. Студенту не навязывается новая сдача; новое несданное задание не выдаётся за старую самостоятельную попытку.

### Будущая адресная приёмка

1. Снять точные фактические версии и scoped identities; сопоставить исходную успешную попытку, новую задачу, работу, слот, студента и внешнюю связь Moodle. PR27 и документация не заменяют работающую базу.
2. На изолированном примере подготовить ещё не посещённую целевую задачу. Проверить отдельно создание instance/variant/submission, итоговый статус и журнал административного основания. Не имитировать студенческое прохождение новых тестов.
3. Проверить полный балл и доступность вложений в PL, затем completion/Gateway/Moodle; повтор операции не должен удваивать зачёт.
4. Повторить sync, новую неуспешную попытку, смену/повтор выдачи назначения и пересчёт. Перенос не должен исчезать незаметно. Это главный технический риск, а не вопрос о необходимости повторной ручной проверки.
5. План восстановления сохраняет ответы, полученные после переключения: простая загрузка старой резервной копии может их потерять. Файлы/история сохраняются и для разрешённого сброса частичного прогресса.

## Вопросы для короткого разговора

- На примере ошибки компиляции и API-задачи: доходят ли принятые сообщения до фактического студенческого экрана, различимы ли автоматический результат и ожидающая ручная часть? Технический формат payload автор выбирать не должен.
- На `Book`/`Car`: какие сигнатуры соответствуют учебной цели, достаточно ли компактного контракта в QMD или нужен стартовый проект и сколько кода он даёт? Решение 51 уточняет носитель контракта; 80/20 сохраняется, конкретный API и объём готового кода ещё не утверждены.
- На одной лабораторной: как студент различает обязательную работу, тренировку и резерв? ID, UUID и slot mapping обсуждаются технически отдельно.
- По переносу новый принцип выбирать не нужно: уже принятый полный зачёт требуется осуществить честно и устойчиво. Для автора достаточно наглядно проверить конечный результат; механизм должны доказать технические владельцы.

Прямые решения пунктов 35–38 имеют приоритет; остальные варианты и рекомендации этого приложения остаются непринятыми до прямого решения пользователя. Следующая беседа может выбрать один предметный вопрос; приложение не запускает старые очереди, импорт или рефакторинг.
