# CUE и TypeScript в проверках курса и расширений

**Уточнение от 29 октября:** пользователь выбрал исполняемый TS-канон и исключение CUE из целевого решения, включая dev/reference-схемы ([пункт 35](../../refactoring-plan.md#уже-принятые-решения-и-сохраняемые-требования)). Факты этого исследования сохраняются; прежняя рекомендация оставить CUE заменена прямым решением. Нынешние CUE-проверки — реализация/эталон до переноса, не постоянный целевой fallback.

Исследование от 28 октября 2026 года. **CUE сейчас приносит конкретную пользу: проверяет не только форму данных, но и отношения между заданиями, работами и правилами адаптеров. Его уникальная необходимость не доказана: эти проверки можно написать на TypeScript. Однако один большой модуль подробных статических типов не заменит исполняемую проверку внешних данных.**

## Где есть дублирование и пределы

Core уже повторяет часть правил CUE в [release.ts:73–119](../../../tasks/_extensions/Afonenko-Course-Tools/course-core/domain/release.ts#L73): уникальность, ссылки, slots, stage/visibility. TS-проверки дают более предметные source/ID/related/hint; CUE независимо проверяет собранные данные. Это реальное пересечение, но не доказательство, что любую из границ можно убрать без замены гарантии.
Нынешние [TS-интерфейсы](../../../tasks/_extensions/Afonenko-Course-Tools/course-core/domain/model.ts#L3) слабее CUE: `nested: number` вместо 0, `unknownAttributes: string[]` вместо пустого списка, свободные строки runtime и открытые поля check. Усилить эти типы полезно независимо от дальнейшего выбора CUE. Словарь `contract-vocabulary.json` уже является одним каноном для производных CUE/TS/Lua; эти копии не надо превращать в три ручных определения.

Обратный предел тоже важен: `package.cue` оставляет AST/resources открытыми списками, а `closedKey` — произвольным значением. Его успешная проверка не доказывает полноту AST, публичность, сохранность ресурсов или native proof. Например, публичный Body получается **после** проверки полного пакета явным исключением полей в [producer.ts:355–372](../../../tasks/_extensions/Afonenko-Course-Tools/course-core/body-export/producer.ts#L355). Перенос JavaBuild/API-precheck из Core к владельцу runtime — самостоятельный вопрос архитектурной границы, не аргумент против языка CUE.

### Проверка и нормализация не равны

Для `{ "answer": { "type": "manual" } }` существующий `cue vet` успешен, а `cue export -e answer` возвращает ещё `"submission": "text"`. Схема дополнила значение литералом; успех проверки не утверждает, что это поле уже было в исходном JSON.
В [native Lua](../../../tasks/_extensions/Afonenko-Course-Tools/course-core/native-answers.lua#L15) возвращённый export декодируется; [TS fallback](../../../tasks/_extensions/Afonenko-Course-Tools/course-core/body-export/answer.ts#L13) выполняет vet, затем использует исходный `data`. [validateRelease](../../../tasks/_extensions/Afonenko-Course-Tools/course-core/infrastructure/validate.ts#L34) тоже не возвращает нормализованный CUE-результат. Это уточняет уже известный предел эквивалентности путей, **не автоматически новый production-дефект**. Замена должна сохранять принятые/отвергнутые входы, нормализованный выход и проекции, а не только форму типов.

## Сколько CUE реально запускается

Native Core проверяет каждый answer-bank/choice до проекции; TS-обработка ответа в Body — запасной путь, когда нет уже подготовленного `fullAnswers`, а не обязательная повторная проверка каждого ответа. PL выполняет native vet деклараций/политик в подходящем контексте. Release-проверка запускает **один** vet Core и всех явно активных adapter rules вместе. В конце Body есть отдельный vet пакета; manifest-схема сама по себе не добавляет subprocess при каждом collect.
Это подтверждают [native-answers](../../../tasks/_extensions/Afonenko-Course-Tools/course-core/native-answers.lua#L15), [переиспользование ответа](../../../tasks/_extensions/Afonenko-Course-Tools/course-core/body-export/producer.ts#L205), [release vet](../../../tasks/_extensions/Afonenko-Course-Tools/course-core/infrastructure/validate.ts#L34), [PL native](../../../tasks/_extensions/Afonenko-Course-Tools/course-prairielearn/native.lua#L61). У Cloud остаются отдельные native вызовы; у QRC [пример-тест](https://github.com/Afonenko-Course-Tools/quarto-reference-catalog/blob/3df2110e9f525f03f3ecb4926b5d55718e955c4c/tests/example.ts#L47) использует CUE как JSON Schema-валидатор каталога.
CLI и временные файлы создают дополнительную работу, но её длительность здесь неизвестна. Прежние пары `course-performance` измеряли другой вопрос, не CUE против TS. Ни процент стоимости CUE, ни ускорение замены не установлены; число вызовов нельзя выдавать за измеренные секунды.

## Реальные варианты вместо большого модуля интерфейсов

| Вариант | Польза | Цена и обязательное условие |
| --- | --- | --- |
| Сохранить CUE для декларативных политик владельцев, усилить типы TS | Сохраняет работающие отношения Core + активные адаптеры и общий договор Lua/TS | Остаются два языка/CLI; согласовать один канон каждого правила и убрать только доказанное лишнее повторение |
| Исполняемые TS-схемы владельцев + вывод статических типов | Может объединить форму, runtime-проверку и тип потребителя; Zod или TypeBox/Ajv — готовые семейства средств | Межобъектные правила остаются исполняемыми функциями; нужны композиция активных owners, ранняя Lua-стадия, unknown-key политика и эквивалентная нормализация. Не один гигантский общий модуль |
| Переносимая JSON Schema для формы + предметные проверки владельцев | Удобнее общий контракт внешних потребителей и IDE | Динамические ссылки, уникальность по вычисленному ключу и графовые политики не сводятся к обычному `uniqueItems`; появляется явная граница формы и смысла |

Подробные TS-типы не выполняются над `JSON.parse` или Lua JSON: [TypeScript прямо описывает стирание type assertions](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#type-assertions). При этом написать все нынешние проверки в обычном runtime TypeScript возможно. Например, [Zod refinements](https://zod.dev/api#refinements) позволяют добавлять проверки сверх формы; стандартный object нельзя незаметно использовать с удалением unknown keys вместо прежнего отказа. [TypeBox](https://github.com/sinclairzx81/typebox) и [Ajv](https://ajv.js.org/guide/typescript.html) — другой путь, а не обязательные дополнительные слои поверх Zod.
Автогенерация не решает всё бесплатно: [генерация JSON Schema из CUE](https://pkg.go.dev/cuelang.org/go/encoding/jsonschema#Generate) имеет экспериментальный статус; [cuetsy](https://github.com/grafana-cold-storage/cuetsy) — архивированный эксперимент CUE→TS, не готовый исполняемый валидатор. Огромные вычисляемые TS-типы также имеют цену компилятора/IDE ([TypeScript Performance](https://github.com/microsoft/TypeScript/wiki/Performance)); весь динамический граф курса не следует превращать в рекурсивную систему типов.

**Историческая рекомендация агента — заменена решением пользователя от 29 октября (пункт 35):** действующие CUE-проверки пока сохранить как рабочую реализацию и эталон поведения. Не распространять CUE принудительно на Print/Moodle и другие потребители, уже имеющие TS-декодеры. Для целевого упрощения сравнить первый и второй варианты на одном answer и одной Course + adapter композиции; полноценный исполняемый TS-канон — реальный кандидат, большой модуль одних типов — нет. Не оставлять двойную постоянную валидацию как самоцель и не выбирать новый механизм лишь по числу строк.
Общий принцип — **один принадлежащий владельцу исполняемый контракт на границе данных, типизированный результат для потребителя и отдельно проверки среды/актуальности**. Native Quarto-наследование не передаётся ни CUE, ни новому TS-resolver.

### Какая приёмка понадобится при замене

Одинаковые положительные/отрицательные входы и нормализованные выходы; неизвестное поле, литерал по умолчанию, числовая граница, дубли/ссылка, конфликт Core + адаптер; ранняя ошибка до проекции; source/ID/field и различие неверных данных от отсутствующего инструмента. Затем один установленный потребитель. Только отдельное сопоставимое измерение может ответить о стоимости CLI/нового пути. На дату исследования схема/библиотека/перенос ещё не были выбраны; позднее пункт 35 утвердил TS-направление без CUE. Конкретная библиотека, API и реализация по-прежнему не выбраны.
