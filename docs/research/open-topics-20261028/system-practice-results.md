## Конкретный новый разрыв: пустой каталог теряется

Нынешний [Archive][sp-support] содержит **два** вида фактов: `files: dict[path,bytes]` и `directories: set[path]` (строки 29–32). Читатель сохраняет явные пустые каталоги и выводит родительские каталоги из файлов, отвергает противоречие «путь и файл, и каталог», ссылки и повторные имена (35–67). [Проверка work-environment:25–40][sp-check-work] объединяет файлы и каталоги перед проверкой отсутствия work.

Следовательно, два дерева с одинаковыми файлами, но с дополнительным пустым `survey/work`, различаются по условию и нынешнему предикату. Транспорт, передающий только выбранные file bytes, не различает эти деревья. Это логический контрпример по исходнику, не выполненный student-тест.

У прочитанного pinned upstream [workspace.ts:733–748][up-workspace] резервный путь получения сдачи открывает gradedFiles, затем добавляет в ZIP каждый file stream; отдельных directory records в этом цикле нет. [graded-files.ts:28–103][up-graded] выбирает совпавшие пути, открывает их как файлы и предоставляет потоки. Поэтому нельзя без дополнительного свидетельства преобразовать такой набор в Archive с полным фактом отсутствия каталогов. Даже наличие слова directory в [vendored schema][platform-schema] не доказывает сохранение пустых каталогов конкретным путём исполнения. Работающий контейнер сначала опрашивается отдельно, затем возможен этот filesystem fallback; весь host-путь здесь не квалифицирован.

**Кандидат:** транспорт фиксирует полный ограниченный снимок учебного дерева, включая пустые каталоги и типы узлов, либо сообщает, что эта часть состояния не установлена. Перечень каталога в присланном студентом manifest — утверждение студента; он не становится доверенным наблюдением от одного хеша. Для автоматического сбора нужна привязка перечня к тем же фактически прочитанным байтам/моменту снимка. Точная схема и способ фиксации не выбраны.

## Как переиспользовать проверки без двух валидаторов

Предметная граница — уже прочитанное состояние с проверенными относительными именами, типами узлов, байтами и происхождением стартового комплекта. Upload и Workspace должны приводить к этой границе разными адаптерами там, где контракт результата одинаков; затем выполняются предикаты конкретной задачи. Разные результаты не обязаны сводиться к одному валидатору. Архивный разбор и сбор Workspace не должны сами решать, правильный ли порог или сколько строк в отчёте. Формат нового API здесь не утверждается.

| Существующий код | Переиспользуемая часть | Необходимое разделение |
| --- | --- | --- |
| [system_support.py:21–115][sp-support] | Безопасные имена, запрет ссылок/дубликатов/файлового конфликта, ограниченное чтение ZIP/tar.gz, files+directories | Это транспортный reader; не превращать его в новую учебную модель |
| [check_work_environment.py:13–48][sp-check-work] | Точные байты, сохранность, лишние учебные файлы, отсутствие work, читаемое пояснение | Сейчас expected одновременно включает три файловых результата и line-count; разделить два exercise-контракта до подключения |
| [check_data_processing.py:13–79][sp-check-data] | Семантический CSV для PowerShell, побайтовый fish, пустой файл, отсутствие missing-результатов, сохранность входов | Он не исполняет submitted script; runtime-наблюдение и оценка содержательного конвейера остаются отдельными |
| [Repository:31–116][sp-check-git] | Чтение объектов/refs/index, режимы, разбор config как данных без его активации | Читатель данных не равен проверке всех семи задач и не должен выполнить hooks/config из сдачи |
| [Git check:194–288][sp-check-git] | Поиск отношений истории, сравнение двух копий и чистоты, синтаксический SSH URL | Монолит требует обе копии и merge-порог; ни самостоятельная SSH-история S0→S1, ни local-history по отдельности ему не соответствуют |

Для Git безопасный reader копирует только HEAD/index/packed-refs, objects и heads/tags, задаёт собственное окружение и отключает внешние протоколы/замены; submitted config читается через `--no-includes` как данные. Отклоняются внешние object stores, grafts, shallow/commondir/gitdir и незавершённые операции: [checker:31–61][sp-check-git]. Эти guards нужно сохранить независимо от доставки. Новый транспорт не должен обходить их только потому, что данные пришли из своего Workspace.

### Найденное различие статусов ограничения средства

[ArchiveLimit][sp-support] наследует ArchiveError и обозначает исчерпание ресурса без установленного нарушения учебного договора. ZIP reader ограничен 1000 записями и 8 MiB распакованных данных. Git checker отдельно перехватывает ArchiveLimit/ToolLimit и возвращает `automated: manual`, `toolLimited: true` ([283–285][sp-check-git]); work/data ловят общий ArchiveError и включают сообщение в `errors`, получая `automated: fail` ([work:46–48][sp-check-work], [data:77–79][sp-check-data]).

Это статически установленная разница, не результат запуска. При выделении общей границы следует различить некорректный транспорт, незавершённую проверку из-за лимита и установленное предметное несоответствие. Нельзя автоматически присваивать учебный отказ только за превышение технического лимита. Аналогично Git-лимит 256 коммитов, timeout 6 s и ограничение вывода относятся к возможностям средства, не к новому требованию задачи. Их политика требует технической приёмки, без изменения весов здесь.

## Git: минимальные данные и предел доказательства

Один рабочий файл не сохраняет историю; один набор коммитов не сохраняет текущий индекс. [Git описывает index как отдельные записи с режимом, object ID, stage и flags](https://git-scm.com/docs/gitformat-index). Для restore исходное условие различает HEAD/индекс/рабочий файл в промежуточной точке: после `restore --staged` notes в индексе — понедельник, в рабочем дереве — вторник. В B изменён только README; в финале всё чисто. Чистый итог A→B допускает разные предшествовавшие действия, поэтому не доказывает оба обязательных восстановления. Условие уже допускает краткие существенные status/diff либо показ, без полного журнала терминала: [version-control:398–426][sp-git].

Минимум для чтения предъявленного конечного Git-состояния: граф достижимых объектов с проверенными refs/HEAD, фактический индекс с его объектами и режимами, рабочие файлы, требуемые конфигурационные сведения как данные. Наблюдения промежуточных состояний — отдельное свидетельство; автоматически считать student log достоверным событием нельзя. Восьми успешных процессов или нескольких нулевых кодов недостаточно без связи с нужными входами, стадиями и результатом. Здесь процессы и их число не измерялись.

[Git bundle переносит выбранные refs и достижимые объекты](https://git-scm.com/docs/git-bundle), но не является снимком незакоммиченного индекса/рабочих изменений. Объекты, доступные только из текущего индекса, могут не войти в bundle выбранных refs. Варианту с sidecars понадобится явная полнота этих данных; восстановление «чистого index из HEAD» уничтожило бы значимое промежуточное различие restore. Связанный worktree тоже не обычная переносимая папка `.git`: [его `.git` указывает на private/common directories, HEAD/index отделены от общих refs](https://git-scm.com/docs/git-worktree#_details). Текущий reader требует собственный обычный `.git` согласно условиям; поддержку иных layout нельзя обещать без нового ограниченного контракта.

У GitHub/SSH совпадение двух локальных графов и SSH-строка remote устанавливают только локальные факты. [Условие:270–298, 340–356][sp-git] отдельно требует реальный обмен, ожидаемый login и доступ к Private либо согласованный показ. Один `ssh -T` exit 1 без соответствующего сообщения не доказывает успех; successful push/clone — другой результат. Секретный ключ, парольная фраза и настройки личного хранилища не являются данными сдачи. Автоматическая проверка архива не может достроить отсутствующее внешнее наблюдение.

**Историческая рекомендация, заменённая пунктом 42:** A как исходный переносимый путь, B как следующий способ получения снимка. **Принято вместо неё:** оба маршрута входят сразу в одну ближайшую реализацию будущего согласованного плана; общая проверка только для совпадающего контракта результата. Собственная ОС — полноценный маршрут, не аварийная замена. Оговорка прежнего исследования о C как основном транспорте всех Git-задач не ограничивает пункт 43: адресный bundle-upload для существующей задачи прямо выбран. Bundle не устраняет необходимость отдельно установить значимые index/worktree и обязательные наблюдения; конкретный состав этого случая ещё не принят. Сравнение не выбирает новые поля или собственный контейнерный runtime.

Workspace не заменяет Windows OpenSSH/системный агент там, где они выбраны условием; Linux-контейнер с PowerShell не доказывает результат Windows. Маршрут собственной ОС сохраняет эти наблюдения. Общий валидатор может исполняться в квалифицированной среде преподавателя/сервера, не требуя идентичного внутреннего окружения на машине студента.

## Что есть в upstream и чего пока нет у курса

На 28 октября официальная [документация Workspace](https://docs.prairielearn.com/workspaces/#infojson) описывает seed `workspace/`, `gradedFiles` относительно home, маски без скрытых файлов для `*`, optional wildcard paths и выключенную по умолчанию сеть. Это возможности upstream, не наблюдение сервера. Сохранение файла в IDE и submission для grader — разные действия. Внешняя проверка настраивается отдельно от IDE.

Для привязки к исходнику прочитаны Platform `1cab18c5e693210b2b52930cacb00ceb5acd9797` и указанный его [Dockerfile:1–2][platform-docker] upstream `92584fe426ececb84bc2d09de9975c7056c0c5f6`. Это Platform pin исследуемой Java-линии, **не доказанный pin развёрнутого SP-сервера**. Vendored [infoQuestion:274–353][platform-schema] допускает image/home/gradedFiles/environment/network. Pinned [graded-files.ts:33–103][up-graded] проверяет containment, запрещает обратную косую черту в имени, не следует symlinks, ограничивает count/size и закрывает handles. Это реальные guards транспорта, не семантическая проверка Git или файлового преобразования.

Базовый [compose][platform-compose] задаёт PL, Docker socket и `/jobs` для grader. Он не устанавливает в этом исследовании готовность workspace host, хранения, маршрутизации, возобновления или сети GitHub. Проверка актуального deployment не выполнялась; его готовность — UNKNOWN. Не предлагается собственная IDE, а требуется ограниченная интеграция уже имеющегося upstream с course exporter и общим результатным контрактом.

## Следующие адресные проверки при разрешённой реализации

1. Одна file-state сдача через A и B должна дать одинаковые предметные факты. Отрицательные случаи: лишний пустой work, удалённый исходник, неправильные байты, symlink, дубликат/конфликт имени; отсутствие данных при неполной маске не превращается в «каталога нет».
2. Для одного Git-контракта проверить loose/packed refs и objects, HEAD/index/worktree, режимы, LF/CRLF; отдельный индекс и unstaged правка сохраняются при сборе. Ошибка/лимит транспорта не выдаёт предметный PASS/FAIL по отсутствующему снимку. Расширения index, включая split index, требуют заявленного охвата: нынешняя копия `.git/index` сама по себе не обещает все зависимые файлы.
3. Разделённые validators должны принимать разрешённые независимые file-state/launch и local-history/SSH входы. Restore и release требуют своих предикатов, а не вызова старого монолита под новым ID. Никаких новых учебных кейсов или весов этим исследованием не введено.
4. Runtime обработки данных квалифицировать отдельно: действительно исполненный сценарий, заменённые результаты, stdout/stderr/exit и разрешённые CSV-различия. Статические файлы/журналы и наличие непустого script не устанавливают работу алгоритма.
5. Workspace проверить старт → сохранение → закрытие/возобновление → повторная сдача → общий grader; полноту `.git`, пустых каталогов, согласованность snapshot и лимиты. Затем отдельно подтвердить внешний GitHub/SSH и Windows-маршрут. Здесь ни один из этих прогонов не выполнен.

## Вопросы для обсуждения

- Какой вход показывать первым после готовности Workspace: браузерную среду или локальный комплект, сохраняя полноценность обоих маршрутов и одну проверку результата?
- Как показывать отдельно «состояние проверено» и «нужно подтвердить обязательное действие/внешний SSH», чтобы частичная автопроверка не выглядела полным принятием?
- При техническом лимите допустим ли явный статус «нужен ручной разбор» с сохранённой сдачей, без объявления учебной ошибки?
