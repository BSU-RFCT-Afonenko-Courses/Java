## QMD и встроенный код

Обычный Markdown-форматтер нельзя без проверки объявить поддерживающим весь Quarto: здесь есть native Div/атрибуты, `{java}`-ячейки, `#|`-параметры, shortcodes, raw-блоки и служебный YAML. Первичные описания: [Markdown Quarto](https://quarto.org/docs/authoring/markdown-basics.html), [shortcodes](https://quarto.org/docs/extensions/shortcodes.html).
В таблице расширений Deno `.qmd` отдельно не указан. Принудительный Markdown parser — лишь кандидат проверки. У Prettier [встроенное форматирование включается отдельно](https://prettier.io/docs/options#embedded-language-formatting); это не обещание форматировать Java-блоки штатной поставкой и не доказательство сохранения наших конструкций.
Сначала проверить небольшой представительный набор QMD: вложенный Div, include/shortcode, блок с атрибутами, `#|`, служебный YAML, таблица, raw HTML, Java 25 и намеренно ошибочный код. Не менять пробелы в ожидаемом выводе/данных и смысл block scalar ради внешнего вида.
Неполные фрагменты и намеренно некомпилируемые примеры получают явные узкие исключения из неподходящих правил; не «исправляются» до другого учебного смысла и не исключают весь каталог из проверки.
Java/C#/C++/Python/Kotlin/Go/Rust внутри QMD тоже входят в область читаемости, но не требуют автоматически общего компилирующего конвейера всех языков: сначала отбор полных файлов и самостоятельных блоков, затем проверка допустимых фрагментов.

## Предлагаемый процесс

1. Установить общую политику и выбор файлов по владельцам: канон курса, исходники владельцев расширений, генераторы, производные результаты, сторонние зависимости, исторические примеры.
2. Выбрать и закрепить версии инструментов централизованно для нужного репозитория, не добавляя Node/Gradle в каждый самостоятельный проект. Начать с Java и проверенного набора QMD, затем покрыть перечисленные языки.
3. Разделить режим проверки без записи в CI и явное исправление разработчиком. IDE при сохранении использует ту же версию/настройки; IDE не единственный путь воспроизводимой проверки.
4. Если создающий исходники генератор существует, исправить его шаблон или применить форматтер при выпуске канонического файла. Генератор проверяется по результату и повторяемости; упаковщик копирует уже подготовленные исходники.
5. Отдельно проверять пригодность выдачи: читаемые исходники в ZIP и показе PL, точный выбранный состав, прежние учебные assertions/данные. Форматтер не заменяет компиляцию и JUnit; эти проверки сохраняют свою самостоятельную роль.
6. Новая массовая запись сейчас не выполняется. Для начала нужны выбор стиля/инструментов и техническая проверка Java 25/QMD/фактических toolchain, а не новая методика тестов или универсальный каркас.
