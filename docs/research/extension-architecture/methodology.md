# Метод исследования архитектуры и производительности

Подробная runtime-методика применяется после T00 на исследовательском ПК;
предварительное чтение авторской модели не требует закреплять inputs сейчас. Во время
подготовки этого пакета не запускаются примеры, тесты и измерения. Конкретные
исходники и toolchain здесь намеренно не закреплены.

## Сначала авторская модель

Перед function/call ledger описывается корень и каждый подпроект курса:
авторские входы, производные представления, общие ресурсы, vendor, закрытые
материалы и точки изменения. Проверяются типовые действия автора, literal и
смысловые дубли, устаревшие инструкции, архивы и доступность teacher inputs.
Разная педагогическая роль theory/lecture/practice/handbook сама по себе
не является дублированием; одинаковое имя файла не доказывает копию.

Штатные Quarto metadata/profiles/includes/resources сравниваются с actual
нуждой, а не считаются универсальной заменой. Include меняет контекст
относительных ссылок; перенос произвольного блока в `_metadata.yml` не
гарантирует, что project-level collector увидит его. Компактный source API
отличается от развёрнутого manifest, нужного проверяющему исполнителю.

Отдельные трассы: materialize → IDE → сохранение изменений; export →
qualification эталона/стартера/ошибочных вариантов → student grading →
auto/manual points → итог. Для Docker указываются actual caller, image,
число контейнеров по сценарию и sandbox, а не только слово «container».
В подготовке эти трассы исследуются чтением. Отсутствующие private данные
и невозможность воспроизвести сессию другого ПК остаются ограничениями.

## Единицы учёта и полнота

Дополнение к авторской карте — [хронология новых отказов и выпусков](publication-evidence-2026-10-27.md).
Её ссылки обозначают исторические evidence, не выбранную базу. В T00/R01
сопоставляются normal/emergency route, исходники, локальный итог чата и CI.
Отдельно помечаются прочитанный лог, утверждение PR, отсутствующий local receipt
и проверенная функциональная гарантия. Количество QMD, уникальных checks,
файлов, ZIP, jobs и контейнеров не взаимозаменяемо.

Различаются функция, место вызова, фактическое выполнение и внешняя реализация.
Одна необходимая функция может вызываться избыточно; один callsite может
исполняться на каждом документе или внутри вложенного цикла. Обоснование
функции не заменяет обоснование её частоты и области чтения.

Учитываются собственные TS/JS/Lua/Python функции, методы, локальные функции,
анонимные callbacks, closures и фабрики, top-level действия, динамические
imports/dispatch и вызовы системных/стандартных API. Каждая точка вызова
связывается с операцией. Для чистых однотипных вызовов допустимо общее
обоснование, но сохраняется список всех callsites. Чтение, запись, удаление,
публикация, FFI, внешние процессы, изменение env и межпакетные границы всегда
видны отдельно.

Python Platform и integration tooling входят наравне с расширениями; shell
функции и top-level команды образуют собственные операции/места вызова.
Учитываются import/decorator эффекты и запуск внешних программ. Для Python
используется доступный AST parser; для shell — доступный parser либо ручной
учёт с проверенным списком файлов/команд и явными unresolved связями. Нехватка
парсера не исключает язык из denominator и не превращает regex в полный AST.

Инвентарь извлекается доступными парсерами и средствами Performance. Поиск
текста помогает разведке, но regex-перечень не считается полным AST inventory.
Если Lua dispatch или generated binding нельзя разрешить статически, связь
помечается unresolved с перечисленными кандидатами. Отсутствие события в trace
не доказывает, что код не используется.

Первичная единица отчёта — операция и её инвариант; все функции и callsites
ссылаются на неё и поясняют свои отличия. Это позволяет обосновать весь код,
не переписывая одинаковый текст для каждого вызова стандартной библиотеки.

## Формат исследовательских данных

Используются обычные JSONL/CSV и Markdown, а не новая runtime-система. Каждый
владелец пишет только свой ledger; координатор собирает сводку. Конкретные
source spans и identities заполняются после задачи закрепления исходников.

| Таблица | Обязательные поля |
| --- | --- |
| functions | id, owner, module, symbol, source_span, origin, visibility, operation_ids, requirement_ids, invariant_ids, inputs, outputs, effects, failure_behavior, necessity_status, implementation_status, rationale, evidence_ids, alternative_ids |
| callsites | id, caller_id, callee_id или dynamic_target, source_span, activation_condition, phase, scope, cardinality_formula, reads, writes, processes, retained_resources, mutation_interval, invariant_ids, evidence_ids |
| invariants | id, statement, owner, requirement_origin, protected_subject, failure_scenario, consequence, trust_assumptions, detection_point, enforcing_callsites, limits, evidence_ids |
| evidence | id, claim, kind, scope, method, reference_ids, quality, limitations, status |
| references | id, upstream_project, API_or_pattern, relation, source, applicable_constraints, differences, license_if_copied, evidence_ids |
| alternatives | id, problem, mechanism, preserved_invariants, changed_contracts, cost_model, complexity, risks, required_evidence |
| decisions | id, hypothesis_ids, alternative_ids, result, rationale, evidence_ids, unresolved_questions |

Для release/recovery используется тот же ledger, а не вторая система учёта.
В `results/release-and-recovery.md` добавляются timeline и таблица переходов:
attempt/input tuple, stage, owner, result, evidence scope, earliest detection,
retry/cleanup, qualification debt и неизвестные. Минимально различаются
source release, runtime publication, render/export, qualification, admission
и server import. `DEFERRED_BY_USER / NOT_VERIFIED` не переводится в verified
или grading PASS при переносе между отчётами.

Для наблюдавшихся выполнений используются отдельные данные Performance:
сценарий, invocation/parent/process/executor, phase, размер входа, число
процессов и inspections, bytes read/hashed, FD и метрики с их качеством.
Статическая формула частоты не записывается как измеренное число вызовов.
Самостоятельный минимальный счётчик допускается только при недостаточном
существующем покрытии и с отдельной оценкой его влияния.

Для necessity_status используются: обосновано; требуется, но scope/частота
избыточны; доказанное дублирование; неподключённая возможность; неизвестно.
Для implementation_status отдельно фиксируются стоимость, сложность,
типизация, владение и нарушение контракта. Ненаблюдавшаяся функция не получает
статус «удалить» автоматически.

Дублирование доказано, когда совпадают предмет, контекст, защищаемый интервал
и результат проверок, а отдельного эффекта или требования нет. Повторное
чтение после внешнего процесса может быть необходимым. Неизвестное
обоснование — открытый результат исследования, а не разрешение удалить guard.

Для generated кода учитываются исходная схема, генератор и mapping производных
элементов. Исключения для trivial forwarding/accessors имеют явный список;
wrapper с env, ошибками, observation context или lifetime не считается
тривиальным без проверки.

## Высокоуровневые требования и модель доверия

До оценки SHA/proof перечислить поддерживаемые изменения: сохранение автором
страницы, генерация входов native hooks, прерывание, повторный запуск,
неуспешная публикация, конкурентный процесс, замена пути и восстановление.
Различать обычную ошибку автора, сбой инструмента и враждебную подмену тем же
владельцем checkout. Последняя модель не принимается молча как требование
локального учебного курса.

Для каждой защиты ответить: кто изменяет что; требуется ли идентичность bytes,
inode, permissions, активного run или только public payload; до какой записи
обнаруживать изменение; какие trusted компоненты принимаются; на каких
платформах это должно работать. Наличие A/use/B не обосновывает само по себе
любое количество nested boundaries. FFI/libc и no-replace операции получают
отдельное объяснение необходимости и переносимости.

Текущие tests и contracts являются свидетельствами принятых решений, но не
автоматически вечными продуктовыми требованиями. Конфликт с задачей автора
оформляется как вопрос об изменении контракта, а не разрешается скрытым
ослаблением проверки ради скорости.

## История и внешние references

Для решения проследить цепочку: исходная потребность или сбой → введённый
механизм → последующие расширения области → сегодняшние callers и ограничения.
На финально выбранных refs проверяются code, docs, tests, commits, PR и
сохранённые evidence. Старый отчёт не доказывает поведение новой линии.

До нового опыта строится lineage/capability/fix matrix. Номер SemVer и
`releases/latest` недостаточны: выбранный source может не содержать fix другой
линии. Раздельно фиксируются runtime, host-tools, registry/lock, raw source,
raw release assets и assembled output с разрешёнными overlay. Состав и
контракты важнее искусственного совпадения номеров. Непроверенный гибрид
веток не становится baseline молча; status docs сверяются с фактом CI/release.

Данные human/privacy/failed-report и срок исторической policy выясняются по
первичным доступным источникам. Наличие SHA поля не доказывает содержание
решения. Исследование не запускает stage/publisher/server и не продлевает
допуск; R03 описывает требуемое восстановление как предложение.

Для references различать: реальное заимствование; использованный public API;
похожий независимый подход; внешний аналог для сравнения; происхождение не
установлено. Сходство с Bazel или Ninja не доказывает перенос идей из них.

Начальные семейства для исследования:

- [Quarto](https://quarto.org/docs/extensions/creating.html): lifecycle,
  inspect, profiles, hooks, output lists, preview и incremental rendering;
  документация сопоставляется с исходниками реально используемой реализации.
- [Pandoc](https://pandoc.org/lua-filters.html): AST passes, filters, writers,
  native JSON, subprocess API и стоимость fragment conversion.
- [Deno](https://docs.deno.com/runtime/): typecheck, module graph/cache,
  processes, env, permissions и streams; отличие native и launcher execution.
- [CUE](https://cuelang.org/docs/): closed schemas, validation, schema evolution
  и сравнение наборов допустимых значений, направления input/output compatibility.
- [Ninja](https://ninja-build.org/manual.html) и
  [GNU Make](https://www.gnu.org/software/make/manual/): DAG, prerequisites,
  restat/depfiles, минимальная повторная работа и bounded parallelism.
- [Bazel](https://bazel.build/concepts/build-ref) и
  [Buck2](https://buck2.build/docs/): hermetic actions и цена сложной системы
  доказательств как сравнительный материал, а не выбранная замена.
- [Cargo](https://doc.rust-lang.org/cargo/) и
  [npm](https://docs.npmjs.com/): требования зависимостей, выбранный lock,
  integrity, offline use и обновление независимо от API совместимости.
- Реально используемые HTML/XML/ZIP библиотеки, схема PrairieLearn и native
  средства генерации типов/валидаторов: назначение first-party обвязки,
  уже решённые upstream задачи, поддерживаемые ограничения и лицензии.

References подтверждают конкретное решение и его применимость. Краткое чтение
официального API и исходного решения предшествует подборке общих статей.
На вопрос сначала достаточно одного нормативного и одного реализационного
источника; углубление требуется при противоречии, а не ради числа ссылок.

## Минимальный Java

Базой служит урезанная disposable копия реального курса, выбранная при передаче.
Она сохраняет root и пять видов подпроектов: theory, tasks, lectures,
practice, handbook. Это один сценарий архитектуры, а не требование во всех
микропроверках рендерить весь портал.

| Часть | Минимальное содержание |
| --- | --- |
| Root | Одна страница, композиция, profiles, search и переходы к подпроектам |
| Theory | Одна Markdown-страница с кодом, таблицей, формулой, изображением и QRC target/link |
| Tasks | Один документ банка и один документ работ; несколько различающихся упражнений и назначений |
| Lectures | Одна короткая Reveal-презентация с вертикальным слайдом и Navigation |
| Practice | Одна страница с учебным элементом и межпроектными ссылками |
| Handbook | Одна страница с кодом, вложением и ссылкой на исходники |
| Projects | Малый Java/JUnit и малый Gradle пример; public/common/closed partitions и контролируемая история, если она нужна реальному контракту |
| Explicit exports | Небольшие Body/Download/PrairieLearn/Print/Moodle сценарии; Cloud declaration отдельно от неподдерживаемых операций |

Карта возможностей связывает каждый содержательный элемент с требованием,
гипотезой, observer и проверкой результата. Разные случаи объединяются,
когда это не скрывает нужную ветвь: public/restricted, solution, fixed/choice,
manual/mixed/external, resources, common files и profiles. Не требуется тащить
в малый пример все настройки, предметные тексты или всю grading-инфраструктуру.
R/Python computations в базовом сценарии отсутствуют. Проверка VM, grading
server и внешних сервисов не изображается выполненной.

Генератор минимального примера сохраняет исходный курс, фиксирует сокращения
и создаёт только собственный disposable output. Источник истины для выбора
возможностей — high-level требования и actual course, а не старый N1 fixture.
Окончательный размер определяется полнотой ветвей; семь QMD — ориентир,
не жёсткий предел и не обещание покрытия.

В выбранные малые случаи включаются canonical и materialized QMD рядом,
сохранность модели между helper/native фазами, common inputs в source и
assembled workspace, optional-primary/ZIP и fixed API. Это отдельные ветви,
не дополнительный полный курс. Qualification использует только собственные
малые данные и предусмотренный sandbox; этот опыт не допускает реальный банк.

## Сценарии и оси масштаба

Сначала одиночная обычная страница, страница банка и Reveal; затем preview
до готовой страницы и правка текста в уже запущенном preview. Отдельно
изменяются metadata, общий исходник и ресурс, требующие более широкой
актуализации. Readiness означает готовый нужный результат, а не только строку
Listening. Измеряются save-to-visible latency и правильность выбранной страницы.

Затем полная композиция, warm repeat, student → full → student, selected Body,
materialization, ZIP и малые явные экспорты. CLI checks и release/installation
проверки относятся к отдельным сценариям.

Оси масштаба меняются по одной: число несвязанных документов при неизменной
выбранной странице; упражнения/назначения; metadata origins; common files;
bytes ресурсов; подпроекты; repeated questions и links/conditions. Начальные
геометрические ступени 1/4/16 — исследовательский выбор, который уточняется
после smoke; полный декартов набор запрещён как бессодержательное раздувание.
FD/currentness роста достаточно сначала проверить счётчиками и малым N.

## Три базы сравнения

1. Native reference: штатные Quarto-команды для содержательно сопоставимых
   готовых входов и выходов. Для портала учитываются все нужные команды,
   а не одна native страница против всей композиции.
2. Прямой обычный render с действующими расширениями и требуемыми функциями.
   Это основная пользовательская база для сравнения вариантов рефакторинга.
3. Тот же маршрут через public Performance off. Разница с прямым вызовом
   характеризует оболочку наблюдения, а не Core.

Summary/CPU/trace объясняют стоимость отдельно. Семантическая работа, которую
не делает native reference, перечисляется явно; её цена не называется чистым
overhead. Непосредственно comparable варианты сохраняют функции и инварианты.
Дополнительный renderer не используется как ускоренный «эквивалент» без
доказательства того же native поведения.

## Исполнение измерений и качество

- До новых запусков прочитать имеющиеся Performance/CI evidence и определить,
  какой недостающий вопрос действительно требует нового наблюдения.
- Матрица Cybersecurity из нового evidence note уже содержит сравнительные
  серии и traces. Проверить доступность raw data, версии и metrics domains;
  четырёхкомпонентное сравнение не локализует причину регрессии. Неполный
  старый результат не заменяет более поздний, но остаётся частью истории.
- Одновременно выполняется одна тяжёлая очередь: render, export, CPU profile,
  browser suite, compilation или benchmark. Аналитические агенты читают код.
- Не останавливать чужие процессы и не менять governor, caches ОС и настройки
  ноутбука. При неконтролируемой нагрузке отметить условие и перенести пару.
- Питание, текущая нагрузка, argv/cwd/env, outputs, cache policy, functional
  profiles, native flags и инструментальная оболочка записываются раздельно.
- Warmup исключается. Стартовая серия — пять последовательных пар AB/BA;
  увеличение числа пар зависит от шума и оставшегося бюджета. Эта схема не
  используется для сравнений с разным набором функций.
- Cold означает явно названный новый disposable output/cache, не холодный
  кэш ОС. Preview, warm full и clean full не смешиваются.
- Публикуются абсолютные секунды, медиана, разброс и uncertainty, дополнительно
  отношение к native и исходной реализации. CPU, IO, процессы, inspections,
  hashed bytes и peak memory имеют точные области учёта.
- Inclusive spans, parent/child и overlapping intervals не суммируются как
  wall. Lua CPU не смешивается с TS wall. GNU time RSS не считается пиком
  суммы памяти всех одновременно живых процессов.
- Один outer perf run передаёт контекст обычным children. Нельзя вкладывать
  public perf runners с конфликтующим telemetry env; async branches не меняют
  общий env. Jobs и уровень наблюдения независимы.
- Lost events, incomplete spans, неуспешная сборка и неполное coverage
  сохраняются в результате. Они не становятся нулевыми затратами или PASS.
- Непредусмотренное повторное выполнение большого Java запрещено. Сначала
  анализ raw data, затем один минимальный различающий опыт.
- Для отказов отдельно считать стоимость до ошибки, cleanup и повторяемые
  этапы. Gradle/toolchain hashing, контейнеры и assembly recheck учитывать
  только в тех сценариях, где они реально вызываются. При reuse указать,
  какие inputs/контракты делают evidence устаревшим; cold/warm не угадывать.

## Корректность и применимость

Проверяются selected outputs и их состав, семантика учебных элементов,
crossrefs/search/navigation, stable IDs, public/closed resources, ZIP contents,
требуемые audience и допустимые изменения source/config. Failure/interruption
проверяются адресно в isolated fixture с восстановлением. Изменения timestamps
и других native динамических данных перечисляются явно; универсальная
нормализация HTML не должна скрывать различия.

Малая fixture подтверждает конкретный механизм и закон роста, а не готовность
всего Java или всех платформ. Экстраполяция отдельно указывает предположения.
Финальная проверка большого курса обсуждается отдельной задачей после
исследования; она не включена в текущую подготовку и не подменяет малые опыты.

Если выбранная actual композиция не проходит smoke из-за дефекта продукта,
это сохраняется как baseline failure. Нельзя тайно заменить producer старым,
удалить падающий consumer или ослабить privacy, чтобы получить красивое время.
Для исследования других маршрутов используются явно отделённые работающие
подсценарии; минимальная исправляющая проба имеет отдельное имя варианта и
не называется исходной базой. Полный fail не запрещает статический анализ.

В fixture используются собственные учебные примеры и маркеры закрытых тел,
а не избыточная копия закрытого банка. Raw evidence с реальными closed данными
хранится в соответствующей области доступа; публичный PR получает только
разрешённые результаты и индексы. Обезличивание не меняет первичное evidence.

## Решение по каждому кандидату

Для каждого предлагаемого изменения представить: сохраняемое требование;
стоимость существующего механизма; происхождение идеи; минимум два применимых
варианта или объяснение единственного; изменение types/contracts/lifetime;
ожидаемый и измеренный эффект; риск; цену сопровождения; способ проверки.

Чисто статическое упрощение не объявляется ускорением. Быстрый вариант,
который переносит десятки проверок в новый общий runtime, не считается
автоматически лучшей архитектурой. Нужна граница Pareto по времени, сложности,
числу процессов и независимости владельцев, а не фиктивный общий балл.
