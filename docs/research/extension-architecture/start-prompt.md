# Старт исследования на другом ПК

Текст ниже предназначен для новой сессии после завершения чата
«Выполни план публикации банков». Ссылка на PR передаётся вместе с ним.

---

Выполни исследование по пакету `docs/research/extension-architecture` из
переданного PR Java. Текущая задача — исследование и предложения, не продуктовая
реализация. Порядок: T00 и начало R01 → A01–A12 и ранний отчёт → углублённые
T01–T13 и R02–R04 → T14–T15. Закрой 88 пунктов A/H/B с evidence/ограничениями.

1. Убедись, что чат **«Выполни план публикации банков»** завершил работу.
   Прочитай его итог, фактические worktrees/PR, known failures, evidence и
   расположение teacher root. Завершение не означает успешный экспорт:
   сохрани неуспехи и не повторяй уже сделанные дорогостоящие попытки без
   конкретного различающего вопроса. Не возобновляй тот план автоматически.
   Восстанови также отказы штатного выпуска, изменение стратегии, реальное
   согласование, failed/human/privacy reports и конечное состояние публикации.

2. Получи документы PR отдельно от исходников курса: прочитай их через GitHub
   либо извлеки только этот каталог в собственный исследовательский workspace.
   Не переключай, не сбрасывай и не очищай пользовательский checkout.
   Документальная ветка, её base `master` и старый аудит не выбирают code base.
   Прочитай `AGENTS.md`, применимый `START-CODEX.md` и действующие owner contracts,
   затем `README.md`, `design.md`, `java-authoring-audit.md`,
   `publication-evidence-2026-10-27.md`, `hypotheses.md`,
   `methodology.md`, `plan.md` и `handoff.md` этого пакета.

3. Выполни T00. Выбери фактический итог предыдущего чата для Java, самые свежие
   поведенческие PR владельцев расширений и актуальный локальный worktree
   Performance. Различай owner source, installed vendor и исторические
   evidence. Никакого молчаливого fallback на main/master, старый PR или старый
   PASS. Сохрани переносимые staged/unstaged/untracked исследуемые inputs без
   коммита чужих изменений; запиши воспроизведение и ограничения. Создай
   `results/source-selection.md` в своём workspace; отсутствие этого файла
   в опубликованном пакете является ожидаемым, а не блокировкой запуска.
   Построй lineage/capability/fix matrix: максимум SemVer, `latest` и main
   не доказывают наличие fix. Раздели course source, runtime, host-tools,
   raw assets и assembled tree; не собирай непроверенный гибрид веток.

4. ОС и окружение идентичны компьютеру подготовки, но фактическую аппаратуру,
   доступные runtimes, нагрузку, границы evidence и общий срок зафиксируй в T00.
   Найди и сохрани teacher inputs вне публичного дерева. Не публикуй закрытые
   исходники, персональные данные или чувствительные пути. Недостающие private
   inputs ограничивают соответствующий вывод; независимый анализ продолжай.

5. Сначала исследуй авторскую модель **всего Java**: root, theory, tasks,
   lectures, practice, handbook, общие ресурсы/примеры/архивы и связанные tools.
   Проследи типовые изменения условия, API, общего кода, состава работы и новой
   задачи; найди канонические источники, реальные копии и производные реестры.
   Сравни со штатными metadata/profiles/includes/resources Quarto. Отдельно
   разбери teacher/IDE workflow и путь export → qualification → Docker/host →
   auto/manual points → completion. Не объявляй разные учебные формы дублями
   только по теме и не ограничивайся переносом огромного YAML в sidecar.
   Раздели source/runtime release, render/export, qualification, admission и
   server import. Если был DEFERRED_BY_USER / NOT_VERIFIED, выясни проверенное,
   отложенное и неизвестное; наличие policy SHA не заменяет документ решения.

6. До тяжёлых измерений дай ранний связный отчёт: подтверждённые расхождения,
   необходимые и избыточные механизмы, неизвестные данные, варианты понятной
   авторской модели, хронологию отказов и долг проверки. Новые серьёзные вопросы группируй с примерами и вариантами;
   согласованные решения заново не открывай. Независимую работу продолжай.

7. Затем обоснуй каждую собственную функцию и callsite в области плана через
   requirements/invariants/consumers/effects/cost/history/references. Исследуй
   snapshots/SHA/inspect, публичные типы и schemas, раннюю совместимость,
   lock/install/release/CI и реальные upstream идеи. Полнота учёта отделяется
   от runtime observation; неизвестные связи не исчезают из ledger.
   Включи новые optional-primary/ZIP/API/schema/ID границы, canonical и
   materialized QMD, lifetime course model/common inputs, assembly checks,
   qualification/Docker/Gradle и восстановление после отказа. Исторически
   исправленную ошибку не называй новым дефектом без проверки выбранной линии.

8. Новые опыты выполняй на урезанной disposable копии настоящего Java по
   capability manifest. Сначала прочитай существующий perf/evidence. Одна
   тяжёлая очередь, без дублирования рендеров аналитиками. Сравни native,
   прямой маршрут расширений и public perf off; активный profiling учитывай
   отдельно. Приоритет — правка страницы/preview, но полная композиция и явные
   экспорты тоже нужны. Измеряй секунды; произвольный SLA и десять минут как PASS
   не назначай. Параллелизм исследуй отдельно от уменьшения лишней работы.
   Новая матрица Cybersecurity уже существует: переиспользуй её по применимости;
   регрессия изменённого состава не устанавливает виновный компонент.
   Не смешивай стоимость страницы, qualification, assembly и повторной попытки.

9. Роли и effort бери из `plan.md`: анализ архитектуры, авторская модель,
   контракты, спецификации, docs и review — ultra либо максимум доступного;
   inventory automation, механика fixture и выполнение опытов — medium.
   Не больше четырёх агентов вместе с координатором, по одному владельцу
   writable partition. Не меняй глобальную конфигурацию моделей. Исторические
   задания учебного авторства не являются новым поручением переписать курс.

10. Варианты и минимальные исследовательские пробы держи в своих isolated
    копиях. Не делай продуктовых commits/releases, не публикуй курс и серверный
    импорт, не сливай PR и не чисти чужие ветки. Не запускай большой Java
    «для уверенности»: перенос выводов и финальная большая проверка отдельны.
    Заверши полным отчётом, вариантами рефакторинга, приоритетами, миграцией,
    evidence/ограничениями и независимым ревью. Решение о реализации оставь
    пользователю. Новые авторские документы и описания PR — по-русски.
    Исторический deferred допуск не replay/продлевать; новый staging, обход
    qualification, production publisher и серверные действия не разрешены.
    Предложение закрытия долга проверки оформи в `results/release-and-recovery.md`.
