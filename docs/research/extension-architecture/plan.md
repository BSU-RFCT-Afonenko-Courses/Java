# План исследования архитектуры и производительности расширений

> Для исполнителей: это исследовательский план. После завершения чата
> «Выполни план публикации банков» и получения стартового поручения начать
> с T00 на исследовательском ПК. При доступности навыков использовать
> superpowers:subagent-driven-development для независимых задач либо
> superpowers:executing-plans для последовательной работы. Отсутствие навыка
> не отменяет явных задач и ограничений этого документа. Продуктовый
> рефакторинг не входит в разрешённое исполнение плана.

**Цель:** обосновать каждую собственную функцию и место вызова, установить
источники сложности и задержек, сравнить архитектурные варианты на малом Java
и подготовить доказанный рефакторинг с сохранением высокоуровневой задачи.

**Архитектура исследования:** function/call ledger связывает код с требованиями,
инвариантами, происхождением и стоимостью. Чтение существующих evidence
предшествует новым опытам. Один минимальный Java и одна тяжёлая очередь
измерений используются несколькими аналитиками без дублирования запусков.

**Средства:** штатные Quarto/Pandoc/Deno/CUE, существующий Performance,
доступные парсеры для inventory, JSONL/CSV/Markdown. Версии не выбраны.

**Основание:** [проект требований к исследованию](design.md).

**Уточнённый приоритет:** сначала авторская модель корня и всех подпроектов,
затем углублённое исследование функций, performance и API. Нельзя принимать
развёрнутую нынешнюю конфигурацию за необходимую высокоуровневую задачу.

**Дополнение 27 октября:** исследовать также понятный выпуск и восстановление
после сбоев. [Новые свидетельства](publication-evidence-2026-10-27.md) вводят
B01–B16 и R01–R04: отдельные release-линии, runtime/host assembly, schema drift,
capture lifecycle, qualification и временный NOT_VERIFIED admission. Это
расширение исследовательского scope, не разрешение воспроизвести обход выпуска.

## Общие ограничения

- Подготовка этого пакета: только документы. Не запускать examples, tests,
  renders, profiles и benchmarks; не менять код, исходники курсов и pins.
- Закрепление версий/исходников/PR — T00 при запуске на другом ПК после
  завершения предыдущего чата. При публикации этого пакета T00 не выполнять
  и не заполнять её результат предполагаемыми refs.
- Будущий research использует актуальные поведенческие PR и согласованные
  локальные worklines. Main, последний номер версии и старый PASS не заменяют
  проверку фактического исследуемого состояния.
- Все новые авторские документы и инструкции по-русски. Технические имена,
  команды и URL сохраняются буквально.
- Сохранять чужие рабочие деревья, незакоммиченные изменения, источники и raw
  evidence. Не запускать очистку, release/publish или изменение remote веток.
- Исследовательский код/однофакторные пробы допускаются только в собственных
  disposable fixtures/вариантах, после фиксации методики и входов. Они не
  становятся исправлениями расширений автоматически.
- Не начинать full Java benchmark ради разведки. Перенос выводов с малого
  примера на большой курс имеет отдельное обоснование и ограничения.
- Основная цель — минимизация ожидания и общей работы при сохранении задачи.
  Приоритет одиночной странице; полная композиция и экспорты также изучаются.
  Десять минут, проценты или придуманные секундные пороги не являются PASS.
- Одновременно до четырёх агентов вместе с координатором; тяжёлый локальный
  запуск только один. При более строгом фактическом лимите уменьшить очередь.
- Source release, успешный render, public inventory, полная qualification,
  admission и рабочий сервер получают отдельные статусы. Исторический deferred
  допуск не является новым разрешением staging, продления policy или публикации.

## Основные риски ревью

1. Plain Markdown случайно оплачивает full-bank/materialization proof.
2. Private JSON consumer отвергает новый producer после дорогого render.
3. Быстрый вариант меняет scope, закрытые данные, native crossrefs или recovery.
4. Минимальный пример либо profiler скрывает реальный закон роста и задержку.
5. Исследование повторяет тысячи пояснений, но не закрывает карту функций.
6. Успешный release/CI скрывает другой состав или незавершённую qualification.
7. Срочный обход выпуска превращается в постоянную зависимость либо новое
   разрешение без прочитанного решения и понятного recovery.

Эти риски адресованы соответственно T06, T11, T02/T07, T04/T05/T13, T01/T15,
R01/R02/T12 и R03/R04.

Большие raw logs/profiles/outputs остаются в отдельном каталоге evidence,
определённом T00. В Git передаются небольшие индексы, выводы и необходимые
воспроизводимые fixtures, а не копия всех установленных runtime деревьев.

T01 назначает каждой функции и callsite ровно одну writable partition.
В частности, Core render и Core export не редактируют один ledger: общий
символ получает одного основного исследователя, второй ссылается на его ID
и передаёт замечание координатору. Cross-owner таблица T11 добавляет связи,
а не создаёт конкурирующие классификации тех же функций. Объединение и
разрешение разногласий выполняются координатором после владельческих задач.

Общий `results/release-and-recovery.md` собирает координатор. Если R01–R04
выполняют разные агенты, они передают отдельные секционные drafts/выводы и
не редактируют общий файл одновременно. Это не дублирует исходный ledger.

Используемые Platform qualification/execution, release assembly и host
admission входят в явные partitions R02–R04. T01 назначает один основной
ledger на модуль; T09/T11/T12 ссылаются на эти записи, не создают второй аудит
тех же функций. Весь unrelated сервер Platform в scope не добавляется.

## Порядок и бюджет

Порядок будущего запуска: T00 → A01–A12 и ранний отчёт авторской модели →
углублённые T01–T13 и R02–R04 → T14–T15. R01 начинает хронологию в T00,
дополняется в A и входит в ранний отчёт. Предварительный этап A01–A12 выполняется до
углублённых T01–T13. Для его
начального статического разбора не требуется выбирать pins или запускать
рендер. [Предварительный аудит Java](java-authoring-audit.md)
является первой итерацией, а не закрытием всех вопросов. При старте
на другом ПК T00 проверяет применимость этого разбора к выбранным источникам.
Ранний отчёт показывает выводы и существенные вопросы пользователю до тяжёлых
опытов; он не требует нового согласования каждой технической детали и не
разрешает продуктовую миграцию. В нём отдельно показаны фактическое состояние
выпуска, причина изменения стратегии, проверенные/отложенные гарантии и долги,
которые нельзя восстановить только по публичному GitHub.

Три независимых участка предварительного этапа назначаются волнами:

| Задания | Ответственный / усилие | Что передать |
| --- | --- | --- |
| A01–A03, A07 | Аудитор курса / ultra | Все подпроекты и типовые авторские правки, actual copies/consumers, разрывы поставки |
| A04–A06 | Архитектор авторского интерфейса / ultra | Native возможности, короткие декларации и самостоятельные авторские решения |
| A08–A12 | Аудитор полного проекта и оценки / ultra | Teacher provenance, IDE workflow, export/qualification/Docker/scoring |

Каждый пункт A имеет таблицу свидетельств и статус. Итоговый authoring-model
показывает рядом «как сейчас» и «минимально необходимое описание», не только
предлагает разнести YAML по файлам. Условие/код/пример/проверка/эталон получают
явные канонические места; производные manifests и receipts отделяются от
редактируемых входов. Для IDE определяется, есть ли roundtrip либо только
однонаправленный staging, и какой минимальный контракт нужен для сопровождения.
Проверка эталона и выставление баллов не считаются одной операцией экспорта.

Приёмка предварительного этапа: карта охватывает корень и все подпроекты;
разные педагогические формы не удалены как «дубли»; показаны конкретные
многоместные правки, установленные расхождения и неизвестные private inputs.
Продуктовые изменения и новые запуски не начинаются по одному факту аудита.
T02 использует эту модель как вход, T04 сохраняет её необходимые возможности,
а T06–T12 обосновывают реализацию относительно неё.

Далее последовательные gates: принятая исследовательская постановка авторской
модели → карта требований/кода → подготовленная fixture
и протокол T05 → smoke через T13 → принятая fixture → адресные опыты → варианты
→ независимое ревью. T04 публикует подготовленный manifest до smoke и закрывается
после него; для первого smoke T13 не ждёт окончательного закрытия T04.
T01/T02/T03 могут идти параллельно. T12 начинает чтение независимо. После T01
владельческие задачи распределяются волнами по свободным слотам; нельзя
создать всех перечисленных агентов одновременно.

Когда T13 занимает один слот и ноутбук измерением, два других исследователя
могут читать код и evidence. Координатор выдаёт только один measurement token.
Заявки T06–T12 и R02–R04 поступают в общую очередь; агенты не запускают свои повторы.

До исполнения в T00 определяется доступный общий срок из действующих
инструкций и бюджеты волн. При угрозе лимиту сокращается число недоказательных
повторов и вариантов, а не скрывается неполное покрытие. На каждый новый
опыт требуется различающий вопрос; при отсутствии такого вопроса запуск
отклоняется. После одного неудачного smoke сначала читаются причины и raw
данные, а не начинается большой повтор того же курса.

## T00 Приёмка предыдущей работы и выбор исследуемого состояния

**Когда:** начало исследовательской сессии на другом ПК после завершения
чата «Выполни план публикации банков», до A01–A12 и новых опытов.
**При публикации документов:** не исполняется. **Усилие:** ultra, координатор.

**Вход:** пакет документов, ответы пользователя, законченные или согласованные
параллельные worklines. **Выход:** results/source-selection.md и запускной prompt.

- [ ] Убедиться, что чат «Выполни план публикации банков» завершил работу;
  прочитать его итог, текущие PR/worklines, known failures, raw evidence и
  ограничения. Успешный экспорт не является условием старта исследования.
- [ ] Начать R01: восстановить хронологию неудач и изменения стратегии,
  исходные человеческие решения, обычный и фактически применённый выпуск.
  Прочитать связанные failed/human/privacy документы; их hash-поля в policy
  не доказывают содержание, актуальность или новое разрешение.
- [ ] Проверить актуальные указания и доступные инструменты; согласовать
  границы с другими сессиями, не останавливая чужую работу. Найти teacher
  root и его сохранённые исходники по фактическому итогу предыдущего чата.
- [ ] По каждому владельцу выбрать актуальный поведенческий PR/head либо
  последний слитый поведенческий PR; отдельно записать local dirty state.
  Источник Java — фактический итог предыдущего чата. Отличать установленный
  vendor от выбранного owner source; Performance читать из актуального
  локального worktree. PR документов и исторический аудит не выбирают эту базу.
- [ ] Проверить lineage и матрицу fixes/capabilities, а не максимум SemVer.
  Раздельно выбрать course/source tag, runtime images, registry/lock/assets,
  host-tools и исходную assembly. Не склеивать divergence и не переписывать
  canonical prepared metadata ради совпадения номеров. Зафиксировать actual
  qualified/admitted/server состояния и происхождение каждого PASS.
- [ ] Только теперь закрепить исходники, toolchain, installed packages,
  курс-источник, референсы и соответствие старых evidence выбранной базе.
- [ ] Сохранить выбранные незакоммиченные входы независимо от изменяемого
  worktree: base commit, staged/unstaged patches и необходимые untracked
  файлы либо переносимый архив исходников. Записать идентификатор содержимого,
  способ восстановления и проверку соответствия workspace перед опытами.
  Не коммитить чужие изменения; исключённые ignored/generated/private данные
  перечислить явно. Это однократная воспроизводимость исследования, а не
  новый продуктовый snapshot runtime и не архив всего рабочего каталога.
- [ ] Назначить свой isolated workspace, evidence root, бюджет и единую
  measurement queue; записать ограничения аппаратуры/доступных платформ.
- [ ] Проверить отсутствие main/latest fallback и смешения разных source
