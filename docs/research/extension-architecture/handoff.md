# Передача исследования архитектуры расширений

Статус: пакет для отдельного Java PR и запуска на другом ПК после завершения
чата «Выполни план публикации банков». Выполнен предварительный статический
аудит; полное исследование и новые запуски не начаты. Продуктовый рефакторинг
не разрешён. База будущего исследования выбирается в T00 на том ПК.

## Что запросил пользователь

Исследовать обоснованность текущей архитектуры всех расширений курса и её
влияние на скорость, включая каждую собственную функцию и место вызова,
точные snapshots/SHA/inspect, межпакетные API/типы/схемы, lock и выпуск.
Проверить реальные источники архитектурных идей в документации, commits,
PR и внешних открытых проектах. После доказательств предложить более стройный
рефакторинг с максимальной обоснованной производительностью.

Основная проблема автора — длительное ожидание обычного Markdown без R/Python
вычислений и потеря управляемости расширений. Приоритет у одиночной страницы
и preview; полная сборка и экспорты тоже включены. Основные метрики — секунды
ожидания и реальная работа; native ratio является дополнительным сравнением.
Готовность ждать десять минут не превращается в порог PASS. Численные SLA
пользователь не задал: цель — максимально возможная скорость без нарушения
высокоуровневой задачи и общей архитектуры.

Исследование следует проводить на урезанной копии настоящего Java,
сохраняющей необходимые демонстрационные возможности и роли подпроектов.
Текущая подготовка документов не включает запусков этого примера.

После просмотра Java пользователь уточнил порядок: сначала восстановить
стройную авторскую модель всех подпроектов, затем исследовать performance
и API. Проверять root/theory/tasks/lectures/practice/handbook, а не только
большой YAML заданий. Добавлены A01–A12: повторная конфигурация, копии и
native механизмы, расположение эталонов, полный IDE-проект, проверки при
экспорте, Docker и начисление баллов.
[Предварительный аудит](java-authoring-audit.md) сохраняет текущие свидетельства.
Java создан на другом ПК; его исполняющая сессия здесь не прочитана.
Не выдавать предположение о её мотивах за установленное согласование.

## Что известно из предварительного разбора

Предварительное ревью просмотрело собственный runtime владельцев, актуальные
на тот момент PR, локальный Performance и сохранённые evidence. Оно не
включало новых запусков examples/tests/render/benchmark. Конкретные версии
и PR этого разбора намеренно не становятся базой будущего задания.

Сохранить следующие направления, перепроверив их на финальных входах:

- Общий proof/currentness слой может оплачиваться на обычном Markdown без
  использования materialization. Различать нужность функции и цену её scope.
- Повторные source/metadata origins, raw inspect stdout и nested boundaries
  могут размножать одну и ту же работу. Число строк кода не является замером.
- Owned JSON writer имеет подозрительные prefix loops, повторные binding
  digests и lifetime FD. Эти находки относятся к export, не ко всему HTML.
- Временное изменение авторской конфигурации само создаёт сложные требования
  восстановления, FFI и точной identity. Нужно исследовать сам выбор механизма.
- Private pointer/witness читается consumers; известный additive-field
  конфликт commonPathDocuments проявился лишь после дорогой предыдущей работы.
- Dynamic imports/any и независимые TS/CUE/Lua predicates мешают ранней
  проверке связи. Наличие строгого runtime guard не равно строгому API.
- Publisher делает собственные inspections и последовательную композицию;
  HTML/collection/conditions passes и QRC local/full имеют разные назначения,
  поэтому их нельзя механически удалить как «повтор».
- Download уже использует batch в части путей. Отдельно проверяются fallback,
  SHA receipts, resource walks/Git и источник моделей. Не считать кеширование
  и фазовое reuse полностью отсутствующими.
- Exporters могут повторять Body/JSON/data preparation, fragment processes,
  валидации и узнавать простые конфликты после компиляции. Не относить цену
  явного Print/Moodle экспорта к каждому обычному render.
- Presentation/Navigation не показали собственных snapshot/inspect слоёв;
  их функции всё равно входят в полную карту. Cloud требует явной границы
  поддерживаемого legacy/current поведения.
- Project lock, installed receipt, native vendoring, release evidence и API
  compatibility — разные гарантии. Точный SHA одной CI-пары не является
  публичным API. Ручная синхронизация версий и повторные CI renders нуждаются
  в оценке отдельно от per-page runtime.
- Performance уже предоставляет полезную инфраструктуру. Native, public off,
  summary/CPU/trace и setup/report имеют разные границы измерения. Старые
  inconclusive результаты и одиночные наблюдения не доказывают новый speedup.
- Bounded concurrency может ускорить полную композицию, но не заменяет
  уменьшение лишней работы и не решает тяжёлый один подпроект.

Полный список H01–H60 и различающие свидетельства находится в реестре.
Новые функции и проблемы, которых там нет, не исключаются из исследования.

## Что выполняется на другом ПК при запуске

T00 входит в начало исследовательского поручения после завершения предыдущего
чата. PR документов публикуется раньше, без runtime pins. Не нужно отдельное
повторное поручение только ради создания `source-selection.md`.

- Выбрать актуальные поведенческие PR/head и local worklines всех владельцев.
- Учесть завершение параллельных работ, dirty/staged изменения и происхождение
  vendor copies. Ничего не сбрасывать и не подменять старым main автоматически.
- Сохранить выбранные staged/unstaged/untracked входы переносимо и независимо
  от текущего worktree: base и patches с файлами либо архив исходников;
  записать идентификатор содержимого, исключения и восстановление. Перед
  опытами проверить соответствие workspace. Не коммитить чужие изменения
  и не вводить продуктовый snapshot runtime ради этой разовой передачи.
- Закрепить course source, расширения, toolchain, среду и необходимые внешние
  references. Различить исторический evidence source и базу нового опыта.
- Проверить доступность существующего Performance, парсеров и raw evidence;
  выбрать собственные workspace/evidence paths и согласовать общий срок.
- Заполнить source-selection, финальный launch prompt и метаданные передачи.
- Прочитать итог чата «Выполни план публикации банков», даже если экспорт
  остался неуспешным. Не повторять его команды без различающего вопроса.
- Использовать PR документов только как источник задания, не как course base;
  не запускать продуктовую реализацию вслед за исследованием.

Смена версии после T00 требует явной записи новой базы и
оценки применимости уже полученных данных, а не молчаливого update.

## Работа следующей сессии

Координатор запускает роли волнами, максимум четыре агента вместе с собой.
Сначала карта требований/кода и references, затем подготовленная минимальная
fixture и измерительная методика. Первый smoke через T13 завершает приёмку
T04; последующие серии используют принятую fixture. Владельческие аналитики
готовят заявки в одну очередь.

Эта последовательность начинается после уточнения авторской модели A01–A12.
Однонаправленный grading stage нельзя объявлять полноценным IDE workflow;
наличие эталонных файлов — прохождением их проверки; public inventory —
подтверждённой квалификацией или студенческой оценкой.
Тяжёлые рендеры и профили выполняет только назначенный исполнитель.

Architectural analysis, contracts, docs и review — ultra или максимальное
доступное усилие. Состав и конфигурация проектов малого Java — ultra;
inventory automation, механическая подготовка fixture и выполнение опытов — medium.
Имена моделей и фактический доступный параллелизм определяются при запуске.

T01 назначает непересекающиеся ledger partitions для всех функций и callsites.
За смысловой аудит Performance отвечает T05; за Template и проектную интеграцию
Java/Cybersecurity — T12. Общие символы получают одного основного владельца.

Каждому агенту передаются: одна задача и scope; входные документы и invariant
IDs; потребляемые/создаваемые артефакты; запрет продуктовых правок; effort;
гипотезы; критерий завершения; правило единой measurement queue. Ответ агента
содержит вывод, evidence, coverage gaps и следующие различающие вопросы.

Отчёт должен дать обоснование и для сохранения кода. Итог «функция нужна,
но вызывается на слишком широкой границе» отличается от «удалить функцию».
Сложность новой системы не оправдывается одним удачным benchmark.

## Стартовое поручение и T00

Полный переносимый prompt находится в [start-prompt.md](start-prompt.md).
Он начинает исследование с T00, затем A01–A12. Отсутствующий
`results/source-selection.md` — результат, который нужно создать в T00,
а не причина навсегда остановиться в режиме подготовки документов.

Сначала уточнить авторскую модель всех подпроектов по A01–A12, затем получить
полную карту функций/вызовов, требований и происхождения решений, прочитать
применимые существующие evidence. Дальше использовать
малый Java и единую очередь недостающих опытов. Сохранять функциональную
эквивалентность и primary evidence. Никаких продуктовых commits/releases,
публикации курсов или очистки чужих веток по этому поручению. Итог —
исследование, сравнение вариантов и предложение рефакторинга для решения
пользователя. Не продолжать автоматически реализацию предложенного варианта.

## Пакеты вопросов

Уже решённые вопросы не открывать повторно: оба цикла исследуются; приоритет
одиночной странице; фиксированного SLA нет; максимальная скорость ограничена
сохранением high-level свойств. При подготовке PR опыты и выбор pins запрещены;
при будущем запуске T00 выбирает входы, а опыты выполняются по методике.

Новые вопросы группировать по решениям, а не по файлам:

1. **Требования и модель доверия:** конкретный пример изменения/подмены,
   требуемый момент отказа, последствия, более простой вариант гарантии.
2. **Граница поддержки:** фактически используемая возможность, native API
   ограничения, необходимость legacy/платформенной совместимости и миграция.
3. **Выбор архитектуры:** два или три доказанных варианта, seconds/complexity
   и сохранённые инварианты; явно указать, какое решение нужно от пользователя.
4. **Финальная приёмка:** нужен ли ещё конкретный опыт большого Java после
   малых сценариев и что он способен подтвердить. Не запускать весь курс
   только потому, что осталось время.

До вопроса проверить, не отвечает ли на него контракт или согласованное
указание. Каждый пакет содержит связное объяснение, примеры и варианты,
рекомендацию и влияние ответа; routine implementation choices решает агент.
