# Самостоятельные комплекты, исполнение и перенос результатов

**Прямые уточнения 29 октября, решения [57–60](../../refactoring-plan.md#decision-57):** действует только текущий договор без снимков прежнего API/тестов; студент при необходимости переделывает. Обычный перенос полного автоматического зачёта при однозначных соответствиях сохраняется, редкие неоднозначные split/merge допускают потерю связанных данных без сложного механизма. Самостоятельная некомпиляция →0 текущей попытки; обязательная проверка интерфейса — допуск без баллов, проваленные ячейки с комментариями/успешные скрыты только в показе; провал →0 без запуска предметных тестов. Проверки допуска не входят в предметный знаменатель; прежний лучший результат/имеющиеся ручные результаты сохраняются. Это документная синхронизация, не исполнение генератора/интерфейса и не новая рецензия старого снимка.

## 1. Рекомендуемая конструкция

Один кодовый проект содержит стартер, обычные JUnit-тесты, данные и отдельно объявленные авторские решения. Core получает проверенные объявления из native Quarto-контекста, вычисляет явное замыкание компонентов и готовит файловый состав. Настоящие общие Gradle-файлы включаются как файлы, а не генерируются из YAML. Из одного состава student получаются одинаковые байты ZIP для Pages и PL. Авторский комплект включает полный оценочный набор и отдельные контексты решений. Контракт ответа независимо определяет один `Main.java`, несколько файлов или архив.

Рекомендуемый исполнитель — обычный Gradle `Test` с JUnit Platform как локально, так и в PL. Тонкий адаптер принимает завершённые события/диагностику, проверяет целостность результата и переводит их в PrairieLearn. Он не задаёт второй тестовый DSL, не требует обязательного `TestReporter` от каждого теста и не заменяет JUnit собственным движком. Platform отвечает за изоляцию и достоверность запуска; Gradle сам по себе этих гарантий не даёт.

Документ дополняет [архитектуру](architecture.md) и [авторский вход](authoring-and-pipeline.md). Имена ниже обозначают обязанности, а не утверждённые публичные типы/API. Для согласования новой схемы нужен весь пакет и независимая рецензия.

## 2. Четыре разных предмета вместо общего большого объекта

| Предмет и владелец | Вход | Выход и срок жизни |
| --- | --- | --- |
| Состав проекта, Core | Проверенные объявления проекта/наборов/компонентов с происхождением | Конечный план относительных файлов, выбор тестов и решений; актуален для конкретного снимка входов |
| Условие, Core + native Quarto/Pandoc + QRC | Канонический QMD, native include/ссылки, публичность | Разрешённое публичное либо авторское AST и адресуемые ресурсы; отдельная проекция для получателя |
| Материализованный комплект, Core и Download | План, байты и разрешённое условие | Проверяемый inventory с хешами; файлы/детерминированный ZIP без обращения к соседнему checkout |
| Исполнение, Platform и PL | Контракт ответа, доверенная сборка и тесты, присланные файлы | Либо полный достоверный результат, либо полная ошибка проверки; отдельное отображение в score/feedback PL |

План не содержит JUnit outcomes; отчёт исполнения не получает доступ ко всему авторскому дереву; Print не нужен доступ к submission или author solutions. Receipt фиксирует конкретные байты и входы, но не превращает прежний запуск в вечное разрешение читать изменившийся канон. Операция получает ограниченные возможности чтения/записи и завершается до публикации; переносимая выдача содержит нужные байты и свидетельства, а не открытый callback.

Прежняя реализация уже защищает два полезных свойства: единое планирование файлов и текущесть источников ([Core materialize.ts:132–179][core-materialize]); PL получает проверенный student inventory ([materialized-student.ts:4][pl-materialized]). В новом дизайне сохраняется смысл этих проверок, но не старые типы, partitions teacher overlay или формат receipt.

## 3. Канон, замыкание и переносимость

### 3.1. Что хранится один раз

| Канонический ввод | Что нельзя дописывать рядом вручную |
| --- | --- |
| Полное условие в тематическом банковском QMD, inline либо include | Отдельный вручную синхронизируемый statement для ZIP/PL |
| Единственный локальный `_metadata.yml` | Второй `project.yml` или созданный нами YAML merge |
| Определения переиспользуемых компонентов и общие defaults native metadata | Полные копии helper в каждом проекте |
| Обычные Java/JUnit-файлы и test resources рядом с проектом | Карточки каждого теста, второй список ожидаемых исходов, собственный test DSL |
| Настоящий выбранный Gradle build/settings/convention-код | Maven-координаты/версии и конфигурация Test, повторённые в course YAML |
| Объявленные авторские solutions/alternatives | Неявный запуск всех каталогов с именем solution либо смешение двух `Main` в одной компиляции |

Точные предложенные ключи находятся только в [авторском проекте §4.1](authoring-and-pipeline.md#41-reverse-array-банк-include-и-кодовый-проект). Этот документ не задаёт параллельную YAML-схему. Для простого проекта demo/full выбирают свои каталоги напрямую. Имя компонента оправдано реальным переиспользованием.

### 3.2. Как формируется состав

После штатного наследования Quarto эффективная bool-map задаёт прямой выбор наборов конкретной выдачи. Core проверяет известность имён, разворачивает объявленные `includes`/`requires`, обнаруживает цикл с полной цепочкой и лишь затем расширяет выбранные каталоги в файлы. Это граф файлов курса. Он не угадывает зависимости по Java imports и не разрешает Maven-версии.

По решениям 46/47 наследование `demo: true → false` допустимо. Но `extra: true → includes demo` вместе с прямым `demo: false` — ошибка с цепочкой `extra → demo` и позициями запрета/включения. Запрещённый набор нельзя ни вернуть молча, ни отрезать от обязательной зависимости. Неизвестный helper, отсутствующий выбранный каталог, несовместимый build и два владельца одного target также останавливают всю выдачу. Неиспользуемый набор не добавляет свои библиотеки в выбранный проект.

Два различных source в один target — ERROR, в частности starter `Main.java` и reference `Main.java` в одном контексте. Один и тот же уже выбранный компонент в diamond-графе включается один раз; повторная явная конкурирующая запись target не скрывается сравнением одинаковых байтов. Порядок обхода не меняет полученный состав. У выбранной выдачи есть ожидаемый непустой состав: отсутствие full-тестов нельзя превратить в успешную пустую проверку.

Общие пути считаются от места определения компонента; локальные пути — от выбранного кодового проекта. Ресурсы условия следуют native базе банковского input. Строка после native rebasing не объявляется исходным путём повторно. Для объяснения ошибки сохраняются объявление, физический source и позиция, native эффективное значение, роль пути и цепочка включения. Provenance не выводится задним числом из одного merged object: [исследование native origins](../open-topics-20261028/native-models-delivery.md#2-строка-пути-и-происхождение-значения) уже показало недостаточность обычного inspect JSON.

### 3.3. Какой состав получает каждый адресат

| Комплект | Исходники и тесты | Build и инструкции | Что исключается |
| --- | --- | --- | --- |
| student, одинаковый для Pages/PL | Starter/обязательные данные + только явно выбранные demo и их транзитивные helpers/resources | Выбранные реальные Gradle-файлы, общая инструкция и полный README | Полный оценочный набор, author solutions, PL executor/report adapter, реальные ответы студентов |
| author-full | Стартер, весь оценочный набор, все объявленные корректные/негативные решения; каждый в отдельном контексте | Те же native Gradle conventions; инструкция проверки ожиданий и ручных критериев | Секреты, реальные студенческие данные; отсутствие полного набора — ошибка подготовки, не «почти full» |
| PL grading | Полный оценочный набор и его зависимости, доверенные build/adapter, submission mapping | Подготовленное окружение с закреплёнными версиями | Лишние библиотеки других задач, demo как замена full; для Java source-only профиля — присланные build/init scripts |

При пустом выборе demo не нужно притягивать test support всех задач: достаточно starter и применимого build-профиля. Состав student не зависит от доступности полного Git, количества попыток или решения открыть IDE. Скачанный ZIP — помощь, а не ответ. Для задач с обязательным starter API ссылка из условия делает этот API обязательным; простая сигнатура может оставаться в QMD без искусственной заглушки (51).

В готовом проекте helper включён как исходник либо выбранный обычный локальный Gradle-проект. Ссылка на `../../author-checkout` запрещена. Для малой reverse-array рекомендованы скопированные при материализации test-support sources; для действительно самостоятельной общей библиотеки — обычный Gradle subproject/convention plugin внутри выдачи. Такой модуль выбирается только нужным проектом. Публикация helper в Maven допустима при реальном доступном репозитории и необходимости, но не является обязательной новой инфраструктурой курса. Если выбранный helper требует внешнюю библиотеку, её координаты/scopes принадлежат его настоящему Gradle-модулю или явно выбранному native build/convention. Простая копия Java sources не обещает автоматически получить classpath. Несовместимость выбранного состава с build — ошибка до выдачи. Для нетипового проекта нормален собственный настоящий build, переиспользующий общие conventions; producer не дописывает dependencies из YAML.

## 4. Настоящий native build и отдельные авторские контексты

В [examples/delivery/profiles/java-junit](examples/delivery/profiles/java-junit/) помещён небольшой настоящий пример Gradle, **не запущенный** и не установленный в курс. Он использует стандартные source roots, Jupiter, BOM и launcher, `useJUnitPlatform()` и диагностические отчёты. Это файлы профиля для копирования, а не строки Groovy, синтезируемые из YAML. JDK задаёт выбранный технологический профиль; пакеты Java из него не возникают. Reverse-array сохраняет простой `Main` без `package`.

Для особого проекта вроде GradeApp настоящий native build сохраняет `jar`, manifest/main-class и связь теста с артефактом. Эти факты не переносятся в course YAML. Нынешний [GradeApp build:1–31](../../../tasks/projects/files/gradeapp-report/student/build.gradle#L1) уже демонстрирует эту разницу; его `prepareDependencies` не нужен целевому простому профилю, поскольку разрешением зависимостей занимается стандартный Gradle task graph.

Авторский комплект рекомендуется материализовать как обычную multi-project сборку: `contexts/starter`, `contexts/reference`, `contexts/<alternative>`. Каждый контекст имеет свой `src/main/java`, одинаковый выбранный полный test source/resource closure и копию одного подходящего настоящего build-файла. Настоящий корневой settings включает только материализованные контексты. В общем профиле это может быть обычный Gradle-обход отведённого `contexts` внутри выдачи: producer заранее поместил туда только явно выбранные решения. Это не поиск solutions в авторском репозитории и не генерация Groovy из YAML. Показанный небольшой settings явно перечисляет два контекста как статический пример, а не выход нового генератора. Производное повторение байтов между контекстами допустимо: канон Java/JUnit и build хранится один раз. Оно проще скрытого переопределения classpath, при котором тесты случайно видят starter вместо alternative. [Пример settings](examples/delivery/author-full/settings.gradle) показывает ровно два контекста; сам полный комплект здесь не собран.

`gradle :reference:test` запускает обычный Test нужного решения; локальный `gradle test` student-комплекта — только явно выбранные demo. Команда приёмки всех ожиданий может вызывать стандартные tasks и анализировать результаты, но не становится второй системой тестов. Непрошедший negative должен отказать по заявленной предметной причине: например, нужный assertion, а не случайный javac error. Ожидания относятся к решению/стадии, а не дублируют каждый тест. Состояние локального JUnit, PL и ручной проверки фиксируется отдельно.

По решению 49 до выпуска проверяются **все** объявленные корректные решения, все активные кодовые задачи, starter с объявленным ожиданием и отрицательные контроли. Точный полный набор не подменяется двумя demo. У исторического reverse-array-примера есть лишь [образец решения и missing-full manifest](../yaml-authoring-integration-20261027/_examples/reverse-array/missing-full-input.yml): он не выбранный финальный teacher input и не доказательство квалификации. В этой фазе новые учебные решения/тесты не сочинялись.

Первое разрешение зависимостей student может потребовать сеть/cache; чистый offline не обещан. В PL проверенный набор заранее находится в образе/ограниченном cache, grading не должен зависеть от текущей доступности Maven Central. Это два режима поставки одной native сборки. Наличие cache не доказывает корректность dependency lock/verification: их точный состав входит в квалификацию выпуска. Рендер сайта не запускает Gradle и тесты.

## 5. README: полное условие и настоящие ресурсы

Композиция по решению 48 выполняется для выбранной публичной задачи, а не копированием исходного файла вместе со служебным YAML:

1. Полное разрешённое native условие из канонического QMD, без solution/grading notes, но с допустимыми публичными материалами.
2. Общая Markdown-инструкция из выбранного Java/Gradle-профиля, хранимая один раз рядом с его настоящими build-файлами.
3. Необязательные особенности из локального `README.md`; его отсутствие нормально.
4. Состав ответа и простые действия сдачи из единственного submission-контракта.

Для reverse-array итоговые разделы — условие; исходник/инструменты; IDE и необязательный `gradle test`; что отправить. Техническая инструкция не становится новым обязательным письменным отчётом. Авторский README отдельно поясняет контексты, весь набор и ожидания решений.

Получатель получает разрешённый native AST и выбранные ресурсные байты. Один final writer создаёт README; копировщик использует тот же inventory ресурсов. Внутренние fragment links получают проверяемые anchors, относительные изображения/скачивания — переносимые targets, ссылки на другие страницы — проверенные публичные адреса QRC/Publisher. Если конкретная native конструкция не поддержана GFM, нужен читаемый локальный HTML-fragment либо другое поддержанное локальное представление с сохранением полного содержания. Ссылка допустима дополнением, но не заменяет обязательную часть README. Пока такого представления нет, операция отказывает: потерянное содержание не скрывается как успешный экспорт.

Проверка необходима: прежний [JSON→GFM опыт](../open-topics-20261028/native-models-delivery.md#3-native-json--gfm-не-создаёт-готовую-выдачу) потерял explicit Header ID при сохранении ссылки, не раскрыл include и не скопировал SVG. Это не повод для Markdown parser: include/crossref решает native стадия, адреса — QRC, assets — инвентарь, writer — Pandoc. Новый consumer не должен восстанавливать условие через HTML→AST→HTML и заново решать публичность.

## 6. Независимый контракт сдачи

| Один и тот же reverse-array source | Имя/роль |
| --- | --- |
| Канон стартера | Выбранный проектный `starter/src/main/java/Main.java` либо нынешний `student/src/main/java/Main.java` |
| Готовый IDE/ZIP | `src/main/java/Main.java` |
| Отправляемый файл | `Main.java`, явно разрешённый контрактом ответа |
| Изолированный grader staging | Например, `submission/src/main/java/Main.java`, явно назначенный исполнителем |

Это четыре различных адреса. Basename не служит алгоритмом нормализации. Grader читает разрешённое логическое имя, проверяет точное множество обязательных/дополнительных файлов, лимиты, дубликаты, регистр/коллизии и безопасные относительные имена, затем помещает байты в доверенный source root. Student ZIP с Gradle не превращает build scripts, тесты, `.class` или ресурсы соседнего проекта в сдаваемые исходники. Если задача требует несколько файлов/архив, их схема и допустимая структура задаются явно; пример Main нельзя обобщить на package/multi-file задачи.

Контракт отвечает и за автоматически полученный раздел README «что отправить», и за PL upload/editor/Workspace mapping. Переписывание этого текста независимо экспортёром запрещено смыслом одного канона. Простую сдачу можно сделать с JDK/любым редактором без установки Gradle и запуска demo.

## 7. Исполнение: Gradle/JUnit и тонкий PL adapter

### 7.1. Сравнение путей

| Путь | Что даёт штатно | Что всё равно требуется | Оценка кандидата |
| --- | --- | --- | --- |
| Обычный trusted Gradle Test + события + небольшой adapter | Native dependency/task graph, компиляция, forked JVM, Jupiter, test diagnostics, HTML/XML; те же тесты в IDE | Допуск окружения/источников, идентичность invocation, полнота результата, PL projection, изоляция | Рекомендуемый основной путь; один build/test канон |
| Отдельный trusted JUnit Platform Launcher | Прямой доступ к TestPlan/UniqueId и listener, точный контроль запуска | Те же classpath/compilation/deps, lifecycle/timeout/isolation/reporting; риск двух несовпадающих execution recipes | Резервное техническое решение при доказанном необходимом отличии; не второй набор тестов |
| Только чтение XML после произвольного `gradle test` | Простой внешний формат и привычные средства | Не устанавливает provenance, полный plan, корректное окончание процесса и стадии API/compile | Недостаточно как единственный источник оценочного результата |

Это сравнение основано на официальных [Gradle TestListener](https://docs.gradle.org/9.8.2/javadoc/org/gradle/api/tasks/testing/TestListener.html), [TestResult](https://docs.gradle.org/9.8.2/javadoc/org/gradle/api/tasks/testing/TestResult.html), [JUnit Launcher API](https://docs.junit.org/6.1.3/advanced-topics/launcher-api.html), а не на старом `gradle-jar-v1`. Listener имеет suite/atomic test boundaries, result — counts и причины ошибок; JUnit предоставляет plan/идентичности. XML полезен как отчёт, но не имеет автоматически согласованного полного контракта всех стадий. [Gradle XML documentation](https://docs.gradle.org/9.8.2/userguide/java_testing.html#sec:test_reporting) описывает самостоятельный отчёт; не доказательство защиты его файла.

Если Gradle events не передают нужную точность assertion или invocation identity, небольшой обычный JUnit listener дополняет их внутри того же Test task. Он переводит события, а не организует иной тестовый язык/runner. Точная пара API и версия должны пройти параметризованный и аварийный контроль до выбора реализации. Отдельный Launcher не решает доверие автоматически: когда студент и тест находятся в одном JVM, оба варианта разделяют эту границу.

### 7.2. Порядок доверенного запуска

Platform допускает конкретную trusted сборку, JDK/Gradle/Jupiter, полный test closure и submission contract. В Java-профиле со сдачей исходников student sources — данные входа; присланные `build.gradle`, `settings.gradle` и init scripts не исполняются как конфигурация. Это предел конкретного ответа, не общий запрет для project/Workspace-задач, где изменение сборки само является учебным результатом: для них явно выбирается иной договор входа и исполнения. Native build может выполнять код, поэтому доверенный авторский build квалифицируется как программа; YAML validation не заменяет эту проверку.

Изолированный чистый контекст не переиспользует старые class/report файлы или результат UP-TO-DATE другой сдачи. Сеть и ресурсные пределы задаёт исполнение. Доверенный supervisor сохраняет identity запуска и получает окончательный статус отдельно от student stdout; пути публикации отчёта защищены от записи студенческим процессом. Обычная JVM fork не считается сама по себе песочницей. Для CLI helper решение запускается отдельным ограниченным процессом. API-тесты могут работать в одной JVM; обычный тест/listener не следует объявлять самостоятельной изолированной средой. Здесь проектируется корректное исполнение и предел сдаваемого ответа, а не новая система защиты от целенаправленных атак.

JUnit исполняет обычные канонические тесты и сообщает names/assertions/exceptions. Portable test support содержит предметные Java helpers и необходимые данные, без импорта PL и знания `/grade`, JSON score или путей рабочего checkout. Adapter Platform владеет PL payload, ограничениями вывода, mapping файлов/стадий, process admission и complete report. Общий helper вроде запуска Java-процесса может быть полезен локально и в PL; ему не обязательно быть PL adapter.

## 8. Полный результат и равные тесты

**Статусное уточнение 29 октября, [решение 65](../../refactoring-plan.md#decision-65).** Каждый самостоятельный проверяемый случай принят как один равновесный оценочный тест, включая самостоятельные параметризованные/динамические случаи. Методы и контейнеры без собственного исхода не добавляют тестов. Прежнее «не принято» ниже — исторический статус сравнения; реализация и квалификация полного достоверного набора ещё впереди.

По решениям 52/53 score появляется только из завершённого достоверного оценочного набора: `passed / total`, с равным весом каждого оценочного теста. Для mixed задачи автоматическая часть — `0.8 × passed / total`, ручная — отдельно до 0.2. В примере 8/10 дают 64% максимума до ручной проверки. Demo не знаменатель, assertions не дополнительные веса. Полностью ручная задача не получает фиктивный auto suite. Считать отдельную atomic JUnit invocation отдельным оценочным тестом — рекомендуемый технический вариант этого проекта, **не принятое пользователем уточнение знаменателя**; учёт parameterized/dynamic случаев ещё требует квалификации.

Обычный Gradle Test при непройденных тестах завершает task/build с ненулевым кодом. Если получен полный достоверный набор outcomes и причина отказа — проваленные тесты, это штатный результат решения с долей `passed / total`, а не инфраструктурная или полная ошибка проверки. Допуск результата опирается на завершённость, целостность и причину завершения; требование общего exit 0 отвергло бы и такие валидные результаты.

Предлагаемая техническая квалификация:

| Ситуация | Требование к исполнителю/результату |
| --- | --- |
| Обычный assertion failure или исключение решения, полностью локализованное тестом | Штатный failed outcome; остальные тесты продолжаются, fail-fast выключен |
| Parameterized/dynamic test | Каждая фактическая invocation имеет уникальную identity и terminal outcome; class#method недостаточен; поведение discovery зависит от trusted fixture, не ответа студента |
| Disabled/assumption-aborted/неожиданно skipped | Не прибавлять PASS и не сокращать знаменатель молча; квалификация полного оценочного набора должна исключить либо явно обработать такую структуру |
| Ошибка контейнера, worker crash, незавершённый suite, потерянное/дублированное событие | Полная ошибка проверки, score не выдаётся; прежний лучший результат сохраняется |
| Timeout отдельной студенческой операции | Failed допустим только если доверенный helper зафиксировал именно ограниченную операцию, сохранил целостность процесса и весь набор завершился; общий timeout/потеря worker — ошибка проверки |
| Javac/API mismatch до обычных тестов | Полная понятная диагностика стадии; нельзя выдумывать failed исходы всех неисполненных тестов или считать долю по нулю discovery |

Исключение: в существующей учебной задаче предметный JUnit-тест может сам проверять ожидаемую ошибку компиляции/диагностику. Тогда javac — наблюдаемая операция теста, а проверенный исход достоверен и входит в полный набор. Это не предварительный отказ подготовки запуска. Явные ожидания стартера по решению 49 также сохраняются.

**Статус после решений 59/60:** следующий абзац — историческая непринятая рекомендация, заменённая прямым выбором: ноль за самостоятельную некомпиляцию; интерфейсный допуск без баллов и вне предметного знаменателя, при провале 0; предметные тесты только после допуска. Ошибка проверяющего средства остаётся отдельной от студенческого отказа, а не0 по пункту 53.

Для compile/API стадии рекомендуемый консервативный вариант — не выдавать числовую долю при отсутствии полного предметного набора: ответ помечается как пока не поддающийся оценке с точной студенческой диагностикой, а не как инфраструктурная авария. Это техническое предложение, не новое принятое правило баллов. Если потребуется числовой ноль за эту стадию, его нужно вывести из отдельного согласованного полного договора исполнения, не из фиктивных JUnit outcomes. [PrairieLearn external grading](https://docs.prairielearn.com/externalGrading/#grading-results) поддерживает `gradable:false` без score, в том числе для синтаксической ошибки. Прежний успех не теряется ни в этом случае, ни при infrastructure error. Слова «ошибка решения» и «ошибка проверки» в feedback различаются.

Сертификат завершённости связывает конкретные входы и запуск с обнаружением/регистрацией всех invocation, их уникальностью, terminal outcomes и финалом suites/процесса. Parent containers, lifecycle failures и пустой набор проверяются отдельно от счётчика passed. Динамическая регистрация не позволяет взять denominator из незавершённого префикса событий. Повторный запуск не добавляет вторую оценочную invocation и не скрывает прежний fail через retry/merge XML. Отчёт и payload ограничиваются по размеру: усечение stdout допустимо с явной пометкой, усечение множества результатов — ошибка, не частичная оценка.

Для всего оценочного набора сохраняется обратная связь 37: понятное русское имя и проверяемое свойство из обычного JUnit; expected/actual и локализация различия там, где применимы; при compile — присланный файл/строка/диагностика; при API-отказе — конкретная нарушенная уже объявленная сигнатура, без расширения учебного контракта ради проверяющего клиента. Объекты/байты/stdout показываются в подходящем виде. Это требования к будущему adapter, а не проверенный здесь payload/UI.

Завершённый отчёт может содержать 0 passed и все достоверные failed; это нормальный ноль по 52, а не сбой 53. PL adapter включает дробное оценивание и не оставляет старый all-pass/partialCredit=false. Официальный external-grader контракт различает score в [0,1] и `gradable:false`; настройка partial credit может обнулить дробь, поэтому её проверяют вместе с exporter, а не только вычислением дроби. Неустранимые runner-отказы — предмет разработки и отрицательной приёмки, не вопрос выбора студенту.

Все семь существующих договоров нужно сохранить; монолитные checker делятся по их фактическим задачам. Таблица ниже — техническое распределение-кандидат, не новая редакция заданий.

Никакого нового отчёта, веса или упражнения здесь не добавлено.

### 9.1. Общая граница upload/Workspace

Разные transport adapters получают ограниченное дерево: безопасное относительное имя, тип узла, байты, режим там, где значим, пустые каталоги, происхождение стартовых файлов и согласованный момент снимка. Reader защищает от traversal/ссылок/дубликатов/конфликтов, ограничивает объём и число узлов. Предметные предикаты задачи получают это дерево, не ZIP API или browser session. Лимит/потеря snapshot — транспортная ошибка с сохранением сдачи, не утверждение о неправильных файлах.

Workspace использует upstream startup/storage/submission, не собственную IDE. Для состояний, где достаточно явных файлов, обычный `gradedFiles` применим. Для directory/.git полноты требуется квалифицированный collector, который сам читает дерево и передаёт единый snapshot; присланный студентом manifest не становится доверенным от наличия хеша. Снимок нельзя собирать из изменяющихся частей без фиксации границы или обнаружения изменения. [Официальный Workspace](https://docs.prairielearn.com/workspaces/#infojson) отделяет save submission от IDE и описывает file selection; [pinned graded-files][workspace-files] и [fallback][workspace-fallback] не доказывают сохранность пустых каталогов.

Первыми интеграционными проверками идут start → save → close/resume → repeated submit → общий grader, затем пустые каталоги, hidden `.git`, HEAD/index/worktree, concurrent change и пределы. Upload reader и Workspace collector должны давать одинаковые предметные факты для одинакового договора. Режимы, специальные Git layout/index extensions и LF/CRLF проверяются по реально разрешённым условиям, не по единственному образцу репозитория. Текущий deployment Workspace — UNKNOWN, не готовая возможность курса.

### 9.2. Один ZIP local-history с bundle

Предлагаемый состав: один самодостаточный bundle и только уже предусмотренные условием результаты/пояснения. Имена вроде `history.bundle`/`result.zip` — предложения. Сдача не требует всей `.git` и не вводит новый README. Выбранные refs должны сохранять итоговую и нужную рабочую ветки; HEAD/default branch определяется явно, а не предположением `master`. Для полноты удобно включить все нужные refs без exclusions, ограничений по дате/числу коммитов и внешних prerequisites.

Проверяющий: (1) безопасно читает ZIP; (2) проверяет формат/capabilities/отсутствие prerequisites и фильтрованного promisor-набора; (3) получает объекты в пустой изолированный репозиторий без hooks/network/внешних alternates; (4) перечисляет refs, устанавливает нужную ветку и проверяет достижимость/полноту; (5) проверяет предусмотренные отношения графа и содержимое, не fixed commit SHA; (6) отдельно учитывает уже требуемые наблюдения конфликта и чистоты исходного состояния.

`git bundle verify` проверяет формат и prerequisites относительно текущего repo, а не предметную правильность ([официальный git-bundle](https://git-scm.com/docs/git-bundle#_options)); [bundle capabilities](https://git-scm.com/docs/gitformat-bundle#_capabilities) допускают object filter, который здесь нельзя молча принять за полную историю. Индекс, незакоммиченный worktree, исходная чистота и факт остановки на конфликте не восстанавливаются из bundle. Чистая новая копия не доказывает чистоту исходной. Эти остаточные требования сохраняются для содержательной рецензии; задача restore не переводится на bundle по аналогии.

Точные публичные контракты согласуются с общим архитектурным проектом, а не копируются из этой таблицы.

## 11. Разовый административный перенос

**Уточнение 58 к следующему описанию карты:** обычные однозначные соответствия и полный зачёт сохраняются; ради редких реальных неоднозначных split/merge сложный механизм переноса не требуется, соответствующие данные допустимо потерять. Это узкое исключение, не общий сброс истории и не разрешение менять данные сейчас.

Принятые требования не пересматриваются: каждый объективный полный старый auto-pass даёт полный новый зачёт без ручной части, даже если старый код несовместим; сохраняются именно код успешной попытки и старая выдача как частные свидетельства. Частичный прогресс можно начать заново без удаления истории. Один действующий курс, согласованные PL/completion/Gateway/Moodle, limited transition map и предусмотренный optional UUID сохраняются.

Рекомендуемый кандидат — штатные административные возможности PL с адресной операцией подготовки контекста/вложений там, где штатного UI/CSV недостаточно. Не новый постоянный сервис зачётов. Ограниченная карта связывает old/new question, course/work/slots/assignment и отдельно URL/anchors. Сопоставления проверяются на one-to-one и явно разобранные split/merge; optional UUID переиспользуется, но не доказывает весь перенос. Его exact author entrypoint в установленной линии ранее не найден: пользовательскую предусмотренную возможность нельзя объявить отсутствующей или заменить вторым mandatory key.

Последовательность-кандидат: зафиксировать read-only исходный срез/успешные attempt IDs и хеши → dry-run соответствий/целевых контекстов → сохранить частные байты и provenance → создать необходимые native контексты → административно начислить полный зачёт с причиной «перенесён прежний полный результат», без отметки об успехе новых тестов/ручной рецензии → проверить состояние PL и completion текущего назначения → Gateway/Moodle → отчёт и сверка до переключения. Повтор операции идемпотентен; восстановление не затирает новые ответы после переключения.

Почему это пока proposal: [официальный CSV](https://docs.prairielearn.com/manualGrading/#uploading-the-scores-and-feedback) меняет баллы/feedback, но игнорирует `submitted_answer`; [score-upload.sql:30][migration-upload] требует уже существующий `instance_question`. [manualGrading.sql:553][migration-status] снимает manual flag, но unanswered может сохраниться. [обновление:724][migration-update] не доказывает Gateway AGS. [Bridge v2.4.1:54][migration-bridge] выбирает попытку после текущего назначения, не автоматически лучшую историческую. Поэтому один CSV total=100 не равен завершённой миграции. Проценты/auto/manual components и освобождение должны правильно отображаться без фиктивной проведённой ручной проверки.

Вложения не публикуются через clientFilesQuestion; штатные personal notes имеют собственные доступ/удаление/контекст и не доказаны как неизменяемый bulk admin import. Подробные ограничения и pinned источники — [исследование переноса](../open-topics-20261028/assessment-identity-migration.md#куда-прикрепить-старый-код). Нужен адресный rehearsal с резервным восстановлением, повтором sync, новой попыткой/переназначением, правами разных студентов и сверкой Moodle. Сервер/данные здесь не читались и перенос не выполнялся.
