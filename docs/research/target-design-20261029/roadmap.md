## Правила перехода между этапами

- Результат этапа — связанная гарантия/маршрут, а не число перемещённых файлов. Независимые части допустимо готовить параллельно при одном владельце файла; зависимый результат не объявляется готовым до проверки его входов.
- Нужные тесты старого механизма переносятся, но его API не становится ограничением цели. Неиспользуемый эксперимент удаляется/архивируется после разбора назначения; похожесть кода или static unused не заменяют это решение.
- [Предупреждение project/ID (55)](../../refactoring-plan.md#decision-55) проверяется отдельно от ERROR-конфликтов: без автопереноса/переименования и без вымышленного project; составные имена сохраняются. [Именование A принято (56)](../../refactoring-plan.md#decision-56): известный project → ожидаемый exr, обратного разбора нет. Native тип и смысловой суффикс не требуют полного пути в каждом ID; точная реализация ещё не утверждена.
- Рабочий цикл следует принятому пункту 41: локальная правка → адресные проверки; общий договор → реальный producer/consumer; выпуск → точный состав, исполнение и восстановление. Это не полный курс на каждое изменение и не обещанный автоматический impact graph.
- Задачи с кратким классом/методом не получают обязательную заглушку; сложный состав может получать стартер по ссылке. Reverse-array сохраняет ручную проверку массива в 20%; её не превращают в невыполнимое утверждение по stdout.
- Ошибка компиляции/API до поведенческого набора получает точную диагностику. Предложение не выдавать новую числовую долю до исправления — ещё технический вариант внутри общего дизайна, не новое принятое правило; его нельзя незаметно вывести из пункта 53.
- Старые измерения и native-опыты остаются датированными свидетельствами. Новые версии Zod/Gradle/JUnit, инструменты форматирования, payload/UI и серверные операции не утверждены этой таблицей.
