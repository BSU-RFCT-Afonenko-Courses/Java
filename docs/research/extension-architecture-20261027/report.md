# Исследование Java: авторская модель, выпуск и предложение рефакторинга

Главный вывод: курс можно сделать понятнее и сократить повторную техническую работу без смены всей системы сборки. Первые кандидаты — один авторский канон, подходящее поле ответа, осмысленная группировка, малые публичные контракты и reuse фактов внутри доказанного lifetime. Скорость будущего рефакторинга ещё не измерена; текущие результаты дают baseline и различающие следующие опыты.

Исследование не выполняло продуктовых исправлений, releases, staging, server import или продления прежнего допуска. Исходники, старые worktrees, неуспехи и закрытые материалы сохранены. У всех 88 вопросов A/H/B есть [статус, evidence и ограничение](hypothesis-decisions.md). Полное обоснование необходимости каждого внутреннего вызова остаётся ограничением; подробности — [coverage-notes.md](coverage-notes.md).

Документы PR №24 прочитаны отдельно от кода. Для Java выбран фактический итог PR №26; прежний пользовательский checkout не переключался. Установленная композиция оставлена базой опытов. Исходники владельцев, расходящиеся линии Core 8.3/8.2.8 и Publisher 5.1.5/5.1.4, runtime 2.4.0, host 2.4.1 и assembly рассмотрены отдельно. Для Performance найден наиболее актуальный локальный worktree. Подробности — [выбор исходников](source-selection.md).

Закрытый архив преподавательских материалов восстановлен в отдельный закрытый каталог: все 5379 файлов совпали по размеру и SHA256, лишних нет. Это проверка сохранности, не проверка корректности эталонов. Переносимые Git-копии Java, обеих локальных Performance линий и добавленного System Practice проверены. Закрытые исходники и чувствительные пути в публичный текст не включены.

## Авторская модель всех подпроектов

[Полная модель](authoring-model.md) охватывает root, theory, lectures, practice, handbook и tasks. Их разные учебные функции сохраняются. Подтверждены 48 копий условий, повторные examples/API, противоречивые build-инструкции и большая производная конфигурация tasks. 1015 common mappings описывают 251 source; часть profiles повторяет defaults. Просто вынести YAML в другой файл недостаточно: автору нужен компактный рецепт с каноническим условием, API, зависимостями и формой ответа, а развёрнутая выдача должна получаться автоматически.

Для коротких задач обязательный ZIP/README и upload не являются необходимой моделью. Фактический Native содержит 128 upload questions и ни одного редактора, хотя exporter умеет редактор для подходящих контрактов. Проекты с несколькими файлами, packages, data/JAR и свободными именами требуют другого режима. Ограничивать допустимое решение фиксированным Main.java ради UI нельзя.

Все 10 лабораторных присутствуют в Native. Проблема структуры подтверждается иначе: 97 works включают 87 unit works, а весь набор помещён в один Homework set. Source подборки и назначение упражнений недостаточно отражены в выдаче; реальная видимость серверной UI отдельно не проверена.

Требование пользователя к скачиванию принято в предложение: `<lab-or-group-id>--<exercise-id>.zip`, иначе `<exercise-id>.zip`. Смысловая группа принадлежит месту выдачи; повторное включение question не должно разрушать dedup/identity. Постоянный `starter.zip` подтверждён исходником; суффикс `starter-1` вероятно создаёт браузер при повторном скачивании, HTTP headers не исследованы.

Баллы `23.333333333333332` подтверждены в Native. Предложено отделить точный расчёт от формата показа, сохранив равные веса, 70/30 и итог 100. Простая замена трёх значений на 23.33 даёт 69.99. Реальное поведение grading/gradebook пока неизвестно.

## Выпуск: рабочая публикация с открытым долгом

Прочитан завершённый чат «Выполни план публикации банков»: все 28 ходов, решения, failed/human/privacy документы и изменения стратегии. [Хронология и recovery](release-and-recovery.md) различают проверенные исходники, Native export, qualification, admission и сервер.

Сохранённые серверные receipts подтверждают импорт 128 Java + 7 System и доступность сервиса в тот момент. Публичный merge CI также завершился успешно 27 октября в 07:00 UTC; это source/student/assembly/declared inventory, а не private qualification. Но final Java runtime qualification исполнена **0/672**: infrastructure failure произошёл до сценариев. 118 включённых auto questions не равны 118 qualified. Deferred admission остаётся **NOT_VERIFIED**; историческая policy истекла и не продлевалась. Реальная Moodle-сдача, feedback/privacy и начисление баллов не проверены. Известны 34 upload ограничения.

Дополнительно найден конфликт source attempts:3 с принятой политикой неограниченных попыток и best result. Позднего человеческого согласования ограничения в истории нет. Это source-level расхождение; фактический серверный лимит требует отдельной проверки.

## Функции, контракты и стоимость

Inventory содержит 7538 функций и 65 301 callsites в 17 partitions. Source identity и полнота строк внутри parsed scope проверены. Для всех 7538 функций теперь есть operation audit либо точное source dossier; 6167 function spans отдельно перепроверены по bytes/hash. Наличие такого dossier не доказывает независимую необходимость функции или полноту автоматически составленной оценки эффектов. Отдельная статическая проверка связала 9721 прямых TS/JS вызовов с concrete declarations; 55 580 callsites не имеют static callee ID. Runtime dispatch не наблюдался; module purpose не выдаётся за доказанную необходимость каждой инструкции. [Coverage](coverage-notes.md) показывает неизвестные и исключённые части, включая partial Cybersecurity и historical vendor provenance.

Важные уточнения прежних подозрений:

- Core уже имеет batch native extraction, regular owner-row reuse и immutable snapshot. Старые сильные тезисы о глобальном inspect на каждый документ и повторной сериализации всего binding неверны. Остаются широкие input sets, повторные reads и нелинейные representation/lookups.
- Обычный hooked project всё же входит в common materialization proof и документный bridge. Возможность более узкого пути подтверждена как исследовательский кандидат; выигрыш в секундах не измерен.
- Active Performance меняет Core reuse/cache ветви. Его counters нельзя переносить на off workload.
- Stock PrairieLearn exporter уже переиспользует один collected model; полного render на каждую работу нет. Повторная обработка question до membership dedup остаётся статическим finding.
- Selected root Publisher не запускает все children без render-all. Полная композиция сериализована; jobs не заменяют уменьшение лишней работы.
- QRC переиспользует parsedPages для search; local/full обеспечивают разные scopes.
- Исторические `commonPathDocuments`, embedded feedback/publicCases и host digit-leading instance имеют выбранные fixes. Print/Moodle/Cloud сохраняют объявленные legacy boundaries и не названы новыми регрессиями Java.

[Контракты](contracts.md), [CI/поставка](dependencies-and-ci.md) и owner reports связывают операции с гарантиями и ранними отказами. Нельзя удалять integrity/privacy/currentness проверки только из-за числа SHA или LOC. Подтверждены узкие повторы validation/hash и поздние дешёвые conflicts; их runtime доля ещё неизвестна.

## System Practice

[Отдельный аудит](system-practice.md) подтверждает 7 manual questions без grader/Workspace и 58 файловых входов, включая 36 download elements. Есть локальные checker scripts, но два старых монолитных контракта не соответствуют новым независимым задачам. Git-download отдельных рабочих файлов теряет начальную историю.

Предложены ясные условия и проверки результатов всех семи задач: bytes/state, воспроизводимый pipeline, graph/refs/blobs/index/worktree Git. Своя система и native PL VS Code Workspace используют один валидатор. `.git`/index нельзя считать автоматически захваченными; bundle один не сохраняет незакоммиченные изменения. Внешний GitHub SSH и Windows имеют отдельные доказательные границы. Upstream Workspace существует, но текущий exporter seam отсутствует, а server host readiness неизвестна. Настройка сервера не выполнялась.

## Что предлагается дальше

[Сравнение вариантов](architecture-options.md) и [план рефакторинга](refactoring-proposal.md) задают владельцев и gates. Порядок: авторский/UI договор → tiny actual producer/consumer contracts → фазовое упрощение на малом Java → отдельный System Workspace pilot → новое закрытие qualification/recovery долга. Новый resolver/cache/build engine не выбран по умолчанию.

Готовы направления и критерии проверки. Не доказаны полный semantic necessity всех инструкций, скорость будущих вариантов, большой scaling, Body export completion и реальный LMS workflow. Эти ограничения входят в результат и не замещаются общим словом «готово».

Независимое [review T15](review.md) завершено: замечания к статусу fixture и исследовательскому binder исправлены. Финальные проверочная сводка (сохранена локально) и [индекс evidence](README.md#область-отчёта) сохранены. Review подтверждает ограниченные выводы, не присваивает полный semantic necessity PASS.

Дальнейшие действия собраны в [единую текстовую очередь](next-work.md): сначала понятная выдача и малые контракты, затем адресные технические пробы и отдельное закрытие долга выпуска.
