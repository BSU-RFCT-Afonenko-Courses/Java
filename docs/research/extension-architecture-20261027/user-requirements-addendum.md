# Уточнения пользователя во время исследования

Эти требования дополняют исходный план. Они исследуются без продуктовых изменений; реализация остаётся отдельным решением.

1. **Короткая задача должна иметь соразмерный интерфейс.** Отдельно проверить необходимость скачивания архива и README для короткой консольной программы. Автономный локальный комплект может оставаться дополнительной возможностью; он не должен автоматически усложнять основной путь ответа.
2. **Редактор кода — полноценный вариант.** Выяснить, почему выбран upload вместо встроенного редактора, какие ограничения реальны для свободных имён/пакетов, фиксированного API и нескольких файлов. Не вводить обязательный Main или новый учебный API ради удобства интерфейса.
3. **Нужен понятный учебный маршрут.** Разобрать фактические лабораторные со списками заданий и отдельные выдачи. Технические unit wrappers не должны оставлять студента с неясной россыпью задач. Проверить состав опубликованного Native, memberships и доступность, не подменяя это одним числом97.
4. **Имя архива содержит учебную группировку и ID упражнения.** По последнему уточнению скачиваемая заготовка называется `<lab-or-group-id>--<exercise-id>.zip`, например `lab-numbers--exr-numbers-image-size.zip`; без применимой группировки — `<exercise-id>.zip`. Нужна понятная учебная группировка, а не технический unit wrapper или порядковый номер. Имена вида `starter-1.zip` неприемлемы. При принадлежности нескольким работам проверить имя скачивания в контексте выбранной работы отдельно от единственного физического ZIP и deduplication payload. Сохраняются стабильный ID, корректные ссылки, безопасные имена и содержимое ZIP. Проверить владельца имени в exporter/download/native delivery и включить узкую миграцию в предложение.

5. **Понятное отображение grading/auto grading points.** Убрать длинные десятичные хвосты вроде `23.333333`. Сначала разделить точную политику расчёта и представление в native UI. При трёх равных slots и 70 auto points доля равна `70/3`; округление каждого значения до `23.33` даёт `69.99`. Согласованные равные веса, 70/30 и 100 за обязательную работу сохраняются. Проверить поддерживаемое форматирование и нормализацию; если требуется менять саму шкалу, показать отдельный вариант с точной суммой и последствиями, не скрывать изменение весов.

6. **System Practice: содержательная переработка и автоматическая проверка.** Пользователь указывает на неясные условия, чрезмерные файловые ссылки и отсутствие первичных автоматических проверок. Расширить исследование текущим System Practice: проверить фактические условия/пакет; предложить ясные формулировки и минимальный student flow. Сравнить выполнение в своей системе со штатным PrairieLearn Workspace (VS Code, терминал, Git, управление файлами). Для каждого типа задачи определить автоматически проверяемый результат, исходное состояние, submitted/graded files, ограничения воспроизведения и остающуюся ручную оценку. Возможность штатных Workspaces не доказывает их настройку на текущем сервере. Реальную переработку курса и серверный запуск это исследование пока не выполняет.

7. **Условие, свобода проектирования и стартер согласованы.** Проверить 5.4 Book/Car и весь банк: какие имена и сигнатуры действительно обязательны, какую структуру студент проектирует сам, что даёт готовый шаблон и что требует проверяющий клиент. Обещанную свободу нельзя отменять молча фиксированной привязкой.
8. **Границы оценки показаны непосредственно у задачи.** Явно указать автоматические свойства, доступные примеры, ручные демонстрации, проверку исходника и объяснения, вес и промежуточный статус. Публикация критериев не требует раскрытия закрытых значений и кода тестов.
9. **Проверить сообщение о двух публичных тестах и проходящем Main.** Различать запуск Main, PublicChecks, публичные/закрытые JUnit и ручное предъявление; не считать количество тестов доказательством покрытия. Выполнить адресные контроли неизменённых стартеров и варианта только под открытую пару, сохранив неизвестное для остальных задач и текущего сервера. [Результат проверки](assessment-contract-audit.md).

Для всех пунктов отчёт различает исходный рецепт, исторический пакет, наблюдаемое пользователем состояние и предлагаемое поведение. Новая проверка сервера или публикация автоматически не разрешена.
