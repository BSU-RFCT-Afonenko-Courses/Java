# Авторская модель Java: все подпроекты и типовые изменения

Закрытые преподавательские материалы сохранены и проверены восстановлением: все 5379 файлов совпали, лишних нет. Это проверка сохранности, не квалификация эталонов. Подробные проверочные материалы остаются локально.

Исследование подтверждает проблему многоместного сопровождения, но не потерю преподавательских исходников. Канонический банк, общая поддержка, разделение student/grading и штатные выдачи уже существуют. Автору приходится вручную связывать их подробными реестрами; некоторые инструкции и независимые копии остаются несогласованными. Главный кандидат на упрощение — краткие семантические зависимости с производным точным manifest. Перенос нынешнего YAML в другой файл этой задачи не решает.

Это повторная проверка фактического итога Java PR №26. Установлены Core/PrairieLearn 8.3.0, Publisher 5.1.5, QRC 3.1.0 и Download 3.2.1. Runtime Platform 2.4.0 и host tools 2.4.1 рассматриваются отдельно. Более поздние исходники владельца не подменяют установленный набор; [выбор исходников](source-selection.md) фиксирует границы сравнения.

Этот раздел подготовлен статическим проходом до новых малых опытов. В нём выполнены чтение, разбор YAML/QMD и сравнение файлов/ZIP; последующие измерения описаны в performance-findings.md. Тесты, render/preview, материализация, export, Docker, CI, сервер и сдача студентом не запускались. Числа исходников получены через `git ls-files`, без vendor и результатов сборки. Их нельзя смешивать с числами файлов материализованного выпуска. Переносимый проверочная сводка (сохранена локально) содержит конкретные пути, строки, mappings и алгоритмы сравнения; проверочная сводка (сохранена локально) не раскрывает закрытые исходники и чувствительные пути.

Число строк не измеряет runtime-стоимость. Здесь установлен объём ручной формы и повторов. 7547 строк checks + materialization составляют около 94,85% tasks config. 118 канонических блоков выбирают 118 профилей; `java-labs`, `java-queue`, `java-cli` не выбираются актуальными `project-check` атрибутами. Полезность исторических профилей либо иных внешних callers требует отдельного inventory; их удаление не выполнено.

В Core уже есть merge defaults с выбранным профилем; nested maps объединяются, списки заменяются ([projects.lua, merge](https://github.com/BSU-RFCT-Afonenko-Courses/Java/blob/60e50f8304c8c7097047f23e6a4488f2c330c48c/tasks/_extensions/Afonenko-Course-Tools/course-core/projects.lua#L45)). Наследование одного named profile от другого здесь не объявлено. Нельзя предложить перенос пустых списков в defaults, не проверив inherited `verification-tests`.

Имена SHA-каталогов сейчас совпадают с первыми 12 символами SHA-256 bytes всех 47 файлов. Однако materializer читает их как обычные буквальные source paths и отдельно хеширует bytes; проверки соответствия имени каталога хешу нет. Поэтому имя не даёт дополнительной гарантии immutable-содержимого. Это отличается от published image digest, snapshot hash и before/after проверки: у них другие subjects и consumers.

## 3. Типовые изменения: где требуется согласование

| Действие | Канон и осмысленные зависимые изменения | Нынешнее дополнительное согласование | Целевой минимальный результат |
|---|---|---|---|
| Изменить условие без смены API | Один блок `tasks/bank/<theme>.qmd`; изменить тест/ожидание только если поменялось поведение | Для 48 задач существует независимый `student/statement.qmd`; derived условия/Body/ZIP требуют обновления | Одна правка канона, остальные выдачи и локальная копия условия получаются из native результата |
| Изменить обязательный API | Канонический API/условие, starter, открытые проверки, teacher reference/bindings/prechecks и их ожидания | Профиль tests/API subsets плюс common placement содержат согласуемые перечни одного физического набора | Явный API contract и объявление компонента; generated manifest доказывает subset/placement, не вводит новое API |
| Изменить общий Java-компонент | `tasks/common` либо `test-support`; все использующие его проверки перечитывают новую версию | 1015 mappings уже обеспечивают один source для многих комплектов, но списки подключений редактируются вручную | Одно определение компонента, явные зависимости задач, раздаваемые копии производны |
| Изменить пример | Владелец соответствующего учебного примера; конкретные объяснения theory/lecture/practice/handbook меняются по смыслу | 13 ZIP handbook сопровождаются отдельно; одинаковые классы есть в нескольких source-комплектах | Воспроизводимая сборка ZIP из канона; различающиеся учебные варианты сохраняют отдельные identities |
| Изменить состав работы | `labs/*.qmd` task-items: required/choice/optional, веса/порог | Instance selection и chapters меняются, когда меняется доступность/навигация; wrappers добавляют отдельные декларации | Один выбор учебных slots и отдельно один policy доступности; derived native layout не становится вторым авторским реестром |
| Добавить задачу | Новый canonical ID, условие, student/teacher материалы, проверка либо manual policy, зависимости | Profile, 128-проектный registry, unit QMD, chapters, works, bibliography/context требуют координации | Короткая карточка зависимости + включение в нужную работу/банк; readiness показывает конкретный отсутствующий input |

Для сохранения свободного решения новый класс/метод ради теста не вводится. Если задача фиксирует API, отдельная компиляция решения → независимый API precheck → компиляция зависимых tests → поведение — реальное требование, а не лишняя формальность. Оно не означает, что автор должен повторно перечислять одни файлы в нескольких технических списках.

## 5. Штатный Quarto: применимость и пределы

Штатные project/directory/document metadata поддерживают общие значения и локальные исключения; `metadata-files` разделяет конфигурацию по файлам. Это достаточная основа для повторяющегося Reveal оформления и части defaults. Перенос registry в sidecar уменьшит файл, но сохранит независимые ручные решения. Массивы native metadata объединяются; это отличается от замены списков собственным checks merge. [Документация Quarto](https://quarto.org/docs/projects/quarto-projects.html#shared-metadata).

Profiles выражают student/full и служебные варианты. Они не заменяют учебную политику доступа, доказательство privacy и соответствие capture фактическому input. Добавлять новую профильную систему поверх них без недостающей возможности не требуется. [Project Profiles](https://quarto.org/docs/projects/profiles.html).

Native include пригоден для общего условия/API/примеров и уже применяется. Включение использует контекст родительского документа: относительные ссылки и metadata требуют внимания. Оно не выбирает произвольный `exr-*` Div из большого файла автоматически. Варианты канона: отдельный task fragment, включаемый в банк и представление, либо существующая выборка из разрешённого native результата; окончательный выбор требует сравнения на тех же outputs. [Includes](https://quarto.org/docs/authoring/includes.html).

Native resources пригодны для публичных данных и файлов сайта. Они не выражают сами по себе отображение `source → target → audience`, teacher overlay, столкновения целевых путей, assembly checks либо квалификацию эталона. Нынешний Core `conditions` получает уже разрешённый HTML/AST, исключает закрытые элементы, упаковывает локальные assets и переводит междокументные HTML-ссылки на сайт. Это отдельный полезный контракт; он не делает каждый starter автоматически автономным и не превращает онлайн-ссылки в офлайн-копию всего курса ([resolve.ts:75–123](https://github.com/BSU-RFCT-Afonenko-Courses/Java/blob/60e50f8304c8c7097047f23e6a4488f2c330c48c/tasks/_extensions/Afonenko-Course-Tools/course-core/artifacts/resolve.ts#L75)).

Проектный collector может читать только owner-level metadata; нельзя считать перенос произвольных `project-materialization`/`project-checks` в `_metadata.yml` уже поддерживаемым без анализа consumer. Точечное использование native не оправдывает новый универсальный resolver, DSL или build system.

## 6. Teacher и работа в IDE

Преподавательские материалы найдены, их потеря не подтверждена. Выбран конечный teacher input завершённой предыдущей сессии `prep304-refresh314`, а не более ранние historical/base/fix274 деревья. В нём 5379 файлов, 7 593 389 bytes; 128/128 canonical project roots имеют `reference`, `contract.md`, `rubric.md`, 119 имеют `tests/contract-cases.json`. Наличие файла не равно достаточности/правильности эталона либо выполненной квалификации. Полный private inventory и exact root сохранены отдельно; публичная сводка содержит только агрегаты и хеш алгоритма manifest. Сам факт checksum не обеспечивает резервное хранение. Переносимая копия требует отдельного закрытого сохранения и контроля exact inputs.

Стандартный materializer уже умеет однонаправленный staging. Student получает public tree и student common. Grading добавляет common обеих аудиторий и внешний teacher overlay; teacher может менять только `reference/tests/rubric.md/contract.md`, не student. Требуются current полный NativeRun owner, выбранные `--task`, новый внешний output, для grading — teacher root. Материализация не запускает JDK/Docker. Название grading означает состав дерева, а не подтверждение работоспособности.

IDE может открыть stage, но roundtrip не реализован: `--write` требует нового дерева; `--check` сравнивает точный receipt, bytes и отсутствие лишних файлов. Build/IDE files делают изменённый workspace отличным от reference stage. Provenance source/target существует, но конфликт нескольких изменённых копий одного common source им не разрешается. Owner checks config и canonical condition в этот проект не включаются; универсальный build student/reference/fixtures не создаётся. Это разные компиляционные контексты. Четыре source-проекта получают Gradle build через common mappings; активный native Gradle runtime сейчас один — GradeApp; остальные scopes не приравниваются к нему.

В выбранной чистой исследовательской копии действующий capture отсутствует. Исторический «старый pointer не читается» не повторяется как новый дефект: текущий reader принимает v2/v3 и `commonPathDocuments`. Новый native pass в рамках A не выполнялся.

Два минимальных варианта IDE:

- Открывать канонические public/common/teacher деревья через явные модули с отдельными компиляционными контекстами; stage остаётся проверяемым результатом. Обратного sync не требуется, но IDE должна показывать реальные владельцы зависимости.
- Получать stage и явный compare/patch по provenance: правки разных copies common согласуются перед переносом в один source; public/teacher boundaries сохраняются. Такой возврат — отдельный контракт, не существующая команда и не автоматический двусторонний sync.

## 8. Исторический выпуск и долг проверки

Повторные отказы и смена стратегии относятся к завершённой сессии. Три публичных отказа Java — неоднозначные captured identities при 177 QMD, потеря `course.json` между native passes, отсутствие physical common source/student inputs — привели к CI-профилю, сохранению принятой модели и проверяемому common overlay. Текущий CI содержит эти изменения; объявлять прежний отказ новым по одному старому журналу нельзя.

Фактический конечный выпуск и его ограничения различаются: исторически HTTP200/доступность получили Java128 и System7; Java содержит 118 auto/mixed + 10 manual, System — manual. Qualification имела `DEFERRED_BY_USER / NOT_VERIFIED`; оставались 34 known upload issues, а реальная Moodle student submission не была подтверждена. Позднее prep314 содержит 5379 teacher files, M 5148 files и 436 stock prepare PASS при 672 runtime сценариях OPEN. Prepare PASS — подготовка jobs, не их runtime выполнение. Эти числа имеют собственный provenance и не переименовывают выпуск в VERIFIED.

Полная хронология, exact bindings, failed/human/privacy documents, временный допуск, причина смены стратегии и предлагаемый recovery находятся в [release-and-recovery.md](release-and-recovery.md). Новый staging, повтор deferred admission, publication либо серверный импорт данным исследованием не разрешены. Имеющиеся согласованные решения не переоткрываются. Разрыв source-инструкций, готовности архива, квалификации и реальной сдачи должен быть видим автору в нормальном интерфейсе.

## 10. Варианты и следующая проверка

Первый вариант использует существующие defaults и native metadata, оставляет current exact manifests. Это малое, обратимое сокращение авторской формы; не требует нового runtime и не обещает измеренного ускорения. Второй добавляет узкие именованные dependency sets с раскрытием нынешнего manifest и сохраняет provenance/collision/audience checks. Он уменьшает многоместные правки, но требует отдельного публичного контракта и migration review. Универсальный DSL, resolver и постоянный cache пока не обоснованы.

Минимальная авторская карточка должна содержать ID/условие, student source, режим проверки, специфичный API/пример/ожидание, семантические зависимости и исключения. Работа отдельно содержит slots/choice/обязательность/веса; instance — отбор и время доступности. Native outputs, exact tests/source placement, manifests/hashes и receipts получаются из этих входов. Ни semantic-set API, ни IDE возврат не объявляются уже реализованными.

Дальше требуется адресно сравнить варианты на малом настоящем Java: один condition edit, один API edit, один common edit, work membership и новая задача; проверить совпадение public/closed outputs, автономность starter/conditions, IDE compile contexts и изменение source после capture. Ускорение измеряется отдельно от export/qualification/assembly, без произвольного SLA. Для нового решения о privacy либо учебной политике оснований нет: они уже заданы. Реализация и новый server workflow остаются отдельным будущим поручением.

## 11. Дополнение по прямому замечанию пользователя: редактор, архивы и группировка работ

Пользователь отдельно поставил под сомнение обязательные архив/README в короткой задаче, диалог прикрепления файла вместо простого редактора и показ разрозненных задач вместо лабораторных. Это новые вопросы исследования существующего UX, а не разрешение продуктовой правки. Старое решение готовить автономные task kits не означает вечного требования заставлять студента скачивать их для решения короткого упражнения в PrairieLearn. Дополнительно уже принято последнее уточнение имени: **`<lab-or-group-id>--<exercise-id>.zip`** при наличии содержательной лабораторной/группы, иначе **`<exercise-id>.zip`**. Например, `sec-lab-numbers--exr-numbers-image-size.zip`. Технические `sec-unit-*`, порядковый номер, `starter` и дата не становятся названием учебной группы. Это решение повторно не открывается.

Проверен сохранённый Native, подготовленный для фактического допуска завершённой сессии, без обращения к серверу. Две сохранённые копии согласуются по содержимому delivery. Подробные сведения о составе, memberships, именах и элементах управления сохранены локально. Статическая разметка показывает предусмотренные действия; фактическая видимость, диалог браузера, отправка и Moodle остаются непроверенными.

**Причина upload установлена.** Все 128 canonical exercise attrs переопределяют общий default editor значением `prairielearn-submission="upload"`. В сохранённом Native все 128 `question.html` содержат upload, ни один — editor; у каждого есть ссылка на `starter.zip` и README. Это blanket настройка текущей поставки. Сам exporter поддерживает `pl-file-editor`, включая несколько объявленных файлов и optional additional ZIP ([export.ts:595–640](https://github.com/BSU-RFCT-Afonenko-Courses/Java/blob/60e50f8304c8c7097047f23e6a4488f2c330c48c/tasks/_extensions/Afonenko-Course-Tools/course-prairielearn/application/export.ts#L595)). Ограничения текущего контракта уже: manual10 требует upload, а 62 automatic задачи с `primary-required:false` также не принимают editor. Для остальных 56 automatic source-задач такого запрета нет. Это ограничения установленного adapter API, а не универсальная необходимость PrairieLearn.

| Вид задачи | Конкретный пример и текущее поведение | Минимальный студенческий путь | Что необходимо сохранить |
|---|---|---|---|
| Короткая консольная с уже фиксированным Main | `exr-numbers-image-size`: один обязательный Main.java; Native предлагает upload и необязательный additional ZIP, отдельные starter/README | Полное условие + один editor + проверка/обратная связь; локальная заготовка/самопроверка — необязательный download | Published Main/API, stdin/args, допуски, manual demonstration и свободные вспомогательные классы |
| Короткая задача со свободной организацией | `exr-text-sum-text-digits`: optional Study.java либо additional ZIP с произвольными .java/package paths; Native допускает upload | Удобный editor с явно выбранным именем/путём либо необязательный upload/ZIP для нескольких файлов; это требует узкого нового контракта optional-primary editor | Не навязать Study/Main/package ради harness; сохранить законные решения и действующую 70/30 оценку |
| Задача с фиксированным API из нескольких исходников | Например опубликованные типы Vehicle/Truck: число обязательных файлов и API имеют учебный смысл | Нужные editor tabs с готовыми сигнатурами; archive опционален, если нет внешних данных/локального проекта | API precheck, поддержка иных разрешённых файлов, требуемая документация доступна прямо из условия |

В текущем starter архива `image-size` шесть файлов, 25 909 bytes: README, CHECKS, один Main и три файла открытой проверки/поддержки. Для `lunar-weight` также шесть файлов, 26 348 bytes; для `sum-text-digits` девять файлов, 29 830 bytes; GradeApp — 17 файлов, 33 018 bytes. Это не оценка сетевой задержки: архивы малы. Подтверждена лишняя обязательная последовательность действий для простого кейса, а не измеренная «медленная загрузка». Общая JUnit-поддержка нужна локальной самопроверке, но не доказывает, что студент должен скачать/прочитать комплект до ввода одной программы в браузере. README оправдан отдельной локальной операцией; инструкции ввода/сдачи простого упражнения должны читаться в самом вопросе.

**Происхождение имени архива.** В exporter нет нумерации `starter-1.zip`: файл жёстко записывается как `clientFilesQuestion/starter.zip` (:571), ссылка ведёт на `/starter.zip` (:640). В Native 128 одинаковых basename, ни у одной anchor ссылки нет атрибута `download` с содержательным именем. `starter-1` может возникать при разрешении коллизий в загрузках браузера/клиента — это вывод, а не наблюдение HTTP headers. Фактический Content-Disposition здесь не читался. Узкая будущая owner-правка должна согласовать storage/link/download name по последнему договору `<lab-or-group-id>--<exercise-id>.zip`, а без группы — `<exercise-id>.zip`, сохранив логическое владение ZIP, bytes, privacy и integrity. Один question может входить в разные работы: contextual download name/атрибут либо отдельная ссылка должны меняться на границе представления, не создавая конфликтующих payload одного logical question. Нынешний exporter сравнивает повторные question payload; этот guard сохраняется. Current Core Download отдельно использует `<exercise-id>-starter.zip`; новый пользовательский договор имени относится и к согласованности этого маршрута. Не следует менять алгоритм содержимого ZIP ради одного basename.

**Лабораторные существуют все десять; форма группировки банка действительно раздроблена.** В сохранённом Native все 97 assessments имеют один `set:"Homework"`, номера 1–97. Первые десять — лабораторные, остальные 87 — отдельные units. `assessmentSets` в `infoCourse.json` не задан. Внесение вопроса в Native ещё не означает проверенную видимость его entrypoint на сервере. Наблюдение пользователя «вижу только несколько» не опровергается наличием JSON: для этого нужна адресная проверка navigation/launch/access/UI.

87 Native units — 87 других вопросов без пересечения с 41 лабораторным. Их источник понятен: три существующих добровольных reserve menus содержат 8 + 23 + 22 = 53 memberships; одна задача (`property-count`) уже присутствует в обязательной работе, поэтому они добавляют 52 новых вопроса. Ещё 35 — тренировочный банк. В Native резервные меню не представлены тремя целыми assessment-группами: их контекст копируется в отдельные units, а вопросы получает единичный entrypoint. Например, `lunar-weight` — единичная Homework №61 с текстом о добровольной тренировке и required slot внутри неё. Технический required здесь относится к завершению выбранной добровольной unit, но выглядит как новое разрозненное задание; обязательным вкладом в курс оно становиться не должно.

Минимальный вариант A — оставить identities/оценочные работы и объединить видимую навигацию: десять лабораторных со своими списками, три reserve menu и тематический тренировочный банк; доступ к вопросу/результату остаётся адресным. Вариант B — выводить единичные Native entrypoints из явного policy доступности банка, а групповые представления — из уже существующих source menu. В обоих вариантах 35 тренировочных вопросов не становятся новой обязательной лабораторной, reserve не превращается в требование выполнить все задачи, пары не удваивают вес, и повтор condition не создаётся. Отдельная работа над discovery/access необходима прежде, чем обещать исправленную серверную витрину.
