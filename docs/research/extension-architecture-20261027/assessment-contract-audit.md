# Условие, стартер и границы оценки: дополнительная проверка банка Java

Дополнение от 27 октября 2026 года по замечаниям о задании 5.4, свободе API, двух публичных тестах и предъявлении преподавателю. Проверены все 128 карточек, их декларации, студенческие комплекты и сохранённая Native-выдача. Чтение закрытых материалов проводилось локально; здесь приведены только агрегаты и выводы без закрытых данных и решений. Живой сервер и студенческие сессии не проверялись.

**Основной вывод:** в 5.4 есть реальное несогласование обещанной свободы API с фиксированным проверяющим клиентом и формой сдачи. Объяснение автоматической и ручной оценки распределено между разными материалами. Утверждение «вся проверка состоит из двух публичных тестов» для сохранённой Native-выдачи не подтвердилось: у всех 118 автоматических задач есть также закрытые тесты. Это ещё не доказывает их достаточность или исполнение на текущем сервере.

## 1. Задание 5.4: что именно расходится

В лабораторной «Классы» четвёртый слот — выбор **Book либо Car**, а не два обязательных задания. Это видно в [составе лабораторной](https://github.com/BSU-RFCT-Afonenko-Courses/Java/blob/master/tasks/labs/objects.qmd#L37). В [условиях Book/Car](https://github.com/BSU-RFCT-Afonenko-Courses/Java/blob/master/tasks/bank/objects.qmd#L122) заданы модели, свойства и поведение, но студент выбирает наборы параметров двух конструкторов, имена методов отбора, представление результата и разрешённую организацию программы. Речь о сигнатурах конструкторов: имя конструктора Java определяется именем класса.

В [стартере Book](https://github.com/BSU-RFCT-Afonenko-Courses/Java/blob/master/tasks/projects/objects/book-selection/student/src/main/java/Book.java) уже предоставлены поля, два конкретных конструктора, методы чтения/изменения, `toString` и операции отбора `author`, `publisher`, `after`. Конструкторы и отборы требуют реализации; часть структуры и методов уже готова. [TaskBinding](https://github.com/BSU-RFCT-Afonenko-Courses/Java/blob/master/tasks/projects/objects/book-selection/student/src/test/java/TaskBinding.java) обращается именно к этому варианту. Car устроен аналогично. Такое количество готовой структуры также требует отдельного педагогического решения: какой проектный выбор должен сделать студент сам.

Само наличие примера не делает эти имена обязательными. [README Book](https://github.com/BSU-RFCT-Afonenko-Courses/Java/blob/master/tasks/projects/objects/book-selection/student/README.md#L40) прямо допускает другой API и адаптацию клиента, а отсутствие подготовленной привязки не объявляет ошибкой решения. Поэтому формулировка «условие требует придумать, а пример существует» ещё недостаточна для технического обвинения.

Подтверждённый разрыв находится дальше:

- Native-форма принимает фиксированные `Book.java,Main.java` или `Car.java,Main.java`.
- Автоматическая поставка использует собственную доверенную привязку к конкретным конструкторам и методам; редактируемый клиент из студенческого комплекта не заменяет её автоматически.
- Указание «согласуйте привязку / предъявите преподавателю» не оформлено как понятный путь сдачи и оценки для разрешённого другого API. Нельзя требовать от студента угадать этот технический переход.

### Адресное воспроизведение

На JDK 25 использован уже существующий закрытый положительный пример Book с другим допустимым API. Новое решение задачи не создавалось. Запущены те же публичный и закрытый JUnit-наборы из сохранённой Native-выдачи:

| Контроль | Компиляция решения | Компиляция проверяющего клиента | Локальный JUnit |
| --- | --- | --- | --- |
| Эталон + штатная привязка | Успех | Успех | 4 из 4 |
| Другой допустимый API + его подходящая привязка | Успех | Успех | 4 из 4 |
| То же решение + фиксированная Native-привязка | Успех | Отказ | Не запускался |
| То же решение + фиксированная привязка, дополненная правильным import | Успех | Отказ из-за типов конструктора и отсутствующих методов | Не запускался |

Последний контроль отделяет несовпадение API от одного лишь различия пакетов. Это локальная диагностика компиляции и поведения, **не** официальная контейнерная qualification, серверная сдача или новая оценка студента. Отказ подготовки проверяющего клиента не доказывает неправильность решения.

**Предлагаемое направление:** сохранить обещанную свободу. Стартер должен явно отделять обязательную часть от необязательного примера; объём готовой модели должен соответствовать учебной цели. Для свободного API нужна поддержанная преподавательская привязка либо явный ручной путь без автоматического штрафа за её отсутствие. Если автор решит закрепить API, это отдельное изменение учебного договора с одновременным обновлением условия, комплекта и проверки; нельзя закреплять его молча одним тестовым клиентом.

## 2. Проверка проблемы в общем случае

Сопоставлены 128 карточек из 12 тематических банков, 128 студенческих каталогов и 128 записей материализации. Из 121 объявленного профиля используются 118; три общих профиля не приписаны задачам. Common-files учитывались: отсутствие исходного файла в каталоге задачи само по себе не считалось отсутствием файла в выдаче.

| Раздел | Задач | Консольный договор явно фиксирован | Конкретный клиент при разрешённой свободе API/пакетов | Ручные |
| --- | ---: | ---: | ---: | ---: |
| Числа | 13 | 8 | 5 | 0 |
| Управление | 11 | 5 | 4 | 2 |
| Массивы | 11 | 5 | 4 | 2 |
| Текст | 13 | 3 | 10 | 0 |
| Классы | 10 | 0 | 10 | 0 |
| Полиморфизм | 10 | 0 | 10 | 0 |
| Обобщения | 7 | 0 | 6 | 1 |
| Исключения | 6 | 0 | 3 | 3 |
| Файлы | 14 | 1 | 13 | 0 |
| Коллекции | 14 | 0 | 12 | 2 |
| Потоки и лямбды | 16 | 0 | 16 | 0 |
| Проекты | 3 | 0 | 3 | 0 |
| **Всего** | **128** | **22** | **96** | **10** |

Это классификация договоров и способа подключения клиента. **96 — область риска, а не 96 воспроизведённых ошибок.** Свобода бывает частичной: заданный интерфейс не отменяет разрешённых пакетов, вспомогательных типов или способа демонстрации. Даже группа 22 не объявляется полностью квалифицированной по этой таблице.

Помимо Book/Car, предметную сверку требуют отборы Customer/Patient, операции с матрицами, свободные функциональные интерфейсы и методы, а также задачи с заданным интерфейсом и свободными вспомогательными классами. Необходимое правило одинаково: имя из примера не становится требованием; конкретный проверяющий клиент должен соответствовать разрешённому решению. Нельзя исправить все эти случаи глобальным требованием `Main` или одинаковых методов.

Полный механический охват дополнен предметным разбором выбранных семейств и малым воспроизведением Book. Семантическая приёмка всех разрешённых вариантов API по 128 задачам остаётся дальнейшей работой.

## 3. Действительно ли имеются только два публичных теста

Статически прочитаны все 128 Native-вопросов и конфигурации 118 автоматических заданий; методы подсчитаны строго в файлах, включённых в их grading-job.testFiles. Счётчики относятся к сохранённой поставке, а не к наблюдению JUnit на сервере.

| Единица учёта | Результат | Что это означает |
| --- | ---: | --- |
| Автоматические / ручные вопросы | 118 / 10 | У ручных нет автоматического grading-job |
| Публичные сценарии каждого автоматического вопроса | Ровно 2 | Всего 236 опубликованных сценариев |
| Публичные JUnit-методы автоматических вопросов | 236 | По два метода-адаптера на вопрос |
| Закрытые JUnit-методы | 276 в 154 файлах | Статические объявления, не 276 новых исполненных опытов |
| Автоматические вопросы без закрытых методов | 0 | У каждого есть от 1 до 30 закрытых методов |
| Все JUnit-методы в автоматической поставке | 512 | От 3 до 32 на вопрос; число методов не равно качеству покрытия |
| Проверенные ZIP | 128 | Каждый побайтно совпадает с соответствующим распакованным комплектом |

Два общих адаптера [DirectPublicExamplesTest](https://github.com/BSU-RFCT-Afonenko-Courses/Java/blob/master/tasks/test-support/junit/DirectPublicExamplesTest.java) и [PublicScenarioTest](https://github.com/BSU-RFCT-Afonenko-Courses/Java/blob/master/tasks/test-support/junit/PublicScenarioTest.java) проверяют normal/boundary. За одним методом могут стоять несколько действий и сравнений. Число двух видимых тестов не раскрывает ни полный закрытый набор, ни полноту покрытия.

Также нельзя смешивать эти числа с 436 преподавательскими qualification fixtures, описывающими ожидаемые результаты для разных реализаций. Это другой уровень проверки; не 436 скрытых входов одной студенческой программы. Историческая final qualification остаётся **0/672**: выполнение остановлено на инфраструктурном разборе до сценариев; адресные локальные пробы этот статус не заменяют.

### Может ли неизменённый стартер уже пройти проверку

Проверены девять неизменённых стартовых ZIP из сохранённой Native-выдачи. Компилировались рекурсивно все файлы комплекта, затем запускался его собственный PublicChecks. Это малые локальные пробы, без сборки курса, рендеринга и публикации.

| Задача | Режим | Только запуск Main без аргументов | PublicChecks стартера |
| --- | --- | --- | --- |
| Book | Автоматический | Код 0 | Код 1, не прошёл |
| Car | Автоматический | Код 0 | Код 1, не прошёл |
| Приветствие из аргумента | Автоматический | Код 0 | Код 1, не прошёл |
| Таблица умножения | Автоматический | Код 0 | Код 1, не прошёл |
| Функция делимости | Автоматический | Код 0 | Код 2, сбой предметного вызова |
| Объединение и пересечение множеств | Автоматический | Код 0 | Код 2, сбой предметного вызова |
| Локальные минимумы матрицы | Ручной | Код 1 | Код 1, демонстрация не завершена |
| Хеширование объектов | Ручной | Не запускался отдельно | Код 2, демонстрация не завершена |
| Представления и снимки коллекции | Ручной | Не запускался отдельно | Код 2, демонстрация не завершена |

Во всех девяти случаях неизменённый стартер **не** получил успешный результат PublicChecks. В шести автоматических задачах успешный процесс Main оказался только запуском незавершённой программы. Это возможное объяснение части сообщений студентов, но происхождение конкретных сообщений не установлено.

Отдельный контроль Book использовал уже существующую ошибочную реализацию, рассчитанную только на открытую пару. **Два публичных теста прошли, один из двух закрытых тестов отказал.** Этот пример не является стартером: он показывает, почему зелёная открытая пара не означает корректное решение, и что выбранный закрытый набор различает хотя бы этот недостаток. На все задачи такой результат не переносится.

Отдельно, комплект GradeApp содержит шесть локальных JUnit-методов (четыре из исходного проекта и два добавленных адаптера). Один из них проверяет предоставленную модель Student: его успех совместим с незавершённой основной программой. Это не успешное выполнение всей задачи; полный Gradle/JAR workflow ради этого замечания не повторялся.

У шести ручных задач PublicChecks только предъявляет наблюдения преподавателю, без автоматического сравнения предметного результата: локальные минимумы, седловые точки, хеширование объектов, представления/снимки коллекции, справочное меню, таблица дюймов. Даже код 0 такого клиента означал бы завершённое предъявление, а не начисленные баллы. Четыре другие ручные задачи не имеют PublicChecks; для задач на ошибку компиляции это может соответствовать учебной цели.

**Не установлено:** отсутствие успешного неизменённого стартера во всех 128 задачах; полнота закрытых проверок; фактическое состояние текущего сервера. Девять запусков не заменяют полный отрицательный контроль банка. Для остальных задач результат записывается как «локально не запускался», а не PASS/FAIL. Если обнаружится реально проходящая заготовка, её надо отделить от неверной команды запуска, ручного режима, другого/устаревшего ZIP и серверного расхождения.

## 4. Что должно быть явно показано студенту

Общее разделение уже есть в [README раздела tasks](https://github.com/BSU-RFCT-Afonenko-Courses/Java/blob/master/tasks/README.md#L30), введениях банков и многих README комплектов. Но изолированный Native-вопрос не включает всё введение банка. У 117 комплектов есть CHECKS.md, у 61 — BINDING.md; соответствующее объяснение часто требует скачивания. В 128 телах question.html не найдено явного объяснения долей автоматической и ручной оценки по проверенным формулировкам. Дополнительный интерфейс самого PrairieLearn отдельно не проверялся.

Предлагается единый предметный блок непосредственно у задания и согласованная короткая версия в комплекте:

| Блок для студента | Что требуется указать |
| --- | --- |
| Обязательный договор | Точные обязательные типы, сигнатуры, доступность, данные, точность, порядок и допустимые ошибки; отдельно — что студент выбирает сам |
| Открытая самопроверка | Какие сценарии доступны, что они сравнивают, как их запускать; успех примеров не равен полноте решения |
| Автоматическая оценка | Исчерпывающий перечень проверяемых свойств в опубликованной области данных; условия сравнения и реальный путь для другого допустимого API |
| Предъявление преподавателю | Конкретные исходники/артефакты, демонстрации, обязательные конструкции и вопросы объяснения; необходимость письменного отчёта, если он предусмотрен |
| Баллы и статус | Вес этой задачи в данной работе, автоматическая/ручная доли, pending до ручной проверки, участие выбранного варианта и повторных попыток |

Закрытыми остаются контрольные значения и реализация тестов. Сами критерии не должны быть секретными. Нельзя требовать скрытое имя метода, новый формат или непредусмотренную область входов.

Для **Book** предлагаемый предметный текст должен различать:

- **Автоматически:** наблюдаемое поведение согласованного клиента — создание записей и работа с их свойствами, три отбора, точное сравнение строк, строгая граница года, порядок/кратность, пустые результаты и сохранность данных. Это перечень для сверки и дальнейшего договора, а не утверждение полной доказанности текущих тестов.
- **Преподавателю:** показать исходники, два варианта конструктора, обычные и граничные демонстрации трёх отборов; объяснить закрытые поля, выбор представления авторов, устройство методов и сохранность данных. Проверить то, чего одни наблюдения результата не устанавливают.
- **Свободно:** разрешённые условием сигнатуры конструкторов, имена отбора, вид результата и организация программы. Наличие TaskBinding не отменяет свободу; отсутствие подходящей привязки требует ручного разбора.
- **Вес:** в четвёртом выбранном слоте этой лабораторной максимум 25, из них 17.5 автоматических и 7.5 ручных; Book и Car не удваивают обязательство. Это доли существующей конфигурации, не новая схема баллов.

Точные ручные рубрики и достаточность автоматического покрытия надо утвердить по каждой задаче. Общая фраза «исходник и объяснение проверяет преподаватель» полезна, но не заменяет такого предметного списка.

## 5. Очередь дальнейшей работы и приёмка

В единую локальную очередь добавлены EDU-01…EDU-05 с выполненными адресными пробами. Оставшиеся вопросы объединены в EDU-06, без запуска полной публикации или большого курса:

1. Сопоставить по каждому ID условие → допустимый стартер → открытые свойства → закрытые свойства → ручная рубрика → вес в работе. Секретные тестовые данные не включать в студенческий текст.
2. Для 96 задач со свободными измерениями отдельно выбрать поддержанный путь привязки/ручной оценки. Сначала Book/Car и один представитель консольного, интерфейсного и многофайлового договора; не вводить единый обязательный API.
3. Выполнять недостающие отрицательные контроли неизменённых стартеров адресно, переиспользуя существующие qualification fixtures. Нужны также эталон, ошибочный вариант, вариант только под публичную пару и допустимый другой API. Для каждого — действительное исполнение, число найденных/выполненных тестов, причина отказа и различение student/binding/infrastructure failure.
4. Проверить, что два публичных сценария дают полезную диагностику, а не только существуют. Для ручных клиентов исключить формулировку успешной автоматической оценки; свойства исходника и объяснение остаются ручными.
5. Отдельным разрешённым серверным сценарием сверить скачиваемый ZIP, выбранный question, отображаемые проверки/баллы и настоящий результат сдачи с исследованной поставкой. Такое разрешение не выводится из старого допуска.

Продуктовые исправления, изменение оценок, releases и серверная публикация этим дополнением не выполнялись. Первичные логи, закрытые контроли и исходники сохранены локально; в PR добавлен только текст.
