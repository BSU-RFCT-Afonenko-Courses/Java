## Затем — ранние контракты и сокращение повторной работы

1. **Actual producer→consumer.** Малый установленный пример Core → PrairieLearn/QRC/Platform: допустимое добавленное поле ответа, отсутствующая capability, неподдерживаемая schema, digit-leading instance, optional primary и ZIP union. Проверять действительный decoder, а не только producer double. Связанные вопросы: C-09, PL-M03, H41–H44, B05–B06/B13.
2. **Один immutable интервал.** Сравнить самостоятельные и batch helpers с mutation между A/use/B; выяснить, какие проверки можно повторно использовать внутри одной фазы. Сохранить свежесть на внешней границе. Связанные вопросы: C-02/C-03/C-07, PL-M02, H07–H18/H31–H35.
3. **Один вопрос в нескольких работах.** Подготовить question один раз до work overlay; сохранить отказ при различающихся payload одного ID. Проверить равные и конфликтующие bindings. Связанные вопросы: PL-UNIQUE, H34–H35.
4. **Узкие дубли и ранний отказ.** Body validation Print/Moodle, непосредственный повтор DTO digest, destination conflict до compiler. Это отдельные явные export/grading пути, а не цена обычной страницы. Связанные вопросы: PRINT-01, MOODLE-01, H36–H38, B14.
5. **Контролируемое измерение.** Разделить absent/off/active: profiler меняет некоторые Core ветви. Затем парное N1/N4 scaling с неизменным содержимым выбранной страницы. Native floor без расширений не считается равноценной заменой. Связанные вопросы: C-01/C-10, M01, H03–H04/H50–H55.
6. **Состав и выдача.** Проверить local/full QRC, selected root/child Publisher, общий output graph и только после этого bounded jobs. Параллельность не уменьшает лишнюю работу внутри тяжёлого child. Связанные вопросы: QRC-01, SITE-01, H21–H30/H56.

Для plain page, owned overlay, временных FD, незначимого файла, Presentation и Navigation остаются адресные C-04/C-05/C-06/C-08/C-11/C-12. Полные описания находятся в соответствующих `owners/*.md`. Не требуется заново собирать весь банк, чтобы ответить на каждый из этих вопросов.

## Отдельно — долг выпуска

Final runtime qualification Java исполнена 0/672 из-за инфраструктурного отказа. Старый deferred admission истёк; он не разрешает новый запуск или публикацию. Порядок закрытия долга:

- выбрать новый точный набор course/teacher/runtime/host и выполнить дешёвый input/schema/lifetime preflight;
- различить малые free-name, nested ZIP, fixed API и data/JAR случаи;
- затем выполнить согласованный полный набор reference/starter/negative сценариев и получить настоящую строгую receipt;
- отдельно проверить реальные Moodle/PL sessions, баллы, feedback/privacy и сохранность истории.

Реальная серверная проверка и новый выпуск требуют отдельного поручения. Большой Java и вся Cybersecurity matrix не повторяются для уверенности. После отказа повторяется фаза, потерявшая основание; наличие файла не считается достаточным checkpoint.

## Правила исполнения следующего этапа

Один вопрос — одна минимальная проба, одна тяжёлая очередь. До запуска назвать сохраняемые возможности и ожидаемый различающий результат. Сохранять неуспехи и частичные результаты; инфраструктурный отказ не превращать в ошибку студента. Секунды публиковать отдельно для страницы, preview, композиции, export, qualification и assembly. Новый cache, resolver и build engine не вводить без доказанного пробела более простого решения.
