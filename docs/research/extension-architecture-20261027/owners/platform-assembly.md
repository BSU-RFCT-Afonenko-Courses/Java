# Platform: композиция, assembly и границы стоимости

Статический аудит R02/T11 выполнен на `platform-current Platform PR №24` и `platform-runtime Platform runtime 2.4.0`. Product `Context`, GitSource, exporter, publisher, tests, Docker и сервер не запускались. Машинная карта операций — `results/sections/platform-operations.json`; факты чтения и ограничения — локальные исследовательские материалы. Функции, callsites, import/decorator/top-level строки исходного T01 ledger сохраняют свои identities; семантические аннотации добавлены только к прочитанным группам. Серверный bridge, TLS/provisioning и непрочитанные tests не получают автоматического обоснования.

## Независимые компоненты

Для Java выбран source `Java PR №26`, Core/Exporter8.3.0, runtime2.4.0 `Platform runtime 2.4.0`, host-tools2.4.1 `Platform host 2.4.1` и отдельно текущий HTTPS fix `Platform PR №24`. Это разные компоненты одного проверяемого tuple. Смена host validator не требует пересборки OCI, если runtime/provenance contract сохранён. Различие номеров само по себе не дефект; совпадение номеров не доказывает совместимость.

Raw runtime source, raw release assets и assembly различаются. Три raw assets — `runtime-image.json`, `published-runtime-profiles.json`, `published-toolchain-lock.json`; `images.lock.json` — отдельная observed pull view с descriptor `releaseAssembly`. В assembly допускаются ровно два unstaged data overlays: `runtime-profiles.json` и `runtime/gradle-jar-v1/toolchain-lock.json`. Остальные 214 файлов и modes обязаны совпадать с Git tree. Снимки inputs без `.git` пригодны для чтения и побайтного сравнения; исполнить authenticated GitSource на них нельзя.

`GitSource.__init__` (`tools/release_assembly.py:36`) проверяет contained `.git`, отсутствие alternates/commondir и небезопасных metadata members, exact HEAD/tree/tag/origin/root, regular blobs, stage0 index без skip/assume flags, VERSION. Он читает каждый blob отдельным `git cat-file` и удерживает bytes всех blobs. `physical` (`:61`) обходит actual tree, включая ignored files и пустые директории, сверяет modes/bytes, точный dirty set двух overlays и сохраняет stamps. Это две разные гарантии: canonical object identity и соответствие живого рабочего дерева.

`Context.__init__` (`:92`) дополнительно требует private external asset directory0700 с ровно четырьмя файлами0600; проверяет hashes трёх raw assets, receipt protocol2/delivery3/results2, source-derived registry/generated lock и image-role binding. `derive_release_registry` использует canonical Git reader; ему не подставляется overlay вместо исходного prepared lock. При этом `_fish_view` перечисляет physical fish bundle: derivation не полностью абстрагирована от живой FS, хотя bytes читает через переданный reader. Последующий `physical` замыкает состав source.

`for_build` и `for_stage` выбирают release route по external context и запрещают downgrade к legacy source images при overlays. `validate_provenance` связывает builder/images/source/delivery, а не доверяет self-reported native builder. `Context.images` возвращает deep copy; `@property` применяется при загрузке класса, payload при этом не читается. `Context.recheck` полностью создаёт новый Context и сравнивает builder/stamps/registry/images: он не использует ранее проверенные canonical blobs.

## Частота и цена: формулы, не измерения

Runtime tree содержит216 файлов и5,615,889 bytes. Успешный Context выполняет `F+9` Git processes: F отдельных blob reads, восемь fixed Git inquiries в GitSource и `status` в physical. При F216 это225 процессов. Кроме них он повторно читает все actual source files, hashes canonical/physical bytes, assets и derivation dependencies. Фактическое время, page cache, Git object inflation и bytes системного чтения не измерены; сумма размеров snapshot не равна syscall IO.

`build_course` создаёт Context один раз до export и recheck после external Quarto и непосредственно перед publish (`tools/build-course.py:151,179,190`). На успешном release route это три Context/675 Git processes. Защита post-process currentness обоснована IN05/IN06; необходимость повторно восстанавливать immutable canonical blobs на каждой границе пока не доказана. Во время export также дважды проверяется private stage, перед publish сравниваются actual native bytes и используется Linux `renameat2(RENAME_NOREPLACE)`. Новый checks output пишется отдельно от публичного native; при отказе публикации он удаляется, temporary native удаляется владельцем TemporaryDirectory.

Host `stage_registry` создаёт Context и делает финальный recheck. Для каждого existing checkout добавляются3 rechecks strict либо4 deferred; для нового checkout4 strict либо5 deferred. Итого `Context_count = 2 + Σ course_rechecks`; формула действует для успешно завершённого прохода без раннего отказа. `validate_pinned_native` делает два полных Git/blob/FS сравнения на existing и три на fresh path. Между двумя проверками внутри `validate_checkout` есть только assembly.recheck: он читает Platform/assets, native не меняет. Это самый узкий кандидат на устранение повторения при явном договоре отсутствия конкурентной native mutation; без такого договора две проверки закрывают интервал внешнего процесса. Объявлять все rechecks дублированием нельзя.

## Import и build preparation

`stage_courses` при import вставляет tools в sys.path, импортирует grading/check_registry и выполняет loader `build-course`; тот загружает private-source и release_assembly; последний загружает publish-receipt → prepare_native_toolchain. Их CLI guarded, обычный import не запускает подготовку, Git, export или stage. Dynamic `load_normalizer` регистрирует модуль перед `exec_module`, чтобы `@dataclass(frozen=True)` имел корректный module context. Default `_Policy()` создаётся при определении функций, source payload не копируется.

Shell `tools/start-pl.sh` вручную прочитан как смежная server boundary: top-level `set -eu`, проверка absolute HOST_JOBS_DIR и `exec "$@"`. Существование host jobs directory обеспечивает Compose `create_host_path:false`, а не эта строка shell. `images/prairielearn/start-bridge.sh` делает Node preflight, запускает init и bridge, ждёт ping до180итераций, ставит trap на принадлежащие PID и `wait -n`. Это lifecycle сервера, а не containers qualification. T01 исключает `tools/start-pl.sh` из своего server scope; прочтение не добавляет выдуманные ledger строки или полное покрытие bridge.

Иная граница — `images/java25-grader/toolchain/install-native.py` и `complete-native.py`: у них нет main guard. Import/exec действительно меняет umask/FS, нормализует JDK, извлекает pinned Gradle, создаёт nativebuild account/group, пишет locks/receipts и удаляет staging inputs. Dockerfile RUN намеренно выполняет этот код только при image preparation; он не является допустимым introspection import. Runtime `grade.py` import лишь определяет код/constants; grader вызывается отдельно.

`prepare_native_toolchain` отделяет authenticated download/cache от pure generated locks/baked view, private context и tar. `prepare_native_jdk` делает316-file normalized copy с единственным известным broken src.zip omission; completion добавляет3 management libraries только в private build JDK319. Оригинальный grading JDK остаётся hardened. Prepared context/actual copy receipt прямо не заявляют functional image admission. Эти операции не принадлежат page preview и не должны входить в его latency.

## История и ранние contracts

По исходникам отдельно прослежены assembly, переход Gradle, copied inputs/proofs, optional union, embedded feedback/publicCases, исправление stale negative control, host grammar/deferred route и HTTPS правка. Runtime и current содержат одинаковые release_assembly/grading_job/build-course/check-course/grader/preparation bytes. Current меняет admission/delivery validation, VERSION/proxy/docs/tests; по одной ancestry нельзя переносить runtime identity на новый host. Семантика критических fixes прочитана, не выведена только по названию коммита.

Ранний owner-owned compatibility набор должен принимать реальный producer DTO через `prepare_job`, standalone/embedded descriptor и actual host `package_integrity`, включая digit-leading instance, optional-primary absent/true/false, nested ZIP и fixed API public suite. Он нужен до большого render/export. Current embedded `grading` структурно равен standalone descriptor, включая publicCases/feedback. Это проверка данных схем, не утверждение полной runtime эквивалентности: duplicate public case IDs дополнительно отвергает `validate_public_cases`, а schema сама uniqueness по ID не выражает.

Существующие tests имеют пригодные точечные controls: `test_publish_metadata.py:177` меняет первый hex символ фактического runner hash и отдельно утверждает отличие bytes; `test_delivery_verification.py:27` пропускает `2026-2027-s1`/`7`, но сохраняет отрицательные catalog/path cases; `test_grading_job.py:165` действительно вызывает prepare_job с feedback/publicCases. Они прочитаны как regression design, но не запускались. Hash для отрицательного опыта нельзя брать из устаревшего literal без проверки, что mutation изменила actual input.

Минимальное упрощение: одна authenticated canonical source/assets derivation на operation, отдельно live boundary rechecks по поддерживаемым mutations; read-only phase object не должен пересобирать Git bytes без нового входа. Сохранить final live inventory, exact overlay contract, source/assets/image pins и безопасный publish. Такой вариант требует малого mutation/control опыта и измерения T13, прежде чем обещать ускорение; новая система workflow/cache не предлагается.
