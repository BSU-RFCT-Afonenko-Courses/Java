# PrairieLearn: Body v2, экспорт, повторное использование и студенческий интерфейс

Исследован exact owner 8.3.0 `PrairieLearn 8.3.0`, совпадающий с установленным Java exporter. Это static research: новые rendering, grading, staging или серверные действия здесь не запускались. Исторический admitted Native — отдельное свидетельство конкретной поставки, а не доказательство сегодняшней видимости UI или успешной сдачи.

## Контракты и порядок

Stock `entrypoints/export-course.ts` делает native inspect конфигурации, находит installed Core в двух известных layouts, динамически загружает `body-export/collect.ts`, `project-checks/collect.ts`, `body-export/producer.ts`. Вызывает **один** `collectNativeModel(root,{book})`, затем `collectProjectChecks(...,collected)`. Work callback строит публичный Body из уже полученного `collected.result`; утверждение о новом полном native render каждой работы неверно. Однако сбор whole model происходит до выбора instance works. Отдельный `inspect-grading.ts` опять делает inspect и `collectNativeModel`; между разными командами принятого контекста нет.

Публичная граница low-level exporter — `course-body-package-v2`: один work, полный candidate set, qualified keys, public question projection, явные binding каждого вопроса и resources с hashes. В отличие от legacy Print/Moodle этот consumer принимает текущий Body v2. Он отвергает неизвестные поля и закрытые AST marks, проверяет внутренние fragment anchors, переносит публичные resources и подтверждает SHA256 bytes. Внешние HTTP links открываются с `noopener noreferrer`; произвольный local href без declared resource отвергается. Эти проверки решают публичность и переносимость, а не текущесть авторского дерева.

`native.lua` дополнительно читает внутренний Core pointer v2/v3. Owned export branch вручную перечисляет fields active run/common binding, temporary profile, overlay и optional `commonPathDocuments`. Это явная private API зависимость от Core, хотя shared contract vocabulary генерируется. Текущая 8.3 reader уже принимает `commonPathDocuments`; исторический отказ старого reader нельзя переносить на эту выбранную линию. Narrow public enrollment/capability DTO и ранняя installed compatibility проверка предпочтительны ручному копированию закрытого layout.

Production registry для automatic jobs требует digest-pinned image; candidate image допускается только отдельным CLI флагом с локальным Docker inspect. Descriptor связывает runtime source mode, trusted tests, API precheck и Java build. Manual projects обязаны не иметь project-check. Validation/readiness не являются runtime qualification, а `verificationInventoryHash` связывает объявленные сценарии, не доказывая их исполнение.

## H34–H35: что действительно повторяется

`exportCourse` идёт по selected works. Для каждого work строит Body и scratch project; для каждого membership заново выбирает student sources, читает trusted tests, создаёт descriptor и запускает `exportPrairieLearn`. В low-level exporter `renderPublicBody` вызывает один `quarto pandoc --from=json --to=html5 --mathml` на question condition. Overview каждого work/menu также вызывает renderer. После этого automatic question снова проходит `selectedSources` для `serverFilesQuestion/starter`, затем `inventory(partial question)` читает и хеширует все файлы. Лишь после всей этой работы проверяется: вопрос уже есть в stage или нет.

Повторный question допускается только при одинаковых canonical semantic snapshot и inventory bytes. Неодинаковый payload того же logical ID — отказ. Это важный conflict guard. Для M memberships и U unique questions подготовка/рендер/первый inventory масштабируются с M, а сохранённый logical bank — с U. При повторе inventory уже сохранённого stage question читается заново. `menuBodies` кэширует только получение menu Body; его introduction всё ещё конвертируется при каждом связанном unit context. Кроме того, `.find` по model/checks/projects расположен внутри question loops; индексирование по identity могло бы убрать линейный поиск, но не native conversion.

H34 **поддержана статически** для повторных memberships; секунды и байты повторной работы не измерены. H35 **поддержана частично** на границах CLI и whole scope до отбора; внутри stock exporter collected уже переиспользуется. Корректный следующий опыт — один и тот же question в двух works, равные и конфликтующие binding, изменение resource/source между фазами; сравнить unique compilation с work overlay при неизменных UUID, hashes, grading и отказах. Нельзя просто пропускать второй question по ID: это скрыло бы конфликт.

`publication-conditions.ts` — отдельная explicit historical dependency. Loader кэширует snapshot reads, связывает ZIP/receipt/source manifest, ограничивает размер, затем `check()` заново читает bytes/identity перед публикацией. Эти повторные чтения находятся на явно отделённых границах мутации; их стоимость и нужность отделяются от вопроса «зачем несколько раз рендерить один immutable fragment». Исторический ZIP не выбирает актуальную базу всего исследования.

## Editor, upload и архив

Adapter поддерживает два native submission mode: `editor` и `upload`. Editor создаёт `pl-file-editor` на каждый фиксированный `b.files`, требует UTF-8, лимит 1 MiB и отсутствие NUL, допускает несколько файлов; сохранить необходимые пути можно. Поэтому «PrairieLearn умеет только прикреплять файл» опровергнуто кодом. Для `additionalJavaSources.primaryRequired=false` exporter сейчас требует upload: свободные имена/пакеты и multifile решения нельзя молча заменить одним обязательным `Main.java`.

Если передан `studentArtifact`, независимо от mode создаётся `clientFilesQuestion/starter.zip`, а в HTML всегда добавляется ссылка на ZIP и отдельная ссылка на README, если он есть. Эти ссылки — сознательный текущий шаблон exporter, не требование native платформы. Upload дополнительно выдаёт download каждого student файла. Избыточность для короткого упражнения подтверждается структурой шаблона; состав полезного минимального primary flow зависит от API/data конкретного задания.

В admitted Java Native статически найдены 128 upload, 0 editor, 128 ZIP и README links; source defaults тоже upload. Это выбор текущего курса. Из 118 automatic questions 56 допускают простой editor по текущим контрактам, 62 имеют свободный primary source path, для них нужна более богатая модель или upload/workspace. 10 manual не следует автоматически переводить в фиксированный editor. Реальное browser submission/editor experience отдельно не проверялось.

Имя `starter.zip` зафиксировано в `application/export.ts:571` и `:640`. `starter-1` не найден как generated author filename; браузерное переименование повторной загрузки — предположение. Новое требование `<lab-or-group-id>--<exercise-id>.zip` относится к download presentation, тогда как logical question один на несколько works. Group-dependent изменение общего question HTML может вызвать существующий dedup conflict. Следует выбрать canonical meaningful group либо contextual link name с единым payload; manifests, ссылку и фактический download name проверять вместе. Не использовать ordinal или technical sec-unit как педагогическую группу.

## Группировка и баллы

`exportCourse` сейчас назначает `set` только по `Exam`/`Homework`; `assessmentSets` не создаёт. Work overview содержит публичное введение и контекст reserve menu для single-unit wrapper, но плоские 87 unit assessments не становятся от этого ясной учебной картой. Admitted Native содержит все 10 laboratory assessments и 97 works всего; утверждение «остальных лабораторных вообще нет в пакете» не подтверждается. Причина реальной видимости части работ на сервере остаётся неизвестной. Следует сохранить 10 содержательных лабораторных и тематические reserve/training groups, порядок, optional policy и choice один раз, затем проверять student view.

`gradingPolicy` переносит authored конечные неотрицательные числа в native `points`/`autoPoints`/`manualPoints` без display formatting. Равные три доли automatic pool 70 дают в IEEE754 `23.333333333333332`. Это не отдельный алгоритм grading, придумавший дробь: число уже задано текущим author policy и сериализуется без округления. Три округлённых 23.33 дают 69.99; распределение24/23/23 меняет равенство slots. Предпочтительный исследуемый путь — точный author recipe «общий вес + равные slots», finite UI formatting при сохранении расчёта; если pinned Native не позволяет нужное представление, отдельный согласованный вариант шкалы и bridge normalization. Не подменять договор 70/30/100 молчаливой правкой.

`attempts` экспортируется как native `triesPerVariant`; обязательный positive integer validator не выражает unlimited policy сам по себе. `singleVariant` — отдельный question setting. Completion считает только fully complete required slots на exact row set; auto score1 не отменяет pending manual grading. Новый UX не должен изменять попытки, best result, choices, optional weights или manual completion.

## Следующие проверки и предел полноты

В единую очередь нужны: duplicate question compilation до work overlay с negative conflict case; cross-command bound context invalidation; fixed single/multi-file editor и свободные paths; meaningful filename при multi-work question; grouping actual student view; finite points display с сохранением суммы/равенства; native workspace support как отдельный third submission route, ещё отсутствующий в exporter declaration schema. Ни один из этих пунктов не требует повторять full Java publication в этом исследовании.

Runtime measurements и dynamic target identity не выдуманы. проверочная сводка (сохранена локально).
