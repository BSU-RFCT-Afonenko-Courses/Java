## prepare_job и дополнительный public job

`prepare_job` проверяет schema/readiness и все selected source/trusted/public/test/fixture hashes до создания scratch. Он выбирает starter/reference/contract, проверяет mapping/API subset, descriptor, delivery/question/runtime/source binding. Reference extras при разрешённом ZIP детерминированно упаковываются в память; optional-primary contract заменяет набор sources, legacy absent/true сохраняет обязательные primary. Schema PASS требует nonempty starter inventory даже при optional-primary; возможность студента загрузить только ZIP — отдельное runtime свойство.

`primaryRequired=false` разрешает отсутствие primary и компилирует фактическую union присутствующих primary и безопасных Java ZIP members. Отсутствующий primary не освобождает от unsafe path/size checks; пустая union отвергается. ZIP parser замыкает paths/types/duplicates/collisions/UTF-8/actual inflated sizes до extraction. Free class/package name не требует Main. Fixed API компилирует student отдельно, потом trusted API reflection precheck, затем dependent tests; mismatch имеет `student-api-mismatch`, trusted compile failure — infrastructure. Public fixed-API suite требует собственного explicit precheck, проверяемого до scratch.

Scratch включает отдельный `public-verification` только при verificationTests. `run_job` рекурсивно запускает его после **infrastructure complete** primary result; даже compilation/API student failure с complete infrastructure может получить public run. Каждый такой job имеет собственный adapter/compiler archive и, при native runtime, собственную Gradle build. `publicResult` не является вторым canonical scenario receipt: оно вложено в результат и влияет на required-tests expectations. Empty/partial results не образуют complete receipt.

`check-course.main` исполняет project×scenario последовательно; результаты накапливаются в памяти. Scratch удаляется finally после сохранения private native build evidence. Uncaught preparation failure обрывает loop и пишет error без накопленных result rows; interruption до final write также не оставляет resumable report. Поэтому текущий CLI после раннего сбоя повторяет уже выполненную работу; наличие private logs не означает готовый resume. Сохранить partial observation report с exact closure — узкое будущее изменение, но API повторного принятия такого report требует отдельного контракта.

## Контейнеры и toolchain hashes

Container backend `run_job` делает один `docker run --rm` на primary job и ещё один на public job при описанном условии. Формула `C=Σ(1+I(publicTests && primary.infrastructure=complete))`, без факультативно недоступных references и без jobs, оборванных до launch. При outer timeout он делает `docker rm --force` своего случайно названного container. Mutation variants и JUnit child JVM выполняются внутри того же container, не становятся дополнительными Docker runs. Host diagnostic backend создаёт0 containers и не удовлетворяет strict container receipt. Для финальных672 исторически0containers сценариев, поскольку отказ произошёл до loop.

`runtime_evidence` повторно читает bundle/runner/shared closure: после complete run, для native build-proof validation и при verify_results на каждом scenario; strict release reader повторяет closure на каждую automatic question. Эти вызовы возвращают одинаковый subject при неизменном runtime, но разделены execution/result/admission trust boundaries. Число вызовов по одному имени не доказывает необходимость полного FS read на каждой question.

Native Gradle success проходит `_verify_native_toolchain`7раз на один job: initial build, до/после Gradle через intact, после build return, до/после dependent execution и final finish verify. Каждый раз читается вся JDK319 и Gradle716 installation. Дополнительно `_grading_boundary` хеширует5 hardened core files (включая lib/modules) до/после каждого hardened Java subprocess; плюс native initial/intact boundaries. Если J — число соответствующих Java child calls, это `2J+7` hardened boundary scans на успешном native job. Initial/final preflight также запускают java/javac version; native recipe/source/artifact checks повторяются на тех же intact boundaries. Formula не равна измеренному bottleneck.

Изоляция здесь существенна: official root supervisor, отдельный nativebuild UID, private tests/canary denied, фактически только loopback, Landlock, очищенный env, offline Gradle9.8.0 без daemon/build-cache; process group cleanup и reaper отделяют build children от private grader. Постоянный глобальный runtime cache без границы trust не обоснован. Кандидат — один проверенный read-only toolchain identity на job/operation плюс проверки реально изменяемых source/artifact/role границ; сначала измерить, какие protected files может менять каждый UID. Adapter уже компилируется один раз на `_JobRuntime` и переиспользуется между mutation variants внутри job; этот существующий reuse следует сохранить.

## Platform/T11 и новые UX вопросы

Editor поддержан existing exporter и Platform `package_integrity`: по одному `pl-file-editor` для каждого declared bound filename, UTF-8 starter≤1MiB; это может быть несколько фиксированных файлов. Это не произвольный file tree редактор: `primaryRequired=false` требует upload, nested/free names идут через ZIP; manual route требует upload. Для короткого фиксированного файла нет Platform требования обязательно скачивать архив/README. Autonomous kit может остаться дополнительной выдачей. Дефолт upload в Java — owner recipe choice, а не отсутствие editor capability.

Current producer сохраняет физический `clientFilesQuestion/starter.zip` и literal link. Требование `<lab-or-group-id>--<exercise-id>.zip` надо реализовать на presentation/download имени в контексте выбранной работы, отдельно от canonical payload deduplication. Platform checksum/inventory binding должен проверить получившийся пакет, но не должен сам выбирать педагогическую lab grouping.97 works и slot catalog проверяют состав/идентичность, не понятность student navigation. Actual published UI остаётся не наблюдённым этим аудитом.

`package_integrity` различает auto/manual/mixed компоненты, но не доказывает принятую политику100/70/30 или human-readable формат. Runtime возвращает normalized score0..1; `student_feedback` пропускает bounded finite score и только явно публичные case observations, не private logs/rawResult/tests source. Равные auto70/3 нужно сохранять в расчёте; отображение округляется native UI отдельно. Форматирование и навигацию должен проверить Native/bridge consumer audit, а не менять веса до69.99. Исходное unlimited/best решение остаётся требованием; попытки3 — отдельное source-policy расхождение.

Самые ранние достаточные проверки: full descriptor/host grammar до render; schema/profile/readiness/API source selection до scratch; missing reference/fixture до большого scenario loop; closure/runtime prerequisites до expensive build; complete coverage только после выполнения. Сохранять успешный render полезно, но это не даёт оснований пропустить изменившиеся capture/export/qualification inputs. Доказанное изменение каталога QRC требует нового freeze/export, а host-only digit grammar fix может повторить qualification без нового рендера при сохранённом exact tuple.

## Дополнение: Native Workspace для SystemPractice

У выбранной Platform исходник upstream Community и образ учтены отдельно; актуальный опубликованный образ определяется внешними runtime assets. Vendored `schemas/native-upstream/infoQuestion.json:274` уже описывает `workspaceOptions`, `gradedFiles`, image/port/home, environment и network. Наличие полей в vendored schema подтверждает DTO capability, но не работу workspace host на этом exact Community image: schema provenance относится к отдельному Exporter snapshot, а upstream runtime источник/сервер здесь не прочитан целиком.

Compose даёт PL Docker socket и `/jobs` для sibling external graders. Example prod/local config задают external grading, но workspace host configuration/service/storage/routing в выбранных manifest не объявлены; Docker socket сам по себе не включает persistent student workspaces. Patch local grader связывает host jobs path и external grading, а не workspace lifecycle. Никакой проверки current server config, workspace image pull/start, persistence или реальной передачи файлов не выполнялось. Следовательно «current server workspaces enabled» остаётся UNKNOWN.

Согласно отдельно проверенным координатором официальным [Workspaces](https://docs.prairielearn.com/workspaces/) и [pl-workspace](https://docs.prairielearn.com/elements/pl-workspace/), native workspace может дать persistent container с редактором/terminal/files и export gradedFiles в submission для external grading. Это отдельный долгоживущий student container; grader остаётся коротким изолированным проверяющим запуском. Установленный Exporter8.3 допускает только submission upload/editor и сам workspaceOptions/data_files/gradedFiles seam не производит. Потребуются явный owner contract, workspace image с нужными Git/fish/tooling, course seed files и проверка фактического extraction/packaging в grader input; нынешний Java/fish runner не принимает произвольное дерево или репозиторий без declared mapping.

Для7manual SystemPractice отсутствие auto checks в текущем recipe не доказывает непригодность native workspace: manual grading и workspace — разные решения. Но создать workspace не означает автоматически получить semantic tests и правильную оценку Git/history/files. Native path следует сравнить с собственным интерфейсом на маленьком учебном случае; новый deploy/система не выбран. Legacy course-cloud VM API принадлежит другому контракту и не заменяет workspace host. Содержательные условия, ссылки и actual Native SystemPractice исследует координатор отдельно.
