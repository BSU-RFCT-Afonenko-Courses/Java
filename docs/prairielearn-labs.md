# Поставка лабораторных в PrairieLearn

Курс `java-semester-one` хранит условия в `tasks/bank/`, состав работ в
`tasks/labs/` и проекты в `tasks/projects/`. Действующий
[план](course-revision-plan.md) распространяет проверенную поставку на всю
отобранную лабораторную линию. Этот документ различает исходный состав
и правила предстоящей технической работы. Подборка первых трёх работ
в базе `68ee355` не содержит случайных позиций:

| Работа | Обязательные задачи |
|---|---|
| Числовые вычисления | Приветствие, размер изображения, принадлежность интервалу |
| Управление обработкой данных | Подсчёт пробелов, экстремумы последовательности |
| Массивы и изменения данных | Обратный вывод, вычитание среднего строки, устойчивая перестановка строк |

Итого восемь обязательных позиций: 3/2/3. Дополнительные подключённые
карточки сохраняются в банке, но не входят в обязательный знаменатель.
Новая карточка `exr-numbers-image-size` использует проект `/projects/image-size`.
Состав сверяется одновременно в условиях, подборках, стартерах, тестах
и экспорте. Прежний запуск этой восьмёрки сохранён в исторической части
[журнала](full-revision-progress.md); новый запуск восстановленной поставки
фиксируется отдельно в его актуальном разделе.
Прежние результаты для 17 вопросов и случайных позиций 6/4/4 относятся
к прежнему составу и не подтверждают новую поставку.

## Исходные проекты

Обычный консольный проект содержит:

- `student/src/main/java/Main.java` — компилируемую стартовую программу;
- `student/src/test/java/PublicExamplesTest.java` — публичные примеры запуска;
- `reference/Main.java` — авторское решение;
- `tests/junit/ContractTest.java` — закрытую оцениваемую проверку;
- `tests/fixtures/` и `tests/contract-cases.json` — ошибочные реализации и ожидаемые результаты их проверки.

Условие каждого задания определяет стандартный ввод, аргументы и наблюдаемый вывод. Выбор алгоритма и методов остаётся у студента. Задачи с заданными константами не требуют числовых CLI-аргументов. Для трёх матричных задач обязательный исходный пример выполняется при пустом вводе; дополнительные входы — строго 3×3 со значениями −3…3. Проверка сортировки включает переставленные строки и равные суммы.

Ссылки «Скачать стартовый проект» используют штатный `project-download` shortcode и мост `course-model: true`. Каждый архив должен содержать только каталог `student/`, включая публичные примеры; эталоны и закрытые проверки исключаются в обоих профилях student и full. Пути `project="/projects/…"` относятся к корню проекта `tasks`. Состав новых архивов подтверждается отдельной проверкой.

Отдельная manual-задача gradeapp имеет стартер из 17 публичных файлов с предоставленными `build.sh`, `build.cmd` и `wrapper/maven-wrapper.properties`; `.mvn` создаётся только локально. Студент реализует пять TODO; отчёт допускает цикл или Stream. Reference и закрытые проверки не входят в публичный ZIP.

Java 25 — выбранная среда проверки. В среде с несколькими JDK явно задайте
`JAVA_HOME` и `PATH` на JDK 25. Исходные консольные проекты запускают `Main`
в отдельной JVM с UTF-8 вводом, EOF и ограничениями времени и вывода.
Публичные примеры выполняются отдельно от закрытой оцениваемой проверки
и не определяют балл. Эталон должен пройти проверки; стартовая программа
компилируется, но её поведение не выполняет условие полностью. Для каждой
ошибочной реализации задаётся ожидаемый отказ. Сбой инфраструктуры
отличается от ошибки решения.

При преподавательской проверке просмотрите диапазон промежуточных вычислений изображения, использование массивов и сохранение исходных данных там, где этого требует условие. Автоматическая проверка наблюдаемого результата не доказывает эти свойства исходника. Дополнительная часть про эхо не оценивается.

## Контракт и порядок проверки

Astra передаёт Sol опубликованные цель, допустимые входы, результат,
исключённые случаи, необходимые требования к технике и API, допустимые
варианты решений и способ предъявления. Имя уже требуемого метода
согласуется в условии и стартере. Новая сигнатура ради удобства теста
свободному решению не навязывается. Автоматические проверки соблюдают
опубликованные ограничения; требования к исходнику и рассуждению сохраняют
отдельную проверку там, где запуск их не устанавливает.

Для фиксированного API обязателен следующий порядок:

1. Компиляция решения отдельно от зависимых тестов.
2. Независимая рефлексивная предпроверка опубликованных классов, методов,
   параметров, возвращаемых типов и модификаторов. Контракт checked-исключений
   учитывается в пределах требований опубликованного условия. Предпроверка
   не содержит статических ссылок на студенческие типы; загрузка для
   диагностики не инициализирует класс.
3. Компиляция unit-тестов с прямыми вызовами после успешной предпроверки.
4. Проверка поведения.

`@BeforeAll` и `@Order` этот порядок компиляции не обеспечивают. Ошибка
компиляции решения, несоответствие опубликованному API и неверное поведение
получают разные сообщения: ожидание, наблюдение и причину отказа. Зависимые
проверки пропускаются с понятной причиной; независимые могут продолжаться.
Сбой компиляции зависимого типизированного клиента, включая unit-тесты,
классифицируется по установленной причине. Нарушение опубликованного
контракта решением сообщается как несоответствие API; дефект теста или среды
— как инфраструктурный сбой. Оба вида отказов возникают до проверки
поведения и не обозначаются как неверный результат исполнения решения.

Для обобщений добавляются положительные и отрицательные компиляционные
пробы типизированных клиентов. Сначала должны компилироваться решение
и положительный клиент. Отрицательная проба изолирует проверяемую причину:
ошибка типа аргумента не подменяется необработанным checked-исключением
или отсутствующим классом. Рефлексия стёртых типов эту проверку не заменяет.

## Выбор средств и общая поддержка

Выбор процессного инструмента остаётся открытым до технического сравнения.
Sol проверяет выделение нынешнего JUnit runner и адаптированный процессный
подход на размере изображения, изменении регистра и сортировке строк
матрицы; очередь и gradeapp дополняют проверку API, типов и диагностики.
`CGrader.test_run` требует Java-среды и адаптации; его объединение stdout/stderr
нужно согласовать с конкретным контрактом. Наличие примера в
`TESTING-OPTIONS.md` пакета не подтверждает запущенную Java-интеграцию.

Прямой вызов `main` допустим для совместимой программы. Общих требований
повторного вызова любого `main` в одной JVM и запрета `System.exit`
или статических полей нет. Средство исполнения сохраняет допустимые решения.
Новая библиотека выбирается по предметной пользе и стоимости поддержки.

| Наблюдаемый контракт | Проверка |
|---|---|
| Значение метода | Параметризованные примеры с обычными утверждениями JUnit |
| Консольный текст | Точный текст с сохранением значимых пробелов, переводов строк и EOF; каналы и статус по условию |
| Числа, массивы, коллекции | Точные целые, опубликованный числовой допуск, размерность, порядок и кратность |
| Состояние и отказы | Последовательность операций и состояние после отказа |
| API и типы | Предварительная диагностика опубликованной структуры и типизированные клиенты |
| Исходная программа | Компиляция и проверка сохранённых фрагментов или обязательной техники |
| Файлы и приложение | Временные файлы, компоненты напрямую и отдельные интеграционные запуски |
| Несколько допустимых ответов | Независимые свойства и воспроизводимые примеры без навязанного единственного ответа |

Общая поддержка `tasks/test-support/` создаётся для повторяющегося запуска,
разбора чисел/матриц с явными правилами, компиляционных проб и диагностики
опубликованного API. Данные конкретной задачи и алгоритмы ожидаемого ответа
остаются вне неё. Универсальный DSL и обёртки над каждым обычным assertion
не вводятся. Публичные и закрытые данные разделены при общей версии
инфраструктуры. `tests/contract-cases.json` задаёт ошибочные реализации
и ожидаемые результаты их проверки; это проверка качества тестов.
Вес задания фиксируется независимо от числа параметризованных случаев.

## Подготовка и подтверждение поставки

Расширения устанавливаются целиком штатным `quarto add` через
`tools/sync-providers.py`; базовые commit, состав и hashes закреплены в
`providers.json` и `installed-packages.json`. Восстановленная база включает
16 локальных поправок из `docs/local-extension-patches.json`. До переустановки
Sol обеспечивает их воспроизведение закреплённым выпуском либо явным
применением commits/patches со сверкой хешей. Optional-time, названия проектов
и исправленный переход к началу длинного раздела сохраняются. Локальный
commit инструмента сам по себе не считается опубликованным выпуском.
Runtime source и OCI digests закреплены в `CI/toolchain.json` и `UPSTREAM.md`.

Для подготовки поставки используйте `CI/render.sh` и `CI/check-projects.sh` с точной выпущенной Platform в `PL_PLATFORM_ROOT`. Сборки student/full проверяют публичные материалы и преподавательскую проекцию; проекты и записи закрытой проверки исключены из ресурсов сайта. Экспорт и container verification выполняются для всей выбранной поставки, без сокращения списка вопросов и сценариев.

Команды выполняет Sol из корня курса с Quarto 1.11.5, CUE 0.17.1, Python,
JDK 25 и Docker, после проверки восстановленных зависимостей и локальных
поправок. Внешний checkout Platform должен соответствовать `platform.commit`
из `CI/toolchain.json`. По завершённому аудиту handoff от 16 октября 2026 года
все три GHCR packages публичны; для чтения закреплённых образов GHCR login
не требуется. Анонимное чтение manifests не подтверждает загрузку слоёв,
архитектуру и запуск на новой машине: эти проверки выполняются отдельно.
Нужные текущие образы загружаются по digest; повторный аудит публичности
и скачивание всех исторических версий в этот этап не входят.
Замените абсолютные пути путями своей установки:

```sh
export JAVA_HOME=/absolute/jdk-25
export PATH="$JAVA_HOME/bin:$PATH"
export PL_PLATFORM_ROOT=/absolute/prairielearn-platform
export CI_CHECK_OUTPUT="$(mktemp -d -t java-project-checks-XXXXXXXX)"
python3 - <<'PY'
import json, os, subprocess
from pathlib import Path
platform = json.loads(Path('CI/toolchain.json').read_text())['platform']
actual = subprocess.check_output(['git', '-C', os.environ['PL_PLATFORM_ROOT'], 'rev-parse', 'HEAD'], text=True).strip()
if actual != platform['commit']:
    raise SystemExit('Исходник Platform не совпадает с закреплённым commit')
subprocess.run(['docker', 'pull', platform['javaImage']], check=True)
PY
python3 -m pip install --requirement "$PL_PLATFORM_ROOT/requirements.txt"
bash CI/render.sh
bash CI/check-projects.sh
```

`CI_CHECK_OUTPUT` хранит manifest, inventory, delivery и результаты полного прогона вне исходного репозитория. Проверка проектов выполняет обе среды, `host` и `container`; обе должны пройти.

Sol проверяет необходимость прежнего login в потребляющих workflow публичного
GHCR, сохраняя digest pins и права доступа к исходникам. Серверные secrets
и настройки организации автоматически не меняются. Новый hosted CI,
действующая Moodle-связь и серверная поставка получают отдельные свидетельства;
локальный успешный прогон их не подтверждает. Технический отчёт фиксирует
исходный SHA, зависимости, полный выбранный состав, допустимые решения,
показательные ошибки и фактические границы проверки.
