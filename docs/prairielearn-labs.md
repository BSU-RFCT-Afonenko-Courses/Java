# Поставка и проверка задач Java и System Practice

Нормативны последние прямые решения [плана](refactoring-plan.md).
Полномочия, календарь и критерии выпуска задаёт [регламент](release-execution-regulation-20261103.md),
вход на целевой машине — [стартовое поручение](refactoring-start-20261030.md),
роли и усилия — [принятая матрица](agent-execution-proposal-20261029.md).
Этот документ сохраняет предметные правила; перечисленные ниже target-проверки
выполняются в будущей исполнительной сессии. Они здесь не объявлены пройденными.
Прежние локальные составы `pilot`, номера образов, Maven-стартеры и отдельные
JUnit-прогоны не являются выбором или допуском нового выпуска.

## Канон, выдача и сдача

У задачи один канонический текст в банковском QMD — непосредственно либо
через native include. Полное условие доступно на странице темы, в PL
и README самостоятельного комплекта. README объединяет условие, общую
инструкцию выбранного native build-профиля и необязательные локальные особенности.
Раздел «что отправить» получается из контракта сдачи без ручного повторения.

Проекты группируются как `tasks/projects/<theme>/<task>`. Тесты, данные,
стартеры и объявленные авторские решения хранятся рядом с проектом;
общая поддержка имеет один канон. Общий Git открыт, но это не определяет
состав student/full. В student входят стартер, необходимые данные и только
явно выбранные demo со своими зависимостями; авторские решения и полный
оценочный набор по умолчанию не входят в архив и показ Pages/PL.
Полный авторский IDE-комплект содержит нужные исходники, тесты, ресурсы,
зависимости и решения; альтернативы с одноимёнными классами компилируются
в отдельных контекстах. Материализация не меняет канон и не означает зачёта.

Скачанный проект и сдаваемый ответ различаются. Простую Java-задачу можно
написать и сдать одним файлом с JDK и любым редактором; установка Gradle,
IDE и запуск demo не являются условием зачёта. Несколько файлов, архив
или Workspace выбираются по договору задачи. Пакет не добавляется без
явного требования. Обязательные имена и сигнатуры задаются текстом либо
каноническим каркасом без реализации; если обязательны именно сигнатуры
стартера, условие прямо на него ссылается. Пример кода не вводит скрытый API.

Для сложных задач и необязательной JUnit-самопроверки используется установленный
Gradle без Wrapper. Настоящие build/settings/convention-файлы владеют внешними
зависимостями, scopes, версиями и tasks; YAML не создаёт второй менеджер
зависимостей. Общие helper и build logic включаются в самостоятельную выдачу
либо доступны как обоснованная обычная зависимость. После первоначальной
настройки выбранная самопроверка запускается одной командой `gradle test`
или из IDE. Первоначальная настройка может требовать сети/cache; полностью
offline на чистой машине не обещается. Непрограммные и Git-задачи не получают
Gradle по умолчанию.

**Target-проверка:** распаковать student/full вне авторского checkout,
проверить полный состав и запуск выбранных тестов; пройти условие/include/ресурсы
→ README/ZIP → Pages/PL; отдельно проверить отображение проектного пути
в разрешённое имя сдачи, multi-file/package и отсутствие лишних обязательных файлов.

## Контракт и порядок проверки

Учебный автор передаёт опубликованную цель, допустимые входы, результат,
исключённые случаи, обязательные приёмы, необходимый API, допустимые варианты
решения и способ предъявления. Предпосылка задачи не становится обязанностью
проверять её программой. Свободная задача сохраняет свободу классов, методов
и допустимого запуска. Общих требований повторно вызывать `main` в одной JVM
или запрещать `System.exit` нет. Автоматическая проверка следует условию;
изменение обязанности ради удобства теста требует содержательной проверки.

Фиксированный API проверяется в таком порядке:

1. Самостоятельная компиляция присланного решения отдельно от зависимых тестов.
2. Независимый рефлексивный допуск опубликованных классов, методов,
   параметров, возвращаемых типов и модификаторов; checked-исключения —
   в пределах объявленного договора. Диагностическая загрузка не инициализирует класс.
3. Компиляция зависимых unit-тестов после успешного допуска.
4. Предметная проверка поведения обычными Java/JUnit-тестами.

`@BeforeAll` и `@Order` не обеспечивают этот порядок компиляции.
Провал обязательного допуска останавливает предметные тесты этой попытки.
Он проверяет только объявленный API; успешные служебные ячейки скрыты только
в показе и остаются в полном отчёте. Для обобщений положительные и отрицательные
типизированные клиенты проверяются отдельными компиляционными контекстами:
отрицательная проба должна изолировать ожидаемую причину. Рефлексия стёртых
типов её не заменяет. Предметная задача, проверяющая ожидаемую ошибку компиляции,
отличается от предварительного отказа компиляции студенческого решения.

Требуемая техника, свойства исходника и рассуждения проверяются по коду
или вручную там, где исполнение их не устанавливает. Правильный stdout
не доказывает использование и сохранность массива в `reverse-array`:
это отдельные ручные 20%, без нового отчёта студента. Данные случаев
отделяются от общей инфраструктуры; общие helpers не получают алгоритм
ожидаемого ответа каждой задачи, PL-пути или второй тестовый DSL.

**Target-проверка:** все объявленные корректные эталоны и альтернативы проходят
полный предметный набор; стартер соответствует своему явно объявленному
ожиданию, обычно компилируется, но ещё не решает задачу. Отрицательные
контроли обнаруживаются предусмотренной проверкой по предметной причине;
случайный compile/infra-сбой не заменяет отрицательный результат.
Локальный JUnit, PL-grader и ручные критерии дают отдельные результаты.

## Баллы и обратная связь

Обычное смешанное оценивание — 80% автоматической и 20% ручной части.
Каждый самостоятельный проверяемый случай равновесен, включая отдельные
параметризованные и динамические случаи. Контейнеры, demo и API-допуск
не увеличивают предметный знаменатель. Доля `passed / total` применяется
только к завершённому достоверному полному оценочному набору; 8/10 дают
64% общего максимума до ручной части. Равные обязательные слоты,
лучший результат и остальные незаменённые правила сохраняются по плану.

Достоверная самостоятельная некомпиляция или провал обязательного API
дают ноль текущей попытки с диагностикой, без выдуманных провалов
неисполненных тестов. Инфраструктурный отказ, неполный или недостоверный
отчёт означают неустановленный результат, а не студенческий ноль.
Предыдущий лучший результат и имеющиеся ручные результаты сохраняются.

Feedback различает компиляцию, API, предметный провал, исключение/таймаут
и ошибку проверки. Он показывает файл/строку/причину либо конкретную
объявленную сигнатуру; для предметного случая — русское имя,
проверяемое свойство и существенные expected/actual по применимости.
Для простых задач основное сообщение кратко; технические детали доступны
отдельно. Потеря observation не выдаётся за доказанное неисполнение теста.
Полный автоматический успех отображается отдельно от ожидающей ручной части.

**Target-проверка:** discovery и полный отчёт, parameterized/dynamic outcomes,
пустой/skip-набор, compiler/API-отказы, timeout, worker crash и усечённый отчёт;
дробная оценка и сохранение best в реальном PL, повторно открытый feedback.
Trusted build, submission и отчёт изолируются так, чтобы старые class/report
или присланные build scripts не подменяли исход текущего запуска.

## System Practice и сохранность результатов

Upload и native PL Workspace входят в один выпуск; маршрут и достаточный
состав состояния определяются задачей. Собственная ОС остаётся полноправным
путём. Конечное состояние, обязательные действия и внешний обмен различаются:
архив или bundle сами по себе не доказывают действие либо доступ к аккаунту.
Для `local-history` один архив содержит самодостаточный Git bundle и уже
предусмотренные материалы; bundle не заменяет незакоммиченные index/worktree
или наблюдение остановки на конфликте. Дополнительный отчёт не вводится.

**Target-проверка:** Workspace start/save/close/resume/repeated submit,
согласованный снимок и общий grader; пустые каталоги и `.git`/HEAD/index/worktree
там, где они нужны; upload и Workspace дают одинаковые предметные факты
для одинакового договора. Сбой транспорта или среды не подменяет ошибку решения.

Перенос сохраняет признанный прежний полный автоматический зачёт без новой
ручной части, именно успешный код и нужную старую выдачу при однозначном
соответствии. Частичный прогресс можно сбросить без удаления прежних файлов
и истории; потеря при редких неоднозначных split/merge ограничена решением 58.
Идентичность студентов, частные вложения и согласованность PL/Gateway/Moodle
проверяются по [регламенту](release-execution-regulation-20261103.md).

## Итоговая выдача и границы приёмки

Условие, стартер, README, подсказки, локальная проверка, grader и экспорт
сверяются вместе: допуски, порядок, кратность, состояние после отказа и файлы
следуют договору задачи. Повторяющийся дефект исправляется у владельца
генератора или общего расширения с проверкой потребителей. Расширения
устанавливаются целыми согласованными пакетами, а не ручными изменениями
vendored-копий. Источники, установленные пакеты, server tools, OCI и выходы
выпуска связываются точным снимком; старый PASS или локальный commit
не доказывает новую опубликованную композицию.

**Target-проверка:** точный активный состав обоих курсов и установленные
producer→consumer; сборка итогового снимка, реальные ссылки/скачивания,
HTML и студенческий путь; внешний вход, портал и Moodle/Gateway.
Изменённый фрагмент проверяется в полученной выдаче, а не только в исходнике.
При содержательных изменениях проверяются затронутые смысловые переходы,
гипертекстовые входы и видимый рассказ. Глубокая переработка лекций/теории
имеет собственную последующую проверку качества по решению 67.

Перед переключением обязательны сверка, резервирование и проверка
восстановления. Rehearsal проверяет повтор переноса, новую попытку,
переназначение, доступ разных студентов и согласованность потребителей;
откат сохраняет новые ответы после переключения. Неизвестный исход
операции сначала устанавливают, затем решают, нужен ли повтор.
Финальная приёмка содержит точный снимок, состав, зависимости,
реально выполненные проверки и ограничения. Общий PASS распространяется
только на подтверждённый объём; отсутствие доступа или непрочитанный
результат не превращаются в успешную приёмку.
