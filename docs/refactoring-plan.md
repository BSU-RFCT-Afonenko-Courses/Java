## Уже принятые решения и сохраняемые требования

<a id="decision-1"></a>

1. Сохраняются каталоги учебных форм, близкие структуре итогового сайта, и понятные пути правки.
   Теория, цельная лекция, справка, подготовка и задачи имеют разные назначения; тематическая связь не требует их физического объединения.
<a id="decision-2"></a>

2. Полные условия читаются на странице темы. Канонический текст равноправно пишется непосредственно на странице или подключается через include.
   Отдельные страницы каждой задачи не создаются. Отдельный фрагмент не обязателен; имена `task.yml` и каталога `exercises` пока не выбраны.
<a id="decision-3"></a>

3. Название группы открывает её введение штатными средствами Quarto; тот же принцип применим к подходящим вводным других групп.
<a id="decision-4"></a>

4. `j25` убирается из активных смысловых идентификаторов, меток, категорий, стилей и целей ссылок.
   Версия JDK в командах и реальных технических требованиях имеет другое назначение и не удаляется механически.
<a id="decision-5"></a>

5. Переименования `exr/sec` допускаются и требуют мягкого перехода: ограниченной карты совместимости либо другого проверенного способа.
   Старый запрет псевдонимов, перенаправлений и миграций в затронутой области заменён этим решением.
<a id="decision-6"></a>

6. На портале нужна одна согласованная текущая редакция Java.
   Каждая задача с объективно полностью успешной прежней автоматической проверкой переносится независимо от завершённости всей работы.
<a id="decision-7"></a>

7. При переносе текущая задача засчитывается целиком; ручная часть не требуется.
   Сохраняются прежняя оценка и именно решение успешной попытки, даже если код не соответствует новой версии.
   Исторический факт отсутствия ручной проверки не превращается в утверждение о проведённой рецензии или успехе новых тестов.
<a id="decision-8"></a>

8. Старый код и старая выдача прикрепляются к новой задаче как частные вложения/свидетельства; новый редактор заполнять ими необязательно.
   По сообщению пользователя, решения в основном однофайловые и одна задача двухфайловая.
   Состав старой выдачи уточняется по фактической базе; его нельзя заранее свести только к обратной связи.
<a id="decision-9"></a>

9. Частичный автоматический прогресс можно начать заново; прежние сохранённые файлы и история не удаляются.
   Стратегия «всем нынешним студентам старый живой курс до конца» не принята.
<a id="decision-10"></a>

10. Статус переноса и полный зачёт должны согласованно отображаться в самом PL, механизме завершения работ Gateway и Moodle.
    Первый кандидат — штатное административное начисление с объяснением, вложениями и проверяемым отчётом соответствий.
    Постоянный отдельный реестр или сервис зачётов либо версионный проверяющий модуль не является обязательным решением.
<a id="decision-11"></a>

11. Для обычных новых сдач сохраняются согласованные правила: равные обязательные слоты, 100 за лабораторную, смешанное оценивание 70/30 (историческое соотношение; [заменено на 80/20 пунктом 36](#decision-36)),
    добровольные отдельно без обязательного веса, выбор без двойного начисления, неограниченные попытки до закрытия и лучший результат.
    Освобождение от ручной части при переносе — отдельное принятое исключение, а не отмена обычной политики.
<a id="decision-12"></a>

12. Учебный API не сужается ради проверяющей обвязки; критерии понятны из условия.
    Уточнение [пункта 36](#decision-36): явная ссылка из условия делает выверенный базовый API канонического стартера частью обязательного контракта; это выбранный путь, а не требование заново согласовывать сам принцип для каждой сигнатуры.
    Состав студенческой и полной выдачи выбирается отдельно от доступности общего Git; исходники и чужие деревья сохраняются.
    Простые Java-задачи используют JDK/консоль; сложные — установленный Gradle без Wrapper.

Большой ZIP не обязывает сдавать ZIP. Студент сам выбирает условие/код, IDE-проект или необязательную самопроверку из одного канона; личное использование IDE и запуск demo не являются условием зачёта, учебные требования и критерии одни. Нынешний Gradle/JAR-кейс GradeApp не переключает автоматически все grader-профили; код JavaProcess и полезные CLI-утилиты не объявляются лишними.

Новые версии, build scripts и схемы не утверждены; стоимость нового пути не измерена, рендер страницы курса не обязан запускать Gradle. Прежний выбор bundled JUnit JAR против ручной установки JUnit не остаётся открытым авторским выбором: целевой путь зависимостей — Gradle.

35. 29 октября пользователь выбрал ранний штатный Quarto TS JSON-filter как основной транспорт предметной модели. Lua остаётся только для необходимой native технической адаптации и позднего сбора наблюдений; собственный facts/decisions-мост не является выбранным путём по умолчанию. Quarto сохраняет reader, наследование metadata, crossref и рендер сайта.
    Целевая модель и исполняемые контракты находятся в TypeScript: один исполняемый канон формы, нормализации/defaults и runtime-валидации у каждого владельца. TS-типы выводятся/генерируются из него; если нужен отдельный интерфейс, его согласованность проверяется автоматически, без второго вручную поддерживаемого описания той же формы. Это не замена проверок одними static interfaces/type assertions и не гигантский общий модуль: контракты Core/PL/Cloud/QRC/Publisher и других владельцев остаются у них, активные части соединяются через публичные API.
    CUE исключается из целевого решения во всех рассмотренных расширениях, включая dev/reference-схемы. Будущая миграция охватывает CUE-проверки/вызовы, зависимость от инструмента и CI-настройки, тестовые схемы и производные CUE-выходы словаря; нынешняя реализация и исторические свидетельства не переписываются как уже удалённые. CUE не является целевым постоянным fallback или обязательной двойной валидацией.
    При переносе сохраняются прежние инварианты, accepted/rejected входы, нормализованные выходы (включая различие vet/export), диагностика и причины отказов, композиция адаптеров и public/full гарантии. Нынешние CUE-схемы служат текущей реализацией и эталоном эквивалентности до переноса, не вторым целевым каноном.
    Принято архитектурное направление, не конкретная TS runtime-библиотека, сигнатуры/ключи, модульная раскладка, все детали примеров или разрешение продуктовой миграции. Независимая рецензия дизайна и это прямое пользовательское решение имеют разные статусы; прежние 34 решения сохраняются.

51. <a id="decision-51"></a>29 октября 2026 года пользователь уточнил пункты 36 и 50: носитель обязательного контракта выбирается по учебной цели и компактности описания. Если задача требует создать класс, метод и т. п., его сигнатуру или краткий контракт можно пояснить текстом в QMD, оставляя самостоятельную реализацию студенту; стартер-заглушка не обязателен. При комплексной обработке, когда текстовое описание классов, методов, файлов и сигнатур становится чрезмерным, контракт задаёт конкретный стартовый проект, а QMD ссылается на него без огромного повтора.
    Технические сведения JDK/сборки остаются в README. Это уточнение прежнего общего предпочтения ссылки на стартер, не обязательный стартер для всех задач и не запрет компактных текстовых сигнатур. Носитель не меняет единства обязательного контракта и доверенной проверки. Конкретный API и объём готового Book/Car, включая предложение обязательного тонкого стартера для них, не приняты; новых требований по умолчанию не добавляется. Выбор минимального Main для reverse-array и раздельной автоматической/ручной проверки пункта 50 сохраняется.

52. <a id="decision-52"></a>29 октября 2026 года пользователь выбрал во всех задачах с автопроверкой начисление автоматических баллов по доле пройденных оценочных тестов с равным весом каждого: `passed / total`. Поддержка дробного результата подтверждена по закреплённым экспортёру/Platform и контракту внешнего проверяющего PrairieLearn. В будущем рефакторинге это заменяет нынешний `all-pass`, а не вводит отдельно выбранные веса учебных групп.
    В смешанном оценивании эта доля применяется к автоматическим 80% максимума задачи, ручные 20% учитываются отдельно; например, 8 из 10 тестов дают 0.8 автоматического результата, то есть 64% общего максимума до ручной части. Для полностью ручной задачи правило не создаёт автотестов или фиктивной частичной автоматической оценки. Считается полный оценочный набор, не малый необязательный demo. При равных весах добавление тестов меняет относительный вес покрываемых областей — это следствие выбранного правила.
    Параметризованные/динамические случаи, обнаружение тестов, пропуски и прерывания, ошибки инфраструктуры, компиляции и обязательного API требуют явного согласования/проверки исполнения; конкретное поведение этих границ здесь не выбрано. Сбой инфраструктуры сохраняет смысл пункта 37, а не становится предметной ошибкой автоматически. Живой UI/сервер не проверены; общий план и реализация пока не утверждены, конфигурация курса не переключена.

53. <a id="decision-53"></a>29 октября 2026 года пользователь уточнил пункт 52: результат проверки принимается как завершённый достоверный набор исходов, по которому считается `passed / total`. Обычные непройденные тесты — штатные достоверные исходы; частичный балл пункта 52 сохраняется. Полная ошибка исполнителя, невалидный или неполный отчёт не выдаются за частично успешную оценку; зачёта по обрывкам и отдельного пользовательского сценария начисления баллов из прерванного запуска нет.
    Полная ошибка проверки не равна нулю баллов студенту: результат не установлен, прежний лучший результат сохраняется, инфраструктура не подменяет ошибочный ответ по пункту 37. Подобные отказы должны выявляться при разработке и отрицательной квалификации по пунктам 49 и 41, а не оставаться выбором автора или студента. Это требование к надёжности, не доказанное отсутствие любых runtime-сбоев.
    Обработка таймаута отдельного теста и другие технические границы требуют квалификации достоверного исполнения; самостоятельная политика баллов для такого случая этим не принята. Прежние источники и реализации сохраняют исторические факты; новый код или запуск проверок этим решением не разрешены.

54. <a id="decision-54"></a>29 октября 2026 года пользователь выбрал проектировать целевую архитектуру заново, без обязательств обратной совместимости со старыми API, схемами, форматами Body/pointer и проверяющей обвязкой. Нужные поддерживаемые экспортёры и расширения переводятся на новые договоры; постоянные legacy-адаптеры и двойной канон ради старых потребителей не являются целевым решением. Новый дизайн не привязывается к случайным механизмам нынешнего кода.
    Сохраняются выбранные native Quarto/Pandoc, строгая модель и исполняемые контракты TypeScript без CUE, штатный рендер сайта Quarto и переиспользование готовых стандартных средств вместо собственных аналогов. Нужные проверенные гарантии и отрицательные проверки сохраняются при замене по пунктам 49/41; отказ от старого API не отменяет их смысла.
    Разовый перенос прежних студенческих оценок, кода, выдачи и нужных ссылок по принятым решениям сохраняется как сохранность данных, а не поддержка старого runtime API. Это полномочие заново спроектировать целевую структуру, не автоматический запуск тотального переписывания. Репозитории, ветки, история и данные не удаляются; продукт, CI и сервер сейчас не меняются. Прежние пункты сохраняют историю и читаются с этим последующим уточнением.

55. <a id="decision-55"></a>29 октября 2026 года пользователь принял диагностическое предупреждение `WARNING`, если объявленный в метаданных `project` не соответствует ожидаемой связи с ID упражнения `#exr-…`. Это предупреждение о согласованности именования, не `ERROR` и не автоматическое исправление, перенос каталога или переименование. Если `project` не объявлен, вымышленный путь не подставляется. Структурные конфликты/несовместимые требования пункта 47 остаются ошибками.
    Последующим прямым уточнением пользователь потребовал сохранять имя задачи и, возможно, имя предметной темы, которые могут быть составными. Разрезание всех дефисов на каталоги не является выбранным правилом: `exr-arrays-reverse-array` не требует пути `/projects/arrays/reverse/array`. Общее правило для ID блоков и файловой структуры ещё выбирается; [исследование именования](research/target-design-20261029/naming.md) различает прежнюю норму, фактические примеры и новые варианты.
    Сообщение должно показывать известный источник/строку, ID, фактический `project` и ожидаемое имя по согласованному правилу. Виртуальная база `/projects/` не выдаётся за абсолютный путь файловой системы; недоказанная строка не придумывается. Пока правило не согласовано, нынешние примеры не объявляются несоответствиями из-за разрезания составных имён. Коды предупреждений, параметры подавления и реализация не утверждены; продуктовая реализация этим решением не запускается.

56. <a id="decision-56"></a>29 октября 2026 года пользователь выбрал вариант A: продолжить прежнее правило содержательных имён. Для уже известного эффективного `project` вида `/projects/<theme>/<task>` ожидаемый ID — `exr-<theme>-<task>`: убрать виртуальную базу `/projects/` и заменить `/` на `-` только в этой прямой проекции. Составные имена темы и задачи сохраняются целиком; путь из строки ID не восстанавливается. Например, `/projects/arrays/reverse-array` соответствует `exr-arrays-reverse-array`.
    Несовпадение вызывает WARNING по пункту 55 без автоматического исправления/переименования; без project путь не выдумывается. Дубли опубликованных ID и структурные конфликты остаются ERROR. Новые разделители варианта B и независимые имена варианта C не выбраны; история уточнения в пункте 55 сохраняется, открытый там выбор разрешён этим решением.
    Принято и общее правило: опубликованная цель получает штатный тип и содержательный суффикс; смысловые QMD/каталоги не получают служебные версии и номера выпуска. Полный путь в `sec/fig` кодировать не обязательно. `course-role`, идентичность появления/назначения/слота, UUID и принадлежность решения не вычисляются разрезанием ID; их задают соответствующие свойства и структурные связи. Штатные технические имена и имена Java-файлов сохраняют своё назначение.
    Точные поля/API, коды и подавление предупреждений, реализация и весь остальной целевой дизайн этим выбором не утверждены. Разовая карта переименований и сохранность студенческих данных остаются обязательными; продуктовая реализация не запускается.
