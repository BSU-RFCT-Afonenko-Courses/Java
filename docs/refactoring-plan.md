<a id="decision-9"></a>

9. Частичный автоматический прогресс можно начать заново; прежние сохранённые файлы и история не удаляются.

<a id="decision-10"></a>

    Постоянный отдельный реестр или сервис зачётов либо версионный проверяющий модуль не является обязательным решением.
<a id="decision-11"></a>

11. Для обычных новых сдач сохраняются согласованные правила: равные обязательные слоты, 100 за лабораторную, смешанное оценивание 70/30 (историческое соотношение; [заменено на 80/20 пунктом 36](#decision-36)),

    Принято только требование будущей проработки; архитектурный проект, инструменты, конкретные удаления и реализация не утверждены. Нужны обоснованный выбор сохранить/переиспользовать/заменить/объединить/удалить и поэтапные перспективы рефакторинга; подробности — в разделе 5.
    По последнему уточнению это часть единой программы курса и расширений вместе с результатами исходного исследования и измерений через `course-performance`; отдельная автономная линия не создаётся. Общая связь оснований, целей, кандидатов изменения и приёмки — в разделе 11.
<a id="decision-31"></a>

31. Демонстрационные тесты — необязательные подсказки для строгой самопроверки, когда собственное решение уже начинает оформляться; изучать тесты сразу при чтении условия не требуется, момент обращения выбирает студент.
    Основная доставка явно выбранных demo — файлами из канона: в стартере/студенческом ZIP GitHub Pages, в PL отдельными файлами либо архивом по задаче. Полный JUnit-файл по умолчанию не показывается inline; фрагмент со ссылкой допустим, но ни фрагмент, ни развёрнутое описание каждого теста не обязательны. В условии достаточно короткого указателя к самопроверке.
    Предпочтение «возможно текстовое описание со ссылкой» не утверждает новый обязательный слой прозы, поля, карточки/DSL или pipeline извлечения исходника. Обычный Java/JUnit остаётся каноном; файлы получаются без ручной копии кода.
    Это уточнение пунктов 18/27 не открывает автоматически весь grader/авторский набор, не вводит ограничение Git или доступ после заданного числа попыток. Точные составы, зависимости и самостоятельность выбранной выдачи ещё обсуждаются; её нынешняя готовность не доказана.
    Упрощение относится к показу/получению demo до отправки решения, а не к отмене содержательной обратной связи после проверки. Удаление или замена нынешнего publicCases/observation/report adapter не выбраны; файловая доставка не делает эту обвязку автоматически лишней.
    Для дальнейшей проработки общий принцип: один канонический студенческий стартер конкретной задачи используется на сайте и в PL как комплект помощи разной глубины; это не единый шаблон всего банка и не преподавательский full/IDE-комплект с решениями. Показ базового файла остаётся простым; полный стартер может предлагаться необязательным скачиванием.
    Состав скачиваемого комплекта не определяет состав сдачи: где достаточно одного файла с кодом, приём остаётся однофайловым; для сложных задач отдельные файлы/архив выбираются по задаче. Большой ZIP не обязывает сдавать ZIP. Студент сам выбирает условие/код, IDE-проект или необязательную самопроверку из одного канона; личное использование IDE и запуск demo не являются условием зачёта, учебные требования и критерии одни. Обязательные ресурсы и части комплекта, прямо требуемые условием, и проверки при оценивании сохраняются.
    Отображение путей скачанного проекта (например, `src`) на имя отправляемого файла и вход grader требует отдельной точной проверки; новая нормализация/состав grading files не считаются уже реализованными.
<a id="decision-32"></a>

32. Целевое обобщение необязательной самопроверки — обычные Java/JUnit и общие библиотеки в готовом Gradle-проекте: после первоначальной настройки запуск одной командой из README (`gradle test`) или через IDE, вместо универсальной самописной Java-системы проверок.
    Используется установленный Gradle без Wrapper. Это уточняет пункты 12/31: базовый путь написать/сдать один `Main.java` не требует Gradle; IDE и самостоятельный запуск тестов остаются необязательными. Первоначальная настройка включает JDK, Gradle и разрешение зависимостей через сеть/cache; полный offline на чистой машине не обещан.
    Внешними build-зависимостями и версиями управляют стандартные механизмы Gradle; именованные компоненты/файлы курса относятся к другому уровню и не создают второй реестр версий в metadata. Общие helper/build logic должны быть доступны в самостоятельной выдаче как включённые исходники/локальные проекты либо обоснованная доступная зависимость, без битой ссылки на соседний канон; точный модульный вариант ещё не выбран.
    PL повторно использует канонические JUnit-тесты/helper; исполнение обычным адаптером или Gradle, scoring, API-precheck, feedback и observations требуют отдельной технической приёмки. Нынешний Gradle/JAR-кейс GradeApp не переключает автоматически все grader-профили; код JavaProcess и полезные CLI-утилиты не объявляются лишними.
    Нынешний JDK-only selfcheck — факт прежнего состава, а не универсальная целевая тестовая система. Новые версии, build scripts и схемы не утверждены; стоимость нового пути не измерена, рендер страницы курса не обязан запускать Gradle. Прежний выбор bundled JUnit JAR против ручной установки JUnit не остаётся открытым авторским выбором: целевой путь зависимостей — Gradle.
<a id="decision-33"></a>

33. Пользователь одобрил картину одного канона по типам данных: QMD — полное условие; `_metadata.yml` — свойства курса, выбор компонентов/наборов/выдачи и объявленное замыкание состава; настоящий Gradle-код — внешние зависимости/scopes/версии/tasks; общие helper хранятся один раз; inventory/receipt/provenance — производные результаты.
    Для типовых задач настоящие общие Gradle build/settings материализуются существующим producer в готовый самостоятельный проект; обязательный канонический `build.gradle` каждой задачи не нужен. Особые проекты сохраняют свой настоящий native build, стандартное переиспользование применяется при обоснованной необходимости.
    Gradle-файлы не генерируются из YAML; второй внешний граф зависимостей, собственный Gradle parser/dependency manager не создаются. Граф выбранных компонентов/файлов курса и их объявленного замыкания сохраняется; Gradle не выводит учебный состав по Java imports.
    Принято направление, не точные ключи/пути/имена тестов, версии библиотек или модульная структура; три прежних YAML-блока reverse-array остаются историческим эскизом. Пункты 31/32 и независимый от ZIP простой контракт ответа сохраняются.
    Native input/origins/базы путей кодовой папки требуют технического исследования; одобрение не объявляет Quarto-мост реализованным. Нынешний общий build ещё не готовый JUnit-шаблон; исполнение PL, API/scoring/feedback/observations, стоимость и готовность самостоятельной выдачи остаются предметом технической приёмки, без разрешения реализации.

40. <a id="decision-40"></a>29 октября 2026 года пользователь принял основу чистки тестовых систем и примеров: у каждой группы тестов назвать защищаемое поведение и ошибку, которую она должна обнаруживать. 41. <a id="decision-41"></a>29 октября 2026 года пользователь принял трёхуровневый цикл проверки. Локальная правка: относящиеся к ней типы/lint, тесты и нужный фрагмент выдачи.     Точные маркеры/API, парсер и преобразователь, штатный мост Quarto, ссылки/anchors, ресурсы, происхождение значений и версии Gradle ещё технически открыты; готовность этого пути исполнением не доказана. Продуктовая реализация этим решением не запускается.

49. <a id="decision-49"></a>29 октября 2026 года пользователь принял обязательный контроль активных кодовых задач перед выпуском. Все объявленные корректные эталоны и альтернативные решения компилируются и проходят полный предметный автоматический набор. Стартер проверяется по объявленному ожиданию: обычно компилируется, но ещё не решает задачу; особые случаи ожидаемой ошибки компиляции задаются явно.
    Отрицательный контроль должен обнаруживаться предусмотренной проверкой и по предусмотренной причине; случайная ошибка компиляции или инфраструктурный сбой не заменяют предметный отказ. Набор отрицательных случаев подбирается по учебным требованиям. Развиваются существующие `references`, `verification-expectations` и маршрут проверок, а не новый runner или DSL; локальный JUnit, PL-grader и ручная проверка имеют отдельные результаты.
    Это обязательная приёмка перед выпуском, не запуск сейчас. Точные ключи/CLI и Gradle-проверка ожидаемых отказов ещё не утверждены и не объявлены готовыми. Для reverse-array выбор между `Main` с ручным чтением кода и обязательным методом стартера ради проверки сохранности массива ещё не сделан; один stdout сохранность массива не доказывает.

50. <a id="decision-50"></a>29 октября 2026 года пользователь выбрал для маленькой reverse-array минимальный `Main` без нового обязательного метода `printReverse`. Автоматический набор проверяет поведение вывода на предусмотренных случаях; использование массива и его сохранность проверяются по сданному коду в ручных 20%, без нового письменного отчёта или показа. Требование не изменять массив сохраняется; один stdout не доказывает его выполнение.
    Для более крупных задач целесообразно заранее задавать явный базовый контракт через канонический стартер, на который ссылается условие по пункту 36, оставляя внутреннюю реализацию студенту в пределах учебной цели. Это не перевод всех маленьких задач на обязательный метод/API. Конкретные сигнатуры Book/Car и объём готового кода ещё не приняты.
    Приёмка пункта 49 сохраняет отдельные результаты автоматической и ручной проверки: отрицательный вариант с правильным stdout, но изменением массива может пройти CLI-тесты и должен обнаруживаться ручной частью. От автотестов не требуется недоступное им свидетельство; предметная причина отказа указывается в соответствующей части проверки. Продуктовые условия, стартеры и тесты этим решением не изменены.

51. <a id="decision-51"></a>29 октября 2026 года пользователь уточнил пункты 36 и 50: носитель обязательного контракта выбирается по учебной цели и компактности описания. 52. <a id="decision-52"></a>29 октября 2026 года пользователь выбрал во всех задачах с автопроверкой начисление автоматических баллов по доле пройденных оценочных тестов с равным весом каждого: `passed / total`. Поддержка дробного результата подтверждена по закреплённым экспортёру/Platform и контракту внешнего проверяющего PrairieLearn. В будущем рефакторинге это заменяет нынешний `all-pass`, а не вводит отдельно выбранные веса учебных групп.
    В смешанном оценивании эта доля применяется к автоматическим 80% максимума задачи, ручные 20% учитываются отдельно; например, 8 из 10 тестов дают 0.8 автоматического результата, то есть 64% общего максимума до ручной части. Для полностью ручной задачи правило не создаёт автотестов или фиктивной частичной автоматической оценки. Считается полный оценочный набор, не малый необязательный demo. При равных весах добавление тестов меняет относительный вес покрываемых областей — это следствие выбранного правила.
    Параметризованные/динамические случаи, обнаружение тестов, пропуски и прерывания, ошибки инфраструктуры, компиляции и обязательного API требуют явного согласования/проверки исполнения; конкретное поведение этих границ здесь не выбрано. Сбой инфраструктуры сохраняет смысл пункта 37, а не становится предметной ошибкой автоматически. Живой UI/сервер не проверены; общий план и реализация пока не утверждены, конфигурация курса не переключена.

53. <a id="decision-53"></a>29 октября 2026 года пользователь уточнил пункт 52: результат проверки принимается как завершённый достоверный набор исходов, по которому считается `passed / total`. Обычные непройденные тесты — штатные достоверные исходы; частичный балл пункта 52 сохраняется. Полная ошибка исполнителя, невалидный или неполный отчёт не выдаются за частично успешную оценку; зачёта по обрывкам и отдельного пользовательского сценария начисления баллов из прерванного запуска нет.
    Полная ошибка проверки не равна нулю баллов студенту: результат не установлен, прежний лучший результат сохраняется, инфраструктура не подменяет ошибочный ответ по пункту 37. Подобные отказы должны выявляться при разработке и отрицательной квалификации по пунктам 49 и 41, а не оставаться выбором автора или студента. Это требование к надёжности, не доказанное отсутствие любых runtime-сбоев.
    Обработка таймаута отдельного теста и другие технические границы требуют квалификации достоверного исполнения; самостоятельная политика баллов для такого случая этим не принята. Прежние источники и реализации сохраняют исторические факты; новый код или запуск проверок этим решением не разрешены.

54. <a id="decision-54"></a>29 октября 2026 года пользователь выбрал проектировать целевую архитектуру заново, без обязательств обратной совместимости со старыми API, схемами, форматами Body/pointer и проверяющей обвязкой. Новый дизайн не привязывается к случайным механизмам нынешнего кода.

Это полномочие заново спроектировать целевую структуру, не автоматический запуск тотального переписывания. Репозитории, ветки, история и данные не удаляются; продукт, CI и сервер сейчас не меняются. 55. <a id="decision-55"></a>29 октября 2026 года пользователь принял диагностическое предупреждение `WARNING`, если объявленный в метаданных `project` не соответствует ожидаемой связи с ID упражнения `#exr-…`. Структурные конфликты/несовместимые требования пункта 47 остаются ошибками.

Общее правило для ID блоков и файловой структуры ещё выбирается; [исследование именования](research/target-design-20261029/naming.md) различает прежнюю норму, фактические примеры и новые варианты.

Пока правило не согласовано, нынешние примеры не объявляются несоответствиями из-за разрезания составных имён. Коды предупреждений, параметры подавления и реализация не утверждены; продуктовая реализация этим решением не запускается.

56. <a id="decision-56"></a>29 октября 2026 года пользователь выбрал вариант A: продолжить прежнее правило содержательных имён. Штатные технические имена и имена Java-файлов сохраняют своё назначение.
    Точные поля/API, коды и подавление предупреждений, реализация и весь остальной целевой дизайн этим выбором не утверждены. Разовая карта переименований и сохранность студенческих данных остаются обязательными; продуктовая реализация не запускается.

Но таких задач на курс должно быть совсем мало. В основном старайся сформулировать условие и стартер пригодным для автотестов». Основной путь — ясное каноническое условие и минимальный обязательный интерфейс в каноническом стартере, достаточный для настоящих автотестов при сохранении учебной цели и свободы алгоритма за пределами этого договора. Каждое ручное исключение учитывается и обосновывается отдельно; отсутствие готового grader или инфраструктурный отказ не становятся основанием ручного зачёта либо фиктивного автоматического PASS. Для задач с реальными автотестами сохраняется 80/20; прежде явно ручные задачи не переводятся на новое оценивание этим решением автоматически. Прежние признанные зачёты и законные старые решения не переоцениваются из-за нового обязательного API. Каждая содержательная дельта проходит учебного автора и другого содержательного рецензента по принятой матрице; код стартера, эталонов и тестов пишет технический исполнитель.
