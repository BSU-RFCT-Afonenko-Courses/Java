## Область и исходная база

Объекты работы — Java, System Practice и используемые ими общие расширения.
Java и System Practice сохраняют разные учебные предметы и отдельные публикации и курсы PrairieLearn.
Требование одной актуальной редакции Java для прежней тестовой группы и новых студентов не объединяет две дисциплины.
Cybersecurity и документация-шаблон служат проверкой переносимости решений, без полной переработки этих проектов.
Несвязанные с этими задачами части сервера Platform, другие проекты, новая исполняющая среда IDE и универсальный каркас в область не добавляются.

Исследовательская база Java — `273ce2d63cc245d8c70e00167acb15e4bc63ef64`, состояние [PR27](https://github.com/BSU-RFCT-Afonenko-Courses/Java/pull/27).
System Practice — PR8, состояние `76a87d65bf73605b8d1e2bb0e81e8949e0defa08`; старые локальные деревья его не заменяют.
В Java установлены Core/Presentation/Navigation/PrairieLearn 8.3.0, Publisher 5.1.5, QRC 3.1.0, Download 3.2.1; System Practice — Core/PrairieLearn 8.2.4.
Исполняющая среда Platform 2.4.0, серверные инструменты 2.4.1, исходники, опубликованные файлы выпуска, OCI и Native имеют разные идентичности.
Эти ссылки на версии — база исследования, а не уже выбранный набор новой версии и не свежая инвентаризация сервера.
Происхождение и расхождение линий сохраняет [Выбор исходников](research/extension-architecture-20261027/source-selection.md).

## Уже принятые решения и сохраняемые требования

1. Сохраняются каталоги учебных форм, близкие структуре итогового сайта, и понятные пути правки.
   Теория, цельная лекция, справка, подготовка и задачи имеют разные назначения; тематическая связь не требует их физического объединения.
2. Полные условия читаются на странице темы. Канонический текст равноправно пишется непосредственно на странице или подключается через include.
   Отдельные страницы каждой задачи не создаются. Отдельный фрагмент не обязателен; имена `task.yml` и каталога `exercises` пока не выбраны.
3. Название группы открывает её введение штатными средствами Quarto; тот же принцип применим к подходящим вводным других групп.
4. `j25` убирается из активных смысловых идентификаторов, меток, категорий, стилей и целей ссылок.
   Версия JDK в командах и реальных технических требованиях имеет другое назначение и не удаляется механически.
5. Переименования `exr/sec` допускаются и требуют мягкого перехода: ограниченной карты совместимости либо другого проверенного способа.
   Старый запрет псевдонимов, перенаправлений и миграций в затронутой области заменён этим решением.
6. На портале нужна одна согласованная текущая редакция Java.
   Каждая задача с объективно полностью успешной прежней автоматической проверкой переносится независимо от завершённости всей работы.
7. При переносе текущая задача засчитывается целиком; ручная часть не требуется.
   Сохраняются прежняя оценка и именно решение успешной попытки, даже если код не соответствует новой версии.
   Исторический факт отсутствия ручной проверки не превращается в утверждение о проведённой рецензии или успехе новых тестов.
8. Старый код и старая выдача прикрепляются к новой задаче как частные вложения/свидетельства; новый редактор заполнять ими необязательно.
   По сообщению пользователя, решения в основном однофайловые и одна задача двухфайловая.
   Состав старой выдачи уточняется по фактической базе; его нельзя заранее свести только к обратной связи.
9. Частичный автоматический прогресс можно начать заново; прежние сохранённые файлы и история не удаляются.
   Стратегия «всем нынешним студентам старый живой курс до конца» не принята.
10. Статус переноса и полный зачёт должны согласованно отображаться в самом PL, механизме завершения работ Gateway и Moodle.
    Первый кандидат — штатное административное начисление с объяснением, вложениями и проверяемым отчётом соответствий.
    Постоянный отдельный реестр или сервис зачётов либо версионный проверяющий модуль не является обязательным решением.
11. Для обычных новых сдач сохраняются согласованные правила: равные обязательные слоты, 100 за лабораторную, смешанное оценивание 70/30,
    добровольные отдельно без обязательного веса, выбор без двойного начисления, неограниченные попытки до закрытия и лучший результат.
    Освобождение от ручной части при переносе — отдельное принятое исключение, а не отмена обычной политики.
12. Учебный API не сужается ради проверяющей обвязки; критерии понятны из условия.
    Состав студенческой и полной выдачи выбирается отдельно от доступности общего Git; исходники и чужие деревья сохраняются.
    Простые Java-задачи используют JDK/консоль; сложные — установленный Gradle без Wrapper.
13. Принятые неизменённые лекции 1, 2 и 5 сохраняют статус.
    Новый общий педагогический пилот и повторное утверждение всей методики не требуются; содержательные изменения проверяются адресно.
14. Нужна команда подготовки отдельного самостоятельного IDE-проекта со всеми включениями и транзитивными зависимостями выбранного проекта и его тестов.
    Автоматический обратный перенос IDE-правок в канон сейчас не реализуется; возможный будущий путь рассматривается отдельно в разделе 9.
15. Пользователь предпочитает хранить тесты рядом с проектом. По умолчанию тесты исключены из студенческих ZIP и показа PL;
    исключение — явно помеченные демонстрационные. Точная раскладка и способ такой отметки ещё обсуждаются.
16. Для большинства Java-задач в PL нужно условие, а к нему — пример кода либо стартер ZIP с README внутри;
    приём архива или отдельных файлов выбирается по задаче. Обязательный встроенный редактор или IDE не вводится.
17. В стартер или базовый файл не добавляется `package` без явного требования задания; проверка принимает такое решение.
    Это не отменяет пакеты там, где они действительно требуются учебным договором.
18. На GitHub Pages нужен полноценный ZIP с README и структурой `src`; демонстрационные тесты включаются только по явному выбору.
    Открытые тесты и примеры в PL показываются из канонического источника без ручной копии текста или кода; способ выбора и показа ещё открыт.
    Это не требование полной автоматизации тестовых пояснений; выбранная база и исключение новых карточек зафиксированы в пункте 27.
19. Принят принцип: один типизированный вход в существующие модели и проверки, совместимые короткие атрибуты для простых случаев и YAML для сложных деклараций.
    Одобрен общий вид: native Div с ID `exr`, служебный YAML-блок для нескольких настроек и обычный Markdown условия.
    Имена маркеров/полей, схемы, парсер, приоритеты и конкретная реализация ещё не утверждены; совместимость с native Quarto предстоит доказать.
    Реализованной поддержки этим решением не заявлено.
20. Подготовленные общая инфраструктура тестирования и библиотеки сохраняют один канон; проекты ссылаются на зависимости без исходных копий в каждом проекте.
    Авторские/эталонные решения, включая несколько вариантов, сохраняются в общем Git и не входят в студенческие архивы по умолчанию.
    При сборке IDE нужные зависимости и решения включаются с раздельными контекстами компиляции альтернатив.
21. Выбран вариант А: внутри `tasks` тематические страницы `bank/<theme>.qmd` отделены от `projects/<theme>/<task>/`.
    Тесты располагаются рядом с проектом; точные внутренние каталоги, размещение общих компонентов и выбор demo/full-наборов ещё обсуждаются; база Java/JUnit уже выбрана.
22. Для исходников проектов, тестов, общих библиотек и авторских решений используется общий Git без закрытых частей.
    Прежнее отдельное хранение преподавательских входов остаётся фактом прежней поставки, а не требованием новой структуры.
    Открытый Git не определяет автоматически состав `full`/`student`, ZIP PL или Pages.
    Реальные студенческие ответы и учётные данные — другой предмет; их правила этим решением не меняются.
23. Одобрено разделение учебного QMD, локального описания проекта и общих правил с зависимостями.
    Принят единственный локальный YAML `_metadata.yml`; дополнительный `project.yml` не создаётся. Тесты, данные и авторские решения хранятся отдельными файлами рядом.
    Крупные параметры проверок и PL не раздувают QMD; точные поля и схема ещё не выбраны.
24. По прямому запросу выполнен статический инвентарь авторской поверхности семи установленных расширений, с отдельным legacy-контролем Cloud/Print/Moodle.
    [Результат и реестр](research/yaml-authoring-integration-20261027/README.md) фиксируют наблюдения и варианты, не новую универсальную схему или разрешение реализации.
25. Для повторяемых настроек принят подход штатного наследования Quarto: уровень проекта, каталога и документа вместо явных ссылок на общий файл в каждой задаче.
    Общие определения компонентов доступны по именам; конкретные зависимости выбирают наборы тестов соответствующего проекта.
    Общий технологический профиль не включает библиотеки и адаптеры всех задач.
    Принято разграничение баз путей: общие источники — от места определения, локальное расположение — от выбранного кодового проекта; provenance сохраняется для каждого значения.
    Точные поля, схема и мост к native метаданным кодового проекта ещё не утверждены.
26. README каждого самостоятельного ZIP/IDE-комплекта включает полное условие из канонического QMD без ручного дублирования.
    Способ преобразования, ссылки, ресурсы и оформление ещё требуют технической проверки; сырое копирование QMD в README этим решением не утверждено.

31. Демонстрационные тесты — необязательные подсказки для строгой самопроверки, когда собственное решение уже начинает оформляться; изучать тесты сразу при чтении условия не требуется, момент обращения выбирает студент.
    Основная доставка явно выбранных demo — файлами из канона: в стартере/студенческом ZIP GitHub Pages, в PL отдельными файлами либо архивом по задаче. Полный JUnit-файл по умолчанию не показывается inline; фрагмент со ссылкой допустим, но ни фрагмент, ни развёрнутое описание каждого теста не обязательны. В условии достаточно короткого указателя к самопроверке.
    Предпочтение «возможно текстовое описание со ссылкой» не утверждает новый обязательный слой прозы, поля, карточки/DSL или pipeline извлечения исходника. Обычный Java/JUnit остаётся каноном; файлы получаются без ручной копии кода.
    Это уточнение пунктов 18/27 не открывает автоматически весь grader/авторский набор, не вводит ограничение Git или доступ после заданного числа попыток. Точные составы, зависимости и самостоятельность выбранной выдачи ещё обсуждаются; её нынешняя готовность не доказана.
    Упрощение относится к показу/получению demo до отправки решения, а не к отмене содержательной обратной связи после проверки. Удаление или замена нынешнего publicCases/observation/report adapter не выбраны; файловая доставка не делает эту обвязку автоматически лишней.
    Для дальнейшей проработки общий принцип: один канонический студенческий стартер конкретной задачи используется на сайте и в PL как комплект помощи разной глубины; это не единый шаблон всего банка и не преподавательский full/IDE-комплект с решениями. Показ базового файла остаётся простым; полный стартер может предлагаться необязательным скачиванием.
    Состав скачиваемого комплекта не определяет состав сдачи: где достаточно одного файла с кодом, приём остаётся однофайловым; для сложных задач отдельные файлы/архив выбираются по задаче. Большой ZIP не обязывает сдавать ZIP. Студент сам выбирает условие/код, IDE-проект или необязательную самопроверку из одного канона; личное использование IDE и запуск demo не являются условием зачёта, учебные требования и критерии одни. Обязательные ресурсы и части комплекта, прямо требуемые условием, и проверки при оценивании сохраняются.
    Отображение путей скачанного проекта (например, `src`) на имя отправляемого файла и вход grader требует отдельной точной проверки; новая нормализация/состав grading files не считаются уже реализованными.
32. Целевое обобщение необязательной самопроверки — обычные Java/JUnit и общие библиотеки в готовом Gradle-проекте: после первоначальной настройки запуск одной командой из README (`gradle test`) или через IDE, вместо универсальной самописной Java-системы проверок.
    Используется установленный Gradle без Wrapper. Это уточняет пункты 12/31: базовый путь написать/сдать один `Main.java` не требует Gradle; IDE и самостоятельный запуск тестов остаются необязательными. Первоначальная настройка включает JDK, Gradle и разрешение зависимостей через сеть/cache; полный offline на чистой машине не обещан.
    Внешними build-зависимостями и версиями управляют стандартные механизмы Gradle; именованные компоненты/файлы курса относятся к другому уровню и не создают второй реестр версий в metadata. Общие helper/build logic должны быть доступны в самостоятельной выдаче как включённые исходники/локальные проекты либо обоснованная доступная зависимость, без битой ссылки на соседний канон; точный модульный вариант ещё не выбран.
    PL повторно использует канонические JUnit-тесты/helper; исполнение обычным адаптером или Gradle, scoring, API-precheck, feedback и observations требуют отдельной технической приёмки. Нынешний Gradle/JAR-кейс GradeApp не переключает автоматически все grader-профили; код JavaProcess и полезные CLI-утилиты не объявляются лишними.
    Нынешний JDK-only selfcheck — факт прежнего состава, а не универсальная целевая тестовая система. Новые версии, build scripts и схемы не утверждены; стоимость нового пути не измерена, рендер страницы курса не обязан запускать Gradle. Прежний выбор bundled JUnit JAR против ручной установки JUnit не остаётся открытым авторским выбором: целевой путь зависимостей — Gradle.
33. Пользователь одобрил картину одного канона по типам данных: QMD — полное условие; `_metadata.yml` — свойства курса, выбор компонентов/наборов/выдачи и объявленное замыкание состава; настоящий Gradle-код — внешние зависимости/scopes/версии/tasks; общие helper хранятся один раз; inventory/receipt/provenance — производные результаты.
    Для типовых задач настоящие общие Gradle build/settings материализуются существующим producer в готовый самостоятельный проект; обязательный канонический `build.gradle` каждой задачи не нужен. Особые проекты сохраняют свой настоящий native build, стандартное переиспользование применяется при обоснованной необходимости.
    Gradle-файлы не генерируются из YAML; второй внешний граф зависимостей, собственный Gradle parser/dependency manager не создаются. Граф выбранных компонентов/файлов курса и их объявленного замыкания сохраняется; Gradle не выводит учебный состав по Java imports.
    Принято направление, не точные ключи/пути/имена тестов, версии библиотек или модульная структура; три прежних YAML-блока reverse-array остаются историческим эскизом. Пункты 31/32 и независимый от ZIP простой контракт ответа сохраняются.
    Native input/origins/базы путей кодовой папки требуют технического исследования; одобрение не объявляет Quarto-мост реализованным. Нынешний общий build ещё не готовый JUnit-шаблон; исполнение PL, API/scoring/feedback/observations, стоимость и готовность самостоятельной выдачи остаются предметом технической приёмки, без разрешения реализации.

Следующие разделы уточняют способы достижения этих требований, а не открывают принятые решения заново.
Пользовательский выбор нужен для учебного смысла, обещаний интерфейса и существенных компромиссов.
Вопросы о версиях, объединении метаданных, доступном API, SQL, статусах и стоимости — техническая работа владельцев в рамках соответствующей фазы;
их проверка не перекладывается на пользователя как выбор сигнатур или внутреннего поля. Технические варианты выносятся на обсуждение с последствиями для автора и студента.

## 3 Метаданные YAML общие настройки и зависимости

**Цель.** Автор описывает смысловые решения и исключения; точные файлы, отображения путей и манифесты выводятся там, где выбор однозначен.
**Уже известно.** В Java 1015 отображений общих файлов описывают 251 исходный файл; часть профилей повторяет существующие общие настройки.
Объединение настроек проверок Core объединяет вложенные отображения и заменяет списки; метаданные Quarto объединяют массивы по собственным правилам.
Перенос огромного реестра в отдельный файл уменьшает файл, но сам по себе не уменьшает число ручных решений.
По итогам исследования пользователь принял принцип из пункта 19: единый типизированный вход с совместимыми короткими атрибутами и YAML для сложных деклараций.
Конкретные имена, схемы владельцев, парсер, приоритеты и реализация остаются открытыми; второй модели курса не создаётся.
Сравнение скалярного сокращения и общего входа сохраняется как основание выбора; произвольный setter всех атрибутов не подходит.
Принят принцип native Quarto inheritance из пункта 25; `project.yml` или обычная папка Java сами по себе не являются входным документом Quarto.
Каталожный inspect даёт конфигурацию владельца, а метаданные `bank/arrays.qmd` не подменяют контекст соседнего каталога кода.
Принятое имя локального входа `_metadata.yml` сокращает отдельное подключение YAML; bridge выбранного input и допуск origins требуют проверки.
Принято сохранять provenance каждого значения, а базу пути задавать типом: общие источники (в эскизе `components.*.sources`) — от origin определения,
`starter` и локальные пути тестов/решений/выдачи — от выбранного кодового проекта, даже при наследовании правила.
Это не доказанная возможность native rebasing; мост должен проверить raw/effective и origin, не переинтерпретируя уже перебазированную строку вслепую.

**Открытые вопросы.** Что принадлежит метаданным проекта, каталога, документа и настройкам формата, что — сборщику данных уровня проекта?

### Рефакторинг расширений и очистка репозиториев

Это тема единой программы курса и расширений: новый авторский формат проходит через модели/интерфейсы, библиотеки и материализацию к потребителям и выдаче. Исследование кода/репозиториев, качество, стоимость и совместимость оцениваются в одной цепочке разделов 2–6/9/11–12, а не в автономной линии.
Область — код и репозитории общих расширений целиком под согласуемый формат курса: структура, назначение содержимого, архитектура, конфигурации, тестовая инфраструктура, примеры и документация. Дополнительные исследования и согласования ещё впереди; крупная очистка не разрешена этой записью.
Наработки [чата «Поиск инструментов рефакторинга»](https://chatgpt.com/c/6abe56fc-a488-83eb-ab95-8aadc5fcd99f) от 1 октября 2026 года разделяют реализацию, архитектуру пакета и согласованность Lua↔TS↔CUE/YAML/JSON/Quarto.
В доступных трёх ходах есть рекомендации и постановка аудита, но нет результатов прогонов или приложенных отчётов; прежние версии и рекомендации не подтверждают состояние на 28 октября.
Legacy, общая структура тестовых систем/примеров и обоснование объёма кода в том чате не разобраны: это новая часть текущего поручения, а не уже выполненное исследование.

**Что проработать.**

- Обоснование структуры репозиториев, архитектуры и обязанностей модулей, внешних публичных и внутренних интерфейсов, точных точек входа и ошибок; единый типизированный путь QMD/YAML→нормализация→существующие модели→потребители без второго канона.
- Проверить, где собственные механизмы повторяют существующие инструменты, библиотеки или встроенные возможности; сравнить переиспользование и свой код по поддерживаемости, совместимости и стоимости, без заранее выбранной замены.
- Общие функции, блоки и модули выделять по повторяющейся обязанности и оправданной цене зависимости. Производный словарь, пример и независимая проверка не становятся лишними только из-за похожего текста.
- Строгую типизацию TS и отдельную проверку типов, линтеры и статический анализ самого кода расширений; различать Quarto/Deno, Node и браузерные контексты. Для Lua отдельно учесть типы границ, nil/globals, состояние и порядок фильтров.
- Инвентарь legacy, устаревшего содержимого, конфигураций, примеров и старых тестовых систем: назначение, действующие потребители, замены, причины оставить или удалить; сопоставить разрозненные средства тестирования и примеры по общим целям/категориям, не объявляя все проверки дублирующими.
- Обоснование объёма кода через цепочку назначение→контракт→потребитель→необходимая проверка/свидетельство: где объём нужен, где обязанности повторяются или перемешаны. Одно число строк/функций не доказывает избыточность.
- Устойчивые небольшие этапы рефакторинга, правила разработки и проверки качества перед интеграцией: проверяемые границы, адресная регрессия, обновление документации и совместимый переход вместо единовременного переписывания.

**Инструменты пока кандидаты.** В чате предложены `deno check/lint/fmt --check`, LuaLS, YAML LS/JSON Schema, Serena и dependency-cruiser.
Запуск TS не равен проверке типов; LSP/подсказки редактора не заменяют runtime/schema-проверку; граф imports не описывает весь межъязыковой договор.
Пригодность инструментов, разрешение imports в фактической среде, строгие настройки TS и единый источник схем ещё проверяются; новый сервис, оркестратор или монорепозиторий этим не выбираются.

**Планируемый результат.** Карта структуры/назначений/контрактов/потребителей и целей tests/examples, проверка готовых альтернатив, аргументированный перечень сохранить/переиспользовать/заменить/объединить/удалить, перспективы и этапы рефакторинга, минимальные правила разработки/проверок качества. Это будущий результат исследования и согласования, не принятый проект архитектуры или очистки.
Принятая совместимость старых ID/входов и перенос PL сохраняются; историческое предложение из чата не добавлять слои совместимости их не отменяет.
Нужные legacy-потребители, сохранённые данные и история не удаляются под видом очистки. Сегодня новый широкий аудит, настройка инструментов и изменения исходников не выполняются.
**Опоры.** [Контракты](research/extension-architecture-20261027/contracts.md), [Core export](research/extension-architecture-20261027/owners/core-export.md), [реестр разметки](research/yaml-authoring-integration-20261027/attributes.md), [качество исходников](research/yaml-authoring-integration-20261027/source-quality.md) и [измерения через course-performance](research/extension-architecture-20261027/performance-findings.md); они обосновывают общие кандидаты изменения и проверки раздела 11, а не отдельный завершённый рефакторинг.

Какие формы уже поддерживает PL; где нужны изменения показа или приёма, а не новая IDE? Это техническая проверка после выбора авторского и студенческого вида.

**Планируемый результат.** По каждому активному ID: условие→допустимый стартер/API→демонстрационная и полная проверка→рубрика→вес в работе.

Отдельно проверить допустимое решение без `package` и задачу с действительно обязательным пакетом; пример не становится скрытым ограничением проверки.
Обязательные API и данные доступны в выбранной форме выдачи.

## 9 Общий Git состав выдачи и работа в IDE

**Цель.** Общий редактируемый канон, самостоятельный IDE-комплект и нужные студенту архивы имеют понятные разные составы.
**Уже известно.** В прежней поставке преподавательские входные материалы сохранялись во внешнем `teacher root`; проверка 5379 файлов установила сохранность, не корректность эталонов.
Теперь для исходников проектов, тестов, библиотек и авторских решений выбран общий Git без закрытых частей. Отдельное закрытое хранилище для них не требуется.
Материализация пока однонаправленная; подготовка и точная сверка дерева не обеспечивают обратный перенос IDE-правок.
В Download [DEFAULT_EXCLUDES](../tasks/_extensions/Afonenko-Course-Tools/project-download/domain/config.ts#L7) содержит `**/*.jar`.
Прежний кандидат самостоятельного `full` с JUnit JAR в `lib` не выбран как общий путь: пункт 32 задаёт Gradle-managed зависимости. Исключение JAR остаётся условной проверкой возможной предсобранной/offline binary-выдачи, а не обязательной первой задачей разрешить JUnit JAR в каждом ZIP; второй архиватор и глобальное разрешение JAR не предлагаются.
Нынешняя материализация `student`/`grading` не равна уже готовому новому договору `student`/`full`/IDE.
[Узкое чтение student starter/проекции ответа от 28 октября](research/yaml-authoring-integration-20261027/public-tests.md#стартер-и-проекция-ответа) подтвердило нынешний `src/main/java/Main.java`→`Main.java` mapping и малый JDK-only selfcheck reverse-array; нового basename-правила для них не требуется. Единый student inventory сайта/PL, самостоятельный Gradle/JUnit-комплект с доступными общими библиотеками и полный IDE-состав ещё не доказаны; materialization перечисляет файлы, а не выводит Java import closure. Пункт 31 сохраняется с целевым уточнением пункта 32.
[Исследование открытых тестов](research/yaml-authoring-integration-20261027/public-tests.md) описывает выбранную Java/JUnit-основу и существующий протокол результатов PL как предмет аудита; это не рекомендация новой модели карточек.
Общая инфраструктура тестирования, библиотеки и авторские решения уже подготовлены; их нужно сохранить и использовать с явными зависимостями.
13 ZIP справочника совпали с исходниками. GradeApp инструкции расходятся; Truck API QMD исключается обычным отбором файлов стартера.

**Различаемые представления.** В выбранной раскладке А определяются четыре назначения; доступность Git и состав конкретной выдачи не отождествляются.

| Представление | Что редактируется или получается | Состав |
| --- | --- | --- |
| Отдельно редактируемый канон | `bank/<theme>.qmd` и отдельный `projects/<theme>/<task>/` с тестами и авторскими решениями в общем Git | Общая инфраструктура и библиотеки хранятся один раз, задачи ссылаются на них; inline/include равноправны |
| Полный IDE-комплект автора | Все включения и транзитивные зависимости проекта **и его тестов**, нужные библиотеки и авторские/эталонные решения | Самостоятельный проект; альтернативы с одноимёнными классами имеют раздельные контексты компиляции |
| Студенческая проекция PL | Выбранная для задачи форма из раздела 6; демонстрационные примеры получены из канона | Тесты по умолчанию не входят в показ и ZIP; демонстрационные выбираются явно, при их выдаче нужны все зависимости для обещанного запуска |
| Студенческая проекция GitHub Pages | Полноценный ZIP с README и структурой `src`, при явном выборе — демонстрационные тесты | Общий Git не означает архивирование всех файлов; нужные библиотеки, инструменты и данные выбираются по договору выдачи |

Общие библиотеки и тестовая инфраструктура не копируются в каждый исходный проект: нужные файлы собираются вместе при подготовке IDE.
Авторские решения сохраняются в общем Git, но не входят в студенческие архивы по умолчанию.
Единственный локальный вход `_metadata.yml` принят; внутренние пути и способ демонстрационной отметки ещё обсуждаются.
Дополнительный `project.yml` не вводится; отдельный файл сценариев или фрагмент условия не предписан.
Отдельные страницы задач не создаются.
Полное условие из канонического QMD в README самостоятельного комплекта принято в пункте 26.

**Открытые вопросы.** Каковы общие правила архивирования `full` и `student` и какие исключения действительно нужны PL и Pages?
Как сохранить его ссылки, ресурсы и оформление при преобразовании без ручной копии и без обещания работоспособности сырого QMD в Markdown?
Какие исходники, тесты, авторские решения, инструменты, данные и транзитивные зависимости включает каждый состав?
Когда элементы общей тестовой библиотеки нужны студенту для самостоятельных обычных unit tests, а когда они относятся только к PL-адаптеру?
Можно ли обобщить отбор и архивирование через существующий механизм, сохранив различия полных комплектов, стартера и демонстрационных тестов?
Где полезны fixtures/MethodSource поверх обычного JUnit, как доставить выбранные demo-файлы и дать краткую ссылку к самопроверке; какие содержательные сообщения действительно даёт существующий протокол PL?
Как локальное описание проекта получает общие правила без повторения большого PL/check recipe в QMD и без обхода нынешней привязки materialization origins?
Как команда сообщает о недостающем включении, конфликте пути или зависимости, которую нельзя включить в обещанный самостоятельный проект?

**Отложенное направление, не реализация сейчас.** Возможный будущий обратный перенос IDE-правок в канон обсуждается после однонаправленной подготовки.
Предложения для него: манифест происхождения `source→target`, хеши исходного состояния (baseline), предварительный diff и трёхстороннее сравнение,
разбор конфликтов, общих зависимостей и удалений, затем явное применение выбранных правок владельцем канона.
Это не утверждённый дизайн и не обещание уже работающего обратного переноса; подготовленная копия сама по себе канон не изменяет.

**Планируемый результат.** В выбранной раскладке показать обычную авторскую правку и точный состав четырёх представлений;
согласовать переносимость библиотек, локальные сценарии и общий договор подготовки/архивирования без заранее выбранных имён команд или схем.
**Проверка.** На одном проекте раскрыть все включения и транзитивные зависимости: у общего компонента один канон, IDE-комплект самодостаточен.
Проверить сохранность и отдельный запуск нескольких авторских решений; стартер и отрицательные варианты имеют свои ожидаемые исходы по разделу 6.
Для `full` и `student` сверить состав и обещанный запуск, включая инструменты и данные; у ZIP Pages есть README и `src`.
Для выбранных демонстрационных тестов проверить доступность общих библиотек/build setup и запуск Gradle/JUnit одной командой после первоначальной настройки; зависимости Gradle не обязаны лежать JAR-файлами в ZIP. Сам факт выбора файловой доставки не доказывает нынешнее содержимое ZIP или PL; полный grader/авторские тесты не включаются автоматически. Проверить, что demo-файлы не становятся лишними обязательными файлами сдачи; ссылки/ZIP/README ведут к правильным ресурсам.
Показ PL и архивы соответствуют своему отбору; доступность этих же исходников в Git не считается ошибкой состава выдачи.
Правка общего компонента обновляет производные файлы; подготовка не меняет канон. Материализация не объявляется оцениванием или квалификационной проверкой.
Обратный перенос не включён в критерий нынешней реализации.
**Зависимости и владельцы.** Разделы 2–6; Core и материализатор — зависимости и составы, владельцы библиотек и PL — переносимое ядро и адаптеры,
курсовые владельцы — предметные варианты и данные, Download/PL — архивы и показ.

## 10 Перенос результатов PrairieLearn

**Цель.** Одна актуальная Java витрина и полный признанный зачёт тестовой группы с доступным успешным старым решением.
**Уже принято.** Каждый прежний полностью успешный автоматический результат даёт полный зачёт текущей задачи с освобождением от ручной части.
Успешные 1–2 исходника и старая выдача доступны как частные вложения; несовпадение с новыми тестами не препятствие.
Частичный прогресс может начаться заново, файлы/история сохраняются; новые студенты выполняют текущие условия обычным способом.

**Предлагаемый минимальный путь.** Ограниченная карта соответствий «исходная задача, студент, успешный результат → текущая задача» и штатное административное начисление.
В PL сохраняется объяснение основания; запись Manual или импорта означает административный перенос, не новую педагогическую проверку.
Допустима честно помеченная сегодняшняя запись импортированного ответа или события; нельзя выдавать её за самостоятельную новую сдачу или успешную внешнюю проверку новых тестов.
Старые действующие курсы, проверяющие модули и постоянный отдельный журнал зачётов не требуются по умолчанию.

**Что ещё доказать.** Сначала установить фактически работающие версии исходников, Native, образа, серверных инструментов и Gateway, контексты курса, зачисление, прежние вопросы/работы/слоты и связи Moodle/LTI.
Отбор опирается на реальный успешный автоматический результат и именно связанную с ним сдачу, а не закрытую работу, общий балл либо последний произвольный ответ.
Штатный CSV оценок меняет баллы и обратную связь, но игнорирует `submitted_answer` и не прикрепляет код.
Обработчик ищет существующую целевую `instance_question` и сохраняет статус `unanswered`, если задача была неотвеченной; подготовку целевой записи и её статус нужно проверить.
После импорта нужно проверить синхронизацию, новую неуспешную попытку/пересчёт и повторное назначение с границей времени активации: обычное административное переопределение нельзя заранее считать бессрочно сохраняемым зачётом.

**Планируемый результат.** Проверяемый отчёт предварительной сверки соответствий без изменения данных, сохранённые исходные свидетельства и выбранные штатные операции/привязка вложений.
**Проверка.** Студенческий интерфейс PL, его журнал оценок, завершение работ Gateway и Moodle одинаково отражают полный зачёт; успешный код/выдача видны нужному студенту.
Повтор не удваивает начисление; последующее обновление не стирает принятый перенос; ошибочная связь обнаруживается до записи.
Резервное копирование, переключение и восстановление — будущие действия согласованной реализации; откат сохраняет новые ответы после переключения.
**Зависимости и владельцы.** Разделы 6/8/9/12; курс задаёт право на зачёт, PL/Platform/Gateway — согласованную операцию и доступ.

## 11 Авторский цикл CI производительность и процесс работы

**Цель.** Быстро видеть корректный результат правки и уменьшить повторную работу при сохранении полной выдачи.
**Уже есть.** Пакетное извлечение, повторное использование обычных записей и неизменяемый снимок Core; повторное использование parsedPages в QRC, единой собранной модели PL и пакета артефактов Download.
Выбранная корневая страница Publisher не запускает все подпроекты; полная композиция выполняется последовательно. Platform компилирует адаптер один раз на задание проверки.
Поздние исправления CI по каноническому отбору, сроку жизни модели и общим входным файлам уже внесены; их не требуется заново «внедрять».
Публичный CI исходной ветки и результата слияния прошёл, но цикл защиты публичности `student→full→student` и объявленный состав проверок решают разные задачи.

**Качество исходников — отдельная проработка.** [Исследование оформления и lint](research/yaml-authoring-integration-20261027/source-quality.md) фиксирует фактические однострочные файлы, состав языков и нынешние проверки; происхождение генерации этих строк не установлено.
Нужно разделить форматирование и статический анализ, режим CI без записи и явное исправление, согласовать общие настройки IDE и охват QMD и блоков кода с узкими исключениями для намеренно неверных примеров.
Канон исправляется у автора курса/общего владельца расширения; генератор или шаблон включается в маршрут только после установления происхождения.
Байты установленных копий расширений и сторонние библиотеки не правятся вручную; будущие выдачи/receipts пересоздаются штатным производителем из исправленного канона.
Исторические снимки, прежние выдачи, студенческие вложения и загрузки сохраняют прежние байты. Инструменты и правила пока остаются кандидатами.

**Открытые технические вопросы.** Где обычная страница оплачивает ненужную возможность; какие факты можно повторно использовать внутри неизменной фазы?
Где нужны индексы вместо линейного поиска, однократная подготовка вопроса до контекста назначения, раннее обнаружение конфликта целевого пути?
Каковы границы проверки актуальности при изменении данных; что меняется между предварительными и завершающими обработчиками, независимыми командами и заданиями CI?
Ограниченный параллелизм обсуждается после карты общих выходных файлов и потребления RAM и сокращения лишней работы, не вместо этого.
Повторы Print/Moodle относятся к явному экспорту прежних поддерживаемых форматов, а не стоимости обычной Java страницы.

**Планируемый технический результат.** Одна связанная проверяемая партия курса и расширений за раз: исходное свидетельство→общая цель→кандидат изменения→приёмка всей затронутой цепочки, а не независимые планы формата и оптимизации.

### Связь исследования изменений и приёмки

Для `course-performance` в читаемой базе указан локальный worktree с ABI 1 и сохранением mtime; commit/SemVer здесь не установлен. Publisher Performance-линия 5.1.4 не является версией инструмента. Старые наблюдения не доказывают правильность или ускорение будущего состава.
Связка продолжает [RQ07/10/11/18/19/20](research/extension-architecture-20261027/high-level-requirements.md): авторский цикл, актуальность, native-семантика, состав выпуска, восстановление и доказанное сокращение ожидания; T04/T05/T13 дали малые опыты, T06–T12 — карту владельцев, R01–R04 — вопросы выпуска/восстановления ([прослеживаемость предложений](research/extension-architecture-20261027/proposal-traceability.md)).

- Копии условий и повторяемые отображения файлов (разделы 2–3) → понятный единый канон → принятые типизированный вход/наследование и предлагаемые именованные зависимости → проверка inline/include, ресурсов, столкновений путей, актуальности и полного IDE/student/full-состава. Новый формат и его реализация проверяются вместе.
- Межъязыковые границы, ранние читатели и разрозненные проверки (разделы 4–5) → обоснованные обязанности и объём кода → кандидаты типизированных интерфейсов, общей функции, reuse готового средства или удаления legacy → настоящий установленный consumer, положительные/отрицательные случаи и сохранение нужной гарантии/совместимости. Typecheck/lint не заменяют эту приёмку.
- [Пять direct/off пар](research/extension-architecture-20261027/performance-findings.md): медианы 14.6335/14.7791 с, медиана парной разности +0.2350 с со смешанными знаками; target HTML одинаков во всех 10 запусках → уменьшение ожидания без потери результата → сокращение доказанно повторной работы/повторное использование фазы как кандидаты → сопоставимая работа, outputs и затронутые зависимости. Стабильный overhead ≤1% не доказан; одиночные native floor 3.3454 с и N4 15.6867 с не дают цены Core или закона масштабирования.
- [Preview и Body](research/extension-architecture-20261027/performance-findings.md): startup 38.8699 с и save→visible 15.6216 с — одиночные наблюдения; экспорт трёх упражнений остановлен на 60 с/−15 до выпуска package → быстрый авторский цикл и понятное восстановление → сокращение повторной подготовки и ясное замыкание входов как кандидаты → отдельно доказать результат страницы, сохранения, композиции и экспорта, отмечая завершение/timeout. Это не диагноз «экспорт сломан».
- [Историческая Cybersecurity matrix](research/extension-architecture-20261027/measurement-protocol.md) меняла сразу несколько владельцев на другой машине; active Performance меняет workload Core → честное обоснование стоимости → сравнивать absent/off/active лишь по различающему вопросу с одинаковыми гарантиями. Ни межмашинные секунды, ни active counters не приписываются одному расширению/режиму off.

Общая приёмка партии включает применимые смысл/API и канон, реальные контракты, ресурсы/аудитории/зависимости выдачи, совместимость/историю/перенос, типизацию/статический анализ и сопоставимость стоимости на точном составе версий.
Для очистки tests/examples и объёма кода карта назначение→контракт→потребитель→проверка учитывает стоимость и нужную гарантию; уменьшение строк или числа тестов само по себе не успех.
[Неустановленная необходимость функций](research/extension-architecture-20261027/coverage-notes.md) не означает dead code; существующие batch/memo/reuse, собранная модель PL, QRC parsedPages и пакет Download не предлагаются к повторному внедрению.
Страница, preview, подпроект, композиция, экспорт, qualification и assembly имеют отдельные свидетельства. Старый PASS не переносится на новую партию; живой UI/сервер и прежние 0/672 остаются открытым долгом.
Масштабирование N1/N4, завершение/восстановление Body, полный рендер и квалификация выполняются лишь по согласованному различающему вопросу и области, не как автоматический полный список. Сегодня новые замеры, оптимизация, изменения инструментов или очистка не выполняются.

**Процесс будущей работы.** Сохранять короткую передачу: вопрос/владелец/изменённый состав/результат/проверки/ограничения.
На возобновлении читать актуальное задание и затронутый контекст; повторный полный аудит нужен только при новой причине.
Использовать существующие команды/API; повторяемую ручную последовательность обобщать после наблюдённой необходимости.
Независимые вопросы можно делегировать в пределах действующего допуска и лимита, у общего файла один владелец.
Уже принятый цикл «авторство→независимое чтение→техническая выдача→адресный возврат» не заменяется новым метарегламентом.

**Проверка процесса.** На сопоставимых партиях учитывать ожидание пользователя, общие токены/вызовы, повторное чтение, возвраты и регрессии.
Это не новый сервис телеметрии: достаточно имеющихся журналов. Меньше шагов не означает полный качественный результат.

[MAST,v3](https://arxiv.org/abs/2503.13657v3) различает сбои постановки, согласования агентов и проверки; это опора для разбора наших возвратов, не доказательство пользы большего числа агентов.
