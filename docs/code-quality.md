# Качество исходников

Единый локальный цикл запускается из корня репозитория:

```sh
go-task format
go-task check-format
go-task check
```

`format` исправляет оформление собственных исходников. `check-format` проверяет
оформление без записи; `check` включает эту проверку и статический анализ. После изменения
кода или материалов сначала выполните этот цикл, затем нужную сборку, render
или export. Проверка качества исходников не заменяет проверку поведения
примеров и отдельную проверку заданий.

## Инструменты

Используются установленные системные команды из `PATH`; версии инструментов
не закрепляются отдельным installer или lock-файлом курса. На Arch команда
Task называется `go-task` и устанавливается пакетом `go-task`.

| Исходники                                         | Оформление и проверка                                                             |
| ------------------------------------------------- | --------------------------------------------------------------------------------- |
| Java                                              | `google-java-format`, синтаксическое дерево JDK, `checkstyle`                     |
| Java в QMD                                        | `google-java-format`, синтаксический разбор JDK; временные обёртки для фрагментов |
| Python                                            | `ruff format`, `ruff check`, `pyright`                                            |
| Shell                                             | `shfmt`, `shellcheck`, синтаксическая проверка Bash                               |
| Markdown, JSON, YAML, CSS, JavaScript, TypeScript | `prettier`                                                                        |
| Lua                                               | `stylua`                                                                          |
| XML, CSL, SVG, C# project и NuGet config          | `xmllint --nonet --format`                                                        |
| TOML                                              | `taplo format`                                                                    |
| BibTeX                                            | `bibtex-tidy`, только оформление                                                  |
| `.gitmodules`                                     | синтаксический разбор `git config`                                                |
| Groovy и Gradle                                   | `npm-groovy-lint` с CodeNarc                                                      |
| Примеры C++, C#, Kotlin                           | `clang-format` и `g++`, `dotnet`, `ktlint` и `kotlinc`                            |

Отсутствующий инструмент или неподдерживаемый им синтаксис — ошибка проверки.
Курс не скачивает замену автоматически. Настройки и точные команды находятся
в `tools/quality/` и конфигурационных файлах корня.

## Какие исходники проверяются

Общий список собственных исходников включает отслеживаемые и новые
неигнорируемые файлы;
добавлять каждый новый файл в отдельный manifest не требуется. Охват задают
типы файлов и исключения общего обхода, а не только файлы текущего diff.

Java проверяется во всех авторских частях курса: отдельные `.java`, блоки
Java в QMD, стартеры, эталоны, тесты и отрицательные примеры. Намеренно неверный
пример сохраняет учебный смысл: его оформление и допустимые статические
проверки не означают требование успешно скомпилировать его как обычный проект.
Для намеренных диагностик используется адресное описание ожидаемого результата;
его исчезновение тоже требует проверки. Неполные или намеренно синтаксически
неверные QMD-фрагменты требуют адресного исключения с причиной и отпечатком
содержимого в `tools/quality/qmd/exclusions.json`. Новая ошибка не получает
исключение автоматически. Неизвестные типы и отсутствующие части учебной
программы не требуют превращать фрагмент в отдельный компилируемый проект:
разбор проверяет синтаксис.

Форматирование QMD затрагивает Java-блоки; текст, метаданные и другие языки
сохраняются. Обычный Markdown проверяет `prettier`, не форматируя содержимое
его fenced-блоков.

Зависимости и результаты генерации не становятся отдельными владельцами
исходного кода. Исправляйте канонический исходник, затем обновляйте получаемые
из него копии или архивы. Для комплектов примеров канонические исходники лежат
в `handbook/examples/<тема>/`; существующие `handbook/examples/*-examples.zip`
содержат распространяемые копии. После оформления канонических исходников
`format` обновляет эти 13 существующих архивов через
`tools/quality/archives.py`. `check-format` и `check` сверяют состав и байты
файлов архива с каноническим деревом: устаревший ZIP не проходит проверку.
Список комплектов определяется уже существующими архивами; новый реестр
зависимостей не вводится.
Зависимости в `_extensions` и submodules обновляются своим механизмом;
форматировать их как собственный
код курса не следует. Исторические снимки и сохранённые доказательства
не переписываются ради текущего оформления.
Точный общий список исключений задаёт `tools/quality/common.py`: каталоги
зависимостей, сборки и кэшей, архивные исследования и отчёты, а также symlink,
который не является самостоятельным каноническим текстом. При добавлении нового
типа исходника дополните соответствующую проверку; при новом исключении укажите
его причину. Изменение расположения файла само по себе не должно скрывать
собственный код от проверки.

## Проверка учебных заданий

`go-task verify:declared` и `go-task verify:delivery` проверяют уже собранный
выпуск через Platform. Это отдельная стадия: зелёная проверка оформления
не подтверждает оценивание решений, а успешный grading не подтверждает
качество авторских исходников. Параметры выпуска описаны в `Taskfile.yml`.

## Семантический слой

В `check` обязательны 26 структурных правил Panache для всех собственных QMD.
Panache используется только как анализатор, без external formatter: Java-блоками
по-прежнему владеют batch Google Java Format и проверки JDK AST. QRC остаётся
владельцем namespace-ссылок и библиографии. Неоднозначное Markdown-написание
обращения к массиву в лекции заменено inline code без изменения Java-примера.

`semantic.py` проверяет синтаксис и дубликаты ключей YAML (`yamllint`) и JSON,
GitHub Actions (`actionlint`), CSS/SCSS (`stylelint`), собственные HTML-фрагменты
(`html-validate`), TOML (`taplo lint`) и синтаксис каждого shell-файла. Правила
стилей ищут неизвестные свойства, селекторы, единицы, неверные цвета и опасные
повторы; HTML проверяет структуру и атрибуты фрагмента. Итоговый DOM эти проверки
не заменяют. Форматированием HTML/SCSS, как и CSS/YAML/JSON, владеет Prettier.
Stylelint, SCSS plugins и HTML Validate устанавливаются обычным `npm ci` из
существующего `package.json`; остальные CLI берутся из системного `PATH`.
Отсутствие анализатора и ненулевой код его завершения останавливают проверку.

Ruff дополнительно включает bugbear (`B`). Строгий Pyright и точные ожидаемые
диагностики динамического Python-примера сохранены. Для парных списков
Java-фрагментов явно проверяется одинаковая длина; ошибка согласования теперь
не может незаметно обрезать проверяемые исходники через `zip`.

## PMD и намеренные Java-диагностики

Обязательный PMD с Java 25 проверяет служебную область: `tools/`,
`tasks/test-support/`, `tasks/projects/common/` и каталоги `observations`,
`checks`, `demo`. Новые неигнорируемые Java-файлы в этой области обнаруживаются
автоматически. Все девять правил пилота оценены: восемь включены в `pmd.xml`;
`NullAssignment` отклонено как правило этого курса. Освобождение ссылки на
извлечённую ячейку очереди/стека предотвращает удержание объекта, а обнуление
`FileInvocation.last` перед ожидаемым отказом предотвращает чтение прошлого
результата. Удалять такую корректную очистку ради этого правила нельзя.

Полный аудит банка запускается отдельно и сохраняет настоящий код отказа:

```sh
python3 tools/quality/pmd.py check --audit /tmp/java-pmd-all.json
```

PMD 7.29.0 не разбирает корректный Java 25 compact source
`handbook/examples/runtime/Reading.java`, начинающийся со `static int`.
Это ограничение анализатора: `javac --release 25` принимает исходник. Полный
аудит поэтому остаётся неполным и завершается ошибкой; он не объявляется
успешной проверкой всего банка и не заменяет JDK. Пять намеренно синтаксически
неверных примеров по-прежнему проверяются отдельным точным договором JDK.

Оставшиеся сообщения полного аудита имеют конкретный учебный контекст:

- `FinallyDemo` намеренно показывает потерю возврата/исключения через `return`
  в `finally`; два `ReturnFromFinallyBlock` сохраняются.
- `ValueSemantics`, `MethodValues`, `ArgumentsDemo` и оба `ObjectsTailDemo`
  показывают отсутствие влияния присваивания локальной копии аргумента на
  вызывающий код, потерю ссылки и недостижимые объекты. `UnusedAssignment`
  у этих присваиваний является наблюдаемым предметом демонстрации.
- `rejected/ReassignedCapture` и `rejected/FinalReference` намеренно нарушают
  ограничения effectively final/final; побочные `UnusedAssignment` не повод
  исправлять отрицательный пример.
- `negative-controls/no-retry` намеренно завершает цикл после первой попытки;
  `AvoidBranchingStatementAsLastInLoop` соответствует проверяемому дефекту.
- `stack-exceptions/negative-controls/shared-state` намеренно хранит стек в
  общих static-полях; два `AssignmentToNonFinalStatic` соответствуют дефекту.
- `remove-nonletters/negative-controls/merge-words` намеренно не использует
  `previous`; `strong-password/negative-controls/no-digit-condition` намеренно
  не использует `digit`. Четыре `UnusedAssignment` отражают эти отрицательные
  сценарии.
- `airline-persistence-project/**/airline/Plane.java` увеличивает явный счётчик
  созданных экземпляров. `AssignmentToNonFinalStatic` отмечает предусмотренное
  наблюдаемое состояние; это не гарантия многопоточной безопасности и не
  ошибка сериализации. Четыре независимых варианта сохраняют этот приём.

Реальные мёртвые присваивания в общей поддержке процессов, `FileInvocation`,
`TimetableProbe` и меню авиакомпании устранены. Нужный вызов `load`, способный
дать отказ, сохранён. Все собственные встраивания `JavaProcess` синхронизируются
из канонического helper через `format` и проверяются побайтно.

CPD не имеет порога допуска для учебных вариантов: повтор стартера, эталона,
отрицательного контроля и независимого встраивания теста предусмотрен способом
поставки. SpotBugs/Error Prone для Platform runtime принадлежат репозиторию
Platform. Их пилотные сообщения в `ArrayRecordsDemo` относятся к намеренным
`equals(null)` и сравнению несовместимых типов, массиву как компоненту record,
тождеству ссылок и простому default-package примеру. `ConstructorDemo` намеренно
отклоняет null; `MissingOverride` и default package — контекст оформления
учебного примера. Они не включены как обязательный compilation gate для
студенческих решений и не объявлены найденными дефектами поведения.

Узкий `clang-tidy` проверяет корректные C++ translation units и заголовки через
включающий TU после штатного `g++`; диагностические категории указаны в
`examples-clang-tidy.yaml`, каждое предупреждение — ошибка. Намеренный
`negative.cpp` сохраняет точный договор отказа g++, а не маскируется как
успешный анализ. Широкое `bugprone-exception-escape` и cppcheck
`throwInEntryPoint` не включены: настоящий demo вызывает шаблон только с равными
размерами, а несовпадение размеров предусмотренно отклоняется исключением.
Cppcheck дублирует текущий семантический профиль и не распознаёт отрицательный
compile-пример; отдельного обязательного прохода нет.

Для C# включены SDK analyzers `latest-all` с ошибкой на предупреждениях.
`Program` объявлен `sealed`: подклассов у входа демонстрации нет, предмет
обобщённого скалярного произведения сохранён. Собственные C# projects копируются
во временное дерево; новые файлы проекта попадают в настоящую сборку.
Kotlin/Gradle продолжают использовать существующие ktlint/CodeNarc.
Положительный `generic-interface/positive` теперь действительно входит в
`gradle classes`, зависит от `compileJava` и не включает намеренно неверный
`negative`. Отдельная проверка компилирует настоящий reference-комплект,
проверяет `Good.class` и отклоняет испорченный `Good`; ручная оценка и условия
задания сохранены. В CI Gradle устанавливает стандартный
[setup-gradle](https://github.com/gradle/actions/blob/main/docs/setup-gradle.md)
без добавления wrapper в выдачу.
