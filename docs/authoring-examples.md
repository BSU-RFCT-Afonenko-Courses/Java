## Исполнение программы

### Фрагмент теории

Компактный исходный файл позволяет запустить небольшую Java-программу
без явного объявления класса. Сохраните в `Hello.java`:

```java
void main() {
    IO.println("Hello");
}
```

`main` задаёт начальное действие, `void` означает отсутствие возвращаемого
значения, `IO.println` печатает строку. Команда `java Hello.java` компилирует
исходник для этого запуска и выполняет программу; вывод — `Hello`.
Здесь команды `java`, `javac`, `javap` выбираются из одного JDK 25.
При нескольких JDK можно указать полный путь, например
`/usr/lib/jvm/java-25-openjdk/bin/java Hello.java`.

Чтобы сохранить результат компиляции и исследовать его, выполним отдельно
`javac -g Hello.java`, затем `java Hello`. Компилятор создаёт `Hello.class`;
имя класса выбирается из имени файла. Неявно объявленный класс содержит
наш метод `main`. Для вызова этого нестатического метода среда создаёт
объект. В `java Hello` аргументом служит имя класса, поэтому этот режим
читает уже созданный `.class`. Режим `java Hello.java` читает исходник
и не обновляет сохранённый файл класса.

В `javap -c -p -l Hello` видны загрузка строки, вызов `IO.println` и возврат.
JVM — абстрактная машина с заданными инструкциями. Для каждого вызова
метода её модель создаёт кадр: локальные переменные хранят значения вызова,
а стек операндов передаёт промежуточные значения инструкциям. Загруженная
ссылка на строку становится аргументом библиотечного метода. Реализация
JVM выполняет эти действия на конкретном процессоре, сохраняя их смысл.
`-g` сохраняет отладочные сведения, включая имена локальных переменных,
которые `javap -l` способен показать.

HotSpot — реализация JVM в используемом OpenJDK. Её интерпретатор выполняет
инструкции байткода, а JIT-компилятор во время работы программы переводит
выбранные методы в машинный код процессора. При длительной работе HotSpot
собирает профиль: частоту выполнения кода и ветвей, типы объектов
в определённых точках кода. Эти данные помогают
выбрать часто выполняемый участок для JIT-компиляции и специализировать
его под наблюдавшиеся случаи. Например, известный тип получателя позволяет
выбрать реализацию вызываемого метода и встроить её тело с проверкой
предположения. Фактическое решение устанавливают по журналам компиляции
и, при необходимости, машинному коду выбранного запуска.

### Последовательность экранов

#### Компактный исходный файл

Файл `Hello.java`, JDK 25:

```java
void main() {
    IO.println("Hello");
}
```

```bash
java Hello.java
```

Вывод — `Hello`. `main` задаёт начальное действие, `IO.println` выводит
строку. Команда компилирует исходник для текущего запуска.

**Notes.** После запуска попросить указать текст, определивший результат.
Затем предложить назвать артефакт, который можно получить отдельно
и открыть для исследования работы компилятора.

#### Файл класса

```bash
javac -g Hello.java
java Hello
javap -c -p -l Hello
```

`javac` сохраняет `Hello.class`, `java Hello` запускает этот класс.
`javap -c` показывает инструкции, `-p` — все методы,
`-l` — отладочные таблицы. Для последних при компиляции указан `-g`.
Метод `main` принадлежит неявно объявленному классу; перед его вызовом
среда создаёт объект этого класса.

**Notes.** Сопоставить аргументы двух команд `java`: имя файла с `.java`
и имя класса. До следующего экрана предложить прогноз: исходник изменён
на `IO.println("Changed")`, команда по-прежнему `java Hello`.

#### Сохранённый результат компиляции

В `Hello.java` заменили `IO.println("Hello")` на `IO.println("Changed")`.
Сохранённый `Hello.class` пока содержит прежний текст:

| Действие | Вывод | Основание |
|---|---|---|
| `java Hello` | `Hello` | Читается прежний `Hello.class` |
| `java Hello.java` | `Changed` | Компилируется текущий исходник для запуска |
| `javac -g Hello.java`, затем `java Hello` | `Changed` | Сохранённый класс обновлён |

Режим запуска определяет входной файл. Первый результат сохранился,
потому что инструкции прежнего класса ещё содержат старую строку.

**Notes.** Показать ответ после прогноза. Предложить найти действие,
обновляющее сохранённый класс. Затем восстановить строку `Hello`
и повторить компиляцию перед исследованием инструкций.

#### Модель JVM

В `Hello.java` восстановлена строка `IO.println("Hello")` и снова выполнен
`javac -g Hello.java`. Фрагмент вывода `javap -c -p -l Hello` для `main`:

```text
0: ldc           #7   // String Hello
2: invokestatic  #9   // Method java/lang/IO.println:(Ljava/lang/Object;)V
5: return
```

`ldc` помещает ссылку на строку в стек; `invokestatic` забирает её как
аргумент `IO.println`; `return` завершает метод:

```text
кадр main: стек операндов
[] → [ссылка на "Hello"] → [] → возврат
       загрузка строки     вызов println
```

Кадр хранит данные одного вызова; стек операндов переносит промежуточные
значения между инструкциями. Формат класса и смысл инструкций общие
для JVM разных платформ. Реализация обеспечивает их действие
на своей операционной системе и процессоре.

**Notes.** Указать на ссылку как аргумент печати. Предложить проследить
состояние стека кадра `main` перед `invokestatic` и после возврата из
`println`; затем указать инструкцию, завершающую кадр.

#### Профиль выполнения HotSpot

HotSpot — реализация JVM в OpenJDK. Интерпретатор исполняет байткод,
а JIT-компилятор во время работы переводит выбранные методы в машинный код
процессора.

Счётчики выделяют часто выполняемый код.
Частоты ветвей и типы получателей помогают JIT-компилятору выбрать обычный путь
и специализировать вызовы. Встраивание выбранного метода открывает
оптимизатору его тело вместе с окружающим вычислением.

Встраивание конкретного метода зависит от собранного профиля и решений
оптимизатора. Диагностика данного процесса и нагрузки позволяет установить,
какое решение было принято.

**Notes.** Сопоставить единственную печать `Hello` и многократную обработку
запросов сервисом. Предложить назвать наблюдение, которого ещё нет у `javac`
при подготовке класса: типы реально поступающих объектов.

### Авторские решения

«Исполнение программы» охватывает запуск, класс и реализацию;
«Файл класса» и «Профиль выполнения HotSpot» называют отдельные механизмы.
В начале объяснения даны код, версия, результат и назначение команды. Различие
режимов запуска видно до вывода о старом классе. Notes ставят прогноз
до ответа и связывают новое наблюдение с опытом C++.

Вместо «Само число вызовов ещё не обещает конкретной оптимизации» показано,
какие данные помогают выбрать участок для оптимизации и как установить
решение конкретного запуска. Условие диагностики стоит рядом с утверждением об оптимизации;
оно не становится обязательной последней оговоркой каждого экрана.

## Передача аргументов по значению

### Фрагмент теории

При вызове Java вычисляет аргументы и присваивает их значения новым
переменным параметров. Для `int[]` значением служит ссылка на массив.
Поэтому вызывающий метод и параметр могут обращаться к одному объекту.
Начальное состояние — `int[] pages = {5, 7};`.

```java
static void correctFirst(int[] data) {
    data[0] = 9;
}

static void replace(int[] data) {
    data = new int[]{1, 2};
}
```

Первый метод записывает число в компонент полученного массива;
после `correctFirst(pages)` чтение `pages[0]` даёт `9`. Следующий вызов
`replace(pages)` создаёт новый массив и меняет значение `data` в своём
кадре. Переменная `pages` в вызывающем `main` сохраняет ссылку на прежний
массив, поэтому очередное чтение снова даёт `9`. Различие результатов
определяется левой частью присваивания при едином правиле передачи значения.

### Последовательность экранов

#### Копирование ссылочного аргумента

Переменная `int[] pages = {5, 7};` хранит ссылку на массив.
Метод получает этот существующий непустой массив:

```java
static void correctFirst(int[] data) {
    data[0] = 9;
}
```

В начале `correctFirst(pages)`:

```text
кадр main                  кадр correctFirst
pages ─────────┐           data ────────┐
               └───────────┬────────────┘
                           v
                       A: [5, 7]
```

Параметр `data` получил копию ссылки. Обе переменные ведут к одному
массиву `A`; буква обозначает объект в опыте.

**Notes.** До перехода к результату попросить назвать место записи
`data[0] = 9`: переменная или компонент массива. Сохранить на доске
два имени разных переменных, даже если студент говорит «это один массив».

#### Изменение общего массива

После `data[0] = 9` обе ссылки ведут к `A: [9, 7]`. По завершении вызова
параметр `data` исчезает вместе с кадром, а `pages` сохраняет доступ к `A`.

```java
correctFirst(pages);
System.out.println(pages[0]); // 9
```

Запись изменила компонент общего объекта, поэтому изменение доступно
вызывающему коду через его собственную ссылку.

**Notes.** Перед следующим экраном показать только следующее действие:
`data = new int[]{1, 2}`. Попросить предсказать `pages[0]`, учитывая,
что исходный массив к этому моменту содержит `[9, 7]`.

#### Присваивание параметру

Переменная `pages` сохраняет ссылку на массив `[9, 7]`:

```java
static void replace(int[] data) {
    data = new int[]{1, 2};
}
```

После присваивания внутри `replace(pages)`:

```text
кадр main                  кадр replace
pages ──> A: [9, 7]         data ──> B: [1, 2]
```

```java
replace(pages);
System.out.println(pages[0]); // 9
```

Ссылка на `B` записана в параметр `data`. Переменная `pages` другого кадра
сохранила ссылку на `A`.

**Notes.** Если прогноз дал `1`, проследить левую часть присваивания
до переменной на схеме. Сопоставить с C++ `T&`: присваивание через такую
ссылку действует на связанный с ней объект. Параметр Java здесь является
отдельной переменной со скопированным значением.

### Авторские решения

Название указывает правило языка, применимое к любому аргументу.
Вход задаёт тип, массив, условие индекса и начальные значения.
Оба результата видны; схема кадров и имена переменных позволяют найти место записи.
«Один журнал, два имени» не называло механизм, а «Копирование ссылочного
аргумента» связывает рисунок с действием вызова. Notes развивают прогноз
и разбирают конкретную ошибку рассуждения.

Разбор Шилдта на печ. с.190–192 помог выбрать парные опыты. Фраза
на с.191 о поведении «как будто по ссылке» уточняется на следующей странице
копированием самой ссылки. Здесь правило сразу дано по JLS §15.12.4.5,
а кадры — по JVMS §2.6.

## Параметризация контейнера

### Фрагмент теории

Контейнер с полем `Object` принимает ссылки на объекты разных классов.
Его `get()` возвращает `Object`, поэтому клиент, которому нужна строка,
применяет приведение:

```java
final class ObjectBox {
    private final Object value;
    ObjectBox(Object value) { this.value = value; }
    Object get() { return value; }
}

ObjectBox box = new ObjectBox("Java");
String text = (String) box.get();
```

Сохранена строка, проверка успешна. Если заменить аргумент конструктора
на `25`, число упакуется в `Integer`. Такая коробка допустима, но её чтение
тем же клиентом завершится `ClassCastException`. Объявление контейнера
допускает любую ссылку и не связывает содержимое конкретной коробки
с ожидаемым типом результата.

Параметр `T` выражает эту связь:

```java
final class Box<T> {
    private final T value;
    Box(T value) { this.value = value; }
    T get() { return value; }
}
```

В `Box<String>` поле, аргумент конструктора и результат `get()` согласованы
со `String`. Попытка `new Box<String>(25)` отвергается при компиляции;
чтение строки больше не требует приведения в клиентском исходнике.
Параметризация описывает типовую связь, а сохранение ссылки по-прежнему
подчиняется присваиванию. Если передать изменяемую книгу, контейнер
и исходная переменная будут обращаться к одному объекту.

### Последовательность экранов

#### Контейнер с типом `Object`

```java
final class ObjectBox {
    private final Object value;
    ObjectBox(Object value) { this.value = value; }
    Object get() { return value; }
}
```

Два альтернативных опыта с этим классом:

```java
ObjectBox box = new ObjectBox("Java");
String text = (String) box.get(); // строка, проверка успешна
```

```java
ObjectBox box = new ObjectBox(25);
String text = (String) box.get(); // Integer: ClassCastException
```

`get()` имеет тип `Object`. Приведение проверяет класс полученного объекта;
во втором опыте он не совместим со `String`.

**Notes.** Предложить назвать место внесения несогласованности и место
её обнаружения. Сохранить два события для сравнения со следующим экраном.
Попросить назвать класс объекта, который появляется при упаковке числа `25`.

#### Связь типов в контейнере

```java
final class Box<T> {
    private final T value;
    Box(T value) { this.value = value; }
    T get() { return value; }
}
```

Допустимый вариант:

```java
Box<String> title = new Box<>("Java");
String text = title.get();
```

Альтернативная попытка создания:

```java
Box<String> title = new Box<>(25); // ошибка компиляции
```

`T` связывает поле, аргумент конструктора и результат `get()`.
`String` — аргумент типа; `<>` поручает компилятору вывести его справа
из контекста. Несовместимое значение обнаружено уже при создании.

**Notes.** Проследить три использования `T`. Предложить заменить только
аргумент конструктора в рассуждении и установить, почему ошибка теперь
обнаруживается раньше. Уточнить, какие три места объявления
согласуются с выбранным аргументом `String`.

#### Общий объект в контейнере

Книга хранит признак выдачи читателю:

```java
final class Book { boolean borrowed; }

Book book = new Book();
Box<Book> stored = new Box<>(book);
book.borrowed = true;
System.out.println(stored.get().borrowed); // true
System.out.println(stored.get() == book);  // true
```

Конструктор скопировал ссылку `book` в поле коробки. Обе ссылки ведут
к одной книге, поэтому изменение её поля видно через `stored.get()`.
`final` у `value` запрещает замену сохранённой ссылки; `borrowed`
принадлежит книге и остаётся изменяемым.

**Notes.** До разбора `final` предложить нарисовать два объекта — коробку
и книгу — и ссылку между ними. Затем найти точное поле, к которому
относится `final`; это предотвращает перенос свойства поля на весь граф.

### Авторские решения

Название обозначает механизм связи типов и не зависит от книги примера.
Экран вводит `Book` и действие на месте. Обозначение альтернатив находится
у кода, поэтому два объявления `title` не воспринимаются как один блок.
Notes направляют внимание на типовую связь и объектный граф.

Случай `null` нужен при обсуждении допустимости отсутствия или распаковки.
Его место выбирается по возможному выводу читателя. Обязательный финал
«обобщение не запрещает `null`» у каждого перехода разрывал бы рассуждение.
Стирание и мостовой метод продолжают тему отдельно, сохраняя различие
исходных типов, дескрипторов и вставленного компилятором кода.

## Прямое изложение и масштаб

Общее предметное объяснение устанавливает механизм: «Параметризация
связывает типы частей объявления через параметры. Граница параметра
определяет доступные операции; конкретный аргумент типа выбирается
при использовании объявления».
Такое объяснение пригодно после перечня тем, до выбора предметного контейнера
или алгоритма.

У отдельного опыта иная функция: «`java Hello` читает сохранённый файл класса.
После изменения исходника этот файл содержит прежнюю строку. Повторная
компиляция обновляет его, и следующий запуск печатает новый текст».
Здесь условия опыта устанавливают причину наблюдаемого результата.

Отрицательный вариант «Это объясняет, почему нужно пересмотреть привычки,
а не только запомнить синтаксис» сообщает оценку обучения. Предметный вариант:
«Переменная ссылочного типа в Java хранит ссылку на объект или `null`.
Присваивание копирует ссылочное значение, поэтому обе переменные могут
обращаться к одному объекту».
Замена запрещённого союза с сохранением прежней оценки оставила бы дефект.

Отрицательная пара показывает сохранение оговорки при смене слов.
Первый вариант: «Это намерение автора, а не доказательство, что любое
использование класса быстрее или яснее любого другого решения».
Его неудачная замена: «Эффективность конкретной программы при этом зависит
от выбранных представлений данных, алгоритмов и реализации языковых
средств». Оба предложения защищают предыдущее историческое утверждение
от не поставленного читателем вывода. Во втором варианте отсутствует
местный механизм, который сделал бы общую зависимость предметом объяснения.
Такое продолжение не требуется.

Положительный вариант исторического утверждения: «Страуструп описывает
свой исходный замысел как сочетание эффективности системных программ
с абстракциями и стилем Simula». За ним следует ссылка на источник.
Это законченная мысль; новый заключительный комментарий не добавляется.

Отрицательное обобщение: «Эти источники отвечают за разные части одного
запуска». Перед ним уже указаны источники правила целочисленного деления,
единицы длины строки и устройства исполнения метода. Заключительная фраза
повторяет установленное распределение и не добавляет отношения, условия
или следствия. Её удаляют без замены; предметные утверждения об источниках
сохраняются.

Положительный вариант существенного условия: «`checkcast` пропускает `null`;
для ненулевой ссылки он проверяет совместимость класса объекта с указанным
типом. Успешная проверка сохраняет исходное ссылочное значение».
Условие различает два допустимых случая операции. Его удаление исказило бы
общее правило проверки ссылочного значения. Определение понятия,
классификация и историческое утверждение сохраняют собственный масштаб;
обязательный частный опыт к каждому из них не добавляется.

Отрицательный ввод «В Python сначала напишем функцию, затем добавим
аннотации» объявляет следующие действия автора. Предметный вариант:
«Функция начинает накопление с `0` и использует операции `+` и `*`.
Аннотации задают для статического анализатора допустимые типы аргументов
и результата». Объяснительная проза устанавливает свойства программы;
объявление очередного авторского шага в неё не включается.

Задание «Определите тип выражения по данным объявлениям» предлагает
читателю действие с проверяемым результатом. Указание в notes «Попросить
студентов предсказать результат до запуска» организует работу преподавателя.
Такие задания, содержательные вопросы и мысленные действия сохраняются.
Критерий — функция высказывания в данном контексте; форма глагола
не служит самостоятельным основанием для удаления.

Notes первого образца предлагают сравнить команды и предсказать результат
изменения исходника; notes второго — найти место записи. Эти инструкции
организуют действия преподавателя с видимым материалом. Проверка прямого
изложения сохраняет их сценарную функцию. Редакторскую оговорку нельзя
сохранить переносом в notes: она не задаёт действия преподавателя
с предметом занятия.

### Наблюдение: копирование ссылочного значения

В [лекции 2](../lectures/values-absence.qmd#sec-lecture-values-absence)

общего массива раскрывают значение, скопированное присваиванием.

Прогноз организован до открытия экрана с результатом. Когда этот экран
уже виден, notes предлагают сопоставить прогноз с числом `9` и найти
место записи. Так заметки учитывают фактический момент показа. Начало
не нуждается в пересказе всей лекции об исполнении: для нового вывода
важны значение переменной, присваивание и общий объект.

### Общее определение: параметризация программ

[Принятая предметная последовательность лекции 5](../lectures/generics.qmd#sec-l-generics)
открывается определением обобщённого программирования. Параметр типа
связывает места общего объявления; аргумент выбирается при его использовании. Границы параметра
определяют доступные операции. Затем сопоставляются моменты проверки
общего тела и конкретного использования в Java и C++.

Это самостоятельное предметное знание до выбора контейнера. Следующий

типов. Обязательный предварительный сюжет с ошибкой отсрочил бы уже
достаточное общее объяснение. Notes направляют сравнение параметра значения
и параметра типа.

Все три объяснения продолжаются рассуждением о введённом предмете. Различаются
их исходные действия: выбрать артефакт, объяснить наблюдение, применить

### Прямое описание ограничения

Отрицательные формулировки экрана о памяти и ресурсе в
[лекции 3](../lectures/objects-invariants.qmd#sec-j25-lecture-objects-invariants-resources):
сборщик «не обещает» своевременного закрытия, программа «выразит отдельно»
обязанность. Они смешивают свойство механизма и будущий ход объяснения.
Существенные границы должны остаться. Вариант предметной редакции:

> Сборщик мусора освобождает память недостижимых объектов. Присваивание
> `null` одной переменной может оставить другие пути к объекту; даже
> недостижимость не задаёт момент освобождения его памяти.
>
> Открытый файл требует вызова `close`. Конструкция `try` с ресурсами
> вызывает `close` для успешно инициализированного ненулевого ресурса
> при выходе из блока, включая выход через `return` или исключение.
> Выход локальной переменной из области видимости в Java не вызывает
> деструктор объекта по правилу автоматического времени хранения C++.

Текст сохраняет достижимость, отсутствие фиксированного момента сборки,
управление внешним ресурсом и границу аналогии с C++. Условия автоматического
закрытия сверены с [JLS 25 §14.20.3](https://docs.oracle.com/javase/specs/jls/se25/html/jls-14.html#jls-14.20.3),
назначение сборки памяти — с [JVMS 25 §2.5.3](https://docs.oracle.com/javase/specs/jvms/se25/html/jvms-2.html#jvms-2.5.3).
Notes предлагают указать, какая переменная ещё хранит ссылку
и какое действие завершает работу файла. В полном разделе отдельно
разбираются исходы самого `close`.

Похожая метафора возникает в [лекции 8](../lectures/exceptions-resources.qmd#sec-j25-lecture-exceptions-resources-contract).
Заголовок в этом снимке «События и обещание операции», слова «не выполнила
обещание» и соответствующие notes — отрицательные примеры. Сохраняется
различение трёх ситуаций. Предметный вариант под заголовком «Исход операции»:

> Поиск может успешно завершиться без совпадения. Для загрузки каталога
> нужен доступный файл; отказ чтения препятствует получению каталога.
> Обращение загрузчика по неверному индексу требует исправления алгоритма.

Notes предлагают сопоставить успешный поиск без совпадения, отказ внешнего
ресурса и дефект программы. Эти действия сохраняют педагогическую пользу
исходного экрана. Прежние формулировки экрана сохраняются здесь
как материал разбора.

### Техническая преамбула и местное условие

Перед `parseScore` в [лекции 8](../lectures/exceptions-resources.qmd#sec-j25-lecture-exceptions-resources-context)
перечислены `ErrorsDemo.java`, импорты, отдельные `main`, соседние классы
ресурсов и будущие файловые клиенты. Это отрицательный пример общего
паспорта опытов: перечисленные элементы пока не участвуют в преобразовании
балла. Их место — полный файл и инструкция воспроизведения.

Полезное условие из того же блока сохраняется рядом с методом:

> `parseScore` принимает ненулевой текст без краевых пробелов. Успешный
> результат — целый балл от 0 до 100; числовой синтаксис и диапазон
> проверяет сам метод.

На этом основании понятны два последовательных действия: преобразование
строки в число и проверка предметного диапазона. Вход `"120"` проходит
первое действие и отвергается вторым. Предпосылка о ненулевом тексте
сохраняет границу допустимого вызова. Очистка преамбулы не удаляет её
вместе с организацией файлов.

В начале [лекции 6](../lectures/equality-collections.qmd) действует тот же
критерий: опыту с двумя строками нужны сами строки и операции сравнения.
Импорты будущих `Student` и `Book` вводятся при опытах с этими объектами.
Указание на альтернативные варианты кода остаётся непосредственно у таких
вариантов, если без него повторные объявления можно прочитать как один блок.

### Сохранение одной линии примера

В [лекции 9](../lectures/io-application.qmd#sec-j25-lecture-io-application-step-01)
команда `deliveries.Main input` и строки поставок задают понятную задачу.
Отрицательный переход вставляет перед её трассой `InputDemo`, файл
с `first\n\nlast` и путь `data/students.txt`. Эти данные относятся к другим
опытам и не участвуют в накоплении количеств.

Предметная последовательность сохраняет один вход: после строк
`тетрадь;4`, `ручка;2`, `тетрадь;3` рассматривается состояние сумм после
каждой строки, затем объясняется порядок первого появления товара.
Данные файлового опыта вводятся при чтении соответствующего файла.
Вводная фраза «Разберём журнал поставок…» удаляется: задача уже задана
входом и результатом. Notes могут добавить неверное количество и предложить
объяснить, какая ранее накопленная сумма сохранится.

Отдельно проверяется смысл входящей ссылки. В конце раздела об исходах
[главы о потоках](../theory/chapters/streams.qmd#sec-j25-theory-streams-outcomes)
в проверенном снимке описаны `grade.Main input threshold`, участники и отказ
всего входа.
Цель ссылки — [приложение поставок](../theory/chapters/application.qmd#sec-j25-theory-application-behavior)
с одним аргументом и продолжением после неверной строки. Адрес существует,
но утверждение о его содержании ошибочно. Вариант согласованного перехода:

> Приложение поставок сохраняет принятые строки и собирает диагностику
> отклонённых. После полного чтения и закрытия входного файла оно выводит
> суммы. Отказ чтения или закрытия препятствует публикации отчёта.

Ссылка помещается у этого описания. Если пример с участниками нужен
самостоятельно, его договор определяется в собственном месте; ссылка
на другую программу не может служить его недостающим объяснением.

### Развитие модели ввода-вывода

Повторная рецензия пользователя открыла композицию всей лекции 9 и связанных
глав. Локальная связность примера поставок, разобранная выше, сохраняет
своё значение. До применения средств в приложении требуется самостоятельное
объяснение модели ввода-вывода, её развития и конкурирующих вариантов.

**Недостаточный вариант.** Перечень «`Path` задаёт путь, `Files` выполняет
операции, `InputStream` передаёт байты» пригоден для справочного поиска.
В основном объяснении он оставляет открытыми вопросы о разделении этих
понятий и сосуществовании прежних и новых средств. Совет «для файлов
используйте `Files`, для скорости — NIO» дополнительно приписывает всему
семейству API неустановленное преимущество. Даты перед прежней таблицей
не раскрывают связь между решениями.

**Предметный фрагмент.** `InputStream` позволяет алгоритму читать
последовательность байтов из файла, массива в памяти или сетевого
соединения. Алгоритм вызывает `read` и обрабатывает полученный результат;
выбор источника остаётся снаружи. Буферизующая обёртка может получать
крупные порции и выдавать их этому алгоритму понемногу. Удобство модели
состоит в едином последовательном ходе вычисления.

Для одного файла такой ход часто совпадает с самой задачей. У сервера
с тысячами медленных соединений появляется другое условие: большинство
соединений ждёт данные. Один вызывающий поток, остановившийся внутри
`read`, пока не может обслужить остальные. Отдельный платформенный поток
на соединение сохраняет последовательный код, но расходует ресурсы
потоков и во время ожидания. Выбор по готовности позволяет одному потоку
обслуживать несколько соединений; программа хранит состояние каждого
незавершённого обмена отдельно.

В NIO эту организацию поддерживают неблокирующие сокетные каналы и
селектор. Селектор сообщает о готовности попытаться выполнить операцию;
обработчик сам вызывает чтение и учитывает фактически полученную порцию.
Для файлов `FileChannel` даёт позицию и операции с буферами. Он не относится
к выбираемым каналам и не регистрируется в селекторе. Выбор канального API
и выбор способа ожидания — две связанные, но самостоятельные задачи.

**Авторское решение.** Фрагмент сначала объясняет, что даёт прежняя
модель. Новое условие меняет цену решения; последующий механизм отвечает
именно на это изменение. У вариантов остаются понятные области применения.
Сопоставление файлового и сокетного каналов опирается на разные возможности
типов. Документированные цели NIO устанавливаются отдельно по
[JSR 51, §§2.1–2.4](https://www.jcp.org/en/jsr/detail?id=51);
модель выполнения сверяется с контрактами
[каналов](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/channels/package-summary.html).

В лекции эта связь может занимать последовательные экраны с двумя
соединениями: первое ждёт данные, второе готово к работе. Notes предлагают
проследить остановку вызывающего потока и место хранения незавершённой
записи. Ответы остаются видны в основном тексте. Последующее объяснение
асинхронного API меняет событие уведомления: обработчик получает завершение
уже заказанной операции. Затем конкретное приложение позволяет выбрать
подход по его нагрузке и порядку обработки.

**Граница образца.** Этот фрагмент развивает одну связь между моделями.
Полная тема отдельно объясняет байты и символы, состояние буфера,
готовность и завершение, владение незавершённой операцией и файловую
модель NIO.2. Простое упоминание этих терминов не закрывает соответствующие
переходы. Сам образец не устанавливает новую обязательную сетевую задачу.

## Применение уточнённых правил

Фраза «В теории объясняется копирование ссылки; справочник содержит форму
вызова метода» использует согласованные названия учебных форм. Предложение
«Книга хранит признак выдачи читателю» в третьем образце описывает предметную
сущность `Book`. Его терминология сохраняется. В диагностике сборки уместно
«проект `theory`»; машинный ключ Quarto `book` остаётся буквальным.

В первом образце конкретный JDK указан рядом с командами компактного файла.
Версия задаёт условие запуска; дополнительная тема JDK preview здесь
не вводится. В рабочем отчёте «предпросмотр сайта» обозначает раздаваемый
результат сборки. Проверка свежести такого результата фиксирует исходный
снимок и сравнивает изменённый текст с конкретной страницей; одного сообщения
о запущенном сервере недостаточно.

Корневая карта связывает пять форм курса. Вход теории содержит оглавление
собственных тем, а отдельная презентация сохраняет ссылку возврата
«Курс Java». Эти элементы выполняют свои навигационные функции. Повтор
корневой карты в теории и второй одноимённый пункт рядом с названием сайта
не создаются.

Код `Box<T>` и связанные экраны передаются как один авторский набор:
текст устанавливает типовую связь и совместный доступ к книге, notes
организуют прогноз и разбор схемы. Sol получает код для проверки и конкретные
места для просмотра; изменение объяснения этой связи возвращается автору.
При переносе механизма в самостоятельную задачу опубликованное условие
определяет обязательный API. Наличие метода в демонстрации само по себе
не делает его обязательной сигнатурой студенческого решения.
