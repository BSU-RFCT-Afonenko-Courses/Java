## Проверочные критерии

| Критерий | Проверяемое понимание | Существенный дефект |
|---|---|---|
| Предмет и масштаб | Название всей лекции, группы и шага соответствует своему содержимому | Грамматически именное слово оставляет предмет неопределённым |
| Причинная связь | Понятны действующее средство, условие, операция и следствие | Результат сопровождается общими словами вместо механизма |
| Местный вход | Понятны данные, сущности, новый синтаксис и необходимые операции | Для понимания текущего вывода нужно искать отсутствующую предпосылку |
| Непрерывность опыта | Сохранены имена и состояния; новый опыт явно начинает новое состояние | Вывод требует невидимой замены исходных данных |
| Видимый рассказ | При закрытых notes восстановим предметный смысл в соответствии с функцией введения, объяснения или опыта | Существенное условие или отличие вариантов доступно только преподавателю |
| Сценарий notes | Прогноз, внимание, пауза и вероятная ошибка связаны с текущим экраном | Notes скрывают основание вывода либо только повторяют экран |
| Предметная точность | Различены язык, модель JVM, реализация и фактический запуск | Схема выдана за вывод инструмента или предполагаемая оптимизация за наблюдаемую |
| Полнота и формы | Сохранены глубина обобщений, самостоятельная теория, девять лекций и пять форм | Краткость устраняет необходимое понятие или его объяснение |
| Отображение | Код, схема, подпись и заметка читаемы и находятся при нужном состоянии | Обрезка, масштаб или неверная привязка мешают восстановить механизм |

Блокирующим считается неверное основное правило или неработающий обязательный
путь. Существенным — потеря причинной связи, входа, видимого условия или
читаемости. Мелким — локальная неточность без изменения понимания механизма.
Находка требует поиска функционально сходных случаев, а исправление —
перечитывания всей затронутой последовательности.

## Калибровка критериев

Новая методика пригодна для смысловой проверки. Она разделяет грамматику
и масштаб названия, требует прямой причинной связи и проверяет закрытые
notes. Требование восполнить смысл вместо замены слов распространяется
на новые случаи. Ниже зафиксированы собственные решения рецензента;
автору сначала переданы решение и причина, без переписывания учебного текста.

### Случай A: прежний экран профиля

«Профиль сообщает, куда вложить работу» с таблицей наблюдений и фразой
«Само число вызовов ещё не обещает конкретной оптимизации» — недостаточно.
Читатель узнаёт, какие данные собираются, но не восстанавливает, какое
средство использует их для выбора специализации и как установить решение
для конкретной нагрузки. Последнее скрыто в notes. Заголовок описывает
метафорическое действие вместо предметного механизма. Причина отклонения —
потеря положительной связи между наблюдением, решением и проверкой;
само наличие отрицания не является основанием отклонения.

### Случай B: `correctFirst` и `replace`

Вся последовательность с исходным `[5, 7]`, двумя кадрами, изменением
компонента до `[9, 7]` и последующим присваиванием нового массива параметру
достаточна. Читатель может найти две разные переменные, общий объект,
левую часть обоих присваиваний и причину результата `9` после обоих вызовов.
Начальное состояние второго опыта сохраняется явно. Notes переводят
типичную ошибку прогноза в поиск конкретного места записи. Краткое условие
«непустой массив» существенно для обращения к индексу `0`; отрицательная
форма этого условия не делает его стилистическим дефектом.

### Случай C: клонирование вложенного массива

Заголовок «Сохранение состояния», код клонирования `int[][]`, изменение
`saved[0][0]` и результат `original[0][0] == 9` вместе с объяснением
«Внутренние данные имеют иной статус, поэтому результат закономерен» —
недостаточно. Действие и результат видны, но «иной статус» не объясняет,
почему изменение достигает первоначального массива. Нужно восстановить
тип компонентов внешнего массива, копирование их ссылочных значений
и общий объект строки. Именно эта существенная связь спрятана в notes.
«Сохранение состояния» дополнительно не называет исследуемый механизм
поверхностного копирования. Дефект распознаётся без прежних словесных формул.

### Случай D: «Адаптивность»

Заголовок слишком широк для единственного экрана о восстановлении состояния
интерпретатора при нарушении предположения JIT. Именная форма соблюдена,
предметная точность и масштаб — нет. Здесь исследуется конкретный механизм
деоптимизации. Сам текст экрана отдельно не предоставлен, поэтому качество
его объяснения по одному заголовку не оценивается.

### Независимый новый случай E: вывод локального типа

Рецензент отдельно выбрал следующий мысленный экран с правильным предметным
заголовком «Вывод локального типа»:

```java
Object source = "Java";
var text = source;
System.out.println(text.getClass().getSimpleName()); // String
```

Видимый абзац: «Автоматический выбор опирается на доступную информацию;
имя класса отражает конкретное значение». Notes: «Назвать `Object`
как статический тип `text`, выведенный по выражению `source`;
`getClass()` показывает класс объекта».

Экран недостаточен, хотя код, вывод и название по отдельности допустимы
и знакомых неудачных формул здесь нет. При изучении `var` читатель видит
единственный явный ответ `String`, но не получает объяснения статического
типа `Object` и основания его выбора. Значение результата диагностического
вызова не заменяет объяснения вывода типа. Существенное различие находится
только в notes. Правило §14.4.1 связывает вывод с типом выражения
инициализатора; оно проверено непосредственно по
[JLS 25](https://docs.oracle.com/javase/specs/jls/se25/html/jls-14.html#jls-14.4.1).
Этот случай проверяет применимость критериев к иной теме и одновременно
показывает, что одного исправления заголовка недостаточно.

## Замечания к новым образцам

В первом чтении блокирующих предметных ошибок не обнаружено. Найдены
три существенных разрыва первого образца; второй и третий образцы достаточны
для калибровки в прочитанном исходном представлении.

### К1. Невидимое изменение исходника — существенное

Место: `docs/authoring-examples.md`, строки 92–107, последовательность
«Файл класса» → «Сохранённый результат компиляции».
Точная замена `IO.println("Hello")` на `IO.println("Changed")` находится
только в notes. На следующем экране написано «После замены строки
в исходнике», а новое значение появляется лишь как ответ в таблице.
Читатель вынужден восстанавливать действие по результату. Нарушены
критерии непрерывности опыта и видимого рассказа. Сам прогноз в notes
уместен, но не заменяет видимое состояние изменённого файла.

Устранено при повторном чтении: новые строки 101–102 явно называют замену
`Hello` на `Changed`, строки 119–120 — обратную замену и повторную
компиляцию. Прогноз в notes сохранил самостоятельную функцию.

### К2. Не введён действующий компилятор — существенное

Место: `docs/authoring-examples.md`, строки 134–146; также местный вход
теоретического фрагмента, строки 46–52.
На экранах после `javac` появляется «компилятор», которому помогают
счётчики и типы получателей. Видимый рассказ не определяет HotSpot как
реализацию JVM и не вводит JIT-компиляцию во время исполнения с результатом
в виде машинного кода. В теории употреблено название JIT, но эта связь
также не раскрыта. Читатель не получает достаточного основания отличить
участника текущего механизма от уже знакомого `javac`. Сопоставление
с `javac` в notes подчёркивает, что различие нужно текущему рассуждению.
Нарушены критерии местного входа и прямого объяснения.

Устранено при повторном чтении: новые строки 46–55 и 149–159 связывают
HotSpot с реализацией JVM, интерпретацию — с байткодом, JIT — с получением
машинного кода во время работы. Профиль относится к уже введённому средству.
Полная лекция сохраняет собственный качественный разбор этих механизмов.

### К3. Отсутствует видимый результат исследования байткода — существенное

Место: `docs/authoring-examples.md`, строки 80–132.
Показана команда `javap`, затем авторская схема стека и пересказ эффектов.
Фактические инструкции отсутствуют. Поэтому в образце, прямо предназначенном
для исследования класса и байткода, читатель не может сопоставить действие
исходника с полученной инструкцией и затем с её эффектом. Схема полезна,
но выполняет другую работу. Нарушены критерии видимого основания вывода
и предметного исследования результата инструмента. Замечание не требует
полного служебного дампа или универсального формата всех экранов.

Устранено при повторном чтении: новые строки 119–140 показывают инструкции
`ldc #7`, `invokestatic #9`, `return`, соответствующие исходнику и схеме
стека. Фрагмент непосредственно сопоставлен с `Hello.javap.txt`
технического исполнителя: операнды, смещения 0/2/5 и вызываемый метод
совпадают. Произвольная схема больше не является единственным видимым
основанием рассказа о байткоде.

### Достаточные решения второго и третьего образцов

Разбор передачи значения сохраняет `[9, 7]` между вызовами, различает
переменные разных кадров и объект массива. Заметки направляют прогноз
на левую часть присваивания и не подменяют объяснение на экране.
В контейнере типовая связь поля, конструктора и результата видна; альтернативы
с одинаковыми именами прямо обозначены; момент ошибки перенесён от
чтения к созданию. `Book` введён локально. Общая ссылка и смысл `final`
объяснены через разные объекты и конкретное поле. Эти решения можно
переносить по функции, сохраняя самостоятельную композицию других тем.

### Предметная и педагогическая оценка

Существенных разрывов в прочитанной последовательности не обнаружено.
Компактный запуск объяснён до явного класса. Запуск исходника и сохранённого

на `{9, 7}` и обратное восстановление видимы. Значения, необходимые для
трассировки, не переносятся только в notes.

Сохранена содержательная последовательность исходника, фактических инструкций,
локальных позиций, стека операндов и общего массива. Указано, что кадр `total`
принадлежит статическому методу и `pages` занимает позицию 0; схема разных
кадров не выдаётся за физическую раскладку памяти. Возврат из метода
отделён от достижимости объекта и работы GC.

HotSpot определён как реализация JVM. JIT получает машинный код во время
работы, профиль участвует в выборе работы и специализации; решение
конкретного запуска устанавливается по диагностике. Механизм больше
не заменён предостережением о числе вызовов. Сохранены встраивание,
прогрев, издержки памяти и компиляции, метрики, деоптимизация и ограничения
измерительного опыта. Условия качественного примера и фактическое
наблюдение различены.

Числовые опыты показывают момент переполнения и расширения, выбор деления
по типам операндов и двоичное округление. Явный класс и именованный пакет
введены для собственной задачи распространения. Теория объясняет JDK,
среду выполнения и поставку приложения с runtime image; пользователю
готового пакета не приписана обязанность устанавливать полный JDK.

Название лекции «Ссылочные значения» соответствует целому: начальная
«Семантика присваивания» является одним из предметных узлов, далее следуют

и операции, а не на ход рассказа. Видимые вопросы в учебных опытах

У присваивания и передачи аргументов явно различены переменная, её значение
и общий объект. Числовой опыт отделён от ссылочного. `correctFirst` и `replace`
используют последовательно один массив: после первого изменения сохраняется
`[9, 7]`, второй метод не возвращает и не присваивает новую ссылку переменной
вызывающего кода. Схемы двух кадров и места записи видимы. Сравнение с C++
различает `T&`, указатель и значение `std::array`; Python сопоставляется
по общему объекту, без приписывания ему статической модели Java.

При входе во вложенные массивы локально объяснён `int[][]`. Поверхностное
копирование создаёт внешний массив, а ссылки на строки остаются общими.
Следующие действия `copy[0][0] = 9` и `copy[0] = new int[]{1, 2}` проходят
по разным путям и имеют разные видимые результаты. Теория расширяет эту
модель перестановкой строк, копированием каждой строки, обработкой `null`
и отдельным требованием сохранить общность вложенных объектов. `final`
ограничивает присваивание переменной, не выдаётся за глубокую неизменяемость.

Строковый блок отделяет неизменяемость значения от обязательного создания
нового объекта. У `concat("")` прежняя ссылка обоснована контрактом;
у `strip()` утверждение ограничено значением результата. Непосредственно
сверены целевые описания этих методов и общая модель индексов в
[String API Java 25](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/String.html).
Схема `A😀B` показывает четыре единицы UTF-16, три кодовые точки и переходы
`0 → 1 → 3 → 4`. В теории явно отделено внутреннее хранение от контракта
индексации. Дополнение о нормализации не отождествляет кодовую точку
с воспринимаемым знаком. Полуоткрытый диапазон имеет точные границы.

Отсутствие объекта, пустая строка и неприсвоенная локальная переменная
различены результатом и моментом отказа. У Nullness Checker указан конкретный
импорт, участие анализатора, отличие от `javac -proc:none` и от выполнения.
Замена тела `length` объявлена видимо. Обработка `null` ветвью и выбор
результата `0` отделены от действия аннотации. В notes не обещается
устранение всех NPE во внешнем коде.

Сохранённые теоретические разделы проверены вместе с новыми входами:
числовое повышение до операции, определённое переполнение, порядок
вычисления, короткое замыкание, перегрузка, возвращаемая ссылка, varargs,
рекурсия, эффект частичного изменения при исключении, границы массивов,
поиск, сортировка и построение текста по исходным координатам. Ссылки
на справочник дополняют местный договор, а не заменяют его объяснение.

Notes первой и последующих проверок предлагают прогноз до открытия
результата, затем возвращают к месту записи и двум кадрам. Итоговая задача
с `String[]` соединяет копирование внешнего массива и замену строкового
компонента. Её ответ следует из уже показанных правил, а не из скрытой
оговорки. Соответствие заметок реальным экранам остаётся предметом
отдельного визуального прохода.

### Предметная глубина и местные объяснения

`ObjectBox` показывает потерю статического результата, приведение и
отложенный отказ; `Box<T>` связывает поле, конструктор и результат.
Альтернативы исходного опыта обозначены, неверные строки не предлагают
дописать к несовместимому варианту. У `Book` локально объяснено изменяемое
поле `borrowed`; `final` поля коробки и общность объекта рассмотрены отдельно.
Новый узел `var` различает выведение по контексту, отсутствие такого
контекста и явный аргумент конструктора. `getClass()` содержимого не
используется как доказательство сохранённого `T`.

Обобщённый метод имеет собственный параметр типа. Граница `Number`
разрешает `doubleValue`, не обещая оператор `+` или точность любых чисел.
Для порядка введён `Comparable<T>`; результат сравнения трактуется по знаку.
Строгая граница `<T extends Comparable<T>>` приводит к конкретному
ограничению на `Student`, гибкая `<T extends Comparable<? super T>>`
заменяет её явно, сохраняя нужный тип результата. Отказ не объясняется
неверным запретом сравнивать объекты разного класса.

Инвариантность, ковариантные массивы, неизвестный тип, верхняя и нижняя
границы раскрыты через разрешённое чтение и запись. `copy` имеет две роли
источника и получателя; указаны существующие независимые списки и способность
получателя принимать добавления. `List.of` не представлен изменяемым списком,
а типовая допустимость `null` отделена от договора реализации. Дополнительный
захват неизвестного типа сохраняет одну связь через именованный `T`.

Стирание, `Signature`, сырой тип, загрязнение кучи и мостовой метод сохранены
как разные механизмы. Непосредственно прочитан также `BoxClient.javap.txt`:
вызов стёртого `get(): Object` и клиентский `checkcast String` соответствуют
объяснению. Ограничения `new T()`, массивов параметризованных типов
и `instanceof` не объясняются произвольным расходом памяти. У `List<?>[]`
различены тип компонента массива и неизвестный тип элемента каждого списка.

Общее вычисление скалярного произведения сохранено во всех четырёх языках.
Названы равные длины, начальное значение, сложение и умножение; для комплексных
чисел выбран явно билинейный вариант без сопряжения. Java передаёт операции
через `Arithmetic<T>`; C++ ограничивает доступные выражения, но не доказывает
нейтральность `T{}`; C# задаёт операции через ограничения generic math;
Python отделяет обычное выполнение, аннотацию и статическую проверку.
Состояние счётчика умножений обосновывает дополнительный `Protocol`.
