# Публичные API Core и строгая типизация

По прямому уточнению пользователя от 7 ноября разрешены только `gpt-6.1-sol` и `gpt-6.1-terra`; роли и усилия задаёт обновлённая матрица. Учебный автор и независимый рецензент — разные Sol/high; ключевая архитектура и её независимая рецензия — разные Sol/max. Standard сохраняется.

Вы — N3, `gpt-6.1-sol/high`. Прочитайте [общее поручение](common.md). Владеете каноническими `quarto-course` и `quarto-course-performance`, включая Core/Presentation/Navigation, собственные tests/tools и проверяющую конфигурацию. Начинайте только после старта и READY N0.

## Вход и границы

Начальная закреплённая версия Java Core — `c62e6c877f769f33a9ffd6fe713811df75c794c6`; актуальный remote и Performance ref выдаёт N0. Локальные старые Core5/Performance с пользовательскими untracked docs не изменять. Установленные копии курсов и provider pins принадлежат N0.

Основные границы: `public.ts` → PL/Download/QRC/Site; `AnswerSpec`/`AnswerFacts`/`NativeResponseSlot`; AST и документные преобразования; Performance bridge ABI. Реальные остатки найдены в `document/answers.ts`, `normalize.ts`, `assignment-primary.ts`, `assignment-finalize.ts`, `catalogue-cite.ts`, `runtime/assignment-declarations.ts` и обёртках Performance. Это начальные адреса, полный собственный активный состав требуется инвентаризировать.

## Порядок

1. Составить конечный список поддерживаемых own source/tests/tools/entrypoints и публичных consumers; vendor/imported исключить из ручной правки. Производные исправлять через источник.
2. Описать и согласовать с N4/N5 упрощённый публичный договор. Использовать имеющиеся типы/схемы и узкие guards. Ключевой межрепозиторный дизайн и независимую Sol/max-рецензию выполнить до массовой адаптации потребителей.
3. Перед исправлением конкретного дефекта заказать N0 различающую проверку с ожидаемым отказом. Типовой отрицательный случай проверяет запрет неправильного вызова; runtime-случай — поведение и guards. Избыточные тесты на механическую аннотацию не писать.
4. Строго типизировать полный собственный активный состав. Удалять legacy после проверки прямых/косвенных callers и конфигураций. Не маскировать входы `as any`, широкими suppressions или параллельными неточными DTO.
5. Реализовать общую семантику раскрытого заголовка «Открытые примеры» существующим документным проходом. Старые ручные подписи удаляются N1 после согласования; собственный parser их распознавания не создавать. N4/N5 должны получить одинаковую семантику в PL/README.
6. Типизировать Performance wrappers с сохранением параметров, возвращаемого типа, синхронности/Promise и исключений. Единственный канонический template передать всем потребителям; ABI/отсутствующий агент сохраняют документированное поведение.
7. Заказать N0 штатные checks по свежим workflows: Core `npm run test:quick -- <evidence>`, `bash tools/check-core-early-slice-ts.sh`, `npm run test:navigation-model`; актуальные Performance commands уточнить по выбранному ref. Excluded Print/Cloud не оживлять старой полной командой.

## Выход и приёмка

Независимо принятые коммиты, конечная карта собственного кода/entrypoints, строгие проверки producer/consumer, новый публичный договор и список удалённых callers. Проверить manual/numeric/multipart/matching/choice, nested AST/таблицы/ссылки, public visibility и Performance wrappers. Ни число удалённых `any`, ни зелёный тест отдельной функции не заменяют полный согласованный охват.
