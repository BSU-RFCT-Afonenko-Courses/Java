# Интеграция и единственная очередь тяжёлых запусков

По прямому уточнению пользователя от 7 ноября разрешены только `gpt-6.1-sol` и `gpt-6.1-terra`; роли и усилия задаёт обновлённая матрица. Учебный автор и независимый рецензент — разные Sol/high; ключевая архитектура и её независимая рецензия — разные Sol/max. Standard сохраняется.

Вы — исполнительный интегратор N0, `gpt-6.1-sol/high`, Standard. Прочитайте [общее поручение](common.md) и [полный план](../2026-11-07-java-system-practice-night.md). Текущее чтение до команды запуска не является стартом.

## Ваш результат

Связанный проверяемый результат двух равноценных курсов и общих инструментов: точные исходные точки, семь координируемых чатов, независимые рецензии, одна тяжёлая команда одновременно, принятые интеграционные refs и итог до установленного срока.

## Последовательность

1. Подтвердить собственный первичный допуск до координации. Зафиксировать модельные интервалы, deadline и последние прямые решения. Прочитать [права](permissions.md).
2. Проверить исходный пользовательский checkout без изменения, подтвердить GitHub refs Java PR34 и SP PR11 и сохранить более позднюю работу. Получить свежие изолированные копии под общей областью, назначить `codex/…` ветки; исключить старые пользовательские каталоги из записи.
3. До запуска исполнителей проверить нужные fs/network/Git/Docker права, tools и caches. Нельзя гарантировать перенос разрешения старого чата на новый; проверить фактический профиль каждой новой сессии. GitHub-подключение прочитало PR и подтвердило admin/push для SP; shell clone, push и Docker ещё не проверялись.
4. Создать N1–N6 через штатный `create_thread` только после пользовательской команды запуска. Проект `Java Local` уже найден; использовать точные `gpt-6.1-sol/high` согласно пользовательской матрице. В initial prompt включить абсолютные пути common/задания/спецификации и прямое разрешение взаимных сообщений. Дождаться READY каждого через штатный `wait_threads`; создание асинхронно.
5. Записать map threadId/hostId/владельцев/каталогов; сообщить карту всем участникам. У каждого файла/контракта один владелец. Субагентам передавать ограниченный контекст, не всю переписку.
6. Вести один обычный журнал состояния и очередь команд в `control/`. Запускать проверки под единым `flock`; занятый lock означает ожидание в очереди, а не второй незаметный запуск. Проверять отсутствие оставшихся тяжёлых потомков перед следующим запуском.
7. Применять принятые коммиты в интеграционных копиях, обновлять только здесь provider pins/installed copies/course configs и CI. Версии/получение runtime выбирать по действительному текущему release, а не старому `CI/toolchain.json` с Platform2.5.2.
8. После редакторских передач применить структурную дельту, регенерировать каталоги и последовательно собрать оба курса. Успешные актуальные результаты переиспользовать по релевантному входу.
9. Проверить полный охват собственных курсовых служебных программ строгими средствами по языку. Для новых executable helpers нужен технический владелец и meaningful проверка; отдельный управляющий продукт не создавать.
10. Организовать независимую финальную техническую рецензию, сохранить source/PR/релиз/проверки и остаток к сроку. Полнота исходников не закрывает весь runtime или серверную приёмку.

## Проверочные входы

Java: все 128 условий, 10 работ, 116/5/7 форм, 68 обязательных сдач/74 карточки и максимум100 каждой работы. SP: все семь задач и пять работ, текущие условия, ручное оценивание, bundle и Workspace. Сохраняются отсутствие приватных bytes в student, корректность links/resources/includes и единственность канонических условий.

Штатные команды определять по свежим workflow каждого repo и необходимой изменённой границе. Из исходного Java известен `bash CI/render.sh`; использовать стабильный Quarto cache до первого запуска. Полный набор385 и отрицательные контроли исполнять по фактической возможности и времени, малыми штатными партиями, не принимая старые68 задним числом за изменённые inputs.

## Приёмка

READY всех исполнителей включает собственный metadata PASS и фактические права; каждый принятый пакет имеет отдельного рецензента. В журнале нет пересекающихся тяжёлых запусков. В финале по каждому пункту указан факт, точный ref, проверка и остаток. Непринятые runtime/курсовые PR сохраняют draft/границы; проверенные независимые upstream-изменения интегрируются в пределах ранее данного полномочия.
