# Общий план публикации банков Java и System Practice

Согласованный порядок от 20 октября 2026 года. Это единственный общий план
исполнения для обоих курсов. Предметные требования находятся в методиках
[Java](authoring-methodology.md#публикация-банка-заданий) и
[System Practice](https://github.com/BSU-RFCT-Afonenko-Courses/System-Practice/blob/codex/task-publication-methodology-20261020/docs/authoring-methodology.md#публикация-банка-заданий).
Исходный состав и особенности курсов сохраняют их планы:
[Java](course-revision-plan.md#публикация-банка-заданий-согласованный-порядок-от-20-октября-2026-года)
и [System Practice](https://github.com/BSU-RFCT-Afonenko-Courses/System-Practice/blob/codex/task-publication-methodology-20261020/docs/course-revision-plan.md#публикация-банка-заданий-согласованный-порядок-от-20-октября-2026-года).
Для другой машины предназначен [стартовый промпт](task-publication-start.md).

## Границы поручения

Нынешняя подготовка меняет только документы и обновляет существующие
[PR Java №18](https://github.com/BSU-RFCT-Afonenko-Courses/Java/pull/18)
и [PR System Practice №4](https://github.com/BSU-RFCT-Afonenko-Courses/System-Practice/pull/4).
Исполнение плана начнётся отдельным запуском по стартовому промпту.
Этот будущий запуск разрешает локальную переработку, проверки и новые PR
с реализацией. Слияние PR, выпуск общих инструментов, публикация в действующей
PrairieLearn, изменение Moodle, аккаунтов, ключей и настроек доступа требуют
отдельного поручения. До него независимые локальные этапы продолжаются.

Охват — весь действующий банк обоих курсов, сначала обязательные работы.
Исторические 26 карточек System Practice проходят отдельное сопоставление
по принятому решению ниже. Прежние этапы и свидетельства сохраняют границы;
лекции Java 1, 2 и 5 сохраняют принятый статус. Повторного общего утверждения
методики и нового педагогического пилота Java нет.

## Принятые решения

1. **Единица System Practice.** Отдельная задача даёт самостоятельный
   законченный результат внутри лабораторной. Подготовка, связанные
   представления и проверки могут составлять одну задачу; каждый файл
   или команда не становятся отдельной задачей автоматически.
2. **Исторические карточки.** Сопоставить 26 карточек с действующими задачами
   и содержанием курса. Совместимые пробовать объединить без повторов.
   Карточки, которые сейчас не используются и не соответствуют содержанию,
   удалять при переработке. Историю Git и прежние свидетельства сохранять.
3. **Запуск Java.** Простые задачи используют только JDK и явно описанные
   компиляцию и запуск через консоль. Сложные задачи, которым нужна система
   сборки, используют Gradle вместо Maven. Непрограммные задачи Java
   и задачи System Practice с оболочкой или Git не получают Gradle.
4. **Сеть.** Первоначальная подготовка загружает необходимые зависимости;
   предусмотренные локальные сборки и публичные проверки затем выполняются
   без загрузок. Реальный обмен с GitHub и сдача в PrairieLearn требуют сети.
5. **Оценка.** Автоматические проверки сочетаются с оценкой преподавателя.
   Для преподавателя действует единая базовая структура с критериями задачи.
   Подробная рубрика остаётся в преподавательских материалах; условие кратко
   называет необходимые дополнительные результаты или действия. Тесты
   следуют условию и не вводят скрытых требований; закрытые тесты и ответы
   не становятся публичными.
6. **PrairieLearn.** Два отдельных курса: Java и System Practice.
   Лабораторной соответствует оценочная работа, задаче — вопрос в её составе.
7. **Установленный Gradle.** Для задач с системой сборки Gradle уже должен
   быть установлен в среде. Wrapper и его файлы в комплект не входят.
   README содержит краткую предпосылку установленного Gradle, без руководства
   по установке. Исходный и студенческий комплекты минимальны; производные
   файлы, которые Gradle воспроизводимо создаёт сам, генерируются при работе.
   Совместимую версию проверяет технический исполнитель; выбор Wrapper
   больше не является открытым вопросом.

Проекты группируются по темам QMD с каноническими условиями; для Java —
`tasks/projects/<theme>/<task>`. Основная раздача — архив одной задачи;
поздний архив лабораторной собирается из тех же источников. У общего
компонента строго один канонический исходник; необходимые копии общих
компонентов в ZIP генерируются. Это не основание заранее включать
воспроизводимые результаты сборки. Зависимости решения, публичных проверок,
закрытой оценки и платформы описываются раздельно.

ID имеют вид `exr-<theme>-<semantic-name>`, без `j25`, дат и версий.
Текущие ссылки, профили и экспорт обновляются согласованно в одной дельте.
Псевдонимы, перенаправления и таблицы обратной совместимости не создаются.
Сохранность внешнего входа в курс и связи Moodle не закрепляет прежние ID.
Все восемь правил студенческого представления из методик обязательны.

## Роли и модельный допуск

Таблица — единственный нормативный источник ролей для этого плана.
Справочная копия пар в стартовом промпте сверяется с этой таблицей.
Правила применяются только к данной линии публикации и имеют приоритет
над прежним общим назначением технической работы на `high`.

| Роль | Модель | Усилие | Граница ответственности |
|---|---|---|---|
| Координатор | `gpt-6.1-sol` | `high` | Управляет очередью, владением, передачами и основаниями готовности; не подменяет содержательную рецензию. |
| Архитектор | `gpt-6.1-sol` | `xhigh` | Задаёт контракты компонентов, организацию исходников, зависимости, сборку и экспорт; реализации кода не выполняет. |
| Автор и методист | `gpt-6-astra` | `ultra` | Определяет учебные результаты, единицы задач, условия и критерии оценки; выполняет содержательную и стилистическую редактуру. |
| Независимый содержательный рецензент | `gpt-6-astra` | `ultra` | Проверяет законченный текст другого автора, сохранность целей и обязанностей студента; не принимает собственную редактуру. |
| Технический исполнитель | `gpt-6.1-sol` | `medium` | Пишет весь код: стартеры, эталоны, тесты, Gradle, общую поддержку и экспортёр; собирает выдачу, выполняет проверки и подготавливает Git/PR. |

Вся первоначальная реализация кода в этой линии принадлежит техническому
исполнителю. Автор задаёт учебный замысел, условия и ожидаемое поведение,
затем содержательно проверяет результат; архитектор задаёт контракты
компонентов без реализации. Прежнее назначение первоначального учебного
кода Astra в этом плане не применяется. Изменения условий и допустимых
решений возвращаются автору и независимому содержательному рецензенту.

При каждом создании агента явно задаются `fork_turns="none"`, `model`
и `reasoning_effort` по таблице. Название роли и настройки родителя
не подтверждают нужный запуск. Каждый исполнитель до своей работы
проверяет собственные первичные `session_meta` и `turn_context`: ID чата,
при наличии путь агента, модель, усилие и ID начального хода; настройки
режима совместной работы должны быть согласованы с выбранной парой.

Исполнитель сохраняет собственный ID, начальный ход и свидетельство
в рабочей области текущей машины. После возобновления и перед приёмкой
проверяется весь интервал от исходного хода; начало не сдвигается.
Отсутствие данных или несовпадение останавливает соответствующую роль.
Старый проверяющий инструмент с ограниченным набором допустимых усилий
не разрешает заменить ожидаемые `xhigh` или `medium` на другое значение.
Проверка должна поддерживать точные пары этой таблицы. Локальная утилита
прежнего компьютера и изменение глобальной конфигурации не требуются;
глобальную конфигурацию моделей менять нельзя.

При четырёх доступных местах роли работают волнами. Сначала — координатор,
архитектор, автор и технический исполнитель. После архитектурной передачи
архитектор освобождает место независимому рецензенту. Дальнейшая волна —
координатор, автор, рецензент и технический исполнитель. Архитектор
возвращается адресно при освобождённом месте; пять ролей одновременно
не запускаются. Модель работающего агента молча не заменяется.

## Владение и передача

Координатор ведёт для каждого набора фазу, точные пути, владельца и исходный
снимок. У файла в одной фазе один владелец. У общих конфигурации, поддержки
и экспорта один технический исполнитель; содержанием условий и рубрик
владеет автор. Рецензент читает согласованный снимок и передаёт замечания,
не редактируя принимаемый текст. Правка учебной цели, обязательного приёма
или обязанностей студента возвращается автору.

Передача содержит законченный результат, точный коммит или состав файлов
с хешами, изменения, зависимости, выполненные проверки и открытые ограничения.
Владелец явно освобождает файлы до следующей фазы. Координатор принимает
свидетельства соответствующих ролей; автор не принимает собственный текст.
Замечание закрывается на исправленном снимке адресной повторной проверкой.

## Фазы исполнения

| Фаза | Вход и ответственные | Результат передачи | Условие перехода |
|---|---|---|---|
| 0. Вход | Координатор проверяет свой допуск; технический исполнитель получает свежие базы обоих репозиториев и PR | Точные коммиты, сохранённая пользовательская работа, изолированные деревья, область и владельцы | Подтверждены обе базы и модельные допуски; выбранные документы содержат последние решения |
| 1. Состав и контракты | Автор читает весь актуальный банк; архитектор изучает структуру; технический исполнитель выполняет ограниченную техническую пробу | Реестр обязательных и остальных задач, границы System Practice, решения по 26 карточкам, договоры входов и результатов, архитектурная передача | Другой содержательный рецензент подтверждает единицы и сохранность учебных целей; техническая проба подтверждает осуществимость без нового педагогического пилота |

| 3. Обязательные работы | Автор готовит небольшие тематические партии по принятой основе; другой рецензент читает; технический исполнитель реализует и проверяет выдачу | Принятые условия, преподавательские рубрики, решения и проверки, архивы задач, страницы и экспорт обязательных работ | Каждая партия проходит содержание и стиль, затем применимые проверки ниже на одном итоговом снимке; смысловые технические изменения возвращаются автору |
| 4. | 5. Фактическая PrairieLearn | Координатор уточняет оставшиеся настройки и внешний доступ; технический исполнитель проверяет импорт и действия студента; автор и другой рецензент проверяют учебное представление | Два курса с подтверждённым объёмом импорта и сдачи либо точный перечень ещё открытых внешних проверок | Выполнены восемь правил представления и реальные действия студента; ограничения Windows, GitHub и доступа названы отдельно |

Фаза 1 определяет границы задач по уже выбранному принципу самостоятельного
результата; этот принцип заново не выбирается. В фазах 3–4 последовательность
внутри партии: авторство → независимое чтение содержания и стиля → техническая
выдача и проверки → адресное возвращение обнаруженных смысловых изменений.
После архитектурной передачи фаз 1–2 архитектор не требуется постоянно.
Результат каждой партии можно оформлять отдельным реализационным PR после
применимых проверок; завершения внешней фазы для независимого PR не требуется.

## Проверки результата

Технический исполнитель проверяет применимые случаи на точном снимке;
непрограммные задания не получают фиктивных проверок компиляции.

- Стартовый проект компилируется и запускается в пределах обещанного
  сценария, оставаясь незавершённым. Эталонное решение проходит проверки;
  характерные ошибочные решения отвергаются с предметной диагностикой.
  Публичные и закрытые проверки наблюдают опубликованный договор задачи.
- Распакованный студенческий архив содержит нужные исходники, данные,
  открытые проверки и используемые инструкции. Эталоны, закрытые тесты,
  ожидаемые ответы и личные данные в него не попадают. Каждая ссылка
  на README или ресурс ведёт к действительно доступному материалу.
- Первичная подготовка получает зависимости, затем локальная сборка
  и публичные проверки выполняются без загрузок. Простые Java-задачи
  проверяются через JDK и консоль; сложные — установленным Gradle.
  В комплекте нет Wrapper и заранее размноженных результатов сборки.
- Запуски на рабочей системе, в контейнере и CI имеют отдельные результаты.
  Поддерживаемые действующим проектом профили проверяются по их назначению;
  успех одного окружения не подтверждает остальные. Для System Practice
  отдельно проверяются PowerShell 7/Windows, fish/Linux и реальный GitHub
  по SSH. CachyOS и локальный удалённый репозиторий не закрывают эти границы.
- Публичный сайт, скачиваемые файлы и экспорт сверяются с теми же исходниками.
  Проверяются ссылки, ресурсы, оформление кода и примеров, отсутствие закрытых
  материалов и служебных вставок. Повторяющийся дефект устраняется в источнике
  генерации; готовая страница не становится независимым исходником.
- В PrairieLearn проверяются фактические условие и действия: открыть ссылку,
  скачать комплект, предъявить решение настроенным способом и прочитать
  обратную связь. Библиографический аппарат и инфраструктурные преамбулы
  не генерируются; необходимые ресурсы и предметные условия сохраняются.
  Наличие HTML или экспорта не заменяет просмотра студенческого интерфейса.

Координатор раздельно фиксирует пять состояний: **исходники**, **скачиваемый
комплект**, **экспорт**, **импорт на сервер**, **сдача студентом**. Каждое
состояние имеет свой состав, снимок, проверку и ограничения. Экспорт одного
набора не объявляется публикацией всего банка. При отсутствии внешнего
доступа первые три состояния могут быть готовы, а последние остаются открытыми.

## Оставшиеся решения

Перед зависимыми настройками PrairieLearn уточняются число попыток,
порядок повторной сдачи, баллы, веса и сочетание автоматической оценки
с оценкой преподавателя в итоговом результате. Координатор предлагает
короткое меню с кириллическими вариантами и возможностью ответить строкой
вида `8А 9Б`. Номера продолжают уже принятые решения 1–7; варианты описывают
только оставшийся выбор. Неопределённый ответ задерживает зависимое действие,
независимая работа продолжается. Установленный Gradle, структура двух курсов,
границы задач и методика повторному согласованию не подлежат.

Совместимые версии и детали технической реализации устанавливаются
проверкой текущих инструментов. Этот план не задаёт вымышленных версий,
нового общего runtime или заранее выбранного API будущей реализации.
