# Получение исходной позиции

Команды ниже выполняются в Bash или совместимой оболочке в выбранном вами рабочем каталоге. Обязательных абсолютных путей прежней машины нет. Внешний архив содержит копию этих документов, `Java.bundle`, итоговые `PUSH-STATUS.md`, `GIT-STATUS.json` и контрольные суммы. После клонирования читайте канонические документы из `Java/docs/handoff/2026-10-15/`.

## Через GitHub

```sh
git clone https://github.com/BSU-RFCT-Afonenko-Courses/Java.git
cd Java
git switch --track origin/codex/java-course-pilot
git status --short
git rev-parse HEAD
```

При настроенной SSH-аутентификации вместо HTTPS допустим URL `git@github.com:BSU-RFCT-Afonenko-Courses/Java.git`. Право последующей отправки изменений и способ аутентификации на новой машине проверяются отдельно; SSH-ключи и токены в пакет не входят.

Если клон уже существует, сначала сохраните его незакоммиченные изменения, затем выполните `git fetch origin` и проверьте `git branch -vv` и `git status --short`. Переключайтесь на существующую локальную ветку пилота либо создайте tracking-ветку, если её ещё нет. Не сбрасывайте существующую ветку и не перезаписывайте чужие изменения ради совпадения со срезом.

## Из автономного архива

Сначала сверьте файлы внешнего архива с `SHA256SUMS` доступной утилитой SHA-256. Затем, находясь рядом с `Java.bundle`, выполните:

```sh
git clone --branch codex/java-course-pilot Java.bundle Java
git -C Java bundle verify ../Java.bundle
git -C Java remote set-url origin git@github.com:BSU-RFCT-Afonenko-Courses/Java.git
cd Java
git status --short
git rev-parse HEAD
```

Bundle переносит историю Java и все переданные ветки, перечисленные в `GIT-STATUS.json`. Ключевые ветки: `master`, `codex/labs-1-3-prairielearn`, `codex/java-course-pilot`, `codex/java-authoring-integration-20261014`, `codex/windows-device-ca`. Он не переносит внешние репозитории инструментов, пакеты ОС, авторизацию и конфигурацию действующего развёртывания. При появлении сети выполните `git fetch origin` и сравните актуальные refs с переданным срезом.

## Проверить состояние и начать ветку полной редакции

`GIT-STATUS.json` и `PUSH-STATUS.md` во внешнем архиве фиксируют финальные SHA и факт прямой проверки удалённых веток после передачи. Сравните с ними `git rev-parse HEAD`. Принятый учебный пилот `62b7c8a272976a0eb6f002f3f92e34809456f779` должен оставаться предком полученного HEAD:

```sh
git merge-base --is-ancestor 62b7c8a272976a0eb6f002f3f92e34809456f779 HEAD
git log -5 --oneline
git ls-remote --heads origin
```

Последняя команда требует сети; первые две доступны автономно. Если удалённая ветка после передачи продвинулась, прочитайте новую дельту и сохраните её; несовпадение не является основанием для автоматического reset. Перед технической интеграцией проверьте свежие `master` и PR #14. В передаче `master` подтверждён прямой SSH-проверкой как `eb1badca7d9879e2c3fe1e7a9fdb27c99a57e844` на `2026-10-15T09:55:18Z`; это merge PR #10, уже содержащий merge PR #6 (`3aebd0da122f3d40ce922a2911772e799a7dc915`) как первого родителя. Прежняя запись `3aebd0d` как текущего master в исходном аудите была ошибочной.

После чтения [START.md](START.md), [CONTEXT.md](CONTEXT.md) и [PLAN.md](PLAN.md) создайте свободную рабочую ветку `codex/` от полученного пилота. Например, если такого имени ещё нет:

```sh
git switch -c codex/java-course-full-revision
```

## Среда для последующих проверок

Источники технических требований — [CI/toolchain.json](../../../CI/toolchain.json), [CI/render.sh](../../../CI/render.sh), [UPSTREAM.md](../../../UPSTREAM.md) и [документация пилота](../../java-course-pilot.md). В исходной позиции указаны Quarto `1.11.5`, CUE `0.17.1` и JDK 25 без preview. Сверяйте их с полученной веткой; установка окружения ещё не означает прохождения проверки.

Настройте `JAVA_HOME` и доступ к JDK 25 обычным для своей ОС способом. Если CUE находится в `PATH`, переносимая форма запуска из корня курса такова:

```sh
export CUE="$(command -v cue)"
java --version
javac --version
quarto --version
"$CUE" version
bash CI/render.sh full student
```

Проверьте, что `CUE` не пуст и версии соответствуют выбранной конфигурации. Сначала нужна независимая содержательная рецензия законченных новых исходников; рендер проверяет уже подготовленное состояние. К сборке каждой текстовой правки отдельно возвращаться не требуется. Команды здесь описывают будущую проверку: handoff не выполнял новую сборку курса.

Для перестройки поставки PrairieLearn понадобятся дополнительные компоненты и доступы из [EXTERNAL-DEPENDENCIES.md](EXTERNAL-DEPENDENCIES.md). Их отсутствие не мешает начать согласованную редактуру текста.
