## Непрерывность Moodle → UID → курс → учреждение

### Личность и границы доверия

В прочитанном Gateway `identity_key = digest([issuer, clientId, deploymentId, sub])`, а PL UID имеет вид `gw-<identity_key>@example.invalid`. Поэтому при неизменной четвёрке два входа должны адресовать одну личность; изменение любого её элемента потенциально создаёт другой UID. Это вывод из [строк 69–74](https://github.com/Afonenko-Course-Tools/moodle-prairielearn-gateway/blob/44f5c2116470e37180050f1eba1ab230ab4794d7/src/gateway/launch.py#L69-L74), который ещё нужно сопоставить с фактическим историческим механизмом входа. Нельзя предполагать, что прежняя установка использовала именно этот ref/алгоритм.

LTI 1.3 определяет `sub` как устойчивый локально уникальный в пределах `iss` идентификатор; имя и email не заменяют эту идентичность. `deployment_id` и `resource_link.id` имеют собственные области уникальности; копирование активности может изменить resource link. Поэтому визуально та же Moodle-ссылка, одинаковое имя, email или номер native course недостаточны для принятия карты. [Официальная спецификация LTI 1.3, §§5.3.3–5.4.1](https://www.imsglobal.org/spec/lti/v1p3/), обращение 05.11.2026.

Для будущей разрешённой сверки оператор составляет **закрытую одноразовую карту**, вне Git и публичного отчёта. Предлагаемый минимальный состав:

| Связь | Что сверяется по фактическому readback | Условие допуска |
| --- | --- | --- |
| Moodle user → LTI identity | Внутренний Moodle user ID; исходные `issuer/client/deployment/sub`; используемый auth/provider; источник и дата подтверждения | Одна реальная личность однозначно соответствует прежнему UID. Ни имени, ни email для автоматического слияния недостаточно. |
| LTI activity → Gateway course | `contextId`, `resourceLinkId`, точный target, зарегистрированный course key; роль; существующий grade binding при наличии | Отказ чужому/неизвестному контексту или курсу. Отсутствие AGS в login-only пути не ослабляет подпись, state/nonce/TTL/replay/CSRF/course/role guards. |
| Gateway identity → PL user | Старый и новый UID, native numeric `user.id`, фактическая принадлежность старых attempts/submissions/files | Повторный вход не создаёт дубль и сохраняет владельца прежних данных. Teacher не получает студентские полномочия автоматически и наоборот. |
| Registry/delivery → PL course instance | Source course key/UUID; actual native course ID/path; instance key/UUID и actual native CI ID; binding и delivery hash | Указатель на тот же подтверждённый контекст либо отдельная явно проверенная old→new карта. Название и один UUID вопроса всей цепочки не доказывают. |
| SP → native institution | Registry `institution` key, descriptor, actual `courses.institution_id` и соответствующая native institution | Подтверждён именно SP course. Утверждение «в config есть БГУ» недостаточно. |

Результат публичной сверки содержит только числа строк, числа неоднозначностей, точные refs и итог условий; реальные UID/имена/вложения остаются в закрытом пакете. Секреты, JWT, cookies, token, password и DSN в карту соответствий и Git не включаются. Секретные файлы резервируются отдельно с сохранением доступа, без печати их содержимого.

В frozen Bridge `context()` проверяет зарегистрированный `courseKey/instance`, существующий CI, совпадение CI UUID с `infoCourseInstance.json`, затем существующего user по UID. `enrollBasic()` отклоняет blocked enrollment и отсутствие native Student access; [строки 357–390](https://github.com/Afonenko-Course-Tools/prairielearn-platform/blob/728830780925ac10519db4325065b85152a94b7a/bridge/server.mjs#L357-L390) возвращают лишь enrollment evidence. Доверенный адрес списка лабораторных и согласованный новый login-only контракт проверяет владелец Gateway на актуальной дельте; старый ответ `enrolled:true` сам этого не доказывает.

### SP и учреждение

Versioned [institution catalog](https://github.com/Afonenko-Course-Tools/prairielearn-platform/blob/728830780925ac10519db4325065b85152a94b7a/config/institutions.json) задаёт `bsu`, БГУ, `Europe/Minsk`, `uidRegexp:null`. [Bootstrap](https://github.com/Afonenko-Course-Tools/prairielearn-platform/blob/728830780925ac10519db4325065b85152a94b7a/tools/institution-bootstrap.mjs#L32-L64) разрешает numeric institution ID через native models и отказывает при несовпадении descriptor или учреждения существующего курса. Он не переносит существующий курс между учреждениями. Каталог учреждений не содержит SSO registration и не меняет LTI subjects — это отдельно зафиксировано в [операторской инструкции](https://github.com/Afonenko-Course-Tools/prairielearn-platform/blob/728830780925ac10519db4325065b85152a94b7a/docs/proxmox-pilot.md#L90-L149).

Следовательно, для пятничного просмотра можно показать новый изолированный SP course под проверенным descriptor. Принадлежность прежнего SP course, его enrollment/attempts и перенос в правильное учреждение остаются отдельными неподтверждёнными фактами. Если обнаружен Default/pilot или другой institution, остановить эту строку карты; не исправлять `institution_id` прямым SQL и не удалять pilot. Нужна отдельная проверенная административная операция, сохраняющая пользователей и историю. Прежнее описание Moodle-элемента SP в `docs/two-courses.md` — историческая возможность, а не действующее требование: [решение 79](../refactoring-plan.md#decision-79) снимает обязательность Moodle для SP.

## Резервирование и реальная проверка восстановления

Это план следующего назначенного владельцу этапа. Автор стратегии не выполняет его и не заявляет PASS по прежнему отчёту.

1. **Установить источник и момент согласованности.** Оператор подтверждает фактические приложения, версии PostgreSQL/SQLite/Moodle, расположения file stores/volumes и состояние writers. Проверяет сохранённое разрешение и актуальное состояние остановки: [решение 80](../refactoring-plan.md#decision-80) — историческое поручение остановить сервис, не доказательство сегодняшнего состояния. До capture согласованно завершаются либо сохраняются jobs/workspaces и очереди; неизвестный исход операции выясняется до повтора.
2. **Снять полный согласованный checkpoint.** Для PL нужен backup PostgreSQL плюс все фактические внешние файлы/объекты, workspace state и конфигурация. PostgreSQL `pg_dump` даёт согласованный снимок одной БД; global roles/tablespaces в него не входят, selective dump может исключить large objects. Формат и версии выбираются под установленную систему; для разового переноса кандидат — полный custom archive и отдельный учёт globals, не самостоятельная политика production backup. [PostgreSQL 18: pg_dump](https://www.postgresql.org/docs/18/app-pgdump.html), обращение 05.11.2026. Консистентность PostgreSQL и внешних файлов требует общего checkpoint приложения; один dump этого не обеспечивает.
3. **SQLite резервировать штатно.** Использовать проверенную текущей версией SQLite backup API/штатный helper либо согласованную остановленную копию со всем необходимым journal/WAL состоянием. Не считать одиночный `cp` живого `.db` доказанным backup. [SQLite Online Backup API](https://sqlite.org/backup.html), обращение 05.11.2026. При копировании уже имеющегося backup честно сохранить его исходный capture ID: это новая копия, а не свежий backup сервера.
4. **Если позднее разрешён backup исходной Moodle, сохранить весь сайт.** Нужны database, `moodledata` и code/plugins/config в согласованном состоянии. `.mbz` курса или новая тестовая Moodle не являются полным восстановлением старой установки. В этом окне оригинальная Moodle не читается. [Официальный Moodle Site backup](https://docs.moodle.org/503/en/Site_backup), обращение 05.11.2026; применимость проверяется по фактической версии.
5. **Восстановить в новое изолированное назначение.** Сначала сохранить frozen checkpoint без записи; создать отдельную рабочую копию, отдельные БД/files/volumes и loopback доступ. Запретить исходящие AGS/email/webhook/production callbacks и разделить writable mounts. Сначала проверить восстановление старой совместимой версией приложения, затем на отдельной копии — кандидатом с нужными schema migrations. Секреты подаются закрыто, содержимое не выводится. PostgreSQL custom archive восстанавливается через штатный `pg_restore`; его exit code, stderr и фактический readback сохраняются. [PostgreSQL 18: pg_restore](https://www.postgresql.org/docs/18/app-pgrestore.html), обращение 05.11.2026.
6. **Сверить содержимое, затем поведение.** Для SQLite проверить schema version, `integrity_check` и отдельно `foreign_key_check`: integrity не проверяет FK. [SQLite PRAGMA](https://www.sqlite.org/pragma.html#pragma_integrity_check), обращение 05.11.2026. Сопоставить DB row counts/owner joins, признанные успехи, manual/best, историю, bytes/size/hash файлов и manifest; отдельно отсутствующие/orphan references. Счётчики сами по себе не доказывают принадлежность. На изолированной копии через native API/UI проверить собственные загрузки файлов и запрет чужих/anonymous; старт/сохранение/закрытие/возобновление SP Workspace там, где нужно.
7. **Зафиксировать разные результаты раздельно.** `backup создан`, `байты/manifest сверены`, `старое приложение восстановлено`, `кандидат прошёл репетицию` и `Moodle/AGS фактически проверены` — отдельные статусы с refs, командами, exit/error и временем. Любое отсутствие свидетельства остаётся «не проверено». Документация PrairieLearn сама не описывает полноценный production backup; пример запуска контейнера не восполняет этот пробел. [PrairieLearn production setup](https://docs.prairielearn.com/running-in-production/setup/), обращение 05.11.2026.

Существующий [source-план Platform](https://github.com/Afonenko-Course-Tools/prairielearn-platform/blob/728830780925ac10519db4325065b85152a94b7a/docs/recognized-credit-native-plan.md) ссылается на backup identity `bc320d59ce606cb013929962a5bc35a2ef605bc69ff99b0fffb61ca816ee3c60` и evidence c81f; отдельно помечает rollback copy как не запускавшуюся. Автор стратегии эти backup/БД не открывал. Это безопасная подсказка оператору для адресной проверки происхождения и пригодности, **не подтверждение свежести, полноты или восстановления**. Требование текущего состава исходников/образа нельзя закрывать старыми hashes.

## Репетиция переноса зачётов и файлов

Существующий кандидат реализации — [Platform recognized-credit](https://github.com/Afonenko-Course-Tools/prairielearn-platform/blob/728830780925ac10519db4325065b85152a94b7a/docs/recognized-credit.md), `tools/recognize-credit.mjs`, `bridge/recognized-credit-native.mjs` и private-file helper. Это ограниченная административная операция с audit/score events и native aggregate, без подделки student submission. Документ источника прямо сообщает: SQL не исполнялся, реальный student download ACL не доказан, прежний target252/c81f не содержит новых hooks. Локальный source PASS нельзя выдать за рабочую миграцию.

После подтверждения actual mapping оператор на изолированной копии проверяет:

- Успешная старая автоматическая попытка → полный признанный current IQ: обычный mixed 80+20 и manual-only 0+100, с пояснением происхождения. Старые raw answers/jobs/dates остаются прежними. Прежний best/manual не уничтожается.
- Совпадают source UID/user/course/CI/assessment/AI/IQ/question/AQ и соответствующие UUID; destination выбран из фактического экспорта. Старый вопрос не сопоставляется по названию, номеру слота или «похожему» решению. Отсутствующий selected IQ даёт `NEEDS_NATIVE_ADMIN_EVENT` ([код](https://github.com/Afonenko-Course-Tools/prairielearn-platform/blob/728830780925ac10519db4325065b85152a94b7a/bridge/recognized-credit-native.mjs#L54-L61)); подмена альтернативным вопросом запрещена, административная материализация ещё требует реализации/квалификации.
- Private source references из `raw` и `submitted_answer`, включая Workspace `_files`, сохраняются полностью. Проверяются owner joins и байты до записи, destination `student_upload` и настоящий download под владельцем. Admin `getFile` не доказывает Student ACL. Проверяются чужой user/AI/IQ, anonymous и deleted/notes=false отказы.
- Повтор той же одобренной строки карты не дублирует event/job/file/ACL или баллы. При неизвестном результате upload сначала readback, затем отдельное решение о повторе; возможный orphan не удаляется автоматически.
- Новая неверная/неоцениваемая попытка, новый variant, recompute и sync maxima не отзывают признанный результат, не начисляют его другому IQ и не создают фиктивный успех новой submission. Проверяются смешанный AI, обычный непризнанный IQ, закрытый и открытый контекст.
- Native course/CI access, изменённый Bridge enrollment/catalog и сохранение UID проверяются независимо от административного зачёта. Java PL/Gateway/Moodle grade/completion readback — отдельный integration case; отсутствие AGS не должно блокировать проверенный login-only вход. Если передача баллов отложена, это явно отражается в приёмке, без ложного утверждения о согласованности Moodle.

Карта разовая и ограниченная; новый постоянный сервис/реестр зачётов не предлагается. Даже успешная репетиция с fictional accounts подтверждает поведение механизма, но не правильность realUID или полноту фактической карты студентов.

## Пятничный просмотр, переключение и откат

### Что предъявить вечером 6 ноября

Для локального PL, Gateway/Bridge и собственного непроизводственного Moodle fixture назначаются отдельные владельцы. Для показа нужен точный согласованный source/runtime/delivery набор, native список **10** лабораторных, реальные editor/ZIP сценарии и SP upload/Workspace по соответствующим договорам. У локального стенда должен быть явный адрес и отдельный статус готовности, полученный от владельца после запуска; данный read-only документ адрес и готовность не устанавливает.

Пакет просмотра содержит: refs/receipts, что исполнено на локальном стенде; отдельный статус existing Moodle identity; таблицу нерешённых соответствий; manifest и результат restore rehearsal, если его владелец действительно выполнил; перечень блокеров для cutover. Новая Moodle fixture проверяет протокол/изолированные роли. Она не доказывает прежнюю registration и не разрешает вход от имени основных студентов; [решение 79](../refactoring-plan.md#decision-79) требует использовать существующие разрешённые записи. Приведённый в старой Platform документации пункт о двух actual students не возобновляет снятое требование отсутствующих тестовых аккаунтов.

### Условия следующего разрешённого cutover

Переключение следует после пользовательского просмотра, независимой приёмки согласованной дельты и назначения конкретного разрешённого окна. Вечер 5 ноября разрешает подготовку локального основания и стратегии; этот документ не выполняет production deployment. Перед cutover должны быть одновременно закрыты:

1. Однозначные real identity/course/institution карты либо явный список отложенных строк; ни одному неизвестному UID/учреждению не присвоен PASS.
2. Полный checkpoint с проверенными manifests, успешным изолированным восстановлением нужной версии и измеренной длительностью rollback. Числовые RPO/RTO сейчас не заданы: оператор измеряет репетицию и фиксирует приемлемое окно до действия. Новые принятые ответы при rollback должны сохраняться.
3. Согласованный Gateway↔Bridge contract и точные refs; security guards и чужие course/role отказы; установленный native доступ к списку лабораторных. Нет скрытой зависимости login-only от worker/AGS.
4. Проверенный путь признания результата/файлов на actual установленном кандидате либо честное откладывание этих записей с сохранёнными исходниками и запретом выдавать перенос за завершённый.
5. План одного writer каждого изменяемого scope, контроль AGS/outbox, выбранный rollback checkpoint и отсутствие одновременного приёма в старую и новую инсталляцию.

Порядок: заморозить приём/зафиксировать in-flight состояние → сделать финальный согласованный checkpoint → сохранить старый release/config/данные отдельно → применить только принятый состав к изолированно проверенному назначению → выполнить readback UID/course/institution и необходимой карты → проверить owner ACL/native список/сохранённые результаты → открыть приём → наблюдать новые writes и очередь. Если разрешён только локальный просмотр, остановиться на локальном стенде; production шаги остаются планом.

### Откат без потери новых ответов

Триггеры остановки приёма: новый/чужой UID, неверный курс или учреждение, доступ к чужим файлам, потеря ответа/признанного зачёта, несогласованный schema/runtime, неисправность grading/очереди с неизвестным исходом. Инфраструктурный отказ показывается отдельно от student 0.

Сначала остановить новых writers и outbound AGS; сохранить состояние нового стенда **после** переключения отдельным checkpoint: новые submissions/files/workspaces, audit, outbox и статусы отправок. Не откатывать БД поверх этого состояния и не запускать слепой retry. Затем вернуть согласованный старый release с его проверенным backup в отдельное назначение и восстановить маршрутизацию только после контрольного readback.

Дельту новых ответов сохранить частно и сверить по owner/context/hash; импортировать обратно лишь проверенным идемпотентным путём. Если такого пути ещё нет, сохранить обе копии, оставить затронутый приём закрытым и передать оператору конечный список записей для восстановления. Это сохраняет данные, но не даёт обещания нулевого простоя. Уже отправленные Moodle grades/outbox нельзя «отменить» восстановлением локальной БД: фактический readback и отдельное корректирующее действие в разрешённом scope предшествуют возобновлению worker. Автоматический rollback к старой БД без сохранения новых writes неприемлем.
