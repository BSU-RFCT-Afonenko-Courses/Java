## Исполни согласованный объём

По [73](refactoring-plan.md#decision-73) предусмотрены ключевые архитектурные задачи на Astra/max и независимая архитектурная рецензия другим исполнителем, без обязательного предварительного провала Sol. По [74](refactoring-plan.md#decision-74) сокращай повторные inspect/полные хеш-проверки: пакетный native-контекст, переиспользование актуальных результатов, адресное обновление при значимых изменениях. Финальная приёмка/восстановление и полный модельный допуск сохраняются; алгоритм кэша и вечный API не обещаются.

Результат — полный активный состав **Java + System Practice + необходимых общих расширений** на Pages/PrairieLearn, IDE-комплекты и действующая Moodle/Gateway-связь. **Print и Cloud исключены**, включая специальные модели/контракты/экспорты/проверки и проектирование «назапас»; удаление их репозиториев не разрешено.

Архитектура и производительность идут вместе. Сохрани native Quarto/Pandoc, ранний TS JSON-filter, исполняемый TS-канон по владельцам без CUE и штатное наследование; собственные reader/merge/writer и обязательная поддержка старых runtime API не вводятся. Сохраняй нужные проверенные гарантии при замене кода, измеряй одинаковые входы без выдуманных обещаний ускорения.

Четыре существующие задачи — ранний внутренний контроль: `reverse-array`, `book-selection`, `local-history` с bundle-upload, `restore-selected-state` в Workspace. Они не заменяют сквозную приёмку всего активного состава. Оба SP-маршрута обязательны в одном выпуске; конкретный маршрут и достаточные состояния определяются задачей.

Ранний срез достаточен для начала массового переноса, когда на этих четырёх задачах и относящихся к ним различающих случаях проверены наследуемые метаданные кодового проекта и origins, связь ранних и поздних появлений, полный путь условие/ресурсы → README/ZIP и связанные реальные установленные потребители. Четырёх простых успешных запусков недостаточно. Случаи выбирает исполнитель по решениям 41/66; это техническая проверка существующих гарантий, не новые задачи курса, полный педагогический пилот или очередной опрос автора. Финальная приёмка всего активного состава сохраняется.

К выпуску обязательны структура/разметка, выдача/проверка, перенос и сохранность результатов; вместе с ними исправляются противоречия условие/стартер/тесты и подтверждённые ошибки, мешающие понять и выполнить задания. Глубокая композиционная/литературная переработка лекций и теории — следующий этап той же программы со своей проверкой качества (67).

Оценивание и обратная связь следуют принятым решениям: 80/20; самостоятельные предметные случаи равновесны; только полный достоверный набор даёт passed/total. API-допуск без баллов, compile/API-fail дают принятый ноль попытки; инфраструктура не подменяется студенческим нулём, лучший результат сохраняется. Для простых задач feedback краток, для сложных допустимы пояснения; размещение проверяется на живом PL.

Перенос сохраняет признанный полный зачёт, код успешного решения, нужные вложения/выдачу и контексты по однозначным соответствиям; редкие split/merge — в пределах принятого исключения. Перед переключением нужны сверка, резервирование и проверка восстановления; после — проверка реального результата и согласованности PL/Gateway/Moodle.

При сверке личности проследи устойчивый UID через Moodle→Gateway→PL: ФИО не ключ, UID не меняется ради исправления имени; повторный вход сохраняет внутреннюю запись. На двух разрешённых тестовых студентах проверь раздельные профили/внутренние записи, сдачи и результаты. Прежние результаты сначала сверяются без изменений; переатрибуция допустима только по доказанному основанию. Это сохранённые требования прежнего дополнения, а не новая система идентичности или оценивания; проверяются только на целевой машине.

## Работай самостоятельно в принятых границах

По решению 66 самостоятельно выбирай внутренние API/инструменты, перерабатывай согласованный состав, создавай и сливай связанные PR, выпускай расширения после независимой рецензии и нужных проверок. Публикация Pages/PL и перенос разрешены после предусмотренной подготовки; рутинные шаги не требуют повторного подтверждения.

Обращайся к пользователю при изменении учебных целей/правил оценки, потере данных сверх исключений, расширении поручения либо существенном риске срыва срока. Покажи последствия и рекомендуемый выход. При локальной блокировке продолжай независимую работу; связанные результаты рецензируй целиком, без множества микрорецензий.

Не читай все research по порядку. Решения нормативны; непринятые технические схемы — материал, который исполнитель выбирает и уточняет по архитектурным гарантиям. «Не исследовано до конца» само по себе не блокирует самостоятельную реализацию в согласованном объёме. Техническую неопределённость разрешай адресной проверкой, а не новым кругом магистральных вопросов автору.
