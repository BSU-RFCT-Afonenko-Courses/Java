### Quarto: доступный кеш до первого запуска

По [решению 78](refactoring-plan.md#decision-78) сразу подготовь стабильный кеш в уже разрешённом workspace. Для известного корня Java следующий префикс одинаково пригоден в bash и fish (при другом корне заменяются оба пути):

```sh
mkdir -p /home/tolya/Java/.cache/codex-tools
env XDG_CACHE_HOME=/home/tolya/Java/.cache/codex-tools quarto check info
```

Тот же `env XDG_CACHE_HOME=…` ставь перед фактической командой рендера/экспорта либо перед целым пакетным build-процессом, чтобы вложенные Quarto унаследовали настройку. Отдельные вызовы инструментов переменные предыдущего вызова автоматически не наследуют. Кеш переиспользуй между попытками; не помещай его в `.quarto`, не меняй HOME/права глобальных каталогов и не ищи обход разрешений после каждой ошибки. Отдельная переменная `QUARTO_CACHE_DIR` для этого не требуется. `.cache/codex-tools` исключён из Git; также исключи его из выдачи/ZIP и предметного input inventory.

29 октября на Quarto 1.11.6 в изолированной пробе `check info`, минимальный HTML-рендер с Sass и `quarto run` локального TS завершились с exit0 без escalation; render/TS повторены без очистки кеша с тем же результатом. Sass использовал `cache/quarto/sass`, Quarto сам задал дочернему процессу `DENO_DIR` внутри `cache/quarto/deno_std/cache`; bootstrap Deno использовал `cache/deno`. HOME не менялся, `XDG_DATA_HOME` не потребовался. Это проверка перенаправления кеша, не сборка курса. После установки целевого Quarto 1.11.5 достаточно одной адресной проверки фактического каталога кеша; повторный поиск решения и логи прежней `/tmp` не обязательны.

## Выполни согласованный состав

Полный активный **Java + System Practice + нужные общие расширения**: Pages, PrairieLearn, самостоятельные IDE-комплекты и действующая Moodle/Gateway-связь. **Print/Cloud исключены** вместе со специальными контрактами/проверками; их не проектируют «назапас» и не удаляют репозитории.

Архитектура и performance идут вместе: native Quarto/Pandoc, ранний TS JSON-filter, исполняемый TS-канон владельцев без CUE, штатное наследование, без обязательной поддержки старых runtime API. По 73 — выборочные ранние архитектурные Astra/max и независимый другой Astra/max. По 74 — пакетный native-контекст, переиспользование актуальных результатов, адресные inspect/хеш-проверки на значимых границах; финальная приёмка и полный модельный допуск сохраняются.

Ранний внутренний срез: `reverse-array`, `book-selection`, `local-history` с bundle-upload, `restore-selected-state` в Workspace. До массового переноса различающие случаи должны проверить inherited code-project metadata/origins, early→late binding, условие/ресурсы→README/ZIP и реальных установленных потребителей. Четырёх happy-path запусков мало; новые учебные задачи/общий педагогический пилот не нужны. Оба SP-маршрута обязательны в этом выпуске по задачам. Затем — сквозная приёмка **всего активного состава**.

К выпуску — структура/разметка, архитектура/performance, выдача/проверка, полный переход и сохранность данных; обязательно исправить противоречия условие/стартер/тесты и подтверждённые ошибки, мешающие выполнить задание. Глубокая композиционная/литературная переработка лекций/теории — следующий этап по 67, не основание задержать технический переход массовой редактурой.

Оценивание: 80/20; равные самостоятельные предметные случаи; passed/total только полного достоверного набора. API-допуск без баллов; собственная некомпиляция/API-fail — ноль текущей попытки, инфраструктура не студентский ноль, best/прежняя ручная часть сохраняются. Feedback краток для простых задач, для сложных допустимы пояснения; живой PL проверяется исполнением. Эталоны/альтернативы, ожидание стартера и отрицательные контроли обязательны.

Однозначный перенос сохраняет полный признанный зачёт без новой ручной части, код успешного решения, вложения/выдачу и нужные контексты; редкий неоднозначный split/merge ограничен 58. По Moodle→Gateway→PL проверь устойчивый UID (ФИО не ключ, UID не менять ради имени), повторный вход в ту же запись и раздельные профили/сдачи/результаты двух разрешённых тестовых студентов. Прежние результаты сначала сверяются без изменения; переатрибуция — только по доказанному основанию. После новой попытки/переназначения и отката зачёт и новые ответы не должны теряться.
