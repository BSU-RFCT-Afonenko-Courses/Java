# Инцидент 1 ноября 2026: поздняя диагностика стоимости расширений

Пользователь попросил сохранить этот разбор для будущих работ. Он относится
к исполнению согласованного рефакторинга Java/System Practice. Быстрые native
сборки и разумное число внешних вызовов уже требовались исходным поручением;
это не новое требование, возникшее после неудачного запуска.

## Что произошло

Координатор слишком поздно проверил стоимость всей цепочки расширений на
реальном составе курса. Локальные улучшения маленького примера обсуждались
как оптимизация сборки без достаточного подтверждения на полном курсе.
Обычная сборка Java остановилась по лимиту 7200 секунд уже на первой
student-проекции. Полный цикл student/full/student не завершился.

Основные подтверждённые причины:

* В Core и Publisher цикл document `quarto inspect` скрывал повторную
  обработку всех входов проекта внутри самого Quarto. N вызовов для N входов
  превращались в квадратичную обработку metadata. Число CLI-вызовов само по
  себе не описывало стоимость.
* Локальные проверки Core использовали растущее объединение зависимостей
  нескольких контекстов и снова проверяли уже обработанные соседние проекты.
* Publisher буферизовал stdout/stderr дочерней сборки до её окончания.
  Пакетная печать скрывала текущий этап; timestamps такого вывода не позволяли
  надёжно приписать задержку отдельному документу или проверке.
* Сначала исследовались отдельные расширения. Сквозной учёт прямых и
  косвенных вызовов остальных потребителей начался лишь после замечания
  пользователя. Наличие `inspect` ещё не означает, что каждый такой вызов
  лишний: назначение и ветвь выполнения нужно устанавливать по исходникам.

Это ошибка организации исполнения и обоснования выводов. Она не доказывает,
что Quarto непригодна для задачи. Увеличение timeout, общий кэш без правил
актуальности или отключение проверок сохранности не являются исправлением.

## Как действовать при похожей задаче

1. До массовой интеграции определить стоимость сквозного пути: кто вызывает
   внешний инструмент, на каком наборе входов, сколько раз за фазу и какую
   работу инструмент выполняет внутри. Учитывать косвенных потребителей и
   общие зависимости, а не только имя расширения в профиле.
2. Рано проверить настоящий представительный состав с несколькими размерами
   входа. Отдельно фиксировать wall time, число subprocess/inspect, полных
   обходов, чтений и хеширований. Малый пример не подтверждает скорость курса.
3. Убирать повторную работу в месте её возникновения. Использовать публичные
   native API и факты текущей операции; сохранять границы источника, профиля,
   формата и срока жизни. Не заменять native разрешение metadata своим merge.
4. Обеспечивать живой вывод и начало/окончание существенных этапов. Отсутствие
   сообщений не выдавать за установленную причину зависания.
5. В отчёте разделять гипотезу, подтверждённый исходниками механизм, измерение
   небольшого примера и завершённую проверку полного курса. Не обещать выигрыш
   полного курса по локальному счётчику.

Эти правила не вводят повторный общий аудит перед каждой правкой. Принятые
неизменные результаты переиспользуются; повторяются только затронутые проверки
или проверки по конкретной неопределённости. Сам диагностический слой не должен
создавать новую дорогую индексацию и непрерывную проверку неизменности файлов.

## Состояние на момент записи

Общий source-аудит Core, Presentation, Navigation, Theme, QRC, Download,
Publisher, экспортёра, Platform и Performance назначен; следующий benchmark
приостановлен до его результата. Исправления Core и потока вывода проверяются
адресно; ускорение полного Java ещё не подтверждено. Независимая рецензия,
реальные экспорты и итоговая проверка всего состава остаются необходимыми.

исполнительной сессии; этот документ не содержит данных студентов или секретов.
