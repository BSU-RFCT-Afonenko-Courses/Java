Общий клиент документов

Тип Document предоставляет краткое описание. Обычный документ возвращает заголовок, текстовый дополняет его числом символов. Клиенту печати нужна одна операция summary():

static void print(Document document) {
    System.out.println(document.summary());
}

Какие объявления позволят этому методу обработать оба вида документов? Объявления документов: Суперкласс и состояние подкласса.

Предложить назвать общий тип параметра и место выбора конкретного описания. После обсуждения открыть объявления. Если предложен switch по названию класса, сохранить этот вариант для сравнения с вызовом summary.

Состояние базового класса

class Document {
    private final String title;

    Document(String title) {
        this.title = java.util.Objects.requireNonNull(title);
    }

    String summary() { return title; }
}

Конструктор устанавливает ненулевой заголовок, summary() читает его. Закрытое поле входит в состояние объекта; доступ к нему имеет код Document. Классы этого опыта находятся в одном пакете, поэтому конструктор и метод без модификаторов доступа доступны подклассу.

Найти проверку, после которой можно считать заголовок ненулевым. Спросить, нужно ли открывать поле, чтобы подкласс использовал описание.

Расширение описания

class TextDocument extends Document {
    private final int characters;

    TextDocument(String title, int characters) {
        super(title);
        if (characters < 0) {
            throw new IllegalArgumentException("Отрицательное число символов");
        }
        this.characters = characters;
    }

    int characters() { return characters; }

    @Override String summary() {
        return super.summary() + ": " + characters + " chars";
    }
}

Один объект хранит заголовок и число символов. super(title) инициализирует базовое состояние; super.summary() получает базовый текст при формировании описания.

Сопоставить два употребления super. Перед следующим экраном предложить вызвать print для TextDocument("Notes", 120) и предсказать строку.

Динамическое связывание

Document value = new TextDocument("Notes", 120);
print(value); // Notes: 120 chars

Тип Document разрешает вызов summary(). Параметр print получает копию ссылки на тот же TextDocument; вызов выбирает TextDocument.summary(). Тело print сохраняется для нового подкласса с собственным описанием.

Через value недоступен characters(): эта операция объявлена только в TextDocument. Сам объект по-прежнему хранит число 120.

Интерфейсная роль

Роль Sender из теории обрабатывает ненулевое сообщение. Консольная реализация печатает его:

interface Sender { void send(String message); }

final class ConsoleSender implements Sender {
    @Override
    public void send(String message) {
        System.out.println(java.util.Objects.requireNonNull(message, "message"));
    }
}

implements Sender устанавливает подтип. Метод реализации открыт, поскольку операция интерфейса неявно public. Одного совпадения имени и параметров для подстановки недостаточно.

Предложить убрать implements, сохранив метод. Проверить рассуждением, можно ли после этого записать Sender s = new ConsoleSender().

Запись в буфер

StringBuilder накапливает текст; append дописывает его, toString() возвращает строку с текущим содержимым.

final class RecordingSender implements Sender {
    private final StringBuilder text = new StringBuilder();

    @Override
    public void send(String message) {
        text.append(java.util.Objects.requireNonNull(message, "message"));
        text.append('\n');
    }

    public String text() { return text.toString(); }
}

Операция send изменяет буфер. Общий тип Sender позволяет передать этого получателя вместо консольного.

Найти состояние получателя и место его изменения. Предложить оставить построение текста напоминания прежним и заменить только способ его обработки.

Получатель напоминания

final class Reminder {
    private final Sender sink;

    Reminder(Sender sink) {
        this.sink = java.util.Objects.requireNonNull(sink, "sink");
    }

    void remind(String title) {
        sink.send("Return: " + java.util.Objects.requireNonNull(title, "title"));
    }
}

RecordingSender recording = new RecordingSender();
new Reminder(recording).remind("Java");
System.out.print(recording.text()); // Return: Java и перевод строки

Поле связывает два объекта, вызов sink.send делегирует действие. Другой Sender выбирается при создании Reminder. Композиция и обёртка: Композиция и делегирование.

Вызовы через IVehicle

В задаче об IVehicle общий тип предоставляет чтение и изменение характеристик, int range() и double fuelNeeded(int miles). Vehicle(int passengers, int fuelcap, int mpg) создаёт автомобиль; конструктор принадлежит классу. Запас fuelcap измеряется в галлонах, а mpg — в милях на галлон. Дальность равна fuelcap * mpg, топливо для поездки — отношению расстояния к mpg.

Для готового решения:

IVehicle vehicle = new Vehicle(2, 10, 25);
System.out.println(vehicle.range());         // 250
System.out.println(vehicle.fuelNeeded(100)); // 4.0

Методы реализации имеют доступ public. setFuelcap(0) выбрасывает IllegalArgumentException и оставляет прежний запас топлива и дальность 250: проверка выполняется до изменения состояния. Полный договор: Упражнение 22.2.

Сопоставить объявление интерфейса с доступными вызовами. Попросить указать два наблюдения при неверном изменении: тип исключения и прежнее значение при следующем чтении.

Общий договор очереди

Очередь возвращает самый ранний из ещё не извлечённых символов — FIFO:

interface ICharQ {
    void put(char ch);
    char get();
}

FixedQueue, CircularQueue, DynQueue реализуют этот интерфейс, хранят символы в закрытом массиве и принимают положительную начальную ёмкость в конструкторе. Имена полей и устройство индексов выбирает автор решения.

Успешные операции ничего не печатают. get() у пустой очереди печатает Очередь пуста и возвращает '\0'; этот символ исключён из данных. Неудачное put печатает Очередь переполнена и сохраняет очередь. Точные условия: Очереди символов.

Перед следующим экраном задать ёмкость 2 и последовательность: поместить A, B; извлечь A; поместить C. Предложить сравнить оставшееся содержимое и возможность последнего помещения.

Вместимость и повторное использование

После помещения A, B и извлечения A при начальной ёмкости 2:

Реализация Попытка put('C') Оставшаяся последовательность
FixedQueue Отказ: обе линейные позиции уже использованы B
CircularQueue Занимает освободившуюся позицию B, C
DynQueue Обеспечивает место, увеличивая массив по необходимости B, C

Порядок оставшихся элементов общий. Вместимость и повторное использование позиций определяются выбранной реализацией. У DynQueue рост сохраняет порядок; в пределах доступной памяти отказ из-за заполнения не требуется.

Сопоставить прогноз с каждой строкой. Найти условие, при котором клиент может выполнить одинаковое число помещений для любой реализации.

Общий клиент

С готовыми реализациями из условия:

ICharQ[] queues = {
    new FixedQueue(2), new CircularQueue(2), new DynQueue(2)
};
for (ICharQ queue : queues) {
    queue.put('A');
    queue.put('B');
    System.out.println(queue.get()); // A
}

У каждой новой очереди есть место для двух помещений. Цикл использует операции ICharQ; их реализации работают со своими массивами и индексами. Добавление ещё одной подходящей реализации в массив сохраняет тело цикла.

Сброс и перенос

reset() делает очередь пустой и возвращает индексы в начальное состояние. Текущая ёмкость сохраняется, включая уже увеличенную ёмкость DynQueue. После A, B, извлечения A, сброса и помещения C извлекается только C.

transfer(source, destination, count) переносит все count элементов в другую пустую очередь. Клиент знает число элементов, поскольку заполнял источник. Приёмник должен допускать столько успешных помещений; для линейной очереди важны ещё не использованные позиции. После переноса источник пуст, приёмник сохраняет порядок.

Варианты работы: Упражнение 22.4, Упражнение 22.8.

Для сброса предложить очередь, которая уже увеличивалась, и найти сохраняемую ёмкость. Для переноса спросить, какие чтения из обеих очередей подтвердят требуемый результат. Рассмотреть count = 0.

Проверка состояния

Чтобы проверить выбор переопределённого метода, вызов выполняют через общий тип. Для изменяющей операции наблюдают результат и последующее состояние: после отказа при изменении характеристик автомобиля их значения прежние; после роста очереди извлечение сохраняет FIFO; после переноса изменены обе очереди.
