Исключительное завершение

Исход операции

Поиск студента может успешно завершиться без совпадения. Для загрузки обязательного каталога нужен доступный файл; отказ чтения препятствует получению каталога. Неверный индекс внутри загрузчика требует исправления алгоритма.

Исход Действие вызывающего уровня
Совпадения нет Выбрать действие при отсутствии
Файл не прочитан Сообщить о неудачной загрузке
В алгоритме неверный индекс Установить и исправить дефект

Попросить объяснить, почему пустой результат допустим при поиске. Затем предложить заменить им отказ чтения: какую информацию потеряет клиент? Для неверного индекса установить, поможет ли повтор с тем же входом.

Условия проверки балла

parseScore получает строку, отличную от null, без пробелов по краям. Успешный результат — целое число от 0 до 100 включительно.

"90"      — допустимый балл
"0"       — допустимый нулевой балл
"ninety"  — текст не обозначает целое число
"120"     — целое число за пределами диапазона баллов

Если вернуть 0 для "ninety", вызывающий код примет ошибку данных за допустимый результат. Отказ должен сохранять это различие.

Проверка балла

static int parseScore(String text) {
    java.util.Objects.requireNonNull(text, "text");
    int score = Integer.parseInt(text);
    if (score < 0 || score > 100)
        throw new IllegalArgumentException("балл вне диапазона 0..100: " + score);
    return score;
}

Для "90" число входит в допустимый диапазон; метод возвращает 90. null нарушает предусловие и приводит к NullPointerException.

Проследить успешный путь до return. Перед следующим экраном предложить заменить только вход на "ninety" и найти первое действие, которое не удастся.

Ошибка числового представления

int score = Integer.parseInt("ninety");
System.out.println("балл: " + score);

parseInt выбрасывает NumberFormatException. Присваивание score и печать не выполняются: исключение прерывает вычисление выражения и обычное продолжение вызова.

Программа компилируется. Ошибка обнаружена при обработке конкретной строки.

Механизм передачи управления: Путь через стек вызовов.

Ошибка предметного диапазона

Вызов parseScore("120") сначала вычисляет:

int score = Integer.parseInt("120"); // 120
if (score < 0 || score > 100)
    throw new IllegalArgumentException("балл вне диапазона 0..100: " + score);

Преобразование в int успешно. Проверка score > 100 приводит к throw, поэтому метод не достигает return score.

Для parseScore("0") проверка диапазона проходит; результат равен 0. Подстановка нуля при отказе смешала бы эти исходы.

Объект исключения и throw

int score = 120;
var failure = new IllegalArgumentException("неверный балл: " + score);
throw failure;

new создаёт объект с сообщением неверный балл: 120. throw передаёт ссылку на этот объект механизму обработки исключений. Дальнейшие обычные действия текущей ветви пропускаются.

В обработчике доступны тип объекта, сообщение и диагностические сведения. Повторное throw failure передаёт тот же объект.

Ответственность вызывающего кода

parseScore → проверяет текст и диапазон балла
загрузчик  → знает путь и физический номер строки
приложение → выбирает повтор ввода, пропуск записи или завершение

Парсер передаёт причину отказа уровню, который располагает данными для дальнейшего действия. Его можно использовать и в интерактивном вводе, и при чтении обязательного файла [4].

Передача управления в catch

try {
    int score = parseScore("120");
    System.out.println("балл: " + score);
} catch (IllegalArgumentException failure) {
    System.out.println("неверный балл");
}

Вывод — неверный балл. Тип параметра catch подходит к выброшенному объекту. В failure записана ссылка на него, затем выполняется обработчик. Строка балл: ... пропущена.

До раскрытия результата попросить выбрать выполняемую строку печати. После раскрытия показать объект исключения и новую переменную failure.

Продолжение после обработчика

try { parseScore("120"); }
catch (IllegalArgumentException ex) { System.out.println("ошибка"); }
System.out.println("следующая операция");

Вывод — ошибка, затем следующая операция. После нормального завершения обработчика выполнение продолжается за всей конструкцией. Вызов parseScore состоялся один раз; к месту после throw управление не возвращается. Повторную попытку организуют циклом с новым вводом.

До раскрытия результата предложить проследить путь управления. После ответа спросить, где должен находиться цикл для запроса нового балла.

Раскрутка стека вызовов

static int readStudent(String text) {
    int score = parseScore(text);
    System.out.println("запись проверена");
    return score;
}

В main подходящий catch охватывает readStudent("120"):

main → readStudent → parseScore → throw
       прерывается   прерывается
catch в main ← объект исключения

запись проверена не печатается. Исключение прерывает незавершённые вызовы на пути к подходящему обработчику. По пути выполняются предусмотренные finally и закрытия ресурсов; выполненные ранее изменения сохраняются.

Неперехваченное исключение

Если подходящий catch не найден, завершается текущий поток выполнения. Его обработчик неперехваченных исключений может вывести трассировку.

В приложении с единственным рабочим потоком это завершает программу. Другие рабочие потоки могут продолжить выполнение: исключение не переносится автоматически в их стеки вызовов.

Типы и объявления исключений

Иерархия Throwable

Throwable
├─ Exception
│  └─ RuntimeException
└─ Error

RuntimeException, Error и их подклассы — непроверяемые исключения. Все остальные классы этой иерархии — проверяемые.

Для проверяемого отказа компилятор требует обработки или допустимого объявления передачи. Оба вида исключений возникают при выполнении.

Объявление проверяемого отказа

class EmptyException extends Exception {}

static int take(boolean empty) throws EmptyException {
    if (empty) throw new EmptyException();
    return 7;
}

throw выполняется только при empty == true. throws EmptyException входит в объявление метода и учитывается при проверке каждого вызова, включая take(false).

Без throws этот метод отвергается при компиляции: проверяемый отказ его тела не обработан и не объявлен [9].

Сопоставить место создания объекта с записью типа в объявлении. Предложить прогноз для отдельного метода, содержащего только take(false) без обработки и без throws. Затем проверить прогноз на следующем экране.

Обработка и передача проверяемого отказа

Передача следующему вызывающему уровню:

static int forward() throws EmptyException {
    return take(false);
}

Обработка в месте, где можно выбрать дальнейшее действие:

try { System.out.println(take(true)); }
catch (EmptyException ex) { System.out.println("хранилище пусто"); }

Первый метод возвращает 7, второй фрагмент печатает хранилище пусто. Аргумент false не отменяет объявленный EmptyException у take; throws у forward требуется и для этого успешного запуска.

Порядок обработчиков

try { parseScore("ninety"); }
catch (NumberFormatException ex) { System.out.println("нужно число"); }
catch (IllegalArgumentException ex) { System.out.println("нужен диапазон"); }

Вывод — нужно число. NumberFormatException является подклассом IllegalArgumentException, поэтому обратный порядок сделал бы частную ветвь недостижимой.

Выбор обработчика по подтипу

Для обработчиков предыдущего экрана:

Вход parseScore Исход Выбранная ветвь
"ninety" NumberFormatException нужно число
"120" IllegalArgumentException нужен диапазон
"90" Возвращён 90 Ни один catch

Поиск выбирает первую подходящую ветвь. После её выполнения второй обработчик той же конструкции не запускается.

Предметное исключение

class DataFormatException extends Exception {
    DataFormatException(String message, Throwable cause) {
        super(message, cause);
    }
}

DataFormatException обозначает неверное содержимое записи. IOException сообщает о неудачной операции ввода-вывода. Тип позволяет вызывающему коду различить эти причины без разбора текста сообщения.

Сохранение причины

static int parseAt(String text, long number)
        throws DataFormatException {
    try { return parseScore(text); }
    catch (IllegalArgumentException ex) {
        throw new DataFormatException("строка " + number, ex);
    }
}

Для parseAt("ninety", 3) внешний отказ — DataFormatException. Его getMessage() возвращает строка 3, а getCause() — исходный NumberFormatException. Обёртка добавила контекст и сохранила причину.

Попросить указать объект, доступный через getCause(). Затем заменить вход на "120": внешний тип и номер сохранятся, изменится тип причины.

Многовариантный обработчик

DataFormatException — собственный подкласс Exception для ошибки содержимого. Загрузчик объявляет отдельно IOException и этот тип. При одинаковой реакции допустима форма:

catch (java.io.IOException | DataFormatException failure) {
    System.err.println(failure.getMessage());
}

Типы в перечне catch не могут быть подтипами друг друга. NumberFormatException | IllegalArgumentException отвергается компилятором. Параметру многовариантного обработчика нельзя присвоить другую ссылку.

Исключения переопределённого метода

interface TextSource {
    String read() throws java.io.IOException;
}
final class ConstantSource implements TextSource {
    @Override public String read() { return "90"; }
}

Реализация может убрать IOException или сузить его до подкласса. Добавить более широкий Exception нельзя: клиент TextSource обрабатывает лишь отказ, разрешённый интерфейсом.

new ConstantSource().read() обходится без обработки. Вызов через TextSource source требует учитывать IOException, даже когда ссылка ведёт к ConstantSource [11].

Цена проверяемого договора

TextSource допускает файловый источник; объявление throws требует от клиентов учесть IOException. Это обязательство действует и для клиента, который сейчас получил ConstantSource.

Если убрать отказ из интерфейса, новая файловая реализация потребует выбрать другое представление ошибки или изменить договор клиентов. Компилятор проверяет наличие обработки или объявления передачи; полезное восстановление зависит от возможностей приложения. [5]

Рассмотреть два клиента: один может попросить другой файл, второй лишь передаёт данные следующему слою. В первом обязанность обработать отказ помогает найти место решения, во втором объявления могут только передавать его по цепочке. Назвать альтернативы: непроверяемое исключение с описанным договором или отдельный результат с диагностикой. Выбор меняет обязанности вызывающего кода. Уже знакомый Function даёт пример интерфейса, чья операция не допускает проверяемого исключения в объявлении.

Граница перехвата

catch (Exception ex) охватывает также RuntimeException. Если общий обработчик вернёт пустой каталог, он скроет и отказ чтения, и возможный дефект алгоритма.

catch (Throwable ex) дополнительно охватывает Error, включая OutOfMemoryError. Прежде чем продолжить работу, нужно установить, какие части программы ещё работоспособны.

Перехват располагают там, где можно выбрать допустимое действие. Промежуточный метод может передать отказ дальше и добавить свой контекст.

Завершение блока и закрытие ресурса

Порядок return и finally

static int withFinally() {
    try { return 10; }
    finally { System.out.println("выход"); }
}

При System.out.println(withFinally()):

выход
10

Сначала вычислено значение 10, затем выполнен finally. Его нормальное завершение сохраняет выбранный возврат; клиент печатает число после завершения вызова.

Замещение завершения в finally

static int replacedReturn() {
    try { return 10; }
    finally { return 20; }
}

replacedReturn() возвращает 20: новый return вытеснил прежний. Если тело try вместо возврата выбросит исключение, тот же finally всё равно вернёт 20 и скроет этот отказ.

try { throw new IllegalStateException("body"); }
finally { throw new IllegalArgumentException("cleanup"); }

Наружу передаётся cleanup. Исключение body автоматически не сохраняется в cause или suppressed. Резкое завершение finally заменяет прежнюю причину выхода из блока.

Нормальное и резкое завершение

Блок завершается нормально, когда выполнение доходит до его закрывающей скобки. return, throw, break и continue прерывают обычную последовательность; для охваченных блоков это резкое завершение.

При выходе из try или его обработчика выполняется finally. Если он завершается нормально, исходная причина перехода сохраняется.

Бесконечный цикл не выходит из блока. Остановка процесса может прекратить исполнение до очистки [12].

Память и внешний ресурс

Объект файлового потока хранится в памяти JVM. Через него программа использует файловый дескриптор операционной системы.

GC освобождает память недостижимых объектов. Завершение области локальной переменной не вызывает close; незакрытые файлы могут исчерпать внешние ресурсы задолго до памяти JVM.

Владелец ресурса определяет момент закрытия. Объект в памяти и внешний ресурс

Время жизни ссылки, ресурса и данных

область reader:   [открытие → чтение → close]
файловый ресурс:  [открыт-----------→ закрыт]
готовый список:               [создан → используется дальше...]

Ссылка может оставаться видимой после close, но чтение через закрытый файловый поток завершится IOException. Список уже прочитанных строк остаётся доступным независимо от файла.

Пропущенное закрытие

path имеет тип java.nio.file.Path и указывает на UTF-8-файл. Файловые методы принадлежат java.nio.file.Files:

var reader = Files.newBufferedReader(path, java.nio.charset.StandardCharsets.UTF_8);
String line = reader.readLine();
reader.close();

При исключении из readLine строка reader.close() пропускается. Если поместить закрытие в finally, оно выполняется при выходе; одновременный отказ чтения и закрытия передаст наружу ошибку close.

Попросить проследить успешный путь, затем остановить его на readLine. Сопоставить новый отказ в finally с ранее разобранным cleanup.

Интерфейс AutoCloseable

java.lang.AutoCloseable объявляет:

void close() throws Exception;

Try с ресурсами вызывает close для успешно инициализированных ресурсов, отличных от null, при выходе. Реализация может сузить или убрать проверяемые исключения.

java.io.Closeable расширяет этот интерфейс, объявляет IOException и требует отсутствия эффекта при закрытии уже закрытого потока. AutoCloseable допускает эффект повторного закрытия [7], [8].

Граница try с ресурсами

static String firstLine(java.nio.file.Path path) throws java.io.IOException {
    try (var reader = java.nio.file.Files.newBufferedReader(path,
            java.nio.charset.StandardCharsets.UTF_8)) {
        return reader.readLine();
    }
}

Для UTF-8-файла с первой строкой first метод возвращает "first" после закрытия. Для пустого файла результат readLine — null; закрытие также выполняется.

Если close выбросит исключение, подготовленная строка не возвращается. catch этой конструкции охватывает открытие, тело и закрытие.

Порядок инициализации и закрытия

final class Trace implements AutoCloseable {
    final String name;
    Trace(String name) {
        this.name = name;
        System.out.println("open " + name);
    }
    @Override public void close() {
        System.out.println("close " + name);
    }
}

Конструктор отмечает успешное открытие, close — вызов закрытия. Этот ресурс позволяет наблюдать порядок без обращения к диску.

Перед следующим экраном задать порядок ресурсов A, затем B и тело, печатающее body. Попросить прогноз всех событий.

Трасса двух ресурсов

try (var a = new Trace("A"); var b = new Trace("B")) {
    System.out.println("body");
}
open A
open B
body
close B
close A

Инициализаторы вычисляются слева направо. Закрытие идёт в обратном порядке; это позволяет завершить зависимый ресурс до ресурса, на который он опирается.

До раскрытия сопоставить порядок объявлений с прогнозом. После раскрытия попросить указать первую и последнюю выполненную операцию.

Отказ инициализации

Ресурс A успешно инициализирован. При создании следующего ресурса B конструктор выбрасывает IOException("open B") до возврата ссылки.

A успешно инициализирован
инициализация B прервана
A получает вызов close
обработчик получает IOException("open B")

Тело try и B.close не выполняются. Если A.close тоже отказал, его исключение добавляется к open B как подавленное.

Конструкция закрывает успешно инициализированные ресурсы. Объект, открытый внутри неудавшегося конструктора B, требует очистки самим конструктором или фабрикой.

Копирование файла

В каталоге опыта input.txt содержит UTF-8-текст first\n\nlast\n, где \n — перевод строки. copy.txt первоначально отсутствует. Переменные путей имеют тип java.nio.file.Path:

var source = java.nio.file.Path.of("input.txt");
var target = java.nio.file.Path.of("copy.txt");
try (var input = java.nio.file.Files.newInputStream(source);
     var output = java.nio.file.Files.newOutputStream(target)) {
    input.transferTo(output);
}

При успехе copy.txt содержит те же байты. Закрывается сначала output, затем input. Если открытие output отказало, input получает close. Существующий целевой файл при открытии был бы усечён: ошибка копирования может оставить записанный префикс.

Ошибки очистки и владение

Первичное и подавленное исключения

тело:  IllegalStateException("body")
close: IOException("close")

Try с ресурсами передаёт наружу исключение тела. Ошибка закрытия добавляется к нему как подавленное исключение; она доступна через getSuppressed().

Если тело успешно, основной становится первая ошибка закрытия. Остальные ресурсы тоже получают close; их ошибки добавляются к первичной [10].

Наблюдение ошибки закрытия

class Failing implements AutoCloseable {
    @Override public void close() throws java.io.IOException {
        throw new java.io.IOException("close");
    }
}

Клиент:

try (var resource = new Failing()) {
    throw new IllegalStateException("body");
} catch (Exception ex) {
    System.out.println(ex.getMessage());
    System.out.println(ex.getSuppressed()[0].getMessage());
}

Вывод — body, затем close. Обработчик начинает работу после очистки.

Причина отказа и ошибка очистки

Resource.close печатает close и выбрасывает IOException("cleanup"). Тело передаёт другую ошибку с причиной:

try (var resource = new Resource()) {
    throw new java.io.IOException("read",
        new IllegalArgumentException("bad bytes"));
} catch (java.io.IOException failure) {
    System.out.println("primary: " + failure.getMessage());
    System.out.println("cause: " + failure.getCause().getMessage());
    System.out.println("suppressed: "
        + failure.getSuppressed()[0].getMessage());
}

Как связаны три объекта исключений и в каком порядке появятся сообщения?

Сначала записать прогноз. Отделить создание причины в теле от нового отказа при close; затем перейти к выводу и схеме связей.

Причина отказа и ошибка очистки

close
primary: read
cause: bad bytes
suppressed: cleanup
IOException("read")
├─ cause ──────> IllegalArgumentException("bad bytes")
└─ suppressed → IOException("cleanup")

cause был задан при создании ошибки read. Подавленная ошибка добавлена при автоматическом закрытии: close завершился дополнительным отказом. Затем конструкция передала read обработчику.

Сопоставить прогноз с выводом. При мысленной замене тела на успешное попросить назвать основное исключение: cleanup; его причина не задана.

Временное пользование ресурсом

Метод получает java.io.BufferedReader, который закрывает вызывающая сторона:

static long countLines(java.io.BufferedReader reader) throws java.io.IOException {
    long count = 0;
    while (reader.readLine() != null) count++;
    return count;
}

Для строк first, пустой строки и last результат равен 3. Ресурс остаётся открытым, а его позиция находится в конце входа. Следующий readLine вернёт null.

Передача ссылки разрешила чтение; обязанность закрытия осталась у владельца.

Закрытие обёртки общего потока

Закрытие Scanner, читающего System.in, закрывает его нижележащий вход. Остальное приложение может потерять доступ к общему ресурсу.

Владелец определяет момент закрытия общего потока. Вспомогательный метод только читает его во время вызова и оставляет открытым для других частей приложения.

Готовые данные и ленивый источник

static java.util.List<String> nonblankLines(java.nio.file.Path path)
        throws java.io.IOException {
    try (var lines = java.nio.file.Files.lines(path,
            java.nio.charset.StandardCharsets.UTF_8)) {
        return lines.filter(s -> !s.isBlank()).toList();
    }
}

Для input.txt с first, пустой строкой и last возвращается [first, last]. toList читает источник внутри блока; список доступен после закрытия.

Возврат одного lines.filter(...) передал бы ленивый конвейер с уже закрытым источником. Терминальная операция сама close не вызывает.

Состояние и реакция приложения

Частичное изменение состояния

var scores = new java.util.ArrayList<Integer>();
try {
    for (String text : java.util.List.of("90", "80", "120"))
        scores.add(parseScore(text));
} catch (IllegalArgumentException ex) {
    System.out.println(scores);
}

Вывод — [90, 80]. Первые два вызова add завершились. Третье преобразование прервалось до добавления; раскрутка стека не отменяет уже выполненные записи.

До раскрытия попросить указать аргумент каждого add. После ответа обсудить требование «получить все баллы или сохранить старый список».

Подготовка результата до публикации

старый каталог доступен вызывающей стороне

чтение → новый локальный список → все проверки → закрытие → возврат
                   ↘ отказ           ↘ отказ        ↘ отказ
                         новый список не опубликован

Старый каталог сохранится, если чтение и проверка изменяют только новый список и не публикуют его до завершения. Запись в общий объект или файл создаёт внешний эффект; сохранение прежнего состояния требует отдельного решения [6].

Отказ создания объекта

final class Limits {
    final int maximum;
    Limits(int maximum, java.util.List<String> events) {
        events.add("начало создания");
        if (maximum < 0) throw new IllegalArgumentException("maximum < 0");
        this.maximum = maximum;
    }
}

До вызова: пустой events, Limits saved = null. После неудачного saved = new Limits(-1, events) ссылка saved остаётся null; журнал содержит "начало создания".

new не вернул ссылку. Запись во внешний список уже состоялась. Проверка аргумента до events.add оставляет журнал неизменным при этом отказе.

Пустой результат и неудачная загрузка

Предположим, метод чтения использует:

catch (java.io.IOException ex) { return java.util.List.of(); }

Теперь корректный пустой файл и недоступный файл дают один результат. Клиент не сможет отличить «записей нет» от «данные не получены».

Для загрузки обязательного каталога отказ передают исключением или отдельным вариантом результата. Пустая коллекция остаётся успешным результатом чтения пустого источника.

Пропуск строки допустим, если результатом операции служат принятые записи и перечень отклонённых. Такой результат явно сообщает о неполной загрузке. Временный внешний отказ может допускать ограниченное число повторов.

Дополнительные механизмы отказа

Типизированный результат

Интерфейс проверки балла

Для строки, отличной от null, без пробелов по краям проверка различает балл 0–100, неверное представление int и число вне диапазона.

Исключение прерывает обычную последовательность исполнения. Другой интерфейс возвращает значение, которое кодирует успех или причину отказа. Вызывающий код выбирает дальнейшее действие по этому значению.

Варианты типизированного результата

sealed interface ScoreResult permits Score, ScoreFailure {}
record Score(int value) implements ScoreResult {}
enum ScoreProblem { NOT_INTEGER, OUT_OF_RANGE }
record ScoreFailure(ScoreProblem problem) implements ScoreResult {}

ScoreResult задаёт два исхода: балл или причину отказа. Вариант ScoreFailure хранит причину, а Score — полученное число.

Нарисовать два допустимых варианта и поля каждого. Попросить показать, где хранится число при успехе и где хранится причина при неудаче. Перед разбором адаптера выбрать три входа: "90", "ninety", "120". Затем пройти тело метода и для каждого return указать создаваемый вариант.

Возврат предметного исхода

static ScoreResult parseScoreResult(String text) {
    java.util.Objects.requireNonNull(text);
    final int score;
    try { score = Integer.parseInt(text); }
    catch (NumberFormatException ex) {
        return new ScoreFailure(ScoreProblem.NOT_INTEGER);
    }
    if (score < 0 || score > 100)
        return new ScoreFailure(ScoreProblem.OUT_OF_RANGE);
    return new Score(score);
}

NumberFormatException преобразуется в ScoreFailure. null нарушает предусловие и по-прежнему приводит к исключению. NOT_INTEGER включает число, которое не представимо в int.

Результаты трёх вызовов

"90"     → Score(90)
"120"    → ScoreFailure(OUT_OF_RANGE)
"ninety" → ScoreFailure(NOT_INTEGER)

После возврата значения с описанием ошибки выполнение продолжается со следующей инструкции. Вызывающий код может отбросить результат; чтобы отреагировать на отказ, ему нужно разобрать полученный вариант. Передача null, нарушающая предусловие, и дефекты реализации не превращены в обычную ошибку данных.

Полнота разбора вариантов

Шаблон типа связывает весь объект. Здесь шаблон записи проверяет вариант результата и связывает его компонент: Score(var value) вводит value типа int, а ScoreFailure(var problem) — problem типа ScoreProblem.

String message = switch (parseScoreResult("120")) {
    case Score(var value) -> "балл: " + value;
    case ScoreFailure(var problem) -> "ошибка: " + problem;
};
System.out.println(message); // ошибка: OUT_OF_RANGE

Выражение разбирает оба разрешённых вида. Дальнейшее действие задаёт каждая ветвь: в этом клиенте результат проверки превращается в сообщение.

Прочитать switch вместе с типами двух связанных переменных. Попросить заменить вход на "90" и получить точное сообщение. Затем обсудить действие после сообщения об ошибке: повтор, пропуск и завершение потребуют самостоятельного решения вызывающего кода. Для каждого варианта указать, какой участок клиента задаёт эту реакцию.

Состояние после возвращённой ошибки

Если до возврата ScoreFailure уже добавлены две записи в общий список, они остаются там после return, как остаются после throw.

Способ сообщения об отказе не создаёт откат. «Объект корректен» и «объект совсем не изменился» — разные требования к состоянию после отказа.

Возврат результата и ошибка закрытия

вычислен Score или ScoreFailure → close → возврат
                                      ↘ IOException вместо результата

return ScoreFailure выбирает возвращаемое значение и запускает закрытие. Если close отказал, значение не возвращается; сведения об ошибке данных автоматически не попадают в cause или suppressed.

Сравнить возврат 90 и возврат ScoreFailure: оба запускают close перед возвратом выбранного значения. Если close выбрасывает IOException, значение не возвращается. Попросить объяснить, почему ScoreFailure автоматически не появляется в suppressed. Сопоставить с выброшенным DataFormatException в таблице двух исходов.

Ошибка как значение и исключение тела

Для ресурса, чей close выбрасывает IOException("close"):

Действие тела Основной отказ Подавленные ошибки
return ScoreFailure IOException("close") Нет
throw DataFormatException DataFormatException IOException("close")

Чтобы сохранить ошибку данных, переданную значением, вместе с ошибкой закрытия, метод должен явно объединить сведения о них. В первом опыте getCause() == null, getSuppressed().length == 0. Полные примеры: Дополнительно: возврат ошибки и завершение работы с ресурсом.

Передача отказа и восстановление

Механизм Что происходит с отказом

Java ScoreFailure / Rust Err Возврат отдельного варианта

Повтор, отказ от загрузки и накопление ошибок — решения приложения. В Rust panic! запускает отдельный механизм аварийного завершения [17].

Тип Result в Rust

fn parse_score(text: &str) -> Result<i32, ScoreProblem> {
    let score = text.parse::<i32>()
        .map_err(|_| ScoreProblem::NotInteger)?;
    if score < 0 || score > 100 {
        return Err(ScoreProblem::OutOfRange);
    }
    Ok(score)
}

? извлекает успех либо возвращает ошибку из текущей функции. ScoreProblem — перечисление двух причин [16].

Значение error в Go

score, err := parseScore("120")
if err != nil {
    fmt.Println(err)
    return
}
fmt.Println(score)

Функция возвращает (int, error). По её соглашению балл пригоден только при err == nil; это проверяет вызывающий код. Тип пары сам не запрещает одновременно значение и ошибку [13]. Полная функция: Дополнительно: проверка балла в Rust и Go.

Объявление исключений в разных языках

Java проверяет обработку объявленных проверяемых исключений при компиляции. Переопределение метода должно сохранить допустимость прежних вызовов.

В современном C++ noexcept задаёт ограничение распространения исключений: выход исключения из такой функции вызывает std::terminate. Проверять обработку каждого вызова, как для проверяемых исключений Java, noexcept не требует [18].

В Python обычное объявление функции также не содержит проверяемого компилятором списка throws.

Границы освобождения в разных языках

Средство Граница завершающего действия
Java try с ресурсами Выход из ресурсной конструкции
C++ RAII Разрушение управляющего объекта
Python with Выход после успешного __enter__
Go defer Выход из окружающей функции

В Go краткий defer file.Close() отбрасывает возвращённую ошибку закрытия. Java try с ресурсами сохраняет дополнительный отказ закрытия через suppressed [3], [14], [15].

Исключение конструктора суперкласса

class TextSnapshot {
    TextSnapshot(java.nio.file.Path path) throws java.io.IOException {
        java.nio.file.Files.readString(path);
    }
}
class NamedSnapshot extends TextSnapshot {
    NamedSnapshot(java.nio.file.Path path) throws java.io.IOException {
        super(path);
    }
}

Отказ super(path) прерывает создание NamedSnapshot. Конструктор подкласса объявляет IOException или его допустимый супертип. Конструкторы не переопределяются; ограничение сужения из правил методов к ним не относится [11].

Статический тип ресурса

final class Quiet implements AutoCloseable {
    @Override public void close() {}
}
try (var resource = new Quiet()) {} // проверяемого отказа close нет

Альтернативный вариант в методе с throws Exception:

AutoCloseable resource = new Quiet();
try (resource) {} // у AutoCloseable.close объявлен Exception

Оба запуска вызывают пустой Quiet.close. Компилятор учитывает объявление close по статическому типу; второй вариант требует обработки или throws.

Проверяемые исключения в ранней Java

В первой JLS 1996 года throws с проверяемыми исключениями уже описан как часть соглашения автора метода и его пользователя. Цель компиляционной проверки — уменьшить число необработанных отказов.

Проверка требует обработать отказ или объявить его передачу. Разделение на проверяемые и непроверяемые исключения было частью раннего описания [2].

Финализация и задержка очистки

В JDK 18, согласно JEP 421, финализацию объявили устаревшей с намерением удалить её в будущем. Задержка очистки не ограничена; её выполнение не гарантируется.

Cleaner тоже не обеспечивает своевременное закрытие. Для файла нужен владелец и определённая граница close [1].
