Общий алгоритм для разных источников

Изображение находится в файле; для проверки подсчёта байтов его передают массивом в памяти. Алгоритму в обоих случаях нужен следующий байт.

файл   → FileInputStream      ┐
                             ├→ InputStream → подсчёт байтов
массив → ByteArrayInputStream ┘

InputStream задаёт последовательный источник. Замена источника сохраняет алгоритм; способы открытия и возможные отказы различаются. OutputStream представляет последовательную запись [15], [16].

Предложить назвать сведения, действительно нужные подсчёту: следующий байт и признак окончания. Сопоставить с ролью потока C++, отделяющего алгоритм чтения от файлового источника.

Байт и окончание входа

long count = 0;
int value;
while ((value = input.read()) != -1) {
    count++;
}

input — открытый InputStream. Метод read() возвращает 0..255 для байта и -1 для конца входа. Байты 41 00 FF дают count == 3.

Приведение результата к byte до проверки смешало бы FF и конец: оба получили бы значение -1 [11].

Попросить объяснить роль типа int при чтении одного байта. Перед следующим экраном задать буфер на восемь байтов и предположить, что операция получила три. Предложить определить обработанную область.

Фактически прочитанная порция

byte[] block = new byte[8];
int count = input.read(block);

При count == 3 новые данные находятся в block[0..3). Остальные ячейки могут сохранять прежние значения.

Размер массива ограничивает одну порцию. Короткая порция ещё не устанавливает конец входа: следующий вызов может получить продолжение. Порционное чтение сокращает число мелких обращений.

Сопоставить прогноз с границами массива. Предложить разбор ошибочного копирования всех восьми ячеек после получения трёх байтов: в выход попали бы пять значений, не относящихся к этой порции.

Буферизующая обёртка

Алгоритм распознаёт разделитель по одному байту, а источник удобно читать крупными порциями.

источник → BufferedInputStream → read() алгоритма
            порция в памяти       один байт

Обёртка получает блок снизу и обслуживает мелкие чтения из памяти. Контракт последовательного источника сохраняется. Дополнительный буфер полезен, когда сокращает дорогие обращения; для массива в памяти он может только добавить работу.

Предложить проследить первые два чтения после заполнения буфера: почему второе может не обращаться к файлу. Затем назвать событие, которое снова потребует чтения нижнего слоя.

Байты и символы текста

«Ада» в UTF-8:       D0 90 D0 B4 D0 B0    — 6 байтов
строка Java:        А     д     а          — 3 единицы char

Граница порции может разделить кодировку одного знака. InputStreamReader декодирует байты выбранной кодировкой и сохраняет нужное состояние между порциями. Reader предоставляет символы.

Некоторые Unicode-символы занимают две единицы char; длина строки в Java измеряется этими единицами.

Показать порцию D0 90 D0 и спросить, какие сведения нужны для третьего байта. Предложить объяснить, почему приведение каждого байта к char не заменяет декодер.

Составление символьного источника

new BufferedReader(
    new InputStreamReader(
        new FileInputStream(file),
        StandardCharsets.UTF_8.newDecoder()))

file — строковый путь. FileInputStream получает байты, InputStreamReader преобразует их в символы, BufferedReader буферизует символы и читает строки.

Явный декодер по умолчанию сообщает об ошибочных байтах (REPORT). Замена повреждённого текста другим символом была бы отдельной политикой [7].

Предложить менять по одному условию: источник стал массивом; кодировка стала иной; алгоритму нужны строки. Для каждого изменения назвать слой, который отвечает за соответствующую работу.

Последовательность Ада\nБоб\n каждый раз открывается заново:

InputStream.read() 14 байтов

Переводы строк входят в первые два подсчёта. readLine() убирает разделители. Каждый проход расходует свой источник до конца.

Владение цепочкой

владелец → BufferedReader → InputStreamReader → файловый поток
             close()           close()              close()

Try с ресурсами над наружным читателем закрывает всю цепочку. Метод, получивший заимствованный Reader, оставляет срок закрытия вызывающему коду по договору.

Синхронное получение результата

поток выполнения → read() ── ожидание данных ──→ результат → следующий шаг

Результат приходит из самого вызова. Пока операция ждёт, вызывающий поток не выполняет следующий шаг программы.

Чтение из заполненного буфера может завершиться сразу. Способ получения результата остаётся синхронным. Поток данных — последовательность байтов; поток выполнения — исполнитель этого вызова.

Попросить различить две причины быстрого возврата: данные уже были в памяти и внешний источник быстро ответил. Обе сохраняют порядок «вызов — результат — следующий шаг».

Два независимых соединения

соединение A: данных пока нет
соединение B: данные готовы

один поток → read(A) → ожидание
                      B пока не обслуживается

Последовательный код сохраняет состояние работы в стеке вызовов. Но ожидание одного источника задерживает другие, уже готовые.

Предложить два изменения организации: отдельный поток для B или способ узнать о готовности до чтения. Обсудить, что понадобится при тысячах соединений, большинство из которых молчит.

Цена независимого ожидания

Один платформенный поток на соединение сохраняет простой ход программы: читать, обработать, ответить. Каждая ожидающая задача имеет свой стек и связана с ресурсами потока операционной системы.

Совместное ожидание нескольких соединений сокращает число таких потоков. Тогда приложение отдельно хранит состояние каждого незавершённого обмена и выбирает, какой продолжить.

Предложить найти место хранения «уже полученной половины строки» в обоих вариантах. Сопоставить удобство локальных переменных с явным состоянием обработчика соединения.

Задачи NIO

NIO появилась в JDK 1.4. JSR 51 связывала новые средства с крупными приложениями: управлением блоками, кодировками и многочисленными соединениями [2].

Каналы и буферы сделали передачу порций явной. Неблокирующие сокетные каналы и селектор позволили совместно ожидать готовности.

Прежняя потоковая модель сохранилась: для последовательного чтения файла её простой порядок по-прежнему соответствует задаче.

Связать каждое приобретение с уже поставленной задачей: размер порции, кодировка, ожидание B при молчащем A. Не объединять их в одно утверждение о скорости всей библиотеки.

Канал и буфер

источник ←→ канал ←→ ByteBuffer ←→ обработка данных
          связь       память и состояние порции

channel.read(buffer) записывает полученную порцию в переданную область. Канал и буфер имеют разные обязанности. У массива из java.io границу порции задавало возвращённое число; у буфера есть явные позиция и предел.

Предложить указать, что остаётся в памяти после закрытия файлового канала: уже прочитанные байты буфера. Затем отделить позицию внешнего файла от позиции следующего действия внутри буфера.

Позиция и предел буфера

Поле Смысл
capacity Вместимость области
position Индекс следующего относительного чтения или записи
limit Первая позиция за доступной областью

0 ≤ position ≤ limit ≤ capacity.

После записи трёх байтов в буфер вместимостью 8: position=3, limit=8. Для обработки нужны именно записанные три байта.

Переключение на чтение

после put:  [10 20 30 ... ... ... ... ...]  position=3, limit=8
flip():     [10 20 30 |                ]  position=0, limit=3

flip() делает прежнюю позицию пределом и возвращает позицию к нулю. Байты остаются в тех же ячейках.

После двух get() позиция равна 2. Значение 30 ещё нужно обработать [5].

Сопоставить результат с прогнозом. Затем предположить, что для обработки остатка нужны ещё два байта источника. Попросить сохранить 30 и указать место следующего заполнения.

Остаток между порциями

до compact:       [10 20 30 | ...]   position=2, limit=3
после compact:    [30 | ... ... ]   position=1, limit=8
добавлены 40, 50: [30 40 50 | ...]   position=3, limit=8
после flip:       [30 40 50 | ...]   position=0, limit=3

compact() сохраняет непрочитанный остаток в начале. clear() подготавливает всю область заново, меняя границы; старые байты в ячейках остаются до перезаписи [6].

Попросить назвать следствие замены compact на clear: следующая запись может затереть непрочитанный остаток. Отличить такую потерю от физического стирания всех ячеек, которого clear не делает.

Позиции файлового канала

FileChannel читает байты в буфер:

int n = channel.read(buffer);       // текущая позиция файла
// После обработки полученной порции:
buffer.clear();
int m = channel.read(buffer, 100);  // явное байтовое смещение

Первый вызов сдвигает позицию файла на фактически полученное число байтов. Второй сохраняет текущую позицию канала. Оба дают результат синхронно; размер фактической порции может быть меньше свободной области буфера.

Задать файл из abcdefgh и буфер на четыре байта. Сначала прочитать abcd, затем порцию с позиции 1. Предложить восстановить текущую позицию файла после второго вызова: она останется 4.

Границы канальных возможностей

Произвольный доступ существовал ещё у RandomAccessFile в Java 1.0. FileChannel включил файловые операции в модель каналов и буферов [12].

FileChannel работает синхронно и не является SelectableChannel. Его нельзя зарегистрировать в селекторе как обычный сокетный канал. Файловый поток может предоставить связанный канал через getChannel(); у этой пары общее файловое состояние [9].

Предложить различить вопросы «какими порциями передаются данные» и «что делает поток, пока данные не готовы». Наличие буфера отвечает на первый и ещё не устанавливает ответ на второй.

Неблокирующая попытка чтения

У SocketChannel в неблокирующем режиме вызов read(buffer) может вернуть 0, если сейчас нет порции, при наличии места в буфере. Значение -1 означает окончание входа.

read(A) → 0 → можно заняться B

Результат попытки возвращается из вызова. Постоянное повторение без ожидания тратило бы процессор на опрос.

Предложить различить нулевую порцию и конец входа. Затем спросить, какое событие позволило бы прекратить бесполезный опрос молчащего A.

Совместное ожидание готовности

A: ожидает ┐
           ├→ Selector → B готов → read(B) → обработать порцию
B: готов  ┘

Подходящие каналы регистрируются в неблокирующем режиме для нужных операций. Селектор позволяет ждать их готовности в одном месте. После уведомления программа сама выполняет чтение или запись [13], [14].

Готовая порция может содержать только часть строки. Остаток и состояние разбора принадлежат конкретному соединению.

Попросить найти место ожидания и место самого чтения на схеме. Предложить вход тетрадь; в первой порции и 4\n во второй: до второй порции предметная запись ещё не закончена.

Уведомление о завершении

готовность:    ждать возможности → выполнить попытку чтения

завершение:   заказать чтение → получить результат выполненной операции

Асинхронный API отделяет заказ от получения результата. Пока операция выполняется, вызывающий поток может продолжить другую работу. Быстрая операция может завершиться уже к следующей инструкции.

Предложить назвать содержание уведомления в каждом случае. У готовности это основание для попытки; у завершения — исход уже заказанного чтения. Сохранить различие при переходе к файловому каналу.

Будущий результат файлового чтения

channel — открытый AsynchronousFileChannel:

var first = ByteBuffer.allocate(4);
var second = ByteBuffer.allocate(4);
var a = channel.read(first, 0);
var b = channel.read(second, 4);

У каждой операции явное смещение и свой буфер. a и b имеют тип Future<Integer>: результатом станет число прочитанных байтов. Порядок завершения двух операций может различаться.

Предложить указать, какие два чтения независимы по памяти и файловым позициям. До следующего экрана спросить, когда программе разрешено читать содержимое first.

Ожидание результата

int firstCount = a.get();
// Здесь можно обработать first.
int secondCount = b.get();
// Здесь можно обработать second.

get() ждёт, если операция ещё не закончена. Отказ операции передаётся через ExecutionException; ожидание может быть прервано.

Немедленный get() после каждого заказа возвращает ожидание в последовательный код. Ожидание можно совместить с независимой работой или выполнением нескольких заранее заказанных операций [10].

Сопоставить прогноз с успешным возвратом a.get(). Если второе чтение закончилось первым, показать, почему этот код всё равно обработает first раньше second.

Обработчик завершения

Другой вариант передаёт CompletionHandler вместе с заказом:

read(buffer, offset, ..., handler)
               ↓
     completed(число байтов, ...)  или  failed(причина, ...)

Продолжение располагается в обработчике. Завершение может запустить следующий шаг без ожидания get в вызывающем коде. Состояние незавершённой работы приходится передавать явно [4].

Сопоставить локальную переменную последовательного метода с данными, которые понадобятся обработчику: смещение, буфер, назначение результата. Оба способа должны сохранить эти сведения до завершения операции.

Время жизни операции

заказ чтения ─── операция использует буфер ─── завершение → обработка буфера
открытие канала ─────────────────────────────────────────→ закрытие

Пока чтение не завершено, программа не использует тот же буфер для другой работы. Закрытие канала прервёт незавершённые операции.

Try с ресурсами подходит, если до выхода из блока закончились все использования канала. Возвращённый Future сам его открытым не удерживает.

Предложить проследить return channel.read(...) внутри try с ресурсами. Сначала вычисляется Future, затем закрывается канал, затем происходит возврат. Найти зависимость поведения от того, успело ли чтение закончиться.

Реализация и цена асинхронности

Асинхронный канал задаёт способ заказа и завершения операции. Конкретная реализация может использовать рабочие потоки; отдельный системный асинхронный механизм API не гарантирует.

Управление порядком результатов и буферами усложняется. Для одного небольшого файла полезной независимой работы может не оказаться. Выигрыш зависит от нагрузки и реализации, а модель API определяет обязанности программы.

Сопоставить два заказа с немедленными get и два заказа перед независимым вычислением. Предложить назвать, что необходимо измерить, прежде чем говорить о времени работы конкретного варианта.

Виртуальные потоки

Виртуальный поток позволяет сохранить последовательные блокирующие вызовы. JVM во многих случаях ожидания освобождает выполняющий его платформенный поток для другой задачи.

readLine() по-прежнему возвращает строку после чтения: API остаётся синхронным. Меняется цена множества ожидающих задач; одиночный диск или вычисление быстрее от этого не становятся [3].

Задачи файловой модели

Приложению нужно объяснить файловый отказ, получить атрибуты, работать с символическими ссылками и разными файловыми системами. Например, File.delete() возвращает false при неудаче; Files.delete(path) передаёт отказ исключением и позволяет сообщить больше о причине [8].

JSR 203 расширила файловый API и добавила асинхронные операции. NIO.2 вошла в Java 7. Path описывает путь, Files предоставляет операции, провайдер связывает их с файловой системой [1].

Предложить сравнить сообщение «операция не выполнена» с различением отсутствующего файла и недоступного каталога. Связать точность диагностики с возможностью выбрать дальнейшее действие программы.

Новое открытие и прежний читатель

try (var reader = Files.newBufferedReader(path, StandardCharsets.UTF_8)) {
    String line;
    while ((line = reader.readLine()) != null) {
        process(line);
    }
}

path — Path, process обрабатывает строку. NIO.2 возвращает BufferedReader из java.io. Цикл и владение остаются последовательными. Пустая строка — ""; null означает конец входа.

Сопоставить с ручной цепочкой трёх обёрток. Предложить указать, какая часть программы стала короче и какое поведение цикла сохранилось.

Путь и рабочий каталог

Path path = Path.of("data", "input.txt");

Создано описание пути; файл ещё не открыт. Относительный путь обычной файловой системы разрешается от рабочего каталога процесса.

При запуске той же команды из другого каталога data/input.txt может обозначить другой файл. Каталог исходников и каталог JAR этого правила не меняют.

Задать два рабочих каталога /course и /tmp, затем построить оба абсолютных пути. Предложить объяснить, почему перенос одного JAR не переносит автоматически его входные данные.

Запись пути и идентичность файла

normalize() упрощает компоненты пути лексически. toRealPath() обращается к существующему файлу; Files.isSameFile проверяет, обозначают ли два пути один файл.

Предварительное Files.exists(path) не резервирует объект: между проверкой и открытием другой процесс может его заменить. Результат доступа устанавливает сама операция открытия.

Предложить разместить удаление файла между exists и открытием. Выяснить, почему обработка отказа открытия нужна и после положительной предварительной проверки.

Память при построчном чтении

память = буфер читателя + текущая строка + сохранённые данные программы

readAllLines сохраняет весь текст. Построчный цикл позволяет использовать строку сразу, но список всех результатов всё равно растёт. Одна очень длинная строка тоже занимает память целиком.

Files.lines даёт ленивый Stream<String> с файловым ресурсом. Его закрывают после обхода; сама ленивость не делает чтение асинхронным.

Предложить два обработчика: подсчёт числа строк и сохранение каждой строки в список. Сравнить память при одинаковом способе чтения.

Уровни проверки входа

байты → декодирование → строка → поля → число → допустимая поставка

Повреждённый UTF-8 мешает получить текст. ручка;ошибка — корректный текст с неверным числовым полем. ручка;0 содержит допустимое число, но нарушает положительность количества.

Разные границы отказа позволяют выбирать разную реакцию приложения.

Выбор последовательной обработки

Один файл читается по порядку. Следующая запись нужна после обработки предыдущей; первым появлением товара определяется порядок отчёта.

Синхронный BufferedReader сохраняет этот ход непосредственно. Files.newBufferedReader предоставляет нужную цепочку декодирования и буферизации.

Асинхронное чтение порций потребовало бы дополнительно собирать границы UTF-8, строк и исходный порядок. Независимой работы, оправдывающей эту цену, у небольшого журнала может не оказаться.

Предложить найти в договоре два основания последовательности: физические номера строк и порядок первого появления. Связать выбор с нагрузкой конкретной программы.

Отложенная публикация

Немедленная печать каждой новой суммы дала бы две строки для тетрадей и могла бы оставить часть отчёта при позднем отказе чтения.

читать и накапливать → закрыть вход → получить результат → печатать

Договор требует окончательные суммы. Накопление откладывает печать до получения полного входа и успешного закрытия, расходуя память под товары и диагностику.

Попросить указать место возможной ошибки диска после строки 4. Сопоставить видимый stdout при немедленной и отложенной печати.

Значение поставки и ключ товара

Delivery(String item, long quantity) представляет одну поставку. Конструктор применяет strip к названию, требует непустое имя без ;, CR и LF и положительное количество.

тетрадь;4 и тетрадь;3 — разные значения записи. Для суммы они имеют один ключ item.

Ограничение названия позволяет безопасно соединять поля отчёта через ;. Числовое значение и накопленная сумма проверяются в разных местах.

Предложить объяснить, почему равенство всей записи неудобно как ключ суммирования. Затем сопоставить ручка и ручка после нормализации.

Строка и предметное значение

Вычисление до изменения состояния

long previous = totals.getOrDefault(delivery.item(), 0L);
long next = Math.addExact(previous, delivery.quantity());
totals.put(delivery.item(), next);

При переполнении addExact выбрасывает ArithmeticException, до put выполнение не доходит. Прежняя сумма сохраняется.

После Long.MAX_VALUE - 1 поставка 2 отвергается, следующая поставка 1 принимается. Ошибки отдельной строки не меняют уже принятую часть.

Результат после закрытия

локальные суммы и проблемы
          ↓
полное чтение → успешное закрытие → ScanResult

При IOException результат не возвращён и печать ещё не началась. Отдельные неверные строки уже представлены значениями LineProblem.

ScanResult копирует карту с сохранением порядка и список проблем. Запрещающая изменения обёртка над копией отделяет результат от накопителя.

Предложить сравнить копию карты и только unmodifiableMap над исходной картой. При последующем изменении накопителя второй вариант показывает новые данные через прежнее представление.

Границы печати

ReportPrinter получает готовый результат, out и err. В stdout идут суммы, в stderr — диагностика. Потоки заимствованы и остаются открытыми.

После печати отдельно вызываются out.checkError() и err.checkError(). Ошибка любого вывода даёт статус 4. Уже переданные байты остаются у получателя [17].

Объединённое отображение stdout и stderr терминалом не гарантирует общего порядка их сообщений.

Попросить указать две независимые проверки и объяснить, почему короткое замыкание между ними было бы нежелательно. Связать проверку с продвижением накопленных данных обоих потоков.

Публикация файла перемещением

вычислить → записать временный файл → закрыть → переместить к цели

До перемещения прежний отчёт остаётся доступным по целевому имени. Отказ записи или закрытия оставляет публикацию невыполненной; временный файл может потребовать удаления.

ATOMIC_MOVE запрашивает неделимость перемещения. Поддержка и замена уже существующей цели зависят от реализации. Границы: Публикация файлового результата.

Разместить сбой после каждой стрелки. Указать, какой файл мог измениться и можно ли считать новый отчёт опубликованным. Отдельно назвать сохранность при отключении питания как другое свойство хранения.

Сохранение представления текста

readLine() удаляет разделители. Последовательности Ада и Ада\n дают одинаковую последнюю строку.

Для суммирования поставок это допустимая потеря сведений. Точное копирование требует сохранить байты. Перекодирование работает с символами, а нормализация разделителей намеренно меняет представление.

Одинаковый вид в редакторе ещё не устанавливает равенство файлов.

Предложить выбрать уровень обработки для трёх целей: резервная копия, перевод UTF-8 в другую кодировку, подсчёт записей. Для каждой назвать сведения, которые должны сохраниться.

Изменение масштаба и политики

Суммы растут с числом разных товаров, диагностика — с числом ошибок. Построчное чтение не ограничивает эти коллекции постоянным размером.

Постепенная печать диагностики уменьшает хранение, но делает сообщения видимыми до возможного позднего отказа. Внешнее хранение сумм меняет стоимость доступа и условия сохранения состояния.

Новый масштаб требует пересмотреть хранение и публикацию результата. Замена цикла на Files.lines при прежних накопителях этого не решает.
