Поля экземпляра

class Book {
    String title;
    boolean borrowed;
}

Поле title хранит ссылку на строку названия, borrowed — признак выдачи: false означает доступную книгу, true — выданную. Объявление класса определило эти поля; экземпляров Book пока не создано.

Создание объекта

Book first = new Book();

new Book() создаёт экземпляр и даёт ссылку на него. Эта ссылка записывается в локальную переменную first. Начальное состояние:

first ───> A: Book
             title = null
             borrowed = false

A обозначает объект на схеме. Его ссылочное поле получило null (названия пока нет), логическое — false. Конструктор без аргументов предоставлен неявно: в объявлении Book конструкторов нет.

Присваивание локальной переменной

В отдельном опыте локальное объявление предшествует присваиванию:

Book pending;
// System.out.println(pending.title); // ошибка компиляции
pending = new Book();
System.out.println(pending.title);    // null

Объявление pending создаёт переменную. Перед чтением её значения компилятор требует определённого присваивания: значение должно быть получено на каждом пути к чтению. После pending = new Book() ссылка есть; чтение поля title созданного объекта даёт его начальное null.

Предложите прочитать отдельно pending и pending.title. В первой строке объекта ещё нет; после присваивания он существует и содержит поле title. Спросите, почему раскомментирование печати меняет именно результат компиляции.

Выражение new Book() создало отдельные поля для B. Запись в second.title изменила поле B; через first читается поле A.

Ссылочная переменная в Java и C++

В C++ локальная запись Book object; создаёт объект с автоматическим временем хранения, если класс допускает такую инициализацию. Book* pointer = &object; создаёт отдельную переменную указателя; копирование указателя сохраняет доступ к общему объекту.

В Java Book first; объявляет ссылочную переменную. Её значение можно заменить другой ссылкой. C++ Book& alias = object; связывает ссылку с объектом; присваивание через alias действует на этот объект.

Ссылка Java позволяет обратиться к полям и методам. Арифметика адресов, оператор разыменования * и явное освобождение через delete в этой модели отсутствуют. [6]

Тождество и содержимое объекта

У новой книги установлены те же значения обоих полей:

Book other = new Book();
other.title = first.title;
other.borrowed = first.borrowed;
System.out.println(first == same);  // true
System.out.println(first == other); // false

first и same ссылаются на A; other — на отдельный экземпляр. Для ссылок == даёт true, когда обе обозначают один объект или обе равны null. Сравнение полей требует своего правила равенства.

Попросите объяснить false при одинаковых title и borrowed. Затем предложите заменить создание other присваиванием first и назвать результат повторного сравнения.

Тождество экземпляра и номер книги

Номер экземпляра в каталоге определяет, какую физическую книгу выдали. Два чтения записи с одним номером могут создать два Java-объекта: каждый хранит своё представление состояния этой книги.

== проверяет тождество объектов в программе. Сопоставление номера позволяет связать загруженные данные с одной предметной сущностью. При обновлении каталога правило поиска определяет, чьё состояние изменится. Одинакового названия для выбора экземпляра недостаточно.

Предметное равенство: Тождество экземпляра и обозначение книги.

Отсутствие объекта

Book missing = null;
System.out.println(missing == null); // true
// missing.title = "Java";           // NullPointerException

Переменной missing явно присвоено значение null: объекта по этой ссылке нет. Обращение к полю экземпляра требует объекта и при null завершается NullPointerException. У new Book() объект существует, а его поле title первоначально равно null.

Требования к объекту и его полю

Поиск может завершиться без книги. Операция чтения названия требует найденную книгу с заданным названием:

static String titleOf(Book book) {
    java.util.Objects.requireNonNull(book, "book");
    return java.util.Objects.requireNonNull(book.title, "title");
}

titleOf(null) вызывает NullPointerException на первой проверке. titleOf(new Book()) доходит до второй: объект существует, его название равно null. Для first с названием Java обе проверки успешны, результат — Java.

Попросите проследить оба ошибочных вызова до конкретной проверки. Затем назовите вызов titleOf(first) и предложите объяснить, почему borrowed не влияет на выполнение этого метода.

Передача значений аргументов

Метод получает существующую книгу и устанавливает признак выдачи:

static void borrow(Book book) {
    book.borrowed = true;
}

Новый опыт: first получает ссылку на новую доступную книгу:

first = new Book();
first.title = "Java";
borrow(first);
System.out.println(first.borrowed); // true

Параметр book получает копию ссылки из first. Обе переменные обращаются к одной книге; запись в её поле меняет false на true. Передача по значению: Передача значений аргументов.

Возвращаемая ссылка

static Book create(String title) {
    Book result = new Book();
    result.title = title;
    return result;
}
Book book = create("Java");
System.out.println(book.title); // Java

return result передаёт ссылочное значение как результат вызова. Инициализатор сохраняет его в book. Локальная переменная result прекратила существование, созданная книга доступна через book. Книгу создала операция new; return передал ссылку на неё.

Копирование полей объекта

Исходная книга first называется Java и выдана:

Book copy = new Book();

copy.borrowed = first.borrowed;

System.out.println(first.borrowed); // true
System.out.println(copy.borrowed);  // false
System.out.println(first == copy); // false

new создал вторую книгу с собственными полями. В её поле borrowed скопировано значение true. Последующая запись false меняет только это поле. В title скопирована ссылка на одну строку; неизменяемость String сохраняет общий текст.

Достижимость объекта

Book kept = create("Java");
Book alias = kept;
kept = null;
System.out.println(alias.title); // Java
kept: null       alias ───> книга: title = Java

Доступ к книге сохранился через alias. Объект достижим, пока к нему можно обратиться в продолжающемся вычислении; путь может проходить через поля и компоненты массивов. Недостижимая группа объектов может быть собрана целиком, включая её внутренние циклы.

Попросите проследить оставшийся путь. Добавьте поле каталога со ссылкой на ту же книгу и предложите установить, что изменит alias = null. Отсутствие локальных ссылок ещё оставляет путь через каталог.

Закрытие внешнего ресурса

Сборщик мусора освобождает память недостижимых объектов. Присваивание null удаляет одну ссылку; остальные пути могут сохраниться. Недостижимость не задаёт момент освобождения памяти.

Открытый файл требует вызова close. Конструкция try с ресурсами вызывает close для успешно инициализированного ресурса, отличного от null, при выходе из блока, в том числе через return или исключение. Закрытие: Глава 22.

Выход автоматического объекта C++ из области вызывает его деструктор. Окончание области локальной переменной Java такого действия с объектом не выполняет.

Инвариант состояния

Объект бронирования хранит вместимость capacity и число занятых мест occupied. Инвариант задаёт допустимое состояние между обращениями клиента:

  • capacity > 0;
  • 0 <= occupied <= capacity.

Конструктор устанавливает эти условия, доступные операции сохраняют их. Для комнаты на 30 мест допустимы и пустое состояние, и занятость 30. Запрос занять ещё 8 мест допустим, только если свободно хотя бы 8. Условие запроса зависит от текущего состояния объекта. Сохранение инварианта. [2]

Назовите occupied = 25 при capacity = 30. Попросите сначала проверить само состояние, затем запрос на 8 мест. Найдите условие запроса, которое нарушено при сохранённом инварианте.

Нарушение инварианта прямой записью

class OpenReservation {
    int capacity;
    int occupied;
}
OpenReservation room = new OpenReservation();
room.capacity = 30;
room.occupied = 100;

Сразу после new вместимость равна нулю. После двух присваиваний занято больше мест, чем существует. Оба числа допустимы для int; проверка типов пропускает эти записи. Сохранение инварианта требует контролировать создание и последующие изменения состояния.

Попросите проверить оба состояния по неравенствам предыдущего экрана. Предложите клиенту самостоятельно проверять каждую запись и найти, какие места пришлось бы проверить после появления второго клиента.

Закрытое представление

final class Reservation {
    private final int capacity;
    private int occupied;
    // Конструктор и методы управляют этими полями.
}

Если room — переменная типа Reservation, запись room.occupied = 100 из внешнего клиентского кода отвергается при компиляции. Изменение проходит через доступные операции Reservation. private ограничивает доступ по месту кода: метод этого класса может читать закрытое поле другого экземпляра того же класса.

final у capacity запрещает повторное присваивание после инициализации; final у класса запрещает его расширение подклассом.

Попросите найти два разных применения final и назвать их адресатов. Затем предложите ошибочный метод самого Reservation, записывающий 100, и установите, почему private не проверяет арифметическое условие.

Допустимое начальное состояние

Reservation(int capacity) {
    if (capacity <= 0) {
        throw new IllegalArgumentException("positive capacity required");
    }
    this.capacity = capacity;
}

При new Reservation(30) проверка пропускает положительную вместимость. this.capacity получает 30, occupied сохраняет начальный 0. Оба условия инварианта выполнены.

При new Reservation(0) оператор throw прерывает выполнение. Выражение создания завершается исключением и не даёт клиенту ссылку на готовую комнату.

Попросите проследить new Reservation(-1) до последней выполненной строки. Затем сопоставьте this.capacity и capacity: поле создаваемого объекта и параметр вызова конструктора.

Вычисляемое состояние

int available() {
    return capacity - occupied;
}

Для вместимости 30 и занятости 8 результат равен 22. Из инварианта следует, что разность неотрицательна и помещается в int.

Если хранить свободные места третьим полем, операция бронирования должна согласованно менять занятость и остаток. Вычисление разности получает остаток из двух уже сохранённых величин.

Предложите добавить поле free = 30 и при бронировании поменять только occupied. Попросите назвать два противоречащих друг другу ответа о свободных местах и найти лишнюю связь, которую пришлось бы поддерживать.

Проверка запроса до изменения

void reserve(int count) {
    if (count <= 0 || count > available()) {
        throw new IllegalArgumentException("invalid size");
    }
    occupied += count;
}

Успешный запрос удовлетворяет 0 < count <= capacity - occupied. Поэтому новая занятость остаётся между нулём и вместимостью. При отказе выполнение заканчивается до записи, и поля сохраняются.

Проверка через остаток также предотвращает переполнение int: допустимая сумма ограничена вместимостью. Предварительное вычисление occupied + count для произвольного запроса могло бы переполниться.

Для изначально пустой комнаты на 30 мест предложите два вызова: сначала reserve(8), затем reserve(25). До следующего экрана попросите назвать остаток после каждого вызова и указать, какой дойдёт до присваивания.

Наблюдение состояния после отказа

Reservation room = new Reservation(30);
room.reserve(8);
System.out.println(room.available()); // 22
try {
    room.reserve(25);
} catch (IllegalArgumentException ex) {
    System.out.println("refused");
}
System.out.println(room.available()); // 22

catch позволяет продолжить выполнение после исключения. Состояние осталось прежним благодаря порядку действий в reserve: проверка отвергла 25 до изменения occupied. Сам перехват исключения не восстанавливает поля.

Сопоставьте результат с прогнозом. Предложите мысленно перенести occupied += count перед проверкой и объяснить, какой прежний результат потеряется, даже если сообщение refused останется тем же.

Операция изменения состояния

При занятости 8 действие reserve(8) занимает ещё восемь мест: занятость становится 16. Присваивающий метод setOccupied(8) оставил бы занятость равной 8.

Для бронирования клиент сообщает размер новой группы. Метод сам читает текущую занятость, проверяет остаток и выполняет переход. Setter требует от клиента заранее получить итоговое число; отдельная операция исправления учёта может иметь собственные условия доступа.

Предложите последовательно забронировать группы из 8 и 5 человек. Попросите записать аргументы reserve и, отдельно, аргументы присваивающего setter. Установите, в каком варианте клиент вычисляет новую занятость и хранит сведения о предыдущих вызовах.

Изменение представления бронирования

Вместо occupied можно хранить число свободных мест. Клиент продолжает вызывать available() и reserve(count), если их договор сохранён. Прямое чтение и запись occupied связали бы клиента с прежним устройством.

Закрытые поля ограничивают места изменения состояния. Проверка инварианта сосредоточена в создании объекта и его операциях; новый клиент использует уже определённые переходы. [4]

Операция выдачи

Методы того же класса Book:

    public String title() { return title; }
    public boolean borrowed() { return borrowed; }
    public void borrow() {
        if (borrowed) throw new IllegalStateException("Книга уже выдана");
        borrowed = true;

}

title() и borrowed() читают состояние. borrow() допускает переход false → true; при уже выданной книге выполнение прекращается до присваивания. public делает эти операции доступными клиенту, private у полей направляет изменение через проверяющее тело метода.

Копирование входного контейнера

Внешний код передаёт изменяемый список имён и сохраняет свою ссылку. Прямое сохранение этой ссылки в поле оставляет общий контейнер: последующий clear() клиента удалит все имена и для владельца поля.

Снимок и представление списка

Список и все имена в этом опыте отличны от null:

final class GuestList {
    private final java.util.List<String> names;
    GuestList(java.util.List<String> initial) {
        names = new java.util.ArrayList<>(initial);
    }
    void add(String name) { names.add(name); }
    java.util.List<String> snapshot() {
        return java.util.List.copyOf(names);
    }
    java.util.List<String> view() {
        return java.util.Collections.unmodifiableList(names);
    }
}

snapshot() фиксирует текущий состав. Через результат view() при каждом обращении доступен текущий состав внутреннего списка. Через оба результата изменение состава запрещено.

До следующего экрана предложите получить оба результата, затем добавить имя через GuestList.add. Попросите предсказать состав каждого результата. Отдельно установите условие List.copyOf: наличие null среди имён вызвало бы NullPointerException.

Наблюдение изменений через представление

var view = guests.view();
guests.add("Bob");
System.out.println(snapshot); // [Ann]
System.out.println(view);     // [Ann, Bob]

Снимок сохранил состав на момент вызова snapshot(). Через представление виден изменённый состав списка владельца. Запрет view.add(...) ограничивает операции через представление; сам владелец продолжает менять свой список через guests.add(...).

Имена и статическая проверка

В Python присваивание second = first может связать два имени с одним изменяемым объектом. Изменение его поля через second тогда наблюдается через first, как в опыте с общей книгой Java.

В Java объявленный тип переменной определяет доступные члены и допустимые значения. Вызов метода, отсутствующего в этом типе, отвергается при компиляции. Python проверяет доступность атрибута у объекта во время выполнения соответствующего обращения.

Обязательное и допускающее отсутствие значение

В Kotlin различаются String и String?:

fun titleLength(title: String): Int = title.length
fun possibleLength(title: String?): Int? = title?.length

titleLength("Java") даёт 4. В possibleLength(null) оператор ?. сохраняет отсутствие: результат — null. Тип параметра и тип результата второго метода явно допускают этот случай.

!! требует значение, отличное от null, и при null бросает исключение. Для пришедших из Java значений проверка зависит от сведений о допустимости null. [8]

Попросите заменить title?.length на title!!.length и предсказать possibleLength(null). Укажите проверку, которая изменила исход вызова.

Неоднозначность перегрузки

static void show(String value) { }
static void show(Integer value) { }
// show(null);       // ошибка компиляции: неоднозначность
show((String) null); // выбран show(String)

null подходит обоим ссылочным параметрам. String и Integer не являются подтипами друг друга, поэтому правила перегрузки не выделяют более конкретного объявления.

Приведение (String) null задаёт тип выражения аргумента и выбирает show(String). Значение параметра при выполнении всё ещё равно null.

Предложите добавить в show(String) чтение value.length(). Попросите разделить успешный выбор объявления при компиляции и отказ обращения к отсутствующей строке при выполнении.

Проверка параметра до конструктора суперкласса

В Java 25 допускаются действия до явного super(...) или this(...):

class Parent {
    final int value;
    Parent(int value) { this.value = value; }
}
class Child extends Parent {
    Child(int value) {
        if (value < 0) throw new IllegalArgumentException();
        super(value);
    }
}

extends Parent задаёт суперкласс. new Child(3).value даёт 3. При new Child(-1) исключение возникает до вызова Parent.

Проследите обе ветви на одном параметре value. Попросите добавить печать в Parent и предсказать её наличие для 3 и -1 до запуска.

Раннее конструирование

Участок перед явным вызовом другого конструктора называется прологом. Он может проверять параметры, вычислять локальные значения и вызывать статические методы. Обращение к создаваемому экземпляру ограничено.

В прологе разрешено простым присваиванием записать собственное поле, объявленное в этом классе без инициализатора. Такая запись запрещена во вложенной лямбде или внутреннем классе. Чтение полей текущего объекта, вызов его методов и передача его this внешнему коду запрещены; присваивание унаследованного поля тоже запрещено.

Без явного this(...) или super(...) конструктор обычного класса, отличного от Object, неявно начинает с super(). Написанные операторы образуют эпилог. [1, Разд. 8.8.7] и 6.5.6.1 Правила инициализации: Конструкторы и проверка исходного состояния.

Для Child с предыдущего экрана предложите добавить своё поле int checked без инициализатора. Сравните допустимое checked = value с checked++, чтением this.value и передачей this в другой метод до super. Для каждого найдите разрешённую запись или запрещённое чтение.

Доступ к незавершённому объекту

В эпилоге конструктор может передать this внешнему объекту. Если тот сразу вызовет метод создаваемого экземпляра, он прочитает поля в состоянии на этот момент. Поэтому передача ссылки до завершения проверок и записей открывает доступ к состоянию, в котором инвариант ещё может быть нарушен.

Вызов переопределяемого метода из конструктора суперкласса выбирает реализацию подкласса. Его инициализаторы ещё могут быть не выполнены, и метод увидит начальные значения полей. В C++ виртуальный вызов при конструировании ограничен строящейся частью иерархии. Переопределяемые методы в конструкторе.

Модификаторы доступа

Модификатор члена Область доступа
private Тело охватывающего класса верхнего уровня, включая вложенные объявления
Без модификатора Тот же пакет
protected Тот же пакет; особый доступ из подкласса в другом пакете
public Клиенты, которым доступен содержащий тип

У модульного приложения доступность типа также учитывает читаемость модуля и экспорт пакета. Публичный метод закрытого для клиента типа сам по себе доступ к этому типу не создаёт. [7]

Выберите public-метод класса без public в другом пакете. Попросите проверить доступность сначала типа, затем члена. После этого перенесите клиента в исходный пакет и установите, какое ограничение изменилось.

Получатель защищённого члена

В отдельной иерархии Parent объявляет protected int value, а Child расширяет его в другом пакете. В теле Child доступ к этому полю через ссылку требует, чтобы её статический тип был Child или его подтипом. Ссылки общего типа Parent для такого доступа недостаточно.

// В классе Child:
void inspect(Child child, Parent parent) {
    System.out.println(child.value);  // допустимо для protected value
    // System.out.println(parent.value); // ошибка доступа
}

Правило ограничивает доступ подкласса к чужим экземплярам общего базового типа. Внутри пакета Parent действует пакетная часть доступа.

Попросите объяснить, почему фактический объект Child в переменной parent не меняет результат проверки. Затем перенесите оба класса в один пакет и предскажите доступность второго обращения.

Общая книга после переназначения

У Book с открытыми полями create создаёт доступную книгу, а borrow записывает true в поле полученной книги:

Book a = create("Java");
Book b = a;
borrow(b);
b = create("Algorithms");
System.out.println(a.title + ": " + a.borrowed);

Результат — Java: true. Вызов borrow изменил общую книгу. Последнее присваивание заменило только ссылку в b; a сохранила доступ к выданной книге с прежним названием.
