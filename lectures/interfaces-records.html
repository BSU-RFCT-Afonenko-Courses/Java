Наследование и отношение подтипов

Наследование классов позволяет подклассу получить доступные наследуемые члены суперкласса, добавить состояние и переопределить методы экземпляра. class TextDocument extends Document задаёт эту связь.

Одновременно TextDocument становится подтипом Document: ссылку на текстовый документ можно передать параметру типа Document. У обычного класса один непосредственный суперкласс; при отсутствии extends им служит Object. Глава 12. [8]

Различите два последствия extends: получение реализации и допустимость ссылки в базовом типе. Попросите назвать, какие обязательства перед клиентом сохранятся у текстового документа, если общая операция возвращает описание.

Контракт описания документа

Document хранит заголовок и предоставляет summary() — строку описания. TextDocument добавляет число символов. Клиенту нужна длина описания, поэтому результат, отличный от null, требуется от любого подкласса.

Предложите назвать, какую операцию документ должен предоставлять общему клиенту. Зафиксируйте summary и её результат. В опыте C++ сопоставьте обращение через базовую ссылку с прямой зависимостью от конкретного класса.

Попросите назвать операцию клиента, которая завершится исключением при null. Это основание для требования к summary, даже когда тип результата String формально допускает null.

Базовое состояние и действие

class Document {
    private final String title;
    Document(String title) {
        this.title = java.util.Objects.requireNonNull(title);
    }
    String summary() { return title; }
}

Конструктор устанавливает обязательный заголовок. Клиент получает операцию описания; внутреннее поле закрыто.

Проследите создание документа с заголовком Guide. Найдите место, которое запрещает отсутствие заголовка, и доступную клиенту операцию.

Дополнительное состояние подкласса

class TextDocument extends Document {
    private final int characters;
    TextDocument(String title, int characters) {
        super(title);
        if (characters < 0) throw new IllegalArgumentException();
        this.characters = characters;
    }
    int characters() { return characters; }
}

new TextDocument("Notes", 120) создаёт один экземпляр с двумя полями. super(title) устанавливает заголовок через конструктор Document, затем конструктор подкласса проверяет и записывает число символов.

Нарисуйте один объект с title и characters. До присваиваний поля имеют null и 0; после завершения создания — “Notes” и 120. Укажите, какой конструктор выполняет каждое присваивание.

Переопределение операции

В тело TextDocument входит собственная реализация базовой операции:

@Override
String summary() {
    return super.summary() + ": " + characters + " chars";
}

Переопределение предоставляет новое тело метода экземпляра с той же сигнатурой. Для показанных методов сигнатура — имя и список типов параметров; возвращаемый тип в неё не входит. super.summary() вызывает базовое тело на том же объекте. Оно читает закрытое поле title; отдельный подкласс напрямую к этому полю обращаться не может. Оба класса находятся в одном пакете.

Замените мысленно super.summary() на summary(). Вызов вернётся в то же переопределение и будет повторяться до StackOverflowError. Затем измените имя метода: при наличии @Override компилятор обнаружит отсутствие переопределяемой операции.

Конструкторы базового и производного классов

Document plain = new Document("Guide");
TextDocument text = new TextDocument("Notes", 120);
// new TextDocument("Notes"); // ошибка: такого конструктора нет

Конструкторы не наследуются. TextDocument(String, int) объявлен в подклассе; Document(String) используется через super(title).

Если явного this(...) или super(...) нет, подразумевается super(). У Document такого конструктора нет, поэтому удаление super(title) из показанного подкласса приводит к ошибке компиляции.

Попросите проследить один вызов new до двух тел конструкторов. Предложите добавить TextDocument(String title) { this(title, 0); } и установить, какой из двух конструкторов подкласса действительно записывает characters.

Статический тип и динамический вызов

Document value = new TextDocument("Notes", 120);
System.out.println(value.summary()); // Notes: 120 chars
// value.characters();              // ошибка компиляции

Статический тип value — Document: в нём есть summary(), но нет characters(). Фактический класс получателя — TextDocument; по нему при выполнении выбирается переопределённое тело summary(). Этот выбор называется динамическим связыванием.

value: Document ──> TextDocument { title="Notes", characters=120 }

На схеме отдельно укажите тип переменной и класс объекта. Спросите, исчезло ли поле characters при присваивании ссылки. Затем предложите предсказать результат summary, если создать обычный Document(“Notes”).

Общий алгоритм обработки документа

static void print(Document document) {
    System.out.println(document.summary());
}
print(new Document("Guide"));       // Guide
print(new TextDocument("Notes", 120)); // Notes: 120 chars

Полиморфизм подтипов позволяет одному клиенту работать с объектами разных классов через общий тип. В print нет проверки конкретного класса: новый согласованный подтип участвует в том же действии без добавления ветви.

Предложите новый подкласс с другим summary. Спросите, какая строка print должна поменяться, если новый тип сохраняет договор.

Перегрузка и динамический вызов

static String kind(Document d) { return "Document"; }
static String kind(TextDocument d) { return "Text"; }
TextDocument text = new TextDocument("Notes", 120);
Document value = text;
System.out.println(kind(value));     // Document
System.out.println(kind(text));      // Text
System.out.println(value.summary()); // Notes: 120 chars

Перегрузка задаёт одно имя с разными сигнатурами. Компилятор выбирает kind по статическому типу аргумента: обе переменные ведут к одному объекту, но выбор перегрузки различается. Для выбранной операции summary() тело определяется фактическим классом получателя.

Закройте комментарии результата и попросите сначала назвать типы аргументов двух kind. После их выбора перейдите к summary. При замене value на text в последней строке выбранное тело останется тем же.

Поведенческий контракт подтипа

Контракт операции определяет допустимый вход, результат, изменение состояния и условия отказа. Для Document.summary() каждый созданный документ возвращает строку, отличную от null; клиент может сразу запросить её длину.

Поведенческая подстановка сохраняет эти условия при передаче подкласса. Допустимый базовому клиенту вызов должен оставаться допустимым, а результат и состояние — удовлетворять требованиям базовой операции.

Попросите сформулировать условие, достаточное для вызова summary().length(). Отдельно спросите о пустой строке: она разрешена, и её длина равна нулю. Тип String допускает null; контракт summary требует результата, отличного от null.

Нарушение контракта документа

class SilentDocument extends Document {
    SilentDocument(String title) { super(title); }
    @Override String summary() { return null; }
}
static int summaryLength(Document d) { return d.summary().length(); }

summaryLength(new TextDocument("Notes", 120)) возвращает 16. Для new SilentDocument("Notes") вызов length() завершается NullPointerException: переопределение вернуло запрещённое контрактом значение.

Компилятор принимает обе реализации, поскольку тип String допускает null. Поведенческая подстановка.

Укажите точное место отказа: summary завершился нормально, следующее обращение к length выполнено через null. Предложите вернуть “” и сравните наблюдаемую длину с отсутствием результата.

Разделение построения и отправки сообщения

Полученное описание документа можно включить в напоминание о возврате. ConsoleReminder формирует текст и печатает его:

class ConsoleReminder {
    void remind(String title) {
        send("Return: " + java.util.Objects.requireNonNull(title, "title"));
    }
    protected void send(String message) {
        System.out.println(java.util.Objects.requireNonNull(message));
    }
}

Подкласс может переопределить send для записи в память. Добавление независимого префикса потребует сочетаний: консоль или память, с префиксом или без него.

Предложите new ConsoleReminder().remind(“Java”) и восстановите строку Return: Java. Затем перечислите четыре сочетания получателя и префикса. Спросите, какие два действия изменяются независимо друг от друга.

Интерфейс отправителя

Интерфейс объявляет ссылочный тип и операции общей роли:

public interface Sender {
    void send(String message);
}

send неявно public abstract. Он обрабатывает одно сообщение, отличное от null, способом, определённым реализацией. Передача null вызывает NullPointerException до обработки. Последовательные вызовы сохраняют порядок обращений. Глава 13.

abstract обозначает метод без тела, реализацию которого предоставляет конкретный класс. Сам интерфейс нельзя создать вызовом new Sender().

Попросите сопоставить тип String и дополнительное требование к аргументу. void означает отсутствие результата вызова. Попросите назвать наблюдаемый эффект отправки в консоль и в буфер.

Реализация интерфейсной операции

public final class ConsoleSender implements Sender {
    @Override
    public void send(String message) {
        System.out.println(java.util.Objects.requireNonNull(message));
    }
}

implements Sender устанавливает отношение подтипов. Метод реализации должен оставаться public; уменьшение доступа до пакетного запрещено. new ConsoleSender().send("A") печатает A и завершение строки.

Одного совпадения имени и параметров метода у постороннего класса недостаточно: связь с Sender должна следовать из объявления типов.

Предложите убрать public у send и объяснить ошибку. Затем уберите implements: метод сохранится, но присваивание Sender s = new ConsoleSender() перестанет компилироваться. Java использует объявленную связь типов.

Композиция и делегирование

public final class Reminder {
    private final Sender sink;
    public Reminder(Sender sink) {
        this.sink = java.util.Objects.requireNonNull(sink, "sink");
    }
    public void remind(String title) {
        sink.send("Return: " + java.util.Objects.requireNonNull(title, "title"));
    }
}

Композиция связывает объекты через поле: напоминание использует отправителя как часть своего поведения. Делегирование передаёт ему действие вызовом sink.send(...). Сам Reminder предоставляет операцию remind.

Нарисуйте два объекта и ссылку sink. Попросите найти отдельно хранение связи и передачу действия. final закрепляет ссылку; второй клиент может получить ссылку на того же отправителя.

Вызов через интерфейсное поле

Sender sender = new ConsoleSender();
Reminder reminder = new Reminder(sender);
reminder.remind("Java"); // Return: Java

Reminder.remind строит строку "Return: Java" и вызывает send через поле типа Sender. Его получатель имеет класс ConsoleSender, поэтому выполняется тело с println.

reminder → Reminder { sink ──> ConsoleSender }

Проведите аргумент “Java” через построение строки к println. Спросите, на каком этапе известен метод интерфейса, а на каком выбирается тело ConsoleSender.send. Клиент Reminder использует ту же диспетчеризацию, что и клиент Document.

Изменяемое состояние отправителя

public final class RecordingSender implements Sender {
    private final StringBuilder text = new StringBuilder();
    public void send(String message) {
        text.append(java.util.Objects.requireNonNull(message));
        text.append('\n');
    }
    public String text() { return text.toString(); }
}

StringBuilder — изменяемый буфер. append добавляет текст, toString() возвращает строку с текущим содержимым. После send("A") пустой буфер содержит "A\n"; после send("B") — "A\nB\n".

Попросите указать объект, чьё состояние изменилось, и поле, чья ссылка сохранилась. Возвращённая из text строка не изменится после последующих добавлений в буфер.

Замена участника композиции

RecordingSender log = new RecordingSender();
Reminder reminder = new Reminder(log);
reminder.remind("Java");
reminder.remind("C++");
System.out.print(log.text());
// Return: Java
// Return: C++

Поле sink и переменная log ведут к одному отправителю. Каждый вызов добавляет строку в его буфер. Тело Reminder осталось тем же; другой объект в конструкторе изменил способ обработки сообщения.

Предложите создать два Reminder с этим же log. Их сообщения накопятся в общем буфере. При двух разных RecordingSender истории будут раздельными. Попросите отметить различие на схеме ссылок.

Дополнительное ограничение на входе

Контракт Sender допускает любую строку, отличную от null, включая "". Следующая реализация добавляет требование непустого сообщения:

final class NonEmptySender implements Sender {
    public void send(String message) {
        java.util.Objects.requireNonNull(message);
        if (message.isEmpty())
            throw new IllegalArgumentException("Пустое сообщение");
        System.out.println(message);
    }
}

Предусловие определяет, какой вход допустим для операции. NonEmptySender усилил его: существующей строки уже недостаточно, нужна непустая. Сигнатура по-прежнему реализует Sender.send.

Сравните null, пустую строку и строку A. Отсутствующая ссылка запрещена исходным договором; пустая строка запрещена только новым ограничением. Назовите точное условие, после которого прежний допустимый вход отвергается.

Усиление предусловия и допустимые вызовы

static void sendEmpty(Sender sender) { sender.send(""); }

RecordingSender log = new RecordingSender();
sendEmpty(log);
System.out.println(log.text().length()); // 1: только '\n'

try { sendEmpty(new NonEmptySender()); }
catch (IllegalArgumentException ex) {
    System.out.println("Пустая строка отвергнута");
}

Клиент передаёт разрешённое пустое сообщение. RecordingSender сохраняет завершение строки; NonEmptySender отказывает из-за нового ограничения. Такая реализация нарушает поведенческую подстановку.

У SilentDocument допустимый вызов давал запрещённый результат null. Здесь запрещён сам прежний допустимый вход. Оба нарушения совместимы с правильной сигнатурой метода.

Проследите один и тот же sendEmpty с двумя получателями. У первого вызов нормально завершается и изменяет буфер; у второго исключение возникает до печати. Отделите этот отказ от нарушения требования к результату summary.

Обёртка как реализация интерфейса

public final class PrefixSender implements Sender {
    private final Sender target;
    private final String prefix;
    public PrefixSender(Sender target, String prefix) {
        this.target = java.util.Objects.requireNonNull(target);
        this.prefix = java.util.Objects.requireNonNull(prefix);
    }
    public void send(String message) {
        target.send(prefix + java.util.Objects.requireNonNull(message));
    }
}

Обёртка реализует Sender, поэтому её можно передать в Reminder. Поле target тоже имеет тип Sender: цель может быть консолью, буфером или другой обёрткой. Перед вызовом цели send добавляет префикс.

Проведите цепочку ссылок от Reminder через PrefixSender до получателя. Reminder вызывает send у своего sink; PrefixSender и RecordingSender реализуют эту операцию. Напоминание формирует текст, префикс дополняет его, последний получатель сохраняет строку.

Последовательность делегирования

RecordingSender log = new RecordingSender();
Sender sender = new PrefixSender(log, "[library] ");
new Reminder(sender).remind("Java");
System.out.print(log.text());

Буфер содержит "[library] Return: Java\n". По цепочке проходит текст:

Reminder → PrefixSender → RecordingSender
"Java"     "Return: Java"  "[library] Return: Java"

Каждый вызов получает свой this; поля и действия принадлежат трём объектам.

Проследите текст по цепочке и отметьте место добавления префикса. Затем мысленно поменяйте местами две обёртки с разными префиксами: порядок станет наблюдаемым.

Порядок композиции

RecordingSender log = new RecordingSender();
Sender sender = new PrefixSender(new PrefixSender(log, "B:"), "A:");
sender.send("X");
System.out.print(log.text()); // B:A:X и перевод строки

Внешняя обёртка получает "X" и передаёт "A:X"; внутренняя добавляет "B:". Перестановка префиксов даст "A:B:X".

Объект цели определяет место обработки. Объекты обёрток и их порядок определяют оформление; класс Reminder сохраняется. [4]

Проведите два вызова send по полям target. Затем замените только log на ConsoleSender: порядок строковых преобразований сохранится, результат станет виден сразу в стандартном выводе.

Несколько интерфейсных ролей

interface Counted { int count(); }
final class CountingSender implements Sender, Counted {
    private final Sender target;
    private int count;
    CountingSender(Sender target) {
        this.target = java.util.Objects.requireNonNull(target);
    }
    public void send(String message) {
        target.send(java.util.Objects.requireNonNull(message));
        count++;
    }
    public int count() { return count; }
}

CountingSender обрабатывает текст и предоставляет число нормальных завершений send. При исключении из цели увеличение пропускается. Количество в опыте помещается в int.

Проследите начальный count=0, нормальную отправку и отправку null. Счётчик станет 1 и останется 1. Увеличение после Integer.MAX_VALUE переполнило бы int; точный длительный учёт требует другого представления.

Две ссылки на один объект

CountingSender object = new CountingSender(new RecordingSender());
Sender sender = object;
Counted statistics = object;
sender.send("A");
sender.send("B");
System.out.println(statistics.count()); // 2

Sender разрешает отправку, Counted — чтение счётчика. Все три ссылки ведут к одной обёртке с одним полем count. Интерфейсы не добавляют полей экземпляра и конструкторов.

В C++ абстрактные базовые классы могут задавать несколько ролей и нести состояние. Java допускает один непосредственный суперкласс и несколько интерфейсов без собственного состояния экземпляра.

Попросите найти причину ошибки sender.count(): значение ссылки подходит, но статический тип не предоставляет операцию. Измените только тип переменной на CountingSender и сравните доступные методы.

Метод интерфейса с общей реализацией

В расширенное объявление Sender добавлен метод с телом:

default void sendAll(String[] messages) {
    java.util.Objects.requireNonNull(messages);
    for (String message : messages) send(message);
}

Модификатор default позволяет реализациям Sender унаследовать этот обход. Для нового пустого RecordingSender log вызов log.sendAll(new String[]{"A", "B"}) вызывает send дважды. Оба вызова выбирают тело RecordingSender; буфер получает "A\nB\n".

Массив обходится в порядке индексов. Первое исключение прекращает обход, предыдущие действия сохраняются. Класс может переопределить sendAll.

Укажите один и тот же получатель для sendAll и двух внутренних send. Предложите вход {“A”, null, “B”} и попросите предсказать состояние буфера в момент отказа.

Частичный эффект до отказа

RecordingSender log = new RecordingSender();
try { log.sendAll(new String[]{"A", null, "B"}); }
catch (NullPointerException e) { System.out.println("rejected"); }
System.out.print(log.text());

Вывод: rejected, затем A на новой строке. Первая отправка уже сохранена; null отвергнут, отправка B не выполнена. Проверка всех элементов перед отправкой отвергла бы такой вход до первого действия. Даже при допустимых элементах получатель может завершить одну из отправок исключением; предыдущие эффекты этот цикл не отменяет.

Остановите трассу на null и назовите уже выполненную отправку. Попросите отделить предварительную проверку входа от возможности откатить внешнее действие.

Новая операция для существующих реализаций

Абстрактный sendAll потребовал бы дополнить старые реализации при перекомпиляции. Тело default даёт им общий способ выполнения через send.

При этом требование «вся группа либо ничего» из прежней операции не следует: уже выполненную отправку цикл отменить не умеет. Новое поведение требует согласования договора и возможностей получателя. [3], [6]

Объясните исторический мотив default: развитие опубликованных интерфейсов без обязательной одновременной переделки всех реализаций. Затем вернитесь к собственному примеру: компиляция ConsoleSender сохранилась, но из этого не следует атомарность группы. Альтернатива — внешний статический обход, принимающий Sender; он сохраняет интерфейс, но не даёт конкретному классу переопределить новую операцию. Обсудите получателя с пакетной отправкой: ему полезна возможность собственного выполнения общего договора.

Статические и закрытые методы интерфейса

Статическая фабрика в Sender создаёт консольного отправителя:

static Sender console() { return new ConsoleSender(); }

Вызов Sender.console().send("A") печатает A. Фабрика вызывается через имя интерфейса и не наследуется как метод экземпляра.

Закрытые методы с телом могут обслуживать другие методы интерфейса; клиенты и реализации напрямую к ним не обращаются. Поля интерфейса неявно public static final: это общие поля типа. Ссылка в таком поле может вести к изменяемому массиву.

Для interface Codes { int[] VALUES = {1}; } предложите две операции: Codes.VALUES = new int[]{2} и Codes.VALUES[0] = 2. Первая запрещена, вторая меняет компонент общего массива. Свяжите это с final у поля text.

Зависимости общего клиента

Document объединяет заголовок и операцию описания. Подкласс TextDocument принимает это состояние и уточняет описание.

Sender задаёт операцию для независимых реализаций. Reminder хранит участника этой роли; замена участника меняет способ отправки без изменения формирования напоминания.

У наследования базовые вызовы на this могут попасть в переопределение подкласса. У композиции вызов цели получает отдельный объект; его внутренние действия выполняются на этой цели.

Вернитесь к одному объекту TextDocument и трём объектам в цепочке Reminder. Попросите указать this в каждом вызове. При новой комбинации префикса и получателя изменяется сборка объектов, при новом виде документа — подкласс.

Объект как значение данных

Счётчик отправителя меняется после каждой успешной обработки. Отчёту может понадобиться число на определённый момент — отдельный снимок:

record DispatchStats(int count) implements Counted {}

record объявляет запись: класс с компонентами, заданными в заголовке. Компонент count создаёт закрытое поле final int count и открытый метод count(). Этот метод уже реализует операцию Counted. Глава 14.

Предложите сравнить хранение CountingSender в отчёте и копирование полученного от него числа. Первый вариант сохраняет доступ к меняющемуся участнику, второй фиксирует числовое значение.

Снимок изменяемого счётчика

CountingSender sender = new CountingSender(new RecordingSender());
sender.send("A");
sender.send("B");
DispatchStats saved = new DispatchStats(sender.count());
sender.send("C");
System.out.println(sender.count()); // 3
System.out.println(saved.count());  // 2

Конструктор записи получил число 2. Последующая отправка изменила поле внутри CountingSender; компонент другого объекта сохранился. Через тип Counted доступны оба участника, поскольку у каждого есть операция count().

Нарисуйте отдельно поле счётчика и компонент saved. При send(“C”) отметьте единственное изменившееся число. Уточните, что интерфейс count() задаёт чтение, а наличие других изменяющих операций зависит от класса.

Стандартные члены записи

Координата объединяет два числовых компонента в одно значение:

record Point(int x, int y) {}
Point a = new Point(2, 3);
Point b = new Point(2, 3);
System.out.println(a.x());       // 2
System.out.println(a.equals(b)); // true
System.out.println(a == b);      // false

Канонический конструктор принимает x и y в порядке заголовка. Открытые методы x() и y() читают закрытые final-поля. Стандартный equals сравнивает оба компонента; == проверяет идентичность. [7]

Попросите объяснить одновременно equals=true и ==false. Затем назовите имена методов чтения: они совпадают с именами компонентов.

Представление для наблюдения

System.out.println(new Point(2, 3)); // Point[x=2, y=3]

toString отражает компоненты. Равенство требует того же типа записи и равных соответствующих значений. Другая запись ScreenPoint(int x, int y) с теми же числами не равна Point. Равные записи имеют одинаковый hashCode; совпадение хешей допускается и у разных значений.

Покажите, откуда toString получил имена x и y. Формат служит наблюдению; для внешнего формата хранения нужны отдельные требования.

Ограничения объявления записи

Запись неявно final и непосредственно расширяет java.lang.Record. Объявить её подкласс или указать другой суперкласс нельзя. Интерфейсы разрешены: DispatchStats реализует Counted.

Дополнительные поля экземпляра запрещены: всё его состояние представлено компонентами. Можно объявлять методы, статические поля и вложенные типы.

Представление записи и её API

record Point(int x, int y) делает два компонента частью API: конструктор принимает их значения, методы чтения их возвращают, равенство и хеш учитывают их содержимое.

Добавление int z изменит форму конструктора и равенство. Обычный класс может изменить внутреннее хранение, сохранив публичные методы; у записи заголовок связывает представление и публичные операции. [1]

Присваивание Point same = a по-прежнему копирует ссылку. Новая координата создаётся отдельным new Point(...).

Попросите перечислить, что изменится у клиента после добавления z. Затем сопоставьте same == a и new Point(a.x(), a.y()).equals(a): первое действие сохраняет объект, второе создаёт равное значение.

Проверка компонентов

record Interval(int start, int end) {
    Interval {
        if (start > end) throw new IllegalArgumentException();
    }
    boolean contains(int x) { return start <= x && x <= end; }
}

Тело Interval { ... } — компактный канонический конструктор: его параметры взяты из заголовка записи. new Interval(2, 5).contains(4) даёт true; new Interval(5, 2) бросает IllegalArgumentException. После нормального завершения тела параметры присваиваются полям автоматически.

Разберите равные границы и обратный порядок границ. Спросите, в какой момент значения параметров присваиваются компонентным полям.

Нормализация параметра

record BookCode(String value) {
    BookCode {
        value = java.util.Objects.requireNonNull(value).strip();
        if (value.isEmpty()) throw new IllegalArgumentException();
    }
}
System.out.println(new BookCode(" A-17 ").value()); // A-17

strip() удаляет краевые пробельные символы. В поле попадёт нормализованный параметр; строка из одних пробелов отвергается. Прямое присваивание компонентному полю в компактном конструкторе запрещено.

Проследите переменную параметра value до и после strip. Запись в параметр отличается от запрещённого присваивания this.value внутри компактного конструктора.

Нормализация сведений о студенте

В учебном журнале код и имя разделяются символом ;, одна строка описывает одного участника. Запись grade.Student хранит код, имя и балл. Нормализация и проверка строк в её компактном конструкторе:

public record Student(String id, String name, int score) {
    public Student {
        java.util.Objects.requireNonNull(id);
        java.util.Objects.requireNonNull(name);
        id = id.strip();
        name = name.strip();
        if (id.isEmpty() || name.isEmpty()
                || hasSeparator(id) || hasSeparator(name)) {
            throw new IllegalArgumentException("неверный код или имя");
        }

Попросите назвать результат нормализации строки с краевыми пробелами. Затем предложите имя с разделителем внутри и найдите, какое условие его отклонит.

Диапазон балла и разделители записи

Продолжение конструктора и закрытый метод проверки:

        if (score < 0 || score > 100) {
            throw new IllegalArgumentException("балл вне диапазона 0..100");
        }
    }

    private static boolean hasSeparator(String value) {
        return value.indexOf(';') >= 0 || value.indexOf('\n') >= 0
            || value.indexOf('\r') >= 0;
    }
}

Балл принадлежит диапазону 0..100. Конструктор проверяет одну запись; уникальность кода среди нескольких записей проверяется при работе с каталогом. Равенство Student сравнивает все три компонента.

Сравните локальное ограничение балла и уникальность id в каталоге. Для второго свойства одной записи недостаточно: нужен контекст множества записей.

Нормализация и равенство записей

Student a = new Student(" s1 ", " Ada ", 90);
Student b = new Student("s1", "Ada", 80);
System.out.println(a.id());      // s1
System.out.println(a.name());    // Ada
System.out.println(a.equals(b)); // false

Конструктор сохранил нормализованные s1 и Ada. Баллы 90 и 80 различаются, поэтому записи не равны. Повторяющийся код допустим для двух отдельных значений; уникальность проверяется на уровне каталога.

Попросите объяснить равенство имён и неравенство записей через все компоненты. equals этой модели сравнивает id, name и score.

final-компонент и общий массив

record Draft(int[] scores) {}
int[] scores = {80};
Draft draft = new Draft(scores);
scores[0] = 90;
System.out.println(draft.scores()[0]); // 90

Поле записи хранит ту же ссылку, что переменная scores. Запись scores[0] = 90 меняет общий массив. final запрещает заменить компонентную ссылку; элементы доступного по ней массива изменяемы.

Нарисуйте массив и ссылку на него внутри записи. Изменение внешнего scores проходит к тому же элементу.

Защитное копирование массива

У последовательности баллов внешнее изменение нужно исключить. В записи Scores конструктор и метод чтения создают копии:

Scores {
    values = java.util.Objects.requireNonNull(values).clone();
}
public int[] values() { return values.clone(); }

Это члены record Scores(int[] values). Первая копия изолирует входной массив, вторая — результат чтения. Равенство, хеш и строковое представление этой записи также определены по элементам массива.

Предложите убрать по одному из clone. Без копии на входе сохранится путь через исходный массив; без копии на выходе клиент сможет изменить внутренние данные через values(). Массив int не содержит изменяемых вложенных объектов.

Наблюдение после изменения копий

Последовательность создана из массива с единственным баллом 80:

int[] input = {80};
Scores scores = new Scores(input);
input[0] = 90;
scores.values()[0] = 100;
System.out.println(scores.values()[0]); // 80

Изменились входной массив и выданная копия. Массив внутри scores сохранил значение 80; новый вызов values() вновь копирует это состояние.

Нарисуйте три массива: вход, внутреннее состояние и результат первого чтения. Проведите каждое присваивание к своей ячейке. Последний вызов возвращает ещё одну копию сохранённого внутреннего массива.

Массивный компонент и равенство записи

record Vector(int[] values) {}
Vector a = new Vector(new int[]{1, 2});
Vector b = new Vector(new int[]{1, 2});
System.out.println(a.equals(b)); // false

Массивы используют равенство по идентичности. Стандартный equals записи обращается к равенству компонента, поэтому одинаковых чисел в разных массивах недостаточно.

У Scores защитные копии тоже создают разные массивы. Поэлементное равенство требуется, чтобы восстановленная через new Scores(scores.values()) запись была равна исходной.

Попросите сравнить две ссылки на один массив и два массива с одинаковыми элементами. Затем укажите, почему clone на обеих границах требует дополнительного решения о равенстве значения Scores.

Проверка типа перед сравнением компонентов

Метод equals получает аргумент типа Object. Образец типа other instanceof Scores that проверяет, ссылается ли он на Scores:

@Override public boolean equals(Object other) {
    return other instanceof Scores that
        && java.util.Arrays.equals(values, that.values);
}

При успехе that обозначает тот же объект с типом Scores. Правая часть && выполняется только после успешной левой проверки. Поэтому в ней доступна that, а внутри Scores разрешено читать закрытое поле другого экземпляра этого класса.

Для null и другого типа проверка ложна: правая часть пропускается, весь equals возвращает false. Для двух Scores Arrays.equals сравнивает длины и соответствующие числа.

Разберите other=null и other=“80” до правой части: чтения that.values не произойдёт. Затем дайте ссылку на Scores и укажите тот же объект, который теперь доступен под именем that.

Согласованное равенство последовательности

Аргумент scores.equals(...) Результат Основание

enum LoanStatus { AVAILABLE, BORROWED, LOST }

Запечатанная семья результатов

Поиск книги по уникальному коду возвращает найденное название или причину отсутствия. У этих случаев разный состав данных:

sealed interface SearchResult permits Found, Missing {}
record Found(String title) implements SearchResult {}
record Missing(String reason) implements SearchResult {}

sealed ограничивает непосредственные реализации списком permits. Записи уже final; обычный непосредственный класс-реализация выбирает final, sealed или non-sealed. Последний открывает свою ветвь расширения. Подинтерфейс выбирает sealed или non-sealed, поскольку final у интерфейса недопустим. [9]

Попросите создать new Found(“Java”) и new Missing(“Нет такого кода”). Оба значения допустимы в переменной SearchResult. Если ссылка отлична от null, её фактический класс сообщает, какие данные результата доступны.

Покрытие вариантов в switch

static String describe(SearchResult value) {
    return switch (value) {
        case Found f -> "Found: " + f.title();
        case Missing m -> "Missing: " + m.reason();
    };
}

describe(new Found("Java")) возвращает "Found: Java". Образец Found f проверяет класс и даёт типизированную ссылку f; во второй ветви m ссылается на Missing.

Компилятор проверяет обе разрешённые ветви. Добавление нового варианта потребует учёта при повторной компиляции. Для null без case null вызов завершится NullPointerException.

Сопоставьте одну и ту же переменную value с разными классами полученного результата. Попросите назвать доступный компонент в каждой ветви. Проверка класса и чтение title выполняются последовательно.

Роль и вариант данных

Открытый Sender допускает новый способ отправки при прежнем вызове клиента. Новая обязательная операция, напротив, затронет реализующие классы.

Для закрытого SearchResult новый отчёт можно написать отдельным полным switch, сохранив варианты. Добавление варианта потребует пересмотреть такие разборы. Проверяемая полнота требует согласования изменений семьи и её клиентов.

Предложите четыре изменения: новый отправитель, новая обязательная операция отправителя, ещё один отчёт о поиске, ещё один результат поиска. Для каждого назовите сторону, которая должна измениться. Закрытая семья полезна, когда автор управляет составом исходов и хочет проверять полноту их обработки; открытая роль позволяет независимо добавлять реализации.

Расширение системы и обработка вариантов

Новая реализация Sender сохраняет вызов sink.send(message) в Reminder, если соблюдает условия операции. Место обработки текста определяется переданным объектом.

Новый вариант SearchResult меняет набор исходов, которые должен различать клиент. При повторной компиляции switch без default потребует его обработки.

DispatchStats сохраняет число на момент создания. Дополнительный вызов send изменит отправителя, а отчёт продолжит читать сохранённое значение.

Предложите три изменения: запись сообщений в файл, неоднозначный поиск, новая отправка после отчёта. Для каждого попросите назвать изменяющийся класс, метод клиента либо объект состояния и объяснить выбор.

Сокрытие поля

class Base { String label = "base"; }
class Child extends Base { String label = "child"; }
Base value = new Child();
System.out.println(value.label); // base

В объекте есть два поля. Выражение выбирает поле по статическому типу. Одинаковые имена затрудняют различение двух полей и хранимых в них значений. [8]

Сопоставьте доступ к полю и вызов переопределённого метода. Укажите статический тип выражения, по которому выбрано объявление поля.

Сокрытие статического метода

class Base { static String kind() { return "base"; } }
class Child extends Base { static String kind() { return "child"; } }
System.out.println(Base.kind());  // base
System.out.println(Child.kind()); // child

У статического метода нет получателя для динамического выбора. Вызов через имя класса явно указывает источник выбора статического метода.

Попросите назвать отсутствие текущего получателя у static. Запишите вызовы через имена классов, чтобы источник выбора был виден.

Сигнатура переопределяемого метода

У операции загрузки документа объявлен результат типа Document и разрешено проверяемое исключение ввода-вывода IOException. Источник в памяти возвращает уже сохранённый TextDocument. Базовый класс abstract оставляет метод load без тела; конкретный подкласс обязан его реализовать:

abstract class DocumentSource {
    protected abstract Document load() throws java.io.IOException;
}
final class MemorySource extends DocumentSource {
    private final TextDocument document;
    MemorySource(TextDocument document) {
        this.document = java.util.Objects.requireNonNull(document);
    }
    @Override public TextDocument load() { return document; }
}

Доступ расширен от protected до public; результат уточнён до подтипа; разрешённое проверяемое исключение опущено. Такое переопределение допустимо.

Сопоставьте возвращённую ссылку с полем document: обе ведут к одному объекту. Отдельный экземпляр документа при вызове load не создаётся. Уточнение результата называют ковариантностью возвращаемого типа. Сопоставьте три изменения заголовка: доступ, результат и throws.

Статический тип результата

MemorySource memory = new MemorySource(new TextDocument("Notes", 120));
TextDocument text = memory.load();
DocumentSource source = memory;
Document document = source.load();
System.out.println(document == text); // true
// TextDocument another = source.load(); // Ошибка типов.

При обращении через DocumentSource компилятор видит результат Document и возможность IOException. Вызывающий метод обрабатывает её или объявляет throws java.io.IOException; фактическое тело MemorySource её не бросает. Нельзя уменьшать доступность или расширять разрешённые проверяемые исключения. В частности, private load вместо public load нарушил бы доступность унаследованного метода.

private-метод не переопределяется. final-метод закрыт для переопределения. Метод с другим списком типов параметров может стать перегрузкой; @Override помогает увидеть случайную замену сигнатуры. [10]

Вернитесь к двум статическим типам одной ссылки. Через memory результат имеет тип TextDocument; через source — Document. Ошибочная строка не меняет фактический объект: компилятор останавливается до выполнения. Сопоставьте допустимую сигнатуру SilentDocument.summary с нарушенным требованием к результату.

Абстрактная операция площади

abstract class Shape {
    abstract double area();
    final String report() { return "area=" + area(); }
}

У фигур есть общая операция площади, но формула зависит от вида. Абстрактный метод объявляет её без тела. new Shape() запрещён; конкретный подкласс предоставляет отсутствующую реализацию. Подкласс без такой реализации тоже должен быть объявлен abstract. Абстрактный класс может иметь поля, конструкторы и обычные методы. final у report сохраняет сам алгоритм построения строки. [8]

Спросите, что нужно общему report от фигуры. Реализация площади становится обязанностью конкретного подкласса.

Реализация площади в конкретной фигуре

final class Square extends Shape {
    private final double side;
    Square(double side) {
        if (!Double.isFinite(side) || side < 0)
            throw new IllegalArgumentException();
        this.side = side;
    }
    @Override double area() { return side * side; }
}
Shape shape = new Square(3);
System.out.println(shape.report()); // area=9.0

Конструктор принимает конечную неотрицательную сторону. Внутри report вызов area выбирает формулу Square. Произведение очень больших конечных double может переполниться до бесконечности.

Проследите report для квадрата со стороной 3. Попросите объяснить, почему тело report обойдётся без проверки класса.

Описание типа объектом Class

Рефлексия — исследование структуры программы во время выполнения. Student.class получает описание типа grade.Student, у которого объявлены String id, String name, int score:

Class<?> type = Student.class;
System.out.println(type.getName());    // grade.Student
System.out.println(type.isRecord());   // true
System.out.println(int.class.isPrimitive()); // true
System.out.println(Integer.class.isPrimitive()); // false

Class описывает тип; <?> обозначает неизвестный аргумент типа. Переменная получает описание Student через Student.class, включая имя пакета grade. Запись — ссылочный тип, int — примитивный; объект Class можно получить для обоих. Параметры типов: Глава 15.

Сопоставьте объект Student и объект, описывающий тип Student. Литерал int.class позволяет исследовать примитивный тип, не превращая число в Object.

Метаданные объявленных компонентов

for (var component : Student.class.getRecordComponents()) {
    System.out.println(component.getName() + ":" +
                       component.getType().getSimpleName());
}

Вывод: id:String, name:String, score:int на отдельных строках. При var компилятор выводит тип переменной из типа элемента массива. У обычного класса getRecordComponents() вернул бы null; здесь известно, что Student — запись. Изменение балла отдельного участника не меняет этот список: он определяется объявлением типа. Описание типа во время выполнения

Попросите получить порядок компонентов из объявления записи. Рефлексия сообщает порядок из объявления; допустимость балла проверяет конструктор.

Подстановка через базовый тип в C++ и Java

Java-присваивание Document value = new TextDocument(...) копирует ссылку. Оно не создаёт отдельный базовый объект и не срезает дополнительные поля.

В C++ сходный полиморфный сценарий использует указатель или ссылку на базовый тип и виртуальный метод. Обычный переопределяемый метод Java не требует отдельного слова virtual.

Попросите сравнить Java-присваивание ссылки с C++ ссылкой на базовый тип. Затем отделите от этого сценария копирование базового объекта C++ по значению.

Изменяемый квадрат и прямоугольник

У Rectangle операция setWidth(w) меняет ширину и сохраняет высоту. MutableSquare переопределяет её, меняя обе стороны ради их равенства. Начальные стороны равны 4, заданная ширина — 7:

Получатель После setWidth(7) area()
Rectangle(4, 4) ширина 7, высота 4 28
MutableSquare(4) ширина 7, высота 7 49

Квадрат нарушил требование операции сохранять высоту. Общий тип с одной операцией area() позволяет обеим фигурам предоставлять площадь без несовместимого изменения сторон. Изменяемый прямоугольник и квадрат.

Попросите указать точное нарушенное условие после первого присваивания. Математическое отношение фигур согласуется с чтением площади; набор изменяющих операций создаёт дополнительные требования к подстановке.

Динамический вызов при конструировании

class Parent {
    Parent() { show(); }
    void show() { System.out.println("parent"); }
}
class ChildState extends Parent {
    int value = 7;
    @Override void show() { System.out.println(value); }
}

new ChildState() печатает 0. Класс объекта уже определён, поле подкласса ещё не получило 7. [5]

Проследите вызов show из Parent до присваивания value=7. Тип объекта уже ChildState, обычный инициализатор поля ещё не выполнен.

Порядок инициализации и ранний вызов

поле value получает 0
→ Parent() вызывает ChildState.show(): вывод 0
→ инициализатор ChildState присваивает 7
→ new завершается; следующий child.show() выводит 7

В Java 25 допустим ограниченный пролог перед super(...). Простое присваивание собственному полю без инициализатора может установить его раньше. Базовый класс не управляет порядком всех будущих подклассов; вызов их переопределяемых методов связывает конструктор с их готовностью. Переопределяемые методы в конструкторе.

Сравните с C++: из базового конструктора виртуальный вызов для создаваемого объекта выбирает окончательное переопределение класса этого конструктора. В Java фактический класс уже ChildState. Предложите убрать ранний вызов и выполнить show после успешного new.

Общий участник и владение ресурсом

RecordingSender shared = new RecordingSender();
Reminder first = new Reminder(shared);
Reminder second = new Reminder(shared);
first.remind("Java");
second.remind("C++");

Оба поля sink ведут к одному буферу; он содержит две строки. final фиксирует каждую ссылку и допускает совместный доступ.

Если отправитель использует файл, его закрытие должно быть согласовано с обоими клиентами. Обычное ссылочное поле Java не выражает исключительное владение наподобие C++ std::unique_ptr.

Предложите первому напоминанию закрыть общий файловый отправитель до вызова второго. Спросите, какой участник должен знать срок общей работы, чтобы выбрать момент close. У показанного RecordingSender закрываемого ресурса нет.

Конфликт методов по умолчанию

interface A { default String label() { return "A"; } }
interface B { default String label() { return "B"; } }
class Both implements A, B {
    public String label() { return A.super.label() + B.super.label(); }
}

Результат AB. Без собственного тела конфликт независимых default-методов отвергается компилятором. Совместимый открытый метод экземпляра, унаследованный от класса, имеет приоритет перед интерфейсным телом.

Уберите тело label из Both и попросите объяснить причину неоднозначности. Затем проследите явные вызовы двух непосредственных суперинтерфейсов.

Устойчивый внешний код перечисления

enum Priority {
    LOW(1), NORMAL(5), HIGH(10);
    private final int weight;
    Priority(int weight) { this.weight = weight; }
    int weight() { return weight; }
}

Priority.HIGH.weight() возвращает 10. ordinal() означает положение константы в объявлении и не подходит как устойчивый внешний код после изменения порядка.

Мысленно переставьте LOW и HIGH. Сравните изменение ordinal с сохранением явно заданного weight.

Поиск с несколькими совпадениями

Поиск по названию может найти несколько книг. Клиенту нужно различить отсутствие совпадений и необходимость уточнить выбор. Новая версия семьи заменяет прежнее объявление:

sealed interface SearchResult permits Found, Missing, Ambiguous {}
record Found(String title) implements SearchResult {
    Found { java.util.Objects.requireNonNull(title); }
}
record Missing(String reason) implements SearchResult {
    Missing { java.util.Objects.requireNonNull(reason); }
}
record Ambiguous(int count) implements SearchResult {
    Ambiguous {
        if (count < 2) throw new IllegalArgumentException();
    }
}

Ambiguous(3) хранит три совпадения; Ambiguous(1) отвергается.

Сопоставьте следующие действия клиента: сообщить причину отсутствия или запросить уточнение. Конструкторы обеспечивают строки, отличные от null, и допустимое количество; эти ограничения относятся к данным конкретного варианта.

Проверка switch при расширении семьи

return switch (result) {
    case Found found -> "Found: " + found.title();
    case Missing missing -> "Missing: " + missing.reason();
    case Ambiguous many -> "Matches: " + many.count();
};

При добавлении Ambiguous прежние две ветви без default перестают компилироваться. Клиент должен решить, что означает новый результат. Для Ambiguous(3) здесь получится Matches: 3.

Конструкторы проверяют поля вариантов. Сам параметр result должен быть отличным от null: без case null переключение по null завершится исключением. [2]

Предложите убрать ветвь Ambiguous и назвать момент обнаружения пропуска. После восстановления ветви спросите, какие ограничения полей по-прежнему не проверены самим switch.
