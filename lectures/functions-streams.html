Функциональный интерфейс

@FunctionalInterface
interface StudentTest {
    boolean test(Student student);
}

Функциональный интерфейс задаёт одну абстрактную операцию. Здесь клиент вызывает test, передаёт Student и получает boolean. При наличии @FunctionalInterface компилятор проверяет это свойство интерфейса. Подходящий интерфейс функционален и без аннотации.

Показать три части сигнатуры test. Предложить добавить независимый абстрактный метод reset: компилятор с учётом аннотации выявит, что интерфейс перестал быть функциональным. Реализации пока нет; выбрать её предстоит вызывающему коду.

Вызов переданного правила

static List<Student> select(List<Student> source, StudentTest rule) {
    var result = new ArrayList<Student>();
    for (Student s : source) {
        if (rule.test(s)) result.add(s);
    }
    return List.copyOf(result);
}

Условие передано параметром. Каждый участник становится аргументом test.

Проследить одну итерацию с Lin: правило возвращает false, добавление пропускается. Спросить, что произойдёт при пустом source и кто владеет структурой result.

Анонимная реализация интерфейса

StudentTest condition = new StudentTest() {
    @Override public boolean test(Student student) {
        return student.score() >= 80;
    }
};
System.out.println(select(students, condition).size());

Анонимный класс задаёт реализацию test. Предскажите число вызовов этого метода и напечатанное число для трёх исходных участников.

Отделить создание condition от запуска select. Собрать прогнозы о вызовах и размере, затем открыть трассу; при расхождении пройти именно ветвь if.

Для имён Ada, Lin, Ann снова отобраны первая и третья записи, но теперь основание другое. Код обхода не изменился. Если балл Ann снизить до 50, отбор по имени всё ещё её сохранит.

Создание действия и вызов

StudentTest passed = s -> s.score() >= 80;
System.out.println(passed.test(new Student("s1", "Ada", 90))); // true

Инициализация задаёт действие. Тело выполняется при test с конкретным участником. Сохранённое действие можно вызвать неоднократно с разными данными.

Поставить паузу после присваивания passed: участник ещё не передан. Вторую строку разобрать как обычный вызов метода объекта.

Целевой тип лямбды

StudentTest a = (Student s) -> s.score() >= 80;
StudentTest b = s -> s.score() >= 80;
// var c = s -> s.score() >= 80; // ошибка компиляции

В первых строках сигнатура test даёт тип s. Для var такого контекста нет: лямбда не выбирает интерфейс самостоятельно.

Попросить найти источник типа s в каждой строке. Ошибка var связана с отсутствующим целевым интерфейсом; добавление явного типа параметра само по себе не выбирает интерфейс.

Тело выражения и тело блока

StudentTest valid = s -> {
    int score = s.score();
    return score >= 0 && score <= 100;
};

В теле-выражении результат задаёт выражение; в блоке нужен return. Все пути нормального завершения должны дать требуемый boolean.

Предложить убрать return и объяснить ошибку. Сравнить с уже знакомым методом void: для действия без результата блок заканчивается без возвращаемого значения.

Абстрактные операции интерфейса

default- и статические методы не увеличивают число абстрактных действий. Публичные методы Object не создают второе действие для определения функциональности.

Поэтому Comparator функционален, хотя объявляет compare и equals. При наличии @FunctionalInterface компилятор проверяет это свойство; отсутствие аннотации не запрещает лямбды.

Напомнить специальное правило для публичных методов Object на примере equals. Аннотацию представить как проверку объявления при его изменении.

  • Вычисление значения и внешний эффект.

Для получения имени, печати и создания списка попросить назвать параметры и результат. Затем для каждого действия указать наблюдаемый эффект, если он есть.

Методы стандартных интерфейсов

Тип Метод клиента Вход → результат
Predicate<Student> boolean test(Student s) участник → ответ
Function<Student, String> String apply(Student s) участник → строка
Consumer<String> void accept(String text) строка → без значения
Supplier<String> String get() без аргументов → строка

Для общего отбора подходит Predicate<Student>. Тело метода определяет вычисление, эффект и возможный отказ [3].

Для печати строки сначала выбрать Consumer по void, затем назвать accept. Для имени участника выбрать Function и apply. Не приписывать чистоту ни одному из этих интерфейсов.

Форма вызова и смысл действия

Predicate<Student> позволяет передать правило другим библиотечным операциям и объединить его с другим условием. Собственный StudentTest потребовал бы переходника на такой границе.

Совпадения формы недостаточно для любого договора: Comparator<T> и ToIntBiFunction<T, T> принимают два значения и возвращают int, но контракт компаратора дополнительно требует соблюдения законов порядка. [4]

Вспомнить транзитивность из лекции о коллекциях. Произвольное вычисление целого по двум участникам не становится сравнением только из-за типов параметров. Стандартная форма помогает совместимости, предметный интерфейс может выразить дополнительные обязательства или проверяемый отказ. Предложить объяснить, почему для select достаточно обычного предиката, а для сортировки библиотека принимает Comparator.

Получение предметного значения

Function<Student, String> name = s -> s.name();
System.out.println(name.apply(new Student("s1", "Ada", 90))); // Ada

Аргумент и результат могут иметь разные типы. Имя apply задано интерфейсом; пользовательская лямбда определяет конкретное преобразование.

Заменить мысленно name на id. Код останется типово корректным, но изменится смысл результата; это повод проверять содержательные примеры.

Вычисление и внешний эффект

Consumer<String> print = text -> System.out.println(text);
print.accept("готово"); // готово

accept возвращает void и печатает строку. Реализация Consumer может также изменять объект, если это допускает договор действия.

Попросить назвать наблюдаемый результат без возвращаемого значения. Указать строку в стандартном выводе, по которой виден вызов.

Отложенное получение значения

Supplier<List<Student>> empty = () -> List.of();
System.out.println(empty.get().size()); // 0

Аргументов нет. Поставщик не обязан каждый раз создавать новый объект: это зависит от переданного действия. Форма полезна для отложенного вычисления запасного значения.

Спросить, выполняется ли List.of при присваивании empty. Оно будет вызвано из get; интерфейс не требует новой коллекции при каждом вызове.

Вычисление отдельно от эффекта

}
static void announceAndBorrow(Book book) {
    System.out.println(label(book));
    book.borrow();
}

label вычисляет строку. Второй метод печатает её и меняет общую книгу.

Ссылка на метод

Function<Student, String> name = Student::name;
Function<String, Integer> parse = Integer::parseInt;

Первая ссылка получает объект и вызывает его метод; вторая обозначает статический метод. Круглых скобок вызова нет: аргумент появится позже.

Развернуть ссылки в лямбды: s -> s.name() и text -> Integer.parseInt(text). Аргумент будущего вызова занимает разные позиции.

Связанный метод и конструктор

Consumer<String> print = System.out::println;
Supplier<ArrayList<String>> create = ArrayList::new;
print.accept("Ada");
System.out.println(create.get().size()); // 0

println связан с выбранным объектом вывода. Конструкторная ссылка создаёт новый список при вызове поставщика.

Найти заранее выбранный System.out и будущий аргумент текста. Для create.get выделить создание объекта как выполняемую операцию.

Захват локального значения

int threshold = 80;
Predicate<Student> passed = s -> s.score() >= threshold;
// threshold = 90; // сделало бы захват недопустимым

Локальная переменная должна быть final или фактически окончательной. Захватываемой локальной переменной после инициализации не присваивают новое значение; до захвата она должна быть определённо инициализирована [8].

Предложить раскомментировать переприсваивание и сформулировать причину ошибки. Уточнить также инициализацию локальной переменной до захвата.

Захват ссылки на изменяемый объект

Student student = students.get(0); // s1/Ada/90
var log = new ArrayList<String>();
Consumer<Student> remember = s -> log.add(s.id());
remember.accept(student);
System.out.println(log); // [s1]

Ссылка log не переприсваивается, поэтому захват допустим. Список изменился. Его общее состояние связывает последовательные вызовы; при параллельной работе доступ к этому списку требует согласования.

Попросить указать, что изменилось: ссылка log сохранилась, содержимое списка стало другим.

Возвращаемое правило

static Predicate<Student> atLeast(int threshold) {
    return s -> s.score() >= threshold;
}
Predicate<Student> passed = atLeast(80);
var ann = new Student("s3", "Ann", 80);
System.out.println(passed.test(ann));

В какой строке проверяется балл? Какой аргумент передан каждому методу?

Разделить два вызова на доске. Сначала atLeast получает число и возвращает объект правила; попросить указать, почему в этом вызове ещё нет участника. Затем разобрать test.

Два момента вызова

Вызов Параметр Результат
atLeast(80) threshold = 80 Predicate<Student>
passed.test(ann) s = ann true, потому что 80 >= 80

Порог остаётся доступен после возврата atLeast. Повторный passed.test(...) получает нового участника с тем же порогом. Сравнение объектов правил через == не выражает этот договор.

Предложить Jo/79 и Ada/90 для двух последующих test. Получить false и true без повторного atLeast. Отметить, что спецификация не требует нового экземпляра лямбды при каждом вычислении выражения.

System.out.println(rule.test(ann));

System.out.println(rule.test(ann));

Локальная ссылка config не переприсваивается. Что изменено между вызовами?

Композиция предикатов

Predicate<Student> passed = s -> s.score() >= 80;
Predicate<Student> named = s -> s.name().startsWith("A");
var both = passed.and(named);

Если первый предикат ложен, второй не вызывается. Поэтому функции с побочными эффектами могут вести себя иначе после перестановки условий.

Для Lin первый предикат ложен: named пропускается. Предложить добавить в named диагностический вывод и предсказать его отсутствие при вызове both.test для этого участника.

Композиция преобразований

Function<String, Integer> length = String::length;
Function<Integer, Integer> twice = n -> n * 2;
System.out.println(length.andThen(twice).apply("Java")); // 8

andThen сначала вычисляет длину, затем удваивает. compose сначала применяет переданную функцию, затем текущую. Тип результата первого шага должен подходить второму.

Записать промежуточное значение 4, затем результат 8. Перестановка функций ограничена не только смыслом, но и типами входа.

Аргументы в двух вызовах

Function<Integer, Predicate<Student>> rules =
    threshold -> atLeast(threshold);
Predicate<Student> check80 = rules.apply(80);
boolean a = check80.test(new Student("s4", "Jo", 79));
boolean b = check80.test(new Student("s3", "Ann", 80));

apply получает порог и возвращает действие; test получает участника. Полученный check80 можно применять многократно. Передачу аргументов по одному через возвращаемые функции называют каррированием.

Назвать тип результата apply до вычисления a и b. Получить прогноз обоих ответов до открытия разбора. Сравнить с вложенной записью rules.apply(80).test(ann), в которой оба момента видны в одной строке.

Управление обходом

В собственном цикле программа явно переходит к следующему участнику. Метод select выполняет этот обход, оставляя клиенту выбор правила.

Stream обобщает передачу управления: клиент описывает связанные операции и нужный результат, библиотека организует проход. Она может соединять стадии без промежуточных списков и прекращать работу, когда ответ получен. [2]

Сопоставить две роли: автор select написал цикл, вызывающий код передал условие. Для Stream автор приложения передаёт библиотеке ещё и цепочку преобразований. Это даёт общий механизм ленивого обхода, но требует рассуждать о договоре результата и допустимых эффектах: количество вызовов действия нельзя выводить только из числа записанных стадий. Если приложению нужен собственный переход после каждого внешнего действия, цикл остаётся самостоятельным полезным решением.

Сверить первые два прогноза. Обвести скобки get в первом вызове: они запускают тело до orElse. Во втором вызове тело остаётся доступным через переданную ссылку.

Запасной результат при отсутствии

System.out.println(empty.orElseGet(fallback));

Каждый отдельный опыт печатает fallback, затем нет участников. orElseGet вызывает поставщика после обнаружения отсутствия. Выбранное поведение отсутствие → текст явно задано вызывающим кодом.

Развитие представления поведения

В Java обработчики и компараторы передавались объектами интерфейсов ещё до лямбд. Проект Project Lambda сократил запись передаваемого поведения, сохранив применение существующих интерфейсов [1].

Лямбда реализует операцию известного интерфейса. Совместимость с существующим API объясняет выбор целевого типа; у лямбды сохраняются собственные правила области видимости и захвата.

Попросить объяснить, почему метод, принимавший Comparator до появления лямбд, может принимать его лямбда-реализацию. Указать роль общего целевого типа.

Договор вызываемого объекта Python

Protocol описывает форму вызова: один позиционный Student → bool.

from dataclasses import dataclass
from typing import Protocol

@dataclass(frozen=True)
class Student:
    id: str
    name: str
    score: int

class StudentRule(Protocol):
    def __call__(self, student: Student, /) -> bool: ...

Прочитать __call__ как договор одного позиционного аргумента и bool. Объяснить роль слеша: имя параметра не становится требованием для именованного вызова. Сравнить с Java-методом test.

Реализация вызываемого объекта

def select(source: list[Student], rule: StudentRule) -> list[Student]:
    return [student for student in source if rule(student)]

class AtLeast:
    def __init__(self, threshold: int) -> None:
        self.threshold = threshold
    def __call__(self, student: Student, /) -> bool:
        return student.score >= self.threshold

AtLeast подходит по форме __call__, наследование от StudentRule для структурной проверки не требуется.

Проследить rule(student) до AtLeast.__call__. Показать, что threshold хранится у объекта, а Student поступает при каждом вызове.

Вызов Python-правила

Предскажите список имён:

            Student("s3", "Ann", 80)]
rule: StudentRule = AtLeast(80)

Истинность значения и договор bool

def wrong(student: Student, /) -> str:
    return student.name

bad: StudentRule = wrong
print([s.name for s in select(students, bad)])

Проверка типов отвергает str вместо bool. При прямом запуске непустые строки истинны в условии: выводятся Ada, Lin, Ann. Аннотации Python сами не проверяют результаты во время выполнения. Договор callback Protocol.

            String title = "inner";
            public String get() { return this.title; }
        };
    }
}

Получатель внутри действия

Лямбда возвращает outer: this взят из окружающего Context. Анонимный объект возвращает inner: this обозначает его самого.

Обе формы реализуют Supplier<String>, но правила области видимости различаются. JLS также не требует нового экземпляра лямбды при каждом вычислении выражения. Значение действия проверяют вызовом его операции [5], [8].

Типы композиции функций

Для Function<T, R> у andThen следующий шаг имеет тип Function<? super R, ? extends V>, а результат — Function<T, V>.

T → текущая функция → R → следующий шаг → V

Следующий шаг должен принять R; полученное значение должно подходить V. Если шаг выбросил исключение, цепочка прекращается и передаёт отказ клиенту.

Прочитать super как возможность передать полученный R и extends как пригодность результата для V. Связать с границами типов предыдущей лекции.

Проверяемое исключение действия

У Function<Path, String> метод apply(Path) не объявляет throws. У Files.readString(Path) возможен проверяемый IOException. Прямая ссылка Function<Path, String> read = Files::readString несовместима.

@FunctionalInterface
interface TextReader {
    String read(Path path) throws IOException;
}
TextReader read = Files::readString;

Вызвавший read.read(path) обязан обработать или объявить IOException.

Сопоставить сигнатуры. Попросить выбрать между собственным интерфейсом, обработкой отказа внутри действия и переносом чтения до преобразования; каждый выбор должен сохранять нужную диагностику.

Источник и состояние действий

Во время выполнения конвейера обычный источник, например ArrayList, сохраняют без изменений. Переданные функции его не изменяют; это условие относится к последовательному и параллельному проходу.

Исключение — источники, рассчитанные на конкурентные изменения (Spliterator.CONCURRENT). Допустимые изменения определяются их договором.

Результат функций filter и map не должен зависеть от внешнего состояния, которое меняется во время прохода. Например, порог отбора фиксируют до запуска [7].

Разделить источник students и накопитель результата. Обсудить добавление в исходный ArrayList из предиката filter: последовательное выполнение не устраняет нарушение договора источника. Затем заменить постоянный порог читаемым полем изменяемой настройки и попросить указать вторую зависимость, даже когда состав списка остаётся прежним.

Владение накопителем

var shared = new ArrayList<String>();
students.parallelStream().forEach(s -> shared.add(s.name()));

Общий ArrayList меняется конкурентно без согласования: элементы могут теряться. Сборка результата задаёт другой порядок владения:

var names = students.parallelStream()
    .map(Student::name).collect(Collectors.toCollection(ArrayList::new));

Коллектор управляет накопителями и объединением частичных результатов.

Попросить найти владельца shared и момент одновременного изменения размера. Сравнить с отдельными накопителями коллектора. forEachOrdered решает вопрос порядка эффектов, а скорость parallel требует измерения на конкретной задаче.

Порядок эффектов и скорость

У параллельного потока forEach не гарантирует порядок встречи элементов. forEachOrdered выполняет действия в порядке встречи, если он определён у результирующего потока. Порядок терминальных действий не задаёт порядок вызовов промежуточных функций.

Невмешательство в источник и корректное владение накопителем требуются при выборе любой из этих операций.

parallel() не гарантирует ускорения. Выигрыш зависит от размера входа, стоимости действий и разбиения; его устанавливают измерением конкретной задачи [7].

Для имён Ada, Lin, Ann сравнить требования к печати: нужны ли три строки в исходном порядке. Связать этот ответ с выбором forEachOrdered. Попросить назвать, что пришлось бы измерить для утверждения об ускорении, сохранив одинаковые данные и смысл результата у обоих способов выполнения.

Тип накопителя и тип элемента

int total = students.stream().reduce(
    0,
    (sum, student) -> sum + student.score(),
    Integer::sum);

Накопитель: Integer × Student → Integer. Объединитель: Integer × Integer → Integer.

Согласованность: добавить балл в сумму равносильно объединению суммы с итогом одного участника — sum + score == sum + (0 + score).
