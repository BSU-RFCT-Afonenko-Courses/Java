21.1 Компиляция, вход и состояние программы

Исключение передаёт сведения о том, что текущая операция не смогла закончиться обычным способом. Это объект типа Throwable и особый путь передачи управления от места отказа к обработчику [66], [84].

Ошибка компиляции возникает до исполнения программы. int score = "90"; отвергается компилятором: выражение имеет неподходящий тип, эта программа ещё не запущена. Строка "ninety" допустима как Java-строка, но не как вход операции чтения балла. Integer.parseInt("ninety") компилируется и при выполнении выбрасывает NumberFormatException. Наконец, инвариант стека 0 <= size && size <= capacity описывает допустимое состояние объекта: если реализация оставила size == -1, инвариант нарушен независимо от того, было ли выброшено исключение. Операция pop должна проверять пустоту до изменения size: такой отказ сохраняет допустимое состояние стека.

Недопустимый вход можно представить исключением или отдельным результатом. Проверяемое исключение возникает при выполнении. Слово checked обозначает обязанность компилятора проверить обработку или объявление возможного исключения. Содержимое внешнего файла становится известно программе при чтении.

В каталоге студентов поиск по идентификатору может ничего не найти: отсутствие входит в обычные результаты поиска. Для загрузки обязательного каталога нужно прочитать все записи указанного источника. Если источник недоступен, каталог получить не удалось. Наконец, выход за границы массива внутри загрузчика может говорить о дефекте его реализации. Возвращённый пустой каталог скрыл бы различие между успешным поиском без совпадения и неудачной загрузкой.

Способ сообщения об ошибке является частью интерфейса операции. Его договор определяет допустимые входы, успешный результат, сведения при отказе и состояние, которое останется у вызывающего кода. Выбор null, отдельного варианта результата или исключения решает только часть этого вопроса. Другая часть — вправе ли программа продолжать и с какими данными.

21.2 Успешный результат и исключение

Метод чтения балла возвращает int. Для строки "ninety" допустимого числового результата нет. Ноль может быть настоящим баллом, поэтому он не обозначает отказ однозначно. Возвращать -1 допустимо лишь при явном соглашении и обязательной проверке каждым вызывающим кодом. Исключение отделяет обычный результат от пути неудачи:

static int parseScore(String text) {
    java.util.Objects.requireNonNull(text, "text");
    int score = Integer.parseInt(text);
    if (score < 0 || score > 100) {
        throw new IllegalArgumentException("балл вне диапазона 0..100: " + score);
    }
    return score;
}

Метод получает строку, отличную от null, и проверяет десятичное целое в диапазоне int без окружающих пробелов. null нарушает предусловие и вызывает NullPointerException в requireNonNull. Для "90" метод возвращает 90. Для "120" он явно выбрасывает IllegalArgumentException. Для "ninety" parseInt выбрасывает NumberFormatException, который является подклассом IllegalArgumentException. Исключение прерывает вызов и выражение, в котором он выполнялся. Вызывающий метод пропускает обычное продолжение до подходящего обработчика.

Поиск участника может возвращать Optional.empty(), когда совпадения нет. Проверка балла обязана получить допустимое число либо сообщить причину отказа. Договор операции определяет, какие исходы являются обычными результатами и какие прерывают вызов.

21.3 Путь через стек вызовов

Пусть main вызывает readStudent, а тот — parseScore. Если parseScore выбрасывает исключение, обычного возврата в readStudent не происходит. Поиск обработчика следует текущему пути вызовов: сначала внутри parseScore, затем в вызывающем readStudent, затем в main. Завершение уже начатых вызовов исключением называют раскруткой стека. При выходе выполняются предусмотренные finally и закрытия ресурсов.

static int readStudent(String text) {
    int score = parseScore(text);
    System.out.println("запись проверена");
    return score;
}

В main обработчик охватывает вызов readStudent:

try {
    int score = readStudent("120");
    System.out.println("балл: " + score);
} catch (IllegalArgumentException ex) {
    System.out.println("ошибка: " + ex.getMessage());
}
System.out.println("следующая операция");

Будет выведено сообщение об ошибке диапазона, затем следующая операция. Строки запись проверена и балл: ... не выполняются. Обработчик не возвращает управление в точку после throw внутри parseScore: после завершения catch выполнение продолжается за всей конструкцией try. Если нужна повторная попытка, её организуют явным циклом вокруг операции.

Неперехваченное исключение завершает текущий поток выполнения; обработчик неперехваченных исключений может вывести трассировку. В простом приложении с единственным главным потоком это обычно означает завершение программы. Остальные потоки программы продолжают исполнение по своим правилам.

21.4 Иерархия и проверяемость

Exception и Error непосредственно наследуют Throwable. RuntimeException и Error вместе со всеми своими подклассами относятся к непроверяемым исключениям. Остальные типы исключений проверяемые: компилятор требует, чтобы потенциально выбрасываемое проверяемое исключение было обработано или допустимо объявлено в throws метода.

static String read(java.nio.file.Path path) throws java.io.IOException {
    return java.nio.file.Files.readString(path,
        java.nio.charset.StandardCharsets.UTF_8);
}

Запись throws сообщает вызывающей стороне о возможном исключении; сама запись не выбрасывает его и не выполняет обработку. Инструкция throw ex прерывает обычное выполнение и передаёт конкретный объект. Непроверяемое исключение тоже можно объявить в throws для документации, однако язык не требует этого.

Проверяемость не определяет тяжесть ошибки или момент её возникновения. Оба вида исключений возникают при выполнении; компилятор по-разному проверяет их обработку и объявление. IOException может быть ожидаемой проблемой внешней среды, IllegalArgumentException — нарушением условий метода. Error, например OutOfMemoryError, обычно указывает на состояние, после которого обычная прикладная операция не может надёжно продолжать работу. catch (Throwable ex) перехватывает и такие ошибки. Прежде чем продолжить работу, обработчик должен установить, какие части программы ещё работоспособны.

В Python нет аналогичной проверки throws при обычной компиляции, а в современном C++ динамические спецификации исключений не служат аналогом проверяемых исключений Java. Поэтому привычный синтаксис try/catch ещё не означает одинаковые правила объявления API. В Java объявление с проверяемым исключением участвует в проверке вызова и переопределения.

Уже первая редакция JLS 1996 года описывала проверяемые исключения в throws как часть соглашения между автором и пользователем метода. Цель проверки — уменьшить число неправильно обработанных отказов; разделение на проверяемые и непроверяемые присутствовало в этом раннем описании [11]. Проверяемость исключений сохраняется в современной JLS. Компилятор устанавливает допустимость пути передачи ошибки. Содержимое обработчика определяет действие при полученном отказе. Непроверяемые исключения освобождены от проверки объявления: например, объявление NullPointerException для каждого вызова затруднило бы чтение, тогда как компилятор не способен в общем случае исключить все обращения к объекту через null [118].

21.5 Проверяемый отказ операции

Операция извлечения возвращает значение при наличии элемента. Для пустого хранилища её договор может предусматривать проверяемое исключение. В отдельном файле EarlyCheckedDemo.java состояние представлено параметром empty; это позволяет проследить обычный возврат, throw, throws и catch:

public class EarlyCheckedDemo {
    static class EmptyException extends Exception {
        EmptyException(String message) { super(message); }
    }

    static int take(boolean empty) throws EmptyException {
        if (empty) throw new EmptyException("empty");
        return 7;
    }

    static int forward(boolean empty) throws EmptyException {
        return take(empty);
    }

    public static void main(String[] args) throws EmptyException {
        System.out.println(take(false));
        try {
            System.out.println(forward(true));
            System.out.println("после успешного вызова");
        } catch (EmptyException failure) {
            System.out.println(failure.getMessage());
        }
        System.out.println("дальше");
    }
}

Вывод: 7, empty, дальше, каждое на отдельной строке. Вызов take(false) возвращает число. throw во втором вызове передаёт объект ошибки и пропускает печать числа и следующую строку тела try. catch выбирает реакцию; после него продолжается код за конструкцией. forward не обрабатывает отказ, а объявляет передачу через throws. Объявление не создаёт исключение само по себе. В main первый вызов тоже требует обработки или допустимого объявления, даже если человек видит аргумент false: компилятор проверяет объявление вызванного метода.

Если в отдельном опыте убрать throws EmptyException у forward, оставив его тело прежним, компилятор отвергнет метод: возможное проверяемое исключение не обработано и не объявлено. Такой вариант не запускается и не имеет вывода: это ошибка компиляции. RuntimeException и его подклассы этой обязанности не создают. В контейнере проверка пустоты предшествует изменению размера и чтению элемента. Такой порядок сохраняет состояние при отказе извлечения [54].

21.6 Выбор подходящего обработчика

Обработчики проверяются сверху вниз. Тип параметра catch принимает исключение этого типа или его подкласса. Более частный случай располагают до общего:

try {
    System.out.println(parseScore("ninety"));
} catch (NumberFormatException ex) {
    System.out.println("нужно целое число");
} catch (IllegalArgumentException ex) {
    System.out.println("нужен балл 0..100");
}

Вывод — нужно целое число. Если общий обработчик поставить первым, второй станет недостижимым и компилятор отвергнет конструкцию. Вторая ветвь полезна для числовой строки вне диапазона: синтаксис числа верен, но условие предметной области нарушено.

Если реакция одинакова, независимые типы объединяют многовариантным catch (java.io.IOException | DataFormatException ex). Здесь DataFormatException — отдельный подкласс Exception для неверного формата записи; он определён в Предметное исключение и сохранение причины. Типы в таком перечне не должны находиться в отношении наследования друг к другу. Параметр многовариантного обработчика нельзя переприсваивать. Запись catch (NumberFormatException | IllegalArgumentException ex) отвергается: перечень одновременно содержит подкласс и его суперкласс.

Широкий catch (Exception ex) иногда оправдан на внешней границе приложения, но внутри алгоритма скрывает различие неверного файла и ошибки программиста. Обработчик выбирают по реальной возможности реакции. Печатать сообщение и возвращать пустой список при сбое чтения означает скрыть его отличие от корректного пустого файла.

21.7 Проверяемые исключения при переопределении

Клиент вызывает метод через статический тип ссылки. Набор допустимых проверяемых исключений берётся из доступного ему объявления:

interface TextSource {
    String read() throws java.io.IOException;
}

final class ConstantSource implements TextSource {
    @Override public String read() { return "90"; }
}

Вызов new ConstantSource().read() обходится без catch и throws. Для TextSource source = new ConstantSource(); source.read(); компилятор учитывает IOException из интерфейса. Реальный объект по-прежнему возвращает "90"; изменился тип, по которому проверяется вызов.

Переопределение вправе сохранить IOException, сузить его, например до FileNotFoundException, или убрать проверяемые исключения. Добавить Exception вместо IOException нельзя: клиент TextSource подготовлен только к IOException и его подклассам. Непроверяемые исключения этому ограничению объявления не подчиняются [131].

Объявление определяет и возможности будущих реализаций. Если бы TextSource.read первоначально не допускал проверяемого отказа, добавление файлового источника потребовало бы решения на границе: изменить интерфейс и его клиентов, преобразовать отказ в непроверяемое исключение либо представить исход отдельным значением. У каждого выбора есть цена. Объявленный IOException заранее заставляет всех клиентов общего типа учитывать отказ, включая тех, чей объект читает константу. Без объявления такой обязанности нет, но вызывающий код должен узнавать об условиях отказа из договора операции.

Проверяемость полезна там, где напоминание компилятора приводит к осмысленному решению: запросить другой источник, повторить допустимую операцию или завершить команду с диагностикой. Она сама не предоставляет средств восстановления. Если множество промежуточных методов только передаёт один отказ наверх, объявления увеличивают связанность их API. У стандартного Function метод apply не объявляет проверяемых исключений, поэтому действие с таким отказом нельзя подставить туда без дополнительного решения о его представлении. Составление правил и границы функционального интерфейса: Составление правил и границы интерфейса. [53]

21.8 Предметное исключение и сохранение причины

Загрузчик каталога должен сообщить не только «не целое число», но и номер строки. Проверяемое исключение формата сохраняет эти сведения:

class DataFormatException extends Exception {
    DataFormatException(String message) {
        super(message);
    }

    DataFormatException(String message, Throwable cause) {
        super(message, cause);
    }
}

static int scoreAt(String text, long line) throws DataFormatException {
    try {
        return parseScore(text);
    } catch (IllegalArgumentException ex) {
        throw new DataFormatException("строка " + line + ": неверный балл", ex);
    }
}

Вызывающий код получает предметный тип и сообщение с номером строки. Через getCause() ему доступна сохранённая исходная причина. Это помогает отделить внешний интерфейс загрузчика от деталей парсинга. Трассировка содержит место создания обёртки и исходную причину с её стеком.

Нельзя превращать любую перехваченную ошибку в «ошибку формата»: проблема ввода-вывода означает, что чтение могло вообще не завершиться. У этих случаев разные источники и возможные действия пользователя. Оборачивают лишь тот участок, который действительно проверяет представление данных. Для повторного выбрасывания без изменения подходит throw ex; новая обёртка нужна, когда уровень абстракции добавляет сведения или меняет тип ошибки, предусмотренный интерфейсом.

21.9 Блок finally и замещение исключения

Блок может дойти до своей закрывающей скобки — это нормальное завершение. return, throw, выход из цикла через break и переход continue завершают охваченные ими блоки резко: обычная последовательность инструкций прерывается по определённой причине. При таком выходе из try или его обработчика выполняется finally [132].

static int value() {
    try {
        return 10;
    } finally {
        System.out.println("выход из метода");
    }
}

При System.out.println(value()) сначала печатается выход из метода, затем 10. Выражение return вычислено до входа в finally. Нормальное завершение finally сохраняет ранее выбранный возврат. Если finally сам завершится return или throw, действовать будет уже его причина выхода:

static int replacedReturn() {
    try { return 10; }
    finally { return 20; }
}

static int swallowedFailure() {
    try { throw new IllegalStateException("body"); }
    finally { return 20; }
}

static void replacedFailure() {
    try { throw new IllegalStateException("body"); }
    finally { throw new IllegalArgumentException("cleanup"); }
}

replacedReturn возвращает 20 вместо 10. swallowedFailure тоже возвращает 20: исходное исключение тела больше не передаётся вызывающему коду. replacedFailure передаёт IllegalArgumentException("cleanup"); объект IllegalStateException("body") автоматически не включается ни в его причину, ни в подавленные исключения. Так действие очистки может уничтожить сведения об исходном отказе.

Если finally завершается нормально, исходный return, throw, break или continue сохраняется. Поэтому полезный результат возвращают из тела метода, а finally используют для завершающего действия. При закрытии ресурсов правило сохранения первичного отказа встроено в try с ресурсами: Первичная и подавленная ошибки.

Бесконечный цикл не достигает выхода из блока. Завершение процесса или принудительная остановка JVM также могут прекратить исполнение до finally.

21.10 Состояние программы после исключения

Раскрутка стека отменяет обычное продолжение, но не производит автоматический откат изменений. Если загрузчик добавил двадцать записей в общий каталог, а на двадцать первой получил неверный балл, первые двадцать остаются добавленными. Если файл вывода частично записан, throw не восстанавливает его прежнее содержимое.

После двух успешных добавлений третье вычисление прерывается:

var scores = new java.util.ArrayList<Integer>();
try {
    for (String text : java.util.List.of("90", "80", "120")) {
        scores.add(parseScore(text));
    }
} catch (IllegalArgumentException ex) {
    System.out.println(scores); // [90, 80]
}

Список остаётся пригодным для использования, но содержит лишь префикс входа. Если вместо исключения вернуть отдельное значение с описанием ошибки и выйти из метода, уже выполненные добавления тоже останутся. Возвращаемая ошибка не создаёт откат, как не создаёт его throw. Такой способ сообщения разобран в Типизированный результат проверки балла.

Состояние после отказа задаётся договором операции. «Объект остаётся корректным» допускает частичный результат. «Неудачная операция сохраняет прежнее состояние» требует более сильной организации изменений. «Обработаны все допустимые строки с перечнем отклонённых» допускает частичную загрузку, но явно сообщает её границы. Для одного интерфейса надо выбрать и проверить конкретное условие состояния, чтобы вызывающая сторона могла распознать неполные данные.

Для операции «прочитать целый каталог» можно сначала заполнять локальную коллекцию, а публиковать готовый результат только после успешного завершения. Тогда вызывающая сторона получает либо весь новый результат, либо исключение. Если парсинг только читает вход и строит этот локальный список, прежний опубликованный каталог остаётся неизменным. Если парсер дополнительно пишет журнал или меняет переданный объект, локальность списка уже не отменяет этих побочных действий. Граница публикации результата должна учитывать все изменяемые объекты. Для файла используются отдельные способы записи и замены: Глава 23.

Трассировку читают от места возникновения исключения к вызывающим методам. Сообщение добавляет сведения об аргументе и операции, а причина сохраняет исходный отказ нижележащего вызова. Пользователю обычно нужно короткое понятное сообщение; разработчику — полная трассировка. Обработчик помещают на уровень, где есть данные и полномочия для выбора дальнейшего действия. Формы конструкций и основные типы приведены в Глава 22.

21.11 Отказ конструктора

Конструктор устанавливает инвариант нового объекта. Если его выполнение прервано исключением, выражение new не возвращает ссылку и присваивание получателю не происходит. Уже совершённые изменения других объектов сохраняются:

final class Limits {
    final int maximum;
    Limits(int maximum, java.util.List<String> events) {
        events.add("начало создания");
        if (maximum < 0) throw new IllegalArgumentException("maximum < 0");
        this.maximum = maximum;
    }
}

Клиент создаёт пустой events и заранее присваивает Limits saved = null. После попытки saved = new Limits(-1, events) и перехвата исключения saved остаётся null, а events содержит "начало создания". Чтобы недопустимый аргумент не изменял журнал, проверку maximum нужно выполнить до events.add. Передача ссылки this наружу до установления инварианта позволила бы другому коду обратиться к частично инициализированному объекту.

Проверяемый отказ конструктора передаётся по тем же правилам throws. Конструктор подкласса вызывает конструктор суперкласса:

class TextSnapshot {
    final String text;
    TextSnapshot(java.nio.file.Path path) throws java.io.IOException {
        text = java.nio.file.Files.readString(path,
            java.nio.charset.StandardCharsets.UTF_8);
    }
}

final class NamedSnapshot extends TextSnapshot {
    NamedSnapshot(java.nio.file.Path path) throws java.io.IOException {
        super(path);
    }
}

NamedSnapshot должен объявить IOException или его допустимый супертип. Отказ super(path) прерывает создание и требует обработки у вызывающей стороны. Конструкторы не наследуются и не переопределяются; правило сужения проверяемых исключений переопределённого метода к ним не применяется. Если в именованном классе не объявлен ни один конструктор, неявный конструктор не имеет throws и не может передать проверяемое исключение конструктора суперкласса [43], [131].

21.12 Ответственность за восстановление

Представим интерактивный ввод одного балла. Здесь после неверного числа можно предложить повтор, потому что программа ещё имеет доступ к источнику ввода и знает, что требуется то же значение. Но при чтении обязательного файла каталога молчаливый пропуск повреждённой строки создал бы неполный каталог при требовании загрузить все записи. Одинаковый тип исключения в разных сценариях не навязывает одну реакцию. Политика зависит от результата, требуемого от всей операции.

Повтор также должен быть ограничен и осмыслен. Если ошибка вызвана неизменным содержимым той же строки, повторное вычисление parseInt без нового ввода даст прежний отказ. Если ошибка внешней среды временная, повтор может помочь, но его условия и число попыток становятся требованиями программы. Бесконечное повторение после любого IOException не является универсальным способом надёжной обработки.

Проверка результата восстановления должна различать основные ветви. Для корректного ввода ожидают число, для неверного — сообщение и переход к разрешённому дальнейшему действию. Для загрузчика обязательного каталога при отказе ожидают отсутствие опубликованного результата. Отдельно проверяют, изменён ли внешний объект, какое сообщение получил пользователь и сохранился ли диагностический контекст.

Требования к типам можно проверить компилятором. Вызов чтения с проверяемым IOException из метода без catch и подходящего throws должен быть отвергнут. При этом вызов parseInt из такого же метода разрешён, хотя при выполнении он способен отказать. Компилятор проверяет обязанность обработать возможный отказ по объявлению вызываемого метода. Соблюдение этих требований не гарантирует корректности внешних данных, поступающих при выполнении.

Сообщение называет операцию и существенный аргумент. Тип исключения позволяет программно различить причины отказа. Человеку удобно прочитать «строка пять: балл вне диапазона», а вызывающей программе удобно отличить DataFormatException от IOException без разбора русской фразы. Тип, сообщение, причина и состояние после отказа вместе задают полезный интерфейс ошибки.

21.13 Типизированный результат проверки балла

Типизированный результат представляет балл и описание неудачи двумя альтернативными вариантами значения. Такой тип часто называют Result. Для проверки балла варианты можно выразить собственным закрытым семейством:

sealed interface ScoreResult permits Score, ScoreFailure {}
record Score(int value) implements ScoreResult {}
enum ScoreProblem { NOT_INTEGER, OUT_OF_RANGE }
record ScoreFailure(ScoreProblem problem) implements ScoreResult {}

sealed ограничивает варианты реализации двумя указанными типами. record хранит данные соответствующего варианта. Перечисление различает ошибку представления и диапазона. Значение ScoreResult принадлежит одному из двух вариантов; полезный балл хранится только в Score.

static ScoreResult parseScoreResult(String text) {
    java.util.Objects.requireNonNull(text, "text");
    final int score;
    try {
        score = Integer.parseInt(text);
    } catch (NumberFormatException ex) {
        return new ScoreFailure(ScoreProblem.NOT_INTEGER);
    }
    if (score < 0 || score > 100) {
        return new ScoreFailure(ScoreProblem.OUT_OF_RANGE);
    }
    return new Score(score);
}

Для "90" получаем Score(90), для "120" — ScoreFailure(OUT_OF_RANGE), для "ninety" — ScoreFailure(NOT_INTEGER). Строка с числом, не помещающимся в int, тоже попадает в NOT_INTEGER: здесь имя означает «не представимо как целое int». Снаружи все три вызова завершаются обычным возвратом. Внутри адаптера всё ещё используется исключение parseInt, потому что так устроен существующий API. Ожидаемый отказ можно преобразовать между двумя способами представления на границе, сохранив смысл операции.

Следующий switch использует шаблоны записей (record patterns). Score(var value) проверяет, что результат является вариантом Score, и связывает компонент записи с переменной value. Её тип — int, как у компонента в объявлении Score. Аналогично ScoreFailure(var problem) связывает компонент с переменной problem типа ScoreProblem. Связанные переменные доступны в выражении соответствующей ветви.

String message = switch (parseScoreResult("120")) {
    case Score(var value) -> "балл: " + value;
    case ScoreFailure(var problem) -> "ошибка: " + problem;
};
System.out.println(message); // ошибка: OUT_OF_RANGE

В этом switch разобраны оба разрешённых вида результата; компилятор проверяет полноту выражения. Вызов метода допустим и как отдельная инструкция: тогда возвращённое значение отбрасывается и выбор реакции отсутствует. Только NumberFormatException перехватывается внутри parseScoreResult; нарушение условия text != null по-прежнему прерывает вызов.

Разница заметна при последовательности действий. После throw обработчик ищется по пути вызовов. После возвращённого ScoreFailure следующая строка выполнится, если мы сами не выберем другую ветвь или ранний return. При исключении передаётся управление; при результате передаются данные, по которым вызывающий код выбирает управление.

21.14 Дополнительно: проверка балла в Rust и Go

В Rust стандартный Result<T, E> содержит Ok(T) либо Err(E). Для той же проверки тип E можно сделать перечислением двух причин:

#[derive(Debug)]
enum ScoreProblem { NotInteger, OutOfRange }

fn parse_score(text: &str) -> Result<i32, ScoreProblem> {
    let score = text.parse::<i32>()
        .map_err(|_| ScoreProblem::NotInteger)?;
    if score < 0 || score > 100 {
        return Err(ScoreProblem::OutOfRange);
    }
    Ok(score)
}

? извлекает успешное значение либо сразу возвращает Err из текущей функции. Для "ninety" преобразование завершается ошибкой, и проверка диапазона пропускается. Вызывающий код получает этот результат и может разобрать Ok/Err через match или передать отказ дальше [149]. Rust также имеет panic!; unwrap() на Err вызывает панику [150].

В Go обычный интерфейс отказа возвращает пару полезного значения и error. Сопоставим те же входы, сохранив 32-битную границу преобразования:

func parseScore(text string) (int, error) {
    score, err := strconv.ParseInt(text, 10, 32)
    if err != nil {
        return 0, fmt.Errorf("не целое int32: %w", err)
    }
    if score < 0 || score > 100 {
        return 0, fmt.Errorf("балл вне диапазона: %d", score)
    }
    return int(score), nil
}

Ноль в неудачной ветви не является баллом: по соглашению этой функции первый компонент используют лишь при err == nil. В отличие от суммы вариантов, тип пары сам допускает одновременно значение и ошибку.

score, err := parseScore("120")
if err != nil {
    fmt.Println(err)
    return
}
fmt.Println(score)

Именно проверка и return останавливают успешную ветвь. Компилятор Go не требует реакции на каждый error. Ошибки являются обычными значениями; их можно сохранять и передавать между функциями [137].

Для ASCII-входов 90, 120, ninety и 32-битного преобразования получаются одинаковые предметные исходы. Java-исключение уводит с обычного пути, Rust Result кодирует альтернативу, Go возвращает пару с соглашением о допустимом использовании. Значения ScoreFailure можно сохранять в коллекции и накапливать при проверке нескольких строк. Для такого отчёта вызывающий код продолжает обход после каждого возвращённого результата.

21.15 Граница обработки в каталоге

Парсер знает причину отказа, загрузчик — путь и номер строки, а приложение — что пользователь хотел сделать. Поэтому место catch определяется доступным решением. Если парсер перехватит всё и напечатает сообщение, пакетная загрузка утратит возможность отличить полный результат от частичного. Если загрузчик навяжет повтор ввода с клавиатуры, его нельзя будет удобно использовать в приложении без интерактивной консоли. Передача причины наверх сохраняет эти варианты использования [43].

При загрузке обязательного каталога внешняя граница может завершить запуск с понятным сообщением. При интерактивном вводе она может предложить новый текст. При массовой проверке ей может понадобиться перечень всех неверных строк: тогда проверка каждой строки возвращает отдельный результат, а сборщик ошибок явно отделяет пригодные записи от отклонённых. Метод parseScore сообщает исход проверки одной строки. Решение о повторе или полноте каталога принимает вызывающий уровень.

Открытый файл требуется закрыть при любом из выбранных способов сообщения об отказе. Момент закрытия определяется областью владения ресурсом: Глава 22.
