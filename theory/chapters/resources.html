22.1 Объект в памяти и внешний ресурс

Загрузчик открыл файл, прочитал записи и вернул список. Для дальнейшего подсчёта список нужен, а доступ к файлу уже не требуется. Если оставить файл открытым до будущей сборки мусора, программа продолжит занимать внешний ресурс после окончания полезной работы. При повторных загрузках дескрипторы файлов могут закончиться, хотя сами объекты читателей занимают немного памяти.

У такого объекта связаны две обязанности. Java управляет памятью, в которой расположен объект. Программа определяет срок использования внешнего ресурса: файлового дескриптора, соединения или другого системного состояния. Исчезновение локальной переменной не устанавливает момент завершения этой работы. Приложению нужна операция освобождения ресурса с определённым местом в ходе вычисления [54].

Владелец ресурса — часть программы, которая определяет время его использования и отвечает за close. Передача ссылки другому методу позволяет этому методу обращаться к ресурсу. Передача обязанности закрыть его требует отдельного соглашения в API.

У загрузчика каталога связаны три времени жизни. Локальная переменная reader видима внутри блока. Файловый ресурс открыт между успешным открытием и закрытием файла. Список студентов, построенный из текста, может использоваться после закрытия: он хранит уже прочитанные данные. Операции чтения выполняются внутри времени жизни файлового ресурса; дальнейший расчёт отчёта обращается к списку в памяти.

открыть файл → читать и проверять → закрыть файл → использовать данные
                       ↘ отказ   → закрыть файл → выбрать реакцию

После close() ссылка может оставаться доступной: объект потока продолжает существовать, а чтение через закрытый файловый поток завершается IOException. Управление памятью и протокол работы с файлом допускают разные сроки жизни.

В JDK 18 финализацию объявили устаревшей с намерением удалить её в будущем. JEP 421 прямо указывает на неопределённую задержку очистки и отсутствие гарантии её вызова. Механизм Cleaner тоже не обеспечивает своевременное закрытие: его отложенная работа может служить вспомогательной защитой. Момент завершения работы с файлом всё равно определяет владелец; вызов finalize или следующий запуск GC эту обязанность не заменяют [5].

В C++ RAII связывает очистку с временем жизни управляющего объекта, часто с окончанием области видимости и вызовом деструктора. В Java само окончание области локальной переменной деструктор не вызывает. Try с ресурсами вызывает close при выходе из конструкции для успешно инициализированных ненулевых ресурсов. Область конструкции становится явным сроком владения [123]. В Python аналогичную роль часто выполняет with, обращающийся к протоколу контекстного менеджера. Каждый язык требует своего соглашения о том, какой объект участвует в очистке. В RAII определённое разрушение относится к управляющему объекту; вручную выделенный сырой указатель сам по себе не превращается во владельца ресурса [39]. В Python with вызывает __exit__ после успешно выполненного __enter__, в том числе при исключении. Выход из обычной локальной области __exit__ не вызывает [148].

22.2 Ручное закрытие при исключении

Метод получает java.nio.file.Path path, указывающий на UTF-8-файл. В этой последовательности close расположен после чтения:

var reader = java.nio.file.Files.newBufferedReader(path,
    java.nio.charset.StandardCharsets.UTF_8);
String first = reader.readLine();
reader.close();

Если readLine выбрасывает IOException, третья строка не выполняется. Добавление catch не решает это автоматически: обработчик может забыть закрытие или сам завершиться исключением. До появления try с ресурсами очистку располагали в finally, учитывали ошибку открытия и отдельную ошибку закрытия. При нескольких ресурсах требуется учесть отказ каждого открытия и каждого закрытия [55].

var reader = java.nio.file.Files.newBufferedReader(path,
    java.nio.charset.StandardCharsets.UTF_8);
try {
    return reader.readLine();
} finally {
    reader.close();
}

Эта форма вызывает close() успешно открытого ресурса при обычном выходе и ошибке чтения. Если и чтение, и close() выбросят исключение, новое исключение из finally вытеснит прежнее. Вызывающий код получит отказ закрытия; причина исходной ошибки чтения будет потеряна.

22.2.1 Ручное закрытие двух ресурсов

Когда ресурсов два, защита первого должна начаться до открытия второго. Защита второго начинается после его успешного получения. ManualResource печатает успешное открытие и каждый вызов закрытия; параметры позволяют воспроизвести отказ в выбранном месте.

final class ManualResource {
    private final String name;
    private final boolean failClose;

    ManualResource(String name, boolean failOpen, boolean failClose)
            throws java.io.IOException {
        if (failOpen) throw new java.io.IOException("open " + name);
        this.name = name;
        this.failClose = failClose;
        System.out.println("open " + name);
    }

    void close() throws java.io.IOException {
        System.out.println("close " + name);
        if (failClose) throw new java.io.IOException("close " + name);
    }
}

Метод close() вызывается явно во вложенных finally. Для такого вызова достаточно обычного метода класса:

static void useManually(boolean failSecondOpen, boolean failSecondClose)
        throws java.io.IOException {
    var first = new ManualResource("A", false, false);
    try {
        var second = new ManualResource("B", failSecondOpen, failSecondClose);
        try {
            // работа с first и second
            System.out.println("work");
        } finally {
            second.close();
        }
    } finally {
        first.close();
    }
}
Вызов Напечатанные события Завершение
useManually(false, false) open A, open B, work, close B, close A Обычное
useManually(true, false) open A, close A IOException("open B")
useManually(false, true) open A, open B, work, close B, close A IOException("close B")

Во втором случае объект B не получен, поэтому его закрытие не вызывается. Исключение открытия проходит через внешний finally, который закрывает A. В третьем случае во внутреннем finally возникает ошибка закрытия B, но выход из внешнего try всё равно приводит к вызову first.close(). Если оба объявления поставить перед первым try, второй путь оставит A без защиты. Если оба close поставить последовательно в одном finally, третий путь пропустит закрытие A.

Вложенные finally обеспечивают вызов очистки каждого успешно полученного объекта, но сами по себе не сохраняют все ошибки. Если основной код выбросил исключение и затем second.close() тоже отказал, исключение закрытия вытеснит ошибку работы. Если откажет и first.close(), уже оно вытеснит предыдущее. Вложенность сама не добавляет cause или suppressed. Для сохранения диагностических событий ручной код должен соединить первичное исключение с дополнительными. Try с ресурсами выполняет это по правилам подавленных исключений.

22.3 Интерфейс AutoCloseable

В конструкции может участвовать объект типа, совместимого с AutoCloseable. Этот интерфейс объявляет void close() throws Exception. Реализация вправе сузить список исключений, например до IOException, либо убрать проверяемые исключения из объявления. java.io.Closeable расширяет AutoCloseable и объявляет void close() throws IOException. Для уже закрытого потока его договор требует, чтобы повторный close не имел эффекта. У AutoCloseable такого общего требования нет [110].

static String firstLine(java.nio.file.Path path) throws java.io.IOException {
    try (var reader = java.nio.file.Files.newBufferedReader(path,
            java.nio.charset.StandardCharsets.UTF_8)) {
        return reader.readLine();
    }
}

Метод получает путь к UTF-8-файлу. Сначала файл открывается, затем блок читает первую строку. При выходе автоматически вызывается close, в том числе при return и при исключении внутри блока. Для пустого файла readLine возвращает null; ресурс также закрывается перед возвратом.

В общем случае значение ресурса может оказаться null. Тогда тело try выполняется, но для этой переменной автоматического вызова close нет. Переменная, объявленная в круглых скобках, доступна в теле и не может быть переприсвоена.

Try с ресурсами можно дополнить catch и finally. Обработчик охватывает не только тело, но также инициализацию и закрытие. Когда его код начинает выполняться, автоматическое закрытие уже произошло. Ресурсная переменная, объявленная в заголовке, недоступна как обычная локальная переменная внутри последующего catch — область действия не включает этот обработчик.

22.3.1 Проверяемый отказ закрытия

Компилятор учитывает исключения, объявленные у close статического типа ресурса, даже если тело try пусто:

final class Quiet implements AutoCloseable {
    @Override public void close() {}
}

static void concrete() {
    try (var resource = new Quiet()) {}
}

static void throughInterface() throws Exception {
    AutoCloseable resource = new Quiet();
    try (resource) {}
}

В concrete выведен тип Quiet, чей close не объявляет проверяемых исключений. В throughInterface используется тип AutoCloseable: его close объявлен с throws Exception, поэтому этот отказ требуется обработать или объявить. В обоих запусках вызывается один и тот же пустой метод Quiet.close; добавление throws не создаёт исключение.

22.4 Порядок открытия и закрытия

Несколько ресурсов объявляются через точку с запятой. Выражения их инициализаторов вычисляются слева направо. После успешных инициализаций выполняется тело; закрытие идёт справа налево. Обратный порядок полезен для зависимых объектов: внешняя обёртка завершается раньше того, на что опирается.

Параметры source и target имеют тип java.nio.file.Path и обозначают разные файлы. Исходный файл существует; целевой путь предназначен для копии:

try (var input = java.nio.file.Files.newInputStream(source);
     var output = java.nio.file.Files.newOutputStream(target)) {
    input.transferTo(output);
}

Если всё успешно, закрывается output, затем input. Если открытие output не удалось, успешно открытый input всё равно закрывается; тело не запускается. Если открытие самого input не удалось, ни одна ресурсная переменная ещё не инициализирована; автоматическое закрытие не вызывается.

Если первый вызов close выбросил исключение, конструкция вызывает close и для остальных успешно инициализированных ресурсов. Успешность самого освобождения при отказе close определяется договором конкретной реализации.

Открытие target создаёт файл или усекает существующий. Если запись прерывается позже, в выходном файле может остаться записанный префикс. Закрытие завершает использование потока; сохранение прежнего файла при отказе требует отдельно организовать запись и замену результата.

Класс Traced регистрирует порядок событий при успешной работе:

final class Traced implements AutoCloseable {
    private final String name;
    Traced(String name) {
        this.name = name;
        System.out.println("open " + name);
    }
    @Override public void close() {
        System.out.println("close " + name);
    }
}

В try (var a = new Traced("A"); var b = new Traced("B")) с телом, печатающим body, вывод последовательно будет open A, open B, body, close B, close A.

22.5 Первичная и подавленная ошибки

Если тело и закрытие выбросили исключения, основным остаётся исключение тела. Ошибка закрытия присоединяется к нему как подавленная (suppressed exception). Её можно получить через getSuppressed(). Это иное отношение, чем getCause(): причина обычно объясняет возникновение обёртки, а подавленная ошибка возникла дополнительно при очистке.

final class Failing implements AutoCloseable {
    @Override public void close() throws java.io.IOException {
        throw new java.io.IOException("close");
    }
}

try (var resource = new Failing()) {
    throw new IllegalStateException("body");
} catch (Exception ex) {
    System.out.println(ex.getMessage());                    // body
    System.out.println(ex.getSuppressed()[0].getMessage()); // close
}

Если тело завершилось успешно, а close выбросил исключение, ошибкой конструкции становится ошибка закрытия. При нескольких ошибках закрытия основной становится первая по порядку закрытия ошибка, остальные присоединяются как подавленные. Для обычных классов исключений с включённым подавлением эта информация сохраняется; специально созданный Throwable может отключить его [109].

Для диагностики отказа ресурса проверяют сообщение основного исключения, его причину и подавленные ошибки. ex.getMessage() даёт короткое сообщение, но не показывает все эти связи.

Причину и ошибку закрытия можно наблюдать одновременно. В отдельном CauseCloseDemo.java вложенный ресурс не обращается к настоящему диску:

public class CauseCloseDemo {
    static final class Resource implements AutoCloseable {
        @Override public void close() throws java.io.IOException {
            System.out.println("close");
            throw new java.io.IOException("cleanup");
        }
    }

    public static void main(String[] args) {
        try (var resource = new Resource()) {
            throw new java.io.IOException("read",
                new IllegalArgumentException("bad bytes"));
        } catch (java.io.IOException failure) {
            System.out.println("primary: " + failure.getMessage());
            System.out.println("cause: " + failure.getCause().getMessage());
            System.out.println("suppressed: "
                + failure.getSuppressed()[0].getMessage());
        }
    }
}

Вывод: close, primary: read, cause: bad bytes, suppressed: cleanup. Сначала вызывается очистка, затем начинает работать обработчик. Причина уже была передана конструктору ошибки чтения; независимая ошибка close присоединена ресурсной конструкцией.

22.6 Владение переданным ресурсом

Метод, который сам открыл файл для своей операции, обычно сам закрывает его. Метод, которому передали готовый Reader, часто только использует его и оставляет закрытие вызывающей стороне. Это соглашение требуется описать; тип Reader не кодирует владение.

static long countLines(java.io.BufferedReader reader) throws java.io.IOException {
    long count = 0;
    while (reader.readLine() != null) count++;
    return count;
}

countLines получает BufferedReader во временное пользование. После успешного вызова ресурс остаётся открытым, а позиция чтения находится в конце входа. Владелец закрывает его после завершения всех нужных операций. Вариант метода с аргументом Path сам открывает файл и может закрыть его внутри себя.

Если остальное приложение ещё использует общий System.in или System.out, этот поток оставляют открытым после работы с временной обёрткой. Некоторые обёртки закрывают лежащий ниже поток при собственном close. Закрытие Scanner, созданного поверх System.in, закрывает и этот вход. Остальные потребители общего потока теряют возможность читать его.

22.7 Уже объявленный ресурс и результат за границей блока

В заголовок можно включить ранее объявленную переменную final или фактически окончательную (effectively final), уже получившую значение:

var reader = java.nio.file.Files.newBufferedReader(path,
    java.nio.charset.StandardCharsets.UTF_8);
try (reader) {
    System.out.println(reader.readLine());
}
// reader всё ещё в области видимости, но ресурс уже закрыт.

После блока имя reader по-прежнему доступно. Чтение через этот закрытый файловый читатель вызовет IOException.

Похожая ошибка возникает при возвращении ленивого Stream из блока, в котором его уже закроют. return lines.filter(...) передаёт конвейер, не вычисленный список; после выхода его файловый источник закрыт. Правильные варианты — выполнить терминальную операцию внутри блока либо явно передать открытый поток вместе с обязанностью закрыть его. Возврат готового списка позволяет полностью завершить чтение внутри метода.

Договор AutoCloseable допускает видимый эффект повторного вызова close(). Обязанность закрытия передают одному владельцу; допустимость повторного закрытия определяет конкретный класс ресурса [99]. Краткие формы — Глава 23; файловые сценарии — Глава 23.

22.8 Дополнительно: зависимые обёртки и безопасная область работы

При работе с текстом несколько объектов могут описывать один путь к внешнему ресурсу: файловый байтовый вход, декодирующий читатель и буферизованный читатель. Обычно закрытие внешней обёртки завершает также лежащий под ней поток. Поэтому нельзя считать каждую ссылку независимым файлом. Владелец строит цепочку и определяет, какой управляющий объект будет участвовать в закрытии, учитывая соглашения конкретных классов.

Если сложное выражение сначала открыло нижний ресурс, а последующий конструктор обёртки отказал, переменная внешней обёртки не была успешно инициализирована. Автоматическое закрытие охватывает ресурсы, инициализация которых завершилась. Нижний объект, открытый внутри неудавшегося инициализатора, отдельным ресурсом этой конструкции ещё не стал. Если построение цепочки способно отказать, полезно явно управлять уже открытым нижним объектом и проверить поведение обёртки при ошибке создания. Готовые фабрики вроде Files.newBufferedReader уменьшают число таких промежуточных обязанностей вызывающего кода.

Понятие «закрыто» тоже определяется реализацией ресурса. Для файла это прекращение дальнейшего доступа через поток; для транзакционного или сетевого объекта могут существовать дополнительные действия. Интерфейс AutoCloseable задаёт сигнатуру метода, но не доказывает, что любая работа успешно закончилась. Если существенны подтверждение записи, отправка или фиксация результата, соответствующая операция должна быть видимой и проверяемой частью соглашения.

Учебные проверки ресурса полезно строить на регистрации событий. Один опыт подтверждает обратный порядок закрытия, другой — закрытие уже открытого первого объекта при отказе второго, третий — сохранение первичной ошибки тела вместе с ошибкой очистки. Наблюдение только сообщения последнего исключения не проверяет все эти свойства: первый ресурс мог остаться открытым, а важная причина — потеряться.

Такие небольшие искусственные ресурсы дают воспроизводимые сценарии без попытки заставить настоящий диск случайно отказать в нужный момент. После этого интеграционный опыт проверяет реальное чтение временного файла. Разделение проверки правила языка и конкретной файловой операции помогает локализовать ошибку и не приписывать случайному состоянию среды общее правило.

22.9 Дополнительно: возврат ошибки и завершение работы с ресурсом

Метод закрывает ресурс и при возврате значения с описанием ошибки. Вариант ScoreFailure обозначает ошибку проверки балла; типы и сама проверка определены в Типизированный результат проверки балла. Загрузчик возвращает этот вариант, когда первая строка не содержит допустимый балл:

static ScoreResult firstScore(java.nio.file.Path path)
        throws java.io.IOException {
    try (var reader = java.nio.file.Files.newBufferedReader(path,
            java.nio.charset.StandardCharsets.UTF_8)) {
        String line = reader.readLine();
        if (line == null) {
            return new ScoreFailure(ScoreProblem.NOT_INTEGER);
        }
        return parseScoreResult(line);
    }
}

Пустой файл в этом договоре даёт ScoreFailure(NOT_INTEGER): обязательный первый балл отсутствует. При любом return из тела сначала вычисляется результат, затем вызывается закрытие. Поэтому ни подготовленный Score, ни подготовленный ScoreFailure ещё не означают возврата из всего метода: если close выбросит IOException, вызывающая сторона получит это исключение. Ошибка как значение не является выброшенным исключением тела. Java не создаёт из содержимого ScoreFailure первичное исключение и не присоединяет его автоматически к ошибке закрытия.

Используем уже определённый ресурс Failing, чей close всегда выбрасывает IOException("close"), и сравним два действия тела:

static ScoreResult resultBeforeClose() throws java.io.IOException {
    try (var resource = new Failing()) {
        return new ScoreFailure(ScoreProblem.NOT_INTEGER);
    }
}

static ScoreResult exceptionBeforeClose()
        throws java.io.IOException, DataFormatException {
    try (var resource = new Failing()) {
        throw new DataFormatException("неверный балл");
    }
}

В первом случае NOT_INTEGER содержится в вычисленном значении, которое метод не вернул. Во втором случае основной отказ тела был выброшен, поэтому ошибка close добавлена к нему по правилам try с ресурсами. Если интерфейс обязан сохранить оба события и при возврате ошибки как значения, их объединение надо предусмотреть явно.

В firstScore неверное содержимое представлено ScoreFailure, а отказ ввода-вывода передаётся исключением. Вызывающий код сначала должен получить результат файловой операции и лишь затем может разобрать его вариант.

В Go после успешного открытия файла часто регистрируют defer file.Close(). Отложенный вызов выполняется при выходе из окружающей функции. Выход из вложенного блока этот вызов ещё не запускает. Возвращённая ошибка Close при таком кратком вызове не объединяется с ошибкой чтения: код должен явно решить, как её сохранить. defer задаёт время действия, а соглашение об ошибках по-прежнему задаёт автор функции [147].

В Rust владение определяет освобождение значения при выходе из области; перемещение значения может передать эту обязанность другому владельцу. Ранний возврат Err через ? завершает область текущей функции; при этом освобождаются принадлежащие её локальным владельцам значения [149].

Загрузчик, который вернул готовые студенческие записи и закрыл источник, передал дальше данные. Загрузчик, который вернул открытый читатель или ленивый файловый Stream, передал также возможность будущего отказа и обязанность закрытия. При проектировании интерфейса нужно выбрать, какой результат и какие обязанности метод передаёт вызывающей стороне.

22.10 Дополнительно: область владения и асинхронное завершение

Лексический блок удобен, когда полезная работа действительно заканчивается до выхода из него. У синхронного чтения результат уже получен к возврату из read. У асинхронной операции вызов возвращает средство получения будущего результата, а чтение может ещё продолжаться (Асинхронная операция и её завершение).

Рассмотрим ошибочный порядок действий метода, который открывает AsynchronousFileChannel в try с ресурсами и возвращает channel.read(buffer, 0). Канал представляет открытый файл, буфер — память для прочитанных байтов. Возвращённый Future позволяет получить результат операции; его get() при необходимости ждёт завершения. Последовательность событий метода:

открыть канал
заказать чтение → получить Future
вычислить возвращаемое значение Future
выйти из try → закрыть канал
вернуть Future вызывающему коду

Закрытие произойдёт до передачи результата вызывающей стороне. Если чтение ещё не завершилось, закрытие прервёт его; если оно успело закончиться, ошибка организации времени жизни может остаться незаметной в данном запуске. Само наличие Future не удерживает канал открытым [33].

Один вариант — дождаться завершения внутри блока и вернуть готовые данные. Он сохраняет локальное владение и последовательную форму вызывающего кода. Другой — передать наружу объект, который владеет каналом вместе с незавершёнными операциями и определяет порядок их завершения и закрытия. Такой интерфейс позволяет продолжать работу независимо, но передаёт клиенту больше обязанностей. Обработчик завершения тоже должен учитывать все операции, использующие канал: окончание одной из них не всегда означает окончание общего владения.

Буфер имеет свой срок исключительного использования. Пока чтение не завершено, операция может изменять данные и позицию; программа не использует тот же буфер для другой работы. Успешное Future.get или вызов обработчика завершения задаёт место передачи готовой порции. Таким образом, надёжное закрытие требует согласовать область владения с фактическими использованиями ресурса, включая те, которые продолжаются после возврата отдельного метода.
