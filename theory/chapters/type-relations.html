16.1 Инвариантность параметризованных типов

List<E> обозначает последовательность с индексами от 0 до size() - 1. get(i) читает элемент, set(i, value) заменяет его, add(value) дописывает элемент в конец. ArrayList<E> поддерживает эти изменения. Параметры и основные операции: Глава 15.5.

Integer совместим с Number, поэтому отдельное целое число можно передать туда, где требуется число. У списка есть также операция записи:

List<Integer> integers = new ArrayList<>();
integers.add(1);

// List<Number> numbers = integers; // ошибка компиляции
// numbers.add(2.5);

Если бы присваивание разрешалось, обе ссылки вели бы к одному списку. Через numbers можно было бы записать Double, поскольку он является Number. Через integers клиент затем прочитал бы его как Integer. Компилятор отвергает присваивание, которое создало бы такой путь записи.

Отсутствие автоматического переноса подтипизации аргумента на параметризацию называют инвариантностью. List<Integer> и List<Number> не являются подтипами друг друга. Обычное наследование классов сохраняется: ArrayList<Integer> реализует List<Integer>. Инвариантность распространяется и на обобщённый класс только с методами чтения: Java задаёт одно правило параметризации, а требуемую совместимость ссылок выражают через wildcard. [15]

У массивов ссылочных типов действует ковариантность:

Integer[] integers = {1, 2};
Number[] numbers = integers;
numbers[0] = 2.5; // ArrayStoreException

Присваивание ссылок разрешено. Сам объект остаётся массивом Integer[]; при записи среда выполнения проверяет совместимость значения с фактическим типом компонента. Упакованный Double отвергается, и компонент сохраняет 1. Нарушение обнаруживается при записи. Для списка компилятор остановил опасное расширение типа ссылки ещё до неё. [13]

16.2 Неизвестный аргумент типа

Wildcard — неизвестный аргумент типа, обозначаемый ?. Его границы сохраняют часть сведений об элементе и позволяют принимать несколько параметризаций одного класса. Компилятор использует эти сведения при проверке чтения, записи и передачи значений между объектами [15], [17].

List<?> допускает список с любым аргументом типа, сохраняя неизвестность этого аргумента в текущем коде:

static void printAll(List<?> values) {
    for (Object value : values) {
        System.out.println(value);
    }
}

printAll(List.of("Ada", "Lin")) печатает две строки. Все ссылочные значения пригодны как Object, поэтому для такой печати конкретный тип элемента знать не требуется. Метод не может добавить произвольно выбранный объект: среди допустимых входов есть List<String>, который отверг бы Integer.

List<Object> имеет определённый аргумент Object и принимает ссылки разных классов. List<?> скрывает аргумент существующего списка. Например, он может обозначать и List<Object>, и List<String>. Набор допустимых действий должен подходить каждому возможному входу. [17], [72]

Верхняя граница сохраняет более точные сведения для чтения:

static double sum(List<? extends Number> values) {
    double total = 0.0;
    for (Number value : values) {
        total += value.doubleValue();
    }
    return total;
}

Неизвестный аргумент является Number или его подтипом. Поэтому каждый прочитанный элемент пригоден для вызова doubleValue(). sum(List.of(1, 2)) даёт 3.0, а sum(List.of(0.5, 1.5)) — 2.0. Список и его элементы должны быть отличны от null; результат вычисляется последовательным сложением double.

Запись Integer через List<? extends Number> запрещена: фактическим входом мог быть List<Double>. Запись Double запрещена по симметричной причине. Верхняя граница даёт общий тип чтения, но не выбирает конкретный тип значений, допустимых для записи в список.

Нижняя граница обеспечивает запись:

static void addSmallIntegers(List<? super Integer> target) {
    target.add(1);
    target.add(2);
}

Допустимы List<Integer>, List<Number> и List<Object>: каждый из них принимает Integer по правилам типов. При поддержке add новый ArrayList<Number> станет [1, 2]. Чтение через эту ссылку даёт только Object: исходный List<Object> мог содержать строку до вызова.

16.2.1 Изменение списка с wildcard

Wildcard ограничивает операции, для которых нужно знать тип элемента. Удаление всего содержимого такого знания не требует:

List<Integer> mutable = new ArrayList<>(List.of(7));
List<? extends Number> view = mutable;
view.clear();
System.out.println(mutable.size()); // 0

view и mutable ведут к одному изменённому объекту. Верхняя граница не создаёт копию и не делает объект неизменяемым. Значение null также подходит неизвестному ссылочному типу, поэтому его запись допускается системой типов. Реализация списка отдельно определяет поддержку изменения и null; список из List.of отвергает такие действия. [106]

16.3 Перенос элементов между контейнерами

Для дописывания элементов источника в приёмник нужна одна связь: каждый прочитанный элемент должен подходить операции записи. Параметр T обозначает передаваемый тип. Источник имеет верхнюю границу, приёмник — нижнюю:

static <T> void copy(List<? extends T> source,
                     List<? super T> target) {
    for (T value : source) {
        target.add(value);
    }
}

Чтение из источника даёт значение, совместимое с T; приёмник допускает T и его подтипы. Отсюда правило producer extends, consumer super (PECS): производитель отдаёт значения общего типа, потребитель принимает их. [57]

List<Integer> ints = List.of(1, 2);
List<Number> numbers = new ArrayList<>();
numbers.add(0.5);
copy(ints, numbers);
System.out.println(ints);    // [1, 2]
System.out.println(numbers); // [0.5, 1, 2]

Вызов допустим, например, при T = Integer: целые элементы подходят приёмнику чисел. Прежнее значение 0.5 сохраняется, новые элементы идут в порядке источника. В обратном направлении гарантии нет: из List<Number> мог бы прийти Double, непригодный для List<Integer>.

Оба списка должны существовать. Приёмник поддерживает добавление передаваемых значений. Их структуры должны быть независимы: если обе ссылки ведут к одному списку либо к связанным представлениям, добавление способно изменить источник во время его обхода. Система типов такие отношения объектов не проверяет.

Метод копирует ссылки, поэтому объекты элементов остаются общими. Пустой источник не вызывает add и ничего не меняет. Если приёмник отвергнет очередной элемент, предыдущие успешные добавления остаются: отката в этом алгоритме нет.

Библиотечный Collections.copy имеет другое действие: он заменяет существующие позиции и принимает приёмник первым. Его точный договор: Замена существующих позиций.

16.4 Граница унаследованного сравнения

Объекты Person сравниваются по целочисленному полю rank. Student наследует этот способ сравнения:

class Person implements Comparable<Person> {
    final int rank;
    Person(int rank) { this.rank = rank; }
    public int compareTo(Person other) {
        return Integer.compare(rank, other.rank);
    }
}
final class Student extends Person {
    Student(int rank) { super(rank); }
}

Integer.compare возвращает знак сравнения двух int. У Student доступен compareTo(Person), принимающий также студента. Унаследованным интерфейсом остаётся Comparable<Person>.

Простая граница требует сравнения с тем же аргументом типа:

static <T extends Comparable<T>> T strict(T a, T b) {
    return a.compareTo(b) >= 0 ? a : b;
}

Student a = new Student(1);
Student b = new Student(2);
Person person = strict(a, b);
System.out.println(person == b); // true

При T = Person оба аргумента допустимы, граница выполнена. Статический тип результата — Person; возвращённая ссылка ведёт к b. Если клиенту нужен результат Student, требования уже не согласуются:

Student student = strict(a, b); // ошибка компиляции

Выбор Person даёт слишком широкий тип результата. Выбор Student нарушает границу, поскольку Comparable<Student> у него отсутствует. Явный аргумент <Student> нарушает ту же границу. Компилятор проверяет объявленную связь типов и не выводит тип результата из анализа того, какой конкретно объект вернула бы ветвь тела.

Сравнение потребляет второй объект. Для T достаточно операции, принимающей T или его супертип:

static <T extends Comparable<? super T>> T flexible(T a, T b) {
    return a.compareTo(b) >= 0 ? a : b;
}

Student student = flexible(a, b);
System.out.println(student == b); // true

Comparable<Person> соответствует Comparable<? super Student>: Person является супертипом Student. Теперь вывод может сохранить T = Student. Метод возвращает тот же объект b, а тип результата подходит переменной Student. При равенстве обе реализации выбирают первый аргумент. Оба аргумента должны отличаться от null и поддерживать согласованный порядок. [33], [34]

При var inferred = strict(a, b) тип переменной — Person; при var precise = flexible(a, b) — Student. var выводит тип по инициализатору и сохраняет его после объявления. Два метода имеют разные имена: перегрузить одно имя только этими границами нельзя, поскольку после стирания параметры обеих версий совпадут.

16.5 Захват неизвестного типа

Для перестановки первых двух элементов неизвестного списка требуется сохранить первый элемент и затем записать его обратно. Переменная Object теряет нужную связь:

static void reverseFirstTwo(List<?> values) {
    if (values.size() >= 2) {
        Object first = values.get(0);
        values.set(1, first); // ошибка компиляции
    }
}

В позиции аргумента set требуется неизвестный тип элемента списка. Тип Object допускает слишком много значений и не сохраняет связь со списком. Непосредственная запись values.set(0, values.get(0)) через List<?> тоже отвергается: отдельные обращения к values получают разные захваты неизвестного аргумента. Компилятору нужна выраженная в типах связь результата чтения с аргументом записи.

При захвате компилятор вводит для неизвестного аргумента новую переменную типа. Вспомогательный метод связывает её со своим T:

static void reverseFirstTwo(List<?> values) {
    if (values.size() >= 2) {
        swapFirstTwo(values);
    }
}
private static <T> void swapFirstTwo(List<T> values) {
    T first = values.get(0);
    values.set(0, values.get(1));
    values.set(1, first);
}

Внутри одного вызова swapFirstTwo чтение и запись используют один T. Он обозначает именно захваченный аргумент входного списка; клиенту не требуется называть этот тип. Захват происходит при проверке типов компилятором; для него не нужно обследовать элементы при выполнении. [20], [57]

List<String> names = new ArrayList<>(List.of("Ada", "Lin"));
reverseFirstTwo(names);
System.out.println(names); // [Lin, Ada]

В метод передаётся существующий список. При размере меньше двух он ничего не меняет; иначе необходима поддержка set. Для списка из List.of("Ada", "Lin") первая замена вызовет UnsupportedOperationException. Два независимых List<?> имеют два независимых неизвестных аргумента: захват не устанавливает их равенство. Перенос между разными контейнерами требует связи в сигнатуре copy.

16.6 Миграционная совместимость

ObjectBox воспроизводит важное свойство ранних коллекций Java: одна реализация работала с разными объектами, но возвращала Object. В первой спецификации Java у Vector были addElement(Object) и Object elementAt(int). Приведение к ожидаемому типу писал клиент; тип элементов конкретного контейнера не входил в его объявление. [10]

В 1998 году авторы GJ предложили расширить Java параметрами типов и переводить такой код в язык без обобщений: заменять параметры их границами, вставлять приведения и сохранять работу переопределений. В авторской аннотации статьи отдельно названа возможность снабдить существующие библиотеки обобщёнными интерфейсами без изменения их кода. [42]

Для JSR 14, начатой в 1999 году, взаимодействие со старым кодом стало явным требованием. Старая программа должна была продолжить работу с новой параметризованной библиотекой, а библиотеки должны были переходить к обобщениям постепенно. Иначе введение параметров потребовало бы согласованного обновления всей цепочки зависимостей. [29]

Обобщения вошли в Java 5 в 2004 году. Выбранная модель разделила проверку исходных типов и выполняемое представление. Компилятор получил более точные объявления, а обычный обобщённый класс сохранил общее представление для разных аргументов типа.

16.7 Стирание параметризованных типов

Стирание отображает исходные типы в представление без аргументов обобщённых типов. Box<String> и Box<Integer> стираются до Box; неограниченный T — до Object. Для ограниченного параметра используется стирание его первой границы: у T extends Number это Number. Проверка исходной программы учитывает аргументы до такого преобразования. [18]

final class Box<T> {
    private final T value;
    Box(T value) { this.value = value; }
    T get() { return value; }
}
Позиция исходного объявления Представление после стирания
Поле T value Object value
Конструктор Box(T value) Box(Object value)
Метод T get() Object get()

Клиент использует более точный тип результата:

static String read(Box<String> box) {
    return box.get();
}

В байткоде BoxClient.read JDK 25 видны вызов и добавленная проверка:

0: aload_0
1: invokevirtual #7  // Method Box.get:()Ljava/lang/Object;
4: checkcast     #13 // class java/lang/String
7: areturn

aload_0 загружает ссылку box, invokevirtual обращается к стёртому get(): Object. Инструкция checkcast String у клиента проверяет совместимость возвращённого объекта со String; значение null проходит проверку. Приведение сохраняет исходное ссылочное значение. areturn возвращает его.

У ObjectBox приведение записывал клиент в исходнике. Обобщённый Box позволяет компилятору проверить согласованность типов при создании, а затем добавить нужное приведение в байткод чтения. Если связь была нарушена небезопасной операцией, это приведение может обнаружить ошибку при выполнении.

16.7.1 Представление обобщённого класса

Box<String> text = new Box<>("Java");
Box<Integer> number = new Box<>(25);
System.out.println(text.getClass() == number.getClass()); // true
System.out.println(text.get().getClass().getSimpleName()); // String
System.out.println(number.get().getClass().getSimpleName()); // Integer

Коробки принадлежат одному классу Box. Их содержимое — отдельные объекты классов String и Integer. Класс содержимого не восстанавливает аргумент коробки: тот же Integer допустим в Box<Number> и Box<Object>.

Обобщённые объявления сохраняются в атрибуте class-файла Signature. У метода get() он содержит ()TT;, тогда как дескриптор JVM содержит ()Ljava/lang/Object;. Инструменты и рефлексия могут прочитать параметр T объявления. Метаданные класса описывают общее объявление; каждый обычный объект Box не хранит отдельного описания выбранного аргумента типа. [132]

16.8 Мостовой метод

Стирание меняет форму метода, используемую для полиморфного вызова:

interface Source<T> { T get(); }
final class TextSource implements Source<String> {
    public String get() { return "Java"; }
}

В исходном коде Java String get() реализует метод Source<String>. После стирания дескриптор интерфейсного метода — ()Ljava/lang/Object;, авторского метода — ()Ljava/lang/String;. Дескриптор JVM содержит параметры и результат; эти две записи различаются. Компилятор добавляет мостовой метод с требуемой стёртой формой.

Фрагмент javap -p -c -v TextSource для JDK 25:

    stack=1, locals=1, args_size=1
       0: aload_0
       1: invokevirtual #9 // Method get:()Ljava/lang/String;
       4: areturn

Мостовой метод загружает this, вызывает авторский String get() и возвращает ссылку как Object. Приведение внутри этого моста не требуется: строка совместима с Object. Флаги ACC_BRIDGE и ACC_SYNTHETIC отмечают метод, добавленный компилятором. [35]

Клиент обращается к интерфейсу:

static String read(Source<String> source) {
    return source.get();
}

System.out.println(read(new TextSource())); // Java

Его байткод содержит отдельное клиентское приведение:

0: aload_0
1: invokeinterface #7, 1 // InterfaceMethod Source.get:()Ljava/lang/Object;
6: checkcast     #13     // class java/lang/String
9: areturn

Вызов проходит через интерфейсный get(): Object, мост объекта TextSource, затем достигает авторского get(): String. После возвращения по этому пути клиент проверяет результат как String. Мост обеспечивает переопределение при стёртом вызове, клиентское приведение восстанавливает ожидаемый исходником тип результата.

В исходнике Java два метода с одинаковыми параметрами и разными типами результата вручную объявить нельзя. Мост появляется при переводе в class-файл. Команды получения обеих трасс: Клиентское приведение и мостовой метод в javap.

16.9 Типы без аргументов

Raw type — использование обобщённого класса или интерфейса без аргументов типа. Оно поддерживает взаимодействие с прежними API и допускает операции, безопасность которых по параметрам уже не доказана:

List<String> words = new ArrayList<>();
List raw = words;
raw.add(25);                // unchecked-предупреждение
String word = words.get(0); // ClassCastException

Через raw список получает ссылку на Integer. После стирания add принимает Object, и выполняемая реализация сохраняет это значение. Через words клиент ожидает строку; добавленный checkcast String обнаруживает несовместимый объект при чтении.

Такое нарушение связи параметризованной ссылки с доступным через неё содержимым называется загрязнением кучи (heap pollution). Предупреждение unchecked указывает на непроверенную операцию. @SuppressWarnings("unchecked") скрывает сообщение компилятора, сохраняя прежнее действие программы. [16], [19]

При переходе к List<?> тип элемента остаётся неизвестным, и такая запись запрещена. Проверка старого внешнего списка требует отдельного договора: приведение к List<String> не обходит каждый элемент и не подтверждает строковое содержимое. При изменяемом общем списке важны также последующие записи через сохранившиеся ссылки.

16.9.1 Ограничения выполняемого представления

Выражение new T() не имеет достаточных сведений для создания объекта: параметр типа не передаёт выполняемому коду конкретный класс, а его граница не устанавливает требуемый конструктор. Алгоритм может получить готовое значение или объект с операцией создания, как Arithmetic<T>.zero().

Создание new T[n] запрещено из-за типа компонента массива, требуемого при выполнении. Поле T[] при этом допустимо. Конструктор контейнера может принять готовый массив: для хранения любых Number необходим массив, фактически допускающий их, например Number[]. При передаче Integer[] через Number[] массив сохраняет тип компонента Integer и отвергает запись Double.

Для ссылки статического типа Object проверка value instanceof Box<String> запрещена: класс Box не предоставляет проверку его аргумента. value instanceof Box<?> допустима и устанавливает принадлежность коробке с неизвестным содержимым. Некоторые проверки конкретной параметризации допустимы, когда её совместимость уже следует из статического типа операнда: Проверка instanceof.

Наконец, f(List<String>) и f(List<Integer>) стираются к одинаковому параметру List. Эти объявления не образуют допустимые перегрузки. Формы ограничений и возможные замены: Ограничения и замены.

16.10 Ограничения массивов параметризованных типов

Для записи в массив выполняемый код использует его фактический тип компонента. Тип, полностью доступный для таких проверок, называют reifiable. К нему относятся String, List<?> и массивы с таким компонентом. List<String> не относится: аргумент String отсутствует в выполняемом классе списка. [22]

Поэтому new List<String>[10] запрещён. Если бы такой массив можно было создать, ковариантность разрешила бы обратиться к нему как к Object[] и записать List<Integer>. Проверка массива увидела бы только класс списка и не смогла бы отвергнуть неверный аргумент. Чтение элемента этого списка как строки нарушило бы исходный договор.

Объявить переменную List<String>[] можно; непосредственное создание массива — отдельная операция с указанным ограничением. Для неизвестных аргументов достаточно проверки принадлежности элементов массива классу списка:

List<?>[] lists = new List<?>[2];
lists[0] = List.of("Java");
lists[1] = List.of(25);
Object value = lists[1].get(0);
System.out.println(value); // 25

Чтение списка здесь даёт только Object, что соответствует неизвестному аргументу. Для последовательности именно списков строк можно выбрать List<List<String>>: внутренние и внешние операции проверяются с сохранением обоих аргументов при компиляции.

16.11 Совместимость типов и изменяемость

Допустимость вызова copy по правилам типов не означает, что приёмник поддерживает изменение состава:

List<Integer> source = List.of(1, 2);
List<Number> target = List.of(0.5);
copy(source, target); // UnsupportedOperationException

Целые числа подходят списку Number, поэтому вызов компилируется. Однако первая попытка add отвергается реализацией из List.of. Приёмник сохраняет [0.5], источник — [1, 2].

Другой объект с тем же статическим типом поддерживает добавление:

List<Number> target = new ArrayList<>(List.of(0.5));
copy(source, target);
System.out.println(target); // [0.5, 1, 2]

Выбор реализации изменил допустимость операции при выполнении. ? super T обосновывает тип её аргумента; договор объекта определяет поддержку самой операции. Правила отказа и библиотечный вариант: Связь источника и приёмника.
