20.1 Цикл и конвейер преобразований

Stream<T> описывает одноразовый проход элементов через последовательность операций. Коллекция отвечает за хранение данных, функции — за действия, а Stream связывает действия в конвейер и передаёт элементы при обходе. Слово «поток» встречается у разных средств Java: java.util.stream предоставляет конвейеры, InputStream — чтение байтов, Thread — отдельный поток выполнения. Вызовы используют функциональные интерфейсы из Глава 19. [47], [54], [105].

Каталог содержит участников с кодом, именем и баллом. У записи grade.Student методы id(), name() и score() возвращают эти значения (Компоненты и стандартные члены записи):

var students = java.util.List.of(
    new Student("s1", "Ada", 90),
    new Student("s2", "Lin", 70),
    new Student("s3", "Ann", 80));

Нужны имена набравших не меньше 80, отсортированные по имени. В цикле сначала создали бы список, затем добавляли подходящие имена, затем сортировали. Конвейер делает эти шаги видимыми в порядке чтения:

var names = students.stream()
    .filter(s -> s.score() >= 80)
    .map(Student::name)
    .sorted()
    .toList();
System.out.println(names); // [Ada, Ann]

Разберите путь Lin/70 до чтения таблицы: дойдёт ли его имя до сортировки?

Стадия Тип элемента / результата Значения в порядке источника
students.stream() Student s1/Ada/90, s2/Lin/70, s3/Ann/80
filter(...) Student s1/Ada/90, s3/Ann/80
map(Student::name) String Ada, Ann
sorted() String Ada, Ann по естественному порядку строк
toList() результат List<String> [Ada, Ann]

Таблица описывает значения после стадий; отдельных списков между стадиями код не создаёт. Lin отклонён фильтром, поэтому его имя в результат преобразования не входит. Источник выдаёт участников. filter сохраняет только подходящих, не меняя тип элементов. map превращает каждого участника в имя и меняет тип с Stream<Student> на Stream<String>. sorted задаёт порядок. toList завершает проход и возвращает список. В исходном списке по-прежнему три участника; результат содержит две строки.

Изменилось и распределение управления. В обычном цикле клиент сам переходит к следующему элементу и выполняет тело в указанном месте. Такой обход называют внешним. В конвейере клиент передаёт библиотеке условие, преобразование и требование к результату; библиотека управляет продвижением элементов. Это внутренний обход. Источник остаётся списком, но порядок вызовов внутри реализации уже нельзя восстанавливать только по виду цепочки методов.

В проектных материалах библиотеки Stream это различие связывалось с развитием существующих коллекций: общий механизм обхода должен был поддержать составление операций, ленивое выполнение и явно выбираемую параллельную обработку. [8] Для нашего отчёта библиотека может передавать прошедшее фильтр значение сразу в преобразование, не создавая промежуточного списка. Сортировка потребует накопить выбранные имена.

Переданная лямбда может менять поля элемента, сохраняя состав списка. Если элементы — изменяемые Book, вызов borrow() в map изменит общую книгу. У записи Student балл заменить нельзя. Эффекты зависят от кода переданной функции; сами операции filter и map состав источника сохраняют.

20.2 Композиция отчёта и границы эффектов

Для отчёта нужно отобрать участников, упорядочить целые записи и только затем представить их текстом. Если сначала оставить одни имена, балл и код уже недоступны компаратору. Тип каждой стадии показывает, какие сведения ещё можно использовать:

java.util.Comparator<Student> reportOrder =
    java.util.Comparator.comparingInt(Student::score).reversed()
        .thenComparing(Student::id);
var report = students.stream()
    .filter(s -> s.score() >= 80)
    .sorted(reportOrder)
    .map(s -> s.id() + ";" + s.name() + ";" + s.score())
    .toList();
System.out.println(report); // [s1;Ada;90, s3;Ann;80]

Порог включён: балл 80 проходит. Для общего числа threshold используют score() >= threshold, диапазон порога 0..100 проверяют до расчёта. У кодов "s10" и "s2" строковый порядок ставит s10 первым: это не числовая сортировка суффиксов. Порядок входа отчётом не меняется.

Тот же расчёт можно выразить циклом и сортировкой отдельного списка:

static java.util.List<Student> selectedLoop(java.util.List<Student> source,
        int threshold, java.util.Comparator<Student> order) {
    var selected = new java.util.ArrayList<Student>();
    for (Student student : source) {
        if (student.score() >= threshold) selected.add(student);
    }
    selected.sort(order);
    return java.util.List.copyOf(selected);
}

Вызов selectedLoop(students, 80, reportOrder) возвращает участников с кодами s1, s3. Их форматирование как id;name;score даёт те же строки, что и конвейер. При пороге 100 на этих данных и при пустом входе обе формы дают пустой результат. selectedLoop сохраняет ссылки на выбранных неизменяемых Student; итоговый report содержит строки. Оба списка запрещают изменения через свои методы. Выбор цикла либо Stream сохраняет условие отчёта и исходный порядок данных источника.

System.out.println(report) здесь показывает готовый список для наблюдения. В CLI каждую строку печатают отдельно: без скобок списка и без заголовка.

Текст можно проверить, сохранить или напечатать позже. Если добавить печать в map, вычисление получит внешний эффект. Тогда отказ на позднем элементе не отменит уже напечатанные строки. Уже выполненные эффекты сохраняются при исключении, как описано в Состояние программы после исключения.

Вычисление результата можно отделить от изменения объектов и вывода. filter не изменяет состав источника, но переданная функция всё ещё способна сделать это или изменить сам элемент. Условия невмешательства в источник и независимости поведения от изменяемого состояния задаются договором Stream [106]. Синтаксис -> сам эти условия не проверяет.

Если задача состоит в вычислении такого отчёта, внутренний обход позволяет сосредоточиться на связях между входом и результатом. Если же после каждого участника требуется выполнить внешнее действие и сразу принять решение о продолжении, собственный цикл сохраняет управление в одном месте: видно, какое действие уже выполнено к моменту отказа. При изменении требований первоначальный конвейер может уступить место циклу. Общность условия отбора при этом сохраняется: тот же предикат может использоваться в обеих формах. Выигрыш одной формы зависит от того, какую часть управления приложение готово передать библиотеке.

20.3 Отсутствие и ошибка в результате обработки

Пустой список прошедших порог — успешный результат. Отсутствие максимального элемента на пустом каталоге тоже ожидаемо и представляется Optional<Student>. Неверный балл входной записи имеет другую причину: данные не соответствуют формату. Если представить оба случая Optional.empty(), вызывающий код уже не сможет отличить «никого нет» от «запись не удалось разобрать».

В Типизированный результат проверки балла для разбора балла использован ScoreResult с отдельными вариантами успеха и ошибки. Для поиска лучшего участника здесь достаточно Optional: поиск даёт ноль или одно значение. Диагностику нарушенного формата хранит отдельный тип результата разбора. Ошибка чтения файла остаётся ещё одним исходом и учитывается на файловой границе. Ожидаемое отсутствие описывает Optional, а причину неверного формата сохраняет результат разбора с диагностикой.

При обработке набора ошибок появляется дополнительный выбор. Можно остановиться при первом неверном поле, собрать все диагностики или пропустить строку. Сбор ScoreResult в список сохраняет исходы, но ещё не выбирает эту политику. Два приложения используют разные договоры. В проекте «Ведомость» (Упражнение 27.14) grade.Main input threshold получает два аргумента. Загрузчик целиком проверяет файл и уникальность нормализованных кодов; неверная запись останавливает загрузку. Только успешная загрузка допускает вычисление и публикацию строк id;name;score. Пустой успешный отчёт даёт пустой стандартный вывод; CLI различает исходы кодами 0/2/3/4.

В Глава 24 программа deliveries.Main получает один аргумент — путь к файлу поставок. Она суммирует положительные количества по названиям товаров. Неверная строка сохраняется как диагностика с физическим номером, а обработка следующих строк продолжается. Готовый результат содержит и суммы принятых строк, и список проблем; переполнение суммы также становится проблемой строки. Ошибка чтения или закрытия файла прерывает получение этого результата. Поэтому выбор между циклом и Stream следует делать после выбора политики ошибок: тип конвейера сам её не устанавливает.

20.4 Ленивость промежуточных операций

Промежуточные операции строят описание обработки; они ленивы. Обход элементов начинается при терминальной операции. Само получение источника может выполнить другую работу: например, файловый источник сначала открывает ресурс. В следующем опыте источник уже задан значениями:

var pipeline = java.util.stream.Stream.of(1, 2, 3)
    .map(n -> n * 2);
System.out.println("built");
pipeline.forEachOrdered(n -> System.out.println("take " + n));
System.out.println("done");

До терминальной операции выводится только built. Затем forEachOrdered выполняет действие для каждого результата в порядке встречи элементов: take 2, take 4, take 6. После его завершения печатается done. Порядок встречи (encounter order) здесь задан источником 1, 2, 3 и сохранён преобразованием. Вызов forEachOrdered — место обязательного вывода. Значения 2, 4, 6 вычисляются из исходных чисел, и печать получает их в заданном порядке. Если действие требуется для каждого элемента результата, его помещают в терминальный потребитель. Эффект промежуточной операции может исчезнуть, когда библиотека получает конечный ответ без этой операции, например при сочетании peek и count. Основания — forEachOrdered и побочные эффекты Stream.

Ленивость позволяет не создавать промежуточный список после каждого шага. Для связки filter и map реализация может обработать первый элемент через обе стадии, затем перейти ко второму. Это не обязательно «сначала проверить всех, затем преобразовать всех». Однако сортировка конечного общего набора должна получить достаточно данных для определения порядка, поэтому sorted относится к операциям с состоянием и требует буферизации.

Если источник изменяемый, результат зависит от правил связывания с этим источником. Создание stream() не создаёт снимка списка. Изменения обычного списка завершают до прохода, а переданные функции оставляют источник прежним. Это условие невмешательства (non-interference). ConcurrentModificationException обнаруживает лишь часть нарушений и не заменяет соблюдения условия.

20.5 Одноразовость потока

Stream предназначен для одного использования. После терминальной операции повторное применение недопустимо. Кроме того, нельзя строить независимые ветки от уже связанного промежуточными операциями экземпляра.

var stream = students.stream();
System.out.println(stream.count()); // 3
// stream.toList(); // повторное использование недопустимо

Реализация может обнаружить повтор и выдать IllegalStateException, но обнаружение нарушения не гарантировано для всех форм повторного использования. Для нового расчёта создают новый students.stream(). Коллекция остаётся доступна для новых проходов. У файлового источника повторный проход означает повторное открытие файла, то есть стоимость и возможные новые ошибки ввода-вывода.

Генератор Python тоже может исчерпаться. У Java Stream обработка выражена типизированными библиотечными операциями; индексного доступа и операции возврата в начало у него нет. Если требуется многократный анализ одних данных, сначала сохраняют данные в подходящей коллекции, если это допустимо по памяти.

20.6 Короткое замыкание

findFirst, anyMatch, allMatch и noneMatch могут завершить обработку, как только ответ известен. Такой ранний выход называется коротким замыканием.

boolean found = java.util.stream.Stream.of(1, 2, 3).anyMatch(n -> {
    System.out.println("test " + n);
    return n == 2;
});
System.out.println(found); // гарантированный ответ: true
var first = students.stream().filter(s -> s.score() >= 80).findFirst();
System.out.println(first.orElseThrow().name()); // Ada

Одна из допустимых трасс отладочного вывода — test 1, test 2, затем true; в этой трассе test 3 отсутствует. Число 2 уже подтверждает наличие подходящего элемента. anyMatch допускает завершение без проверки всех элементов, но API не фиксирует именно такую последовательность вызовов предиката или обязательное отсутствие test 3 в каждой реализации. Гарантирован булев ответ true. Для отдельного запуска можно записать отладочную трассу и сопоставить её с разрешённым коротким замыканием. anyMatch задаёт ответ и возможность короткого замыкания.

findFirst сохраняет смысл первого элемента, если источник и операции задают порядок; в этих данных имя — Ada. findAny допускает любой подходящий элемент и полезен там, где конкретный порядок ответа не требуется.

Для пустого потока anyMatch возвращает false, а allMatch и noneMatch возвращают true: ни один элемент не нарушает универсальное условие, поскольку элементов нет. Успешная универсальная проверка допускает пустой вход. Если задаче нужен хотя бы один участник и все должны пройти проверку, требование непустоты проверяют отдельно.

Ленивость не гарантирует завершение любого конвейера. Бесконечный Stream.iterate(0, n -> n + 1) можно ограничить limit(3) и получить [0, 1, 2]. Но сортировка бесконечного источника перед ограничением не получит окончательного набора. Порядок операций меняет и результат, и возможность его вычислить.

20.7 Преобразование и разворачивание

map даёт один результат для каждого элемента. Если у участника несколько тем проекта, преобразование в список тем образует поток списков. Для общей последовательности тем нужен flatMap:

var topics = java.util.List.of(
    java.util.List.of("java", "git"),
    java.util.List.of("java", "io"));
var unique = topics.stream()
    .flatMap(java.util.List::stream)
    .distinct()
    .sorted()
    .toList();
System.out.println(unique); // [git, io, java]

Сначала flatMap открывает содержимое каждого вложенного списка. distinct оставляет уникальные строки по equals, затем sorted определяет порядок результата. Если использовать только map(List::stream), получился бы Stream<Stream<String>>: уровень вложенности не исчезает автоматически.

При flatMap одному элементу соответствует ноль, один или несколько новых элементов. Эта операция пригодна для раскрытия групп, токенизации строк и дальнейшего общего отбора. Каждому правилу по-прежнему нужен подходящий тип возвращаемого потока.

20.8 Примитивные числовые потоки

Элементы Stream<Integer> имеют ссылочный тип Integer. Числовые формы IntStream, LongStream, DoubleStream дают операции для примитивов:

int total = students.stream().mapToInt(Student::score).sum();
var average = students.stream().mapToInt(Student::score).average();
System.out.println(total);                 // 240
System.out.println(average.orElseThrow()); // 80.0

Сумма пустого IntStream равна нулю, а среднее пустого потока отсутствует и представлено OptionalDouble. Если ноль — содержательная оценка, подстановка его вместо отсутствующего среднего объединит разные состояния. Операции над int по-прежнему могут переполняться; Stream не меняет арифметику языка. Для суммы большого количества баллов можно перейти к mapToLong.

20.9 Нейтральное значение и ассоциативность редукции

Если из многих значений нужен один итог, reduce объединяет их бинарной операцией. Для суммы 90, 70, 80 правило принимает две частичные суммы и возвращает их сумму:

int total = java.util.stream.Stream.of(90, 70, 80)
    .reduce(0, Integer::sum);
System.out.println(total); // 240

Ноль — нейтральное значение: 0 + x == x. Пустой поток поэтому даёт 0. При сложении можно сгруппировать вычисление как (90 + 70) + 80 или 90 + (70 + 80): обе формы дают 240. Это ассоциативность; она позволяет объединить отдельно вычисленные части. Для int сложение остаётся ассоциативным с арифметикой переполнения Java, но переполнение может нарушить предметный смысл суммы.

Предскажите, что изменится, если взять начальное значение 10. Один последовательный проход даст 10 + 90 + 70 + 80 = 250. При разбиении на две части получатся (10 + 90) + (10 + 70 + 80) = 260: лишняя десятка добавлена дважды. Значение 10 не нейтрально, поэтому такой вызов нарушает договор reduce; совпадения с ожидаемым числом в отдельном запуске недостаточно. Вычитание нарушает другое требование: (10 - 3) - 2 = 5, а 10 - (3 - 2) = 9. Оно не подходит для ассоциативного объединения.

Если естественного начального значения нет, перегрузка без identity возвращает Optional<T>:

var longest = java.util.stream.Stream.of("Ada", "Alexander", "Jo")
    .reduce((left, right) -> left.length() >= right.length() ? left : right);
System.out.println(longest.orElse("нет имён")); // Alexander

На пустом входе самого длинного имени нет. На непустом входе первое имя становится первым кандидатом; при равной длине сохраняется левый кандидат. Перегруппировка с сохранением порядка сохраняет и этот выбор.

У трёхаргументной формы тип итога может отличаться от типа элемента: students.stream().reduce(0, (sum, student) -> sum + student.score(), Integer::sum). Здесь накопитель добавляет один балл, объединитель складывает частичные итоги. Помимо нейтральности и ассоциативности требуется их согласованность: добавить участника в общую сумму должно быть равносильно объединению этой суммы с итогом одного участника. Для суммы это sum + score == sum + (0 + score). Изменяемый контейнер с общими add в качестве identity требует другого механизма — collect с отдельной фабрикой накопителей.

20.10 Сборка списка, карты и групп

toList() возвращает список, который нельзя изменить через его методы: запрещены не только добавление и удаление, но также замена set, сортировка sort и другие изменяющие операции. Например, java.util.stream.Stream.of("Ada").toList().set(0, "Ann") выбросит UnsupportedOperationException. Этот запрет относится к списку; изменяемые объекты, находящиеся в нём, сохраняют возможность изменения. Контракт collect(Collectors.toList()) не задаёт конкретный тип и изменяемость результата. Фактический класс, увиденный в отладчике, не закреплён этим контрактом. Если требуется явно изменяемый ArrayList, это выражают collect(Collectors.toCollection(ArrayList::new)).

var byScore = students.stream().collect(
    java.util.stream.Collectors.groupingBy(Student::score));
System.out.println(byScore.get(90).get(0).name()); // Ada

Для входа с баллами 90, 70, 80 ключи — эти три числа, каждая группа содержит одного участника. При добавлении ещё одного участника с 90 появится второй элемент группы byScore.get(90). Коллектор определяет создание контейнеров, добавление элементов и объединение частичных контейнеров. Пользовательский код не добавляет записи в общий внешний список.

groupingBy сопоставляет каждому ключу группу. Порядок обхода ключей в стандартной форме не задан. Если вывод должен быть воспроизводимым по ключу, передают фабрику TreeMap либо отдельно сортируют ключи при выводе. У toMap(Student::id, Student::score) повторные коды приводят к IllegalStateException, пока не задана функция объединения. Для политики «брать последнее» требуется явно задать такую функцию.

Для подсчёта внутри каждой группы передают второй коллектор:

var countByLength = java.util.List.of("Ada", "Lin", "Jo").stream()
    .collect(java.util.stream.Collectors.groupingBy(
        String::length, java.util.stream.Collectors.counting()));
System.out.println(countByLength.get(3)); // 2
System.out.println(countByLength.getOrDefault(4, 0L)); // 0

Ключ — длина строки, значение — Long с числом элементов этой группы. Пустой источник даёт пустую карту. Отсутствующий ключ можно представить нулём при чтении отчёта, сохранив саму карту без лишних записей. Если отчёт следует внешнему списку запросов, порядок задаёт обход этого списка; порядок ключей карты для него не нужен.

20.11 Отсутствующее значение и эффект выполнения

Результат findFirst или max может отсутствовать. Optional<T> делает эту ветвь явной:

String bestName = students.stream()
    .max(java.util.Comparator.comparingInt(Student::score))
    .map(Student::name)
    .orElse("нет участников");
System.out.println(bestName); // Ada

map внутри Optional преобразует только существующее значение. orElse получает уже вычисленный запасной аргумент; orElseGet получает поставщика и вызывает его только при отсутствии. Метод с результатом Optional<T> обозначает отсутствие через Optional.empty(). Возврат null нарушает этот договор и требует от клиента дополнительной проверки ссылки. Его формы собраны в Глава 20.

Переданные действия не вмешиваются в источник и обычно не зависят от меняющегося внешнего состояния. Обязательную печать выполняют терминальным forEach/forEachOrdered, как в опыте выше. Для count достаточно размера некоторых источников; реализация вправе устранить не влияющие на ответ стадии:

long size = java.util.List.of("Ada", "Lin").stream()
    .peek(System.out::println).count();
System.out.println(size); // 2; вывод Ada/Lin не гарантирован

Для этого фрагмента допустим вывод только 2: размер списка известен, а peek не меняет число элементов. Допустима и реализация с вызовами peek. Обязательную запись в журнал и сохранение результата выполняют операцией, которая гарантирует вызов соответствующего действия. Основание — разрешённое устранение стадий и Stream.count.

При параллельном проходе forEach допускает иной порядок эффектов; forEachOrdered сохраняет порядок встречи при его наличии. Это не делает произвольный общий объект безопасным для одновременных изменений. Например, parallelStream().forEach(sharedList::add) с обычным ArrayList может потерять элементы из-за несогласованного изменения массива и размера. collect с подходящим коллектором управляет отдельными накопителями и их объединением. Скорость параллельного прохода зависит от объёма данных, стоимости действий и разбиения; она требует измерения.

20.12 Файловый источник и момент отказа

У списка данные уже в памяти. Files.lines открывает файл, затем лениво читает строки по мере потребления потока. Поэтому файл должен оставаться открытым во время терминального вызова. Следующий метод возвращает число непустых после удаления краевых пробелов строк:

static long countNonblank(java.nio.file.Path path) throws java.io.IOException {
    try (var lines = java.nio.file.Files.lines(
            path, java.nio.charset.StandardCharsets.UTF_8)) {
        return lines.map(String::strip)
            .filter(line -> !line.isEmpty())
            .count();
    }
}

Для содержимого Ada\n \nAnn метод вернёт 2. Последняя строка учитывается и без завершающего перевода строки. Сначала Files.lines открывает ресурс, count требует чтения, а выход из try закрывает поток. Терминальная операция сама файл не закрывает. Если вернуть lines из этого try, вызывающий код получит уже закрытый ресурс; если вообще не закрывать поток, ресурс может оставаться занят.

Момент ошибки влияет на её тип. Открытие может выбросить IOException. Ошибка последующего чтения, декодирования или закрытия потокового источника передаётся как UncheckedIOException, содержащий исходную IOException. Поэтому объявленный throws IOException у метода не перечисляет всех возможных отказов. Вызывающий код, который сообщает об ошибке ввода-вывода, учитывает обе формы. Результат count передаётся наружу только после успешного закрытия. Файл во время терминального прохода не изменяют. Договор Files.lines связывает ленивость, ресурс и ошибки; устройство try разобрано в Глава 22.

20.13 Порядок стадий конвейера

Конвейер читается как порядок действий, поэтому переставлять стадии можно лишь после проверки результата. Для чисел 1, 2, 3, 4 сначала filter по чётности и затем limit(1) дают число 2. Сначала limit(1) и затем та же проверка дают пустой результат: первым ограничение сохранило только единицу. Эти цепочки описывают разные вопросы: первый чётный среди всего входа или проверка первого входного числа.

skip пропускает заданное число элементов на своей стадии. На входе [1, 2, 3, 4] цепочка filter(n -> n % 2 == 0).skip(1) оставляет [4]: сначала найдены 2, 4, затем пропущен первый из них. Цепочка skip(1).filter(n -> n % 2 == 0) оставляет [2, 4]: пропущена исходная единица. При skip(10) этот конечный источник даёт пустой результат; отрицательное число у skip или limit даёт IllegalArgumentException.

Похожее различие есть у сортировки и ограничения. «Десять первых после сортировки» и «отсортировать десять первых входных элементов» равны не всегда. Для отчёта о лучших оценках отбор и порядок должны соответствовать требованию: изменение порядка стадий меняет состав отчёта. В тесте нужен вход, на котором перестановка стадий наблюдаема; уже отсортированный вход не обнаружит такой ошибки.

Поток, построенный от списка, продолжает зависеть от источника и правил его связывания. Если программа должна обработать состав на определённый момент, она сначала получает самостоятельную коллекцию согласно правилам владения. При этом копия структуры ещё не копирует изменяемые элементы; для действительно стабильного отчёта важна также устойчивость их существенных полей.

Для подсчёта результатов полезно сохранять нейтральную форму объединения. Частичные суммы можно сложить и получить общий ответ, а наборы групп можно объединить по ключам. Лямбда, которая печатает позицию в общем счётчике или зависит от предыдущего элемента, скрывает иной алгоритм — последовательную обработку со состоянием. Её нельзя автоматически сделать корректной параллельной цепочкой. Обычный цикл с явным состоянием может яснее выражать такую задачу, чем вынесенные наружу изменяемые массивы и коллекции.

При чтении конвейера прослеживают тип и значение элемента на каждой стадии. Обращения к внешним изменяемым объектам добавляют зависимость от состояния и порядка вызовов; такую зависимость учитывают отдельно от движения элементов.
