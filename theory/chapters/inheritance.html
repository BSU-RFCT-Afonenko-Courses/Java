12.1 Суперкласс и состояние подкласса

Наследование классов связывает объявленный подкласс с его суперклассом. Подкласс получает доступные наследуемые члены, может добавлять собственные поля и методы и переопределять методы экземпляра. Одновременно возникает отношение подтипов: ссылку на экземпляр подкласса разрешено использовать там, где требуется ссылка на суперкласс [81].

Документ хранит заголовок, отличный от null, и возвращает его как краткое описание:

class Document {
    private final String title;

    Document(String title) {
        this.title = java.util.Objects.requireNonNull(title);
    }

    String summary() {
        return title;
    }
}

Текстовый документ дополнительно хранит число символов. Объявление extends Document задаёт непосредственный суперкласс:

class TextDocument extends Document {
    private final int characters;

    TextDocument(String title, int characters) {
        super(title);
        if (characters < 0) {
            throw new IllegalArgumentException("Отрицательное число символов");
        }
        this.characters = characters;
    }

    int characters() {
        return characters;
    }

    @Override
    String summary() {
        return super.summary() + ": " + characters + " chars";
    }
}

new TextDocument("Notes", 120) создаёт один экземпляр. В нём есть поле title, объявленное в Document, и поле characters, объявленное в TextDocument. Вызов super(title) поручает конструктору Document инициализировать заголовок этого же экземпляра. Метод summary() подкласса использует базовое описание через super.summary() и дописывает число символов; результат равен "Notes: 120 chars".

Закрытые члены суперкласса не наследуются. Поле title входит в состояние созданного объекта, но непосредственно обращаться к нему из показанного отдельного класса TextDocument запрещено. Базовый метод summary() читает это поле в коде Document, где доступ разрешён. Изменение представления заголовка поэтому можно выполнить внутри Document, сохранив способ обращения подкласса к описанию.

Доступ public и protected позволяет подклассу пользоваться соответствующими членами суперкласса. Для члена без модификатора необходимо совпадение пакетов объявляющего класса и подкласса. В примере оба класса находятся в одном пакете, поэтому summary() без модификатора доступен подклассу. Для расширения из другого пакета конструктор и переопределяемые операции обычно предоставляют с доступом protected или public. Правила доступа, включая ограничения protected-получателя, приведены в Глава 11.8.

Каждый класс, кроме Object, имеет один непосредственный суперкласс. У обычного класса без extends им служит Object. Если новый класс расширит TextDocument, он будет также подтипом Document и Object: отношение подтипов транзитивно. Наследование класса одновременно от двух классов запрещено. Несколько общих наборов операций объект может предоставлять через интерфейсы: Глава 13.

12.2 Конструкторы базового класса и подкласса

Конструкторы не наследуются. Объявленный TextDocument(String, int) определяет допустимую форму new TextDocument("Notes", 120). Наличие Document(String) не создаёт конструктор TextDocument(String). Его можно объявить отдельно, задав число символов по умолчанию:

TextDocument(String title) {
    this(title, 0);
}

this(...) вызывает другой конструктор того же класса для того же экземпляра. Вызванный конструктор передаёт заголовок в super(title); после его завершения управление возвращается в вызвавший конструктор. Новая копия объекта при таком переходе не создаётся. Цепочка this(...) должна закончиться вызовом конструктора суперкласса; прямой или косвенный цикл вызовов this(...) запрещён при компиляции.

super(...) выбирает доступный конструктор непосредственного суперкласса по аргументам. Если явного вызова this(...) или super(...) нет, в классе, отличном от Object, подразумевается super(). У Document нет конструктора без параметров: удаление super(title) из двухаргументного конструктора TextDocument приводит к ошибке компиляции. Java не подбирает конструктор по совпадению имени параметра title.

12.2.1 Порядок инициализации экземпляра

Память нового экземпляра сразу включает поля всей цепочки классов. Каждое поле первоначально получает значение по умолчанию: например, null для String и 0 для int. Затем конструкторы и инициализаторы устанавливают заданное программой состояние. Для new TextDocument("Notes", 120) порядок таков:

Этап title characters
Значения по умолчанию null 0
Завершение конструктора Object null 0
Присваивание в Document(String) "Notes" 0
Присваивание в TextDocument(String, int) "Notes" 120

После возврата из конструктора суперкласса выполняются инициализаторы полей и блоки инициализации текущего класса в порядке их записи. Затем выполняется часть тела конструктора после super(...) — эпилог. Поля title и characters не имеют явных инициализаторов, поэтому значения им присваивают конструкторы Document и TextDocument. При делегировании через this(...) инициализаторы этого класса выполняются один раз, в ходе вызванного конструктора, который обращается к суперклассу. [52]

В Java 25 перед явным super(...) или this(...) разрешена ограниченная начальная часть тела — пролог. Он позволяет проверить параметры до обращения к следующему конструктору. У Child ниже есть явный инициализатор поля, поэтому видны все этапы:

class Parent {
    Parent(int value) {
        System.out.println("parent: " + value);
    }
}

class Child extends Parent {
    private int marker = initialize();

    private static int initialize() {
        System.out.println("field");
        return 7;
    }

    Child(int value) {
        if (value < 0) {
            throw new IllegalArgumentException("Отрицательное значение");
        }
        System.out.println("prologue");
        super(value);
        System.out.println("epilogue: " + marker);
    }
}

Для new Child(3) вывод состоит из четырёх строк:

prologue
parent: 3
field
epilogue: 7

Сначала проверяется параметр и выполняется пролог Child. Вызов super(value) запускает конструктор Parent, который также обращается к конструктору Object. После возврата из Parent выполняется marker = initialize(), затем эпилог Child читает записанное значение 7. При new Child(-1) проверка завершает создание исключением до первой печати и до вызова Parent(int). При исключении из конструктора или инициализатора оставшиеся этапы создания также не выполняются, а выражение new не возвращает ссылку как нормальный результат.

В прологе можно вычислять значения по параметрам, обращаться к статическим операциям и к другим уже существующим объектам. Читать поля создаваемого экземпляра, вызывать его методы или передавать this внешнему коду запрещено. Например, System.out.println(marker) перед super(value) не компилируется. Есть разрешённая форма ранней записи: простое присваивание полю, объявленному в текущем классе без инициализатора. Для поля int value; запись this.value = value допустима; this.value++ требует чтения и запрещена. Запись в унаследованное поле в прологе также запрещена.

Тело конструктора содержит не более одного явного вызова другого конструктора; разместить super(...) в ветвях if нельзя. Тело конструктора, JLS 25 §8.8.7, порядок создания, §12.5.

12.3 Статический тип и динамический выбор метода

Статический тип выражения определяется при компиляции. Он задаёт доступные объявления методов и полей. Фактический класс объекта устанавливается при его создании и участвует в выборе переопределённого метода во время выполнения:

Document plain = new Document("Guide");
Document text = new TextDocument("Notes", 120);
System.out.println(plain.summary()); // Guide
System.out.println(text.summary());  // Notes: 120 chars

Обе переменные имеют статический тип Document, где объявлен summary(). Поэтому оба вызова допустимы. При выполнении получателем первого вызова служит экземпляр Document, второго — экземпляр TextDocument. Второй вызов выбирает переопределение TextDocument.summary(). Такой выбор называется динамическим связыванием, или диспетчеризацией. Поиск реализации начинается с фактического класса получателя и следует по цепочке суперклассов, пока не найдёт подходящее переопределение. Если подкласс не переопределяет метод, используется унаследованная реализация. [81]

Общий метод печати может принять оба документа:

static void print(Document document) {
    System.out.println(document.summary());
}

print(plain); // Guide
print(text);  // Notes: 120 chars

Параметр document получает копию переданной ссылки. Вызов summary() обращается к тому же объекту, который передал клиент. Добавление подкласса с собственным описанием позволяет использовать прежний print: его тело требует только операции, объявленной в Document.

Метод characters() объявлен лишь в TextDocument. Выражение text.characters() не компилируется, поскольку статический тип text равен Document. Присваивание ссылки базовой переменной сохраняет объект и оба его поля; меняется доступный через выражение набор членов. В C++ копирование производного объекта в отдельный объект базового класса может отбросить производную часть — это срезка. В Java приведённое присваивание копирует ссылку и сохраняет исходный экземпляр. Аналогия с C++ здесь — обращение через базовый указатель или ссылку к объекту производного класса. Для обычного переопределяемого метода Java ключевое слово virtual не требуется.

12.3.1 Уточнение типа ссылки

Проверка instanceof устанавливает, относится ли существующий объект к указанному типу, и может сразу объявить переменную с уточнённым типом:

Document value = new TextDocument("Notes", 120);
if (value instanceof TextDocument text) {
    System.out.println(text.characters()); // 120
    System.out.println(text == value);     // true
}

Обе переменные ссылаются на один документ. Явное приведение (TextDocument) value тоже проверяет совместимость при выполнении. Для new Document("Guide") такая проверка завершилась бы ClassCastException: фактический класс Document не является подтипом TextDocument. Для null приведение возвращает null, а instanceof даёт false. Вызов метода экземпляра через null приводит к NullPointerException.

Если инициализатор записан через переменную базового типа, var сохраняет этот тип:

Document document = new TextDocument("Notes", 120);
var same = document; // статический тип same — Document

Тип same выводится из выражения document; проверка фактического класса при выводе типа не выполняется. Поэтому same.summary() допустим, а same.characters() отвергается при компиляции.

12.4 Перегрузка и динамический выбор метода

При перегрузке одно имя имеет несколько объявлений с различающимися сигнатурами. Компилятор выбирает применимое объявление по статическим типам получателя и аргументов, допустимым преобразованиям и правилам наиболее специфичного метода. Динамический выбор реализации происходит после этого выбора, если вызван переопределяемый метод экземпляра. [97]

static String kind(Document value) { return "Document overload"; }
static String kind(TextDocument value) { return "Text overload"; }

TextDocument text = new TextDocument("Notes", 120);
Document value = text;
System.out.println(kind(value));     // Document overload
System.out.println(kind(text));      // Text overload
System.out.println(value.summary()); // Notes: 120 chars
System.out.println(text.summary());  // Notes: 120 chars

value и text ведут к одному объекту. Для kind(value) компилятор знает тип Document; преобразование к более узкому TextDocument не выполняется автоматически, поэтому выбирается первый метод. У kind(text) применимы оба объявления, из которых вариант с параметром TextDocument более специфичен. В двух вызовах summary() получатель один, и оба выполняют тело TextDocument.summary().

Унаследованные методы тоже участвуют в перегрузке. Если подкласс объявляет summary(int limit), он добавляет новую форму вызова; унаследованный summary() сохраняется. Если требовалось изменить именно summary(), добавление параметра оставит прежний метод действующим. При наличии аннотации @Override на ошибочно написанном summary(int limit) компилятор потребует переопределяемое объявление и обнаружит такую ошибку.

12.4.1 Сокрытие полей и статических методов

Одноимённые поля базового и производного классов хранятся независимо. Доступ к полю выбирается по статическому типу выражения получателя. Статический метод подкласса с той же сигнатурой скрывает статический метод суперкласса; его объявление также выбирается при компиляции:

class Base {
    String label = "base field";
    String label() { return "base method"; }
    static String category() { return "base static"; }
}

class Child extends Base {
    String label = "child field";
    @Override String label() { return "child method"; }
    static String category() { return "child static"; }
}

Base ref = new Child();
System.out.println(ref.label);             // base field
System.out.println(((Child) ref).label);   // child field
System.out.println(ref.label());           // child method
System.out.println(((Base) ref).label());  // child method
System.out.println(Base.category());       // base static
System.out.println(Child.category());      // child static

Приведение ((Base) ref) сохраняет ссылку на Child, поэтому вызов метода остаётся динамическим. Для прямого обращения к реализации суперкласса из подкласса служит super.label(). Эта запись выбирает базовое тело для текущего вызова и сохраняет прежнего получателя this. Если базовое тело само вызовет другой переопределяемый метод, тот внутренний вызов снова подчиняется динамическому выбору.

Допустимая запись ref.category() выбрала бы Base.category() по типу ref. Вызовы через имена классов явно показывают источник статического метода. Заменить статический метод методом экземпляра с той же сигнатурой, как и выполнить обратную замену, нельзя.

12.5 Правила переопределения

Для метода без параметров типов сигнатуру образуют имя и упорядоченный список типов параметров. Имена параметров, возвращаемый тип, модификатор доступа и список throws в сигнатуру не входят. Поэтому объявления int count() и long count() не создают перегрузку: в одном классе такое сочетание недопустимо. Для обобщённых методов дополнительно учитываются параметры типов и предусмотренная языком совместимость сигнатур при стирании: Глава 16.7.

Переопределение задаёт в подклассе реализацию доступного метода экземпляра суперкласса с соответствующей сигнатурой. При отсутствии обобщений типы параметров сохраняются точно. Например, замена accept(Document value) на accept(TextDocument value) создаёт перегрузку. Метод базового типа должен оставаться вызываемым и для обычного Document, поэтому его параметр нельзя сузить таким способом. Замена типа параметра на более широкий, например Object, тоже образует другую сигнатуру.

При наличии @Override компилятор проверяет, есть ли подходящий метод для переопределения. Закрытый private-метод не наследуется и не переопределяется; одноимённый метод подкласса представляет отдельное объявление. У обычного переопределения действуют следующие ограничения:

Часть объявления Допустимое изменение
Доступ Сохранить или расширить: например, protected → public
Ссылочный результат Сохранить тип или уточнить до подтипа
Примитивный результат Сохранить точно тот же тип
Результат void Сохранить void
Проверяемые исключения в throws Оставить прежние типы, сузить их до подтипов или убрать

Метод public остаётся public; метод protected можно объявить protected или public. Уменьшение доступа сделало бы часть допустимых базовых вызовов недоступными. Ковариантность ссылочного результата позволяет клиенту базового типа получить подходящий объект более конкретного класса. [97]

12.5.1 Ковариантный результат и проверяемые исключения

Источник документа объявляет операцию load(). Базовое объявление задаёт результат типа Document; IOException обозначает проверяемый отказ получения данных. Такой отказ вызывающий метод должен обработать либо указать в собственном throws. Источник из памяти уже хранит готовый TextDocument и возвращает его без операции ввода-вывода. Модификатор abstract у базового метода оставляет его реализацию конкретному подклассу:

abstract class DocumentSource {
    protected abstract Document load() throws java.io.IOException;
}

final class MemorySource extends DocumentSource {
    private final TextDocument document;

    MemorySource(TextDocument document) {
        this.document = java.util.Objects.requireNonNull(document);
    }

    @Override
    public TextDocument load() {
        return document;
    }
}

Здесь protected расширен до public, Document уточнён до TextDocument, а throws IOException убран. При вызове из того же пакета, где объявлен DocumentSource, видны такие различия:

MemorySource memory = new MemorySource(new TextDocument("Notes", 120));
TextDocument text = memory.load();
System.out.println(text.characters()); // 120

DocumentSource source = memory;
Document document = source.load();
System.out.println(document == text);  // true

Оба вызова выполняют MemorySource.load() и возвращают одну ссылку. У выражения memory.load() статический тип результата — TextDocument. У source.load() он равен Document; присваивание такого результата переменной TextDocument без приведения не компилируется. Для второго вызова требуется обработка или объявление IOException, потому что компилятор проверяет доступное базовое объявление. Полный метод с этим опытом может объявить throws java.io.IOException.

Подкласс источника мог бы сохранить throws IOException или указать его подкласс FileNotFoundException. Добавить throws Exception либо независимый проверяемый тип, например SQLException, нельзя: обработчик базового клиента, рассчитанный на IOException, не покрывает такие отказы. Каждое проверяемое исключение переопределения должно быть разрешено базовым throws непосредственно или через указанный там супертип. К RuntimeException, Error и их подклассам это ограничение проверяемых исключений не применяется.

Конструкторы не переопределяют друг друга. Если вызываемый через super(...) конструктор объявляет проверяемое исключение, конструктор подкласса должен объявить его или покрывающий супертип в своём throws. Обычные правила обработки исключений и их разновидности даны в Глава 21. [52]

12.6 Поведенческая подстановка

Проверки объявлений обеспечивают совместимость вызова с системой типов. Для работы общего алгоритма нужно также сохранить смысл операции. Поведенческая подстановка требует, чтобы объект подкласса можно было использовать в допустимых для базового типа действиях: принимаемые базовым методом входы остаются допустимыми, требуемые свойства результата и состояния сохраняются, отказы соответствуют условиям операции.

Для Document.summary() результатом служит строка, отличная от null. Это позволяет клиенту сразу запросить её длину:

static int summaryLength(Document document) {
    return document.summary().length();
}

System.out.println(summaryLength(new TextDocument("Notes", 120))); // 16

Подкласс может нарушить требование к результату при формально верном переопределении:

class SilentDocument extends Document {
    SilentDocument(String title) { super(title); }
    @Override String summary() { return null; }
}

summaryLength(new SilentDocument("Notes")) завершится NullPointerException на вызове length(). Ссылочный тип String допускает null, поэтому компилятор принимает такое тело. Возврат "" сохранил бы существующий строковый результат: длина равнялась бы 0. В заданном Document пустой заголовок разрешён, поэтому пустая строка также входит в допустимые результаты.

Усиление требований к аргументу даёт другой вид нарушения. Если базовый reserve(n) принимает любое положительное n, не превышающее свободный остаток, то при остатке 5 запрос reserve(3) допустим. Подкласс, добавивший отказ для нечётных значений, отклонит допустимый базовый запрос. Тип int и сигнатура метода при таком изменении останутся прежними.

12.6.1 Изменяемый прямоугольник и квадрат

У изменяемого прямоугольника setWidth(w) меняет ширину и сохраняет высоту, а setHeight(h) меняет высоту и сохраняет ширину. Пусть стороны имеют целые значения от 1 до 1000; площадь возвращается как int. Для прямоугольника со сторонами 4 и 4 клиент выполняет:

static int widen(Rectangle rectangle) {
    rectangle.setWidth(7);
    return rectangle.area();
}

System.out.println(widen(new Rectangle(4, 4))); // 28

Попытка представить изменяемый квадрат подклассом такого прямоугольника требует сохранять равенство сторон. Переопределение меняет обе стороны:

class MutableSquare extends Rectangle {
    MutableSquare(int side) { super(side, side); }

    @Override
    void setWidth(int width) {
        super.setWidth(width);
        super.setHeight(width);
    }

    @Override
    void setHeight(int height) {
        super.setWidth(height);
        super.setHeight(height);
    }
}

System.out.println(widen(new MutableSquare(4))); // 49

У прямоугольника состояние после вызова равно (7, 4), у квадрата — (7, 7). Квадрат сохранил равенство своих сторон и нарушил требование setWidth сохранять высоту. Математическое включение квадратов в прямоугольники совместимо с чтением площади, но данный изменяемый API требует переходов состояния, невозможных для квадрата.

Общий тип с одной операцией area() позволяет обоим видам сохранять свои свойства. Другой вариант — неизменяемые значения: операция создания прямоугольника с новой шириной возвращает новый прямоугольник, а существующий квадрат сохраняет прежние стороны. Выбор общей операции определяет, какое отношение подтипов пригодно для клиента.

12.7 Абстрактные методы и классы

У всех фигур можно запросить площадь, но её формула зависит от вида фигуры. Абстрактный метод объявляет операцию без тела; конкретный подкласс предоставляет реализацию. Абстрактный класс может сочетать такие операции с полями, конструкторами и готовыми методами:

abstract class Shape {
    abstract double area();

    final String report() {
        return "area=" + area();
    }
}

final class Square extends Shape {
    private final double side;

    Square(double side) {
        if (!Double.isFinite(side) || side < 0) {
            throw new IllegalArgumentException("Нужна конечная неотрицательная сторона");
        }
        this.side = side;
    }

    @Override
    double area() {
        return side * side;
    }
}

Shape shape = new Square(3);
System.out.println(shape.report()); // area=9.0

new Shape() запрещён. Неабстрактный подкласс должен иметь реализации всех обязательных абстрактных методов, получив их по наследованию или объявив самостоятельно. Подкласс, сохраняющий нереализованную операцию, тоже объявляется abstract. Абстрактный класс может иметь полностью реализованные методы и даже не содержать абстрактных; модификатор всё равно запрещает непосредственное создание его экземпляров. [81]

report() задаёт готовый алгоритм: получить площадь и построить строку. При вызове на Square его внутренний вызов area() выбирает формулу квадрата. Модификатор final у report() запрещает подклассу заменять сам алгоритм, сохраняя возможность переопределять вызываемую операцию area(). Абстрактный метод нельзя одновременно сделать final, private или static: для него требуется реализация методом экземпляра подкласса. Конструктор абстрактного класса выполняется в цепочке создания конкретного объекта по обычным правилам.

В Square конечность стороны проверяется при создании. Произведение очень больших конечных сторон может дать Double.POSITIVE_INFINITY: double вычисляет площадь с ограниченными диапазоном и точностью. Если API требует конечную площадь, конструктор должен дополнительно проверить конечность side * side и отвергнуть неподходящее значение.

final у класса Square запрещает объявлять его подклассы. Этот модификатор не запрещает менять поля или вызывать изменяющие методы: неизменяемость объекта определяется устройством состояния и операций. sealed позволяет ограничить набор непосредственных подтипов; модель такой семьи разобрана в Глава 14.

12.8 Переопределяемые методы в конструкторе

Динамическое связывание действует уже во время создания объекта. Если базовый конструктор вызывает переопределяемый метод, выполняется реализация фактического подкласса:

class Parent {
    Parent() { show(); }
    void show() { System.out.println("parent"); }
}

class ChildState extends Parent {
    private int value = 7;
    @Override void show() { System.out.println(value); }
}

ChildState child = new ChildState(); // 0
child.show();                       // 7

До вызова Parent() поле value получило значение по умолчанию 0. В конструкторе Parent вызов show() сразу выбирает ChildState.show(). Инициализатор value = 7 выполняется после возврата из Parent, поэтому первое чтение видит 0. Второе чтение после завершения new видит 7. Если объявить private final int value; и присвоить value = 7 в эпилоге конструктора ChildState(), ранний вызов также прочитает 0. Ограничение однократного присваивания не переносит эту запись перед вызовом базового конструктора. [54]

Ранняя запись в прологе Java 25 может изменить именно этот результат. В альтернативном объявлении поле не имеет инициализатора, а конструктор подкласса присваивает его до super():

class EarlyChild extends Parent {
    private int value;

    EarlyChild() {
        this.value = 7;
        super();
    }

    @Override void show() { System.out.println(value); }
}

EarlyChild child = new EarlyChild(); // 7
child.show();                       // 7

При вызове из Parent() поле этого подкласса уже равно 7. Другой подкласс может устанавливать нужные методу поля после super(); базовый конструктор не управляет их порядком. Чтобы он не зависел от готовности состояния неизвестного подкласса, из него исключают прямые и косвенные вызовы переопределяемых методов. Вызов private- или final-помощника фиксирует его тело, но нужно учитывать и последующие вызовы из этого тела: переход к переопределяемому методу снова допускает выполнение кода подкласса.

В C++ виртуальный вызов для создаваемого объекта из конструктора базового класса выбирает окончательное переопределение для класса этого конструктора. Переопределение более производного класса в этот момент не выбирается. В аналогичном опыте конструктор Parent вызвал бы Parent::show, тогда как Java уже вызывает ChildState.show. Правило виртуального вызова в C++, class.cdtor.

12.9 Композиция и внутренние вызовы

Переопределение меняет также вызовы, которые базовый класс делает на собственном this. Из-за этого подкласс может зависеть от внутреннего устройства базового алгоритма. Пусть счётчик умеет увеличиваться на единицу и на заданное число; add(n) вызывает increment() для каждой единицы:

class Counter {
    private int value;

    void increment() { value++; }
    int value() { return value; }

    void add(int n) {
        if (n < 0) throw new IllegalArgumentException("Отрицательное приращение");
        for (int i = 0; i < n; i++) {
            increment();
        }
    }
}

Для подсчёта добавленных единиц подкласс перехватывает обе операции:

class CountingCounter extends Counter {
    private int added;

    @Override
    void increment() {
        added++;
        super.increment();
    }

    @Override
    void add(int n) {
        if (n < 0) throw new IllegalArgumentException("Отрицательное приращение");
        added += n;
        super.add(n);
    }

    int added() { return added; }
}

CountingCounter counter = new CountingCounter();
counter.add(3);
System.out.println(counter.value()); // 3
System.out.println(counter.added()); // 6

Сначала CountingCounter.add(3) прибавляет 3 к added. Затем super.add(3) выбирает базовое тело, но его this по-прежнему обозначает тот же CountingCounter. Каждый из трёх вызовов increment() возвращается в переопределение и ещё раз увеличивает added. Базовое значение растёт от 0 до 3, а счётчик добавлений — от 0 до 6.

Если оставить учёт только в increment(), результат станет 3 при показанной реализации Counter.add. Однако замена базового цикла на прямое value += n устранит внутренние вызовы, и подкласс перестанет учитывать добавления через add. Для обычного клиента базового класса обе реализации дают то же значение на этих данных. Для подкласса способ вызова increment() становится существенной частью работы. У класса, предназначенного для расширения, такие точки вызова должны быть определены вместе с условиями их использования. [54]

Композиция размещает ссылку на используемый объект в поле другого объекта. Оболочка может учитывать запрос и передавать действие своему внутреннему счётчику:

final class CounterMeter {
    private final Counter counter = new Counter();
    private int added;

    void increment() {
        counter.increment();
        added++;
    }

    void add(int n) {
        counter.add(n);
        added += n;
    }

    int value() { return counter.value(); }
    int added() { return added; }
}

CounterMeter meter = new CounterMeter();
meter.add(3);
System.out.println(meter.value()); // 3
System.out.println(meter.added()); // 3

Здесь существуют два объекта: CounterMeter и его Counter. Вызов counter.add(3) получает this, указывающий на внутренний Counter. Внутренние вызовы increment() остаются в этом объекте; метод оболочки повторно не вызывается. После успешного завершения counter.add(3) оболочка увеличивает added один раз на 3. При отрицательном n внутренний метод бросает исключение до изменения состояния, и присваивание added += n не выполняется.

Счётчики хранят int: при суммах свыше Integer.MAX_VALUE арифметика переполняется. Подсчёт точного количества за произвольный срок потребовал бы другого представления или явного отказа при переполнении.

CounterMeter предоставляет выбранные операции и не становится подтипом Counter. Это различие проявится при развитии счётчика. Если у Counter появится новая доступная операция изменения, подкласс унаследует её; автору учёта придётся выяснить, участвует ли она в подсчёте added. У оболочки новая операция внутреннего объекта сама по себе не становится доступной клиенту. Её включение в API потребует отдельного решения и определения того, что считать.

Композиция уменьшает эту зависимость ценой методов, передающих вызовы, и отсутствия автоматической подстановки вместо Counter. Наследование может быть уместно в семье, которую разрабатывают совместно: базовый класс явно задаёт точки расширения, а договор определяет, какие из них вызывает его алгоритм. В примере CountingCounter зависел от внутреннего устройства add, чьи вызовы increment() не были закреплены в договоре. Проблема возникает именно на этой границе между договором и изменяемой реализацией. [55]

Если общий клиент должен принимать и счётчик, и оболочку, общие операции можно объявить в интерфейсе и реализовать его обоими классами. Устройство такой зависимости и передача действий компоненту разобраны в Глава 13. Формы объявлений и полные запускаемые примеры собраны в Глава 9.
