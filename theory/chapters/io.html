23.1 Последовательный источник данных

Программа подсчитывает байты изображения. Сегодня изображение лежит в файле, а при проверке алгоритма его удобно передать массивом в памяти. В обоих случаях подсчёту достаточно одного действия: получить очередной байт либо узнать, что данные закончились. Устройство источника можно оставить за пределами алгоритма.

Так устроена исходная потоковая модель java.io. Объект InputStream представляет последовательный источник байтов; OutputStream — место, куда байты последовательно записывают. FileInputStream получает их из файла, ByteArrayInputStream — из массива. Общий контракт позволяет обрабатывать оба источника одним методом. Знакомая по C++ идея потока тоже отделяет последовательное чтение от устройства источника; правила результата и ошибок задаёт уже Java API [54], [89].

static long countBytes(java.io.InputStream input)
        throws java.io.IOException {
    long count = 0;
    while (input.read() != -1) {
        count++;
    }
    return count;
}

Метод заимствует уже открытый источник. Он расходует его до конца и возвращает число; создание и закрытие остаются у вызывающего кода. Для массива из трёх байтов 41 00 FF результат равен трём. Ни нулевой байт, ни FF не завершают обход. Замена источника сохраняет смысл подсчёта, хотя возможные отказы и длительность чтения будут различаться.

Слово «поток» здесь означает последовательность данных. Поток выполнения (Thread) — исполнитель вызовов программы. Один поток выполнения может последовательно читать несколько потоков данных.

23.2 Байтовый поток и конец входа

Для одного байта существует 256 значений. Метод InputStream.read() возвращает их как int в диапазоне 0..255; отдельное значение -1 обозначает конец входа. Поэтому результат сначала проверяют как int. При предварительном приведении к byte байт FF и признак конца получили бы одно значение -1. Конец входа является результатом операции чтения; специального байта с таким смыслом в файле нет [43].

Побайтовый цикл удобен для объяснения, но при большом файле создаёт много мелких вызовов. Массив позволяет передавать порции:

static long countBlocks(java.io.InputStream input)
        throws java.io.IOException {
    byte[] block = new byte[4096];
    long total = 0;
    int count;
    while ((count = input.read(block)) != -1) {
        total += count;
        // Новые байты находятся только в block[0 .. count).
    }
    return total;
}

Ёмкость массива задаёт верхнюю границу одной порции. Если пришло 900 байтов, остальные ячейки не принадлежат этому результату: там могли сохраниться данные прошлого чтения. Порция меньше массива ещё не устанавливает конец входа. Следующий вызов проверит продолжение.

23.2.1 Буферизующая обёртка

Иногда алгоритм естественно читает по одному элементу: например, распознаёт разделители. Переписывать его ради крупных обращений к источнику неудобно. BufferedInputStream добавляет промежуточную память: получает порцию снизу и обслуживает мелкие чтения из неё. Последовательный контракт сохраняется; меняется способ его исполнения. Обёртки позволяют соединить эти обязанности без отдельного класса для каждой комбинации источника и обработки.

Выигрыш зависит от того, какие обращения стоят дорого. Дополнительная буферизация массива в памяти может только добавить работу. Алгоритм, уже передающий большие блоки, тоже не обязательно ускорится от обёртки. У выходной буферизации есть ещё цена задержки: write может сохранить данные в памяти, а передача ниже произойдёт при заполнении буфера или вызове flush. Сохранность на носителе при отключении питания определяется отдельными свойствами хранения.

Буферизация позволяет алгоритму пользоваться удобной порцией, сокращая число обращений к нижнему слою. При этом вызов чтения остаётся последовательным: если нужных данных в буфере нет, придётся обратиться к источнику и дождаться результата.

23.3 Декодирование байтов в символы

Текст добавляет другой вопрос: как последовательность байтов обозначает символы? В UTF-8 имя Ада занимает шесть байтов; в Java оно содержит три единицы char. Четырёхбайтовая порция файла может закончиться посередине кодировки знака. Приведение каждого байта к char не выполняет декодирование.

Reader представляет символьное чтение. InputStreamReader соединяет байтовый источник с декодером выбранной кодировки. Декодер учитывает состояние между порциями. BufferedReader над ним хранит символы и предоставляет чтение строк. Цепочка объединяет разные обязанности:

FileInputStream  →  InputStreamReader  →  BufferedReader  →  разбор строки
байты файла        UTF-8 → char           буфер символов     предметные поля

Для строкового пути file чтение выглядит так; окружающий метод объявляет throws IOException:

try (var reader = new java.io.BufferedReader(
        new java.io.InputStreamReader(
            new java.io.FileInputStream(file),
            java.nio.charset.StandardCharsets.UTF_8.newDecoder()))) {
    String line;
    while ((line = reader.readLine()) != null) {
        System.out.println(line);
    }
}

Декодер создан явно и сообщает об ошибочных последовательностях байтов: его исходная политика — REPORT. Другая политика могла бы заменять повреждённые участки специальным символом. Выбор зависит от назначения текста: при импорте идентификаторов незаметная замена может изменить смысл записи. char остаётся единицей UTF-16; некоторые Unicode-символы занимают две такие единицы [39].

В StreamLayersDemo последовательность Ада\nБоб\n открывается трижды. Байтовый проход насчитывает 14 байтов, символьный — 8 единиц UTF-16, строковый получает две строки. Новое открытие нужно, поскольку предыдущий проход уже дошёл до конца своего источника. Замена памяти файлом сохраняет алгоритмы и добавляет внешние отказы.

23.4 Владение открытым потоком

У цепочки обёрток несколько Java-объектов и один исходный файл. Закрытие наружного BufferedReader закрывает вложенный читатель, который закрывает байтовый источник. В показанном блоке эта цепочка целиком принадлежит операции чтения. Выход из try с ресурсами завершает её и при нормальном ходе, и при исключении. Модель владения разобрана в Владение переданным ресурсом.

Метод countBytes получает заимствованный поток. Вызывающий код определяет, когда закрыть ресурс. Время жизни задаётся договором, а передача ссылки предоставляет доступ. Это особенно заметно у System.in, System.out и System.err: они нужны нескольким частям приложения. Закрытие обёртки над таким потоком затрагивает дальнейшую работу остальных частей.

Для выходной цепочки закрытие может включать запись остатка буфера. Поэтому ошибка возможна после последнего успешного write. Передача всех данных обёртке и успешное завершение вместе с закрытием ресурса — разные состояния. При публикации отчёта учитывается второе.

23.5 Синхронный вызов и ожидание

Рассмотрим int value = input.read(). Следующая инструкция получит управление, когда вызов вернёт результат или выбросит исключение. Такое взаимодействие будем называть синхронным: результат относится к самому выполнению вызова. Если данных пока нет, поток выполнения может ждать внутри операции. Это блокирование вызывающего потока.

Байт из массива или заполненного буфера доступен сразу, но способ получения результата остаётся синхронным. Медленный внешний источник может задержать тот же алгоритм надолго. Свойство API и длительность конкретного вызова описывают разные стороны его поведения.

Для команды, читающей один файл перед расчётом, такой порядок удобен: локальные переменные и стек вызовов хранят состояние незаконченной работы. Пока вход не прочитан, рассчитывать ещё нечего. Сложность меняется, если сервер обслуживает много соединений, большую часть времени ожидающих очередную порцию. Один платформенный поток на соединение сохраняет простой код, но связывает ожидание с ресурсами множества потоков операционной системы.

Можно назначить меньше потоков и обходить соединения. Однако обычное блокирующее чтение первого молчащего соединения задержит обслуживание остальных. Требуется узнавать о возможности продвижения работы без ожидания внутри каждого отдельного чтения. Увеличение буфера этому не помогает: готовых данных у выбранного соединения всё ещё нет.

23.6 Канал и явный буфер NIO

В JDK 1.4 появилась NIO. Спецификация JSR 51 связывала развитие ввода-вывода с крупными приложениями: управлением блоками данных, кодировками и обслуживанием большого числа соединений. Эти задачи получили несколько согласованных средств. Новая библиотека расширила набор моделей; java.io сохранила своё место [31], [89].

Канал представляет связь с источником или приёмником, а буфер — область данных и состояние её обработки. В channel.read(buffer) канал записывает прочитанную порцию в буфер, который затем обрабатывает программа. Массив в прежнем read(byte[]) уже позволял получать блоки. Новая модель делает положение и границы используемой части явными, общими для разных операций и каналов.

ByteBuffer содержит три основных числа:

Состояние Смысл
capacity Вместимость выделенной области
position Индекс следующего относительного чтения или записи
limit Первая позиция за доступной в текущем режиме областью

Всегда выполняется 0 ≤ position ≤ limit ≤ capacity. Эти числа описывают использование памяти; сами байты находятся внутри области. Буфер вместимостью 8 после записи трёх байтов имеет position=3, limit=8. Для чтения записанного вызывают flip(): предел становится 3, позиция — 0. Байты при этом никуда не перемещаются [37].

23.6.1 Сохранение незавершённой порции

В буфер записаны 10, 20, 30, а обработчик использовал только первые два значения. Остаток 30 нужен вместе со следующей порцией. compact() переносит остаток в начало и оставляет позицию после него:

действие                    содержимое начала     position   limit
put(10), put(20), put(30)    10 20 30                   3        8
flip()                      10 20 30                   0        3
два get()                   10 20 30                   2        3
compact()                   30                         1        8
put(40), put(50), flip()     30 40 50                   0        3

Так сохраняется начало записи, пришедшее в конце предыдущей порции. Если всё содержимое уже обработано, clear() подготавливает всю ёмкость для заполнения: position=0, limit=capacity. Старые значения ячеек остаются до перезаписи. Полный опыт с этими переходами находится в BufferStatesDemo [38].

Явное состояние даёт управление остатками, но добавляет обязанность следить за режимом буфера. Два потребителя одного буфера могут мешать друг другу изменением позиции. Выгода модели особенно заметна там, где границы порций и переходы между стадиями обработки входят в задачу.

23.6.2 Синхронный файловый канал

У файла полезны операции по смещению: например, чтение записи с известной байтовой позиции. Произвольный доступ был и в исходной библиотеке: RandomAccessFile существует с Java 1.0. FileChannel включил работу с файлом в общую модель каналов и буферов и предоставил дополнительные операции над файлом [41], [45].

У FileChannel.read(buffer) есть текущая позиция файла. Она сдвигается на фактически прочитанное число байтов. Вариант read(buffer, offset) читает по указанному смещению и сохраняет текущую позицию канала. Позиция файла и позиция ByteBuffer описывают разные места: во внешних данных и в памяти для очередной порции.

Оба вызова возвращают число прочитанных байтов непосредственно. Это синхронные операции, способные ожидать файлового ввода. FileChannel не относится к SelectableChannel; переключения обычного файлового канала в неблокирующий режим селектора здесь нет. Частичная порция допустима: обрабатывают фактически прочитанную область.

Прежние средства могут участвовать в той же работе: файловый поток предоставляет связанный канал через getChannel(). У этой пары общее файловое состояние и связанные сроки закрытия. Это позволяет использовать нужную операцию канала, сохраняя остальную потоковую обработку.

23.7 Неблокирующий режим и готовность

Для сетевого соединения возможно другое поведение: попытка чтения возвращает управление, даже если данных сейчас нет. В неблокирующем режиме SocketChannel.read(buffer) может вернуть 0 при наличии места в буфере. Это отсутствие полученной порции в данном вызове. Значение -1 обозначает окончание входа. Результат попытки по-прежнему возвращается из самого метода.

Непрерывный повтор таких попыток тратил бы процессор на опрос. Селектор позволяет ожидать готовности нескольких подходящих каналов в одном месте. Каналы регистрируются для интересующих операций в неблокирующем режиме. Когда селектор сообщает о готовности, программа выполняет попытку чтения или записи [46], [47].

несколько соединений → ожидание готовности → чтение доступной порции
                                            ↓
                            сохранение состояния каждого соединения
                                            ↓
                                  новое ожидание готовности

Сообщение о готовности ещё не является готовым предметным сообщением. В порции могут находиться половина строки или несколько строк сразу. Приложение хранит остатки и состояние разбора для каждого соединения. При частичной записи сохраняется ещё не отправленная часть. Селектор сокращает число независимо ожидающих потоков, но управление незавершённой работой становится явным.

Для чтения одного небольшого журнала такая система состояний обычно не упрощает программу: записи и так обрабатываются последовательно. При многочисленных независимых соединениях возможность ждать их совместно может оправдать дополнительное состояние обработчиков. Свойства выбранного канала и характер нагрузки определяют пользу этой организации.

23.8 Файловая модель NIO.2

Первая NIO улучшила работу с каналами и ожиданием, но оставила другую группу трудностей. Приложению нужно различать причины файлового отказа, работать с атрибутами и символическими ссылками, представлять разные файловые системы. java.io.File представляет имя файла или каталога и предоставляет операции над ним. У этой модели возможности диагностики и работы с файловой системой были ограничены.

Например, File.delete() возвращает false, когда удаление не произошло. По одному этому результату нельзя объяснить, отсутствовал ли файл или операция встретила другую помеху. Files.delete(path) сообщает об отказе исключением; реализация может уточнить причину, например через NoSuchFileException. Если клиенту важен только факт успешного удаления, булева форма достаточна. Если дальнейшее действие зависит от причины, сведения о ней становятся частью нужного договора [40], [116].

JSR 203 развила файловую модель и асинхронные операции; результат вошёл в Java 7 под названием NIO.2. Path описывает путь, Files предоставляет операции, а провайдер связывает эту модель с конкретной файловой системой. Развитие файлового API решает собственную задачу, отличную от организации ожидания [30], [44].

Новые способы открытия часто возвращают прежние абстракции. Например, Files.newBufferedReader даёт BufferedReader. Дальнейший цикл обрабатывает строки так же, как у самостоятельно собранной цепочки обёрток. Способ открыть файл и модель чтения его содержимого могут быть выбраны независимо.

23.8.1 Путь и файловая операция

Path.of("data", "input.txt") создаёт описание пути. Файл в этот момент ещё не открыт и может отсутствовать. Относительный путь обычной файловой системы разрешается от рабочего каталога процесса. Запуск из IDE и запуск из командной оболочки могут обратиться к разным файлам при одинаковой строке аргумента.

normalize() упрощает запись пути лексически, например устраняет избыточные компоненты. Для установления существующего файла требуются операции файловой системы: toRealPath() или сравнение через Files.isSameFile. Символические ссылки делают различие между записью пути и идентичностью файла существенным [120].

Предварительное Files.exists(path) не резервирует файл. Между проверкой и открытием другой процесс может его удалить или заменить. Результат попытки устанавливает само открытие. Более точные исключения NIO.2 помогают различать причины, когда провайдер может их определить; общий IOException остаётся частью договора.

23.9 Асинхронная операция и её завершение

При работе по готовности приложение сначала узнаёт, что стоит попробовать операцию. Асинхронный ввод-вывод меняет событие взаимодействия: приложение заказывает операцию, а её результат получает отдельно. Между этими событиями вызывающий поток может заниматься другой работой. Завершение может наступить очень быстро, в том числе до следующей инструкции вызывающего кода.

У AsynchronousFileChannel задаётся явная файловая позиция каждой операции. Один из вариантов read возвращает Future<Integer> — объект для получения будущего результата. Для уже открытого channel можно заказать две независимые порции:

var first = java.nio.ByteBuffer.allocate(4);
var second = java.nio.ByteBuffer.allocate(4);
var a = channel.read(first, 0);
var b = channel.read(second, 4);

int firstCount = a.get();
int secondCount = b.get();

Окружающий метод обрабатывает исключения ожидания. Оба чтения заказаны до получения результатов; у них разные буферы. Вызов get() ждёт, если результат ещё не готов, и сообщает об отказе операции через ExecutionException. Если поставить get() сразу после каждого заказа, ожидание снова окажется внутри последовательной работы вызывающего потока. Ожидание можно совместить с независимыми действиями между заказом и получением результата либо с выполнением нескольких одновременно заказанных операций [42].

Второй вариант принимает CompletionHandler. Система вызывает completed с результатом или failed с причиной отказа. Продолжение обработки располагается в обработчике. Это удобно, когда завершение должно само запустить следующий шаг; цена — явная передача состояния между шагами. Оба варианта показаны в AsyncReadDemo [36].

23.9.1 Порядок и владение буфером

Возврат из асинхронного read ещё не означает, что буфер готов для чтения программой. Пока операция не завершилась, она может изменять его содержимое и позицию. Программа оставляет этот буфер операции и обращается к нему после успешного ожидания результата либо в обработчике завершения. Два одновременно незавершённых чтения в один буфер нарушили бы такой порядок доступа.

Порядок завершения независимых операций может отличаться от порядка их запуска. Если отчёт должен следовать порядку файловых позиций, это обеспечивает приложение. В демонстрации сначала печатается результат позиции 0, затем позиции 4, поскольку так расположены вызовы get. Реальное завершение второго чтения могло произойти раньше.

Время жизни канала тоже должно охватывать операции. Возврат Future из try с ресурсами с немедленным закрытием канала завершает владение раньше полезной работы: незавершённое чтение получит отказ. Лексический блок подходит, когда в нём действительно ожидают окончание всех использований ресурса. Передача незавершённой операции требует передачи ответственности за этот срок (Дополнительно: область владения и асинхронное завершение).

Конкретная реализация асинхронного канала может использовать рабочие потоки. Договор API определяет заказ и завершение операции; отдельный системный асинхронный механизм и выигрыш скорости для данного файла в него не входят. В NIO.2 остаются и обычные синхронные операции. Название версии библиотеки, модель управления и механизм ОС относятся к разным уровням описания.

23.9.2 Виртуальные потоки и цена ожидания

Виртуальные потоки дают ещё один вариант для многочисленных ожиданий. Код сохраняет последовательные блокирующие вызовы, а JVM во многих случаях ожидания освобождает выполняющий его платформенный поток для другой работы. Это позволяет по-новому оценить решение «отдельный поток на независимую задачу».

Вызов reader.readLine() по-прежнему возвращает строку вызывающему коду после выполнения чтения. Смена вида потока сохраняет синхронный API. Выигрыш связан с организацией ожидания множества задач; одиночный диск или вычисление быстрее от этого не становятся. Возможность освободить платформенный поток зависит от операции и реализации [35].

Незавершённую работу можно хранить в стеке синхронного вызова, в состояниях обработчика готовности или в продолжении после асинхронного завершения. Условия задачи определяют, какая цена — ресурсы ожидающих потоков или явное управление состояниями — окажется существенной.

23.10 Чтение по строкам и память

Консольная обработка одного текстового файла часто выигрывает от последовательной модели. Если весь вход невелик и нужен алгоритму целиком, Files.readString или readAllLines дают самостоятельное значение и сами закрывают файл. Простота оплачивается памятью под весь результат. Построчный цикл позволяет обрабатывать записи постепенно:

try (var reader = java.nio.file.Files.newBufferedReader(
        path, java.nio.charset.StandardCharsets.UTF_8)) {
    String line;
    long number = 0;
    while ((line = reader.readLine()) != null) {
        number++;
        if (!line.isBlank()) {
            process(number, line);
        }
    }
}

Здесь path — Path, process обрабатывает строку с физическим номером, а файловый отказ передаётся вызывающему методу. null означает конец входа; пустая строка имеет значение "". Последняя строка возвращается и без завершающего разделителя. Пустые строки участвуют в нумерации независимо от решения пропустить их предметную обработку.

Расход памяти состоит из буфера, текущей строки и данных, сохраняемых приложением. Если process складывает все строки в список, постепенное чтение не устраняет память под него. Если накапливаются суммы по товарам, память зависит от числа разных товаров и диагностик. Одна очень длинная строка тоже занимает память целиком. Ограничение длины входной записи требует собственного договора.

Files.lines предоставляет ленивый Stream<String>. Чтение происходит при обходе; созданный файловый поток закрывают после использования, обычно в try с ресурсами. Превращение источника в Stream сохраняет синхронное чтение. Связь ленивого обхода и владения рассмотрена в Уже объявленный ресурс и результат за границей блока.

23.11 Декодирование и проверка предметных данных

У текста несколько последовательных границ правильности. Корректный UTF-8 может содержать строку ручка;ошибка, в которой второе поле не обозначает число. Преобразование -3 в long успешно, но отрицательное количество недопустимо для поставки. Корректная отдельная поставка может переполнить уже накопленную сумму.

байты → символы → поля → значения → допустимое изменение состояния

У каждого перехода собственная причина отказа. При ошибке декодирования текст не получен по договорённой кодировке. Предметный парсер уже работает с готовой строкой. Его можно проверять на строках в памяти, а кодировку — на небольшом файле с известными байтами.

Политика продолжения зависит от приложения. Журнал поставок сохраняет диагностику ошибочной строки и читает следующую. Другой импорт может отклонять весь файл при первой ошибке данных. Обе политики осмысленны, если согласованы с назначением результата. У файлового отказа посреди чтения и неверного количества в законченной строке разные последствия: в первом случае полный вход может остаться неизвестным.

23.12 Формат предметной строки

Разделитель ; подходит для небольшого учебного формата, если договор запрещает этот знак внутри поля и не предусматривает кавычек. Тогда split(";", -1) сохраняет последнее пустое поле: строка ручка; содержит два поля, из которых второе пусто. Без отрицательного предела конечные пустые части могут исчезнуть, и диагностика потеряет часть структуры исходной записи.

Удаление пробелов через strip тоже является решением о формате. Если края названия незначащие, нормализация до объединения позволяет ручка и ручка обозначать один товар. В формате со значимыми пробелами тот же шаг изменил бы данные.

Появление кавычек, вложенных разделителей и переносов внутри поля меняет модель разбора. Простое разделение физической строки уже не выражает такую грамматику. Библиотека формата уменьшает число правил, которые приходится поддерживать вручную. Учебный договор поставок сохраняет ограниченную форму (Наблюдаемое поведение приложения).

23.13 Запись, усечение и частичный результат

При записи важно, что происходит с прежними данными. Files.writeString без параметров режима создаёт отсутствующий файл или усекает существующий перед записью. Режим APPEND сохраняет прежнее содержимое и добавляет в конец; CREATE_NEW позволяет потребовать создания нового файла. Выбор следует из назначения результата [116].

Добавление текста не устанавливает границы записей. Если прежний файл заканчивался без перевода строки, добавленная запись может склеиться с последней. При отказе записи часть изменений уже могла произойти. Закрытие ресурса завершает использование, но не откатывает эти байты.

Для журнала постепенное добавление может быть желаемым поведением: каждая запись становится частью истории. Для отчёта, целиком заменяющего прежнюю версию, видимость промежуточного состояния неудобна. Во втором случае нужна отдельная граница публикации.

23.14 Публикация файлового результата

Пусть существующий report.txt содержит прошлый отчёт. Если открыть его с усечением до окончания нового расчёта, прежняя версия исчезнет раньше, чем станет известен успех новой. Подготовка во временном файле позволяет отложить изменение целевого имени. Сначала вычисляют данные, записывают временный файл в подходящем каталоге и успешно закрывают его; затем предпринимают перемещение к целевому пути.

сбой вычисления       → прежний отчёт ещё не затронут
сбой записи/закрытия  → перемещение не начато, временный файл может остаться
успешное закрытие     → подготовленный файл можно пытаться опубликовать
успешное перемещение  → результат доступен по целевому имени

ATOMIC_MOVE запрашивает неделимость перемещения. Поддержка зависит от файловой системы; невозможность выполнения сообщает AtomicMoveNotSupportedException. При атомарном перемещении остальные параметры игнорируются, а замена уже существующей цели зависит от реализации. Добавление REPLACE_EXISTING к запросу поэтому не создаёт переносимой гарантии такой замены.

Без атомарного перемещения состояние после неудачного move не определено универсально. Приложение учитывает договор выбранной операции и среды. Отказ удаления временного файла тоже может иметь значение для диагностики. Атомарная видимость по имени и сохранность при отключении питания требуют разных свойств: последняя определяется отдельным договором с хранилищем [116].

23.15 Строки файла и сохранение исходного представления

readLine убирает разделители строк. После разбора нельзя восстановить, был ли разделитель LF или CRLF и завершалась ли последняя строка разделителем. Для подсчёта поставок это допустимая потеря сведений: важны поля записей. При точном копировании эти сведения принадлежат результату, поэтому побайтовая передача соответствует задаче.

Символьное копирование с явно выбранной кодировкой сохраняет другой уровень представления. Оно уместно, например, при перекодировании текста. Повторная печать через println добавляет разделитель текущей среды; иногда нужна именно такая нормализация, которая входит в договор преобразования. Одинаковый вид в редакторе ещё не устанавливает равенство байтов.

23.16 Границы файловой операции

Выбор API начинается с того, что требуется сохранить и когда результат считается готовым. Последовательное чтение строк соответствует записям журнала. Явные файловые позиции нужны для доступа к отдельным блокам. Готовность помогает распределить внимание между ожидающими соединениями. Асинхронное завершение отделяет заказ операции от обработки результата, добавляя требования к владению и порядку.

Для небольшого приложения удобно сначала получить и проверить вход, затем построить самостоятельный результат и только после этого печатать. Ошибка чтения тогда не оставляет часть полезного отчёта в стандартном выводе. С ростом входа цена хранения может привести к постепенной публикации, а вместе с ней — к определению смысла частичного результата. Такое решение меняет договор приложения.
