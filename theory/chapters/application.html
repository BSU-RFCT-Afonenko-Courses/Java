24.1 Наблюдаемое поведение приложения

Журнал поставок содержит несколько записей об одном товаре. Для отчёта нужна одна сумма на товар в порядке его первого принятого появления. Прочитать файл можно разными средствами; устройство программы зависит также от того, что делать с неверной записью и когда печатать результат. Эти решения связывают ввод-вывод с моделью данных и обработкой ошибок.

Команда deliveries.Main принимает один аргумент — путь к UTF-8-файлу. Относительный путь разрешается от рабочего каталога процесса. Значимая физическая строка содержит ровно два поля: товар;количество. К краям обоих полей применяется strip. Название непустое, не содержит ;, CR или LF; регистр значим. Количество разбирается через Long.parseLong и должно быть положительным. Кавычки и экранирование форматом не предусмотрены. Строки, для которых isBlank() возвращает true, пропускаются, сохраняя место в физической нумерации.

Повтор названия добавляет количество к прежней сумме. Результат содержит одну строку товар;сумма на каждый принятый товар, без заголовка. Сумма должна помещаться в положительный long. Строка с неверным форматом, количеством или переполнением суммы отклоняется целиком; прежнее состояние сохраняется. Диагностика указывает физический номер и причину. После такой ошибки программа читает следующую строку.

Для входа

тетрадь;4
ручка;2
тетрадь;3
ручка;ошибка
альбом;1

после полного чтения stdout получает:

тетрадь;7
ручка;2
альбом;1

В stderr поступает сообщение о строке 4. Код завершения равен 3: отчёт содержит принятые поставки, часть входа отвергнута. Код 0 означает обработку без ошибок, включая пустой файл; 2 — неверную команду или синтаксис пути; 4 — отказ чтения, декодирования, закрытия или вывода. Если вход не удалось полностью прочитать и закрыть, отчёт не публикуется.

24.2 Последовательность обработки

Простой вариант мог бы читать строку и немедленно печатать обновлённую сумму. Но тогда две поставки тетрадей дали бы две строки отчёта, а поздний отказ чтения оставил бы уже напечатанную часть. Требование окончательной суммы и выбранная политика отказа приводят к накоплению данных до печати:

открытие → чтение и накопление → закрытие → готовый результат → вывод

Загрузчик держит суммы и диагностику внутри операции. Клиент получает их только после успешного закрытия. Такой порядок оплачивается памятью под накопленные сведения. Для небольшого журнала цена приемлема; отложенный вывод позволяет отличать полный результат чтения от незаконченной обработки.

Для самого чтения подходят BufferedReader и обычный синхронный цикл. Следующая запись нужна после обработки предыдущей, а файлом владеет один вызов. Files.newBufferedReader(path, UTF_8) соединяет файловую модель NIO.2 с символьным потоком java.io. Селектор не даёт преимуществ для этого обычного файлового источника. Заказ независимых асинхронных блоков потребовал бы дополнительно восстановить границы UTF-8, строк и исходный порядок, от которого зависит отчёт (Глава 23).

Чтение всех строк через readAllLines тоже соответствовало бы договору при небольшом входе. Оно сохраняет в памяти ещё и весь исходный текст. Построчный цикл позволяет сразу использовать каждую запись, оставляя только суммы и проблемы. Эта экономия не делает расход памяти постоянным: он растёт с числом разных товаров и ошибочных строк.

24.3 Ограничения предметной записи

Отдельная поставка — значение Delivery(String item, long quantity). Её конструктор удаляет пробелы по краям названия и проверяет ограничения при любом способе создания. Поэтому объект из файла и объект, созданный напрямую при проверке, подчиняются одному договору.

public record Delivery(String item, long quantity) {
    public Delivery {
        java.util.Objects.requireNonNull(item);
        item = item.strip();
        if (item.isEmpty() || item.indexOf(';') >= 0
                || item.indexOf('\r') >= 0 || item.indexOf('\n') >= 0) {
            throw new IllegalArgumentException("неверное название товара");
        }
        if (quantity <= 0) {
            throw new IllegalArgumentException("количество должно быть положительным");
        }
    }
}

Присваивание параметру компактного конструктора определяет сохранённое название. Строка неизменяема, количество имеет примитивный тип. Готовая поставка сохраняет состояние при передаче между частями программы. Равенство записи включает оба компонента; ключом суммирования служит только item. Поставки тетрадь;4 и тетрадь;3 различны как значения и относятся к одному товару (Глава 14).

Проверка названия в конструкторе добавляет обязанность каждому созданию значения, зато последующая печать может соединять поля через ; без повторного поиска разделителей внутри названия. Ограничение на внешний формат становится свойством допустимой предметной записи.

24.4 Диагностика строки

Разбор строки отвечает за структуру внешнего представления. Он отделён от открытия файла, поэтому вход ручка; можно проверить непосредственно в памяти. Существенная часть DeliveryFiles.parseLine:

String[] fields = line.split(";", -1);
if (fields.length != 2) {
    throw new IllegalArgumentException("нужны два поля");
}
final long quantity;
try {
    quantity = Long.parseLong(fields[1].strip());
} catch (NumberFormatException ex) {
    throw new IllegalArgumentException(
        "количество: нужно целое в диапазоне long", ex);
}
return new Delivery(fields[0], quantity);

Отрицательный предел split сохраняет завершающее пустое поле. ручка; имеет два поля, но пустое количество не разбирается. ручка;0 проходит преобразование в число и отвергается конструктором. Парсер переводит причину числового отказа в формулировку своего уровня, сохраняя исходное исключение как cause.

Внешний цикл превращает ошибку законченной строки в значение LineProblem(long number, String reason). Его номер положителен, а ссылка на текст причины не может быть нулевой. Список таких значений позволяет продолжить чтение и сообщить обо всех отвергнутых записях. В пользовательском результате сохраняется текст причины; объект исключения в LineProblem не входит. Если приложению нужна трассировка для разработчика, её хранение становится отдельной задачей диагностики.

Отказ получения следующей строки имеет другой смысл. Ошибочные байты UTF-8 или ошибка чтения не дают завершить получение входа; IOException прерывает вызов загрузчика. Поэтому перехват ошибок данных расположен внутри цикла после readLine.

24.5 Чтение и накопление поставок

DeliveryFiles.read(Path path) создаёт LinkedHashMap<String, Long> для сумм и ArrayList<LineProblem> для диагностики. Внутри try с ресурсами работает цикл; reader, totals и problems принадлежат этому вызову:

long number = 0;
String line;
while ((line = reader.readLine()) != null) {
    number++;
    if (line.isBlank()) continue;
    try {
        Delivery delivery = parseLine(line);
        long previous = totals.getOrDefault(delivery.item(), 0L);
        long next = Math.addExact(previous, delivery.quantity());
        totals.put(delivery.item(), next);
    } catch (IllegalArgumentException ex) {
        problems.add(new LineProblem(number, ex.getMessage()));
    } catch (ArithmeticException ex) {
        problems.add(new LineProblem(number,
            "сумма количества выходит за диапазон long"));
    }
}

Физический номер увеличивается до проверки isBlank. Если вторая строка пуста, следующая запись всё равно имеет номер 3. Карта хранит одну текущую сумму на товар; getOrDefault даёт ноль для ещё не встреченного названия. Обновление существующего ключа LinkedHashMap в обычном режиме сохраняет его место, поэтому порядок первого появления получается вместе с накоплением [34].

Для исходного журнала состояние развивается так:

После строки Суммы в порядке обхода Диагностика
1 тетрадь=4 Пусто
2 тетрадь=4, ручка=2 Пусто
3 тетрадь=7, ручка=2 Пусто
4 тетрадь=7, ручка=2 Ошибка строки 4
5 тетрадь=7, ручка=2, альбом=1 Ошибка строки 4

24.6 Проверка значения и проверка накопления

Конструктор знает только отдельную поставку. Возможность прибавить её количество к прежней сумме определяется в момент обновления карты. Math.addExact вычисляет сумму либо выбрасывает ArithmeticException при выходе за диапазон long.

Порядок двух строк кода сохраняет состояние при отказе: сначала вычисляется next, затем выполняется put. Пусть прежняя сумма равна Long.MAX_VALUE - 1. Поставка с количеством 2 отвергается, оставляя сумму прежней; следующая поставка с количеством 1 ещё допустима. После преждевременной записи переполненного значения продолжение работало бы с повреждённым состоянием.

Такое свойство относится к обновлению конкретного товара. Успешно принятые предыдущие строки остаются в накопителе, потому что договор разрешает частичное принятие входа. Иное правило — отвергать весь файл из-за одной неверной строки — потребовало бы другой границы результата.

24.7 Результат чтения

После цикла ресурс закрывается. Только затем read возвращает new ScanResult(totals, problems). Если чтение или закрытие завершились исключением IOException, клиент результата не получает. Исключение не очищает накопители автоматически: их недоступность клиенту обеспечивают локальное владение и положение возврата после try с ресурсами.

Уже готовому результату полезно существовать независимо от накопителей. ScanResult копирует структуру коллекций и ограничивает изменение:

public record ScanResult(java.util.Map<String, Long> totals,
                         java.util.List<LineProblem> problems) {
    public ScanResult {
        totals = java.util.Collections.unmodifiableMap(
            new java.util.LinkedHashMap<>(totals));
        problems = java.util.List.copyOf(problems);
    }
}

Одна unmodifiableMap(totals) дала бы представление исходной карты: изменения накопителя были бы видны через результат [33]. Копирование сначала создаёт отдельную структуру; обёртка затем запрещает её изменение через возвращённую ссылку. Копия LinkedHashMap сохраняет наблюдаемый порядок исходной карты. Используемые ключи, числа и диагностические записи неизменяемы, поэтому здесь достаточно структурной копии (Глава 18).

Снимок стоит дополнительной памяти, но разделяет две стадии: изменение во время загрузки и чтение при формировании отчёта. Изменения локального накопителя больше не изменят уже переданный результат.

24.8 Печать готового результата

ReportPrinter.print(ScanResult result, PrintStream out, PrintStream err) получает самостоятельный результат и два заимствованных потока. Он обходит суммы в сохранённом порядке и печатает товар;сумма в out, затем выводит диагностику строк в err. Выбор принимаемых поставок уже сделан загрузчиком.

Разделение позволяет проверить форматирование с заранее созданным результатом и потоками в памяти. Настоящий файл для этого не требуется. Одновременно получаются две наблюдаемые последовательности: отчёт и диагностика. Их объединённое отображение терминалом не устанавливает общего порядка между потоками.

Обычный PrintStream сохраняет признак ошибки вывода. После печати выполняются две отдельные проверки:

boolean outputFailed = out.checkError();
boolean diagnosticFailed = err.checkError();
if (outputFailed || diagnosticFailed) return 4;
return result.problems().isEmpty() ? 0 : 3;

checkError сбрасывает буфер открытого потока и проверяет состояние ошибки [107]. Проверяются оба потока — out и err. Потоки остаются открытыми: временем их жизни управляет вызывающая сторона. У Main это общие System.out и System.err. При отказе уже переданные получателю байты остаются у него.

24.9 Политика точки входа

Точка входа связывает договор команды с этими частями. Main.run проверяет наличие одного аргумента и создаёт Path. Неверное число аргументов или InvalidPathException дают статус 2 с диагностикой. Существование файла проверит открытие. Центральная последовательность:

try {
    ScanResult result = DeliveryFiles.read(path);
    return ReportPrinter.print(result, System.out, System.err);
} catch (java.io.IOException ex) {
    return failure(4, "ошибка чтения: " + ex.getMessage());
}

failure печатает сообщение в stderr и проверяет его состояние; ошибка самой диагностики также даёт статус 4. В main ненулевой результат run передаётся System.exit.

Ошибки отдельных строк уже находятся внутри ScanResult, поэтому их не нужно повторно перехватывать в Main. При IOException печать отчёта ещё не началась. Эта граница позволяет загрузчику описывать файловый отказ, а точке входа — выбирать наблюдаемую реакцию команды.

Код завершения предназначен оболочке, сообщение — человеку. Статус 3 разрешает отчёт по принятым строкам именно по договору этой команды. Получатель, которому нужен полностью корректный журнал, проверяет статус перед использованием отчёта.

24.10 Успех чтения и успех запуска

Завершённое чтение может вернуть суммы вместе с ошибками строк. Успех всей команды дополнительно зависит от отсутствия таких ошибок и от успешной печати.

Исход Результат чтения Stdout Статус
Пустой или пробельный файл Две пустые коллекции Пуст 0
Все строки приняты Суммы без проблем Полный отчёт 0
Отдельные строки отвергнуты Суммы и проблемы Отчёт по принятым строкам 3
Открытие, чтение, UTF-8 или закрытие отказали Не возвращён Пуст 4
Вывод отказал Уже получен Возможно, частичный 4

Таблица предполагает успешную доставку диагностики, кроме последней строки. Если все значимые записи неверны, статус 3 сопровождается пустым stdout и сообщениями в stderr. Поэтому пустой stdout ещё не отличает успешный пустой вход от отказа данных.

Файловый отчёт допускает иной способ публикации: подготовить временный файл, успешно закрыть и попытаться переместить к целевому имени. У консольного получателя уже переданные байты отозвать нельзя. Выбор места вывода меняет доступные гарантии (Публикация файлового результата).

24.11 Сборка и проверка приложения

Полные шесть исходников и входные файлы находятся в Сборка журнала поставок. Они разделяют значение поставки, диагностику, результат, загрузку, печать и команду. Эта организация позволяет изменять форматирование без изменения чтения и проверять парсер без файловой системы.

Из корня проекта с src/main/java/deliveries при JDK 25:

javac --release 25 -encoding UTF-8 -d out src/main/java/deliveries/*.java
jar --create --file deliveries.jar --main-class deliveries.Main -C out deliveries
java -jar deliveries.jar input.txt

Компиляция сохраняет классы в out. Архив JAR объединяет эти классы и указывает точку входа deliveries.Main; при запуске путь input.txt по-прежнему разрешается от рабочего каталога процесса. Упаковка программы не меняет смысл её аргументов. В POSIX-оболочке статус последней команды доступен как $?, в PowerShell — $LASTEXITCODE.

Исходный пример различает нормальное накопление и продолжение после ошибки. Замена ручка;ошибка на ручка;5 даёт сумму ручек 7, пустую диагностику и статус 0. Пара ручка;2, ручка ;3 проверяет нормализацию до объединения, а Ручка;1 — значимость регистра. Пустая строка между ошибками проверяет физические номера.

Отдельные входы с нулём, отрицательным количеством, числом вне long и переполнением суммы различают уровни проверки. Отсутствующий файл и испорченный UTF-8 проверяют границу получения результата. Изменение исходных коллекций после создания ScanResult проверяет самостоятельность снимка. Такие опыты связывают отказы с конкретной обязанностью части программы.

Проект gradeapp в Глава 26 использует Maven Wrapper и собственный договор обработки каталога участников. Его требования задаются своим условием; политика продолжения журнала поставок не переносится на него автоматически.

24.12 Изменение требований приложения

Алфавитный отчёт потребовал бы нового порядка представления готовых сумм. Разбор количества и владение читателем могли бы остаться прежними. Отчёт об отдельных поставках потребовал бы другой накопленной структуры: карта сумм уже потеряла сведения о каждой исходной записи.

Правило «весь файл допустим либо отчёта нет» затронуло бы другую границу. Для входа ручка;2, ручка;ошибка, ручка;3 оно дало бы пустой stdout. Принятая политика продолжения даёт ручка;5 и диагностику строки 2. Одна модель Delivery и те же правила арифметики допускают обе политики; выбор выражается в обработке отказа и составе возвращаемого результата.

Если память под диагностику становится слишком большой, можно передавать её постепенно. Тогда поздний файловый отказ оставит уже опубликованные сообщения. Если вход очень велик, суммы можно хранить во внешней системе, меняя цену доступа и условия сохранения состояния. Переход к Files.lines при прежних накопителях этих потребностей не устранит: ленивый способ получения строк сохраняет выбранные данные результата. Изменение масштаба потребует пересмотреть именно хранение и договор публикации.
