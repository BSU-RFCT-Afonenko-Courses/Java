19.1 Условие отбора как параметр

В списке три участника: s1/Ada/90, s2/Lin/70, s3/Ann/80. Запись grade.Student хранит код, имя и балл; её методы id(), name() и score() читают эти компоненты. Конструктор проверяет допустимость компонентов (Компоненты и стандартные члены записи). Все три записи проходят эти проверки.

В первом случае нужны те, кто набрал не меньше 80 баллов. Во втором — те, чьё имя начинается с A. В обоих случаях есть одинаковый обход списка, проверка условия и добавление подходящего элемента в результат. Если копировать весь метод ради каждого условия, исправлять обход придётся во многих местах. Переменная часть — проверка одного участника.

@FunctionalInterface
interface StudentTest {
    boolean test(Student student);
}

static java.util.List<Student> select(
        java.util.List<Student> source, StudentTest condition) {
    var result = new java.util.ArrayList<Student>();
    for (Student student : source) {
        if (condition.test(student)) result.add(student);
    }
    return java.util.List.copyOf(result);
}

StudentTest — функциональный интерфейс: у него одна абстрактная операция, которую предстоит реализовать. Аннотация @FunctionalInterface поручает компилятору проверить это условие. Если добавить вторую независимую абстрактную операцию, объявление с аннотацией будет отвергнуто. Само свойство интерфейса сохраняется и без аннотации.

Метод test принимает Student и возвращает boolean. Алгоритм вызывает его для каждого участника и добавляет участника при ответе true. Конкретное условие задаёт реализация test [40], [55], [120]. Значения элементов не копируются: результат содержит ссылки на подходящих участников, но структуру результата изменить нельзя.

Объект условия создаётся анонимной реализацией: после new StudentTest() тело { ... } определяет обычный метод test. Он получает участника только в момент вызова из select:

var students = java.util.List.of(
    new Student("s1", "Ada", 90),
    new Student("s2", "Lin", 70),
    new Student("s3", "Ann", 80));
StudentTest condition = new StudentTest() {
    @Override public boolean test(Student student) {
        return student.score() >= 80;
    }
};
var selected = select(students, condition);
System.out.println(selected.size());

Перед чтением трассы определите, сколько раз цикл вызовет test и какие ссылки попадут в result.

Аргумент test Выражение в методе Ответ Состав result после итерации
s1/Ada/90 90 >= 80 true [s1]
s2/Lin/70 70 >= 80 false [s1]
s3/Ann/80 80 >= 80 true [s1, s3]

Печатается 2. На входе три записи, на выходе две в прежнем порядке. Другая реализация test, проверяющая student.name().startsWith("A"), сохраняет алгоритм и меняет лишь критерий. Переданный объект называется callback: алгоритм вызывает его метод в нужном месте обхода.

19.2 Создание действия и вызов лямбды

У StudentTest одна абстрактная операция. Поэтому реализацию callback можно записать лямбдой s -> s.score() >= 80. Запись s -> s.score() >= 80 сама не проверяет всех участников. Она задаёт реализацию операции интерфейса. Вызов condition.test(student) выполняет тело для конкретного аргумента. Это различие позволяет сохранять действие для последующего вызова:

StudentTest passed = s -> s.score() >= 80;
System.out.println(passed.test(students.get(0))); // true
System.out.println(passed.test(students.get(1))); // false

Переменная хранит ссылку на объект, через который доступно действие. При вычислении лямбда-выражения допустимы как создание нового объекта, так и использование существующего. JLS не требует компиляции лямбды в определённый анонимный класс. Лямбда и анонимный класс решают близкую задачу реализации интерфейса, но отличаются областью this и другими правилами языка. У лямбды this сохраняет значение окружающего контекста; у анонимного класса обозначает сам анонимный объект.

В Python функция является объектом с собственным типом и может передаваться без предварительно объявленного интерфейса. В Java нужная форма вызова проверяется через целевой функциональный интерфейс. В C++ близкую задачу решают объекты с operator() и лямбды; в Java вызывающий код использует именованный метод интерфейса.

-> не запускает отдельный поток и не требует чистоты действия. Например, StudentTest noisy = s -> { System.out.println(s.id()); return s.score() >= 80; }; печатает только при noisy.test(student). Тело действия определяет эффект; вызов метода интерфейса определяет момент его выполнения.

19.3 Целевой тип и формы записи

Лямбда требует контекста, который определяет целевой тип. Его дают присваивание, аргумент метода, возвращаемое значение или явное приведение. Из StudentTest компилятор узнаёт тип параметра s. Поэтому допустимы обе формы:

StudentTest first = (Student s) -> s.score() >= 80;
StudentTest second = s -> s.score() >= 80;

var condition = s -> s.score() >= 80; не компилируется: справа нет самостоятельного типа, который var смог бы вывести. Из похожего тела могут получиться разные функциональные интерфейсы, поэтому компилятор не выбирает один произвольно. Для неоднозначных перегрузок иногда требуется явно объявленная переменная нужного интерфейса или приведение.

Если в теле несколько действий, используют блок:

StudentTest valid = s -> {
    int score = s.score();
    return score >= 0 && score <= 100;
};

Фигурные скобки не означают автоматический возврат последнего выражения. В блоке для возвращаемого boolean нужен return на всех путях нормального завершения. Для действия с результатом void допустим блок без возвращаемого значения. Если параметры записываются с типами, типизация должна быть последовательной для всех параметров; нельзя один объявить явно, другой оставить без типа.

Функциональность определяется одним абстрактным действием с учётом правил наследования методов. Статические и default-методы не создают дополнительных абстрактных действий. Публичные методы, совпадающие с методами Object, не считаются вторым действием; поэтому Comparator остаётся функциональным, хотя объявляет также equals. Аннотация @FunctionalInterface включает проверку этого свойства компилятором.

19.4 Стандартные формы действий

У StudentTest задача узкая: предоставить правило нашему select. Если то же правило понадобится библиотечному отбору или составлению нескольких условий, отдельное имя интерфейса станет границей совместимости. Стандартный Predicate<T> уже представляет boolean test(T value) и предоставляет операции объединения условий. Правило, полученное как Predicate<Student>, можно передать другому API с тем же типом без переходника между двумя интерфейсами. Метод select можно объявить с Predicate<? super Student>: он передаёт условию участников. ? super Student позволяет принять также правило, которое умеет проверять любой Object.

Тип действия Метод, который вызывает клиент Передаваемые данные
Predicate<Student> boolean test(Student value) участник → ответ условия
Function<Student, String> String apply(Student value) участник → строка
Consumer<String> void accept(String value) строка → действие без возвращаемого значения
Supplier<List<Student>> List<Student> get() без аргументов → список

Каждая следующая лямбда реализует метод своей строки таблицы:

java.util.function.Predicate<Student> passed = s -> s.score() >= 80;
java.util.function.Function<Student, String> name = s -> s.name();
java.util.function.Consumer<String> print = text -> System.out.println(text);
java.util.function.Supplier<java.util.List<Student>> empty = () -> java.util.List.of();

System.out.println(name.apply(students.get(0))); // Ada
print.accept("готово");                         // готово
System.out.println(empty.get().size());         // 0

Предикат проверяет условие; функция преобразует аргумент в результат; потребитель выполняет действие без возвращаемого значения; поставщик предоставляет результат без аргумента. Consumer может печатать, изменять объект или записывать файл, хотя accept возвращает void. Supplier может каждый раз создавать новое значение или возвращать существующее: это определяется реализацией get.

UnaryOperator<T> — частный случай функции из T в T; BinaryOperator<T> принимает два T и возвращает T. Для числовых операций существуют формы без упаковки: IntPredicate, IntUnaryOperator, ToIntFunction<T>. Входные параметры и результат операции определяют подходящую форму. Таблица форм находится в Глава 18.

Форма вызова ещё не выражает весь смысл операции. Например, Comparator<T> принимает два значения и возвращает int, как ToIntBiFunction<T, T>, но его контракт дополнительно требует соблюдения законов порядка, включая транзитивность. Произвольная функция такой формы может этим законам не удовлетворять. Предметный интерфейс полезен, когда его имя и договор несут дополнительные обязательства либо требуется другая сигнатура, например проверяемый отказ. Стандартная форма сокращает число переходников между библиотеками; отдельный интерфейс делает специальный смысл явным ценой этих переходников. [54]

19.5 Ссылки на методы

Ссылка на метод обозначает уже существующее действие. Student::name при целевом Function<Student, String> означает: получить Student как аргумент и вызвать у него name(). System.out::println привязывается к конкретному объекту вывода; будущий аргумент станет аргументом println. Integer::parseInt обозначает статический метод, а ArrayList::new — конструктор подходящей формы.

java.util.function.Function<String, Integer> parse = Integer::parseInt;
java.util.function.ToIntFunction<Student> score = Student::score;
System.out.println(parse.apply("17"));     // 17
System.out.println(score.applyAsInt(students.get(0))); // 90

Круглых скобок вызова в ссылке нет. Integer.parseInt("17") выполняет преобразование сейчас, а Integer::parseInt передаёт операцию, которой аргумент дадут позже. Перегрузки разрешаются по целевому типу. Если операция требует дополнительных действий или меняет порядок аргументов, лямбда позволяет записать эти действия и нужный порядок явно.

19.6 Захват локального значения

Лямбда может обращаться к локальной переменной окружающего метода, если та final или фактически окончательная: после инициализации ей не присваивают другое значение. Переменная должна быть определённо инициализирована до создания лямбды. При ссылочном типе сохраняется значение ссылки; достижимый по ней объект может оставаться изменяемым [41], [120].

int threshold = 80;
java.util.function.Predicate<Student> passed = s -> s.score() >= threshold;
// threshold = 90; // сделало бы захват недопустимым

Условие сохраняет доступ к значению 80. Если после создания лямбды переприсвоить локальную переменную, компилятор отвергнет её использование в лямбде. При захвате final List<String> log вызов log.add(...) возможен, если список поддерживает изменение. Он меняет объект, сохраняя значение ссылки. Например, два последовательных вызова добавляют код в один список:

var log = new java.util.ArrayList<String>();
java.util.function.Consumer<Student> remember = s -> log.add(s.id());
remember.accept(students.get(0));
remember.accept(students.get(0));
System.out.println(log); // [s1, s1]

Оба вызова используют один список. Второй вызов видит результат первого; внешний код тоже может менять log. final у ссылки не сделал бы список неизменяемым. Для одновременных вызовов добавляется вопрос согласования доступа к общему состоянию.

Захваченный массив counter допускает изменение counter[0]: изменяется ячейка общего объекта. Теперь результат зависит от порядка и числа вызовов действия. Для числа подходящих элементов Stream предоставляет count; в обычном цикле тот же смысл выражает локальный счётчик. Оба варианта позволяют получить число без внешнего изменяемого объекта у callback.

19.7 Возвращаемое правило и состояние замыкания

Метод может вернуть действие, настроенное аргументом. После возврата метода значение его локального параметра остаётся доступно захватившему его действию:

static java.util.function.Predicate<Student> atLeast(int threshold) {
    return student -> student.score() >= threshold;
}
var passed = atLeast(80);
var excellent = atLeast(90);
var ann = new Student("s3", "Ann", 80);
System.out.println(passed.test(ann));    // true
System.out.println(excellent.test(ann)); // false

Здесь два разных момента вызова:

Вызов Аргумент Выполняемая работа Результат
atLeast(80) порог 80 настройка действия Predicate<Student>
passed.test(ann) участник Ann/80 сравнение 80 >= 80 true

atLeast(80) не проверяет ни одного участника: участник ещё не передан. Каждый вызов метода создаёт значение правила с выбранным порогом; позже test использует этот порог. Спецификация не требует нового экземпляра лямбды при каждом вычислении. Результаты test следуют выбранному порогу; сравнение объектов действий через == этого договора не выражает. Параметр threshold не переприсваивается и поэтому подходит для захвата.

Если вместо числа захватить ссылку на изменяемую настройку, поведение может измениться без создания нового правила:

class Settings { int threshold = 80; }
var settings = new Settings();
java.util.function.Predicate<Student> dynamic =
    student -> student.score() >= settings.threshold;
System.out.println(dynamic.test(ann)); // true
settings.threshold = 90;
System.out.println(dynamic.test(ann)); // false

Здесь захвачено значение ссылки settings, а поле читается заново при каждом test. Фактически окончательная ссылка не означает снимка всех данных достижимого объекта. Такая настройка меняет результат уже созданного правила. Для стабильного отчёта в atLeast передаётся число-порог.

У Python аналогичный метод, возвращающий lambda student: student.score >= threshold, может хранить выбранный порог в замыкании. При этом правила переназначения захваченных переменных в Python и Java различаются. Сходство относится к сохранению окружения действия; ограничение Java на локальное переназначение действует и при возврате лямбды из метода. Создание замыкания сохраняет окружение; действие выполняется при последующем вызове в текущем потоке.

19.8 Составление правил и границы интерфейса

Предикаты объединяются коротким замыканием:

java.util.function.Predicate<Student> passed = s -> s.score() >= 80;
java.util.function.Predicate<Student> named = s -> s.name().startsWith("A");
var condition = passed.and(named);
System.out.println(condition.test(students.get(2))); // true

and не вычисляет второй предикат, если первый ложен. or не вычисляет второй, если первый истинен. Поэтому перестановка предикатов с побочными эффектами может изменить наблюдаемую работу, даже если булево выражение кажется симметричным. Для чистых условий композиция удобна именно тем, что результат определяется аргументом.

Поставщик позволяет отложить вычисление запасной строки до выбора ветви:

java.util.function.Supplier<String> fallback = () -> {
    System.out.println("fallback");
    return "none";
};
boolean needsFallback = false;
String result = needsFallback ? fallback.get() : "ready";
System.out.println(result); // ready, fallback не вызван

Создание поставщика не выполняет его тело. Условие выбирает ветвь; при needsFallback = true тот же клиент напечатает fallback, затем none. В прежней проверке предикатов and также выбирал необходимость второго вызова по первому результату. Типы обоих действий допускают эффекты; выполнится ли эффект, зависит от выбранного пути вызова.

У Function метод andThen сначала применяет текущую функцию, затем следующую; compose — сначала переданную, затем текущую. Например, Function<String, Integer> length = String::length и length.andThen(n -> n * 2) дают для "Java" число 8. Имена показывают порядок, а совместимость типов проверяется компилятором. Для Function<T, R> следующий шаг имеет форму Function<? super R, ? extends V>: он принимает полученный R и выдаёт значение, подходящее для результата V. Поэтому andThen возвращает Function<T, V>. Обе переданные функции должны отличаться от null. При вызове составленной функции исключение первого шага прекращает цепочку; исключение любого выполненного шага передаётся вызывающему коду.

Возврат функции позволяет разнести аргументы по двум вызовам. Например, Function<Integer, Predicate<Student>> rules = threshold -> atLeast(threshold); сначала получает порог, затем полученный предикат принимает участника. Такую форму передачи аргументов по одному называют каррированием. Вызовы можно записать в отдельных строках:

java.util.function.Function<Integer, java.util.function.Predicate<Student>> rules =
    threshold -> atLeast(threshold);
var check80 = rules.apply(80);
System.out.println(check80.test(new Student("s4", "Jo", 79))); // false
System.out.println(check80.test(ann)); // true

apply(80) вызывается один раз; test вызывается дважды с разными участниками. Оба применения используют порог 80. Запись rules.apply(80).test(ann) содержит оба момента в одном выражении и даёт булев результат. Во время первого вызова участника ещё нет. Общие типы сохраняют эту границу: Integer относится к созданию правила, Student — к его последующему применению.

Сигнатура абстрактного метода ограничивает и проверяемые исключения. Function<String, String> не позволяет напрямую передать действие, которое может выбросить IOException: у apply нет соответствующего throws. Для такого действия можно выбрать собственный интерфейс с нужным throws, обработать исключение на правильном уровне или вынести ввод-вывод из преобразования. Договоры отказа описаны в Глава 21. Библиотечное составление действий в конвейер — в Глава 20.

19.9 Вычисление и эффект

Правило отбора только читало балл. Переданное действие также может печатать или менять объект. Эффект — наблюдаемое действие помимо возвращённого значения. У знакомого Book метод title() читает название, borrow() помечает книгу выданной, а borrowed() сообщает её состояние:

static String label(Book book) {
    return "Book: " + book.title();
}
static void announceAndBorrow(Book book) {
    System.out.println(label(book));
    book.borrow();
}

Для новой, ещё не выданной книги предскажите вывод трёх следующих вызовов:

Book book = new Book("Java");
String text = label(book);
System.out.println(book.borrowed());
announceAndBorrow(book);
System.out.println(book.borrowed());

Вывод — false, затем Book: Java, затем true. label вычислил строку, оставив книгу прежней. Второй метод напечатал строку и изменил общий Book; вызывающий код видит новое состояние. Вычисление всех строк отчёта можно завершить до начала печати. Такое разделение называют функциональным ядром и внешней границей эффектов. Оно позволяет проверять результат без печати и заранее знать, когда начнётся внешний вывод. Тип результата void не является единственным признаком эффекта: метод, возвращающий значение, тоже способен менять память или печатать.

19.10 Независимая проверка правила отбора

Переданное действие можно проверить на одном объекте, не выполняя полный алгоритм. Для порогового предиката граница особенно важна: участник с 79 баллами должен дать ложь, с 80 — истину, с 81 — истину. После этого отдельная проверка select подтверждает, что обход сохраняет порядок подходящих элементов и не изменяет состав источника. Результаты этих проверок позволяют различить ошибку условия и ошибку его применения в обходе.

Для преобразования имени проверяют другой результат: действие принимает участника и возвращает строку. Оно не должно случайно вернуть код лишь потому, что оба компонента имеют тип String. Компилятор проверяет форму действия, но предметное соответствие «это именно имя» остаётся обязанностью программы. Параметры типов позволяют проверять совместимость данных, однако одинаковый тип двух полей не доказывает правильность их использования.

Если метод принимает два интерфейса с одинаковой формой абстрактного метода в разных перегрузках, непосредственная лямбда может быть неоднозначной. Одинаковая сигнатура не позволяет выбрать один из двух интерфейсов. В таком случае заранее объявленная переменная нужного типа или явное приведение устраняет неоднозначность. При проектировании собственного API лучше не вводить такие перегрузки без необходимости: удобство вызова зависит не только от короткого тела лямбды, но и от ясного целевого типа.

Сохранение действия не гарантирует одинаковый результат всех его вызовов. Предикат может читать текущее время, обращаться к изменяемому полю внешнего объекта или зависеть от содержимого захваченного списка. Для постоянного аргумента ответы тогда могут различаться. Такая операция иногда нужна, но её зависимость надо назвать в соглашении. Чистое преобразование зависит от аргумента и не изменяет внешнее состояние; оно проще для повторного использования, составления конвейеров и проверки.

Если действие разрастается, его выделяют в именованный метод. Клиент по-прежнему передаёт это действие, а проверка отдельно показывает аргументы, результат и возможный отказ.

19.11 Передача поведения в Java и Python

Само действие можно хранить в переменной и передавать другому действию. В Java до лямбд компараторы и обработчики событий уже передавались объектами интерфейсов. В описании Project Lambda 2013 года цель сформулирована как удобное представление кода данными; сохранение функциональных интерфейсов позволяло использовать существующие библиотеки. Отдельные структурные типы функций обсуждались, но команда выбрала интерфейсы, уже встроенные в систему типов Java [7]. Существующий метод, принимающий такой интерфейс, может получить и лямбда-реализацию.

В Python Protocol описывает для анализатора структуру подходящего объекта (Структурный контракт операций). Договор правила отбора задаёт операцию вызова __call__. Полный файл selection.py:

from dataclasses import dataclass
from typing import Protocol

@dataclass(frozen=True)
class Student:
    id: str
    name: str
    score: int

class StudentRule(Protocol):
    def __call__(self, student: Student, /) -> bool: ...

def select(source: list[Student], rule: StudentRule) -> list[Student]:
    return [student for student in source if rule(student)]

class AtLeast:
    def __init__(self, threshold: int) -> None:
        self.threshold = threshold
    def __call__(self, student: Student, /) -> bool:
        return student.score >= self.threshold

students = [Student("s1", "Ada", 90), Student("s2", "Lin", 70),
            Student("s3", "Ann", 80)]
rule: StudentRule = AtLeast(80)
passed = select(students, rule)
print([student.name for student in passed])  # ['Ada', 'Ann']

Python AtLeast не наследует StudentRule: анализатор принимает его по совместимой форме вызова. / обозначает позиционный аргумент; имена параметров не добавляют требование к вызывающему коду. Обычная функция с той же сигнатурой тоже подходит. Класс с декоратором dataclass служит сравнительной моделью на готовых допустимых данных; Java-нормализация и проверка входа остаются у канонического grade.Student и загрузчика.

Отдельный неверный клиент возвращает строку вместо bool:

def wrong(student: Student, /) -> str:
    return student.name

# В отдельном negative.py с объявлениями Student/StudentRule/select:
bad: StudentRule = wrong  # checker отвергает несовместимый результат
print([s.name for s in select(students, bad)])

При прямом запуске Python-аннотации не выполняют такую проверку: непустое имя истинно в условии списка, поэтому при выполнении программа выведет все три имени ['Ada', 'Lin', 'Ann']. Объект с операцией __call__ допускает вызов. Предметный смысл результата определяется реализацией и её договором. Команды и выбор анализатора: Переданные операции и Protocol. Точное основание callback Protocol. В Java объект условия реализует номинальный StudentTest, анализатор Python принимает AtLeast по структуре, а интерпретатор вызывает доступную операцию.

Передаваемое действие не обязано быть математически чистой функцией. Оно может читать внешнюю настройку, печатать, изменять объект или бросать исключение. Функциональный интерфейс задаёт вход, результат и допустимые проверяемые исключения; остальные условия нужно назвать отдельно. В нашем отборе правило только читает устойчивые компоненты Student: результат зависит от входных значений, а исходный каталог не меняется.
