# Инструкции для автора и агента

Текущий технический объём задаёт согласованное поручение владельца.
[Реестр решений](docs/refactoring-plan.md), [методика](docs/authoring-methodology.md)
и [образцы](docs/authoring-examples.md) помогают сохранить принятые продуктовые
и учебные договоры; исторические сроки и стартовые поручения не возобновляются.
Весь код, включая стартеры, эталоны и тесты, пишет технический исполнитель;
учебный автор задаёт цели и обязательный договор при отдельной работе над содержанием.
Print/Cloud не входят в текущую техническую работу.

При изменении стоимости сборки измеряйте всю цепочку прямых и косвенных
вызовов на реальном курсе. Малый пример не подтверждает ускорение курса;
неизменные проверки повторяются только при новом основании.

## Организация работы

Сохраняйте чужие рабочие деревья, незакоммиченные изменения и открытые PR.
У файла и публичного договора в одной фазе один владелец; автор и независимый
рецензент — разные исполнители. Параллельные проверки используют отдельные
временные каталоги, outputs, Compose projects, порты и state; запись в общий
output или DB согласует владелец. Число участников определяется независимостью
пакетов и ресурсами машины.

Разрешены `gpt-6.1-sol` и `gpt-6.1-terra` с явно назначенным усилием.
Координатор, критичные договоры и независимая рецензия — Sol/high;
ограниченная механика по устойчивому договору — Sol/medium; Sol/max — только
ключевая архитектура и её независимая рецензия. Terra применяется к ограниченной
служебной работе с проверкой Sol/high. Standard сохраняется; глобальную
конфигурацию моделей и режим скорости самостоятельно не меняйте.

Проверяйте изменённое поведение через содержательные публичные договоры,
реальных производителей и потребителей и существенный отрицательный сценарий.
Независимый рецензент читает дельту и проверяет существенные гарантии.
Обязательный TDD для каждой правки, квитанции допуска, чтение полных стенограмм
и самопроверка сообщений не требуются. Исторические планы, START и
`docs/superpowers` — справочные источники, а не активные инструкции.
Собственных `SKILL.md` в этих репозиториях нет; дополнительные навыки
не создаются и не требуются. Чужие навыки в зависимостях не редактируйте.
Предыдущие назначения сохранены в истории
[матрицы](https://github.com/BSU-RFCT-Afonenko-Courses/Java/blob/f5d97be630c92f187f78ac9903b3c48ec03f9c99/docs/agent-execution-proposal-20261029.md);
они не возобновляют старые очереди и условия допуска.

## Среда и границы

Используйте системные инструменты из PATH. На Arch Task поставляется пакетом
`go-task`; исполняемый файл — `go-task` (например, `/usr/bin/go-task`),
наличие команды `task` не предполагается. Запуск системного `tsc` и доступность системного TypeScript Compiler
API проверяются отдельно; для Compiler API нужны реальное AST-преобразование
и запуск установленного CLI, одного `tsc --version` недостаточно.

Учебные материалы Java и System Practice — фиксированные входы технической
работы. Изменение условий, учебных целей, обязательного API и весов заданий
требует отдельного содержательного поручения. Действующие гарантии
public/full, полномочий, capability/token/currentness/expiry и физических путей
сохраняются. Используйте публичные API и минимальные адаптеры.
Действия на VM и перенос, исправление или пересчёт старых оценок требуют
отдельного прямого разрешения владельца; текущий перенос ограничен
пользователями и правами. Прежнюю установку и данные сохраняйте.

## Язык

Новые README, документацию и описания PR пишите по-русски по
[общему языковому правилу](https://github.com/Afonenko-Course-Tools/quarto-course/blob/main/docs/russian-language-policy.md).
Команды, идентификаторы API, пути, имена пакетов и URL сохраняйте буквально.

Общие Quarto extensions устанавливаются штатными `quarto add/update` по версии;
установленные `_extensions` хранятся в Git. Исходные зависимости инструментов
закрепляются Git submodules. Собственный manifest, resolver, lock, installer
или gate для управления зависимостями курса не вводится.
